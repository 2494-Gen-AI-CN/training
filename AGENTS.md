# Project agent memory

Committed home for project-intrinsic knowledge: build, test, authoring rules and sharp edges that should travel with the code. `CLAUDE.md` points here.

## What this repo is

Prep repo for the 11-week **2494 Gen-AI Python** training. Two deliverables per day: the live demo walkthroughs the trainer performs (trainer-only, D-0055) and a GitHub Pages site (`docs/`) with notes, quizzes and exercises. `harness/` is the agent-driven pipeline that produces them. Trainer-only walkthroughs, runbooks and solutions live in a separate private repo cloned at `trainer/` (gitignored); the trainer's live demo repo (public `2494-Gen-AI-CN/demos`) is cloned beside it at `demo-repo/` (gitignored) and holds the answer key of every walkthrough as one commit per block on the week's prep branch.

## Status and decision log (read first)

- `STATUS.md` is the single "what's next" surface: phase, milestones, open items. **Read it at session start** and update it in the same commit as any milestone or open-item change. Its Phase line and its Milestones and Open items tables are parsed by the work tracker; `tests/test_status.py` pins their shape (5-column open-item rows, IDs O-1..O-n, a readable date in "Needed by" wherever one exists). The Phase line is one short paragraph: where things stand now, then `Next, in order:` with the steps separated by semicolons; history goes in the Log, never the Phase line.
- `tracker.html` (repo root, open it from disk; D-0035) is the at-a-glance view of all of it: every teaching day by artifact, week plans, alarms, milestones, open items, codify stages, demo threads, workflow runs, decisions. It is generated, never hand-edited, and LOCAL ONLY: gitignored so trainees do not see it (D-0036). Never `git add` it (not even with `-f`); on a fresh clone `python harness/build_tracker.py` creates it.
- `decisions/README.md` is the newest-first index of every on-the-fly decision (schedule, scope, API currency, naming). **Read it at session start.** Never redo or undo a logged decision; supersede it with a new entry.
- Any change to `harness/curriculum.json`, `harness/metrics.json`, `harness/config.json`, `harness/critics/*.md`, or the calendar (dates, holidays) requires an entry: `python decisions/new.py "Decision" --why "..." --affects "..."` and the printed ID (`D-NNNN`) goes in the commit message. `tests/test_decisions.py` enforces the format.
- Run `python harness/drift_check.py` before every push (D-0052): decisions index against files, stale markers, untracked files, taught days without a delivery record, a stale tracker, notes links. Exit 1 means fix before pushing.

## Rules

- `harness/curriculum.json` is the single source of truth for weeks, days, slugs and status. Never hand-edit the WEEKS block in `docs/index.html`; run `python harness/build_index.py`. Day status runs `planned` -> `authored` -> `live` (D-0052); `taught` implies live. `authored` = every artifact exists and passed its critic, the page is written but not linked (`build_index.py` links `live` only). Writers: the Wire step of `day-fanout.js` writes `authored` or `live` from `releaseOnWire`, `release_week.py` flips `authored` -> `live`, `close_day.py` writes `taught`. A live day is never downgraded. `demoFormat` is `walkthrough` (the day has one or two demo blocks) or `none` (D-0055).
- Calendar dates derive from `startDate` + week index + weekday slot, with `holidays` turning slots into `kind: "holiday"` (D-0013, D-0014). Never hand-type a date into a page, prompt or template; use `build_index.slot_date` / `args_for.py`. `day` is the weekday slot (1=Mon … 5=Fri); the feedback form is the last teaching day of each week, derived, never a JSON flag.
- Paths are always `{week.dir}/{day.slug}` (e.g. `week-01/day-2-orientation-agile-and-git`) across `exercises/`, `trainer/`, `docs/weeks/`, `harness/research/`; the one per-week folder is `trainer/{week.dir}/demos/` (the walkthroughs, D-0055). The short `id` (`w01d2`) is only for `<meta name="tc-day">`, localStorage keys and test keys.
- Week plan first (D-0034): no day of a week is authored before `harness/plans/week-WW.md` exists and passes `python harness/plan_check.py <plan>`. It is written once per week by `harness/workflows/week-plan.js` from `python harness/args_for.py <week> --plan --today <date>` (the only source of its args; tiers `week-plan` / `week-plan-critic`, D-0032) and holds the Weekly Epic, the Threads block table (one row per walkthrough block, D-0055), the demo ladder, the per-day shape, the series sections the trainer's README is generated from (Stop points, Squeeze priorities, Hard-stop rule, Scaffold bundle, Run prerequisites), the anti-spoiler and deviation ledgers and the coverage map. `args_for.py <week> <day>` is BLOCKED without it and passes the day's rows (`weekPlanRows`, `blockRows` with `startsFrom` and the stop point, `ladderRows`, `dayShape`) into the day workflow; `args_for.py <week> --demos` passes the week's blocks into `demo-series.js`; `--no-plan` is the logged escape (warning on stderr; record every use in STATUS.md with the reason). An authored or live day's rows are recorded as-is; week N+1's plan starts from week N's last block.
- Exit criteria (D-0063): Revature's per-group Required / Preferred / Stretch rows are the mock-interview and exam bar at each group's exit and a harness input from week 3. Source of truth is the markdown drop zone `Curricula/Exit-Criteria/qc-N-<slug>.md` (lowercase; one file per group; a missing file means "not published yet"); `harness/exit_criteria.py` parses it at runtime (`show <group|week>` prints ids and text, `check`, `json`, `audit <week>`), and `harness/curriculum.json` `exitCriteria` registers the six groups (qc1 weeks 1–2 … qc6 week 11) and `fromWeek` (change via a decision entry). Ids are positional (`qc2.sql.R07` = group, section, tier letter, row within tier), so a published group's file is append-only: never delete or reorder a row once its page is live. From `fromWeek` every week plan ends with `## Exit criteria map` (`| ID | Tier | Criterion | Day | Where | Notes step |`, checked by `plan_check.py`): every criterion of the week's group exactly once, Day = a day id of this week (Where = the walkthrough that exercises it, `facilitation` or `notes-only`; Notes step required on Required rows), `week NN` later = deferred to a later week of the group (never on the group's last week), `week NN` earlier = taught by that week's plan. `args_for.py` passes the group as `exitGroup` and the rows as `exitRows` per day and per block; `day-fanout.js` `exitCtx(d)` reaches the research, depth, notes and runbook authors and critics (never the exercise prompts), `demo-series.js` gives each block its rows. Binding items: notes critic 21 (every mapped criterion answerable from the page, every Required one in a "Say it in an interview" callout or Check yourself item, goals modal written from the Required rows, `.lede .meta` carries `<span class="exit"><a href="../../exit-criteria/<group>.html#<day id>">Exit criteria</a></span>`), demos critic 13 (a block exercises every row whose Where names it), research 7c (Interview questions bullets end with the id), runbook item 4 (Objectives ends with the "Exit criteria mapped to today" table); the Wire step realigns the map's Notes step from the author's `exitStepMap`. Learner pages: `docs/exit-criteria/` (index + one page per published group, self-check boxes in localStorage, links to live day pages only) are GENERATED by `python harness/build_exit_pages.py` (`--check` in tests and inside `build_index.py --check`); `build_index.py`, `release_week.py` and `close_day.py` rebuild them, so never hand-edit them. Weeks 1–2 are before `fromWeek`: their plans carry a backfilled map (links only, no re-author) from `harness/plans/exit-audit-qc1.md`. `--no-plan` gives empty rows and vacuous critic passes; STATUS.md records every use.
- Projects (D-0065): learner-facing spec sheets for the official projects (P0–P2) and the 1–4 day sprints live in the markdown drop zone `projects/` (`official/P<n>-<slug>.md`, `sprints/YYYY-MM-DD-<slug>.md`; grammar and templates in `projects/README.md`) and are GENERATED into `docs/projects/` by `python harness/build_projects.py` (`--check` in the tests, in `build_index.py --check` and in `drift_check.py`; never hand-edit the pages). A sprint is the week's hackathon (`config.json learnerRepo.layout.hackathon`; a second sprint in a week hands in under `<week-dir>/hackathon/<slug>/`). `build_index.py` reads the specs for the calendar only (🏁 pill on sprint due days and official checkpoint days, a span bar per sprint; a broken spec is skipped with a warning and is a HARD drift finding). `draft` official specs render but are not listed or marked (hidden like `authored` days, D-0052). DELIBERATELY decoupled from the day pipeline: no prompt, critic, plan_check or `args_for.py` reads `projects/`; project pages never link day or exit-criteria pages and day pages never link project pages (`tests/test_projects.py`). Specs never name a trainee; pairings live in the private Trainer-Notes.
- Authoring is research-first: no notes page, demo or runbook is written before `harness/research/<week>/<day>.md` exists. Gate level (`full` | `light`) is per day in the curriculum. Full-gate briefs verify every URL; light-gate briefs still need version stamps and 3 official-doc URLs.
- Demos (D-0055, superseding the key-file contract of D-0030): a demo IS the walkthrough the trainer performs live for one demo block (an AM or PM slot, 30–180 min, 4–12 steps), `trainer/week-WW/demos/NN-<slug>.md` (template `harness/templates/demo-script.md`: title line, five blockquote header fields, Hand-typed during demo, Stub manifest, Presenter cheat-sheet, `## Step n — title (M min)` steps with `cwd:` lines and typed fences, `### Talking points while typing`, `> **Pre-empt — "..."**` answers, `Check (expected output)` fences, Common pitfalls, What we did NOT cover (intentional), End-of-demo wrap-up, Sequence pointer), numbered 01.. across the week in ladder order. Its answer key is the demo repo (`config.json` `demoRepo`) at the block's commit on the week's prep branch (`demoRepo.prepBranch`, `prep/week-WW`): one commit per block, authored by `harness/workflows/demo-series.js`; the trainer types live on `main`. No `key/` files, nothing published to the learner site: the notes pages carry no demo card, demo list or code popup, the only demo link on the site is the topnav link to the public demo repo. `python harness/demo_check.py <file or week folder>` is a FORMAT check only (names, header fields, Time = sum of step minutes within `metrics.demos`, cheat-sheet rows = steps, cwd lines, closing sections, the last step's `git commit -m "<the Thread line's message>"`, typed-line cap); the demos critic runs the block's commit. `trainer/week-WW/demos/README.md` is the series README, GENERATED by `python harness/series_readme.py <week>` from the plan (never hand-edited; `--check` in the release gate). Concept subtopics get a timed `## Facilitation` block in the runbook, not code; `demoFormat: none` marks a day with no block at all.
- Demo threads (D-0033, D-0055): most blocks are rungs of one demo codebase that grows across days and weeks (thread `p0-ticket-desk` for weeks 1–5, one per project block; `config.json` `threads.<id>.repoDir` is where it lives in the demo repo). Every walkthrough's Thread line names the thread, the block's commit message and the block it starts from (`cold` for the first block of the scope or after a cold restart); a block EXTENDS the previous block's commit and never re-types or re-scaffolds what an earlier block built (demos critic item 12). Blocks are authored strictly in ladder order by `demo-series.js` (a block that leaves no commit blocks the later blocks of its thread). Re-authoring an earlier block means re-authoring every later block of the thread on the prep branch. The close (`close_day.py`) diffs the room's commits against the prep commits; folding classroom reality back into a walkthrough and the prep branch is a hand step.
- Demos are a separate weekly run (D-0055): `python harness/args_for.py <week> --demos --today <date>` then `Workflow({ scriptPath: "harness/workflows/demo-series.js", args })` (per block: author on tier `demos`, humanize, critic on `demos-critic`, up to 3 passes; then one series-review critic, `series_readme.py`, Record, Verify). It needs the week plan and every day's research brief (research-first stands). Notes, exercise and runbook (`day-fanout.js`) no longer wait for it: the runbook points at each block (`## Demo: NN-<slug>.md`, path, Time, commit, room state, the plan's stop point) and the exercise reads the walkthroughs for context; notes pages name no walkthrough and no trainer path. Push the prep branch by hand after the run (`git -C demo-repo push -u origin prep/week-WW`).
- `harness/config.json` `audience` is the learner persona (D-0048, superseding D-0023): recent CS grads with no industry experience whose backgrounds vary, so assume only general programming ideas from any language and no Python, Git, terminal or CS theory. It reaches every author/critic prompt as "Audience" with its `assumeKnown`, `assumeNotKnown` and `rule`. No notes page claims the reader knows something from outside the course: `metrics.notes.assumptionPhrases` is checked by `notes_check.py --phrases`, and notes critic item 20 also fails an idea used before its home day without a one-line explanation. The guard covers notes pages only (D-0049); demos, runbooks and exercises are outside it for now. Week-level `notes` carry the week arc (what each day assumes from the previous one); day-level `notes` carry a day's shape. Change any of them via a decision entry.
- `harness/config.json` `models` maps each workflow stage to a model/effort tier (D-0026); `null` inherits the session model. A repass numbered ≥ `escalateOn` runs on the `escalate` tier. Tune it from the flag counts at retrospectives, via a decision entry.
- `exerciseKind` per day: `pytest` (default: starter fails, solution passes) or `rubric` (D-0025: hands-on deliverable, acceptance checklist and rubric in `exercises/<rel>/README.md`, trainer marking guide at `trainer/<rel>/solutions/RUBRIC.md`, no starter/ or tests/).
- Learner repo (D-0051, supersedes D-0037): every trainee has one PUBLIC repository `2494-Gen-AI-CN/<FirstnameLastname>` (the nameRule tolerates `-` and `_`), created in the W1D2 Git exercise and kept for the whole course; `harness/config.json` `learnerRepo` is the one place that records its name rule and layout: exercise hand-ins under `<week-dir>/<day-slug>/`, the week's hackathon deliverable under `<week-dir>/hackathon/` (week 1 due Fri 2026-10-16), an optional code-along copy at `code-along/<week-dir>/<day-slug>/` (never marked), `scratch/`. It reaches the exercise and runbook authors and critics as `learnerCtx` in `day-fanout.js`; no exercise asks for a new or personal-account repository (exercise critic item 10, Rubric-kind item 9). The trainer's live demo repo is `config.json` `demoRepo` (public `2494-Gen-AI-CN/demos`, cloned at `demo-repo/`, gitignored).
- Notes pages are reference and study material (D-0040), not a recap of the room: `metrics.notes` sets the bar (4500–7000 prose words, 6–10 steps with h3 subsections, one "Say it in an interview" callout per teaching step, a closing "Check yourself" step, inline citations `sup.cite` to `li#src-N`, a "Sources checked" stamp copied from the brief). Prose never refers to the classroom (`metrics.notes.deliveryPhrases`; broad strokes about what the demo thread builds are fine) and every fact comes from the brief, whose `## Notes depth` section (per subtopic: interview questions, adjacent concept, trade-off, recognise-on-sight, sourced claims) is written by the research agent, never by the notes author. `python harness/notes_check.py <page> --counts --phrases --stamps --citations [--links]` is the one checker (author, humanizer, notes-verify agent, critic, tests, drift check); `--all-live` covers every live page and `--all-authored` every authored or live page (the drift check and the release gate use the latter, D-0052). `python harness/args_for.py <week> <day...> --notes-only` re-authors pages alone (research depth, then notes). Every stage tier in `config.json` `models` is pinned; none inherits the session model.
- Every notes page gets a `humanizer` pass (plugin skill `humanizer:humanizer`, file mode) after the author and before the critic (D-0029), one `section.step` per Edit and proven prose-only by `harness/prose_guard.py` in html mode (D-0040); critic item 18 in `harness/critics/notes.md` fails AI-sounding prose. Hand-edited notes prose gets the same pass and the same guard (`prose_guard.py git <page>`) before commit.
- The trainer's delivery wording gets the same pass (D-0039): in `demo-series.js` a humanize agent rewords each walkthrough after its author and in `day-fanout.js` one rewords the runbook after the runbook author, before their critics. Prose only: `harness/prose_guard.py` (`snapshot` / `check <dir>` in the workflow, `git` for a hand pass against HEAD) fails when a fenced block, inline code span, heading, the walkthrough header block, `cwd:` line, table, bold label, URL or bullet count moved. Keep contrasts that correct what the room really assumes ("review comments, not taste"); the humanizer flattens them when applied by rule. A hand edit to a runbook or a walkthrough's wording runs `prose_guard.py git` and `demo_check.py` before commit. "What we did NOT cover" bullets read `- <topic>: <where it goes>. <reason>.` (`demo_check.py`).
- Quality bars live in `harness/metrics.json`; critic PASS criteria live in `harness/critics/*.md`. Change those files, not the prompts, when the bar moves.
- Workflow scripts cannot read files or call `Date()`. Generate args with `python harness/args_for.py <week> <day...>` and pass them to `Workflow({ scriptPath: "harness/workflows/day-fanout.js", args })`. A week is authored as one batch (D-0038): pass the week's teaching days in one invocation (`args_for.py 1 3 4 5`); research runs in parallel, demos strictly in day order, materials in parallel; a single day stays valid. Target: week N fully authored by the close of week N-1. A week authored before its Monday lands as `authored` (`args_for.py` emits `releaseOnWire`, true from the week's Monday) and is released on the Friday before by `release_week.py` (D-0052). A run that covers more than one day ends its Demos phase with the series-review critic (D-0053): one agent reads the plan and every demo script in ladder order, flags only, no fix loop. The week plan runs once per week before its first day: `python harness/args_for.py <week> --plan --today <date>` then `Workflow({ scriptPath: "harness/workflows/week-plan.js", args })` (≤5 agents: author, critic, one repass of each, Record). Practice tasks come after the batch, from `args_for.py <week> --practice` and `--practice-build` into `harness/workflows/practice-tasks.js` (D-0047).
- Work tracker (D-0035, D-0036): `python harness/build_tracker.py` writes `tracker.html` = the committed, data-free shell `harness/templates/tracker.html` + a data block read from disk (curriculum, plans, briefs, `trainer/`, notes pages, `STATUS.md`, `docs/process/codify-plan.md`, `decisions/`, `harness/runs.jsonl`, `harness/last-tests.json`). Run it after ANY change to those; `tests/test_tracker.py` fails while the local file is stale (and skips where it was never built). Change the page's look or logic in the template, never in the generated file. `build_index.py`, `close_day.py`, `decisions/new.py` and `log_run.py` rebuild it themselves, and the workflows do it in their Wire/Record steps, so the hand case is mostly an edited `STATUS.md` or trainer file. It reads no clock: alarms (previous-Friday readiness, thresholds in `config.json` `tracker`) are computed in the browser. It needs `trainer/` present.
- Delivery cadence (D-0052): close each teaching day the next morning, release next week on Friday, run the drift check before every push. The checklist is `docs/process/delivery-close.md`. `authored` is hidden only in the sense of unlinked: GitHub Pages still serves the file at a guessable URL, so it is not access control.
- Run log (D-0035): every workflow run appends one record to `harness/runs.jsonl` through its own Record agent (`harness/log_run.py add`). The script cannot see its run id or usage, so after each run the session completes the record: `python harness/log_run.py amend --last --run-id wf_... --minutes M --tokens T --tiers-verified yes|no` (verify tiers from the agent transcripts, never from config), plus `--resolved yes --note "..."` when flagged items were fixed by hand. Never edit `runs.jsonl` by hand.
- No backend. Quiz, survey, theme and page-view state are localStorage only. Page views (D-0044): `docs/assets/js/theme.js` sets `html[data-view]` (`compact`, `focus`; absent is Full; Compact until the reader picks one) before first paint and injects the Full / Compact / Focus switch into `.topbar-right`, so a day page needs no markup for it; the view rules in `style.css` stay inside `@media screen` (`tests/test_view_modes.py`). Any `FDE_`, `workers.dev` or `2463` string in `docs/` is a leak from the reference site and fails `tests/test_assets.py`.
- Python that runs in the page (D-0042, D-0043, D-0045; W1D4 only so far, O-17). Runnable examples: `<pre data-run="python">` marks a complete script, with `data-continues` when it builds on the runnable block above it. Practice tasks: `div.ix-task` blocks (`data-id`, `data-title`, `data-q`, a `pre.task-starter` and a hidden `pre.task-tests` of plain asserts, one check per assert, its message is the label shown) inside one `<section class="practice" hidden>` before Check yourself; the model answers are `trainer/<rel>/solutions/practice.py`, and `tests/test_assets.py` runs the page's checks against the starters (must fail) and the answers (must pass) through the same Python runner the browser gets. The checks are tested themselves from `trainer/<rel>/solutions/practice_cases.py` (per task: other right answers, and wrong answers each paired with the label of the check that must catch it): every right answer passes, every wrong answer is caught by its check, and every check on the page is failed by at least one wrong answer. Change a task's text or checks and its cases in the same commit; `python -m unittest discover -s tests -p test_assets.py -k PracticeTaskTests -v` runs just these. `docs/assets/js/widgets.js` draws both, `docs/assets/js/pyworker.js` runs the code in Pyodide, and the editor is CodeMirror 5. The two jsDelivr URLs (Pyodide in `pyworker.js`, CodeMirror in `widgets.js`) are the site's ONLY external origins, each pinned to an exact version (`tests/test_assets.py`); the widget names the runtime's Python version, which can trail `config.json` `python`. It is on for every reader since 2026-10-13 (D-0045; the `?run=1` gate is gone) and shows wherever a page carries the markup, which is W1D4 only so far. No fallback: a load or worker failure is shown as it is. The notes author writes none of this: the practice section is generated by the practice stage (D-0047, next rule) and the `data-run` attributes are still added by hand. Port 8000 may be taken on the trainer machine; preview with `python -m http.server 8123 --bind 127.0.0.1 --directory docs`.
- Practice tasks are a stage of their own, run after a week's days are authored (D-0047); the notes author never writes them. `harness/practice/<week-dir>/<day-slug>.json` is the one source of a page's tasks, and the page's `section.practice` is GENERATED from it: `python harness/practice_tasks.py insert <week> <day>` writes it before Check yourself, `practice_tasks.py check` and `tests/test_practice.py` fail while page and file differ, and the Wire step of `day-fanout.js` runs `insert`, so a re-authored page gets its tasks back. Never edit that section by hand. Three steps, each by a different hand. (1) Suitability: `python harness/args_for.py <week> [day...] --practice --today <date>`, then `Workflow({ scriptPath: "harness/workflows/practice-tasks.js", args })`. One assessor per authored page decides, for every teaching step, whether a task fits the runtime and the page (`harness/critics/practice.md`: standard library only, no `input()`, no packages, one file, a check sees names and return values and never printed output) and writes proposals to the file; the page is not touched. `partial` and `none` are honest verdicts. (2) The trainer decides: the session runs `python harness/practice_tasks.py show <week>`, puts each day's proposals in front of the trainer and records the answer with `practice_tasks.py approve <week> <day> t1 t3` (or `--all`, `--none`). Never approve on the trainer's behalf; `--practice-build` is refused while a proposed task has no answer. (3) Build: `python harness/args_for.py <week> [day...] --practice-build --today <date>`, same workflow. Per day an author fills `q`, `starter` and `tests` for the approved tasks, writes `trainer/<rel>/solutions/practice.py` (one model answer per task) and `practice_cases.py` (other right answers, and wrong answers each paired with the label of the check that must catch it), runs `insert` and `python harness/practice_tasks.py verify <week> <day>`; a critic judges against `critics/practice.md`; up to 3 passes, then the day is flagged. A flagged day is fixed by hand or taken back off the page (`approve --none`, `insert`, remove its two trainer files) before commit. The stage is not done until the browser pass (next rule) is green for every built day. Tiers `practice-suitability` and `practice`; bars in `metrics.json` `practice`; run kind `practice` in `runs.jsonl`.
- Changing tasks by hand, and the browser pass (D-0043, D-0047). A hand change goes in the day's file under `harness/practice/` (never in the page), with `practice.py` and `practice_cases.py` in the same commit; then `practice_tasks.py insert` and `practice_tasks.py verify <week> <day>` (one day) or `python -m unittest discover -s tests -p test_assets.py -k PracticeTaskTests -v` (every page). Last, after every build and every hand change: the browser pass, driven by the agent session with its browser tools (Claude in Chrome), because the contract tests run under CPython and a learner runs Pyodide behind an editor and a button: start `python harness/practice_browser.py <week> <day>` in the background (it re-checks every case under CPython, then serves `docs/` on `127.0.0.1:8124` with the cases and the driver; nothing is written to either repo), open the URL it prints, run `await (await import("/__practice_browser.js")).default()` in the page with the JavaScript tool, and read the JSON: `ok` must be `true`, which means every case behaved in the real page as it did under CPython. A `false` lists under `problems` what the page showed; fix the task, its cases or the widget, then run `verify` and this pass again. Stop the server, then record the pass in the STATUS.md log (runs, seconds, browser, runtime). If the browser tools are not available, say so and leave the item open: the step is not skipped. Run `verify` and this pass again after any change to `docs/assets/js/widgets.js` or `pyworker.js`.
- `Reference-Example/` is read-only inspiration (nested git clones). Never `git add` it.

## Commands

- Interpreter: the project Python is 3.15 (`harness/config.json` `python`, README). On the trainer's Windows machine the bare `python` on PATH is 3.12; 3.15 is the `py` launcher's default (`py --version`). Run every `python ...` command below as `py ...` there (or work from a 3.15 venv: `py -3.15 -m venv .venv`). The harness and the tests spawn their children with `sys.executable`, so the interpreter you start with is the one they use. A fresh 3.15 needs `py -m pip install -r requirements-dev.txt` and the week packages (`numpy`, `pandas`, `matplotlib`) once; a suite run that fails only in `test_exercises.py` for week-2 days is a missing package, not a broken exercise.
