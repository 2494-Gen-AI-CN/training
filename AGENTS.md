# Project agent memory

Committed home for project-intrinsic knowledge: build, test, authoring rules and sharp edges that should travel with the code. `CLAUDE.md` points here.

## What this repo is

Prep repo for the 11-week **2494 Gen-AI Python** training. Two deliverables per day: live code-along demos (`demos/`) and a GitHub Pages site (`docs/`) with notes, quizzes and exercises. `harness/` is the agent-driven pipeline that produces them. Trainer-only runbooks and solutions live in a separate private repo cloned at `trainer/` (gitignored).

## Status and decision log (read first)

- `STATUS.md` is the single "what's next" surface: phase, milestones, open items. **Read it at session start** and update it in the same commit as any milestone or open-item change. Its Phase line and its Milestones and Open items tables are parsed by the work tracker; `tests/test_status.py` pins their shape (5-column open-item rows, IDs O-1..O-n, a readable date in "Needed by" wherever one exists).
- `tracker.html` (repo root, open it from disk; D-0035) is the at-a-glance view of all of it: every teaching day by artifact, week plans, alarms, milestones, open items, codify stages, demo threads, workflow runs, decisions. It is generated, never hand-edited, and LOCAL ONLY: gitignored so trainees do not see it (D-0036). Never `git add` it (not even with `-f`); on a fresh clone `python harness/build_tracker.py` creates it.
- `decisions/README.md` is the newest-first index of every on-the-fly decision (schedule, scope, API currency, naming). **Read it at session start.** Never redo or undo a logged decision; supersede it with a new entry.
- Any change to `harness/curriculum.json`, `harness/metrics.json`, `harness/config.json`, `harness/critics/*.md`, or the calendar (dates, holidays) requires an entry: `python decisions/new.py "Decision" --why "..." --affects "..."` and the printed ID (`D-NNNN`) goes in the commit message. `tests/test_decisions.py` enforces the format.

## Rules

- `harness/curriculum.json` is the single source of truth for weeks, days, slugs and status. Never hand-edit the WEEKS block in `docs/index.html`; run `python harness/build_index.py`.
- Calendar dates derive from `startDate` + week index + weekday slot, with `holidays` turning slots into `kind: "holiday"` (D-0013, D-0014). Never hand-type a date into a page, prompt or template; use `build_index.slot_date` / `args_for.py`. `day` is the weekday slot (1=Mon … 5=Fri); the feedback form is the last teaching day of each week, derived, never a JSON flag.
- Paths are always `{week.dir}/{day.slug}` (e.g. `week-01/day-2-orientation-agile-and-git`) across `demos/`, `exercises/`, `trainer/`, `docs/weeks/`, `harness/research/`. The short `id` (`w01d2`) is only for `<meta name="tc-day">`, localStorage keys and test keys.
- Week plan first (D-0034): no day of a week is authored before `harness/plans/week-WW.md` exists and passes `python harness/plan_check.py <plan>`. It is written once per week by `harness/workflows/week-plan.js` from `python harness/args_for.py <week> --plan --today <date>` (the only source of its args; tiers `week-plan` / `week-plan-critic`, D-0032) and holds the Weekly Epic, the Threads rung table, the demo ladder, per-day shape, the anti-spoiler and deviation ledgers and the coverage map. `args_for.py <week> <day>` is BLOCKED without it and passes the day's rows (`weekPlanRows`, `threadRows` with `startsFrom`, `ladderRows`, `dayShape`) into the day workflow; `--no-plan` is the logged escape (warning on stderr; record every use in STATUS.md with the reason). A live day's rows are recorded as-is; week N+1's plan starts from week N's last rung.
- Authoring is research-first: no notes page, demo or runbook is written before `harness/research/<week>/<day>.md` exists. Gate level (`full` | `light`) is per day in the curriculum. Full-gate briefs verify every URL; light-gate briefs still need version stamps and 3 official-doc URLs.
- Demos (D-0030): a demo IS the walkthrough script the trainer types live, `trainer/<rel>/demos/NN_<slug>.md` (template `harness/templates/demo-script.md`); the committed code is its answer key under `trainer/<rel>/demos/key/` (`NN_<slug>.py` runnable, or `.md` transcript for terminal demos). `python harness/demo_check.py <that dir>` enforces the format and the both-ways check (every typed line is in the key, every key line was typed). Nobody writes to the public `demos/<rel>/` by hand: `harness/publish_demos.py <week> <day>` copies `key/` there and flips the notes demo card only once the day carries `taught: "YYYY-MM-DD"` in `curriculum.json` (set by the delivery-day close). Concept subtopics get a timed `## Facilitation` block in the runbook, not code; `demoFormat: none` marks a day with no code demo at all (no demos stage, no demo card).
- Demo threads (D-0033): most demos are RUNGS of one demo codebase that grows across days and weeks (thread `p0-ticket-desk` for weeks 1–5, one per project block). Every script header carries `Thread:` and `Starts from:` (`cold` or the previous rung's key path); a rung's `.py` key is the thread's whole runnable end state (the one canonical copy) and the script types only what the rung adds; `demo_check.py` accepts carried lines and requires a dropped or rewritten carried line to appear in a ```python replaced block. Authoring order inside a thread is strictly rung order (the `Starts from` key must exist on disk). Re-authoring day N means re-checking every later rung (`tests/test_demos.py` ThreadChainTests fails them loudly). A delivery-day close that changes a key (classroom reality wins) runs BEFORE the next rung is authored. Single-file keys only until a later stage adds folder keys.
- Demos are authored before notes/runbook/exercise; those three refer to demos by objective and to answer-key files only where the contract allows (code popups, runbook pointers).
- `harness/config.json` `audience` is the learner persona (recent CS grads, no industry experience; D-0023). It reaches every author/critic prompt as "Audience". Week-level `notes` carry the week arc (what each day assumes from the previous one); day-level `notes` carry a day's shape. Change any of them via a decision entry.
- `harness/config.json` `models` maps each workflow stage to a model/effort tier (D-0026); `null` inherits the session model. A repass numbered ≥ `escalateOn` runs on the `escalate` tier. Tune it from the flag counts at retrospectives, via a decision entry.
- `exerciseKind` per day: `pytest` (default: starter fails, solution passes) or `rubric` (D-0025: hands-on deliverable, acceptance checklist and rubric in `exercises/<rel>/README.md`, trainer marking guide at `trainer/<rel>/solutions/RUBRIC.md`, no starter/ or tests/).
- Learner repo (D-0037): every trainee has one private repository `2494-Gen-AI-CN/<FirstnameLastname>`, created in the W1D2 Git exercise and kept for the whole course; `harness/config.json` `learnerRepo` is the one place that records its name rule, layout (exercise hand-ins under `{week.dir}/{day.slug}/`, code-along in one folder per demo thread, `scratch/`) and hand-in. It reaches the exercise and runbook authors and critics as `learnerCtx` in `day-fanout.js`; no exercise asks for a new, personal-account or public repository (exercise critic item 10, Rubric-kind item 9). The trainer's demo-thread repo `team-repo` is a different repository and keeps its name.
- Notes pages are reference and study material (D-0040), not a recap of the room: `metrics.notes` sets the bar (4500–7000 prose words, 6–10 steps with h3 subsections, one "Say it in an interview" callout per teaching step, a closing "Check yourself" step, inline citations `sup.cite` to `li#src-N`, a "Sources checked" stamp copied from the brief). Prose never refers to the classroom (`metrics.notes.deliveryPhrases`; broad strokes about what the demo thread builds are fine) and every fact comes from the brief, whose `## Notes depth` section (per subtopic: interview questions, adjacent concept, trade-off, recognise-on-sight, sourced claims) is written by the research agent, never by the notes author. `python harness/notes_check.py <page> --counts --phrases --stamps --citations [--links]` is the one checker (author, humanizer, notes-verify agent, critic, tests, drift check); `--all-live` covers every live page. `python harness/args_for.py <week> <day...> --notes-only` re-authors pages alone (research depth, then notes). Every stage tier in `config.json` `models` is pinned; none inherits the session model.
- Every notes page gets a `humanizer` pass (plugin skill `humanizer:humanizer`, file mode) after the author and before the critic (D-0029), one `section.step` per Edit and proven prose-only by `harness/prose_guard.py` in html mode (D-0040); critic item 18 in `harness/critics/notes.md` fails AI-sounding prose. Hand-edited notes prose gets the same pass and the same guard (`prose_guard.py git <page>`) before commit.
- The trainer's delivery wording gets the same pass (D-0039): in `day-fanout.js` a humanize agent rewords the day's demo scripts after the demo author and the runbook after the runbook author, before their critics. Prose only: `harness/prose_guard.py` (`snapshot` / `check <dir>` in the workflow, `git` for a hand pass against HEAD) fails when a fenced block, inline code span, heading, script header bullet, `cwd:` line, table, bold label, URL or bullet count moved. Keep contrasts that correct what the room really assumes ("review comments, not taste"); the humanizer flattens them when applied by rule. A hand edit to a runbook or a demo script's wording runs `prose_guard.py git` and `demo_check.py` before commit. "What we did NOT cover" bullets read `- <topic>: <where it goes>. <reason>.` (`demo_check.py`).
- Quality bars live in `harness/metrics.json`; critic PASS criteria live in `harness/critics/*.md`. Change those files, not the prompts, when the bar moves.
- Workflow scripts cannot read files or call `Date()`. Generate args with `python harness/args_for.py <week> <day...>` and pass them to `Workflow({ scriptPath: "harness/workflows/day-fanout.js", args })`. A week is authored as one batch (D-0038): pass the week's teaching days in one invocation (`args_for.py 1 3 4 5`); research runs in parallel, demos strictly in day order, materials in parallel; a single day stays valid. Target: week N fully authored by the close of week N-1. The week plan runs once per week before its first day: `python harness/args_for.py <week> --plan --today <date>` then `Workflow({ scriptPath: "harness/workflows/week-plan.js", args })` (≤5 agents: author, critic, one repass of each, Record).
- Work tracker (D-0035, D-0036): `python harness/build_tracker.py` writes `tracker.html` = the committed, data-free shell `harness/templates/tracker.html` + a data block read from disk (curriculum, plans, briefs, `trainer/`, notes pages, `STATUS.md`, `docs/process/codify-plan.md`, `decisions/`, `harness/runs.jsonl`, `harness/last-tests.json`). Run it after ANY change to those; `tests/test_tracker.py` fails while the local file is stale (and skips where it was never built). Change the page's look or logic in the template, never in the generated file. `build_index.py`, `publish_demos.py`, `decisions/new.py` and `log_run.py` rebuild it themselves, and both workflows do it in their Wire/Record steps, so the hand case is mostly an edited `STATUS.md` or trainer file. It reads no clock: alarms (previous-Friday readiness, thresholds in `config.json` `tracker`) are computed in the browser. It needs `trainer/` present.
- Run log (D-0035): every workflow run appends one record to `harness/runs.jsonl` through its own Record agent (`harness/log_run.py add`). The script cannot see its run id or usage, so after each run the session completes the record: `python harness/log_run.py amend --last --run-id wf_... --minutes M --tokens T --tiers-verified yes|no` (verify tiers from the agent transcripts, never from config), plus `--resolved yes --note "..."` when flagged items were fixed by hand. Never edit `runs.jsonl` by hand.
- No backend. Quiz, survey, theme and page-view state are localStorage only. Page views (D-0044): `docs/assets/js/theme.js` sets `html[data-view]` (`compact`, `focus`; absent is Full; Compact until the reader picks one) before first paint and injects the Full / Compact / Focus switch into `.topbar-right`, so a day page needs no markup for it; the view rules in `style.css` stay inside `@media screen` (`tests/test_view_modes.py`). Any `FDE_`, `workers.dev` or `2463` string in `docs/` is a leak from the reference site and fails `tests/test_assets.py`.
- Python that runs in the page (D-0042, D-0043; pilot on W1D4, O-17). Runnable examples: `<pre data-run="python">` marks a complete script, with `data-continues` when it builds on the runnable block above it. Practice tasks: `div.ix-task` blocks (`data-id`, `data-title`, `data-q`, a `pre.task-starter` and a hidden `pre.task-tests` of plain asserts, one check per assert, its message is the label shown) inside one `<section class="practice" hidden>` before Check yourself; the model answers are `trainer/<rel>/solutions/practice.py`, and `tests/test_assets.py` runs the page's checks against the starters (must fail) and the answers (must pass) through the same Python runner the browser gets. `docs/assets/js/widgets.js` draws both, `docs/assets/js/pyworker.js` runs the code in Pyodide, and the editor is CodeMirror 5. The two jsDelivr URLs (Pyodide in `pyworker.js`, CodeMirror in `widgets.js`) are the site's ONLY external origins, each pinned to an exact version (`tests/test_assets.py`); the widget names the runtime's Python version, which can trail `config.json` `python`. Everything is off unless the URL carries `?run=1` (or localStorage `tc_run` is `1`) until the pilot is switched on. No fallback: a load or worker failure is shown as it is. The notes author writes none of this yet. Port 8000 may be taken on the trainer machine; preview with `python -m http.server 8123 --bind 127.0.0.1 --directory docs`.
- `Reference-Example/` is read-only inspiration (nested git clones). Never `git add` it.

## Commands

- Contract tests: `python -m unittest discover -s tests -v`
- Contract tests, recorded for the tracker (use at the end of a session): `python harness/log_run.py tests`
- Index sync check: `python harness/build_index.py --check`
- Tracker rebuild / sync check: `python harness/build_tracker.py` / `python harness/build_tracker.py --check`; preview another day with `tracker.html?today=YYYY-MM-DD`, a day's detail with `?open=w01d3`
- Exercise contract: `cd exercises/<week>/<day> && python -m pytest -q` must fail; with `EXERCISE_SRC=../../../trainer/<week>/<day>/solutions` must pass.
- Preview site: `cd docs && python -m http.server 8000`
- Cache-bust after CSS/JS edits: `docs/bump-css.sh [--all]`

## Sharp edges

- Node is at `C:\Program Files\nodejs\node.exe`; the nvm shell hook may fail in some shells. Tests that need node skip when it is absent.
- Week 7 curriculum names TFLearn (unmaintained). Research must map each topic to a Keras/TF2 equivalent.
- Weeks 9–10 curriculum names pre-1.0 LangChain/LangGraph APIs (LLMChain, *SequentialChain, RouterChain, ConversationBuffer*Memory, AgentExecutor). Teach the LangChain/LangGraph 1.x equivalents; keep topic names in titles only. `notes` on those weeks in curriculum.json flow into every author/critic prompt.
- Key-gated demos (Anthropic wk 5, Pinecone wk 8, Bedrock wk 9, SageMaker wk 11) are compile-checked only by critics; rehearse them manually.

## Maintaining this file

Keep entries useful to almost every future agent session. Point to the authoritative file rather than repeating it. Prefer rewriting over appending.
