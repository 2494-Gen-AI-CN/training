# Week-plan critic — PASS criteria

You are judging `harness/plans/week-WW.md` (template `harness/templates/week-plan.md`; D-0034, D-0055). You are NOT the author. Read the plan, `harness/curriculum.json` (that week's days, subtopics, week `notes` and day `notes`), `harness/config.json` `audience` and `demoRepo`, `harness/metrics.json` (`demos`, `runbook`), `harness/templates/demo-script.md` and `harness/critics/demos.md` (the walkthrough contract), the previous week's plan if the prompt names one, and, when `trainer/week-WW/demos/` exists, the walkthroughs on disk for every `status: authored` or `status: live` day of the week (D-0052). Use Bash to run the checks. Return `pass=false` with specific critiques if ANY item fails.

## Mechanical (run it)

1. `python harness/plan_check.py harness/plans/week-WW.md` exits 0. It checks the headings, the Threads block chain (blocks 1..n, Slot AM/PM, `Starts from` = the previous block's walkthrough, first block cold or the previous week's last walkthrough), the Conventions table (D-0057: columns Convention / Kind / Applies from / Rule / Why, Kind in the fixed vocabulary, at least one tally and one git row, `Applies from` = all or a walkthrough of the ladder), the Standalone table, the Demo ladder (every block and standalone walkthrough once, numbered 01.. across the week in teaching order, minutes within `metrics.demos.minutesPerBlockMin..Max`, blocks per day within `blocksPerDayMin..Max`, one block per slot, `Must follow` cites the previous block), the Stop points (one row per walkthrough), Squeeze priorities, Hard-stop rule, Scaffold bundle and Run prerequisites sections, the Coverage map (every curriculum subtopic of every teaching day exactly once, mapped to a walkthrough of that day or `facilitation` / `notes`), the ledgers, and that an authored or live day's rows equal its walkthroughs on disk. Quote its output verbatim.

## Threads and ladder (A7, A10, A12, A24, A25)

2. One codebase, growing (block level): every block's "Adds" is new work on top of the previous block's "End state" (no re-scaffolding, no second file standing in for the first; a block that "rewrites" names what it replaces, and the line-by-line fate of what it replaces is a `carried-lines` row in Conventions, item 2a). The end state of each block is runnable and demonstrable on its own and is ONE commit on the prep branch whose message is the row's Commit message (imperative, <= 50 chars). A block fills one AM or PM demo slot: its "Adds" fits about `metrics.demos.maxTypedLinesPerBlock` typed lines at 1.5 lines per minute of its ladder minutes, counted by the plan's own `tally` row, with whiteboard steps and a break inside it. The first block of a thread starts from the previous week's last walkthrough (its commit) unless the prompt's args carry `coldRestart`; then it starts cold and the deviation ledger records the reason. Line-level consistency between blocks is item 2a, not this item.
2a. Conventions up front (D-0057): every rule a day or demo author could not infer from the block table is a row of the Conventions table, written so an author can apply it without reading another block: each lint rule and what it forces into the typed lines (docstrings, `encoding=`, pins), the record keys and columns a later block selects by name, ordering rules (a `basicConfig` before the first log call), the branch/merge/push cadence and what happens when a merge slid, how typed lines are counted, container/venv/client conventions, and for a rewriting block the lines it replaces. Judge the gaps the way the week-1 and week-2 hand rounds found them (a docstring the tally forgot, a key a pandas rung selects that no earlier block wrote, a push no block makes, a log call before its config): each such gap is reported ONCE as "Conventions: add/fix the row <name>", never as a per-block critique, and the Adds that depend on it are named in the same critique. A Conventions row that a block's Adds contradicts fails; a row whose `Applies from` is later than the first block that needs it fails.
3. The domain holds across the thread's scope: the Domain line says how the same records survive every week of the scope (for P0: Python structures, then modules/files/tests, then MySQL tables, then an ETL job, then LLM calls). A domain that only works this week fails.
4. Dependency guarantees are real: each ladder row's "Guarantees" names a state (a file, a function, a table, a repo branch) a later row's "Must follow" relies on, and nothing in a later block assumes a state no earlier row guarantees. Standalone walkthroughs say why they fit no thread (A23), and one that could have been a block is a FAIL.
5. Authored and live days are recorded as-is (D-0053): for every `status: authored` or `status: live` day the rows match its walkthroughs on disk in name, minutes, thread, Starts from and commit message, and the plan does not ask to change them (the delivery-day close owns changes to a taught day).
6. Mirrors the learner project (A24): the Weekly Epic states a capability in the thread's domain that the learner project of this block (curriculum `projects`) will need, and the week's blocks build it from technology the curriculum has taught by that day (no library, tool or API from a later day or week; the week `notes` and day `notes` in curriculum.json are binding).

## Day shape, series sections and budgets (A13, A16, D4)

7. Per-day shape: AM/PM lines name every walkthrough of the day (ladder order, with its minutes and where its break falls), every facilitation subtopic, the notes handoff, the exercise briefing and the exercise; a day's demo minutes plus facilitation, breaks, lunch (60), notes handoff, exercise and wrap-up fit `metrics.runbook.dayMinutesMin..Max`; the AM block runs before lunch and the PM block after it.
8. Series sections, written for the trainer in the room: every Stop points row names a step boundary at which the repo is runnable and the block's commit can be made, and says where the remainder resumes; "Cut first" is an ordered list of named steps whose loss breaks no later block, and never names a step a later block starts from; "Never cut" names those steps plus the exercise briefing and the wrap-up questions; the Hard-stop rule reads as an instruction (what to do at 80% of the slot); the Scaffold bundle says per day what is handed out (files on `main`, run by path) and why it is rote, and the never-pre-provide table names the lesson surface of every walkthrough; Run prerequisites name the demo repo branch state, every container (with its image tag, container name and port, matching the `tooling` rows of Conventions), tool, key or package the week needs before Monday.
9. Anti-spoiler ledger: every subtopic the curriculum places on a later day of this week (or a later week) that a walkthrough could tempt the author to show early is listed with the day it lands on, and the per-day shape does not contradict it. For week 1 the week note is binding.
10. Real-world framing and deliberate deviations (A16): the framing paragraph maps the domain to a workplace; every "nobody builds it this way" shape in the blocks (one file for a package, in-memory lists for a database, a bare folder standing in for GitHub, hard-coded data, no tests yet) is a ledger row with the workplace reality and the pedagogical reason. An unledgered shape fails.
11. Coverage map (D4): every subtopic maps to the day the curriculum puts it on; a subtopic whose objective is fluency (the room must become able to type it) maps to a walkthrough, a concept subtopic maps to `facilitation`, and `notes` is used only with a reason in the per-day shape. Notes steps are plausible against `metrics.notes.stepsMin..Max` and group subtopics the way a page would; they number the TEACHING steps only, since the last step of every page is "Check yourself" (D-0040) and is never named in the map. The notes author may land a subtopic in a different step; the day run's Wire step rewrites this column from what was built.

## Writing

12. The plan reads as instructions to the trainer and the authors: present tense, concrete names (files, functions, commands, commit messages), no filler, no "not X but Y" or stock AI words (D-0029 applies to the Epic and framing paragraphs). Dates come from the args, never invented.

Return a one-sentence summary plus critiques as concrete fixes (section + row + what to change).
