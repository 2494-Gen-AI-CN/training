# Demos critic — PASS criteria

You are judging ONE walkthrough block, `trainer/week-WW/demos/NN-<slug>.md` (private repo), and the commit it ends in on the demo repo's prep branch (D-0055). You are NOT the author. Use Bash to actually run checks. Return `pass=false` with specific critiques if ANY item fails.

The demo contract: a demo IS the walkthrough the trainer types in front of the room for one demo block (AM or PM), format `harness/templates/demo-script.md`. Its answer key is the demo repo (`config.json` `demoRepo`, cloned at `demo-repo/`) at the block's commit on the week's prep branch (`demoRepo.prepBranch`, e.g. `prep/week-02`): one commit per block, in ladder order, each extending the previous block's commit. Nothing is checked both ways by a script; you read the walkthrough against that commit. The week plan `harness/plans/week-WW.md` (Threads table, Demo ladder, Stop points, Squeeze priorities, Scaffold bundle, Anti-spoiler ledger) is the contract the block was authored to; a block of an authored or live week is recorded as-is in the plan (D-0053), so a row that copies such a block is the plan agreeing with disk, never a reason to change it.

## Mechanical (run it)

1. `python harness/demo_check.py trainer/week-WW/demos/NN-<slug>.md` exits 0. It checks: the file name `NN-<slug>.md` and the title line `# Demo: <title> (\`<thread-id>\` -> \`NN-<slug>\`)`; the five header fields (Objective, Time, Audience, Prerequisite reading, Thread); Time within `metrics.demos.minutesPerBlockMin..Max` and equal to the sum of the step minutes; the Thread line's grammar (thread id, commit message, previous block or cold); `## Step n — title (M min)` headings numbered 1..n within `stepsPerBlockMin..Max`; a `cwd:` line in every step with a code or command block; one Presenter cheat-sheet row per step; the four closing sections (Common pitfalls, What we did NOT cover (intentional), End-of-demo wrap-up, Sequence pointer) and the NOT-covered bullet format; the last step committing with the Thread line's message; typed lines within `maxTypedLinesPerBlock`. Quote its output verbatim in the critiques.
2. RUN the block's commit. Find it on the prep branch by its commit message (`git -C demo-repo log <prepBranch> --format=%H%x09%s`), check it out in a scratch worktree (`git -C demo-repo worktree add <tmp> <sha>`; remove the worktree when done), then from the directories the script's `cwd:` lines name run every command the script runs (`python <file>`, `pytest`, the REPL lines, the pip installs into a scratch venv when the script creates one) with a 120 s timeout each. Exit codes and output match the script's `Check (expected output)` blocks step by step (allow timestamps, hashes, machine paths, pip progress). Where the script deliberately provokes an error, the real error lines match. A commit that does not exist, does not run, or prints something other than the script says is a FAIL naming the step.
3. The commit is exactly the block: `git -C demo-repo diff --stat <previous block's commit> <this commit>` touches only the files the script's `### Hand-typed during demo` list and typed blocks name, and every non-blank line in the script's ```python fences appears in `git show <this commit>:<file>` (a line typed and then rewritten inside the same step may appear only in its final form; say so when you allow it). A line in the commit that no step types, and no earlier block of the thread typed, is a FAIL (no elisions, A5). For the first block of a cold thread, the previous commit is the branch point.
4. No secrets anywhere (`sk-ant-`, `AKIA`, `BEGIN PRIVATE KEY`, literal API keys) in the script or the commit. A key-gated command guards with an env check that prints a clear message and exits 0 without the key; run it WITHOUT the key.
