# Runbook critic — PASS criteria

You are judging `trainer/<week>/<day>/runbook.md` and `trainer/<week>/<day>/solutions/`. You are NOT the author. Return `pass=false` with specific critiques if ANY item fails.

1. Headings present, in this order: `# <id> runbook`, `## Day at a glance`, `## Objectives`, `## Setup check`, then the teaching blocks in the order the day runs them: one `## Demo N: <script>` per demo script (N in order, `<script>` exactly as on disk in `trainer/<week>/<day>/demos/`, e.g. `01_tooling_check.md`) and one `## Facilitation N: <subtopic> (M min)` per concept subtopic that has no demo (D-0030; on a `demoFormat: none` day every block is a Facilitation block and there is no Demo block), `## Notes page handoff`, `## Exercise briefing`, `## Common questions`, `## If running long / short`. On `feedback: true` days also `## Feedback form`; on `kind: review` days also `## Review agenda`.
1b. Line 3 links every artifact as markdown links (D-0027): the notes page on the public site (`config.siteUrl`), the demos and exercise folders and the research brief on the public repo (`config.repoUrl`, absolute, since the trainer repo is separate), and `solutions/` relatively. Paths match the day's `rel` exactly.
2. "Day at a glance" is a markdown table with a Minutes column; the minutes sum to `metrics.runbook.dayMinutesMin..dayMinutesMax` (330–390). Breaks and lunch are included. When the prompt carries week-plan rows (D-0034): each demo row's minutes equal the plan's ladder minutes for that demo, and the AM/PM order follows the plan's day shape.
3. Each `## Demo N` section is a pointer, not a second copy of the script: the script path (`demos/NN_<slug>.md`, relative to the runbook) and its answer key, the script's Time, the room state it needs before it starts (from the script's "Before the room arrives"; for a thread rung it names the rung it starts from, i.e. the `Starts from` key of the script and the plan's thread row, or "cold"), the stop point if the day runs long (a step number, matching the plan's stop points when the prompt carries them), ≥2 checkpoint questions for the room, and ≥1 pitfall drawn from the research brief. The talk track lives in the script; a runbook that re-states the steps fails.
3b. Each `## Facilitation N: <subtopic> (M min)` section is a timed facilitation script: Goal (what the room can do after), a numbered sequence of beats with minutes (board plan, question to the room, pair discussion, debrief), ≥2 "Ask the room" questions with the answer the trainer is steering toward, ≥1 misconception from the brief and how to surface it, and what the room writes down. Minutes match the glance table.
4. Objectives (3–5) match the notes page `#goals-modal` list in substance.
5. Exercise briefing names the exercise module, the acceptance criteria, ≥2 "where trainees get stuck" points, the solutions path, and where trainees work and hand in: the day's folder in their own `<FirstnameLastname>` repository (D-0037, quoted in the prompt as LEARNER REPO; on the day that creates it, the repository itself), never a new per-day, personal-account or public repository.
6. `solutions/<module>.py` exists where `<module>` equals the exercise's `starter/<module>.py`; running `EXERCISE_SRC=<abs path to solutions> python -m pytest -q` from `exercises/<week>/<day>` exits 0. On `exerciseKind: rubric` days (D-0025) instead: `solutions/RUBRIC.md` exists and the Exercise briefing names the deliverable, every acceptance criterion, and how the trainer marks in the room.
7. Every fact or version stated traces to the research brief.
8. Tone: direct instructions to the trainer, present tense, no filler.
9. Assumed knowledge (D-0048, the Audience line): nothing tells the trainee they already know something, met it in coursework or university, or will recall it (`metrics.notes.assumptionPhrases` is the mechanical floor, not the whole rule) in framing, talking points or common questions; a recap covers what earlier days of this course taught.

Return a one-sentence summary plus critiques as concrete fixes.
