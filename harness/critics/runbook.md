# Runbook critic — PASS criteria

You are judging `trainer/<week>/<day>/runbook.md` and `trainer/<week>/<day>/solutions/`. You are NOT the author. Return `pass=false` with specific critiques if ANY item fails.

1. Headings present, in this order: `# <id> runbook`, `## Day at a glance`, `## Objectives`, `## Setup check`, then the teaching blocks in the order the day runs them: one `## Demo: <walkthrough>` per walkthrough block of the day (`<walkthrough>` exactly as the week plan's ladder names it plus `.md`, e.g. `01-desk-modules.md`, the file in `trainer/<week>/demos/`; AM before PM) and one `## Facilitation N: <subtopic> (M min)` per concept subtopic that has no demo (on a `demoFormat: none` day every block is a Facilitation block and there is no Demo block), `## Notes page handoff`, `## Exercise briefing`, `## Common questions`, `## If running long / short`. On `feedback: true` days also `## Feedback form`; on `kind: review` days also `## Review agenda`. A trailing `## Delivery record (<date>)` section is appended by `harness/close_day.py` after the day (D-0050, D-0055); it is allowed and never judged.
1b. Line 3 links every artifact as markdown links (D-0027, D-0055): the notes page on the public site (`config.siteUrl`), the week's walkthrough folder relatively (`../demos/`), the exercise folder and the research brief on the public repo (`config.repoUrl`, absolute, since the trainer repo is separate), and `solutions/` relatively. Paths match the day's `rel` exactly.
2. "Day at a glance" is a markdown table with a Minutes column; the minutes sum to `metrics.runbook.dayMinutesMin..dayMinutesMax` (330–390). Breaks and lunch are included (a break inside a walkthrough is named in its row, not a row of its own). When the prompt carries week-plan rows (D-0034): each walkthrough row's minutes equal the plan's ladder minutes for that block, and the AM/PM order follows the plan's day shape.
3. Each `## Demo:` section is a pointer, not a second copy of the walkthrough: the walkthrough path (`../demos/NN-<slug>.md`, relative to the runbook), its Time and slot, its commit message on the prep branch (the plan's block row), the room state it needs before it starts (the previous block it starts from and what is on screen and in the repo, or "cold"), the stop point if the day runs long (a step number matching the plan's Stop points row, and where the remainder resumes), ≥2 checkpoint questions for the room, and ≥1 pitfall drawn from the research brief. The talk track lives in the walkthrough; a runbook that re-states the steps fails.
3b. Each `## Facilitation N: <subtopic> (M min)` section is a timed facilitation script: Goal (what the room can do after), a numbered sequence of beats with minutes (board plan, question to the room, pair discussion, debrief), ≥2 "Ask the room" questions with the answer the trainer is steering toward, ≥1 misconception from the brief and how to surface it, and what the room writes down. Minutes match the glance table.
4. Objectives (3–5) match the notes page `#goals-modal` list in substance.
5. Exercise briefing names the exercise module, the acceptance criteria, ≥2 "where trainees get stuck" points, the solutions path, and where trainees work and hand in: the day's folder in their own `<FirstnameLastname>` repository (D-0037, D-0051, quoted in the prompt as LEARNER REPO; on the day that creates it, the repository itself), never a new per-day or personal-account repository.
6. `solutions/<module>.py` exists where `<module>` equals the exercise's `starter/<module>.py`; running `EXERCISE_SRC=<abs path to solutions> python -m pytest -q` from `exercises/<week>/<day>` exits 0. On `exerciseKind: rubric` days (D-0025) instead: `solutions/RUBRIC.md` exists and the Exercise briefing names the deliverable, every acceptance criterion, and how the trainer marks in the room.
7. Every fact or version stated traces to the research brief.
8. Tone: direct instructions to the trainer, present tense, no filler.

Return a one-sentence summary plus critiques as concrete fixes.
