## Hard-stop rule

If a walkthrough reaches 80% of its slot with half its steps still ahead, stop at its clean stop point above: paste the kept lines of the unreached steps from the walkthrough into their files so the room's files equal the block's end state, run what the end state needs (in a BigQuery block the `bq` command that loads or builds the tables the next block reads; in a Python block the `docker exec` of a pasted `sql/` file that writes MySQL, such as 04's `sql/changes.sql`, and nothing that writes BigQuery), make the block's commit, and resume the unreached steps where the Stop points table says. Resuming means the trainer walks the pasted lines with the room and runs the unreached console, `bq`, REPL or shell steps there. A BigQuery console or `bq` step never resumes inside a Python block, and a Python step never inside a BigQuery block. Only a day-end merge into `main` and its push may slide to the next morning's first step. Never double-speed a code-along: a lost trainee cannot catch up, and every later block depends on this one being understood, not just present.

## Real-world framing and deliberate deviations

At a small software company the support desk's database answers one ticket at a time, and the support lead's questions (how long tickets take to close per priority, which customers' plans bring the most work, which agents carry the load) come from a warehouse that a data engineer feeds every night. A job copies the day's rows out of the production database into a landing area, a staging dataset keeps them as they arrived, a transform cleans them and records what it refused, and a star schema keeps history so a report about last quarter still shows last quarter's customer plans. The job logs every run, can run again after a failure without doubling anything, and loads only what is new. A professional team runs that job in an orchestrator on a schedule, lands files in Cloud Storage, keeps the warehouse in an organisation's project per environment with billing, alerts and group-based access, and writes its models in a tool that tests and versions them. This week builds the small version of each piece in one Python file and a few SQL files against a free personal sandbox, and ledgers every shortcut below so the trainer can name it in one sentence when the room asks.

| Deviation | Workplace reality | Pedagogical reason |
|---|---|---|
| the job runs by hand with `python etl.py` | an orchestrator (Cloud Composer or Airflow, Cloud Scheduler with Cloud Run) runs it on a schedule and retries it | scheduling is no curriculum subtopic, and the sandbox has no Data Transfer Service and no scheduled queries |
| the extract writes files on the laptop and loads them from there | files land in a Cloud Storage bucket (the lake or landing zone) and load jobs read `gs://` paths | a sandbox project has no billing, so it has no bucket; the files on disk show the same hand-off |
| the four reference tables are copied whole on every run | change data capture (Datastream, Debezium) or `updated_at` watermarks move only changed rows | four small tables reload in seconds; the incremental lesson is shown once, on `ticket_events` |
| `star.sql` recreates every dimension but `dim_customer` and the whole fact on every run | incremental MERGE statements or incremental models in a tool such as dbt | the sandbox refuses DML; a full rebuild of 12 rows is fast and adds nothing on a rerun |
| every customer's first version in `dim_customer` starts on `DATE '2026-10-01'`, written into `star.sql` | the first version starts at the first load date or at the source row's own created date | one fixed start date before every event keeps 04's Checks identical on every replay and matches `dim_date`'s first day |
| SCD type 2 is computed in Python over the whole dimension and written back with `WRITE_TRUNCATE` | a MERGE in the warehouse or a snapshot feature of the modelling tool | no DML in the sandbox, and a pure Python function is what pytest can test without BigQuery (P0's rule) |
| `dim_agent` and `dim_ticket` reuse the source ids as their keys | every dimension has a surrogate key the warehouse owns | fewer typed lines; `dim_customer` shows the surrogate key where type 2 needs it |
| the fact's `agent_key` is the ticket's agent at extract time | the agent at the moment of each event, captured in the event record | `ticket_events` keeps the agent only inside its `note` text, and parsing it is not the day's lesson |
| `dim_date` covers only October to December 2026 | a date dimension spans decades, built once | it covers every event the desk has and stays small in the sandbox; the one event 06's `close_ticket` call writes is dated the day `changes.sql` runs, so every replay and class run of 06 must fall inside 2026-10-01 to 2026-12-31 for `questions.sql`'s inner join to `dim_date` to keep that event |
| the bad rows are planted by a hand-out file | bad records arrive from upstream systems and people | the room needs one of each data-quality problem, the same on every laptop |
| one sandbox project per learner on a personal Google account, authenticated as that person | projects per environment in an organisation, jobs running as a service account with workload identity | D-0075: no card, no key file beside a public repo, the week-3 one-laptop pattern |
| datasets shared with a personal account, one at a time | access granted to groups through IAM policy managed as code | one principal shows the roles; P0 partners need exactly one share |
| the external Sheet is public to anyone with its link | a Sheet shared with a named group, read through a service account with Drive scope | every learner can read the same source with no setup |
| `extract.py` reads `SELECT *` with the table name in an f-string | explicit column lists checked against a schema contract | one generic function covers five tables; the names come from a constant, never from input |
| `ticket_desk.py` still saves `tickets.json` on every run and the week-2 pandas report and charts (`frame.py`, `chart.py`) read it beside the warehouse; no week-4 block touches them, although week 3's ledger said this week's job replaces the export | reports read the warehouse, and the application writes no analysis file of its own | the week-1 to week-3 desk stays runnable unchanged and the warehouse questions run in `questions.sql`; the trainer names the replacement in one sentence when 06 wraps up |
| the transform tests use inline rows and nothing tests the job against BigQuery | CI runs an integration test against a disposable test dataset | P0's rule: no test connects to BigQuery; a test dataset per run needs a project per CI job |
| one feature branch per day, merged by the trainer without a pull request | a reviewed pull request before every merge | the demo budget goes to the warehouse; code review stays a notes topic and a week-1 exercise |
| no Cloud Storage export in the sandbox: 05 saves the team result to Google Sheets and a CSV download and imports the Sheet as a native table, and the `bq extract` and `bq load` lines on `gs://` paths are written on the whiteboard and never run | exports and bulk loads go through a Cloud Storage bucket (`bq extract` to `gs://`, load jobs from `gs://`), with the bucket's lifecycle rules and access set by the team | a sandbox project has no billing and so no bucket; the two commands are shown so qc3.bigquery.R06's Cloud Storage half is named exactly, and the Sheets and file routes run for real |
| federated queries and connections are shown on the whiteboard and in the console's source list only: 05 runs no `EXTERNAL_QUERY`, has no Cloud SQL instance and creates no connection (`bq ls --connection` prints none), and the external table reads a Google Sheet in place of Cloud Storage files or Cloud SQL | a connection resource (to Cloud SQL, Cloud Storage or Amazon S3) is created and granted once, and federated `EXTERNAL_QUERY` calls and external tables over the lake read through it | a sandbox project has no billing, so no Cloud SQL instance and no bucket to connect to; the Sheets external table runs the same external-data idea for real, which is what carries qc3.bigquery.P04 on 05-external-data, while P03 and P05 are notes-only |
| `desk_dw.load_rejects` is replaced with `WRITE_TRUNCATE` on every run and carries no run id | a reject table appends one set of rows per run, each with a run identifier that links it to its row in the load log, and is kept for audit | a rerun must not double the rejects and the sandbox has no DML to delete one run's rows; replacing the table keeps it equal to the current staged data, and `load_log`'s `rows_rejected` keeps the count per run |
| `sql/changes.sql`, a committed file, plays the role of production edits (Dana's plan change in 04, the `close_ticket` call in 06) | production rows change through the application and its users, and nobody commits those edits to the analytics repo | the job needs one changed customer and one new event on every laptop and every replay (the event's id and time differ, because the trigger stamps it when the file runs, so no Check records them); a file in the repo is what the demos critic can replay and the room can read |
| week 3's untaught blocks handed over as files (only for the blocks 05 to 10 the W3D4 and W3D5 delivery records show untaught: that block's files fetched from 61d70bf, plus 09's `sql/routines.sql` always, Conventions row `week-3 catch-up`) | a team schedules the dependency before the work that needs it, or the work waits | week 4's rebuild, imports, `close_ticket` call and test counts need them, and week 4's days are fixed; the untaught lessons stay week 3's, read in their notes pages |
| frames built from rows (only if `pyarrow` or `db-dtypes` has no cp315 wheel: `query_frame` wraps `query_rows` in `pd.DataFrame` and `load_frame` loads `frame.to_dict("records")` as JSON) | `to_dataframe()` and `load_table_from_dataframe()` move frames through Arrow, faster and with exact types | Python 3.15 is the course's interpreter (D-0058) and the week cannot wait for a wheel; the same functions keep their names, so `etl.py` and the tests do not change |
