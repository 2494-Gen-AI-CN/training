## Weekly Epic

By Friday afternoon a trainee starts the `desk-mysql` container, rebuilds the `ticket_desk` database from three files in `ticket-desk/sql/` (`schema.sql`, `seed.sql`, `routines.sql`) and can explain every line: seven tables (`priorities`, `customers`, `agents`, `tickets`, `tags`, `ticket_tags`, `ticket_events`) normalised to third normal form with primary, composite, foreign and unique keys, NOT NULL, CHECK, DEFAULT, AUTO_INCREMENT and ON DELETE CASCADE; a trigger that writes ticket history through a stored procedure; two views, a user-defined function and an index. At the mysql client the trainee filters, groups and joins those tables and rewrites a subquery as a join. `python ticket_desk.py` then loads the desk from MySQL through mysql-connector-python as the limited `desk_app` account, prints the open board from the `open_board` view, and `assign_ticket` changes a ticket and its history in one transaction that rolls back whole when the agent does not exist; `pytest` runs 25 tests, six of them against the database, each rolled back. The trainee has typed all of it alongside the trainer in ten walkthrough blocks, one commit per block on a feature branch per day merged into `main` on GitHub. Project 0 needs exactly this: its records in a relational database with integrity rules, a write path that cannot leave half a change behind, and a `ticket_events` history table, which week 4's ETL job extracts into BigQuery.

## Hard-stop rule

If a walkthrough reaches 80% of its slot with half its steps still ahead, stop at its clean stop point above: paste the kept lines of the unreached steps from the walkthrough into their files (the room's files then equal the block's end state), run the block's SQL files so the database matches them (from 05-keys-and-constraints on, the rebuild), make the block's commit, and resume the unreached steps at the place the Stop points table names. Every file the block touches, `README.md` included, is pasted to its end state before the commit, so the room's commit equals its prep key; resuming means the trainer walks the pasted lines with the room and runs the unreached prompt, REPL and shell steps there. A client step never resumes inside a Python block, and a Python step never inside a client block. Only a day-end merge into `main` and its push may slide to the next morning's first step. Never double-speed a code-along: a lost trainee cannot catch up, and every later block depends on this one being understood, not just present.

## Real-world framing and deliberate deviations

At a small software company the support desk's tickets live in a database server that the web app, the agents' tool and the reporting job all use at once. A customer's ticket arrives through a form and becomes a row, an agent picks it up, and the assignment changes the ticket and writes a history row in one transaction so the team lead's board never shows half a change. Keys and constraints stop the app from saving a ticket for a customer who does not exist, a view gives the board one query to read, and a trigger keeps the history whoever changed the row. Production databases run on managed servers, change through versioned migrations, keep credentials in a secrets store, and are reached through a connection pool or an ORM. This week builds the small version of each piece on one laptop, in one container and three SQL files, and ledgers every shortcut below so the trainer can name it in one sentence when the room asks.

| Deviation | Workplace reality | Pedagogical reason |
|---|---|---|
| the root password `desk` sits in the `docker run` line and the README, and `desk_app`'s password `deskapp` is committed in `sql/users.sql` | credentials come from a secrets manager or injected environment, never from git | one shared local password makes every recorded Check match on every laptop; the container holds only the seed rows and runs on the learner's own machine |
| `-p 3306:3306` publishes MySQL on every network interface of the laptop | a database port is bound to `127.0.0.1` or a private network only | it is the week note's `docker run` line; the trainer names `-p 127.0.0.1:3306:3306` as the safer form in a talking point |
| the container is started by a hand-typed `docker run`, with no Compose file | a `compose.yaml` in the repository starts the database and the app together | the flags are Monday's lesson (image, container, port, volume); Compose is no curriculum subtopic |
| Monday's tables have no keys or constraints and Tuesday loads a duplicate ticket 1 into them | no team creates a table without a primary key | the duplicate is the problem Wednesday's keys solve, felt before it is named |
| `seed.sql` writes every id, and `insert_ticket` (06) inserts `ticket.ticket_id` into the AUTO_INCREMENT `ticket_id`, so the client picks the primary key (the REPL's ticket 7 pushes the counter to 8) | the database assigns the id: the app inserts without `ticket_id` and reads the new id back with `cursor.lastrowid` | `Ticket` takes its id in its constructor since week 1, and fixed ids keep the seed and every recorded Check identical; 05 shows the server-assigned id once (the ticket inserted with no `ticket_id` gets 7) and 08 reads `cursor.lastrowid` for the event id |
| every schema change drops and rebuilds the whole database from `schema.sql` and `seed.sql` | live databases change through versioned migrations (ALTER scripts run once, in order) that keep the data | the desk's data is the seed, so a rebuild returns every block and test to the same start; ALTER is taught on `scratch_notes` |
| `seed.sql` with customer names and emails is committed | real customer data never goes into git; development uses generated fixtures | the six week-2 tickets are invented sample data, and committing them makes every clone rebuild the same desk |
| `SLA_HOURS` in `desk.py` repeats the `priorities` table | one source of truth: the app reads the SLA from the database | `Ticket` keeps validating in Python so the 19 week-2 tests still run without a database; the views read `sla_hours` from the table |
| `tickets.json` is still written on every run and pandas and the charts read it | reports query the database or a warehouse | the week-2 report and charts keep running unchanged; week 4's ETL job replaces the export |
| `desk_app` is granted on `ticket_desk.*` from any host (`'%'`) | grants per table and per action, from a named host or network | Docker's address for the laptop differs from machine to machine; one GRANT line keeps DCL readable |
| database tests run against the one development database and roll back | each test run gets a disposable database (a test container or a CI service) | one container per laptop; the rollback fixture leaves the seeded rows intact |
| `db.connect()` opens a new raw connection per call, with SQL strings in `storage.py` | a connection pool, and an ORM or query builder | raw SQL with placeholders shows the statements an ORM would generate, in the sublanguages the week teaches |
| `main()` only reads; inserts, closes and assignments are shown in the REPL and the tests | an app or API writes on each user action | repeated runs of `python ticket_desk.py` print the same board, so the Check blocks hold |
| SQL is typed at the `mysql>` prompt inside the container | engineers use a GUI client (MySQL Workbench, DBeaver) or their IDE's database tool | the client ships in the image and needs no install; every statement is visible in full |
| one feature branch per day, merged by the trainer without a pull request | a reviewed pull request before every merge | the demo budget goes to SQL; code review stays a notes topic and a week-1 exercise |
