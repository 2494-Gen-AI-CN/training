## Claims (≥ metrics.research.claimsMin; each MUST carry a source on a full gate; light gate: source optional but recommended)

- HNSW (Hierarchical Navigable Small World) is an approximate nearest-neighbour index built as a stack of proximity graphs over nested subsets of the stored vectors, with each element's top layer drawn at random, and its search cost grows about logarithmically with the number of vectors — [Efficient and robust approximate nearest neighbor search using HNSW graphs (Malkov and Yashunin, arXiv:1603.09320)](https://arxiv.org/abs/1603.09320)
- An HNSW search enters the top layer (the longest links), moves greedily to whichever neighbour is closest to the query until no neighbour is closer, then drops to the same vertex one layer down and repeats until it stops on layer 0; it can stop at a local minimum, which is why it is approximate — [HNSW: Hierarchical Navigable Small Worlds (Pinecone learn series)](https://www.pinecone.io/learn/series/faiss/hnsw/)
- More links per vertex (M) and a larger search candidate list (efSearch) raise recall and slow the search; memory is set almost entirely by M — [HNSW: Hierarchical Navigable Small Worlds (Pinecone learn series)](https://www.pinecone.io/learn/series/faiss/hnsw/)
- A single-node Chroma collection uses an HNSW index configured with `configuration={"hnsw": {...}}` at creation; `space` defaults to `l2`, and the settings are `ef_construction` (default 100), `ef_search` (100), `max_neighbors` (16), `num_threads` (CPU count), `batch_size` (100), `sync_threshold` (1000) and `resize_factor` (1.2) — [Configure Collections (Chroma docs)](https://docs.trychroma.com/docs/collections/configure)
- Chroma's three spaces are `l2` (squared L2: Σ(Aᵢ − Bᵢ)²), `cosine` (1 − cosine similarity) and `ip` (1 − Σ AᵢBᵢ); all are distances, so lower is closer — [Configure Collections (Chroma docs)](https://docs.trychroma.com/docs/collections/configure)
- `space`, `ef_construction` and `max_neighbors` cannot change after a Chroma collection is created; `ef_search`, `num_threads`, `batch_size`, `sync_threshold` and `resize_factor` can, through `collection.modify(configuration={"hnsw": {"ef_search": 200}})`; the old `metadata={"hnsw:space": ...}` form "is still supported for backwards compatibility but is deprecated" — [Configuration (Chroma Cookbook)](https://cookbook.chromadb.dev/core/configuration/)
- Chroma collection names must be unique in a database, 3 to 512 characters, start and end with a lowercase letter or digit (dots, dashes and underscores between), with no two consecutive dots and not an IP address; creating a name that exists raises an exception; `get_or_create_collection` returns the existing one; `list_collections` returns up to 100 by default, oldest first; `count` returns the number of records; `peek` returns the first 10; `modify` changes name and metadata; "Deleting collections is destructive and not reversible" — [Manage Collections (Chroma docs)](https://docs.trychroma.com/docs/collections/manage-collections)
- Since Chroma 1.0.0 (2025-03-01) `list_collections` returns `Collection` objects again (0.6.0 had returned names only); since 0.5.11 `get_or_create_collection` on an existing collection ignores any other arguments, `metadata` included — [Migration (Chroma docs)](https://docs.trychroma.com/docs/overview/migration)
- In Chroma, `add` with an id that already exists is "ignored without throwing an error" (to overwrite, update); embeddings whose length differs from the collection's raise an exception; metadata values are strings, integers, floats and booleans, or non-empty arrays of one of those types — [Adding Data to Chroma Collections (Chroma docs)](https://docs.trychroma.com/docs/collections/add-data)
- Chroma's `upsert` adds records whose ids are missing and updates those whose ids exist "as per `update`"; `update` on an id that does not exist logs an error and is ignored — [Update Data (Chroma docs)](https://docs.trychroma.com/docs/collections/update-data)
- Chroma `where` filters take `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte` (numbers only for the four comparisons), `$in` and `$nin` (a list of one type), `$contains` and `$not_contains` (array metadata), and `$and` / `$or` over a list of filters; each filter object holds one field or one logical operator — [Where Filters (Chroma docs)](https://docs.trychroma.com/reference/where-filter)

### Index management
- Interview questions: What is a vector index for, and why not compare the query with every stored vector? - Adjacent concept: recall of an approximate index — the share of the exact top k the index returns, which `### 1.4` measures, is how a team decides whether `ef_search` is high enough.
- Trade-off or limit: an exact (flat) search costs time in proportion to the number of rows; HNSW answers in about logarithmic time but can miss a true neighbour, and higher `ef_search` or `max_neighbors` buys recall with speed and memory — [Efficient and robust approximate nearest neighbor search using HNSW graphs](https://arxiv.org/abs/1603.09320), [HNSW: Hierarchical Navigable Small Worlds](https://www.pinecone.io/learn/series/faiss/hnsw/)
- Recognise on sight: `client.create_collection("random_2k", configuration={"hnsw": {"space": "cosine"}}, embedding_function=None)`; `pc.describe_index("kb-wednesday")`; `pc.configure_index("kb-wednesday", deletion_protection="enabled")`
- Claims:
  - `ef_search` can be raised on a live Chroma collection with `modify(configuration={"hnsw": {"ef_search": 200}})`; `space`, `ef_construction` and `max_neighbors` are fixed — [Configuration (Chroma Cookbook)](https://cookbook.chromadb.dev/core/configuration/)

## Glossary terms (3–8; one-sentence plain-language definitions; aka = alternate surface forms)

- approximate nearest neighbour search | Finding vectors close to a query without comparing it with every stored vector, accepting that a true neighbour is sometimes missed in return for speed. | aka: ANN, approximate search, approximate nearest neighbor search
- HNSW | An index that links each vector to a few near neighbours in several layers and answers a query by walking those links from a starting point at the top. | aka: Hierarchical Navigable Small World, HNSW index, HNSW graph
- upsert | A write that inserts a record when its id is new and replaces the stored record when the id already exists. | aka: upserts, upserted, upserting
- Pinecone namespace | A named partition inside a Pinecone index; every write and query targets exactly one, so records in other namespaces are never seen. | aka: index namespace
- metadata filter | A condition on the fields stored beside each vector, such as category or year, that limits which records a similarity search may return. | aka: where filter, metadata filtering, filter expression
- unit vector | A vector whose length is 1, so comparing two of them depends only on their direction. | aka: normalised vector, normalized vector, length-1 vector
- deletion protection | A Pinecone index setting that refuses every delete request until it is switched off again. | aka: deletion_protection

## Common pitfalls (3–6; feed the runbook "where trainees get stuck" and quiz distractors)

- Reading a Chroma distance as a similarity, or a Pinecone score the wrong way round: Chroma's `cosine`, `ip` and `l2` are all distances (lower is closer), Pinecone's cosine score is a similarity (higher is closer), and Pinecone's `euclidean` score is a squared distance (lower is closer), so `kb-wednesday-l2` sorts its best match with the smallest number.
- Expecting `add` to replace a record: Chroma's `add` ignores an id that already exists without an error, so the four changed texts in `KB_UPDATES` stay old until `upsert`; if the fresh run confirms that the six new ids are written by that same `add`, the count is already 36 before `### 3.2`, and `### 3.2`'s markdown must say the upsert changes four texts and adds nothing (the plan's "30 to 36" then belongs to `### 7.2` only).
- Using a row number or `enumerate` index as the id: the next load of the same articles writes them again under new ids, so every article appears twice and a query returns duplicates; the id comes from the source record (`"kb-004"`).
- Treating a namespace or a filter as free: a Pinecone query reads one namespace only (a question asked in `web` never finds a `mobile` article), while a filter in one namespace still scans every record in it, so a hard boundary such as one customer's data goes in a namespace and a preference such as a category goes in a filter.
- Expecting to change the metric, dimension or Chroma `space` later: none can change after creation in either database, so a wrong metric means a new collection or index; and a vector from another model (the 768-number add in `### 2.2`) raises instead of being stored.
- Copying pinecone examples from the current docs into a notebook pinned to 9.1.0: Pinecone's docs now lead with `pc.indexes.create(schema=..., deployment=...)` and `index.documents.upsert/search` (the Documents API) and call dimension-and-metric indexes "legacy"; the notebook's `pc.create_index(..., spec=ServerlessSpec(...))`, `pc.Index`, `index.upsert(vectors=...)` and `index.query(...)` are the kept shims, and the two styles do not mix on one index.
