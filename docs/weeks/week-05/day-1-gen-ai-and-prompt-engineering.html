Gen AI orientation & prompt engineering: what a model does with your words

Week 5 · Day 1 Mon Nov 9, 2026 Gen AI introduction ~44 min · reference notes @150 wpm · diagram · check Sources checked 2026-11-03 · python 3.15 · pandas 3.0.6 Exit criteria

This page assumes week 4's ticket desk: its tickets, their three priorities and the ETL job that moves them into a warehouse. It teaches what AI, machine learning, deep learning and generative AI are, how a large language model turns a prompt into text, and how to improve a prompt in rounds, from zero-shot through examples, constraints and an instruction block. It ends with hallucinations and the rules for using an assistant safely. Afterwards you can explain generative AI and its common applications, say why one prompt gives two answers, and walk an interviewer through fixing a prompt that went wrong.

Foundations

AI, machine learning and deep learning

Four terms get used as if they meant the same thing: AI, machine learning, deep learning and generative AI. They nest inside each other, and an interviewer often asks you to say how.

What artificial intelligence means

Google's machine learning glossary defines artificial intelligence as "a non-human program or model that can solve sophisticated tasks".1 That covers a lot: a spam filter, a chess engine, a route planner. The same glossary adds that "formally, machine learning is a sub-field of artificial intelligence."1 So a program can count as AI without learning anything, as long as it solves the task.

Machine learning is "the process of training a piece of software, called a model, to make useful predictions or generate content (like text, images, audio, or video) from data."2 A model, in this vocabulary, is "any mathematical construct that processes input data and returns output."1 On this page "model" always means that trained construct. It never means a data model from week 4 or a Python class.

The four terms sit inside each other like circles on a whiteboard:

  • Artificial intelligence is the outer circle: any program or model that solves a hard task, learned or written by hand.
  • Machine learning sits inside it: the part where a model is trained from data.
  • Deep learning sits inside machine learning: training with neural networks that have several layers.
  • Generative AI, "a class of models that creates content from user input", is built mostly on deep learning.2

The glossary admits the last circle is loosely defined. It calls generative AI "an emerging transformative field with no formal definition".1 In an interview, give a working definition and say where it comes from. You will also meet marketing copy that calls a fixed if rule "AI". Under the glossary's wording that is fair, but it is not machine learning, because nothing was trained.

A rule written by a person against a rule learned from examples

Every ticket on the desk carries one of three priorities, high, normal or low, and the priorities table gives them SLA hours of 4, 24 and 72.3 Here is a rule a person wrote after reading the six seed titles:

def triage(title):
    t = title.lower()
    if "500" in t or "frozen" in t:
        return "high"
    if t.startswith("add "):
        return "low"
    return "normal"

for title in ["Login page returns 500", "Invoice PDF is blank", "Typo on pricing page",
              "Checkout button frozen", "Export is missing rows", "Add dark mode"]:
    print(triage(title), "|", title)
high | Login page returns 500
normal | Invoice PDF is blank
normal | Typo on pricing page
high | Checkout button frozen
normal | Export is missing rows
low | Add dark mode

All six agree with the priorities in sql/seed.sql, because the person who wrote the conditions had already seen those six titles. A seventh title such as "Password reset email never arrives" would fall through to normal whether or not that is right.

A learned rule starts from the other end. A team collects last year's tickets with the priority each one was given, and a training program finds the pattern that links titles to priorities. In machine learning terms each ticket is an example, the title is the input, and the priority is the label, "the 'answer' or 'result' portion of an example".1

Learning from examples that carry the right answer is called supervised learning: "Supervised learning models can make predictions after seeing lots of data with the correct answers".2 Google's list of system types puts it beside unsupervised learning, reinforcement learning and generative AI.2

Google's first rule of machine learning addresses this trade-off. It is "Don't be afraid to launch a product without machine learning", because "Machine learning is cool, but it requires data".4 Six tickets is not data, so the hand-written rule is the right first answer here. The same guide warns that "a complex heuristic is unmaintainable",4 which is when a team with hundreds of conditions and years of labelled tickets starts to train a model instead.

Deep learning, in one line

"Neural networks are a family of model architectures designed to find nonlinear patterns in data",5 and "a deep neural network contains more than one hidden layer".1 Deep learning is machine learning done with those deep networks. How they are built and trained is week 6's subject. For now, recognise it on sight: a project that talks about layers, a network and its weights is doing deep learning.

Takeaways
  • AI contains machine learning, which contains deep learning, which most generative AI is built on.
  • A hand-written rule is AI in the broad sense but not machine learning.
  • Supervised learning finds a rule from examples whose labels hold the right answer.
  • Without data, ship the hand-written rule first.
Say it in an interview

A program with hand-written rules does what a person told it, condition by condition. Machine learning trains a model on examples instead, so the rule comes from the data. If a model learned our ticket priorities from titles, the title would be the input and the priority would be the label, and that's supervised learning.

I'd ship a hand-written rule when there isn't much data or the rule is simple. Google's own first rule says don't be afraid to launch without machine learning, and you move to a model once the heuristics get too complex to maintain.

Foundations

Generative AI and how a large language model writes

What generative AI is and what it is used for

"Generative AI is a class of models that creates content from user input."2 The Government of Canada's guide says it "produces content such as text, audio, code, videos and images".6 It adds that "based on the training data, these models generate content that is statistically likely in response to a prompt."6

NIST quotes a United States executive order that calls it "the class of AI models that emulate the structure and characteristics of input data in order to generate derived synthetic content."7

A large language model, or LLM, is the kind that works with text. The Claude glossary says LLMs "are trained on vast amounts of text data and can generate human-like text, answer questions, summarize information, and more."8 Its common applications include:

  • writing and editing documents and emails6
  • answering questions and summarising long text8
  • drafting and explaining code6

Most people meet an LLM through a chat assistant, a web page where you type a prompt and read a reply; Claude is one example.8 Tuesday's page sorts the other ways a developer reaches a model.

Tokens and next-token prediction

A language model "estimates the probability of a token or sequence of tokens occurring within a longer sequence of tokens", and "a token could be a word, a subword (a subset of a word), or even a single character."9 A tokenizer might split the desk title Checkout button frozen into Check, out, button and frozen.

That split is illustrative. How many characters a token covers "depends on the model and the language", and the Claude docs say one newer tokenizer "produces approximately 30 percent more tokens for the same text than earlier models".8

Writing a reply is a loop over tokens:

  1. The prompt is split into tokens.
  2. The model gives every possible next token a probability, given all the tokens so far.
  3. One token is picked and added to the end.
  4. The loop repeats until the reply is finished.

A model trained only on that loop is "pretrained to predict the next word, given the previous context of text in the document", and such models "are not inherently good at answering questions or following instructions".8 Further training, which the Claude glossary names fine-tuning and RLHF, turns that predictor into an assistant.8

The context window: everything the model sees

The context window is "all the text a language model can reference when generating a response, including the response itself". It is separate from the training data, "a 'working memory' for the model".10 When an interviewer asks what the model actually sees, the answer is the window and nothing else. It has never seen the desk's priorities table unless the prompt puts those rows in front of it.

A bigger window holds more, with a limit: "more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as context rot."10 Training also has a date. The Claude models overview lists a "Reliable knowledge cutoff" for every model,11 so a question about a library release newer than that date asks for something the model never learned.

Sampling, temperature and two answers to one prompt

Step 3 of the loop is a weighted dice roll. Picture the model after The checkout button is, with illustrative scores of 0.6 for frozen, 0.3 for stuck and 0.1 for grey. Sampling picks one in proportion to its weight, so stuck wins about three rolls in ten.

"Temperature controls the degree of randomness in token selection." At temperature 0 "the highest probability tokens are always selected", and replies "are mostly deterministic, but a small amount of variation is still possible."12

The Claude glossary adds that "even with temperature set to 0, the results will not be fully deterministic".8 OpenAI states that "the content generated from a model is non-deterministic" and recommends "pinning your production applications to specific model snapshots".13

Two consequences come back on every later page:

  • The same prompt can give two different replies, so a reply printed on this page is an example, never a promise.
  • The loop picks what is statistically likely, and nothing in it looks a fact up, so a fluent reply can be false.
Takeaways
  • Generative AI creates new content shaped like its training data.
  • An LLM writes one token at a time, each picked from a probability distribution.
  • The model sees only its context window and what training left behind.
  • Sampling makes replies vary; predicting likely text makes fluent errors possible.
Say it in an interview

Generative AI is a class of models that create new content, like text, code or images, from a prompt. The common applications are drafting and editing documents and emails, summarising, answering questions, and for developers, explaining and drafting code.

A large language model produces text one token at a time. It looks at everything in its context window, gives every possible next token a probability, samples one, adds it to the end and repeats until the reply is done.

Because each token is sampled, the same prompt can give two answers. And because the model predicts what's likely instead of looking anything up, a reply can sound fluent and still be false, so I check it.

Prompting

Prompt engineering and zero-shot prompting

The rest of the page follows one prompt through four rounds. It asks for a triage rule for the desk's tickets, and each round fixes what the previous reply got wrong.

What prompt engineering is

A prompt is "any text entered as input to a large language model to condition the model to behave in a certain way".1 Prompt engineering is "the art of creating prompts that elicit the desired responses from a large language model."1 OpenAI's guide says it more plainly: "prompt engineering is the process of writing effective instructions for a model".13

The Claude docs list three things to have before you start improving a prompt:14

  • "a clear definition of the success criteria"
  • "some ways to empirically test against those criteria"
  • "a first draft prompt"

That is the same discipline as code and its tests. For the desk, the success criteria are short. Each ticket lands in exactly one of high, normal or low, the choice respects the SLA hours, and every answer carries one reason line a person can check. The test is to run the prompt on real titles and compare the replies with the priorities the desk already gave them.

The same overview warns that "not every success criterion or failing eval is best solved by prompt engineering".14 Sometimes the fix is a different model, or the hand-written rule from step 1. On a team you recognise prompt engineering by its paper trail: rounds of one prompt kept side by side, each with its reply and a note of what changed.

Zero-shot prompting

A zero-shot prompt is "a prompt that does not provide an example of how you want the large language model to respond".1 You state the task and nothing else. It is the first thing anyone types, and it is often good enough for a general question.

Its limit is that the model fills every gap with its own guess. The glossary's own zero-shot example asks for a country's currency, and notes that "Rupee," "INR," and "₹" could all be correct while the format might still matter to you.1 A reply can be right in substance and still useless to the program or person that reads it. You recognise a zero-shot prompt by what is missing: no examples, no constraints, no output format.

Round 1: a triage rule for the desk

Nothing on this page needs an account or a tool. If you have a free chat assistant of your own, you can try these prompts at home; your replies will differ from the printed ones, which were written for this page.

Prompt, round 1 (shown here, never run):

Write a triage rule for our support tickets.

Illustrative reply (written for this page):

Here is a triage rule for support tickets:

P1 (urgent): system down or security issue. Respond within 1 hour.
P2 (high): major feature broken for many users. Respond within 4 hours.
P3 (medium): feature partly broken, workaround exists. Respond within 1 business day.
P4 (low): cosmetic issues and feature requests. Respond within 1 week.

Assign the highest level that applies.

The reply reads well, and it fails all three success criteria:

  • It invents four tiers, P1 to P4, including an urgent tier, where the desk has three priorities.
  • It makes up response times and ignores the desk's real SLA hours: high 4, normal 24, low 72.3
  • It gives a rule with no reason line per ticket, so nobody can check a single decision.

The model saw one sentence, so it answered for a generic help desk. The Claude docs put it this way: "Think of Claude as a brilliant but new employee who lacks context on your norms and workflows."15 They also advise that "if you want Claude to do more than the task strictly requires, explicitly request it rather than relying on the model to infer this from vague prompts."15

So the first fix to a zero-shot prompt is usually context, before examples. Name the three priorities, give their SLA hours, and say what the output should look like: one priority and one reason line per ticket. Saying why helps too, since "providing context or motivation behind your instructions" gives the model "more information about your goals".15

Takeaways
  • Write success criteria and a way to test them before improving a prompt.
  • A zero-shot prompt states the task with no example of the answer.
  • Round 1 invented tiers and hours because the prompt held no context.
  • The first fix is context: the real priorities, their SLA hours and the output wanted.
Say it in an interview

Prompt engineering is writing and refining the text I give a model until it reliably gives the response I need. Before I start, I write down what a correct answer looks like and how I'll test for it, the same way I'd write tests before changing code.

A zero-shot prompt gives the task with no example of the answer. When a one-line triage prompt came back with made-up P1 to P4 tiers, the first thing I added was context: our three priorities, their SLA hours, and the exact output I wanted.

Prompting

Few-shot prompting and constraints

Few-shot prompting

A few-shot prompt "contains more than one (a 'few') example demonstrating how the large language model should respond."1 Google's prompting guide calls them examples you include "to show the model what getting it right looks like."16 A 2020 paper by Brown et al. showed a large language model working "without any gradient updates or fine-tuning", with "few-shot demonstrations specified purely via text interaction with the model".17 The model itself does not change.

The Claude docs call examples "one of the most reliable ways to steer Claude's output format, tone, and structure". They advise 3 to 5 of them, wrapped in <example> tags "so Claude can distinguish them from instructions".15 You recognise a few-shot prompt on sight by its labelled pairs before the question, such as Login page returns 500 -> high.

Round 2: three labelled tickets, three held out

Round 2 adds the context from round 1's fix and three of the seed's tickets, one per priority. One per priority matters: three high examples would show the model only one label. The other three seed titles are held out, so the prompt is tested on tickets it has not seen. That is how a team learns whether its examples generalise.

Prompt, round 2 (shown here, never run):

We triage support tickets into exactly three priorities:
high (respond within 4 hours), normal (24 hours), low (72 hours).

<example>Login page returns 500 -> high</example>
<example>Typo on pricing page -> normal</example>
<example>Add dark mode -> low</example>

Give the priority for each of these tickets:
Checkout button frozen
Export is missing rows
Invoice PDF is blank

Illustrative reply (written for this page):

Checkout button frozen -> high (customers cannot complete a purchase)
Export is missing rows -> normal (the export runs but some data is missing)
Invoice PDF is blank -> high (a customer cannot read their invoice)

The seed gives Checkout button frozen high and Export is missing rows normal, so two of three are right. It gives Invoice PDF is blank normal.3 The model's high is a plausible reading of a broken billing document. The seed's normal is a decision the team made, and no example in the prompt shows it.

Few-shot examples teach format and pattern; they cannot carry a decision they never show. The fix is a rule that lets the model say it cannot tell.

Constraints

A constraint is a rule about what the reply may contain: which words are allowed, how many lines, what to do when the input is not enough. The Claude docs note that "being specific about the output you want can help enhance results."15 For the desk, the allowed words come straight from the priorities table,3 plus one escape hatch:

  • answer with exactly one of high, normal, low, unsure
  • follow it with one reason line
  • answer unsure when the title gives no evidence for a priority

The unsure answer does the most work. Giving a model permission to say it does not know "can drastically reduce false information".18 It also hands the hard case back to the person on the desk, who knows what the team decided.

Round 3: one word, one reason, or unsure

Round 3 keeps round 2 and adds the three constraints before the titles.

Prompt, round 3 (shown here, never run):

We triage support tickets into exactly three priorities:
high (respond within 4 hours), normal (24 hours), low (72 hours).

<example>Login page returns 500 -> high</example>
<example>Typo on pricing page -> normal</example>
<example>Add dark mode -> low</example>

For each ticket, answer with exactly one word from: high, normal, low, unsure.
Then one reason line. Answer unsure when the title gives no evidence.

Checkout button frozen
Export is missing rows
Invoice PDF is blank

The expected output is high, normal and unsure, each with a reason. The third reason should say that the title does not tell whether billing is blocked, so a person decides. Here is an illustrative reply, written for this page:

Checkout button frozen
This is probably high.
Customers cannot finish a purchase.

normal
The export runs but some rows are missing.

Invoice PDF is blank

The title does not say whether the customer is blocked from paying.

The labels are now right, and the first answer still breaks a constraint. A program that reads the reply checks each answer line against the allowed words:

ALLOWED = {"high", "normal", "low", "unsure"}
for line in ["This is probably high.", "normal", "unsure"]:
    print(line in ALLOWED, "|", line)
False | This is probably high.
True | normal
True | unsure

A constraint narrows the reply but does not guarantee it. The fix is the bare word high on its own line, and the next step gets it two ways: an output-format rule and a follow-up turn. Either way, the reply is checked before anything uses it.18

Takeaways
  • Few-shot examples sit in the prompt and change the reply, never the model.
  • Give one example per label and test on held-out titles.
  • Examples cannot teach a team decision they never show.
  • Constraints, including an unsure answer, narrow the reply, and code still checks it.
Say it in an interview

Few-shot prompting puts a few worked examples in the prompt so the model copies their pattern and format. Nothing about the model changes, which is the difference from fine-tuning. I give one example per label and test on inputs that aren't among the examples.

When the examples were right and the model still mislabelled a blank invoice as high, it was because no example showed how our team treats billing. So I added constraints: one word from an allowed list, one reason, and unsure when the title isn't enough. Then I still check every line against that list.

Prompting

Instructions, guidelines, iteration and dialog state

Instructions and guidelines: the block at the top

Google's prompting guide names the parts a prompt can have:16

  • the task, what you want done
  • system instructions, which "get passed to the model before any user input in the prompt"
  • few-shot examples
  • contextual information the model needs, such as the desk's priorities

The block of system instructions is usually called the system prompt. It sets the model's role, its rules and the output format for the whole conversation. "Setting a role in the system prompt focuses Claude's behavior and tone for your use case."15 OpenAI's version is the developer message, "instructions provided by the application developer, prioritized ahead of user messages."13

To test whether instructions are clear, the Claude docs suggest showing the prompt "to a colleague with minimal context on the task" and asking them to follow it: "If they'd be confused, Claude will be too."15 The model weighs instructions; it does not execute them like code. A reply that ignores a rule is possible, so the output is still checked against the rules.18

Round 4: role, audience, rules, output format

Round 4 moves everything that is not a ticket into an instruction block at the top, in four parts. You recognise a team's reusable prompt by this shape: it opens with a role, then rules, then Output format:.

Prompt, round 4 (shown here, never run):

You are triaging support tickets for a small help desk.
Your answers are read by a program first, then by the agent on duty.

Rules:
- The only priorities are high (4-hour SLA), normal (24-hour SLA), low (72-hour SLA).
- Answer unsure when the title gives no evidence for a priority.
- Judge from the title only. Do not invent details about the customer.

Output format, for each ticket:
line 1: the ticket title
line 2: exactly one word: high, normal, low or unsure
line 3: one reason, one sentence

<example>Login page returns 500 -> high</example>
<example>Typo on pricing page -> normal</example>
<example>Add dark mode -> low</example>

Tickets:
Checkout button frozen
Export is missing rows
Invoice PDF is blank

Illustrative reply (written for this page):

Checkout button frozen
high
A frozen checkout stops customers from paying.

Export is missing rows
normal
The export still runs, so work continues while the gap is fixed.

Invoice PDF is blank
unsure
The title does not say whether billing is blocked, so the agent on duty decides.

This reply meets every success criterion, and it is the expected output for round 4. Every second line passes the allowed-words check from step 4, and every answer has a reason a person can argue with. The audience line mattered: once the model is told a program reads the reply, a bare word is the obvious answer.

Dialog state: the whole conversation, every turn

A chat assistant seems to remember earlier turns, and the mechanism is simple. "The Messages API is stateless, which means that you always send the full conversational history to the API."19 Each turn's input "contains all previous conversation history plus the current user message", and each output "becomes part of the input for the next turn".10 The dialog state is the whole conversation, re-sent every time.

TurnWhat the model receives
1instruction block, first message
2instruction block, first message, first reply, second message
3all of turn 2, second reply, third message
new chatonly its own first message

Two things follow. A new chat starts empty, so it knows nothing about yesterday's conversation, and the priorities have to be in its prompt again. A long chat also drifts. Chat interfaces "can also manage the context window on a rolling 'first in, first out' basis",10 so your first instructions can fall out of the window, and long contexts lose accuracy anyway. A fresh chat with a complete prompt often beats a long, patched one.

Iterating with a follow-up turn

Because the previous reply is in the window, a short follow-up can fix one line of it without restating the prompt. The Claude docs list this as "iterative refinement: use Claude's outputs as inputs for follow-up prompts".18 After round 3's reply, a follow-up turn could read:

Prompt, follow-up turn after round 3 (shown here, never run):

Line 2 of each answer must be the bare word only.
Rewrite just the Checkout button frozen answer.

Illustrative reply (written for this page):

Checkout button frozen
high
Customers cannot finish a purchase.

The follow-up names the rule that was broken and the one answer to redo. When a fix needs more than a line or two, write the improved prompt as a new round and start a fresh chat.

Takeaways
  • An instruction block sets role, audience, rules and output format before any ticket.
  • The model weighs instructions, so the reply is still checked.
  • Every turn re-sends the whole conversation; a new chat starts empty.
  • A short follow-up fixes one line; a big fix belongs in a fresh prompt.
Say it in an interview

A system prompt is the instruction block that goes before any user input. I put four things in it: the role, who reads the answer, the rules, and the exact output format. I test it by asking whether a colleague with no context could follow it.

A chat assistant seems to remember because the whole conversation is sent again on every turn. A new chat starts with nothing, and a long chat drifts because old turns can drop out of the context window, so for a big change I start fresh with a complete prompt.

Definitions

Fine-tuning and conditioning

Interviewers like to ask how few-shot prompting differs from fine-tuning, because the two are easy to blur. Training a model is week 6's subject.

Conditioning: steering through the context window

The glossary's definition of a prompt already holds the idea: text entered "to condition the model to behave in a certain way".1 Conditioning means steering a model through what is in its context window. Instructions, examples, the desk's priorities and the previous turns are all conditioning. Every round of the triage prompt was conditioning, and none of them changed the model.

That has a consequence you can see. Conditioning lasts as long as the text stays in the window. Close the chat, open a new one, and the model is back where it started, with no memory of the three priorities.

Fine-tuning: a second training pass

Before fine-tuning there is pretraining, the long first training run in which the model learns to predict the next word from huge amounts of text.8 Fine-tuning comes after it: "a second, task-specific training pass performed on a pre-trained model to refine its parameters for a specific use case."1 The parameters, also called weights, are the numbers the model learned in training. Fine-tuning changes them.

The Claude glossary describes the effect: fine-tuning "causes the model to start representing and mimicking the patterns and characteristics of the fine-tuning dataset".8 You recognise it on sight by its inputs. Fine-tuning has a training file of hundreds of input and output pairs and a training job that runs on it. Conditioning has a prompt with three examples written into its text.

When a team reaches for each

Conditioning (prompting)Fine-tuning
What changesthe input in the context windowthe model's parameters
How many examplesa few, as many as fit in the windowhundreds or more, in a training file
How long it lastsone request or conversationevery later request to that model
Cost to tryminutes: edit the text and run it againa training job, data preparation and evaluation

OpenAI's optimisation guide puts the order plainly: "the prompt engineering process may be all you need in order to get great results for your use case."20 Fine-tuning earns its place when a team needs to "provide more example inputs and outputs than could fit within the context window of a single request".20 The same guide warns that it "can be a time-consuming process", and states that "OpenAI is winding down the fine-tuning platform."20

The desk's triage needs three labels, six titles and one team decision, all of which fit in a prompt. That is why this week uses prompting only.

Takeaways
  • Conditioning steers the model through the context window and lasts one conversation.
  • Fine-tuning is a second training pass that changes the model's parameters.
  • Teams try prompting first and fine-tune only when the examples outgrow the window.
Say it in an interview

Fine-tuning is a second, task-specific training pass on a pretrained model that changes its parameters. Putting examples in a prompt is conditioning: it steers the model through the context window for that request only, and the model itself doesn't change.

I'd start with prompting because it's fast to try. A team fine-tunes when it has far more examples than fit in a prompt and needs the behaviour on every request, and it accepts the cost of a training job and the evaluation that follows.

Judgement

Hallucinations and how to check an answer

What a hallucination is

The Claude docs define a hallucination as text "that is factually incorrect or inconsistent with the given context".18 NIST prefers the word confabulation: "the production of confidently stated but erroneous or false content (known colloquially as 'hallucinations' or 'fabrications')".7 A hallucination is stated confidently, so it reads exactly like a correct answer.

NIST also says why it happens: "Confabulations are a natural result of the way generative models are designed."7 It is part of how the loop from step 2 works, so no prompt removes it for good.

Why a model invents a method

Here is a question a developer on the desk might ask while counting tickets.

Prompt (shown here, never run):

How do I count the tickets per priority in a pandas DataFrame df?

Illustrative reply (written for this page):

Use DataFrame.count_by, which groups and counts in one call:

counts = df.count_by("priority")
print(counts)

The method name is plausible. pandas has count, it has grouping, and count_by reads like the two joined. There is no such method. A model produces one for three reasons:

  • Next-token prediction with no lookup. Models "generate outputs that approximate the statistical distribution of their training data", which "can also produce outputs that are factually inaccurate".7
  • Missing context. The prompt names neither the pandas version nor its documentation, so the model fills the gap.
  • A question past the knowledge cutoff, the date each model's training stops.11

OWASP's list of risks for LLM applications names this exact case for developers: "The model suggests insecure or non-existent code libraries".21 The same entry defines overreliance, when users "place excessive trust in LLM-generated content, failing to verify its accuracy."21

Checking a claim against the docs

The desk pins pandas 3.0.6, so the check goes to the 3.0 reference. Its DataFrame page lists DataFrame.count, "Count non-NA cells for each column or row", and DataFrame.value_counts. It lists no count_by.22 Running the suggested line settles it:

import pandas as pd
df = pd.DataFrame({"priority": ["high", "normal", "normal", "high", "normal", "low"]})
df.count_by("priority")

Python stops with a traceback whose last line is AttributeError: 'DataFrame' object has no attribute 'count_by'.22

The reference's Series.value_counts is the real tool: "Return a Series containing counts of unique values."23 Selecting the column gives a Series, so the fix is one line:

print(df["priority"].value_counts())
priority
normal    3
high      2
low       1
Name: count, dtype: int64

A developer checks any claim about an API or a library in the same three steps:

  1. Ask for the source: which documentation page, for which version.
  2. Check the official docs for that version, and read the entry itself.
  3. Run it, ideally in a test, before it goes anywhere near a commit.

Prompting helps too. The Claude docs suggest three techniques:

  • Allow the model to say "I don't know".
  • Ask for citations that back each claim.
  • Restrict the model to documents you provide.

They are clear that these techniques reduce hallucinations but "don't eliminate them entirely".18

Takeaways
  • A hallucination is confident, false content, and it reads like a correct answer.
  • It comes from predicting likely text with no lookup, missing context or a knowledge cutoff.
  • Check the docs for your version and run the code before trusting a method.
Say it in an interview

A hallucination is content a model states confidently that is false or doesn't match the context it was given. It happens because the model predicts likely text instead of looking anything up, so a method name like count_by can sound exactly like pandas and not exist.

Before I use a model's claim about a library, I find the entry in the official docs for the version we pin, and I run the code. If the docs don't list it, it doesn't go in.

Judgement

Responsible use and security

Everything so far is about getting a good answer. This step is about what you type in to get it, and what you owe the code that comes back.

What never goes into a public chat

Text pasted into a public chat assistant leaves your machine and goes to the tool's supplier, who may keep a copy.6 OWASP's entry on sensitive information disclosure says such information "includes personal identifiable information (PII), financial details, health records", along with security credentials and confidential business data.24 It adds that users "need to understand the risks of unintentionally providing sensitive data".24

The Canadian guide is blunter: "Public servants must not input personal information into publicly available online generative AI tools."6 NIST's data privacy risk covers "leakage and unauthorized use, disclosure, or de-anonymization" of personal or sensitive data.7 On the desk, four kinds of text never go into a public chat:

  • Personal information, such as the customer Dana Whitfield with her address dana@example.com from customers.3
  • Credentials. The desk reads its database password with os.environ["DESK_DB_PASSWORD"] in db.py, so the line that exports it holds a secret.25
  • The employer's code, which goes only to an assistant the employer has approved.
  • Client data, such as a sample of a client's dataset.

Redaction, and why one regular expression is not enough

Redaction means removing names, emails, hosts, users and passwords from text before it leaves your machine. The desk has a helper, desk.redact, documented as "Return the text with email addresses hidden." It replaces every match of its EMAIL pattern with [email].26 Run from the desk's folder, it does less than its name suggests:

from desk import redact

print(redact("Dana Whitfield (dana@example.com): Login page returns 500"))
print(redact("host=127.0.0.1 user=desk_app password=s3cret"))
print(redact("mysql://desk_app:s3cret@db.internal:3306/ticket_desk"))
Dana Whitfield ([email]): Login page returns 500
host=127.0.0.1 user=desk_app password=s3cret
mysql://desk_app:[email]:3306/ticket_desk

The email goes and the name stays. The second line passes through untouched, password included. In the third, the pattern happens to match s3cret@db.internal, so the line looks cleaned while the user name stays.26 Names and connection strings are removed by hand, and the result is read before it is pasted.

Who owns a generated line

The developer who commits a line owns it, whoever typed it first. The Canadian guide makes the user responsible that generated content "is accurate, non-partisan, unbiased, and doesn't violate intellectual property laws".6 It also warns that generative AI "can produce content that is discriminatory or not representative",6 so a review checks for bias as well as bugs. NIST lists "automation bias, over-reliance" among its risks for generative AI.7

In practice, a generated line goes through the same code review and the same tests as any other. On a good team you recognise it in the pull request: a description that says the change was drafted with an assistant, then reviewed and tested by the author, with the tests that ran.

The rules a developer keeps

OWASP recommends user education with "guidance on avoiding the input of sensitive information."24 The rules this week works by come to six:

  • Never paste PII, credentials, keys or client data into a public chat.
  • The employer's code goes only to an employer-approved assistant, never to a public chat.
  • Every generated line is read, tested and owned by the developer who commits it.
  • A claim about an API or a library is checked in its docs.
  • Iterate; never stop at the first answer.
  • Give the model the code, the error, the constraint and the expected output.
Takeaways
  • PII, credentials, the employer's code and client data never go into a public chat.
  • The desk's redact hides emails only; names and connection strings are cleaned by hand.
  • Generated code gets the same review and tests, and its committer owns it.
Say it in an interview

Personal information, credentials and keys, client data and my employer's code never go into a public chat assistant. To make a stack trace safe, I remove the connection string's host, user and password and any names or emails by hand, then read it again before pasting, because an email regex alone misses most of that.

Whoever commits generated code owns it. I read every line, run the tests, and check any claim about a library in its docs, exactly as I would for code a teammate wrote.

Check yourself

Check yourself

Nine retrieval questions, at least one per section. Answer each out loud before you open it.

Is a hand-written if rule for ticket priorities machine learning? What would the label be if a model learned the rule instead?

It is AI in the broad sense, a program solving a task, but not machine learning, because nothing was trained. A learned rule would use past tickets as examples, the title as the input and the priority as the label, which is supervised learning.

What is generative AI, what is it commonly used for, and how does a large language model produce a reply?

Generative AI is a class of models that create new content, such as text, code or images, from user input. Common uses are drafting and editing documents and emails, answering questions, summarising and working with code. An LLM writes one token at a time: it gives every possible next token a probability from what is in its context window, samples one, appends it and repeats.

Why can the same prompt give two different replies, even at temperature 0?

Each token is sampled from a probability distribution, and temperature only controls how random that pick is. Even at temperature 0 the docs say results are not fully deterministic, so a reply is an example, never a promise.

"Write a triage rule for our support tickets." came back with P1 to P4 tiers. Why, and what do you add first?

The model saw one sentence and nothing about the desk, so it guessed a generic help desk. Add context first: the three priorities, their SLA hours of 4, 24 and 72, and the output wanted, one priority and one reason line per ticket.

The few-shot examples are all correct, yet the model labels Invoice PDF is blank high where the desk says normal. Why, and what fixes it?

No example shows how the team treats a billing ticket, and examples cannot teach a decision they never show. A constraint fixes it: exactly one word from high, normal, low, unsure, one reason line, and unsure when the title gives no evidence, so a person decides.

What does a new chat know about yesterday's chat, and why does a long chat drift?

Nothing: the whole conversation is re-sent each turn, and a new chat starts with only its own messages. A long chat drifts because old turns can roll out of the context window and accuracy drops as the window fills.

How is putting three examples in a prompt different from fine-tuning?

Examples in a prompt condition the model through its context window for that request only, and the model does not change. Fine-tuning is a second training pass that changes the model's parameters, used when a team has far more examples than fit in a prompt.

A reply recommends df.count_by("priority"). How do you check it, and what is the fix?

Look it up in the pandas reference for the pinned version, 3.0.6, which lists no count_by, and run it, which raises an AttributeError. The documented tool is Series.value_counts, so the fix is df["priority"].value_counts().

What does desk.redact miss in a stack trace with a connection string, and what never goes into a public chat at all?

It hides email addresses only, so names, hosts, users and passwords stay and must be removed by hand. Credentials and keys, client data and the employer's code never go into a public chat, and personal information goes only after it is redacted.
