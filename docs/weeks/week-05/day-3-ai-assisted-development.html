Gen AI for developers

Generative AI across the development life cycle

Every program in this course has passed through the stages of the software development life cycle: plan, code, test, review, document and maintain. This step asks where a generative AI assistant fits in each stage and what it never takes over. Monday's page closed with a short list of rules for using an assistant, and this page applies one of them throughout: every generated line is read, tested and owned by the developer who commits it.

Nothing on this page needs an account, a key or an install. Each prompt is shown and never run, and each reply is either quoted from an official doc or written for this page and labelled as illustrative. If you have a free chat or editor assistant of your own, you can try the prompts at home. Your replies will differ from the ones printed here, because a model's answer changes between versions and between runs.

Where an assistant helps, stage by stage

GitHub's best-practices page for its assistant lists the jobs it does best:1

  • "Writing tests and repetitive code"
  • "Debugging and correcting syntax"
  • "Explaining and commenting code"
  • "Generating regular expressions"

Laid over the life cycle, those jobs land in every stage, and each stage keeps a part that belongs to a person.

StageWhere an assistant helpsWhat stays the developer's
PlanBreaking a ticket into smaller tasks; listing questions to ask the clientWhat to build, and in what order
CodeBoilerplate and a first draft of a function from a clear requirementThe design, and whether the draft is accepted
TestDrafting test cases and the repetitive setup around themWhich behaviours must be tested, taken from the requirement
ReviewExplaining an unfamiliar change before you read it closelyThe approval and the merge
DocumentA first docstring, a README outline, a plain summary for a managerChecking every sentence against the code
MaintainExplaining old code before you change itThe change itself, and the commit

Thursday's page takes the review stage further, into analysis, refactoring and the security of generated code; this page stays with writing new code, tests and documentation.

What stays the developer's

VS Code's documentation for its AI features is direct about the risk: "AI can produce incorrect code or misunderstand your intent."2 It is just as direct about who carries it: "You remain responsible for deciding which changes reach your codebase."2 It then advises you to "Review the diff and validate the result before you commit or merge changes."2

That is the ownership question an interviewer asks after "do you use AI?": who is responsible for a bug the assistant wrote? The answer is the developer who committed it. The commit carries your name, the reviewer approved your change, and the client sees the desk's behaviour, not the tool that drafted it. GitHub puts the same limit in its own words: the assistant is not meant to "Replace your expertise and skills".1

The trade-off is speed against verification. An assistant writes repetitive code and tests faster than a person types them, but it can also produce a package, a function or a keyword that does not exist. GitHub's review guide tells reviewers to "Watch out for hallucinated or suspicious packages (such as packages that don't actually exist)."3

Using an assistant well: context in, checks out

Monday's prompting rounds showed the first habit: stop zero-shotting. A one-line request leaves the model to guess everything you did not say, and it guesses with confidence. Give it what a new teammate would need on their first morning:

  • the code the answer must fit beside, such as the function that will call it;
  • the full error message when something fails, with the line it points at;
  • the constraint: the Python version, the library pin, the project's style, what must not change;
  • the expected output for two or three concrete inputs, including the awkward ones.

The second habit is the check on the way out. Read every line before accepting it, run the tests, and look up any claim about an API or library in that library's own docs. GitHub's review guide puts the tests first: "Always run automated tests and static analysis tools first."3

You can recognise unowned generated code in a pull request. The author cannot explain a line when asked, or an import names a package nobody added to the project's requirements.

Takeaways
  • An assistant helps at every life-cycle stage, from planning to maintenance.
  • The decision, the review and the commit stay with the developer.
  • Give the model the code, the error, the constraint and the expected output.
  • Read, test and check every generated claim against the docs before committing.
Say it in an interview

I use an assistant across the whole life cycle: to break a ticket into tasks, draft boilerplate and tests, explain code I have not read yet, and write a first docstring. What I never hand over is the decision about what to build, the review, and the commit. If generated code ships a bug, that bug is mine.

To use it well I don't zero-shot it. I give it the surrounding code, the full error, the constraints and a few expected outputs, then I read every line, run the tests, and check any library claim in the official docs before it goes in.

AI pair programming

Pairing with an assistant

Editor assistants are often sold as an "AI pair programmer". The phrase makes sense only once you know what human pair programming is, so this step starts there and then asks which part of the pair an assistant can play.

Driver and navigator

Pair programming is two developers working on one task at one screen. Böckeler and Siessegger's guide names the two roles. "The Driver is the person at the wheel, i.e. the keyboard."4 The driver also explains as they go: "A driver should always talk through what she is doing while doing it."4

"The Navigator is in the observer position, while the driver is typing."4 The navigator "reviews the code on-the-go, gives directions and shares thoughts" and "has an eye on the larger issues, bugs".4

The assistant as a navigator: what it sees and what it does not

An assistant fits the navigator's seat. It watches what you type and offers directions, in the form of suggested code. You stay the driver, with your hands on the keyboard and the final say over every line. The difference from a human navigator is what each one knows.

QuestionA human navigatorAn editor assistant
Does it know the requirement?Yes, from the ticket and the stand-upOnly if the requirement is written in the prompt or an open file
What does it see?The screen, the team's history, the clientThe code around the cursor, open tabs, recent edits
Does it run the code?It can ask you to run the testsNo; only an agent given tools runs commands
Does it change the file?No; the driver typesOnly when you accept a suggestion

GitHub's application card for inline suggestions describes the assistant's view. The prompt is built from "the surrounding code from your cursor position", combined with "code snippets from open tabs in the editor".5 A requirement that lives in a ticket, a meeting or your head is not in that list. If the assistant does not see the rule, its suggestion follows the most likely pattern instead.

The suggestion loop

Suggestions are "only applied to the file or text field if you explicitly accept them."5 So every accepted line is a decision you made. A working loop with an assistant has four moves:

  1. State the intent: a clear function name and docstring, a comment, or a chat message with the requirement.
  2. Read the suggestion line by line, as a navigator would read your code.
  3. Accept it, edit it, or reject it and restate the intent.
  4. Run the tests before moving on.

You recognise the loop on a teammate's screen by dimmed grey text after the cursor, which the Tab key accepts, or by a chat panel open beside the file. Look for a pause between the grey text appearing and the key press. A developer who accepts faster than they could read has skipped the second move.

When to switch it off

Pairing is not always the right mode, even between people. For tasks with many unknowns, the guide says the usual pairing styles "often don't work as well" and suggests a spike, a short time-boxed investigation, or splitting up.4 The same holds for an assistant. Turn suggestions off, or ignore them, in these cases:

  • a design decision, such as how to model a table, where the common pattern may be wrong for your team;
  • unfamiliar code you have not read yet, because you cannot judge a suggestion for code you do not understand;
  • a task with many unknowns, where you need to explore and learn before anyone writes the final code.

Human review stays in the loop either way. GitHub's guide to reviewing AI-generated code notes that "Pairing and team input helps catch subtle issues."3 An assistant is a navigator that has read part of the code; a colleague in review has read the requirement too.

Takeaways
  • The driver types and explains; the navigator reviews and watches the larger issues.
  • An assistant suggests from nearby code and open tabs, never from the unwritten requirement.
  • The loop is state the intent, read, accept or edit or reject, then run the tests.
  • Switch it off for design decisions, unread code and tasks full of unknowns.
Say it in an interview

In pair programming the driver types and talks through what they're doing, and the navigator reviews as they go and watches the bigger picture. An AI assistant plays a kind of navigator: it suggests code, but it only sees what's around my cursor and in my open files, and it never runs anything unless it's an agent with tools.

So my loop is: state the intent clearly, read the suggestion, accept, edit or reject it, then run the tests. I switch it off for design decisions and for code I haven't read yet.

Overview of Copilot

The editor-assistant category: GitHub Copilot and a second example

Tuesday's page sorted the ways a developer reaches a model into four categories: a chat assistant, an editor assistant, an agentic coding tool and API access. This step is the editor assistant, with GitHub Copilot as the main example because its documentation is public and detailed.

What an editor assistant is

An editor assistant is an extension that runs inside the code editor. For Copilot, "For most supported IDEs, the GitHub Copilot extension or plugin is the primary entry point," and it works "using context from your open files and workspace".7 GitHub describes the product as "an AI assistant that helps you write, understand, and ship software".6

The same page splits its features in two. Assistive ones respond as you go: "Copilot responds while you work, suggesting code, answering questions, or explaining code." Agentic ones take a goal: "You describe a goal, and Copilot can work through multiple steps."6 A chat assistant in a browser tab differs in where its context comes from and how code reaches your file.

Chat assistant in a browserEditor assistant
What it seesOnly what you paste into the chatOpen files and workspace context, picked up automatically
How code reaches the fileYou copy it acrossYou accept a suggestion or a proposed edit

Copilot's surfaces in the editor

SurfaceWhat the docs say it does

Next edit suggestions"Get inline suggestions as you type, including suggestions for your next edit."2
Chat"Ask questions about your codebase, compare approaches, and plan complex changes"7
Agent"Ask an agent to find relevant code, edit files, run commands, and validate its work"7

Agent mode is where the editor assistant overlaps with the agentic coding tool category: VS Code says "An agent uses a model and tools to find relevant code, make changes, and run checks."2 It is the one surface that runs commands, so it is also the one whose changes need the closest review.

Chat commands and context variables

The chat panel accepts short slash commands for common requests and hash variables that attach context. You recognise them on sight in a screenshot or a teammate's chat history.

All six rows come from the Copilot Chat cheat sheet.8 The hash variables are how you choose which code goes with the question.

Plans and seats

GitHub lists the plans as Free, Student, Pro, Pro+, Max, Business and Enterprise, and Copilot Student is "Available to verified students."9 An individual can "Use Copilot Free to explore core features with no paid plan required."6 The limit is volume: inline suggestions are "Limited to 2000 completions per month on Copilot Free."9

A company assigns seats under Business or Enterprise instead, and the seat brings the organization's policies with it. Administrators can "exclude files that Copilot shouldn't see, and review usage data and audit logs".6 The next step covers those settings.

A second example: Codeium, now Windsurf

Codeium's editor extensions are the second example, and their names have moved quickly:

  • On 2025-04-04 Codeium renamed itself Windsurf ("Today, we are proud to officially rebrand our company to Windsurf.") and planned to "Rebrand the original Codeium Extensions to the 'Windsurf Plugins'".10
  • On 2025-07-14 the company announced that "Windsurf is being acquired by Cognition."11
  • On 2026-06-02 the Windsurf editor took a new name: "Devin Desktop is the new name for Windsurf."12

The plugins still carry the Windsurf name. Their docs say "Windsurf Plugins bring AI-powered coding assistance to JetBrains IDEs," offering "Autocomplete, Chat, Command, and more", and that the plugin "is in maintenance mode and Cascade is being deprecated".13 Cascade was Windsurf's agent; the launch post names "Devin Local, which is the successor to Cascade as our primary local agent".14

A product name you remember may be out of date, so product facts come from the vendor's current docs. The category is what carries over from one product to the next.

Takeaways
  • An editor assistant is an extension that reads open files and workspace context.
  • Copilot offers inline and next edit suggestions, chat and an agent inside the editor.
  • Slash commands run common requests; hash variables choose the context sent.
  • Codeium's plugins became Windsurf Plugins; Windsurf itself is now Devin Desktop.
Say it in an interview

An editor assistant is an extension inside the IDE that suggests code using my open files and workspace as context. GitHub Copilot is the common example: it gives inline suggestions and next edit suggestions as I type, a chat panel for questions about the codebase, and an agent mode that can edit files and run commands.

Compared with a chat assistant in a browser, it picks up context automatically instead of me pasting it, which is faster but means the team has to decide what it may read. Codeium's plugins are another example; they're now called Windsurf Plugins, so I'd check the vendor's current docs before saying what they do.

Integration with IDE

Integration with the editor and the team's workflow

Installing an editor assistant connects your editor to a service over the network. Before a team switches one on, someone asks what leaves the machine and which settings control it. This step answers both, then looks at the two other places a model can sit in a team's workflow.

What the extension sends

GitHub's application card for inline suggestions describes the request. "The surrounding code from your cursor position is pre-processed by the inline suggestions system" and "combined with contextual information (such as code snippets from open tabs in the editor)".5 It adds that "Code context — including edit history, surrounding code, and cursor position — is structured and scoped before reaching the language model."5 Put together, a suggestion can be built from:

  • the code around your cursor in the file you are editing;
  • snippets from other files open in tabs;
  • your recent edit history and the cursor position;
  • in chat, the text you type and any file or selection you attach with #file or #selection.

People tend to forget the second item. A file you opened in a tab an hour ago, perhaps an export holding customers.email values such as dana@example.com, can inform a request while you edit something else. That is why the settings below exist.

Settings a team checks before switching it on

SettingWho sets itWhat it controls, and its limit

Content exclusion has a gap: it "is currently not supported in Edit and Agent modes of Copilot Chat in Visual Studio Code and other editors."15 On a personal account, web search for Chat "is disabled by default."16 If you have a free Copilot account at home, the training setting in the table is the one to check first.

The editor has its own telemetry switch. In VS Code it is one setting, telemetry.telemetryLevel, with the values all, error, crash and off.18 You recognise it in a user's settings.json:

{
  "telemetry.telemetryLevel": "off"
}

That line stops VS Code's own usage data, and only that. The docs warn that extensions "may be collecting their own usage data and are not controlled by the telemetry.telemetryLevel" setting, so an assistant extension is checked in its own settings.18

Beyond the editor: a model in a script or a CI job

The fourth category from Tuesday, API access, puts a model inside a program instead of an editor. Two shapes are common, and this page names them without running either:

  • A script sends a request to a provider's API. For Anthropic's Messages API that is a POST to https://api.anthropic.com/v1/messages, and it needs "A Claude Console account" and "An API key".20
  • A CI job calls a model when something happens in the repository. The Claude Code GitHub Action "runs Claude Code inside your repository's workflows", and given a prompt input it runs "without waiting for a mention".19

A CI job of that kind might summarise or review each pull request as it opens. The review still ends with a person, because the job's comments are suggestions like any other.

Secrets in CI

Once a model is called from code, an interviewer asks where the key lives. The Action's docs answer: "Never commit API keys or OAuth tokens directly to your repository. Always store them as GitHub Secrets".19 You recognise the pattern in a file under .github/workflows/:

anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

The workflow names a secret, and GitHub fills in the value when the job runs, so the key never appears in the repository. A script follows the same rule through an environment variable: Anthropic's SDK "reads ANTHROPIC_API_KEY automatically".20 It is the habit from week 4, where the desk's dw.client read DESK_GCP_PROJECT from the environment instead of the code.

Takeaways
  • Suggestions are built from nearby code, open tabs, edit history and cursor position.
  • Content exclusion hides files, but not in Edit and Agent modes.
  • The editor's telemetry setting does not cover an extension's own usage data.
  • A script or CI job can call a model; its key lives in a secret.
Say it in an interview

An editor extension sends the code around my cursor, snippets from my open tabs and my recent edits, plus whatever I type in chat. Before switching it on, the team checks content exclusion for sensitive files, the public-code matching setting, whether our plan's data can be used for training, and the organization's policy.

I'd also know the limits: exclusion doesn't apply in agent mode, and the editor's telemetry switch doesn't cover the extension. Outside the editor, a model can sit in a script or a CI job that reviews pull requests, and its API key goes in a GitHub secret, never in the repository.

Code generation

Generating code with context: ticket_age_band

The running example is a new function, ticket_age_band(hours), which does not exist in the desk's code. It sorts a ticket's age into a bucket, the kind of engineered feature Project 0 asks for, and it is small enough to check by hand.

The requirement

The band edges come from the desk's data. The priorities rows in sql/seed.sql give high an SLA of 4 hours, normal 24 and low 72. The requirement uses the first two as edges:

  • fewer than 4 hours returns under 4;
  • from 4 to 24 hours, both included, returns 4 to 24;
  • more than 24 hours returns over 24, which is where low's 72 lands.

So 3 gives under 4, 4 and 24 both give 4 to 24, and 25 gives over 24.

Round 1: a zero-shot prompt

Prompt, round 1 (shown, never run):

Write a Python function ticket_age_band(hours) that sorts a ticket's
age into the bands "under 4", "4 to 24" and "over 24".

The prompt names the labels but never says whether 24 belongs to the middle band. Illustrative reply (written for this page):

def ticket_age_band(hours):
    """Return the age band of a ticket open for hours."""
    if hours < 4:
        return "under 4"
    elif hours < 24:
        return "4 to 24"
    else:
        return "over 24"

It reads cleanly and runs. The way to judge it is the four values on and beside each edge:

for hours in (3, 4, 24, 25):
    print(hours, ticket_age_band(hours))
3 under 4
4 4 to 24
24 over 24
25 over 24

The third line breaks the requirement. Line 5, elif hours < 24:, leaves 24 out of the middle band, and the fix is elif hours <= 24:. The prompt was ambiguous about 24, so any reply had to guess that edge, and this one guessed wrong.

Round 2: the code, the boundaries and the expected outputs

GitHub's best-practices page asks for exactly what round 1 left out: "Be specific about your requirements." and "Provide examples of things like input data, outputs, and implementations."1 Its prompting guide adds "Use examples to help Copilot understand what you want." and, when the result is wrong, "iterate on your prompt and try again."21

Prompt, round 2 (shown, never run):

I am adding a function to a Python ticket desk. Priorities have SLA hours:
high 4, normal 24, low 72.

Write ticket_age_band(hours) with these rules:
- hours < 4 returns "under 4"
- 4 <= hours <= 24 returns "4 to 24" (both edges included)
- hours > 24 returns "over 24"

Expected: 3 -> "under 4", 4 -> "4 to 24", 24 -> "4 to 24", 25 -> "over 24".
Style: plain if statements, no imports, a one-line docstring that starts "Return".

The prompt carries the context, the edges written as comparisons, four expected outputs and the project's style. Illustrative reply (written for this page), with the same check run below it:

def ticket_age_band(hours):
    """Return the age band of a ticket that has been open for hours."""
    if hours < 4:
        return "under 4"
    if hours <= 24:
        return "4 to 24"
    return "over 24"


for hours in (3, 4, 24, 25, 72):
    print(hours, ticket_age_band(hours))
3 under 4
4 4 to 24
24 4 to 24
25 over 24
72 over 24

Every value matches the requirement, including low's 72. This reply carries no planted bug.

Reading a generated function

The trade-off of round 2 is time: the prompt took longer to write. Deciding the edges was needed either way, and round 1 only hid that decision inside the model's guess. GitHub's application card warns that generated code "may not actually be semantically or syntactically correct."5 Its review guide puts running the tests first in its checklist.3

On sight, look for the comparison at each edge. A < where the requirement includes the edge, as in elif hours < 24:, is the classic off-by-one, a bug where a comparison is wrong by exactly one step. A new task also deserves a fresh session: "Start a new conversation or session when you begin a new task."21

Takeaways
  • A zero-shot prompt left the edge at 24 to the model's guess.
  • Round 2 gave the context, the comparisons, expected outputs and the style.
  • Check a generated function on and beside every edge: 3, 4, 24, 25.
Say it in an interview

When I ask an assistant for a function, I give it the code it has to fit with, the requirement written as exact comparisons, a few expected outputs including the edges, and the project's style. A zero-shot request leaves the boundaries to the model's guess.

Then I run the function on and either side of each boundary before I accept it. For a band from 4 to 24 hours, that's 3, 4, 24 and 25, which is exactly where an off-by-one like a less-than instead of a less-than-or-equal shows up.

Code generation: unit tests

Unit tests with an assistant, and their limits

A unit test runs one small piece of code with a known input and checks the result. Tests are one of the jobs an assistant is best at, and also the place where trusting it goes wrong most quietly.

What an assistant writes well

GitHub lists "Writing tests and repetitive code" among the tasks Copilot does best.1 Its testing tutorial says "you can prompt Copilot to write a full suite of unit tests with the /tests slash command".23 The cookbook gives a sample prompt, quoted here from the official doc:24

/tests Generate unit tests for this function. Validate both success and failure, and include edge cases.

The same page warns that "Copilot Chat responses are non-deterministic, so you may get a different response from the one shown here."24 What comes back is usually strong on the parts that are tedious to type:

  • test names that say what each case checks;
  • the repeated setup and imports around each test;
  • a list of edge cases you can read and prune.

A generated suite that passes on a bug

In pytest, a test is a plain function with an assert in it: "pytest allows you to use the standard Python assert for verifying expectations and values in Python tests."22 Suppose the round-1 function from the previous step sits in bands.py, a new module invented for this page, and an assistant is asked for tests. Illustrative reply (written for this page):

from bands import ticket_age_band


def test_under_four_hours():
    assert ticket_age_band(3) == "under 4"


def test_four_hours_is_middle_band():
    assert ticket_age_band(4) == "4 to 24"


def test_twenty_four_hours():
    assert ticket_age_band(24) == "over 24"


def test_long_open_ticket():
    assert ticket_age_band(72) == "over 24"

Run against the round-1 function in bands.py, pytest reports all four tests passed. Read them against the requirement from the previous step before you open the question.

The assistant read the code, saw that 24 returns over 24, and wrote that down as the expected answer. A passing suite only proves the code agrees with the tests. When the tests were written from the code, that agreement is guaranteed and proves nothing.

The test that comes from the requirement

The test that matters is written from the requirement, which says 24 belongs to the middle band:

def test_twenty_four_hours_is_middle_band():
    assert ticket_age_band(24) == "4 to 24"

This test fails against the round-1 function, which returns over 24, and passes against round 2. It replaces the generated test_twenty_four_hours. GitHub's tutorial states the limit plainly: "The tests that Copilot generates may not cover all scenarios, so you should always review the generated code."23 Its sample prompt even asks for "Tests for boundary conditions", but a boundary test copied from buggy code repeats the bug.

An assistant tests the code as written. It cannot know a requirement or a boundary nobody told it, so expected values come from you.

Boundary-value testing

The next interview question is usually which inputs to test. Off-by-one errors live at the edges, so for each edge you test the value on it and the values either side. For the 4 and 24 hour edges that gives:

  • 3 and 4 around the lower edge, expecting under 4 and 4 to 24;
  • 24 and 25 around the upper edge, expecting 4 to 24 and over 24.

You recognise the failure mode on sight in a review: a generated test such as assert ticket_age_band(24) == "over 24" whose expected value matches the code instead of the ticket.

Takeaways
  • Assistants write test names, setup and edge-case lists quickly.
  • A test generated from buggy code can assert the bug as correct.
  • Expected values come from the requirement, never from the code under test.
  • Test on and beside every boundary, where off-by-one errors live.
Say it in an interview

An assistant is good at the tedious part of testing: names, setup, and a list of edge cases I can review. Its limit is that it tests the code as written. It can't know a requirement nobody gave it, so if the code has an off-by-one, the generated test can assert the bug as the right answer and still pass.

So I take expected values from the requirement and test on and either side of each boundary. For a band that includes 24 hours, the one test I'd add asserts that 24 gives the middle band.

Documentation

Documentation with an assistant

Documentation is the stage developers most like to hand over, and an assistant produces fluent prose on request, but fluent text can still be wrong. This step marks a drafted docstring and README section against the desk's real code.

What an assistant drafts well

"Explaining and commenting code" is on GitHub's list of what Copilot does best.1 The chat cheat sheet has commands for it: /explain will "Explain how the code in your active editor works," and in Visual Studio /doc will "Add documentation comment for this symbol."8 Good uses include:

  • a first docstring for a function that has none;
  • an outline for a README, with the headings a newcomer needs;
  • a plain-language summary of a module for a manager or a client.

The limit is that an assistant describes what the code looks like it does. A parameter's meaning or a feature that sounds natural can be invented, and the code is the source of truth.

Marking a drafted docstring against the code

Here is extract.read_events as it stands in the desk's code at the end of week 4:

def read_events(conn, after):
    """Return the desk's events with an event_id above after, oldest first."""
    cursor = conn.cursor(dictionary=True)
    cursor.execute("SELECT * FROM ticket_events WHERE event_id > %s ORDER BY event_id", (after,))
    rows = cursor.fetchall()
    cursor.close()
    conn.commit()
    return rows

Called with after=0 it returns every event row as a dict, lowest event_id first. Imagine the docstring were missing and an assistant drafted one. Illustrative reply (written for this page):

def read_events(conn, after):
    """Return events created after the timestamp after.

    Args:
        conn: an open connection to the desk's database.
        after: a timestamp; only events created after it are returned.
    """

The draft is wrong about after. The query compares it with event_id, a strict greater-than, and orders by event_id, so after is an event id used as a watermark, not a time. The caller confirms it: etl.run passes watermark(bq), the highest event_id already staged in desk_raw.ticket_events, or 0 when nothing is staged. The fix is the real docstring, and the draft also drops "oldest first".

A flag that does not exist

The same assistant drafts a README section. Illustrative reply (written for this page):

## Loading events

`python etl.py` loads the desk's new events into the warehouse.
Add `--dry-run` to print what would load without writing anything.

The first line is true. The second describes a feature nobody built.

A command-line flag has to be read by something. A Python script reads command-line flags in one of two usual ways: the standard-library argparse module, or sys.argv, the list of words typed after the script's name. Neither extract.py nor etl.py imports argparse or reads sys.argv, so the job accepts no arguments at all. The fix is to delete the sentence. If a dry run is worth having, someone opens a ticket to build it.

Docstring conventions

To mark a draft you need a standard, and for Python that is PEP 257. A docstring "is a string literal that occurs as the first statement in a module, function, class, or method definition".25 A one-line docstring "is a phrase ending in a period" that "prescribes the function or method's effect as a command ('Do this', 'Return that'), not as a description".25 The desk's "Return the desk's events with an event_id above after, oldest first." follows that form.

A longer docstring for a function "should summarize its behavior and document its arguments, return value(s), side effects, exceptions raised".25 That list is the checklist for any drafted docstring: check each argument's meaning against the code that uses it, and each claimed behaviour against what runs. GitHub's review guide says to "Check that the AI-generated code fits the purpose and architecture of your project."3 Documentation is part of that fit.

Takeaways
  • Assistants draft docstrings, README outlines and plain summaries quickly.
  • A draft can misstate a parameter or invent a feature; the code wins.
  • Prove a flag exists by finding the code that reads it.
  • PEP 257's list of behaviour, arguments, returns and exceptions is the marking checklist.
Say it in an interview

I use an assistant for a first draft: a docstring, a README outline, or a summary for a manager. Then I check every sentence against the code. If the docstring and the code disagree about a parameter, the code wins, and I find out by reading the query or the caller that uses it.

If a README mentions a command-line flag, I search for argparse or sys.argv. If nothing reads arguments, the flag doesn't exist and the line comes out.

Learning a library

Learning a new library through an assistant

Sooner or later a ticket needs a class you have never used. An assistant is a fast way in, as long as the learning ends at the library's own reference page and a line of code you have run.

The task: a query parameter from Python

Week 4 ran warehouse/kind_report.sql, which filters WHERE kind = @kind, from the bq tool with --parameter=kind::<kind>. The new task is to run the same file from Python. The desk's dw.py reaches BigQuery through bigquery.Client and loads with bigquery.LoadJobConfig, and it never uses QueryJobConfig. The classes this task needs are new to the desk.28

A prompt that asks for the docs

Prompt (shown, never run):

I use google-cloud-bigquery 3.47.0 with Python 3.15. A SQL file filters
WHERE kind = @kind. Show me how to pass "closed" as @kind from Python.

Give me the official documentation page for each class you use, a minimal
example, and the library version your answer applies to.

The last paragraph turns the reply into something you can check. A doc link tells you where to verify each name, and a minimal example can be compared line by line with the official one. The version matters because a library's keywords change between releases.

Checking the reply against the reference

Illustrative reply (written for this page), trimmed to the line that matters:

from google.cloud import bigquery

config = bigquery.QueryJobConfig(params={"kind": "closed"})

It looks plausible, and params is a name many libraries use. The reference for QueryJobConfig says to "Set properties on the constructed configuration by using the property name as the name of a keyword argument."26 The property it lists is query_parameters, a "list of parameters for parameterized query (empty by default)".26 There is no params property, and the class is documented to "raise error if an unknown property is being set".26 Run under google-cloud-bigquery 3.47.0 on 2026-11-03, the reply's line raises AttributeError: Property params is unknown for <class 'google.cloud.bigquery.job.query.QueryJobConfig'>.2729

The fix follows the reference, with ScalarQueryParameter(name, type_, value) for one typed value:27

from google.cloud import bigquery

config = bigquery.QueryJobConfig(
    query_parameters=[bigquery.ScalarQueryParameter("kind", "STRING", "closed")]
)
print(config.query_parameters)
[ScalarQueryParameter('kind', 'STRING', 'closed')]

The guide on parameterized queries has the same shape in its own Python sample, with ScalarQueryParameter("corpus", "STRING", "romeoandjuliet"), which makes it the minimal example to compare against.28 It also names a limit: "Parameters can't be used as substitutes for identifiers, column names, table names, or other parts of the query."28

On sight, the warning sign is a keyword argument that the reference page does not list. Before such a line goes in a commit, look the name up in the reference and run the line against the version you have installed.

Which version does the page describe?

Reference pages have versions too. The "latest" BigQuery reference pages still render as 3.42.1.26 PyPI's latest release, and the desk's pin, is 3.47.0.29 The two signatures above were checked against both. When the doc page and your pin differ, note the version the page shows and run a one-line check against the installed library, which settles it.

Takeaways
  • Ask the assistant for the doc page, a minimal example and the version.
  • The reply's params keyword does not exist; the reference lists query_parameters.
  • Compare a reply with the official sample, then run it against your installed version.
Say it in an interview

When I need a library I haven't used, I ask an assistant for a minimal example, the official doc page for each class it uses, and the version the answer applies to. That gets me started fast, but the reference page is the authority.

If the assistant says a function takes a certain keyword, I do two things before committing: I find that keyword in the official reference, and I run the line against the version pinned in the project. A made-up keyword like params instead of query_parameters fails right away.

Check yourself

Check yourself

Eight retrieval questions, one per section. Answer each out loud before you open it.

Name two stages of the development life cycle where an assistant helps, and say what stays the developer's in each.

In the code stage it drafts boilerplate and functions, but the design and the decision to accept the draft stay with you. In the test stage it drafts cases and setup, but which behaviours must be tested comes from the requirement. In every stage the review and the commit are yours, so a bug it wrote is your bug.

In AI pair programming, which role does the assistant play, and what does it not see?

It plays a kind of navigator: it offers suggestions while you drive. It sees the code around the cursor, open tabs and recent edits, but not a requirement that is not written in those files, and it does not run the code unless it is an agent with tools.

List GitHub Copilot's surfaces inside the editor and say which one can run commands.

Inline suggestions, next edit suggestions, chat, and the agent. The agent is the one that can find code, edit files and run commands, so its changes need the closest review.

Your team excludes a folder of customer exports with content exclusion. Where does that guardrail stop working?

It is not supported in the Edit and Agent modes of Copilot Chat in VS Code and other editors, and it only covers tools GitHub controls. The safer fix is to keep customer data out of the repository.

A generated ticket_age_band returns over 24 for exactly 24 hours. Give the line, the issue and the fix, and say what the next prompt should contain.

The line elif hours < 24: leaves 24 out of the middle band; the fix is elif hours <= 24:. The next prompt gives the context, the rules as exact comparisons, expected outputs for 3, 4, 24 and 25, and the project's style.

An assistant wrote a function and its tests, and every test passes. Why is that not proof the function is correct, and which test would you add to ticket_age_band?

The assistant tested the code as written, so a test can assert the bug as the expected answer. Expected values have to come from the requirement. The test to add is assert ticket_age_band(24) == "4 to 24", which fails on the round-1 function.

A drafted docstring says after is a timestamp. How do you decide whether it is right?

Read the code that uses it. read_events compares after with event_id and etl.run passes the highest staged event_id, so it is an event id watermark and the code wins.

An assistant tells you QueryJobConfig takes params=. What two things do you do before that line goes in a commit?

Look the keyword up in the official reference, which lists query_parameters and no params. Then run the line against the installed version, where params raises an AttributeError.
