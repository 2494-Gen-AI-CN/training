AI tooling: optimization, analysis & security: reviewing what an assistant hands you

This page assumes Wednesday's loop: give an assistant the code, the error, the constraint and the expected output, then read and test what comes back. It turns that loop on existing code and on security: judging an assistant's review of the ticket desk's clean_events, accepting a faster apply_scd2 only behind tests, and finding five security problems in a generated export script. It then covers responsible use, the legal questions of licensing and copyright, and a comparison of assisted and traditional development. Code analysis

Code analysis: judging an assistant's review

Asking an assistant to review a function

The subject is transform.clean_events from the ticket desk's week 4 ETL job. It joins each staged event to its ticket's opened_at and gives every bad row a reason. A useful review prompt gives the model the code, what the function is for, where its data comes from and the team rules it must respect.

Prompt (written for this page, never run here)

Review this function from our ETL job. It splits staged ticket events into
clean rows and rejects. Events come from MySQL through a staging table, and
the tickets table is reloaded on every run. Our lint config requires a
docstring on every function. For each finding, name the line, say why it
matters, and say whether it is a bug, a risk or a style point.

<the code of transform.clean_events, pasted in full>

If you have a free chat assistant of your own, you can try this prompt at home; nothing on this page needs an account. The reply below was written for the page, so it never changes.

Illustrative reply (written for this page)

1. The merge with how="left": an event whose ticket_id has no row in
   tickets keeps an empty opened_at. created_at < opened_at is then False,
   so the event passes as clean. Consider rejecting events with no ticket.
2. The duplicated(...) line: duplicated marks the first copy of a duplicate
   too, so both copies are rejected and the good event is lost. Rework the
   check so one copy survives.
3. The docstring: drop the one-line docstring, the name says it all.

Three findings, stated with the same confidence and no source. GitHub's application card for Copilot Chat warns that an assistant's explanation may not always be accurate or complete and should be reviewed, and it puts that review on the user.1

Settling each finding with the docs and a test

Finding 2 is a claim about a library, so the library's reference settles it. DataFrame.duplicated defaults to keep="first", which marks duplicates as True except for the first occurrence; only keep=False marks every copy.2 The first copy survives, and a week 4 test already asserts it. The finding is false.

Finding 1 is about the merge. A left merge keeps every key of the left frame, like a SQL left outer join, and fills the right frame's columns with missing values where no row matches.3 A few lines of pandas show both findings at once. Ticket 9 is invented for the example and is not in sql/seed.sql.

import pandas as pd

events = pd.DataFrame({
    "event_id": [1, 2, 3],
    "ticket_id": [4, 4, 9],
    "kind": ["assigned", "assigned", "closed"],
    "created_at": pd.to_datetime(["2026-10-19 09:00", "2026-10-19 09:00", "2026-10-19 10:00"]),
})
tickets = pd.DataFrame({"ticket_id": [4], "opened_at": pd.to_datetime(["2026-10-19 08:00"])})

print(events.duplicated(["ticket_id", "kind", "created_at"]).tolist())
merged = events.merge(tickets, on="ticket_id", how="left")
print(merged["opened_at"].isna().tolist())
print((merged["created_at"] < merged["opened_at"]).tolist())
[False, True, False]
[False, False, True]
[False, False, False]

Only the second copy of the ticket 4 event is marked a duplicate. Event 3, whose ticket is missing, has no opened_at after the merge, and a comparison with a missing time is False, so event 3 gets no reason and comes out clean. Finding 1 is true.

Can it happen? In MySQL, ticket_events.ticket_id is a foreign key with ON DELETE CASCADE: MySQL rejects a child row with no matching parent, and deleting a ticket deletes its events.4 No orphan exists at the source. One can still arrive through staging, because etl.run exports tickets before it reads the events, and staged events are appended while staged tickets are reloaded. The case is rare, so it earns a cheap guard: a missing ticket reject reason and a test that stages an orphan.

The critical-evaluation checklist

Sorting findings needs a fixed set of questions, so the verdict does not depend on how sure the reply sounds. GitHub's best-practice page for Copilot asks you to review suggestions for functionality, security, readability and maintainability, and to back that review with linting and code scanning.5 A checklist that covers all of it:

  • Does it run? Read it, then run it or the test that covers it.
  • Does it meet the requirement, including the edge cases the prompt never mentioned?
  • Is it tested, and does some test fail when the code is wrong?
  • Can the team maintain it: does it follow the team's conventions, and can a teammate read it?
  • Is it safe: does it treat input, secrets and personal data the way the team requires?
  • Is every claim about a library or an API in that library's own docs?

The first three questions are correctness, the fourth maintainability, the fifth security. Finding 2 fails the docs question, Finding 1 passes all six, and Finding 3 fails maintainability.

A linter's rule against an assistant's opinion

Finding 3 says to drop the one-line docstring because the name says it all. The desk runs pylint, and its message C0116, missing-function-docstring, is used when a function or method has no docstring.6 Week 4 made docstrings a team convention, so accepting the suggestion brings back a lint failure on the next run. A style point that contradicts the team's lint configuration is a sign the model knows general taste and not your project.

A static-analysis tool such as pylint reads the code without running it, applies the same rule every time and names the rule that fired. An assistant's review can change between runs and argues in prose. Teams keep both and settle disagreements with the docs and a test. A weak review is easy to spot: it states library behaviour with no link to the docs, or offers a style rule the team's linter would reject.

Takeaways
  • An assistant's review is a list of claims, each settled with the docs or a test.
  • duplicated keeps the first copy by default, and the pandas reference says so.
  • A true finding about a rare case still earns a cheap guard and a test.
  • A suggestion that breaks the team's lint rules fails maintainability.
Say it in an interview

When an assistant reviews my code, I treat each finding as a claim. If it's about a library, I open the docs; if it's about behaviour, I write a small test that shows it. I act on the findings that hold up and fit the team's conventions, and I drop the rest.

I judge generated output on three things. Correctness: does it run, does it meet the requirement, and does a test fail when it's wrong. Maintainability: does it follow our conventions so a teammate can work on it. Security: does it handle input, secrets and personal data safely.

If a finding is true but can't happen at the source, I check the other ways data arrives. Staging can still produce an orphan, so I'd add a reject reason and a test for it.

Code optimization

Optimizing and refactoring behind tests

A refactor keeps the behaviour

Refactoring restructures existing code, altering its internal structure without changing its external behaviour.7 Optimizing is one reason to refactor: the same answers, sooner. GitHub's tutorial on refactoring says Copilot Chat can suggest ways to speed up slow-running code,8 so asking an assistant for a faster version is an ordinary request. Accepting one is where the work starts.

A refactor promises the same behaviour, so the proof is the tests: they pass before the change and must pass, unedited, after it. Tests changed in the same commit as the refactor can be bent to fit the new code. The routine:

  1. Run the existing tests and confirm they pass.
  2. Ask for the rewrite, then read the whole diff before accepting any of it.
  3. Run the same tests, unedited, against the rewrite.
  4. Ask which inputs the tests do not cover, and add a test for each one that matters.

The "faster" apply_scd2

transform.apply_scd2 keeps customer history as a type 2 slowly changing dimension: when a tracked value changes, it closes the current row and adds a new version. It decides "changed" in a Python loop, one source row at a time, comparing each column in TRACKED with ==. Asked for a faster version, an assistant might replace that compare with a pandas merge on customer_id.

Illustrative reply (written for this page)

def apply_scd2(dimension, source, as_of):
    """Return the customer dimension with type 2 history applied on as_of."""
    rows = [dict(row) for row in dimension]
    current = {row["customer_id"]: row for row in rows if row["is_current"]}
    next_key = max((row["customer_key"] for row in rows), default=0) + 1
    cur = pd.DataFrame(list(current.values()), columns=["customer_id", *TRACKED])
    merged = pd.DataFrame(source).merge(cur, on="customer_id", how="left")
    changed = pd.Series(False, index=merged.index)
    for col in TRACKED:
        changed |= merged[f"{col}_x"] != merged[f"{col}_y"]
    for src, is_changed in zip(source, changed):
        if not is_changed:
            continue
        old = current.get(src["customer_id"])
        if old is not None:
            old["effective_to"] = as_of
            old["is_current"] = False
        rows.append(dict(src, customer_key=next_key, effective_from=as_of,
                         effective_to=OPEN_END, is_current=True))
        next_key += 1
    return rows

Columns present in both frames of a merge get the suffixes _x and _y by default,3 so country_x is the source's country and country_y the dimension's. Run under pandas 3.0.6 against week 4's three apply_scd2 tests in test_transform.py, this version passes all three. A reviewer who stops there accepts it.

A missing value and the test the fixtures miss

The rewrite changed behaviour at an edge. In plain Python, None == None is True. In pandas a missing value is never equal to itself in a comparison, which is why the docs say to test for missing values with isna() and not with ==.9

import pandas as pd

print(None == None)
left = pd.Series([None, "CA"])
right = pd.Series([None, "CA"])
print((left == right).tolist())
print((left.isna() & right.isna()).tolist())
True
[False, True]
[True, False]

The loop calls Dana's missing country unchanged; the rewrite calls it changed. Week 4's fixture holds no missing value, so its tests cannot see the difference. The test that can is a copy of test_rerun_after_change_adds_nothing with Dana's country set to None in both the dimension and the source.

def test_rerun_with_missing_country_adds_nothing(dimension):
    """A missing country that did not change adds no row on a rerun."""
    dimension[0]["country"] = None
    source = [dict(row) for row in dimension]
    source[0]["monthly_fee"] = Decimal("199.00")
    once = apply_scd2(dimension, source, AS_OF)
    assert apply_scd2(once, source, AS_OF) == once

Under pandas 3.0.6 this test passes against the loop and fails against the rewrite: the second run closes Dana's current row and appends a fourth. The fix counts a column as changed only when the values differ and are not both missing, using isna().

On the desk the divergence is latent, because sql/schema.sql declares all four tracked columns NOT NULL. It goes live on any source with nullable columns, Project 0's dataset of 100,000 rows or more among them. In a diff, look for a _x against _y compare used as "changed" with no isna() guard, and for a refactor that edits its tests in the same commit.

Measure before you optimize

The next interview question is how you knew the loop was slow. A profile is a set of statistics that describes how often and for how long various parts of a program execute, and Python 3.15 adds a profiling package to collect one.10 The older pure-Python profile module is deprecated in 3.15.11 Profilers are not for benchmarking; timing a small snippet is the job of timeit.12

Measured, the question has an honest answer. At the desk's four customers the loop finishes before anyone could notice, and a rewrite buys only risk. At Project 0's 100,000 rows a vectorized compare may be worth having, once a measurement shows the compare is where the time goes and the missing-value test passes. "This is faster" with no timing is a claim like any other.

Takeaways
  • A refactor changes structure and keeps behaviour; the unedited tests prove it.
  • pandas compares a missing value as unequal to itself; test for it with isna().
  • Existing tests guard only their fixtures; add one for the edge the rewrite touches.
  • Measure with a profiler or timeit before deciding an optimization is worth it.
Say it in an interview

Before I accept a faster rewrite, I run the existing tests, read the whole diff, and run the same tests unchanged against the new version. The tests come first because they describe what the code does today; if I edit them alongside the refactor, they stop proving anything.

Refactoring means changing the structure without changing the behaviour. I prove it with the tests that passed before, and then I add tests for the inputs the rewrite handles differently.

The old tests can pass while the rewrite is wrong, because they only cover their fixtures. A pandas compare treats two missing values as different where plain Python treats them as equal, so I'd add a test with the same missing value on both sides.

Security risks

Security risks in generated code: code injection

A generated export script

The request to an assistant: a script that takes a ticket status from the command line, reads the tickets of that status joined to customers for each customer's email, and writes them to a CSV file. The file it returns, export_tickets.py, is new and not part of the desk. It runs, and on the happy path it works.

Illustrative reply (written for this page)

"""Export the tickets of one status, with each customer's email, to a CSV file."""
import csv
import logging
import os
import sys

import mysql.connector

logging.basicConfig(level=logging.DEBUG)
log = logging.getLogger(__name__)


def main():
    """Write every ticket of the status given on the command line to tickets.csv."""
    status = sys.argv[1]
    conn = mysql.connector.connect(
        host="127.0.0.1",
        user="desk_app",
        password=os.environ.get("DESK_DB_PASSWORD", "deskapp"),
        database="ticket_desk",
        ssl_disabled=True,
    )
    cursor = conn.cursor(dictionary=True)
    cursor.execute(
        "SELECT t.ticket_id, t.title, t.status, c.email FROM tickets t "
        "JOIN customers c ON c.customer_id = t.customer_id "
        f"WHERE t.status = '{status}'"
    )
    rows = cursor.fetchall()
    cursor.close()
    with open("tickets.csv", "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=["ticket_id", "title", "status", "email"])
        writer.writeheader()
        for row in rows:
            log.info("writing %s", row)
            writer.writerow(row)
    conn.close()


if __name__ == "__main__":
    main()

The file carries five security problems. Before reading on, find as many as you can and say how you would fix each. This step takes the query; the next step takes the other four. OWASP's Top 10 for LLM applications frames the right attitude in its entry LLM05:2025, Improper Output Handling: treat the model like any other user, with zero trust, and check what it produces before it runs.13

SQL built from user input

The last line of the query is an f-string, and status comes straight from sys.argv, the list of command-line arguments. Whatever the user types becomes part of the SQL text. That is code injection. MITRE catalogues it as CWE-89, Improper Neutralization of Special Elements used in an SQL Command: the program builds an SQL command from externally influenced input.14 Running the same string-building with a hostile status shows the SQL that reaches the database.

status = "closed' OR '1'='1"
query = f"SELECT t.ticket_id, c.email FROM tickets t JOIN customers c ON c.customer_id = t.customer_id WHERE t.status = '{status}'"
print(query)
SELECT t.ticket_id, c.email FROM tickets t JOIN customers c ON c.customer_id = t.customer_id WHERE t.status = 'closed' OR '1'='1'

The quote in the input closes the string literal, and '1'='1' is true for every row, so the export holds every ticket and every customer's email whatever status was asked for. OWASP names this case directly: LLM-generated SQL queries executed without proper parameterization, leading to SQL injection.13

Binding a parameter, and what binding cannot do

The desk already has the right pattern. extract.read_events passes its watermark as a parameter:

cursor.execute("SELECT * FROM ticket_events WHERE event_id > %s ORDER BY event_id", (after,))

cursor.execute(operation, params) binds the values in the tuple or dict params to the %s markers in the operation, and a tuple of one value needs its comma, as in ('abc',).15 The fix for the generated file has the same shape:

cursor.execute(
    "SELECT t.ticket_id, t.title, t.status, c.email FROM tickets t "
    "JOIN customers c ON c.customer_id = t.customer_id "
    "WHERE t.status = %s",
    (status,),
)

A parameterized query defines the SQL structure separately from its data values,16 so the hostile status is now one odd value that no ticket has, and the export comes back empty. Two wrong fixes come up often: escaping the quote by hand inside the f-string, and writing (status) without the comma, which is a plain string and no tuple.

extract.read_table also runs f"SELECT * FROM {table}", which raises a fair question. OWASP's cheat sheet says parameter markers represent data values, not table names, column names or SQL keywords, so an identifier is fixed in code or mapped from an allow-list.16 read_table gets its table name from the TABLES constant, never from input, which makes the constant its allow-list. The generated file's status is a value from the user, so it must be a parameter.

Binding has a limit. It keeps input as data but does not decide whether this user may see these rows. Access is a separate check.

Defence in depth

A bound parameter closes this hole, and it is one layer. Defence in depth means several independent checks, so that one missed check does not become a breach:

  • bound parameters, so input stays data;
  • least privilege on the database account, so an injection that slips through reads only what that account may read;
  • secrets kept outside the code, so a leaked file does not leak the password;
  • a review and a scanner on every generated change.

You recognise the risk on sight: cursor.execute(f"..."), or a quote and a plus sign gluing a variable into SQL text. Every variable inside SQL text raises the same question: where does its value come from?

Takeaways
  • An f-string query built from user input lets the input rewrite the SQL.
  • Bind values with a %s marker and a tuple, and keep the comma in a one-value tuple.
  • Identifiers cannot be bound; they come from code or an allow-list.
  • Binding is one layer; least privilege and secrets outside the code are others.
Say it in an interview

Generated code brings three security risks I look for. Code injection, like SQL built from user input with an f-string, fixed with a bound parameter. Insecure defaults, like a fallback password or TLS switched off, fixed by failing loudly and keeping the safe default. And data leakage, like customer emails written to a log, fixed by logging only ids and counts.

An f-string pastes the user's text into the SQL itself, so a quote in the input can change the query. With a placeholder and a parameter tuple, the SQL and the data travel separately, and the input can only ever be a value.

The f-string in read_table is acceptable because the table name comes from a constant in the code, and a placeholder can't stand for a table name anyway. The generated script's status comes from the command line, so it has to be a parameter.

Security risks

Insecure defaults, data leakage and the patterns to recognise

A fallback password is a hard-coded credential

The connect call in export_tickets.py reads its password with os.environ.get("DESK_DB_PASSWORD", "deskapp"). It looks careful, because it reads an environment variable. The second argument is the catch: a .get on os.environ returns the default when the variable is missing.17 deskapp is the real desk_app password from the desk's sql/users.sql, so the script runs with no variable set, and the password sits in the file and its Git history for anyone to read.

MITRE calls this CWE-798, Use of Hard-coded Credentials: the product contains hard-coded credentials, such as a password or cryptographic key.18 The fix is to fail loudly. os.environ["DESK_DB_PASSWORD"] raises KeyError when the variable is missing, by the ordinary rules of a mapping.17

import os

os.environ.pop("DESK_DB_PASSWORD", None)
print(os.environ.get("DESK_DB_PASSWORD", "deskapp"))
try:
    os.environ["DESK_DB_PASSWORD"]
except KeyError as err:
    print("KeyError:", err)
deskapp
KeyError: 'DESK_DB_PASSWORD'

The first form hands back the secret without a word; the second stops the program and names what is missing. Better still, replace the whole connect call with from db import connect. The desk already has one connection function, and it reads the password with no fallback.

TLS switched off and a debug level left on

Connector/Python attempts to establish a secure, encrypted connection by default when the server supports TLS, and ssl_disabled=True disables SSL/TLS usage.19 The generated line switches the safe default off, so the password and every row cross the network in the clear. That is CWE-319, Cleartext Transmission of Sensitive Information, data sent in a channel that unauthorized actors can sniff.20

The fix is to delete the line. Replacing it with ssl_verify_cert=False fixes nothing, because that argument already defaults to False.19 A setting left at, or switched to, the unsafe choice is CWE-1188, Initialization of a Resource with an Insecure Default.21

The fourth problem is logging.basicConfig(level=logging.DEBUG). The root logger starts at WARNING, and basicConfig(level=...) sets its level. The levels run DEBUG 10, INFO 20, WARNING 30, so DEBUG lets everything through.22 MITRE's CWE-489, Active Debug Code, is a product released with debugging code still enabled or active.23 The fix is level=logging.INFO.

Customer data in the log

The fifth problem is log.info("writing %s", row) inside the loop. Each row is the joined dict, so the log holds every customer's email, dana@example.com among them. A log file is shared, shipped and committed far more casually than a database. CWE-532 is Insertion of Sensitive Information into Log File,24 and OWASP lists personal data, passwords, access tokens and database connection strings among data that should usually not be recorded directly in logs.25

import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
log = logging.getLogger("export")
row = {"ticket_id": 1, "title": "Login page returns 500", "email": "dana@example.com"}
log.debug("connector detail %s", row)
log.info("writing %s", row)
log.info("wrote ticket %s", row["ticket_id"])
INFO writing {'ticket_id': 1, 'title': 'Login page returns 500', 'email': 'dana@example.com'}
INFO wrote ticket 1

The level and the content are separate problems. At INFO the debug line disappears, but the line with Dana's email is still written. The fix logs each row's ticket_id and, at the end, the count of rows written, and nothing else.

Bandit 1.9.4, run at every severity against a copy of this file, raised only B608 for the f-string query. With every fix in place the file reads:

"""Export the tickets of one status, with each customer's email, to a CSV file."""
import csv
import logging
import sys

from db import connect

logging.basicConfig(level=logging.INFO)
log = logging.getLogger(__name__)


def main():
    """Write every ticket of the status given on the command line to tickets.csv."""
    status = sys.argv[1]
    conn = connect()
    cursor = conn.cursor(dictionary=True)
    cursor.execute(
        "SELECT t.ticket_id, t.title, t.status, c.email FROM tickets t "
        "JOIN customers c ON c.customer_id = t.customer_id "
        "WHERE t.status = %s",
        (status,),
    )
    rows = cursor.fetchall()
    cursor.close()
    with open("tickets.csv", "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=["ticket_id", "title", "status", "email"])
        writer.writeheader()
        for row in rows:
            writer.writerow(row)
            log.info("wrote ticket %s", row["ticket_id"])
    log.info("wrote %d rows", len(rows))
    conn.close()


if __name__ == "__main__":
    main()

It stops at once when DESK_DB_PASSWORD is missing, keeps the connector's TLS default, logs at INFO and writes only ticket ids and a count to the log. The CSV still holds emails, because the task asked for them, and who may receive that file is a decision for the team.

Takeaways
  • A default in os.environ.get is a hard-coded credential; read the secret with no fallback.
  • ssl_disabled=True turns off the TLS the connector uses by default; delete it.
  • Log ids and counts, never whole rows that hold personal data.
  • The scanner caught one problem of five, so a person still reads every line.
Say it in an interview

In generated code I look for SQL built by string formatting, secrets with fallback values, safety settings switched off like TLS, debug logging left on, and whole records written to logs. Each has a plain fix: bind the parameter, read the secret with no default, delete the override, log at info, and log ids instead of rows.

A fallback password looks safe because it reads an environment variable, but the code then runs with no variable set and the real password sits in the file and its history. I'd rather it fail with a KeyError so someone notices.

Data leakage is often quiet. A debug log of whole rows puts customer emails into a file that gets shared or committed, so I log the record's id and a count, and nothing personal.

Responsible use

Responsible and ethical use

Saying when generated code is in a change

Responsible use starts with honesty inside the team. When a block of a change was generated, say so in the pull request description, the way you would credit a snippet taken from documentation. The reviewer then reads that block as code nobody on the team wrote line by line, and looks harder at its edges. A pull request that hides a generated block is the thing to notice in someone else's work.

The same honesty runs outward. Many clients and employers have a written AI policy that says which assistants are approved, what may be sent to them and whether generated code must be disclosed. Read it before the first prompt. Such a policy may draw on public frameworks like NIST's AI Risk Management Framework, which is voluntary, and its Generative AI Profile, NIST-AI-600-1, written to help organisations identify unique risks posed by generative AI.28

What may be pasted, and where

The week's rules on what goes into a prompt matter most at this point:

  • Never paste personal data, credentials, keys or client data into a public chat assistant.
  • The employer's or client's code goes only to an assistant the employer has approved, never to a public chat.
  • A contract that forbids sending the client's data out of the company covers prompts too, because a pasted row is data sent out.
  • What you may paste still carries only the context the model needs: the code, the error, the constraint and the expected output.

On the desk, the code of clean_events may go to an approved assistant, and a staged row holding dana@example.com may go nowhere. When a prompt needs an example row, invent one and say it is invented.

Overreliance and the skills you build by hand

OWASP's entry LLM09:2025 Misinformation defines overreliance as users placing excessive trust in LLM-generated content and failing to verify its accuracy.29 The same entry notes that a model can suggest insecure or non-existent code libraries, and that attackers publish packages under names models commonly hallucinate.29 An install line copied from a reply without opening the package's own docs is how that attack lands.

Overreliance has a slower cost for a junior developer. The critical-evaluation checklist works only if you can judge the answer, and that judgement comes from writing, debugging and reading code yourself. Copilot Chat's application card says users are responsible for reviewing and validating responses.1 Some tasks are worth doing by hand while you learn, even when an assistant would be faster:

  • a first SQL join, written and checked against the rows you expect;
  • a first set of tests for a function, boundaries included;
  • a first debugging session that starts from a traceback and ends at the line at fault.

Bias in generated text about customers

The same application card warns that training data may contain biases and errors that can be perpetuated by the tool.1 On a support desk that shows up in generated text about people: a reply template that guesses a customer's country from a name, or an apology that assumes the customer's job. Read generated text about customers for assumptions the data does not support, and leave personal attributes out of prompts that do not need them.

Ethics and law overlap here, and the next step takes the legal side: who owns the output, which licences ride along with it, and what copyright says.

Takeaways
  • Say in the pull request when a block was generated, and follow the client's AI policy.
  • Personal data, credentials, keys and client data never go into a public chat.
  • Overreliance means using output unchecked; check packages and APIs in their own docs.
  • Read generated text about customers for assumptions the data does not support.
Say it in an interview

The main limitation is that the output can be wrong while sounding sure: it can invent a library or miss my project's rules. The risks are leaking data through a prompt and shipping code nobody read. The ethical side is being open with the team and the client about what was generated, and checking generated text about people for bias.

If the contract forbids sending the client's data out, none of it goes into a public chat: no rows, no keys, no customer details. I use the assistant the client approved, or I write an invented example that shows the shape of the problem.

Responsible use

Legal ramifications: licensing, IP and copyright

Who owns generated output

A provider's terms answer part of the question. Anthropic's consumer terms, effective October 8, 2025, read: "we assign to you all of our right, title, and interest—if any—in Outputs".30 The words "if any" matter, because a provider can only hand over rights that exist. The same terms say outputs may not always be accurate and should not be relied on without independently confirming their accuracy.30 The terms to read are those of the tool your employer approved.

Copyright law answers the rest, and it differs by country. The U.S. Copyright Office's report on copyrightability, Part 2, released January 29, 2025, says outputs are protected only where a human author has determined sufficient expressive elements. That can include creative arrangements or modifications, but not the mere provision of prompts.31 A function generated from a one-line prompt may carry no author's copyright at all, while the human choices in a module built around generated pieces can.

Permissive and copyleft licences

A model trained on public code can produce code close to something in a public repository, and that code came with a licence. The two main families behave very differently:

Permissive (MIT)Copyleft (GPLv3)
Grantto deal in the software without restriction32a free, copyleft licence to use, change and share33
Main conditionthe copyright and permission notice included in all copies or substantial portions32the entire work licensed, as a whole, under the GPL to anyone who gets a copy (section 5(c))33
Source codeno duty to disclosedisclose source, under the same licence34
Inside closed-source client codefine, with the notice keptclashes with the closed licence

choosealicense.com, maintained by GitHub, sums up MIT as a short and simple permissive licence whose only conditions are keeping the copyright and licence notices, and GPLv3 as a strong copyleft licence.34 GNU explains copyleft as requiring all modified and extended versions of the program to be free as well.35 A suggestion that matches GPL code, shipped in a closed-source client product, brings those conditions with it, and the client never agreed to them.

Suggestions that match public code, and training data

Some tools now help with the matching question. GitHub Copilot's code referencing checks a suggestion against code in public repositories on GitHub.com. Depending on the policy set, it blocks matches or shows them with licensing information, if found.36 A long suggestion that reads like a known library's file is the moment to check, with or without such a tool.

Whether training a model on copyrighted code and text is lawful in the first place is still open. The Copyright Office's Part 3, on training, exists only as a pre-publication version dated May 9, 2025.37 An honest answer says so, and adds how teams manage the risk meanwhile: approved tools, licence checks on matching suggestions, and contracts that say who carries it.

Takeaways
  • Provider terms assign output rights only "if any" exist.
  • U.S. copyright protects sufficient human expressive choices, never a prompt alone.
  • MIT asks only for the notice; GPLv3 requires the whole work under the GPL.
  • Copyright in training data is still an open question.
Say it in an interview

Ownership of generated code is less clear than people think. The provider's terms usually assign me whatever rights exist in the output, but in the US copyright protects only the human expressive choices, not a prompt on its own. So I treat generated code as something I shape, review and take responsibility for.

If a suggestion matches a GPL repository and I ship it in closed-source client code, the GPL's conditions come with it: the whole work would have to go out under the GPL, source included. The client never agreed to that, so I'd check matches and rewrite or remove the code.

One task done two ways

Take Wednesday's task: a new function, ticket_age_band(hours), which is not in the desk. Its requirement says fewer than 4 hours is under 4, 4 to 24 hours inclusive is 4 to 24, and more than 24 is over 24. The edges are the high and normal SLA hours from the desk's priorities rows. def ticket_age_band(hours):
    """Return the age band of a ticket that has been open for hours."""
    if hours < 4:
        return "under 4"
    if hours <= 24:
        return "4 to 24"
    return "over 24"


for hours in (3, 4, 24, 25):
    print(hours, ticket_age_band(hours))

Done the traditional way, a developer reads the requirement and writes this function and its tests by hand. Done the assisted way, the developer writes a prompt and reads the reply. On Wednesday the first reply tested hours < 24, so 24 came back over 24, and a generated test asserted the bug as correct. A second round, with the boundaries and the four expected outputs in the prompt, came back right.

The total cost of a change

The assisted version was quicker to write and can still cost the team more. Writing time is one part of a change; review time, defects found later, what the developer learned and who can maintain the code are the rest. An off-by-one that reaches production costs more than the minutes saved, and code its committer cannot explain costs whoever changes it next.

Traditional tools have limits as well. Bandit's B608 is deterministic and narrow: it looks for SQL strings built by string operations,26 and it found one of the five problems in export_tickets.py. A model can suggest libraries that do not exist,29 so the docs check stays in both workflows. GitHub's best practices say Copilot is strong at writing tests and repetitive code, and present it as a tool rather than a replacement for human programming.51

Check yourself

Nine retrieval questions, at least one per section. Answer each out loud before you open it.

An assistant's review says duplicated marks the first copy of a duplicate too, so both copies are rejected. How do you settle it, and what is the answer?

It is a claim about a library, so the pandas reference settles it. duplicated defaults to keep="first" and marks every copy except the first, so the first copy survives and the finding is false.

What questions make up the critical-evaluation checklist, and how do they map to correctness, maintainability and security?

Does it run, does it meet the requirement, and is it tested with a test that fails when it is wrong: correctness. Can the team maintain it under its conventions: maintainability. Is it safe with input, secrets and personal data: security. Is every library or API claim in the docs: a check on all three.

A "faster" apply_scd2 passes week 4's three tests. Why can it still be wrong, and which test do you add?

The tests guard only their fixtures, which hold no missing value, and the rewrite's pandas compare treats two missing values as different. A copy of test_rerun_after_change_adds_nothing with Dana's country set to None on both sides passes on the loop and fails on the rewrite.

Why is f"... WHERE t.status = '{status}'" dangerous in the generated script, and why is the f-string in extract.read_table acceptable?

The status comes from the command line, so a quote in it can rewrite the SQL; that is code injection, fixed with a %s marker and (status,). read_table takes its table name from the TABLES constant, and a placeholder cannot stand for a table name anyway.

What is insecure about os.environ.get("DESK_DB_PASSWORD", "deskapp") and ssl_disabled=True, and what fixes each?

The fallback is the real password, so the script runs with no variable set and the secret sits in the code; read it with os.environ["DESK_DB_PASSWORD"] or use the desk's connect. ssl_disabled=True turns off the TLS the connector negotiates by default; delete the line.

The script logs every row with log.info("writing %s", row). What leaks, does switching from DEBUG to INFO fix it, and what should the log hold?

Every customer's email leaks into the log. INFO still writes that line, so the level fix alone is not enough. Log each row's ticket_id and the count of rows written, nothing personal.

Your client's contract forbids sending its data out. What may you paste into a public chat assistant?

None of the client's data, code, credentials or customer details. Use the assistant the client approved, or write an invented example that shows the shape of the problem, and follow the client's AI policy on disclosure.
