Python basics: writing Python the way a team reads it

Week 1 · Day 3 Wed Oct 14, 2026 Agile for developers, Git & Python fundamentals ~11 min · notes @150 wpm + diagram + check

This page assumes Tuesday's tooling check passed and that team-repo exists with a clean git status. You know Python syntax from coursework, so today covers the conventions a team holds you to: PEP 8 names and layout, comments that earn their place, the operators that catch people out, and input and output for a script that also runs with nobody at the keyboard. The three demos build one file, ticket_desk.py, on a feature branch, and this page is the reference for what the trainer typed.

Conventions

Python syntax: PEP 8 is the team's contract

The syntax itself takes one sentence: a line is a statement, a newline ends it, and indentation is the block structure, four spaces per level under PEP 8. What is new today is the layout around that syntax, which a team agrees in advance. PEP 8 is Python's official style guide, and a team adopts it as its shared contract for names, layout and comments.

Five rules were on the board this morning. Four are PEP 8's own. Functions and variables are named in snake_case and constants in UPPER_CASE. Two blank lines go around top-level definitions. A line is at most 79 characters. Imports sit at the top of the file. The fifth is this course's reading of PEP 8's section on comments: comments say why. Python runs a file that breaks any of these, so the interpreter will never point them out. A reviewer will, and a review comment saying "rename to snake_case" is the contract being applied.

The ticket-record demo starts ticket_desk.py in that shape from its first line. The first statement is a string that says what the module is for. That is the module docstring, and PEP 257 defines its conventions. The three constants follow.

"""Ticket desk: a small board for the support tickets the team tracks."""

SLA_HOURS_HIGH = 4
SLA_HOURS_NORMAL = 24
SLA_HOURS_LOW = 72

Python will not stop you reassigning SLA_HOURS_HIGH. The capitals tell the next reader that nobody does. Habits from other languages tend to show up here first, usually as a camelCase variable or a lowercase constant.

Conventions

Comments: keep the ones that say why

PEP 8 makes two statements about comments that matter today. Comments that contradict the code are worse than no comments, and inline comments are unnecessary and distracting if they state the obvious. This course draws one working rule from those two: a comment records why the code is the way it is, and the code itself says what it does. That wording is the course's own.

The ticket-record demo puts both kinds of comment on screen. The one above the constants stays:

# Hours until a ticket breaches its SLA; the numbers come from the support
# contract, so change them only when the contract changes.
SLA_HOURS_HIGH = 4

Nothing in the assignments can tell a reader that the numbers come from a support contract, or that the contract is the only reason to change them, so the comment stays.

The second comment was # set the ticket id to 101, typed above ticket_id = 101 and then deleted while you watched. It repeats the line below it, which is the "state the obvious" case. Its cost arrives later: someone edits the value, forgets the comment, and the file now holds a comment that contradicts the code. When you find a stale comment, fix it or delete it in the same commit as the code change.

Mechanics

Variables and datatypes: names bound to objects

A Python variable is a name bound to an object. Nothing is declared, and the name has no type of its own. type() reports the type of the object the name is bound to at that moment. The demo writes one ticket as six flat variables:

ticket_id = 101
title = "Login page returns 500"
priority = "high"
is_open = True
hours_open = 5.5
reporter = "Ada Lovelace"

Those six lines hold four types: int, str, float and bool. The trainer confirmed them with a temporary print of type() on four names and then deleted the line, since a probe is not part of the program.

The ticket stays as six separate variables today, and hours_open is a number typed by hand. Every later step reads these six names, so spell them exactly as shown.

The record prints with an f-string, a string literal prefixed with f whose braces hold expressions that are evaluated when the line runs:

print(f"#{ticket_id} {title} [{priority}] {hours_open}h, {reporter}")

Running python ticket_desk.py prints #101 Login page returns 500 [high] 5.5h, Ada Lovelace. The leading # sits inside the string, so Python reads it as text.

Pitfall

Operators: say the output before you run it

You know the operators. The ticket-rules demo spends its time on the cases where a confident guess is wrong, so say the output aloud before each line runs.

Start with division. / is true division and always returns a float, // is floor division and % is the remainder. With hours_open at 5.5, hours_open / 24 is 0.22916666666666666 and hours_open // 24 is 0.0, a float again because one operand is a float. SLA_HOURS_HIGH - hours_open gives -1.5, which means the deadline has passed. For an every-third-ticket rule, ticket_id % 3 == 0 is false for ticket 101 because 101 % 3 is 2.

Comparisons bind tighter than and, so is_breached = is_open and hours_left < 0 needs no parentheses. Comparisons can also be chained: 0 <= hours_open < 24 means 0 <= hours_open and hours_open < 24. in tests membership and returns a bool. For two strings it is a substring test, so "Login" in title is true, while a lowercase "login" would not be found.

and and or short-circuit: they stop as soon as the result is known, and they return one of their operands. not always returns True or False.

The check has to be written as three full comparisons:

priority_ok = priority == "high" or priority == "normal" or priority == "low"

Watch the = key while you type it. If the first == on that line becomes =, Python raises nothing: the line is a legal assignment to two names, and priority is rebound to "high".

Four more results to predict. hours_open += 0.5 is an augmented assignment: it evaluates the target once, applies the operator and rebinds the name, so 5.5 becomes 6.0, while hours_left keeps the value computed earlier. -2 ** 2 is -4, because ** binds tighter than a unary minus on its left; write (-2) ** 2 for the square of minus two. round(2.5) is 2 and round(3.5) is 4, because round() sends a tie to the even neighbour. round(2.675, 2) is 2.67 for a separate reason: most decimal fractions cannot be stored exactly as a binary float, and the value actually stored is slightly below 2.675.

Mechanics

User input and output: a prompt, a board and two streams

input(prompt) writes the prompt, reads one line from standard input, strips the trailing newline and always returns a str. Type 3 and you get the text "3". Today's intake reads a title and a priority as text; turning typed text into numbers is Thursday's topic.

A script that calls input() unconditionally breaks as soon as nobody is typing. With an empty standard input it raises EOFError: EOF when reading a line, and under pytest's default capture it raises OSError: pytest: reading from stdin while output is captured. The desk-intake demo avoids both with a guard under the ticket variables, and with import sys at the top of the file:

if sys.stdin.isatty():
    title = input("Title: ")
    priority = input("Priority (high, normal, low): ")

sys.stdin.isatty() is true when standard input is a character device such as an interactive terminal, and false when it is a pipe or a regular file. At a terminal the two assignments replace the sample values, and anywhere else the sample ticket stays. This is the only if of the day. You know the statement from coursework, and Friday comes back to if as a design choice.

Test both paths. The second command feeds an empty line through a pipe, and it works the same in PowerShell, cmd and Git Bash:

python ticket_desk.py
echo "" | python ticket_desk.py

Avoid redirecting from the null device for the second test. On Windows it also reports a terminal, so the guard is entered and input() crashes.

On the output side, print() takes sep, end, file and flush keyword arguments. sep goes between the values and is a space by default. end goes after the last one and is a newline by default. The board's columns come from the format spec an f-string accepts after a colon: < aligns left, > aligns right, a number sets the width and .1f gives one decimal place. So {title:<30} pads the title to 30 columns and {hours_open:>6.1f} right-aligns the float in 6.

Every process gets three standard streams: stdin for input, stdout for normal output and stderr for warnings and errors. print(..., file=sys.stderr) sends a line to the error stream. At a terminal the two output streams look alike. Adding 2> err.txt to the command splits them: the board stays on screen and the warning goes to the file.

Deep dive: running a script with nobody at the keyboard

Optional. ~5 minutes.

pytest runs your code with nobody typing, and so does anything that pipes input into your script. An unguarded input() fails in two ways there. When standard input is at end of file it raises EOFError: EOF when reading a line. Under pytest's default capture it raises OSError: pytest: reading from stdin while output is captured. The guard asks one question first: sys.stdin.isatty() is true when standard input is a character device such as an interactive terminal, and false when it is a pipe or a regular file.

Windows has one exception that matters when you test the unattended path. The NUL device, which is the null device in every shell there including Git Bash, also reports true. A run redirected from it enters the guard and crashes on input(). Use a pipe: echo "" | python ticket_desk.py works in PowerShell, cmd and Git Bash and gives isatty() == False. In cmd or Git Bash a redirect from a real file, python ticket_desk.py < sample.txt, is the only safe redirect.

The output side has its own check. Add 2> err.txt to the command and stream number 2, stderr, goes to the file. The board stays on screen because it was written to stdout, and the line printed with file=sys.stderr is the only thing in err.txt that Python wrote.

Excerpt: the ticket rules

The arithmetic, comparison and boolean lines from the ticket-rules demo, as they stand after the or pitfall was deleted.

age_days = hours_open // 24
print(f"exact days: {hours_open / 24}, whole days: {age_days}")
hours_left = SLA_HOURS_HIGH - hours_open
is_breached = is_open and hours_left < 0
print(f"hours left: {hours_left}, breached: {is_breached}")

priority_ok = priority == "high" or priority == "normal" or priority == "low"
print(f"priority ok: {priority_ok}")
print(f"under a day old: {0 <= hours_open < 24}")
print(f"still on time: {not is_breached}")
mentions_login = "Login" in title
print(f"mentions login: {mentions_login}")

For the sample ticket these lines print 0.22916666666666666 and 0.0, then -1.5 and True, then True, True, False and True.
