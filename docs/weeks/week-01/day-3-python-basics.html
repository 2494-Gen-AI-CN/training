Python basics: writing Python the way a team reads it

Week 1 · Day 3 Wed Oct 14, 2026 Agile for developers, Git & Python fundamentals ~34 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-12 · python 3.15

This page assumes only that Python 3.15 is installed and runs from your shell, and it teaches the syntax from first principles together with the conventions a team expects: how a block is marked, the layout and naming PEP 8 asks for, comments that record a reason, variables as names bound to objects, what each operator returns, and input and output that behave at a terminal and in a pipe. Afterwards you can explain how Python marks a block, what a = b really does, why x == "a" or "b" always passes, and why a warning belongs on stderr.

Syntax

Python syntax: blocks, lines and the layout PEP 8 asks for

Python reads blocks and lines in a fixed way, and a reviewer checks a file's layout before its logic.

Indentation marks a block

A block is a group of statements that run together, such as the body of a branch. Many languages wrap a block in braces; Python has no braces.

A compound statement such as if, which runs its block only when its condition is true (Friday's page teaches it properly), ends its header line with a colon. And the statements that belong to it are the lines below it indented further than the header.

The block ends at the first line that comes back to the outer level. Python groups the statements of a block by their indentation, so the whitespace at the start of a line is part of the grammar.2

hours_open = 5.5
if hours_open > 4:
    print("over the high-priority limit")
    print("tell the on-call developer")
print("checked")

Run the file with python and its name, the way any script such as hello.py is run, and it prints all three lines. print writes its values to the screen as one line of text. The two indented calls belong to the if and run because 5.5 is greater than 4, and checked runs either way because it sits back at the outer level.

Move the second indented line two spaces to the left and Python reports IndentationError: unindent does not match any outer indentation level, because a dedent (a line that moves back to the left) has to land exactly on the level of an enclosing block.2 Python checks the layout of the whole file before it runs any line, so the file stops with IndentationError and runs nothing.

Significant indentation removes brace noise, and the price is that whitespace becomes part of the program. If a block mixes tabs and spaces so that its meaning depends on how many spaces a tab is worth, Python rejects it with a TabError.2

Logical lines and continuation

A statement normally ends where its line ends. Before running anything, Python's tokenizer splits the source into tokens (names, numbers, operators) plus a NEWLINE token where a statement ends. A whole statement is a logical line, and it ends at a NEWLINE token unless the break falls inside parentheses, square brackets or braces, or the line ends in a backslash.2 That gives two ways to continue a long expression, and PEP 8 prefers continuing inside parentheses over using a backslash.1

priority = "low"
priority_ok = (priority == "high"
               or priority == "normal"
               or priority == "low")
print(priority_ok)

This prints True. The open parenthesis tells the tokenizer the statement is not finished, so the three lines form one logical line, and lining the continuation up under the first operand makes the structure easy to scan. A trailing backslash also runs, and in a pull request it usually draws a suggestion to use parentheses.

PEP 8 layout: line length, blank lines, imports

PEP 8 is the style guide for Python code, and most teams adopt it as the default contract for layout and naming.1 Four of its rules come up in nearly every review.

  • Lines are limited to 79 characters, and the guide itself says a team may agree on a longer limit.1
  • Top-level function and class definitions get two blank lines around them.1
  • Imports go at the top of the file, after the module docstring and before module-level globals, with standard-library imports first.1
  • Indentation is four spaces per level, as above.

A module is a single .py file. An import loads another module, here sys from Python's standard library. A module docstring is the quoted sentence on the first line saying what the file is for.

"""Ticket desk: a small board for the support tickets the team tracks."""

import sys

SLA_HOURS_HIGH = 4
SLA_HOURS_NORMAL = 24
SLA_HOURS_LOW = 72

print(SLA_HOURS_HIGH, SLA_HOURS_LOW)

The file prints 4 72, in the order a reader expects: purpose, dependencies, settings. PEP 8 ranks itself below the project. A project's own style guide takes precedence, consistency within a project matters more than consistency with PEP 8, and consistency within one module or function matters most.1 A file that ignores the guide is easy to spot: import os, sys on one line, an import halfway down the file, or a def with one blank line above it.

Naming conventions

PEP 8 names variables and functions in lowercase words joined by underscores (snake_case), constants in UPPER_CASE with underscores, and classes in CapWords.1

Under the conventions sit the language's own rules: identifiers (the names you choose)

  • are case-sensitive,
  • may contain letters, digits and underscores,
  • cannot start with a digit
  • and cannot be a keyword, one of the words the language reserves for itself such as if, def or class.2

So hours_open and Hours_Open are two different variables, 2nd_reporter is a syntax error, and class = "high" fails because class is a keyword.

A name carries information the language does not enforce. SLA_HOURS_HIGH tells the reader the value is set once and left alone, yet nothing stops a later line from reassigning it; the capital letters are a promise the team keeps. camelCase, common in other languages, shows up as ticketId or hoursOpen, and a module-level Total_Count = 3 mixes two styles at once. Each one costs a review comment.

Takeaways
  • Python marks a block by indentation, and the header line ends in a colon.
  • The style guide asks for a line length limit, two blank lines around definitions and imports at the top.
  • A project's own style guide takes precedence over the general one.
  • Identifiers are case-sensitive, cannot start with a digit and cannot be a keyword.
Say it in an interview

Python marks a block by indentation. The header line ends in a colon and the block is everything indented under it, four spaces per level in PEP 8. If a dedent doesn't line up with an outer level the file won't run, it's an IndentationError, and mixing tabs and spaces ambiguously gives a TabError.

PEP 8 says 79 characters per line, two blank lines around top-level functions and classes, and imports at the top after the docstring, standard library first. It also says the project's own guide wins, so if my team agreed on longer lines, I follow the team.

Comments

Comments that earn their place

Reviewers judge a file by which comments it keeps.

What Python does with a #

A literal is a value written directly in the source, such as 101 or "high", and a string literal is text between quotes. A comment starts with a # that is not inside a string literal and runs to the end of the physical line, and the tokenizer ignores it.2

There is one exception: a comment in the first or second line that declares the source encoding is read. Some scripts start with a #! line, called a "shebang", which the operating system reads to choose an interpreter; Python itself skips it like any other comment.2 A # inside a string literal is part of the string.2

# Tickets from this channel go to the support rota.
channel = "#support-desk"
print(channel)  # the hash inside the quotes is data

This prints #support-desk, hash included, because the tokenizer is already inside a string when it meets that #. The last line also shows PEP 8's layout for an inline comment: at least two spaces after the statement, then # and a single space before the text.1 The interpreter drops comments, so the only cost of a comment is the time it takes to read.

Why-comments and what-comments

PEP 8 makes two statements about comments that count for more than any formatting rule. Comments that contradict the code are worse than no comments, and an inline comment that states the obvious is unnecessary and distracting.1

It also asks that comments be complete sentences and be kept up to date when the code changes.1 This course draws a short team rule from those statements: a comment says why, and the code says what. That phrase is the course's summary; PEP 8 never says it in those words.

# Hours until a ticket breaches its SLA; the numbers come from the support
# contract, so change them only when the contract changes.
SLA_HOURS_HIGH = 4
SLA_HOURS_NORMAL = 24
SLA_HOURS_LOW = 72

hours_open = 5.5  # set hours_open to 5.5

The block comment above the constants records something the code cannot show: where the numbers come from and who is allowed to change them. A developer who wants to "tidy" 4 into 6 now knows to ask first. The inline comment on the last line repeats the assignment in English and adds nothing; deleting it makes the file shorter and loses no information.

In a review you will see both kinds side by side. Delete the second kind and write more of the first.

The trade-off is length against context. Every comment is a second description of the code that a reader has to check against the first, so a file with a comment on every line is slower to read than one with three comments in the right places. Good candidates are

  • a business rule,
  • a workaround with the reason it exists,
  • or a choice that looks wrong but is deliberate.

Docstrings, and names that need no comment

An interviewer who hears "I comment my code" usually asks what you try before reaching for a comment. The two answers are a clearer name and a docstring. A docstring is a string literal that is the first statement of a module, function or class, and PEP 257 sets its conventions.3

Unlike a comment it survives compilation: it is stored as the __doc__ attribute and can be read while the program runs.3 An attribute is a value attached to an object and read with a dot or, at the top of a module, by its bare name.

"""Ticket desk: a small board for the support tickets the team tracks."""

# Python skips this comment when it reads the file.
print(__doc__)

Saved as a file and run, this prints Ticket desk: a small board for the support tickets the team tracks. The docstring is still there at run time and the comment is not, so anything that loads the module can read its purpose back. A good name covers the rest. h = 5.5 # hours the ticket has been open needs its comment; hours_open = 5.5 does not, and the name travels with the variable to every line that uses it, while the comment stays behind on the first.

How a comment goes stale

A comment is never checked by the interpreter or by tests, so it can drift away from the behaviour it describes without anything failing. That is why PEP 8 rates a contradicting comment below no comment at all.1 A reader who trusts a wrong comment decides on false information.

Staleness usually comes from an edit that touched the code line and not the comment beside it. Code review is where it gets caught: a diff that changes a value while leaving the comment above it untouched is the cue to read that comment again. When you change a line, read the comments next to it as part of the change, and update or delete them in the same commit.

Takeaways
  • The interpreter ignores comments, so their only cost is the time a reader spends on them.
  • A comment says why, and the code says what.
  • A docstring is kept at run time as an attribute, and a comment is not.
  • A comment that contradicts the code is worse than no comment.
Say it in an interview

A comment is skipped when Python reads the file, so it never exists at run time. A docstring is a string literal that's the first statement of a module, function or class, and it's kept at run time as the doc attribute, so tools can show it.

A bad comment either restates the code, like "add one to x", or has gone stale and now contradicts it, which PEP 8 says is worse than having no comment. I try a clearer name first, and I keep comments for the reason behind a rule, the part the code can't say.

Variables

Variables and datatypes: names bound to objects

Thursday's page goes deep on each data type. Here the subject is what a variable is in Python, since the rest of the week builds on that model.

Assignment binds a name to an object

In Python every value is an object: a piece of data in memory that carries its own type. Python variables are names bound to objects. They are not declared with a type, and type() reports the type of whatever object the name is bound to at that moment.4 An assignment statement evaluates the right-hand side to an object and binds the name on the left to it. It does not copy a value into a typed slot.5

ticket_id = 101
title = "Login page returns 500"
hours_open = 5.5
is_open = True
print(type(ticket_id), type(title))
print(type(hours_open), type(is_open))

The two lines printed are <class 'int'> <class 'str'> and <class 'float'> <class 'bool'>. Nothing in the source said "int" or "float"; the types belong to the objects the literals created, and the names just point at them.

The model answers a question interviewers like: what does a = b do? It binds a to the same object b is bound to, and nothing is copied.5 Rebinding b afterwards points b somewhere new and leaves a where it was.

reporter = "Ada Lovelace"
owner = reporter
reporter = "Grace Hopper"
print(owner, owner is reporter)

This prints Ada Lovelace False. After the second line both names were bound to one string; the third line bound reporter to a different string, and owner kept the first. This is rebinding a name, as opposed to changing an object.

Rebinding moves one name; changing an object in place would show through every name bound to it. With the types on this page you only ever rebind: even hours_open += 0.5 evaluates the target, applies the operator and binds the name to the result.5 Objects that change in place, such as lists, are Thursday's subject.

The four scalar types

The built-in scalar types this page uses are:

TypeHolds
intwhole numbers
floatnumbers with a fractional part
strtext
boolthe two values True and False

An int has unbounded precision, meaning it grows as large as memory allows. A float is a number stored in binary with a fixed number of digits. bool is a subclass of int, a specialised kind of int (Friday's page explains subclasses), so True + 1 is 2.6 Binary floats cannot store most decimal fractions exactly, which is why 0.1 + 0.2 == 0.3 is False.7

print(2 ** 100)
print(True + 1)
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)

The output is 1267650600228229401496703205376, then 2, then 0.30000000000000004, then False. The first line shows unbounded precision: no overflow. The third line explains the fourth. The sum is stored as the nearest binary value, which is a hair away from the nearest binary value to 0.3, and == compares exactly.7 In someone else's code, == between two computed floats is worth a second look.

Dynamic typing and what it costs

Python is dynamically typed: the type lives on the object, and one name can be bound to a str now and an int later. The cost is that a type mistake surfaces only when the line that contains it runs, and nothing in the language marks a name as a constant.8

count = "3"
total = count + 1

The first line is fine. The second raises TypeError: can only concatenate str (not "int") to str when it runs.

Raising an exception is how Python reports an error at run time. The script stops at that line and prints the exception's name and message, and if that line sat in a branch nobody exercised, the bug would wait for a user to find it.

Converting typed text into numbers is Thursday's topic. When a value behaves strangely, printing its type() is the cheapest first question: it names the type of the object bound on that line.4

The constant problem looks like MAX_RETRIES = 3 at the top of a file and MAX_RETRIES = 5 forty lines down: Python runs it without complaint, and only the naming convention told anyone it was wrong.

An f-string is a string literal with an f before the opening quote, and each expression inside its braces is replaced by that expression's value. The expressions are evaluated when the line runs, so the result uses the binding each name has at that moment.2

hours_open = 5.5
line = f"{hours_open}h"
hours_open = 6.0
print(line, f"{hours_open}h")

This prints 5.5h 6.0h. The variable line holds the string built on its own line, and rebinding hours_open later does not reach back into it.

Identity and equality: is against ==

Once you describe a variable as a name for an object, the follow-up is is against ==. == compares values; is compares object identity, meaning whether two names are bound to the same object.9 Since Python 3.8, using is or is not with a literal, as in priority is "high", emits a SyntaxWarning before the code runs.10

priority = "high"
print(priority == "high")
print(priority is "high")

Run as a file under 3.15, this shows SyntaxWarning: "is" with 'str' literal. Did you mean "=="? before any output, and the first comparison prints True. Whatever the second line prints, it answers a question about identity when you meant to ask about values. Use == for values and keep is for asking whether two names share an object, as owner is reporter did above.

Takeaways
  • A variable is a name bound to an object, and the object carries the type.
  • Assignment binds a name to an object; it does not copy a value.
  • Binary floats cannot store most decimal fractions exactly.
  • Use the equality operator for values and the identity operator for objects.
Say it in an interview

Python is dynamically typed. Names don't have types, objects do, and type of x tells me the type of the object x is bound to right now. The cost is that a type mistake only shows up when that line runs.

a equals b binds a to the same object b is bound to, so nothing is copied. If I then rebind b, a still points at the old object. Rebinding moves one name, while changing an object in place is seen through every name bound to it.

Double equals compares values and is compares identity. I only use is to ask whether two names are the same object, and Python warns me if I use it with a literal.

Operators

Operators: arithmetic, comparisons and boolean logic

An operator is a symbol or word, such as +, == or and, that combines values into a new value. Many of Python's operators are spelled as in other languages, and several behave differently. What interviews probe, and what goes wrong in real code, is what each one returns and which one binds first.

Arithmetic: /, //, % and **, and round()

/ is true division and always returns a float, even when the division is exact, so 6 / 2 is 3.0.

  • // is floor division,
  • % is the remainder and
  • ** is the power operator.4

// floors toward negative infinity, so -7 // 2 is -4, and % takes the sign of the right operand, which keeps a == (a // b) * b + a % b true for every pair.9

To floor is to round down to the whole number below, and below means toward the more negative side. ** binds tighter than a unary minus (a minus sign in front of a single value) on its left, so -2 ** 2 is -4.4

hours_open = 5.5
print(hours_open / 24, hours_open // 24)
print(7 / 2, 7 // 2, 7 % 2)
print(-7 // 2, -7 % 2)
print(-2 ** 2, (-2) ** 2)
print(101 % 3 == 0, 102 % 3 == 0)

The five lines print 0.22916666666666666 0.0, 3.5 3 1, -4 1, -4 4 and False True. The second value, 0.0, is the number of whole days a ticket open for 5.5 hours has been open. The negative line is the one candidates get wrong: the answer is -4, the floor, and anyone who expected the fraction to be chopped off says -3. The last line is the every-third pattern you will see in real code, n % 3 == 0, true for ticket 102 and false for 101.

round() has two surprises that differ in kind. It rounds a tie to the even neighbour, so round(2.5) is 2 and round(3.5) is 4; 2.5 is exactly representable as a float, so that result is the tie rule alone.11 Separately, round(2.675, 2) is 2.67, because most decimal fractions cannot be stored exactly as a binary float and the stored value is slightly below 2.675.11

print(round(2.5), round(3.5), round(2.675, 2)) prints 2 4 2.67. If an interviewer asks why the last one is not 2.68, the answer is float representation. The tie rule does not apply. Integer division or modulo by zero raises ZeroDivisionError.12

Comparisons, chains, membership and +=

Comparisons can be chained. 0 <= hours_open < 24 is evaluated as 0 <= hours_open and hours_open < 24, with hours_open evaluated only once.9 in and not in test membership and return a bool; between two strings, x in y is true when x is a substring of y.9 An augmented assignment such as hours_open += 0.5 evaluates the target once, applies the operator and rebinds the name.5

hours_open = 5.5
title = "Login page returns 500"
print(0 <= hours_open < 24)
print("Login" in title, "login" in title)
hours_open += 0.5
print(hours_open)

This prints True, then True False, then 6.0. The middle line shows that a substring test matches characters exactly, so a lower-case "login" is not found; Thursday's page normalises the case of text before testing it. You recognise a chained comparison on sight as a < b < c.

and, or, not: operators that return operands

and and or short-circuit: they stop as soon as the result is known, and they return one of their operands rather than a fresh True or False. not always returns True or False.9 With bools on both sides the difference is invisible, so is_breached = is_open and hours_left < 0 gives a bool. With other values you can see it, and it explains a logic bug reviewers meet often.

The expression x == "a" or "b" parses as (x == "a") or "b". A value is truthy when Python treats it as true in a test, and a non-empty string is truthy; falsy values, such as 0 and "", count as false in a test.

So when the comparison is false, the whole expression evaluates to the string "b", which is truthy, and the check never fails.9

priority = "low"
print(priority == "high" or "normal")
print(priority == "high" or priority == "normal")
print(not priority)

The first line prints the word normal: the string itself, not True. Placed in an if, a non-empty string counts as true, so every ticket would pass a priority check written that way. The second line repeats the comparison for each value and correctly prints False. The third prints False because not turns the truthy string into a real bool. Thursday's page shows a shorter fix once collections are available.

Returning an operand is also what makes the value or default idiom work: name or "unassigned" gives the name when it is non-empty and the fallback when it is "". The limit is that every falsy value triggers the fallback. With hours = 0, hours or 8 is 8, so a legitimate zero silently becomes eight.9 Use the idiom only when the falsy values really are "missing".

Precedence and parentheses

Precedence decides which operator binds first. not binds looser than the comparison operators, so not a == b means not (a == b). and binds tighter than or, so a or b and c means a or (b and c).9

print(True or False and False)
print((True or False) and False)
print(not 1 == 2)

The lines print True, False and True. Without parentheses the and is applied first and the or then short-circuits on True; with them, the or goes first and the and makes the result false. The precedence table decides how Python reads the expression, and parentheses show the next reader what you meant. When an expression mixes and with or, or a minus sign with **, add the parentheses even where they change nothing.

Takeaways
  • True division always returns a float, and floor division rounds toward negative infinity.
  • Ties round to the even neighbour, and float representation explains the other surprise.
  • The words and and or return one of their operands, not always a bool.
  • Parentheses show the next reader which operator binds first.
Say it in an interview

Slash is true division and always returns a float. Double slash is floor division, and it floors toward negative infinity, so minus seven floor-divided by two is minus four. Modulo takes the sign of the right operand, so the quotient and remainder always fit back together.

x equals "a" or "b" parses as the comparison, or the string "b". When the comparison is false the expression returns "b", a non-empty string, which is truthy, so the check always passes. I write the comparison out for each value.

And and or short-circuit and return one of their operands, which is why "value or default" works and why a zero can get replaced by accident. Not always gives back a real True or False.

Input & output

User input and output: print, format specs and the standard streams

A script talks to people and to other programs through three streams.

print: sep, end, file and flush

print() takes the values to print plus four keyword arguments, which are arguments passed by name as in sep="-":

  • sep,
  • end,
  • file and
  • flush.11

It converts each non-string argument with str(), joins the results with sep, which defaults to a single space, and writes end after them, which defaults to a newline.11 file=sys.stderr sends the line to the error stream instead of standard output.11

print("Ticket", "desk", "board", sep="-", end=" ready\n")
print(1.0, True, 101)

The first call prints Ticket-desk-board ready: the three words joined by hyphens, then the custom ending, which still ends in a newline. The second prints 1.0 True 101, each value converted by str() and separated by the default space. In other people's code, end="" builds a line in pieces and sep=", " lists values.

Aligned output with format specs

An f-string field can carry a format spec after a colon. In the spec, < left-aligns and > right-aligns within a minimum width, and .1f fixes one digit after the decimal point.1314 A field with no spec calls format(value, ""), which for these types gives the same text as str(), so f"{hours_open}" and print(hours_open) show the same thing.2

title = "Login page returns 500"
priority = "high"
hours_open = 6.0
print(f"{'Title':<30}{'Priority':>8}{'Hours':>6}")
print(f"{title:<30}{priority:>8}{hours_open:>6.1f}")

The header and the row use the same widths, so the two lines of the board line up:

Title                         Priority Hours
Login page returns 500            high   6.0

The title is padded to 30 characters, the priority right-aligned in 8 and the hours right-aligned in 6 with one decimal. Because a width is a minimum, a title longer than 30 characters is not cut; it pushes the rest of its row to the right and the board goes ragged. Shortening a title to fit is Thursday's string work. You recognise this pattern by the colon inside the braces, as in f"{name:<30}{n:>6.1f}".

input() always returns a string

input(prompt) writes the prompt, reads one line from standard input, strips the trailing newline and returns the line, always as a str. When standard input is at end of file, meaning the input has no more lines to give, it raises EOFError.11

priority = input("Priority (high, normal, low): ")
print(type(priority), priority)

At a terminal the prompt appears and the script waits. Type 42 and press Enter, and it prints <class 'str'> 42: digits typed at a prompt are still text. Turning them into a number is a cast, which Thursday's page covers. The text also arrives exactly as typed, so " High" and "high" are different strings.

The limit of input() is that it blocks until a line arrives. A script that calls it unconditionally hangs or raises EOFError when it runs unattended or under a test runner (a program such as pytest that runs your code with nobody at the keyboard), and the usual guard is to check sys.stdin.isatty() first.11

Standard streams, redirection and the isatty guard

A process is one running program, and a stream is a channel that text flows through, one line after another. Every process gets three standard streams:

  • stdin for input,
  • stdout for normal output and
  • stderr for warnings and errors.

At a terminal all three are connected to the window you type in. In Python, sys.stdout and sys.stderr are separate text streams, so a shell can send them to different places.15

In a shell,

  • > redirects stdout to a file,
  • 2> redirects stderr, and
  • | pipes one program's stdout into the next program's stdin.

That is the reason a warning goes to stderr. Someone who saves the board with > board.txt still sees the warning on screen, and the file holds only the board.

sys.stdin.isatty() is true when standard input is a character device (a device that passes characters one at a time, such as an interactive terminal), and false when it is a pipe or a regular file.1516 That makes isatty() a guard for prompts. The script below uses if for that guard: its indented line runs only when the condition is true.

import sys

title = "Login page returns 500"
if sys.stdin.isatty():
    title = input("Title: ")
print(f"board: {title}")
print("warning: ticket 101 is past its SLA", file=sys.stderr)

Saved as ticket_desk.py and run at a terminal, it asks for a title and prints the board line with what you typed. Run with something piped into it, it keeps the sample and prints board: Login page returns 500 without waiting. Either way the warning goes to stderr. Friday's page teaches if properly.

python ticket_desk.py
echo "" | python ticket_desk.py
python ticket_desk.py 2> err.txt

The second command tests the unattended path safely: echo prints its text to stdout, and the | hands that text to the script as its input, so isatty() is false. Do not fake an empty input on Windows by redirecting from NUL, Windows' always-empty input. It also reports true, so the script enters the guard, input() meets end of file and raises EOFError.15 The third command leaves the prompt and the board on screen and puts the warning line in err.txt.

Buffering matters once output is piped. A buffer is memory where output waits before it is written. Standard output is line-buffered at a terminal (written at every newline) and block-buffered otherwise (written when the buffer fills), so piped text can lag; flush=True on a print call writes it at once.15

Takeaways
  • Print joins its values with a separator and ends the line with an ending.
  • Input always returns a string.
  • Standard output and standard error are separate streams, so a shell can redirect them separately.
  • Guard prompts with the terminal check so a script still runs when nobody is at the keyboard.
Say it in an interview

input writes the prompt, reads one line, strips the newline and always gives me a str, so if I need a number I convert it myself. At end of file it raises EOFError.

stdout is for the program's normal output and stderr is for warnings and errors. They're separate streams, so the shell can redirect them separately: I can save the output to a file or pipe it on, and still see the warnings.

I guard prompts with sys.stdin.isatty, so the script still runs unattended or under a test runner instead of hanging or hitting end of file.

Practice

Practice

Ten retrieval questions, at least one per section. Answer each out loud before you open it.

A script stops with IndentationError and prints nothing at all, not even its first line. What went wrong, and why did no line run?

A line was dedented to a level that matches no enclosing block. Indentation is part of the grammar, and Python checks the layout of the whole file before it runs any line, so nothing runs.

Name four PEP 8 layout rules, and say what wins when your team's codebase disagrees with PEP 8.

Four spaces per indent level, lines of at most 79 characters, two blank lines around top-level functions and classes, and imports at the top after the docstring with the standard library first. The project's own style guide wins, and consistency inside one module matters most.

What is the difference between a comment and a docstring?

A comment is thrown away by the tokenizer. A docstring is a string literal that is the first statement of a module, function or class, and it is kept at run time as the __doc__ attribute.

A diff changes SLA_HOURS_HIGH = 4 to SLA_HOURS_HIGH = 8 and leaves the comment "High-priority tickets breach after four hours" above it. What do you say in the review?

The comment now contradicts the code, which PEP 8 calls worse than no comment. Ask the author to update or delete it in the same commit, and to keep the part that says why the number is what it is.

After owner = reporter and then reporter = "Grace Hopper", what is owner, and why?

Still the original string. The first assignment bound owner to the same object as reporter, and the second rebound only reporter, so owner kept pointing at the old object.

Why is 0.1 + 0.2 == 0.3 false, and what is True + 1?

Binary floats cannot store most decimal fractions exactly, so the sum is 0.30000000000000004 and == compares exactly. True + 1 is 2, because bool is a subclass of int.

What are -7 // 2, -7 % 2 and -2 ** 2?

-4, because // floors toward negative infinity; 1, because % takes the sign of the right operand; and -4, because ** binds tighter than the unary minus.

With priority = "low", what does priority == "high" or "normal" evaluate to, and how do you fix the check?

The string "normal". The comparison is false, so or returns its right operand, which is a truthy non-empty string, so the check passes for every ticket. Write the comparison out for each value: priority == "high" or priority == "normal".

Why is round(2.5) equal to 2, and why is round(2.675, 2) equal to 2.67?

Ties round to the even neighbour, and 2.5 is stored exactly, so that one is the tie rule. 2.675 cannot be stored exactly; the stored value is slightly below it, so the second result comes from float representation.

What type does input() return, and why does a script guard its prompts with sys.stdin.isatty()?

Always str, even when the person types digits. Unguarded, input() hangs or raises EOFError when the script runs unattended or under a test runner; the guard is false for a pipe or a file, so piped runs keep their default values. On Windows the NUL device also reports true, so test the unattended path with a pipe.
