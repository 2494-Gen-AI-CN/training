This is the first page of the program, so it assumes only what you bring from university: Python syntax, the clone, add, commit and push loop, and the difference between a compiler and an interpreter. A short on-ramp covers what Python is, what a team expects from you, and a check that your shell runs Python 3.15. On-ramp

Python, the job, and a setup you can trust

You know most of this from university; the aim is a machine that runs the interpreter you think it runs.

What Python is and why teams pick it

Python is an interpreted, interactive, object-oriented language with modules, exceptions, dynamic typing, very high level dynamic data types and classes.1 Memory is reclaimed by reference counting plus a cyclic garbage collector.2 Teams choose it for back-end and data work mostly for the standard library, which covers internet protocols and operating-system interfaces among much else,1 and for readability: "Readability counts" is a line of the Zen of Python that people still quote in code review.3

The Python you run is CPython, the reference implementation, pinned here at 3.15.2 Its limit worth naming early is the global interpreter lock, which lets only one thread execute Python bytecode at a time, so CPU-bound threads do not run in parallel.2 You spot a Python script in another repository by a #!/usr/bin/env python3 first line or an if __name__ == "__main__": block at the bottom.

Professionalism: updates people can read

The program opens with Revature's house rules on attendance, communication, written updates and conduct. The Agile principles say business people and developers must work together daily and that the team regularly reflects on how to become more effective,4 and Scrum rests on transparency, so problems are made visible early instead of reported late.5 A spoken update leaves no record, so distributed teams pair short meetings with written status notes in a fixed shape (done, doing, blocked).

Which Python does your shell run?

python --version prints the version and exits.6 On Windows the py launcher ships with the python.org installer, and py -0p lists every interpreter it can find with its path.7 Inside Python, sys.executable is the absolute path of the interpreter actually running.8

python --version
py -0p
where.exe python
python -c "import sys; print(sys.executable)"

The first line should print a version starting Python 3.15. where.exe python lists every python on PATH in search order, and the shell runs the first. If that path contains WindowsApps, it is the Microsoft Store app execution alias, which opens the Store instead of an interpreter; turn it off under Settings, Apps, Advanced app settings, App execution aliases, or use py.7 The trade-off is that py exists only on Windows, so instructions shared with macOS or Linux teammates still say python or python3.7

Interpreted, compiled, and the bytecode in between

A compiler translates the whole program ahead of time; an interpreter executes the source as it goes. Python is interpreted in the everyday sense, because python hello.py runs the source with no separate build step.2 Under the hood CPython compiles the source to bytecode and runs it on a virtual machine, the same shape as the JVM.2 Bytecode for imported modules is cached in __pycache__, with the interpreter version in the file name.9

python hello.py
python -c "import hello"

With a five-line hello.py, both lines print Hello, Toronto. Only the second leaves __pycache__/hello.cpython-315.pyc behind, because the module run directly from the command line is always recompiled and never cached.10 That folder is why a Python .gitignore lists __pycache__/, and a SyntaxError reported before any line runs is the compile step speaking. The virtual machine costs speed, and CPython 3.11's specializing interpreter was reported to run 10 to 60 percent faster than 3.10.11

The REPL and Jupyter notebooks

python with no arguments starts the REPL with its >>> prompt, and exit() leaves it.12 The last printed value is kept in the name _,13 and python -i script.py runs a script and leaves the REPL open with its names defined.6

python -i hello.py
greet("Ada")
_ + "!"
exit()

The script prints Hello, Toronto and the prompt appears. The next line echoes 'Hello, Ada', and the one after echoes 'Hello, Ada!' because _ held the previous value. A common slip is typing git status at >>>: that prompt means Python, not the shell, is listening, so the line is read as Python and rejected with a SyntaxError.12

A Jupyter notebook sends each code cell to a running kernel that holds its state, a REPL that remembers every cell you ran.14 That state follows execution order, shown by the In [3]: counters, rather than page order, which is why "Restart and Run All" sometimes gives a different answer.15

Where Python sits in a full stack

A web application has a browser front end, a server back end and a database. python.org lists web development and scientific and numeric work among Python's main uses,16 and here it sits in the back end and the data layer. The layers talk HTTP, a stateless protocol in which a client sends a request and a server returns a response.17 The standard library's python -m http.server shows a back end answering, but it is not recommended for production because it implements only basic security checks.18 A full-stack repository usually shows frontend/ and backend/ folders beside a docker-compose.yml.

Say it in an interview

Python is an interpreted, dynamically typed, garbage-collected language. Teams pick it for back-end and data work because of the standard library and how easily the code reads. CPython's main limit is the global interpreter lock, which stops CPU-bound threads running in parallel.

It's both, really. CPython compiles my source to bytecode and runs it on a virtual machine, and it caches the bytecode of imported modules in pycache, which is why that folder goes in the gitignore.

Team practice

The software development life cycle, waterfall and Agile

The rest of the day is about how software teams work. The phases underneath every method stay the same, so the vocabulary starts there.

The phases every project passes through

The software development life cycle, or SDLC, is the sequence of phases every piece of software passes through regardless of method: requirements and planning, design, implementation, testing, deployment and maintenance. Where methods differ is how often they go round. Waterfall runs the phases once, in order. Agile methods repeat all of them in short cycles, and Scrum, founded on empiricism (transparency, inspection and adaptation), runs every phase inside every Sprint.5 The Scrum Guide says all the work needed to reach the Product Goal, including Sprint Planning, the Daily Scrums, the Sprint Review and the Retrospective, happens within Sprints.5

That answers a common interview question: where does testing happen in Scrum? Inside the Sprint. Each Increment is additive to all prior Increments and thoroughly verified, so a team cannot push testing into a later phase.5 The limit is that the Guide calls Scrum "purposefully incomplete": it does not tell you how to design or how to deploy, and each team fills those gaps with its own practices.5 On a real team you see the phases as columns on a board (To Do, In Progress, Review, Done), and you see testing and deployment as a pipeline file that builds and tests the code on every push.

Waterfall: every phase once, in order

Waterfall is the sequential model. Each phase is completed and signed off before the next begins, requirements are frozen early, and working software appears only at the end. Its appeal is predictability: a fixed scope, a fixed plan and a document trail for every decision. Its cost is the feedback loop. A wrong assumption written into the requirements in month one is discovered in testing, months later, when every phase built on it has to be reopened.

The shorter the cycle between building something and a customer seeing it, the cheaper a wrong assumption is to fix. Most of what Agile methods do follows from that idea. It also tells you when a waterfall-like plan can still be the honest choice: when the requirements are genuinely fixed and well understood, and changing them later would be expensive for reasons outside the software. You recognise the two styles on sight: a Gantt chart with phases in sequence is waterfall, and a Sprint board with a burndown chart is Agile.

Agile: the Manifesto and short cycles

The Manifesto for Agile Software Development was written in 2001 and has four value statements. It values individuals and interactions over processes and tools, working software over comprehensive documentation, customer collaboration over contract negotiation, and responding to change over following a plan.19 The sentence after the four values matters in interviews: there is value in the items on the right, and the signatories value the items on the left more. Agile does not mean "no documentation" or "no plan".19

The twelve principles behind the Manifesto turn the values into practice. Teams deliver working software frequently, "from a couple of weeks to a couple of months", with a preference for the shorter timescale; they welcome changing requirements, even late in development; working software is the primary measure of progress; and continuous attention to technical excellence and good design enhances agility.4 Scrum is one way to live by these. The Scrum Guide defines it as a lightweight framework founded on empiricism and lean thinking, and never claims to be the definition of Agile.5 If an interviewer says "Agile" and means "Scrum", answer the question, then note the difference in a sentence.

The Definition of Done

A phase list needs an exit test. In Scrum it is the Definition of Done, a formal description of the state of the Increment when it meets the quality measures required for the product.5 It is the checklist that decides whether an item has really passed through every phase. A Definition of Done for a small team repository might read:

  • the change is merged into main and pushed to the shared remote
  • no conflict markers are left in any file
  • every commit message has a summary line a teammate can read
  • the README says how to run the code

Without one, "done" means whatever the person reporting it wanted it to mean, and the Sprint Review turns into an argument. With one, an item that is coded but untested is visibly not done.

Say it in an interview

The SDLC phases are requirements, design, implementation, testing, deployment and maintenance. Waterfall runs them once, in sequence, with a sign-off between each, so working software arrives at the end. Scrum runs all of them inside every Sprint, so a customer sees working software every few weeks.

Two values from the Agile Manifesto are working software over comprehensive documentation and responding to change over following a plan. The Manifesto still values documentation and plans; it just values the left-hand items more.

Team practice

Scrum: three accountabilities, five events, three artifacts

Scrum is the framework you are most likely to meet on your first team, and the 2020 Scrum Guide is short enough to read in one sitting. Interviewers ask about it in numbers, so learn the numbers: three accountabilities, five events, three artifacts.5

Who is on a Scrum Team

A Scrum Team has three accountabilities: the Product Owner, the Scrum Master and the Developers.5 The Product Owner owns the Product Backlog and decides its order. The Developers are the people who build the Increment, and they are the ones accountable for sizing the work. Only the Product Owner can cancel a Sprint.5 As a graduate hire you will be one of the Developers, which means the estimates, the daily plan and the quality of the Increment are partly yours from your first week.

The Guide also sets a size limit with a reason attached. A Scrum Team is typically 10 or fewer people, small enough to stay nimble, because smaller teams communicate better and are more productive. A larger group is expected to reorganise into several cohesive Scrum Teams focused on the same product.5 Every extra person adds conversations the team has to keep up with, and a fifteen-minute Daily Scrum with fifteen people in it stops being a planning meeting.

The five events and their time-boxes

The five events are the Sprint, Sprint Planning, the Daily Scrum, the Sprint Review and the Sprint Retrospective. The Sprint is the container for the other four. It has a fixed length of one month or less, and a new Sprint starts immediately after the previous one ends.5

Sprint Planning addresses three topics: why this Sprint is valuable, what can be done in it, and how the chosen work will get done.5 The answer to the first question is the Sprint Goal, the single objective that tells everyone why the Sprint matters even if some items slip. The Daily Scrum is time-boxed to 15 minutes, and the Developers choose its structure and techniques.5 The familiar stand-up questions ("What did I do yesterday, what will I do today, any blockers?") are one common structure, not a rule from the Guide. For a one-month Sprint, Sprint Planning is capped at eight hours, the Sprint Review at four hours and the Retrospective at three hours, with shorter caps for shorter Sprints.5

Sprint Review versus Sprint Retrospective

These two are the follow-up question people stumble on, because both happen at the end of the Sprint. The Sprint Review inspects the outcome of the Sprint with stakeholders and decides what to adapt next; it is about the product. The Sprint Retrospective plans ways to increase the quality and effectiveness of the team itself; it is about how the team worked.5 A retrospective board with Start, Stop and Continue columns is the version you will see most often. The Retrospective is also where the Agile principle about reflecting at regular intervals and tuning behaviour becomes a calendar entry.4

The three artifacts and their commitments

The three artifacts are the Product Backlog, the Sprint Backlog and the Increment, and each carries a commitment that gives it a purpose: the Product Backlog has the Product Goal, the Sprint Backlog has the Sprint Goal, and the Increment has the Definition of Done.5 The Sprint Backlog is the Sprint Goal, the Product Backlog items selected for the Sprint, and a plan for delivering them.5

Take a single backlog item such as "set up the team's shared repository". It is pulled into the Sprint Backlog at Sprint Planning, someone opens a feature branch for it, its commits land on that branch, it is merged once it meets the Definition of Done, and the merged result is part of the Increment shown at the Sprint Review. Burndown charts, story points and velocity are common additions, and the Guide defines none of them.5

Say it in an interview

Scrum has five events. The Sprint is the container, one month or less. Inside it there's Sprint Planning, where the team agrees the Sprint Goal and the work, a fifteen-minute Daily Scrum for the Developers, a Sprint Review with stakeholders, and a Retrospective for the team.

The Review is about the product: we show stakeholders what we built and decide what to change next. The Retrospective is about us: how we worked, and one or two things we'll do differently in the next Sprint.

Team practice

Story points: sizing work by comparison

What a story point measures

The Scrum Guide says the Developers who will do the work are responsible for sizing Product Backlog items.5 It does not say how. Story points, planning poker and velocity appear nowhere in the Guide; they are practices that teams layer on top of it.5 A story point is a relative size: the team gives each item a number by comparing it with items it has already sized, usually on a Fibonacci-like scale of 1, 2, 3, 5, 8 and 13. The widening gaps are deliberate. Nobody can tell a 7 from an 8 in advance, so the scale does not ask.

Relative sizing works because people are poor at saying "this will take eleven hours" and fairly good at saying "this is about twice the size of that". A point folds effort, complexity and uncertainty into one number. The limit follows from the same fact: the Guide gives no estimation unit, so points are a team convention. One team's 5 is not another team's 5, and neither of them is hours.5

Planning poker

Planning poker is a common way for a team to reach a number together. Each Developer puts forward a size from the scale, and the team agrees one figure for the item by comparing it with items it has sized before. The value of the practice is the conversation it forces. When one person says 3 and another says 8, the question "why is yours a 3 and mine an 8?" usually brings out work that one of them had not thought about. The number belongs to the whole team, so the loudest voice in the conversation does not get to set it.

Take two toy items. The team has already agreed that "add a hello script" is its reference 1.

ItemSizes put forwardAgreed
Add a hello script1, 1, 1, 21
Set up the shared repository with branch protection3, 3, 5, 85

The first item needs little discussion. On the second, the person who said 8 was counting access rights, a README and the protection rules themselves, and the people who said 3 knew a repository template already existed. After comparing it again with items the team has sized, everyone settles on 5, meaning several times the size of the hello script. You recognise the practice by cards or buttons showing 1, 2, 3, 5, 8, 13, and by a "Story Points" field on a ticket.

Velocity, and why it does not travel between teams

Velocity is the number of points a team completes per Sprint. It is meaningful only within one team, measured over several Sprints. Its job is forecasting: the Guide notes that the more the Developers know about their past performance, their upcoming capacity and their Definition of Done, the more confident they will be in their Sprint forecasts.5 A team that finished 20, 22 and 19 points in its last three Sprints has a reasonable basis for pulling about 20 into the next one.

Comparing velocity between teams is misleading because each team built its own scale. A team that calls a small change a 3 will show double the velocity of a team that calls the same change a 1 or a 2, while doing the same work. Once velocity becomes a target that managers compare, the easiest way to raise it is to inflate the estimates, and the forecast stops meaning anything.

Backlog refinement

Estimates do not appear for the first time at Sprint Planning. Product Backlog refinement is the ongoing work of adding detail such as description, order and size to items, and breaking large items into smaller ones.5 By the time Sprint Planning needs a number, the item should already have one, and large items have already been broken down. What reaches the Sprint Backlog is the Sprint Goal, the selected items and a plan for delivering them.5

Say it in an interview

A story point is a relative measure of effort that the team agrees by comparing items, usually on a scale like 1, 2, 3, 5, 8, 13. It isn't hours. Scrum doesn't define points at all; it only says the Developers size the work.

Comparing velocity between teams is misleading because each team's points are its own scale. A five on my team and a five on yours don't mean the same thing, so velocity only helps a team forecast its own next Sprint.

Mechanics

Version control and the three areas

Local, centralised and distributed version control

Version control answers three questions a team keeps asking: what changed, who changed it, and how do two people change the same code without overwriting each other. Version control systems have come in three generations: local systems such as RCS, centralised ones such as CVS and Subversion, where one server holds the history and each client checks out a working copy, and distributed ones such as Git and Mercurial, where every clone fully mirrors the repository, history included.20 A centralised server is a single point of failure: while it is down nobody can collaborate or save versioned changes, and if its disk is lost without backups the history goes with it. In a distributed system any clone can restore the server.20 Because most Git operations need only local files, log, diff, commit and branch work offline, and only push, pull and fetch touch the network.21

Git is the tool; GitHub is one service that hosts Git repositories as remotes you reach over HTTPS or SSH.22 If every clone has the full history, the GitHub copy is simply the one the team agrees to integrate through. You recognise the difference in a README: svn checkout means a centralised system, git clone a distributed one, and a .git folder in the project root means the folder is a Git repository.

Three areas, three states

Git stores each commit as a snapshot of the whole tree rather than a list of per-file differences, and an unchanged file is stored as a link to the previous identical one. It checksums everything with a hash before storing it, so content cannot change without Git noticing; that hash is the 40-character commit id. A file is in one of three states, modified, staged or committed, matching three areas: the working tree, the staging area and the .git directory. The staging area is a file in the Git directory that stores what will go into the next commit, and its technical name is the index.21 git status reports which state each file is in.23

git status
git diff
git add hello.py
git diff
git diff --staged

Run this after editing a tracked hello.py. git status lists the file under "Changes not staged for commit" and the first git diff shows your edit, because plain git diff compares the working tree with the index. After git add, the second git diff prints nothing and git diff --staged shows the change, because it compares the index with the last commit.24 The first line of git status, "On branch main", comes from HEAD, the pointer to the branch you are on. One shortcut has a cost: git commit -a stages every change to files Git already tracks, which saves the add, and silently leaves a new, untracked file out of the commit.25

Initializing a repository

git init creates a .git subdirectory, and nothing is tracked until you git add it; add both starts tracking new files and stages modified ones. git clone copies an existing repository with its history, while git init starts an empty one.26 Git also needs to know who you are. It guesses an identity from the OS user name and host name, and when it cannot (the usual case on Windows) the first commit fails with "Author identity unknown" until user.name and user.email are set. init.defaultBranch (Git 2.28 and later) names the first branch of new repositories and defaults to master unless you set it.27

git config --global user.name "Ada Lovelace"
git config --global user.email "ada@example.com"
git config --global init.defaultBranch main
mkdir team-repo
cd team-repo
git init
git status

git init prints "Initialized empty Git repository in" followed by the path of the new .git folder, and git status answers "On branch main", "No commits yet" and "nothing to commit". git init -b main names the first branch for one repository without touching the global setting.28 The first or second commit is usually a .gitignore; for Python that means at least __pycache__/, *.pyc and .venv/, and a pattern added after a file was committed does not untrack it.29 The whole history lives in .git, so deleting that folder deletes the history and leaves the files, and running git init inside a folder that is already part of a repository (all of Documents, say) creates a nested repository that confuses every later command.

Say it in an interview

Git has three areas. The working tree is where I edit, the staging area or index holds exactly what goes into the next commit, and the dot-git folder stores the committed snapshots. git add stages a change, git commit records it, and git status tells me where each file stands.

In a centralised system like Subversion one server holds the history, so when it's down nobody can commit. In Git every clone has the full history, so most commands work offline and any clone can restore the server.

Mechanics

Commit, branch, merge and conflicts

With a repository and an identity in place, the everyday loop is commit, branch and merge. A conflict is what happens when two branches change the same line, and resolving one by hand is a skill every reviewer expects.

Commit, branch and merge

git commit -m "message" records the staged snapshot; without -m it opens the configured editor. git log --oneline lists one commit per line.25 A branch is a lightweight movable pointer to a commit.30 git branch feature creates one and leaves you where you were; git switch (Git 2.23 and later) moves HEAD, and git switch -c creates and switches in one step.31 Forget the switch and your commits land on main, so the later merge reports "Already up to date". Short-lived feature branches merged into a main line are how teams keep work in progress away from everyone else. Because a branch is only a pointer, creating one costs almost nothing, and HEAD tells Git which pointer moves forward when you commit.30

git add hello.py .gitignore
git commit -m "Add greet function and .gitignore"
git switch -c feature/farewell
git add hello.py
git commit -m "Add farewell function"
git switch main
git merge feature/farewell

Between the switch and the second add, hello.py gains a farewell function. The merge prints "Updating" with two short hashes, then "Fast-forward": main had no new commits since the branch split off, so Git only moved the pointer. When both branches have new commits, Git creates a merge commit with two parents instead.32 git merge --no-ff forces a merge commit even when a fast-forward is possible, for teams that want every feature visible in the graph.33

When both branches changed the same line

When both sides changed the same lines, Git stops with CONFLICT (content) and writes markers into the file: <<<<<<< HEAD opens your side, ======= divides, and >>>>>>> plus the branch name closes theirs. You edit the file, remove all three marker lines, then git add and git commit; git merge --abort backs out entirely.3233

<<<<<<< HEAD
print(greet("Toronto") + "!")
=======
print(greet("Toronto").upper())
>>>>>>> feature/shout

Here main added an exclamation mark and feature/shout upper-cased the greeting. Keeping both ideas gives one line, print(greet("Toronto").upper() + "!"), which prints HELLO, TORONTO!. After git add hello.py and git commit -m "Merge feature/shout into main", git log --oneline --graph draws the two branches splitting and rejoining at a commit with two parents.34

How big a conflict gets is largely in your hands. A branch that lives for a day and is merged soon shares few changed lines with anyone else's work, so it collides less often, and when it does the markers surround a few lines rather than half a file. Long-lived branches drift apart, and the merge at the end of them is where whole afternoons go. In someone else's history you recognise a resolved conflict as a diamond in the graph whose merge commit names the branch it brought in, such as "Merge feature/shout into main". A file in a pull request that still contains <<<<<<< is the mistake a reviewer spots first, because the file no longer runs.

Say it in an interview

git branch creates a branch but leaves me where I am; git switch with -c creates it and moves me onto it. If I forget to switch, my commits land on main and the later merge has nothing to do.

A fast-forward happens when main has no new commits since my branch split off, so Git just moves the pointer. If main has moved too, Git makes a merge commit with two parents, and if both sides touched the same lines it stops with a conflict that I resolve by hand.

Mechanics

Remotes: push, fetch and pull

Naming a remote and pushing with an upstream

A remote is another copy of the repository that you exchange commits with. origin is the default name Git gives the remote you cloned from, and it is only a short name for a URL; git remote add registers one and git remote -v lists them.35 What a hosting service keeps for you is a bare repository, one with no working tree.36 A bare repository in the next folder therefore behaves exactly like GitHub, minus the sign-in.

git init --bare ../origin.git
git remote add origin ../origin.git
git remote -v
git push -u origin main
git status

git remote -v prints origin twice, once marked (fetch) and once (push). The push reports * [new branch] main -> main and that main is set up to track origin/main, and git status now says the branch is up to date with origin/main. The -u sets the upstream, so later git push and git pull need no arguments.37 The setting is stored, which is why you pass -u once per branch. Before it, a plain git push stops with "has no upstream branch". With a GitHub URL in place of ../origin.git the commands are the same.

Fetch first, then pull

git fetch downloads new history from the remote without changing your working tree.38 git pull is git fetch followed by a merge of the tracked upstream branch, or a rebase when pull.rebase is set.39 That makes pull convenient and occasionally surprising: it can create a merge commit you did not plan or drop a conflict into your files. Fetching first lets you look before you integrate.

git fetch
git status
git log --oneline origin/main
git pull

Say a teammate cloned the same remote and pushed a commit that adds README.md. After the fetch, git status reports that your branch is behind origin/main by 1 commit and can be fast-forwarded, and the log of origin/main shows the teammate's commit on top of yours. Nothing in your folder has changed yet. The pull then prints "Fast-forward" and the README appears.

When the two histories have diverged

Now suppose you commit locally before pulling, and the teammate pushes again. Each side has a commit the other lacks. When neither pull.rebase nor a --rebase, --no-rebase or --ff-only flag says how to reconcile them, Git 2.33.1 and later refuses with "Need to specify how to reconcile divergent branches"; versions 2.27 to 2.33.0 printed the same text as a warning and merged anyway.3940 Stating the strategy yourself makes the behaviour the same on every machine:

git pull --ff-only
git pull --no-rebase --no-edit
git log --oneline --graph
git push

The first command fetches, sees the histories cannot be fast-forwarded, and stops with "Not possible to fast-forward, aborting." without touching your files. The second merges the two histories with a merge commit, and the graph shows a new split and rejoin.39 Rebasing is the other way to reconcile, and week 2 covers it. The same rule explains a rejected push: the remote refuses a non-fast-forward update, one where the remote branch has commits you do not have, so you fetch and merge before pushing again rather than overwrite a teammate's work.37 On screen it reads ! [rejected] main -> main (fetch first).

Authenticating to GitHub

GitHub remotes can be addressed over HTTPS or SSH. HTTPS pushes authenticate with a personal access token or a credential helper, and never with your account password; Git Credential Manager, bundled with Git for Windows, opens a browser sign-in on the first push.22 SSH authenticates with a key pair registered on GitHub instead of a token.22 The usual first-day failure is a password typed at an HTTPS prompt and rejected; the fix is the token or the browser sign-in.

Say it in an interview

origin is just the default short name for the remote URL a repository was cloned from. The -u on the first push sets my branch's upstream to origin/main, and Git remembers it, so after that plain push and pull know where to go.

A push gets rejected when the remote branch has commits I don't have. I fetch, look at what came in, merge it, and push again, rather than overwrite my teammate's work.

Practice

The Git exercise: a history a reviewer can read

The day's exercise is a real repository on GitHub with a feature branch, a merge, one resolved conflict and commit messages a teammate could read, marked against a rubric. Git accepts any commit, so the rubric marks what Git does not check: whether the history explains itself and whether the merge really happened.

Commit messages that tell the story

A good commit message is a short summary line of about 50 characters in the imperative mood ("Add login form", not "Added" or "fix"), a blank line, then a body that explains what changed and why rather than how.41 The diff already shows how. Tools such as git log --oneline and git shortlog show only the first line, so the summary has to make sense on its own.42

git commit -m "Document how to run hello.py" -m "New teammates kept asking how to start the script, so the README now says it."
git log -1
git log --oneline

git log -1 shows the full message: the summary, a blank line, and the body sentence explaining why the change was made.34 git log --oneline shows only "Document how to run hello.py" next to its short hash, and the commits below it should read the same way, as a list of changes someone could review one at a time.

Pro Git also asks for each commit to be a logically separate changeset.41 That takes discipline before you commit, because you split your work into focused pieces instead of saving everything at the end of the day. The payoff goes to whoever reads the log next, often you, who can follow one change at a time and find the commit that introduced a bug.

Proving a conflict is really resolved

The two classic mistakes are committing a file with <<<<<<< still inside it, and running git merge --abort then carrying on as if the merge had happened. Resolving means editing the file, removing all three marker lines, then staging and committing.32 Two checks before the commit catch the first mistake:

git diff --check
python hello.py
git add hello.py
git commit -m "Merge feature/shout into main"

git diff --check warns when your changes introduce conflict markers or whitespace errors, and prints nothing when the file is clean.24 Running the script is the second check: a leftover marker is a SyntaxError, and a clean resolution prints HELLO, TORONTO! followed by the farewell line. The graph is the check for the second mistake. After a real resolution, git log --oneline --graph shows a merge commit with two parents; after an abort it shows no merge at all.

Branching strategies

Feature branches isolate work in progress from the main line until it is ready to merge.43 The alternative is everyone committing straight to main, which is simpler and works for one person, and turns every half-finished change into everyone's problem once there are several. Teams choose a strategy and write it down, usually in the same working agreement that holds the Definition of Done. For the exercise the strategy is fixed: work on a feature branch, merge it into main, and push both to GitHub.

Say it in an interview

A good commit message has a short imperative summary, around fifty characters, like "Add farewell function", then a blank line and a body that says what changed and why. The summary has to stand alone, because one-line logs only show that.

To resolve a conflict I read both sides between the markers, write the version that keeps what each change meant, delete all three marker lines, run the code, then add and commit. If I'm lost, merge abort puts me back where I started.

Check yourself

Ten retrieval questions, at least one per section. Answer each out loud before you open it.

Is Python compiled or interpreted, and why does __pycache__/ belong in .gitignore?

Both. You run the source with no separate build step, but CPython compiles each module to bytecode and runs it on a virtual machine. Bytecode for imported modules is cached in __pycache__; it is generated and machine-specific, so it is never committed.

On a Windows laptop, python opens the Microsoft Store. What is happening, and what are two ways out?

The first python on PATH is the Store's app execution alias, under WindowsApps. Turn the two aliases off under Settings, Apps, Advanced app settings, App execution aliases, or use the py launcher, which finds installed versions itself.

Where does testing happen in Scrum, and what decides when an item is done?

Inside every Sprint, because each Increment is thoroughly verified before it counts. The Definition of Done, the team's formal description of the quality an Increment must meet, decides when an item is done.

What is the difference between the Sprint Review and the Sprint Retrospective?

The Review inspects the product outcome with stakeholders and decides what to adapt next. The Retrospective looks at the team itself and plans ways to raise its quality and effectiveness.

Why is comparing velocity between two teams misleading?

Story points are a team convention with no shared unit, so one team's 5 is not another team's 5. Velocity only helps a team forecast its own next Sprint, and comparing it invites inflated estimates.

You edit hello.py and run git add hello.py. Why does git diff now print nothing, and what shows the change?

Plain git diff compares the working tree with the index, and they now match. git diff --staged compares the index with the last commit and shows the staged change.

You ran git branch feature, made two commits, switched to main and merged feature. Git said "Already up to date". What happened?

git branch created the branch without switching to it, so both commits landed on main and feature had nothing new. git switch -c feature creates and switches in one step.

What does -u do in git push -u origin main, and why do you only need it once?

It sets origin/main as the upstream of your local main. Git stores that setting, so later plain git push and git pull know where to go.

git pull --ff-only stops with "Not possible to fast-forward". What does that tell you, and how do you continue?

Your branch and its upstream have diverged: each has a commit the other lacks. Run git pull --no-rebase to merge the two histories with a merge commit, resolve any conflict, then push.

A reviewer sends back a branch whose log reads "fix", "update", "final2". What should each summary line look like instead, and what two checks prove a conflict was resolved before you commit?

A short imperative summary of about 50 characters that says what changed, such as "Add farewell function", with a body explaining why when it needs one. Before committing a resolution, git diff --check should print nothing and the script should run without a SyntaxError.

Deep dive: how a marker proves a conflict was real

Optional. ~5 minutes.

The exercise asks for one resolved conflict, and whoever marks it needs a way to check that the two parents of your merge commit genuinely collided rather than merging cleanly. Git 2.38 added git merge-tree --write-tree <branch1> <branch2>, which performs a real merge of two commits in memory without touching the working tree or the index. It prints the resulting tree and exits 1 with CONFLICT (content) lines when the two sides genuinely conflict.

Run it on the two parents of your merge commit and you see what a marker sees: a clean exit means the "conflict" was not one, and a CONFLICT (content) line naming your file means it was. You need Git 2.38 or later for this command; everything else on the page works from Git 2.28.
