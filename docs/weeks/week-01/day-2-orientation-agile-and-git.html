On-ramp

Thirty minutes to confirm your setup, not to learn Python

Python is general-purpose; python.org lists web development, scientific and numeric work, software tooling, business applications, education and desktop GUIs. In the full stack (browser front end, server back end, database, infrastructure) Python's seat in this course is the back end and the data/ML layer, and 01_tooling_check.py prints that map with both seats marked. "Professionalism at Revature" is house rules about attendance, communication, written updates and conduct; there is no external source for it, so treat it as policy rather than theory.

You know the compiler-versus-interpreter distinction from university. In practice, python hello.py runs the source with no separate build step, which is what "interpreted" means day to day; under the hood CPython compiles each module to bytecode and caches it in __pycache__/*.pyc. That folder is build output, not source, and it belongs in .gitignore; STEP 2 of the demo shows the bytecode with dis.

The tooling check is one line: py --version proves the shell runs the interpreter you think it does. Running python with no arguments opens the REPL at the >>> prompt, where the last printed value is kept in the read-only name _ and you leave with exit(). A Jupyter Notebook is a REPL with a memory: each cell's output appears underneath it, in execution order rather than top to bottom. The pitfall is typing git status at the >>> prompt, getting a SyntaxError, and deciding Python is broken. Tell the PowerShell prompt, the REPL prompt and a running script apart, and the on-ramp is done.

Process

SDLC: the same six phases, walked once or walked in loops

Every piece of software passes through the same phases regardless of methodology: requirements and planning, design, implementation, testing, deployment and maintenance. That is the software development life cycle, and methodologies differ only in how they schedule it. Waterfall signs off each phase before the next begins, so requirements are frozen early and working software appears only at the end. Agile repeats all the phases in short cycles; the Agile principles call for delivering working software frequently, "from a couple of weeks to a couple of months", and for welcoming changing requirements even late in development.

02_sdlc_waterfall_vs_agile.py schedules one small backlog both ways. The waterfall timeline runs ten weeks with requirements signed off in week 2, so when the customer asks for GitHub login in week 6 the change is queued until after release. The Agile schedule runs five two-week Sprints that each pass through every phase and ship an Increment; the same change goes into the next Sprint's backlog.

The Manifesto itself (2001) is four lines: individuals and interactions over processes and tools, working software over comprehensive documentation, customer collaboration over contract negotiation, and responding to change over following a plan. The demo prints them with "over" in the middle because the items on the right still have value; the ones on the left are valued more.

Scrum

Scrum and story points: what the Guide defines, and what teams layer on

Scrum is founded on empiricism (transparency, inspection, adaptation) and runs every SDLC phase inside every Sprint. The 2020 Scrum Guide defines three accountabilities (Product Owner, Scrum Master, Developers), five events (the Sprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective) and three artifacts (Product Backlog, Sprint Backlog, Increment). It also sets time-boxes: a Sprint is one month or less, the Daily Scrum is fifteen minutes, and for a one-month Sprint, Planning is capped at eight hours, the Review at four and the Retrospective at three, with shorter caps for shorter Sprints; 03_scrum_and_story_points.py prints them beside a two-week budget.

The Guide says Developers are accountable for sizing backlog items and nothing more: story points and hours appear nowhere in it. Story pointing is a practice layered on top: the team assigns relative effort on a Fibonacci-like scale (1, 2, 3, 5, 8, 13) by comparing each item with the others and with a reference item. Velocity, points completed per Sprint, is meaningful only within one team compared with its own past Sprints.

The demo's planning-poker round shows the mechanics. On item A ("add a hello script") the votes are 1, 2, 2, 1, adjacent on the scale, and the majority settles it at 2. On item B ("set up the team's shared repo with branch protection") the votes are 3, 8, 5, 13, far too wide, so the 3 and the 13 explain themselves, everyone re-votes 5, 5, 8, 5, and the item is a 5. The pitfalls: reading "5 points" as five hours, comparing points between teams, letting the loudest voice set the number. Today's Git exercise is the kind of item that sits in a Sprint Backlog.

Git

Git as the team's workflow: three states and a log that tells a story

Version control comes in three generations: local (RCS) on one machine, centralised (CVS, Subversion) on one server that clients check a working copy out of, and distributed (Git, Mercurial), where every clone holds the full repository, so log, commit and branch work offline and only push, pull and fetch touch the network. Git stores each commit as a snapshot of the whole tree, not as per-file diffs.

A file is in one of three states, modified, staged or committed, matching three areas: the working tree, the staging area (the index) and the .git directory. git status reports which, and 04_git_local_loop.py runs it after every command so the states stay visible. git init creates .git and tracks nothing until you git add, which both starts tracking new files and stages modified ones; skip it and git commit -m reports "no changes added to commit". On a fresh Windows machine the first commit fails with "Author identity unknown" until user.name and user.email are set, and init.defaultBranch (Git 2.28+) names the first branch, master unless set to main. The demo passes these with -c; you set them once:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

The demo's first commit adds hello.py alongside a .gitignore listing __pycache__/, *.pyc and .venv/, the minimum for any Python project. Then git log --oneline shows one commit per line and only the first line of each message. That is why message shape matters: a summary of about fifty characters in the imperative mood ("Add login form", not "Added" or "fix"), a blank line, then a body explaining what and why rather than how. git commit without -m opens the configured editor.

Branching

Branch, merge, and the one conflict you resolve by hand

git branch feature creates a branch but does not switch to it, so your next commits still land on main; when you later merge, Git says "Already up to date" and the feature branch looks empty. git switch feature (Git 2.23+) or git checkout feature moves HEAD, and git switch -c feature creates and switches in one step, the form the demo uses.

STEP 3 of 04_git_local_loop.py commits a greet function on feature, switches back to main and merges. Because main had no new commits since the branch diverged, Git simply moves the pointer and reports "Fast-forward"; no merge commit is created. STEP 4 forces the other case: a greeting branch and main both change line 1 of hello.py, and the merge stops with "CONFLICT (content)". Git has written three markers into the file: <<<<<<< above your side, ======= between, >>>>>>> below theirs. Read both sides, keep the right lines, delete all three marker lines, then git add and git commit; the result is a merge commit with two parents, visible in git log --oneline --graph. git merge --abort backs out entirely: right when you are lost, wrong if you then submit without resolving anything.

The pitfalls the rubric is written against: deleting the markers blindly and committing with <<<<<<< still in the file. After the demo, repeat the loop by hand in a fresh folder, never inside one that is already a repository such as all of Documents, because nested repositories confuse every later command:

mkdir w01d2-git
cd w01d2-git
git init
git add .
git commit -m "Add hello script and Python .gitignore"
git switch -c feature
Remote & exercise

Push, pull, and what the rubric reads

05_git_remote_round_trip.py starts by running git push with no remote so you recognise "No configured push destination" when you meet it later. git remote add origin <url> names the remote and git push -u origin main uploads the branch and sets its upstream, so plain git push and git pull need no arguments afterwards. The demo uses a bare repository as a stand-in for GitHub; your version uses an empty repository created on github.com, and the only extra step is the Git Credential Manager browser sign-in on first push. Over HTTPS, GitHub accepts a personal access token or that credential helper, never your account password.

STEP 3 has a teammate clone and push a commit, the same event as editing the README in the GitHub web UI. STEP 4 separates the two halves of git pull: git fetch downloads the new history without touching the working tree, so git status says "Your branch is behind 'origin/main' by 1 commit" while the file on disk is unchanged. git pull is fetch followed by a merge of the upstream branch (or a rebase, when pull.rebase is set), which is why a pull can produce a merge you did not expect or refuse with "Your local changes would be overwritten by merge". A pull changes your working tree, which a plain download would not.

The Git exercise is today's deliverable, marked against a rubric rather than tests: a real repository on GitHub with a feature branch, a merge, one resolved conflict and commit messages that read as the story of the work. STEP 5 puts "fix" beside "Add greeting function to hello.py" and states the rule the rubric applies. Demo code: 04_git_local_loop.py

STEPs 3 and 4: a feature branch that fast-forwards, then two branches editing the same line so the merge stops with markers and is resolved by hand.

# --- STEP 3: a feature branch and a fast-forward merge ---
git("switch", "-c", "feature")     # creates AND switches (git branch alone does not)
write("hello.py", 'print("Hello, team")\n\n\ndef greet(name):\n    return f"Hello, {name}"\n')
git("commit", "-am", "Add greet function to hello.py")
git("switch", "main")
git("merge", "feature")             # main had no new commits -> pointer just moves
git("log", "--oneline")

# --- STEP 4: force a real conflict on the same line, resolve it, commit ---
git("switch", "-c", "greeting")
write("hello.py", 'print("Hello, Toronto")\n\n\ndef greet(name):\n    return f"Hello, {name}"\n')
git("commit", "-am", "Greet Toronto instead of the team")
git("switch", "main")
write("hello.py", 'print("Hello, cohort 2494")\n\n\ndef greet(name):\n    return f"Hello, {name}"\n')
git("commit", "-am", "Greet the cohort by number")
git("merge", "greeting")            # both sides changed line 1 -> Git stops
with open(os.path.join(REPO, "hello.py"), encoding="utf-8") as f:
    print("\n(cat) hello.py with conflict markers:\n  " + f.read().rstrip().replace("\n", "\n  "))
print("\n(edit) keep the right lines, delete ALL THREE marker lines, then add + commit")
write("hello.py", 'print("Hello, cohort 2494 in Toronto")\n\n\ndef greet(name):\n    return f"Hello, {name}"\n')
git("add", "hello.py")
git("commit", "-m", "Merge branch 'greeting': combine both greetings on line 1")
git("log", "--oneline", "--graph")

Notice that the resolution is a plain edit followed by add and commit: there is no special "resolve" command, and the merge commit's message says what was combined.

Demo code: 05_git_remote_round_trip.py

STEPs 2 to 4: name the remote, push with -u, let a teammate push, then watch fetch leave the working tree alone before pull merges.

# --- STEP 2: name a remote, push with -u so later push/pull need no arguments ---
git("init", "--bare", HUB, cwd=BASE)  # stands in for the empty repo you create on github.com
git("remote", "add", "origin", HUB)
git("remote", "-v")
git("push", "-u", "origin", "main")

# --- STEP 3: a teammate clones and pushes (same as editing on the GitHub web UI) ---
git("clone", HUB, "teammate", cwd=BASE)
write(os.path.join(MATE, "README.md"), "# Team repo\n\nStand-up at 9:15 daily.\n")
git("commit", "-am", "Add stand-up time to README", cwd=MATE)
git("push", cwd=MATE)

# --- STEP 4: fetch downloads history only; pull is fetch + merge ---
git("fetch")
git("status")                       # behind by 1, but README.md on disk is unchanged
git("log", "--oneline", "HEAD..origin/main")   # what origin has that we do not
git("pull")
git("log", "--oneline")

The bare repository is the only stand-in; every command is the one you type against GitHub, plus the credential-manager sign-in on the first push.
