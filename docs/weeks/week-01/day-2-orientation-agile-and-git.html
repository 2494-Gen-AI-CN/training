Orientation, Agile & Git: the workflow before the code

Week 1 · Day 2 Tue Oct 13, 2026 Agile for developers, Git & Python fundamentals ~12 min · notes @150 wpm + diagram + check

Today's demos ran Python three ways, timed a waterfall project against two-week Sprints, played a round of planning poker, and walked the whole Git loop live, local and then remote. This page is the reference behind those five scripts: what the interpreter really does with hello.py, which SDLC phases Scrum repeats every Sprint, why a story point is not an hour, and what git status is telling you at each of the three states. Run 01_hello_python.py through 05_git_remote_round_trip.py in order while you read.

Framing

Python runs your file top to bottom, and it lives in the back end

In the everyday sense Python is an interpreted language: you type python hello.py and the interpreter executes the source directly, with no separate build step producing an executable. That is why 01_hello_python.py can open with a variable and a print and the greeting appears the moment the command returns. On Windows the py launcher is installed next to Python; python --version or py --version confirms which interpreter your shell will run, and py -3.12 selects a specific version. We are on Python 3.12 all course long.

STEP 2 of the same demo prints the map you will keep returning to. A full-stack application has a front end (HTML, CSS and JavaScript in the browser), a back end (server-side code that receives requests, applies business rules and talks to storage), a database where data persists between requests (MySQL for us), and infrastructure where it all runs: your laptop today, a cloud such as GCP later. Python's sweet spot in this course is the back end and the data/ML layer, matching the Python FAQ's own list: web development, scripting and data analysis. Agile and Git, the rest of today, are about how a team moves code through that stack without losing work.

Mechanics

Interpreter vs compiler, and the REPL's memory

"Interpreted" is the user-facing story. Under the hood CPython first compiles each module to bytecode and then interprets that bytecode on a virtual machine. STEP 3 of 01_hello_python.py proves it: dis.dis(add_tax) lists the instructions generated for a two-line function, and py_compile writes the cached bytecode to __pycache__/. That is why a __pycache__ folder of .pyc files appears after the first import; it is cache, not source.

Running python with no arguments starts the interactive interpreter, the REPL, with the >>> primary prompt and ... for continuation lines. The last printed value is kept in the read-only variable _, so calculator-style work chains. You leave with exit() or quit(), Ctrl-Z then Enter on Windows, or Ctrl-D on Linux and macOS. The third way to run Python, python -i 01_hello_python.py, runs the file and then drops into the REPL with its variables still defined. A Jupyter Notebook is the same idea with memory: each code cell goes to a running kernel and its output appears underneath, in execution order rather than top-to-bottom order. The classic first-day trap is typing git status at the >>> prompt, getting a SyntaxError, and concluding Python is broken; learn to tell the PowerShell prompt, the REPL prompt and a running script apart.

Process

The SDLC, run once or run every Sprint

The software development life cycle is the sequence of phases every piece of software passes through regardless of methodology; 02_sdlc_waterfall_vs_agile.py names them plan, design, build, test, deploy and maintain, then delivers the same three-item backlog two ways. What differs between methodologies is not the phases but whether they happen once, in order, or repeat in short cycles.

Waterfall is the sequential model: each phase is completed and signed off before the next begins, so requirements freeze early and working software appears only at the end. In the demo users first see software in week 10, at deploy, and the "reports" requirement that arrives in week 5 is parked until the next release. Agile is the iterative model: the principles behind the Agile Manifesto call for delivering working software frequently, "from a couple of weeks to a couple of months", and welcoming changing requirements even late. Scrum makes that concrete. It is founded on empiricism (transparency, inspection, adaptation), runs all of the phases inside every Sprint, and requires each Sprint to produce a usable Increment; in STEP 3 the first Increment ships in week 2 and "reports" is picked up in Sprint 4. STEP 4 closes with the four values of the 2001 Manifesto: individuals and interactions over processes and tools, working software over comprehensive documentation, customer collaboration over contract negotiation, and responding to change over following a plan.

Practice

Story points and the Scrum ceremonies

The 2020 Scrum Guide defines three accountabilities (Product Owner, Scrum Master, Developers), five events (the Sprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective) and three artifacts (Product Backlog, Sprint Backlog, Increment). A Sprint is a fixed-length event of one month or less and the Daily Scrum is time-boxed to 15 minutes. For a one-month Sprint, Planning is capped at eight hours, the Review at four and the Retrospective at three; shorter Sprints use shorter caps. STEP 4 of 03_story_points_and_scrum.py halves those for our two-week Sprint.

Story points are not in the Scrum Guide at all. They are a widely used estimation practice layered on Scrum in which the team assigns relative effort sizes, commonly a Fibonacci-like scale of 1, 2, 3, 5, 8 and 13, instead of hour estimates. STEP 2 plays planning poker on two toy items: "add a hello script" draws 1, 2 and 1, one step apart, so the team takes the higher value; "set up the shared team repo" draws 3, 8 and 5, so they discuss and re-vote to 5. The point is the "why is yours a 3 and mine an 8?" conversation, not the number. Do not convert "5 points" to five hours, compare points between teams, or let the loudest voice decide. Points are relative effort agreed by the whole team, and velocity only means something within one team over several Sprints.

Mechanics

Git locally: three states, one loop

Version control comes in three generations: local (RCS, history on one machine), centralised (CVS, Subversion: one server holds the history, clients check out a working copy) and distributed (Git, Mercurial: every clone mirrors the full history). That is why log, diff, commit and branch work offline and only push, pull and fetch touch the network.

A file in a repository is in one of three states, modified, staged or committed, matching three areas: the working tree, the staging area (the index) and the .git directory. git status reports which state each file is in, so 04_git_local_loop.py runs it after nearly every command. git init creates .git and tracks nothing until you git add; add both starts tracking new files and stages modified ones. git commit -m "message" records the staged snapshot and git log --oneline lists one commit per line. On a fresh Windows machine the first commit usually fails with "Author identity unknown"; set user.name and user.email once with git config --global.

git branch feature creates a branch but does not switch to it; git switch feature (Git 2.23+) moves HEAD, and git switch -c feature does both in one step. A merge is a fast-forward when the target branch has no new commits since the feature branch diverged, so Git simply moves the pointer. Otherwise Git creates a merge commit with two parents, and if both sides changed the same lines it stops with <<<<<<<, ======= and >>>>>>> markers for you to resolve, then git add and git commit. STEP 4 of the demo forces exactly that and keeps both greetings.

Mechanics

Remotes: push -u once, then pull is fetch plus merge

05_git_remote_round_trip.py cannot reach GitHub from a script, so it stands up a bare repository on disk to play the "New repository" button and runs the real commands against it. STEP 1 shows the pitfall first: git push with no remote fails with "No configured push destination". git remote add origin <url> names the remote, and git push -u origin main uploads the branch and sets the upstream so later git push and git pull need no arguments.

STEP 3 clones a second copy as the teammate, commits a README there and pushes, which is what editing a file in the GitHub web UI does to your repo. STEP 4 then splits pull in two. git fetch downloads the new history without changing your working tree: the demo's file list after fetch has no README.md yet, while git log --oneline main..origin/main shows the commit origin has that you do not. git pull is fetch followed by merge of the tracked upstream branch; afterwards the README is there. Treating pull as a plain download causes two surprises: uncommitted edits produce "Your local changes would be overwritten by merge", and divergent history produces a merge or conflict you did not expect. Commit or stash first, and read the markers instead of deleting them. One more trap: running git init inside a folder that is already a repository creates nested repos that confuse every later command.

Wrap-up

The Git exercise is live; the pytest exercise is Python

Today's Git practice is not a test file. After demo 04, make a fresh folder (mkdir w01d2-git, cd w01d2-git, git init) and repeat STEPs 2 to 4 by hand: add, commit, git switch -c feature, merge, one deliberate conflict. After demo 05, create an empty repository on GitHub, git remote add origin, git push -u origin main, edit a file in the web UI, git pull, and read git log --oneline.

The pytest exercise is deliberately small: variables, arithmetic, strings and a few simple functions, standard library only. Its job is to prove the script-and-REPL workflow and the test loop. pytest collects files named test_*.py or *_test.py and runs functions whose names start with test; a plain assert is enough, because pytest rewrites it to show the compared values on failure. Run python -m pytest -q until green.

Remember three things. CPython compiles to bytecode and then interprets it, and the REPL keeps your last result in _. The SDLC phases never change; Scrum runs all of them inside every Sprint and sizes work in relative points, not hours. Git moves files from modified to staged to committed, and pull is fetch plus merge. Tomorrow, Day 3, stays inside Python with the basics.

Demo code: 01_hello_python.py

STEP 3 of the demo: CPython compiles a function to bytecode (shown by dis) and caches whole files as .pyc in __pycache__/.

# --- STEP 3: interpreter vs compiler - CPython compiles to bytecode, then interprets it ---
def add_tax(price, rate=0.13):
    return price * (1 + rate)

print("\nBytecode CPython produced for add_tax():")
dis.dis(add_tax)

# The same thing happens for whole files: the .pyc cache lands in __pycache__/
cached = py_compile.compile(__file__)
here = pathlib.Path(__file__).resolve().parent
print("Cached bytecode written to:", pathlib.Path(cached).relative_to(here))

Notice there is no build command anywhere: the compile step happens inside the interpreter, and the cache is a by-product you never edit.

Demo code: 04_git_local_loop.py

STEP 3 (branch, commit, fast-forward merge) and STEP 4 (same line changed on two branches, conflict resolved by hand). Each git(...) call prints the command as $ git ... and then git's reply.

# --- STEP 3: branch, commit on it, switch back, merge (fast-forward) ---
git("switch", "-c", "feature", cwd=repo)
edit(hello, 'print("hello")\nprint("from feature")\n')
git("commit", "-am", "greet from feature", cwd=repo)
git("switch", "main", cwd=repo)
git("merge", "feature", cwd=repo)
git("log", "--oneline", cwd=repo)

# --- STEP 4: force a conflict - same line changed on both branches - and resolve it ---
git("switch", "-c", "greeting", cwd=repo)
edit(hello, 'print("bonjour")\nprint("from feature")\n')
git("commit", "-am", "say bonjour", cwd=repo)
git("switch", "main", cwd=repo)
edit(hello, 'print("hola")\nprint("from feature")\n')
git("commit", "-am", "say hola", cwd=repo)
git("merge", "greeting", cwd=repo, ok=False)
print("\n# hello.py now contains conflict markers:\n" + hello.read_text())
edit(hello, 'print("hola / bonjour")\nprint("from feature")\n')   # keep both: the human decides
git("add", "hello.py", cwd=repo)
git("commit", "-m", "merge greeting: keep both greetings", cwd=repo)

The first merge fast-forwards because main had no new commits; the second stops with markers because both branches changed line 1, and a human picks the result before add and commit.
