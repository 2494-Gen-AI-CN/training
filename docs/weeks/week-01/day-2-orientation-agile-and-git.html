Orientation, Agile & Git fundamentals: how a team turns code into a shared history

Today spends thirty minutes confirming that your tooling works and the rest of the day on how a software team works: the SDLC, Agile against waterfall, Scrum, story points, and Git as the team's shared workflow. On-ramp

Thirty minutes to confirm your setup

Python is a general-purpose language; python.org lists web development, scientific and numeric work, software tooling, business applications, education and desktop GUIs as its main uses. In a full-stack picture (browser front end, server back end, database, infrastructure) Python's seat in this course is the back end and the data and ML layer. The "Professionalism at Revature" block that opens the morning is house rules about attendance, communication, written updates and conduct; it has no external source.

You already know the compiler-versus-interpreter distinction. In practice, python hello.py runs the source with no separate build step, which is what "interpreted" means day to day. Under the hood CPython compiles each module to bytecode and caches it in __pycache__/. That folder appears after the first import, and because it is machine-generated it goes into .gitignore later today.

The tooling-check demo runs three commands and gets three answers. python --version proves which interpreter the shell will run (we want 3.12). where.exe python lists every Python on the PATH, first match wins, and an entry containing WindowsApps is the Microsoft Store stub; if it is first, python opens the Store instead of an interpreter, and py sidesteps it. The REPL starts when you run python with no arguments: the >>> prompt is the tell that you are inside Python, a bare expression prints its value, _ holds the last printed result, and exit() gets you back to the shell. Typing git status at that prompt gives a SyntaxError because that command belongs at the shell prompt. A Jupyter notebook is this same REPL with a memory of every cell you ran, in execution order rather than top-to-bottom order.

Framing

Every piece of software goes through the same phases

The software development life cycle is the sequence every project passes through whatever method the team uses: requirements and planning, design, implementation, testing, deployment, maintenance. Methodologies differ in how often you go round. Waterfall runs the phases once, in order; each one is completed and signed off before the next starts, requirements are frozen early, and working software appears only at the end.

The Agile Manifesto (2001) states four values. It prefers individuals and interactions over processes and tools, working software over comprehensive documentation, customer collaboration over contract negotiation, and responding to change over following a plan, while still valuing the items on the right. The principles behind it call for delivering working software frequently, "from a couple of weeks to a couple of months", and for welcoming changing requirements even late in development.

Scrum is the Agile framework you will meet most. It is founded on empiricism, which the Scrum Guide describes as transparency, inspection and adaptation, and it runs all of the SDLC phases inside every Sprint.

Team practice

Scrum in numbers: three, five, three

The 2020 Scrum Guide defines three accountabilities, five events and three artifacts. The accountabilities are the Product Owner, the Scrum Master and the Developers. The events are the Sprint itself, Sprint Planning, the Daily Scrum, the Sprint Review and the Sprint Retrospective. The artifacts are the Product Backlog, the Sprint Backlog and the Increment.

Every event has a time-box. A Sprint is one month or less and the Daily Scrum is fifteen minutes. For a one-month Sprint, Sprint Planning is capped at eight hours, the Sprint Review at four and the Retrospective at three; shorter Sprints get shorter caps.

Today's Git exercise is a Sprint Backlog item: one piece of work, pulled from the Product Backlog at Sprint Planning, finished inside the Sprint and shown at the Review. The branch you open for it holds that item's commits.

Team practice

Story points are relative, and they belong to one team

The Scrum Guide says the Developers are accountable for sizing backlog items. It never mentions story points or hours. Story pointing is a practice layered on top of Scrum: the team assigns each item a relative effort size, commonly from a Fibonacci-like scale of 1, 2, 3, 5, 8 and 13, by comparing it with the other items in the backlog.

Velocity is the number of points a team completes per Sprint. It is meaningful only within one team, over several Sprints, as a way of guessing how much that team can pull into the next one. The habits that break it: converting "5 points" into "5 hours", comparing points between teams, and letting the loudest voice set the number when the whole team should agree through comparison.

In class you size two toy items, "add a hello script" against "set up the team's shared repository with branch protection". The useful moment is when one person says 3 and another says 8, because explaining why surfaces the hidden work.

Mechanics

Git as the team's workflow: the local loop

Version control has had three generations: local (RCS, history on one machine), centralised (CVS, Subversion: one server holds the history and each client checks out a working copy) and distributed (Git, Mercurial: every clone holds the full repository). So log, diff, commit and branch work offline and only push, pull and fetch touch the network. Git stores each commit as a snapshot of the whole tree, with unchanged files stored as links to the previous identical file, rather than as a list of per-file diffs.

A file is in one of three states, modified, staged or committed, matching three areas: the working tree, the staging area (also called the index) and the .git directory. git status tells you which, and the Git local-loop demo runs it after every single step so the three areas become visible. git init creates the .git folder and tracks nothing until you git add; add both starts tracking a new file and stages a modified one. On a fresh machine the first commit stops with "Author identity unknown" until user.name and user.email are configured, and init.defaultBranch decides whether new repositories start on main or master.

A branch is a movable pointer to a commit. git branch feature creates one and leaves you where you were, so your next commits land on main and the later merge says "Already up to date". git switch -c feature creates and switches in one step, which is the form to use.

git switch -c feature/farewell
git add hello.py
git commit -m "Add farewell function"
git switch main
git merge feature/farewell

That merge is a fast-forward: main had no new commits since the branch diverged, so Git only moves the pointer and creates no merge commit. When both branches have moved, Git creates a merge commit with two parents, and git log --oneline --graph draws the split and the rejoin.

Pitfall

Conflicts, remotes, and a pull that refuses

When both sides changed the same lines, Git stops with CONFLICT (content) and writes three markers into the file: <<<<<<< HEAD opens your side, ======= divides, and >>>>>>> feature/shout closes theirs. Read both sides, keep the lines you want, remove all three markers, then git add and git commit. git merge --abort backs out entirely. People get this wrong by deleting the markers without reading, committing with <<<<<<< still inside the file, or aborting and then submitting as if the merge had happened. Run the file before you stage it.

A remote is a copy of the repository elsewhere. git remote add origin <url> gives it the short name origin, and git push -u origin main uploads the branch and sets its upstream so that later git push and git pull need no arguments; before that first -u push, a plain git push fails with "no upstream branch". Over HTTPS, GitHub accepts a personal access token or a credential helper sign-in, and does not accept your account password. Running git init inside a folder that is already a repository, such as all of Documents, nests repositories and confuses every later command.

git pull is git fetch followed by git merge of the tracked branch; fetch alone downloads new history without changing your files. When your branch and its upstream have both moved, Git 2.33.1 and later refuses a plain pull with "Need to specify how to reconcile divergent branches" unless configuration or a flag says how. The remote round-trip demo makes that stop deterministic with --ff-only, then merges on purpose:

git fetch
git status
git pull --ff-only
git pull --no-rebase --no-edit
Practice

Commit messages, the exercise, and what to carry forward

A good commit message is a summary line of about fifty characters in the imperative mood ("Add login form", not "Added" or "fix"), a blank line, then a body that explains what changed and why rather than how; the diff already shows how. git log --oneline and git shortlog show only the first line, so that line has to stand on its own, and the log should read as the story of the work.

Today's exercise is the Git exercise itself: a real repository on GitHub with a feature branch, a merge, one conflict that you resolve, and commit messages a teammate could read, marked against a rubric. Replay the local-loop and remote round-trip demos in your head before you start.

To remember from today: the SDLC phases are the same under any method and Scrum runs them every Sprint; story points are relative and team-local; a file is modified, staged or committed and git status says which; switch -c over branch; a conflict is resolved by reading both sides and removing all three markers; pull is fetch plus merge. Deep dive: how the rubric proves your conflict was real

Optional. ~5 minutes.

The exercise asks for one resolved conflict, and the marker needs a way to check that the two parents of your merge commit genuinely collided rather than merged cleanly. Git 2.38 added git merge-tree --write-tree <branch1> <branch2>, which performs a real merge of two commits in memory without touching the working tree or the index. It prints the resulting tree and exits 1 with CONFLICT (content) lines when the sides conflict. Run it on the two parents of your merge commit and you see exactly what the marker sees; a clean exit means the "conflict" was not one.

A related repair, in case your first commits carry the wrong name or email: git commit --amend --reset-author rewrites only the most recent commit with the author taken from the current user.name and user.email. It fixes the tip and nothing earlier; older commits with a wrong identity are left and noted, because the rewrite that would fix them is not on today's syllabus.

Transcript: the conflict in the local-loop demo

Step 5 of the local Git loop. Both branches changed the same print line; Git stops and writes the three markers into hello.py.

$ git merge feature/shout
Auto-merging hello.py
CONFLICT (content): Merge conflict in hello.py
Automatic merge failed; fix conflicts and then commit the result.
$ cat hello.py
def greet(name):
    return f"Hello, {name}"


def farewell(name):
    return f"Goodbye, {name}"


<<<<<<< HEAD
print(greet("Toronto") + "!")
=======
print(greet("Toronto").upper())
>>>>>>> feature/shout
print(farewell("Toronto"))

HEAD is your side (main), the line after ======= is theirs. The resolution in the demo kept both ideas: print(greet("Toronto").upper() + "!").
