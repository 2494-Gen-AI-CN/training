ETL overview

ETL and ELT: where the transform runs

Wednesday's staging tables and Thursday's star were each built by hand, one command at a time. A data team wants the same result from one job it can run every night, and the name for that job is a pipeline.

What extract, transform and load each do

ETL stands for extract, transform, load. It describes the work of copying data out of the systems a business runs on and into the warehouse its analysts query.1

  • Extract reads rows out of a source, such as the desk's MySQL tables, without changing the source.
  • Transform cleans and reshapes those rows: it drops or flags bad records, converts types, joins tables and computes keys and measures.
  • Load writes the result into warehouse tables, such as a fact table and its dimensions.

In classic ETL the transform runs on a separate processing system, a server or a script between the source and the warehouse, and only finished rows reach the warehouse.1 No raw row is ever loaded.

The smallest version of that shape fits in a few lines of Python. Three functions, called in order from one main, with a list standing in for the warehouse:

def extract():
    return [{"event_id": 1, "kind": "open"}, {"event_id": 2, "kind": "closd"}]

def transform(rows):
    return [r for r in rows if r["kind"] in ("open", "assigned", "closed")]

def load(rows, target):
    target.extend(rows)

def main():
    warehouse = []
    load(transform(extract()), warehouse)
    print(warehouse)

main()
[{'event_id': 1, 'kind': 'open'}]

The misspelt closd row never reaches the list, because the transform ran before the load. That is also how you recognise an ETL job in someone else's repository: a file with extract(), transform() and load() functions called in that order from main().

ETL's role in a data warehouse

A warehouse is only as useful as the data that reaches it. The operational database is shaped for one ticket at a time, while the star is shaped for questions across thousands of tickets. ETL is the bridge between the two. It decides which rows arrive, in what shape, how often, and what happens to the ones that do not fit.

Nobody types that bridge by hand every day. It runs on a schedule, and the warehouse's numbers can be trusted only as far as the job's rules can be read and checked.

ELT, and why cloud warehouses favour it

ELT swaps the last two letters. The raw data is loaded into the warehouse first, usually into staging tables, and transformed there with SQL.1 In BigQuery the transform is a statement such as this one, run after the load:

CREATE OR REPLACE TABLE desk_dw.events_ok AS
SELECT
  event_id,
  ticket_id,
  kind
FROM desk_raw.ticket_events
WHERE kind IN ('open', 'assigned', 'closed');

The statement returns no rows of its own; afterwards desk_dw.events_ok holds every staged event whose kind is one of the three, and desk_raw.ticket_events still holds all of them. A SQL file of CREATE OR REPLACE TABLE ... AS SELECT statements run after a load step is the sign of ELT.

Cloud warehouses favour ELT because BigQuery separates storage from compute.2 Keeping raw data costs little, and the SQL that transforms it runs where the data already sits, so nothing is copied out to a separate server and back.2 Thursday's star was built this way: the dimensions and the fact were SELECT statements over the staging tables.

ETLELT
Where the transform runsa separate engine, before the loadinside the warehouse, after the load
What the warehouse holdsonly cleaned rowsraw rows and the cleaned tables built from them
Main costthe engine's own computeraw data stored, and the queries that reshape it

The trade-off: raw data in the warehouse

ELT lands raw data first, so unvalidated and sensitive columns sit in the warehouse until a transform cleans or drops them.1 Anyone with read access to the staging dataset can see them. ETL cleans before loading, so the warehouse never holds a bad row, but it needs compute of its own to do that.1

Real pipelines mix the two. The desk's job cleans events in Python before they reach the star, then rebuilds the star with SQL inside BigQuery. Either way, a load into a warehouse should be safe to repeat, and the job's design (its write dispositions and its watermark) is what makes it so.3

Takeaways
  • ETL transforms on a separate engine before loading; ELT loads raw data and transforms it inside the warehouse.
  • Separate storage and compute make ELT cheap in BigQuery, because SQL runs next to the data.
  • ELT leaves raw, possibly sensitive columns in staging until a transform handles them.
Say it in an interview

ETL is extract, transform, load. You read rows out of an operational source, clean and reshape them, and write them into the warehouse's tables, so it's the process that feeds the warehouse and decides what shape and quality the data has when analysts query it.

The difference with ELT is where the transform runs. In ETL it runs on a separate engine before the load; in ELT I load the raw data into staging first and transform it with SQL inside the warehouse.

Cloud warehouses like BigQuery favour ELT because storage and compute are separate, so keeping raw data is cheap and the SQL runs right next to it. The cost is that raw and possibly sensitive columns sit in the warehouse until they're cleaned.

ETL overview

The steps of a pipeline: stage, validate, log

ETL names three steps, but a pipeline has more. In an interview, "what is ETL" is usually followed by "walk me through the steps", and the answer has six.

Six steps from source to warehouse

StepWhat it doesOn the ticket desk
Extractreads rows out of the sourceevents and tickets read from MySQL
Stagelands the raw extract in the warehouse, unchangedtables in desk_raw
Transformcleans, joins and reshapesbad events set aside, keys looked up
Loadwrites the modelled tablesthe dimensions and the fact in desk_dw
Validatechecks the rows against rules and countsevery rejected event kept with its reason
Logrecords what the run didone row per run with rows read, loaded and rejected

Validation is drawn after the load here, but in practice it runs wherever a rule can be checked. A row-level rule, such as "the kind must be one of three", runs inside the transform. A run-level rule, such as "loaded plus rejected must equal read", runs at the end, just before the log row is written.

Staging areas, and what they buy at scale

A staging area is a set of tables that hold the raw extract exactly as it arrived. A load job writes each staging table with its own write disposition, independent of the tables built from it.3

Landing raw extracts first lets a job re-run its transform and validation without extracting from the source again.3 On a desk with a few hundred rows that saves seconds. At scale it pays off in other ways:

  • A bug in the transform is fixed and re-run against staging, while the source is left alone.
  • The source is read once per run, in a short window, instead of once per downstream table.
  • Staging is a record of what the source said at load time, which settles arguments about whose number is right.

The price is storage and a second copy of possibly sensitive data, the same trade-off ELT carries. Staging tables usually get a short expiration for that reason, as desk_raw did on Wednesday.

Extracting from an ODS instead of production

Wednesday named the operational data store, or ODS: an integrated, current copy of operational data, kept for reporting and for feeding the warehouse. At scale a job extracts from an ODS, or a read replica, rather than from the production database, so the extract's reads never compete with production.4 Cloud SQL's read replicas exist for exactly that purpose: to offload read and analytics traffic from the primary instance.4

That choice has three benefits for a large company:

  • No extract load on the database customers are using, so a heavy nightly read cannot slow the desk down.
  • One reconciled source instead of many, because the ODS has already combined the operational systems.
  • One place where operational fixes land, so a corrected record reaches every downstream job.

The cost is another system to run and data that is a little behind production. For a nightly warehouse load that lag rarely matters.

Rejects with a reason, and the load log

A BigQuery load job can skip invalid rows, up to a limit set by max_bad_records, but it reports them only as job errors.5 A job that must keep each bad row and say why writes it to a rejects table itself. The pattern in plain Python:

EVENT_KINDS = ("open", "assigned", "closed")
rows = [
    {"event_id": 12, "ticket_id": 2, "kind": "closed"},
    {"event_id": 13, "ticket_id": 2, "kind": "closd"},
]
clean, rejects = [], []
for row in rows:
    if row["kind"] in EVENT_KINDS:
        clean.append(row)
    else:
        rejects.append({**row, "reason": "unknown kind"})
log = {"rows_read": len(rows), "rows_loaded": len(clean), "rows_rejected": len(rejects)}
print(rejects)
print(log)
[{'event_id': 13, 'ticket_id': 2, 'kind': 'closd', 'reason': 'unknown kind'}]
{'rows_read': 2, 'rows_loaded': 1, 'rows_rejected': 1}

{**row, "reason": ...} builds a new dict with every key of row plus one more. The log dict is the load log's row for this run. A silent drop would leave read at 2 and loaded at 1 with nobody able to say why; the rejects table answers that question with the row and its reason.

You recognise both on sight in a warehouse: a table with the source's columns plus a reason column, and a small table with one row per run holding a timestamp and three counts.

Takeaways
  • A pipeline extracts, stages, transforms, loads, validates and logs, in that order.
  • Staging lets a job re-run its transform without reading the source again.
  • An ODS or replica takes the extract's reads off the production database.
  • Rejects keep each bad row with a reason; the load log keeps one row of counts per run.
Say it in an interview

A pipeline that loads a source into a warehouse has six steps: extract from the source, stage the raw rows unchanged, transform them, load the modelled tables, validate against rules and counts, and log the run. The staging step is what lets me fix a transform and re-run it without hitting the source again.

At scale I'd extract from an ODS or a read replica rather than production, so the job's reads never compete with customers, and the warehouse gets one reconciled source where operational fixes already landed.

ETL overview

Reruns and incremental loads

Every job gets run twice sooner or later: a scheduler retries after a timeout, or someone re-runs it to check a fix. A job is idempotent when that second run leaves the data exactly as one run did. Repeating a load safely is a design choice of the job, made through its write dispositions and its watermark; no tool does it for you.3

Write dispositions: replace, append or refuse

Every BigQuery load job writes with a write disposition, which says what happens to rows already in the destination table.3

DispositionWhat it doesSame load run twice
WRITE_TRUNCATEreplaces the table's rowssame data as one run
WRITE_APPENDadds rows to the tableevery row twice
WRITE_EMPTYfails if the table already has datathe second run fails

WRITE_TRUNCATE is idempotent by itself: repeating the same load leaves the same data.3 WRITE_APPEND repeated with the same rows duplicates them, which is why an append load needs a guard.3 The common slip is appending to a table the job refills from scratch each run, so the second run doubles every row.

So the desk's job replaces most of its tables on every run:

  • the small staging tables
  • the clean events
  • the rejects
  • the star

Only the event history, which grows forever, is appended.

Incremental loads by watermark

Replacing a table means re-reading the whole source. That is fine for a handful of agents and too slow for a billion events. An incremental load extracts only the rows added since the last run. To know where the last run stopped, the job reads a watermark: the highest id or timestamp already loaded.

Here is the idea with lists standing in for the source and the staging table. max(..., default=0) returns 0 when the list is empty, so the very first run loads everything.

source = [1, 2, 3, 4, 5]
staged = [1, 2, 3]

watermark = max(staged, default=0)
new = [e for e in source if e > watermark]
staged = staged + new
print(watermark, new)

watermark = max(staged, default=0)
new = [e for e in source if e > watermark]
print(watermark, new)
3 [4, 5]
5 []

The first run finds 3 already staged and appends 4 and 5. The second run finds 5, extracts nothing, and appends nothing, so the append load is safe to repeat. In SQL the watermark is one query at the top of the job, SELECT MAX(event_id) over the staged events, which you will spot at the start of most incremental jobs.

What a MAX(id) watermark misses

An incremental load by MAX(id) has two blind spots.3

  • A row updated after it was loaded keeps its old id, so the job never sees the change.
  • A row that arrives with a lower id than the watermark, because ids were handed out out of order, is skipped for good.

Event tables suit an id watermark because events are only ever added, never edited. Tables whose rows change need one of three other answers:

OptionWhat it catchesCost
updated_at watermarkrows edited after loadingneeds a reliable timestamp column
change data captureevery insert, update and delete, read from the database's change loganother system to run
periodic full reloadeverything, always correctre-reads the whole source, so it costs more at scale3

The desk's job uses both ideas. Events are appended above a watermark. Customers, which change, are read in full every run, compared with the history dimension and replaced.

Takeaways
  • WRITE_TRUNCATE replaces, WRITE_APPEND adds, WRITE_EMPTY refuses a table that has data.
  • An append load is safe to repeat only behind a watermark read from what is already loaded.
  • An id watermark misses updated rows and late low ids; timestamps, CDC or full reloads cover them.
Say it in an interview

I make a pipeline safe to rerun in three ways. Tables the job rebuilds are written with WRITE_TRUNCATE, so a second run replaces rather than adds. Tables that only grow are appended above a watermark, the max id already loaded, so a rerun finds nothing new.

Bad records go to a rejects table with a reason, which is replaced each run, so nothing is lost silently and nothing doubles.

If the watermark is a max id, I'd watch for rows updated after loading and ids arriving out of order. For those I'd switch to an updated-at timestamp, change data capture, or a periodic full reload.

BigQuery connections

External data, connections and transfers

So far every table BigQuery queried was one it stored, filled by a load job. Not all data is worth loading. A list of which agent sits on which team lives in a spreadsheet a manager edits, and copying it nightly would always be a day stale. BigQuery has several ways to reach data it does not hold.

External tables: data that stays at the source

An external table reads data that stays in Google Drive, as a Sheet, or in Cloud Storage. BigQuery stores only the table's definition, so each query reads the source as it is at that moment.6 The definition is one DDL statement:

CREATE OR REPLACE EXTERNAL TABLE desk_raw.agent_teams (
  name STRING,
  team STRING
)
OPTIONS (
  format = 'GOOGLE_SHEETS',
  uris = ['https://docs.google.com/spreadsheets/d/<sheet-id>'],
  skip_leading_rows = 1
);

Afterwards bq show desk_raw.agent_teams prints the table's type as EXTERNAL where a loaded table says TABLE. skip_leading_rows = 1 tells BigQuery the first row is a header. The table joins to the star like any other, so a query can count events per team. When someone edits a cell in the Sheet, the next run of the same query shows the new totals with no load in between.

Reading a Sheet needs Drive access on the credentials. The console asks for it and grants it, but bq and Python's Application Default Credentials carry no Drive scope by default, so they cannot query a Sheet-backed table.7 Query it from the console, or import it as a native table first.

Federated queries and connections

A federated query goes one step further: BigQuery sends a query to an outside database, such as Cloud SQL, Spanner or AlloyDB, and joins the answer with its own tables.8 It is written with EXTERNAL_QUERY, whose inner SQL runs on the outside database:

SELECT
  t.ticket_id,
  t.status
FROM EXTERNAL_QUERY(
  'connection_id',
  'SELECT ticket_id, status FROM tickets;'
) AS t;

The result is the live tickets rows from the outside MySQL server, read at query time; nothing lands in BigQuery. The first argument names a connection. A BigQuery connection is a stored resource that holds the access details for one outside source, so a query names it instead of carrying a password.8

Connections exist for these sources:8

  • Cloud SQL, Spanner and AlloyDB, for federated queries with EXTERNAL_QUERY
  • Cloud Storage
  • AWS and Azure storage such as Amazon S3, through BigQuery Omni

The free sandbox has none of these to point at, so the desk's one external source is a public Sheet. In code review you recognise both forms on sight: CREATE OR REPLACE EXTERNAL TABLE ... OPTIONS (format = ..., uris = [...]), and FROM EXTERNAL_QUERY('connection_id', '...').

Native copy or external table

An external table is always current, but it is slower and gets fewer optimisations than a native table, so a source that is read often is better imported.6 The import is one statement, run in the console where the Drive access lives:

CREATE OR REPLACE TABLE desk_raw.agent_teams_copy AS
SELECT
  name,
  team
FROM desk_raw.agent_teams;

bq show desk_raw.agent_teams_copy then prints the type TABLE and a row count, one row per row of the Sheet. The copy is fast and readable from bq and Python, but it is only as fresh as the moment the statement ran, so you trade freshness for speed and cost.

Scheduled loads with the Data Transfer Service

Everything above is run by hand or by your own job. The BigQuery Data Transfer Service is Google's managed answer for recurring loads: it schedules transfers from sources such as Cloud Storage, Amazon S3 and SaaS applications into BigQuery.12 Asked "how would you automate a nightly load from S3", this is the first answer to give, before writing a job of your own. The sandbox does not offer it.11

Takeaways
  • An external table keeps the data at its source and reads it fresh on every query.
  • A federated query uses EXTERNAL_QUERY and a connection to reach Cloud SQL, Spanner or AlloyDB.
  • A native copy trades freshness for speed and cost when a source is read often.
  • The Data Transfer Service schedules recurring loads from Cloud Storage, S3 and SaaS sources.
Say it in an interview

To export, I can save a query result to a Google Sheet, to Drive as CSV or JSONL, or download it as CSV or JSON, and I can export a whole table to Cloud Storage with an extract job as CSV, JSON, Avro or Parquet.

To import, I load files from a gs:// path, or I define an external table over a Sheet and copy it into a native table with CREATE TABLE AS SELECT.

An external table leaves the data where it is and reads it at query time, so it's always current but slower. A federated query goes to a live database like Cloud SQL through EXTERNAL_QUERY and a connection, which stores the access details. For a recurring load from S3 or a SaaS app I'd use the Data Transfer Service.

BigQuery connections

Parameterized queries

A report that counts closed tickets per agent is useful. The same report for opened tickets, or assigned ones, is the same query with one word changed. Copying the file three times invites the copies to drift apart, and pasting the word into the SQL by hand invites worse.

A named parameter in the SQL

A query parameter is a named placeholder in the SQL, written with an @ in front, whose value is sent separately from the statement text.13 One file serves every kind of event:

-- events of one kind per agent, from the star
SELECT
  a.name AS agent,
  COUNT(*) AS events
FROM desk_dw.fact_ticket_events AS f
JOIN desk_dw.dim_agent AS a ON a.agent_key = f.agent_key
WHERE f.kind = @kind
GROUP BY a.name
ORDER BY events DESC;

On its own this file is incomplete, because @kind has no value until the caller supplies one. The comment on its first line says what it reports, so a reader knows which value to pass.

From the command line, bq query supplies the value with --parameter=name:TYPE:value. An empty type, two colons side by side, means STRING.13 The same file then runs once per kind, read in through < as Thursday's star file was:

bq query --use_legacy_sql=false --parameter=kind::closed < kind_report.sql
bq query --use_legacy_sql=false --parameter=kind::open < kind_report.sql

Each line prints a table of agents and counts, the first for closed events and the second for opened ones, from one file that never changed. The same idea scales to dates, ids and numbers by naming a type, such as --parameter=day:DATE:2026-10-18.13

You recognise a parameterized query on sight by WHERE kind = @kind in BigQuery SQL, or by a query string and a separate list of values passed to a client library.

Why the value never goes in the text

Because the value travels beside the SQL rather than inside it, a value cannot change the statement's structure.13 This is the BigQuery counterpart of week 3's %s placeholders in Python's MySQL connector, and it buys the same two things:

  • One tested query file serves every value, so the report logic lives in one place.
  • A value is only ever a value, so text such as a quote followed by OR 1=1 is compared as a string and matches nothing, instead of becoming part of the WHERE clause.

Two small pitfalls come up often. Pasting a value into the SQL with an f-string undoes the protection, even when the query also contains an @ elsewhere. And the two colons in kind::closed are not a typo: the empty space between them is the type, and empty means STRING.13

Takeaways
  • A named parameter such as @kind keeps the value out of the SQL text.
  • bq query --parameter=name:TYPE:value supplies it, and an empty type means STRING.
  • Parameters make one query file reusable and stop a value from rewriting the statement.
Say it in an interview

I write the varying part of a query as a named parameter, like at-kind, and pass the value separately, for example with bq query and the parameter flag, where an empty type means string.

That makes one query reusable for every value, and it's safer, because the value is sent beside the SQL and can never change the statement's structure the way a pasted string can. It's the same idea as placeholders in a database connector.

Building ETL/ELT processes

Building the ETL job

The pieces of the week so far were run one at a time. This step joins them into one Python program that a scheduler could start every night, using the ideas of the last three steps.

One run, in order

A run of the desk's job does these things, each a function call from one run function:

  1. Create the job's own tables if they are missing: clean events, rejects and the load log.
  2. Read the watermark, MAX(event_id) of the staged events, or 0 when there are none.
  3. Extract the small tables in full from MySQL, and only the events above the watermark.
  4. Stage them: replace the small tables, append the new events.
  5. Clean all staged events in Python, splitting them into clean rows and rejects with a reason.
  6. Update the customer dimension's history, then rebuild the star with its SQL file.
  7. Write one load-log row with the run's time and counts.

The program authenticates through Application Default Credentials, written once by gcloud auth application-default login, so no key file sits beside the code.14 The only per-person value is the project id, read from an environment variable. A rerun with no new events reads 0 events, re-cleans the same staged rows, and leaves every table but the load log as it was.

Cleansing with pandas: a reason for every reject

The transform is one function from frames to frames. It uses a few pandas tools that are new here:

  • DataFrame.merge joins two frames on a column, like a SQL join.15
  • DataFrame.duplicated marks every repeat after the first, by default.16
  • pd.Series("", index=rows.index) is a column of empty strings, one per row, that the rules then overwrite with a reason.
  • The unknown-kind line uses Series.isin with ~ in front; in the output below it catches event 13, whose kind is not in EVENT_KINDS.
  • ~ flips every True to False and every False to True, so ~rows["kind"].isin(EVENT_KINDS) is True for kinds outside the tuple.
  • The rejects line uses DataFrame.assign to attach the reason column, which shows in the second printed table.
import pandas as pd

EVENT_KINDS = ("open", "assigned", "closed")
EVENT_COLUMNS = ["event_id", "ticket_id", "kind", "created_at"]


def clean_events(events, tickets):
    """Split events into clean rows and rejects that carry a reason."""
    events = events.sort_values("event_id")
    rows = events.merge(tickets, on="ticket_id")
    reason = pd.Series("", index=rows.index)
    reason[rows.duplicated(["ticket_id", "kind", "created_at"])] = "duplicate"
    reason[~rows["kind"].isin(EVENT_KINDS)] = "unknown kind"
    reason[rows["created_at"] < rows["opened_at"]] = "before ticket opened"
    clean = rows[reason == ""][EVENT_COLUMNS]
    rejects = rows[reason != ""].assign(reason=reason)[EVENT_COLUMNS + ["reason"]]
    return clean, rejects

Defining the function prints nothing. Each rule writes its reason over the rows it catches, so a row that broke two rules keeps the last one. Calling it on five events, three of them bad, shows the split:

tickets = pd.DataFrame({
    "ticket_id": [2, 4, 6],
    "opened_at": pd.to_datetime(["2026-10-17 10:00", "2026-10-17 11:00", "2026-10-19 12:00"]),
})
events = pd.DataFrame({
    "event_id": [9, 3, 8, 13, 14],
    "ticket_id": [4, 2, 4, 2, 6],
    "kind": ["assigned", "open", "assigned", "closd", "assigned"],
    "created_at": pd.to_datetime(["2026-10-17 12:00", "2026-10-17 10:00", "2026-10-17 12:00",
                                  "2026-10-18 09:00", "2026-10-19 11:00"]),
})
clean, rejects = clean_events(events, tickets)
print(clean)
print(rejects[["event_id", "reason"]])

Because duplicated keeps the first copy in frame order, row order decides which survives.16 BigQuery returns rows in no fixed order, so without the sort a different copy could be kept on different runs. Sorting by event_id first means event 8 is kept and event 9 rejected every time.

Loading with the table's own schema

Python reaches BigQuery through the google-cloud-bigquery client. A load from a DataFrame takes a LoadJobConfig whose schema and write_disposition control the load, and .result() waits for the job and raises if it failed.17

from google.cloud import bigquery


def load_frame(bq, frame, table, mode="WRITE_TRUNCATE"):
    """Load a DataFrame into an existing table, keeping that table's schema."""
    config = bigquery.LoadJobConfig(
        schema=bq.get_table(table).schema,
        write_disposition=mode,
    )
    bq.load_table_from_dataframe(frame, table, job_config=config).result()

Called as load_frame(bq, rejects, "desk_dw.load_rejects"), it replaces the rejects table and returns once the job has finished. Passing schema=bq.get_table(table).schema keeps the destination's types instead of a guess.17 An autodetected load with WRITE_TRUNCATE could swap a NUMERIC or DATE column for whatever type it guessed.

The other direction, a query result into a DataFrame, uses to_dataframe(), which needs db-dtypes and pyarrow installed so BigQuery's DATE and TIME types map to pandas types.18

The last line of a run writes the load log. Its timestamp comes from datetime.now(timezone.utc), which is timezone-aware and loads into a TIMESTAMP column.19

from datetime import datetime, timezone

run_at = datetime.now(timezone.utc)
print(run_at.tzinfo)

It prints UTC, the time zone the value carries, so the log row means the same moment wherever the job ran.

Takeaways
  • One run creates its tables, reads the watermark, extracts, stages, cleans, rebuilds and logs.
  • Sort by the key before marking duplicates, or a different copy may survive each run.
  • Every load passes the destination table's own schema and a chosen write disposition.
Say it in an interview

My job reads a watermark, extracts only new events plus the small tables in full, stages them, cleans the events in a pure pandas function that returns clean rows and rejects with a reason, rebuilds the star with SQL, and writes one log row. Small tables are replaced, events are appended above the watermark, and rejects are replaced, so running it twice adds nothing.

Each load passes the destination table's own schema and an explicit write disposition, so a rerun never changes a column's type, and I sort by id before marking duplicates so the same copy survives every time.

Building ETL/ELT processes

Testing the transforms with pytest

A job that loads wrong numbers every night is worse than one that fails loudly. Tests are how a team trusts the rules in the middle of the job, and the way the job is split up decides how easy they are to write.

Why a pure transform is testable

A pure function takes inputs and returns outputs without reading or writing anything else. The cleansing function above is one: frames in, frames out. Every BigQuery call lives in a separate module, so the transform can be tested with no database, no network and no credentials.20

That split shapes the whole code base:

ModuleHoldsTested by
transformcleansing and history rules, pure functionspytest, with frames built in the test
warehouse clientevery BigQuery query and loadrunning the job against a sandbox
jobthe order of the steps and the log rowtwo runs and a look at the log

You recognise a testable pipeline on sight by a transform.py that imports pandas and nothing from the cloud, beside a test file for it that never sets a password or a project.

Fixtures and frames built inline

A pytest fixture is a function marked @pytest.fixture whose return value pytest passes to any test that names it as a parameter.20 Here the fixture supplies the tickets table, and a small helper builds events:

import pandas as pd
import pytest

from transform import clean_events


@pytest.fixture
def tickets():
    """One ticket, opened at nine on 17 October."""
    return pd.DataFrame({"ticket_id": [1], "opened_at": pd.to_datetime(["2026-10-17 09:00"])})


def events_frame(ids, kinds):
    """Events on ticket 1, all at ten on 17 October."""
    return pd.DataFrame({
        "event_id": ids,
        "ticket_id": [1] * len(ids),
        "kind": kinds,
        "created_at": pd.to_datetime(["2026-10-17 10:00"] * len(ids)),
    })


def test_unknown_kind_is_rejected(tickets):
    """A kind outside EVENT_KINDS is rejected with its reason."""
    clean, rejects = clean_events(events_frame([1], ["closd"]), tickets)
    assert clean.empty
    assert rejects["reason"].tolist() == ["unknown kind"]


def test_clean_keeps_first_copy_of_a_duplicate(tickets):
    """Of two identical events, the lower event_id is kept."""
    clean, rejects = clean_events(events_frame([2, 1], ["open", "open"]), tickets)
    assert clean["event_id"].tolist() == [1]
    assert rejects["event_id"].tolist() == [2]

Saved beside the transform module and run with pytest -q, it ends with a line reading 2 passed and the time taken. Each assertion compares a column, through .tolist(), with a short list written in the test. clean.empty is True when the frame has no rows.

The second test hands the frame over in the wrong order on purpose, id 2 before id 1. It would pass by luck without the sort, if the rows happened to arrive in id order. Because duplicated keeps the first copy it meets, the test pins down which copy that is.16 One test per rule, each with a docstring saying what it proves, gives a reviewer a list of the job's rules in plain English.

These tests cover the rules and nothing else. A wrong table name, a missing column in the warehouse, or a permission error only shows up when the job runs against BigQuery. That is why the job is also run twice end to end, and why the load log is read after each run.

Takeaways
  • Keeping transforms pure lets them be tested with no database or credentials.
  • A fixture supplies shared inputs to every test that names it as a parameter.
  • Unit tests prove the rules; two end-to-end runs and the log prove the plumbing.
Say it in an interview

I keep the transforms as pure functions in their own module, frames in and frames out, and all the warehouse calls somewhere else. That way pytest can test every cleansing rule with small frames built in the test or in a fixture, with no database and no credentials.

I'd have one test per rule, including the one that checks which copy of a duplicate is kept, and then run the whole job twice against the warehouse to check the plumbing.

Review

Review: the week as one pipeline

Each day of the week added one stage. Read together, they are the answer to the interview question "walk me through how data gets from an operational database to a report".

From the desk's MySQL tables to the star

  1. The desk's MySQL tables hold tickets one at a time, and a trigger writes an event row for every status change.
  2. The extract writes the small tables as CSV files and the events as JSON lines, one object per line.
  3. Load jobs land the files unchanged in the staging dataset, desk_raw.
  4. The transform sets bad events aside with a reason and keeps customer history as SCD type 2.
  5. SQL inside BigQuery builds the star in desk_dw: date, agent, customer and ticket dimensions around one fact table.
  6. Reports query the star, join a Sheet through an external table, and take parameters.

The fact table's grain is one row per ticket event, and it is partitioned by the event's date, which limits the data a query that filters on that date has to scan.21 The star exists because the source tables answer "what is ticket 4 doing" while the star answers "how many tickets did each team close per week" with few joins and no risk to the live desk.

Two practical limits frame the design. Sandbox tables expire after 60 days unless the expiration is changed,11 so the warehouse is rebuildable from the code and the source alone. And Application Default Credentials from one gcloud auth application-default login serve every Python run without a key file,14 which keeps a public repository free of secrets.

Where cleansing runs

On Thursday the star's SQL dropped bad events silently with a WHERE clause. Moving that rule into Python has costs as well as gains.2

Cleansing in PythonCleansing in SQL
Testingunit tests on small framesharder to unit test; needs the warehouse
Bad rowskept with a reason in a rejects tableusually filtered out unseen
Data movementrows leave the warehouse and come backruns next to the data

For a desk with a few dozen events, testable rules and kept reasons win easily. For billions of rows, the same rules would move into SQL, with a rejects table written by a query instead of by pandas.

Comparing warehouse architectures

An interviewer at the next level asks you to choose an architecture for a business, and a good answer names what each option costs.

ArchitectureSuitsCosts
Warehouse fed by ETLstructured sources, a fixed set of reports, strict data qualitya transform engine to run; new questions wait for the pipeline
Warehouse fed by ELTa cloud warehouse with SQL skills on the teamraw data stored and governed; transforms in SQL
Data lake with ELT on readlarge volumes, semi-structured and unstructured data, explorationquality and meaning are worked out later, by every reader

Size, latency and skills decide it. A small support team with a MySQL database, daily reports and SQL skills is served by a cloud warehouse with ELT, a star at the grain of one event, and a nightly job like the desk's. A company with clickstreams, logs and images, and data scientists who want raw files, needs a lake first, with a warehouse built on top for the reports that must agree.

Takeaways
  • The week runs MySQL, extract files, staging, transform, star, then reports.
  • Cleansing in Python is testable and keeps reasons; cleansing in SQL scales and stays near the data.
  • Size, latency, data types and team skills decide between warehouse, ELT and lake designs.
Say it in an interview

Data starts in the operational database, gets extracted to files, lands unchanged in staging, is cleaned with bad rows kept and their reasons recorded, and is loaded into a star schema with one fact row per event and dimensions around it. Reports query the star because it's shaped for questions across many rows and doesn't load the live system.

To pick an architecture I look at volume, latency, the kinds of data and the team's skills. Structured sources and SQL skills point to a cloud warehouse with ELT; lots of semi-structured data and exploration point to a lake, with a warehouse on top for the numbers that must agree.

Check yourself

Check yourself

Eight retrieval questions, at least one per section. Answer each out loud before you open it.

What do extract, transform and load each do, and what role does ETL play for a data warehouse?

Extract reads rows out of an operational source, transform cleans and reshapes them, and load writes them into the warehouse's tables. ETL is the bridge that decides which data reaches the warehouse, in what shape and quality, and how often.

Where does the transform run in ETL and in ELT, and why do cloud warehouses such as BigQuery favour ELT?

In ETL it runs on a separate engine before the load; in ELT the raw data is loaded first and transformed inside the warehouse with SQL. BigQuery separates storage from compute, so keeping raw data is cheap and the SQL runs where the data already is. The cost is raw, possibly sensitive columns sitting in staging until a transform handles them.

Name the six steps of a pipeline that loads a source into a warehouse, and say what staging buys at scale.

Extract, stage, transform, load, validate, log. Staging keeps the raw extract unchanged, so a fixed transform can be re-run without reading the source again, and the source is read once per run.

Why would a large company's job extract from an ODS or a read replica instead of the production database?

The extract's heavy reads then never compete with the customers using production. The ODS is also one reconciled source where operational fixes already landed, so every downstream job reads the same corrected data.

A job appends staged events with WRITE_APPEND and has no watermark. What happens on the second run, and what are two fixes?

Every event is appended again, so each one appears twice. Either replace the table with WRITE_TRUNCATE on every run, or read MAX(event_id) from the staged rows first and append only events above it.

What is the difference between an external table, a native copy and a federated query?

An external table stores only a definition and reads a Sheet or Cloud Storage file at query time, so it is always current but slower. A native copy, made with CREATE TABLE ... AS SELECT, is fast but as old as the moment it ran. A federated query sends SQL to a live database such as Cloud SQL through EXTERNAL_QUERY and a connection.

How do you get a query result out of BigQuery into a Sheet, and a whole table into Cloud Storage, and in which formats?

Save the query result to Google Sheets from the console, or to Drive as CSV or JSONL, or download it as CSV or JSON. A whole table goes to Cloud Storage through an extract job as CSV, newline-delimited JSON, Avro or Parquet.

Why should a report filter on @kind instead of an f-string, and why does a cleansing test hand over its rows out of order?

A parameter's value travels beside the SQL, so it can never change the statement, and one file serves every value. The test reverses the rows because duplicated keeps the first copy in frame order, so only out-of-order input proves the transform sorts by id before choosing.
