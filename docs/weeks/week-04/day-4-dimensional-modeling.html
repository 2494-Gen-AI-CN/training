Modeling

Data models: from business questions to tables

A warehouse starts as a list of questions somebody wants answered. The model is the plan that turns those questions into tables.

What a data model is

A data model is a blueprint of the data an organisation collects: which datasets exist, how they relate to each other, and how they are stored and analysed.12 It is drawn and agreed before anyone writes a CREATE TABLE, so a mistake costs an eraser instead of a migration.

Week 3 used one without naming it. Before the schema file turned the desk into seven MySQL tables, someone decided that tickets belong to customers, that agents take tickets and that a priority sets an SLA. Those decisions were the model, and the file was its last stage.

What a model does in a warehouse

In a warehouse the model settles the three verbs of that definition:

  • organising: which numbers sit together in one table and which descriptions sit beside them;
  • storing: the column types and the physical layout, such as partitions, that decide what a query must read;
  • retrieving: the joins and groupings an analyst writes, which follow the shape the model gave the tables.

A warehouse model serves a different workload from the desk's MySQL tables. A transactional database takes many small writes, one ticket at a time. A warehouse is loaded in batches and then read many times, mostly by queries that scan and summarise large ranges of rows.3

The model follows the workload. The desk's tables are built so that a change touches one row in one place. The warehouse's tables are built so that a question touches as few tables as possible.

From a requirement to a table

Modeling captures the business rules first. A conceptual model bridges those rules to the database, and the logical and physical models then add types, keys and platform details until the tables can be built.1 The next section takes each level in turn. The work runs from what the business asks towards the DDL.

Suppose the desk's support lead asks three questions of the ticket history:

  1. How many events did each agent's tickets have, and how many sit with no agent?
  2. How do the events split by priority, and how many SLA hours does each priority allow?
  3. How many events happened on each day, and which of those days were weekends?

Each question names something counted and the ways it is cut. Counted things become measures in a fact table, and the ways they are cut become dimensions. Both words get a proper definition in the dimensional modeling section below.

Questions name the dimensions

A good dimension design starts by asking users what they analyse. A request such as "sales by salesperson, by month" names its own dimensions: a salesperson dimension, and a date dimension with a month attribute.4 The word "by" is the signal to listen for.

QuestionWhat is countedCut by
Events per agentticket eventsagent
Events and SLA per priorityticket eventspriority, reached through the ticket
Events per dayticket eventsdate, with its weekday

Every row of the table counts the same thing, a ticket event, so the desk needs one fact table. No question cuts by customer yet, but the customer is an obvious next "by", so the model keeps a customer dimension from the start.

A model is never finished when it first ships. A warehouse should be designed to adapt as requirements evolve, so a model built for today's questions gains columns and tables later.5 The limit is what the stored detail allows. If events were never kept one per row, no later column brings the per-event detail back.

In someone else's project the model usually shows up first as a diagram: boxes named ticket, customer and agent with lines between them, committed or photographed before any SQL exists.

Takeaways
  • A data model is the agreed plan of what data exists, how it relates and how it is stored.
  • Warehouse models suit batch loads and many reads; transactional models suit many small writes.
  • Business questions come first, and each "by" in a question names a dimension.
Say it in an interview

A data model is the blueprint of an organisation's data: what it collects, how the pieces relate and how it's stored and queried. In a warehouse it decides how data is organised into tables and how it's laid out on disk, and that decides how quickly and cheaply people can get answers back out.

I start from the business questions. "Events per agent, per month" tells me I'm counting events and cutting them by agent and by date. That becomes a conceptual sketch, then a logical model with keys and a grain, then physical tables in one specific engine.

Model levels

Conceptual, logical and physical models

The three levels describe one design at three distances from the database. Each adds detail the one before it left out on purpose.

The conceptual model

A conceptual model gives the big picture: the entities and the business rules between them, drawn simply enough that business stakeholders and analysts can agree on it.12 It holds names and lines and nothing else. For the desk's warehouse it holds four entities:

  • a ticket, raised by one customer, with one priority;
  • a customer, who raises tickets;
  • an agent, who may be assigned a ticket;
  • an event, something that happened to one ticket at one moment: it was opened, assigned or closed.

A support lead can read this picture and say "yes, that is how the desk works" without knowing what a key is. Stakeholders sign off on this level.

The logical model

A logical model adds data types, relationships and key fields, and stays independent of any one database product.12 The desk's logical model says that an event has an identifier, a kind and a time. It points at one ticket, and a ticket points at one customer, one priority and at most one agent.

For a warehouse the logical model also states the grain, meaning what one row of the main table stands for. The desk's choice is one row per ticket event. Keys, attributes and grain are enough to argue about whether the design is correct, and nothing in them says MySQL or BigQuery yet.

The physical model

A physical model maps the logical one onto one database system, with its real field types and the tuning that system offers.12 For the desk in BigQuery that means:

  • dataset-qualified names such as desk_dw.fact_ticket_events;
  • GoogleSQL types such as INT64 and DATE;
  • partitioning and clustering on the fact table, which a later section covers.

The physical model is where cost and speed are decided, so it is tied to one engine's features and prices. In the BigQuery sandbox, for example, a partition older than 60 days expires.6 A fact table partitioned by an old date can therefore load and still come out empty.

LevelMain readerWhat it holdsTied to one engine?
Conceptualbusiness stakeholders and analystsentities and the rules between themno
Logicalthe team designing the warehouseattributes, keys, relationships and the grainno
Physicalthe developers who build ittypes, table names, partitioning and clusteringyes

In a repository the three levels look different. A sketch of named boxes is conceptual. The same sketch with keys and attributes listed inside each box is logical. A DDL file with column types, PARTITION BY and CLUSTER BY is physical.

Types change with the engine

The clearest test of the split is a change of engine. The desk's customers keep the same logical attributes in MySQL and in the BigQuery staging table, but the physical types differ:

Takeaways
  • Conceptual models show entities and rules, simple enough for stakeholders to sign off.
  • Logical models add keys, attributes, relationships and the grain, without naming an engine.
  • Physical models use one engine's types, names and tuning, such as partitioning and clustering.
  • A change of engine rewrites the physical model and keeps the logical one.
Say it in an interview

A conceptual model is the big picture, the entities and how they relate, simple enough for business people to sign off. A logical model adds the attributes, keys, relationships and, in a warehouse, the grain, still without picking a database. The physical model is the logical one written for a specific engine, with real types and features like partitioning.

Stakeholders read the conceptual model and developers build from the physical one. The logical model is the one that survives if we ever change databases.

Dimensional modeling

Dimensional modeling: facts, dimensions, measures and grain

Dimensional modeling is the way most warehouses organise their tables. It sorts every column into one of two kinds of table.

Fact tables and measures

A fact table holds dimension keys and numeric measures. Each row records one event or measurement, and the measures are the numbers that row contributes to a total.78

The desk's fact table, fact_ticket_events, has one row per ticket event. Its measures are event_count, which is 1 on every row so that a sum counts events, and hours_since_open, the hours between the ticket opening and that event. Everything else on the row is a key pointing at a dimension, or a short code such as the event's kind.

Dimension tables and surrogate keys

Dimension tables hold the descriptive attributes that queries filter and group by: who, what, where and when.78 The desk has dimensions for the ticket, the customer, the agent and the date. A query takes its numbers from the fact and its words, such as an agent's name or a weekday, from the dimensions.

Each dimension row has a surrogate key, an integer the warehouse assigns itself. Surrogate keys insulate the warehouse from the ids of source systems, and they make it possible to keep several versions of one customer, each under its own key.4 That second use comes back in the history sections at the end of the page.

The date dimension is the most common dimension of all. It stores one row per date with attributes such as year, month and weekday, and its key is the date written as a YYYYMMDD integer, so 2026-11-05 has the key 20261105.4

State the grain first

The grain is what exactly one row of the fact table represents. The dimension keys on a fact row set that grain, and a fact table must load at one consistent grain.7 Teams state the grain in words before choosing any column: "one row per ticket event".

Mixing grains gives wrong sums.9 Suppose someone copies a ticket-level number, the hours each ticket took to close, onto every event row. Tickets 1 and 3 took 3 and 10 hours, so the true total is 13. In the loop below, each tuple of three values is unpacked into three names, and the third is added to a running total.

rows = [
    ("open", 1, 3),
    ("closed", 1, 3),
    ("open", 3, 10),
    ("closed", 3, 10),
]
total = 0
for kind, ticket_id, hours_to_close in rows:
    total = total + hours_to_close
print(total)
26

Each ticket has two event rows, so each closing time was counted twice. The fix keeps every measure at the fact's grain. The closing event's own hours_since_open holds 3 or 10, the opening event's holds 0, and a sum over closing events gives 13.

Additive, semi-additive and non-additive measures

Measures differ in where a sum is valid:7

  • additive measures sum across every dimension, like event_count per agent, per day or in total;
  • semi-additive measures sum across some dimensions only, like the tickets open at the end of each day, which add up across agents but not across days;
  • non-additive measures sum across none, like a rate or a temperature, so a report recomputes them from their parts.

Dimensional modeling against ER modeling

Week 3's desk followed entity-relationship modeling and normalisation, so each fact is stored once and a change touches one row. A dimensional model accepts repeated descriptive data in exchange for fewer joins and faster questions.18

ER model (week 3)Dimensional model
Built formany small writes that must stay consistentreading and summarising history
Shapemany normalised tables linked by foreign keysone fact table surrounded by dimensions
Repetitionavoidedaccepted in the dimensions

The two coexist. The desk keeps its normalised MySQL tables for the day's work and copies their history into the dimensional model for questions.

A dimensional model is easy to recognise in someone else's project. Table names start with fact_ and dim_, there is a date_key column, and measures carry names like event_count or amount.

Takeaways
  • Fact tables hold keys and numeric measures; dimension tables hold the words queries filter and group by.
  • State the grain in words before choosing columns, and keep one grain per fact table.
  • Additive, semi-additive and non-additive measures differ in where a sum is valid.
  • ER models keep writes safe; dimensional models trade repetition for fast questions.
Say it in an interview

In a dimensional model, a fact table records events or measurements at one stated grain. Its columns are keys to dimensions and numeric measures, like an event count or an amount. Dimension tables hold the descriptive attributes, like an agent's name or a date's month, that you filter and group by.

The point is fast, simple analytic queries, with one join from the fact to each dimension. An ER model is normalised so writes stay consistent, while a dimensional model accepts some repetition so questions are cheap. I'd keep the normalised database for the application and build the dimensional one for reporting.

Star schema

The star schema built for the desk

A star schema has one central fact table of events or measurements, and its dimension tables form the points of the star, each joined to the fact on a key.5 It suits analytic queries, which filter and group by dimensions and summarise the fact.5

One fact, five dimensions

The desk's star lives in the BigQuery dataset desk_dw and reads from the staging tables in desk_raw:

TableOne row perKey
dim_datecalendar day, 2026-10-01 to 2026-12-31date_key, YYYYMMDD
dim_agentagent, plus one row for no agentagent_key
dim_customercustomercustomer_key
dim_prioritypriority, with its SLA hourspriority
dim_ticketticket, with its priority and SLA hours copied inticket_key
fact_ticket_eventsticket eventevent_id, plus a key per dimension

The fact points at four dimensions directly: ticket, customer, agent and date. dim_priority comes in the snowflake section. The agent dimension carries one extra row, key 0, named unassigned. A special member row such as key 0 stands in for a missing value, so no fact row needs a null key and every join finds a match.4

Building a date dimension in one statement

GENERATE_DATE_ARRAY builds an array of dates, and UNNEST turns an array into rows, so one statement fills a date dimension.10 FORMAT_DATE('%Y%m%d', day) writes a date as text, and the cast to INT64 turns that text into the YYYYMMDD key.11 The is_weekend column is true for Saturday and Sunday.

-- One row per day for the last quarter of 2026.
CREATE OR REPLACE TABLE desk_dw.dim_date AS
SELECT
  CAST(FORMAT_DATE('%Y%m%d', day) AS INT64) AS date_key,
  day AS full_date,
  EXTRACT(YEAR FROM day) AS year,
  EXTRACT(MONTH FROM day) AS month,
  FORMAT_DATE('%A', day) AS weekday,
  EXTRACT(DAYOFWEEK FROM day) IN (1, 7) AS is_weekend
FROM UNNEST(GENERATE_DATE_ARRAY('2026-10-01', '2026-12-31')) AS day;

The new table holds 92 rows, one for each day from October 1 to December 31. Three of them, read back:

SELECT
  date_key,
  full_date,
  weekday,
  is_weekend
FROM desk_dw.dim_date
WHERE full_date BETWEEN '2026-10-17' AND '2026-10-19'
ORDER BY date_key;

| date_key | full_date  | weekday  | is_weekend |

The fact table at its grain

The fact statement reads the staged events, joins each one to its ticket and customer, and keeps one row per event. ROW_NUMBER() OVER (...) numbers the rows inside each group, and QUALIFY filters on that number after it is computed, so only the first copy of a duplicated event survives.1213

-- One row per ticket event, the fact's grain.
CREATE OR REPLACE TABLE desk_dw.fact_ticket_events AS
SELECT
  e.event_id,
  t.ticket_id AS ticket_key,
  c.customer_key,
  COALESCE(t.agent_id, 0) AS agent_key,
  CAST(FORMAT_DATE('%Y%m%d', DATE(e.created_at)) AS INT64) AS date_key,
  DATE(e.created_at) AS event_date,
  e.kind,
  DATETIME_DIFF(e.created_at, t.opened_at, HOUR) AS hours_since_open,
  1 AS event_count
FROM desk_raw.ticket_events AS e
JOIN desk_raw.tickets AS t ON t.ticket_id = e.ticket_id
JOIN desk_dw.dim_customer AS c ON c.customer_id = t.customer_id
WHERE e.kind IN ('open', 'assigned', 'closed')
  AND e.created_at >= t.opened_at
QUALIFY ROW_NUMBER() OVER (PARTITION BY e.ticket_id, e.kind, e.created_at ORDER BY e.event_id) = 1;

Counting the new table's rows gives 11. Staging holds 14 events, and three are bad: a misspelt kind, an event dated an hour before its ticket opened, and a second copy of one assignment. The WHERE lines drop the first two and QUALIFY drops the copy.

Querying the star

A star query joins the fact to each dimension it needs, filters with WHERE, groups with GROUP BY and aggregates with COUNT or SUM.13 The first business question, events per agent, needs one join:

-- Assignments and closures per agent.
SELECT
  a.name AS agent,
  COUNT(*) AS events
FROM desk_dw.fact_ticket_events AS f
JOIN desk_dw.dim_agent AS a ON a.agent_key = f.agent_key
WHERE f.kind IN ('assigned', 'closed')
GROUP BY a.name
ORDER BY events DESC, agent;
+------------+--------+
|   agent    | events |
+------------+--------+
| unassigned |      3 |
| Marco      |      1 |
| Priya      |      1 |
+------------+--------+

The three closed tickets never had an agent in the desk's data, so their closures count under key 0. In someone else's code a star query has the same look: JOIN dim_x AS x ON x.key = f.x_key once per dimension, and a GROUP BY on a dimension attribute.

The cost of the star is repetition. Every ticket row carries its priority's SLA hours, so when a descriptive value changes, the model needs a rule for the old copies.9 Slowly changing dimensions, near the end of the page, are those rules.

Conformed dimensions

A conformed dimension is one dimension table shared by several fact tables.8 If the desk later adds a fact table of customer invoices, it joins the same dim_date and dim_customer. A report can then put ticket events and invoices side by side for the same days and the same customers.

Takeaways
  • A star is one fact table joined directly to denormalised dimension tables.
  • A special member row, like agent key 0, keeps every fact row joinable.
  • A star query joins, filters, groups and aggregates in one SELECT.
  • Conformed dimensions let several fact tables share one date or customer table.
Say it in an interview

A star schema is one fact table in the middle with dimension tables around it, each joined on a key. For a support desk I'd state the grain first, one row per ticket event. Then the fact gets keys to the ticket, customer, agent and date, plus measures like an event count and the hours since the ticket opened.

Queries stay simple. I join the fact to the dimensions I need, filter with WHERE, group by a dimension attribute and count or sum. Events per agent is one join to the agent dimension and a GROUP BY on the agent's name.

Snowflake schema

The snowflake schema and when its joins pay

A snowflake schema is a star whose dimension tables are themselves normalised into linked tables. BigQuery supports both shapes.14

Normalising the dimensions

In the desk's star, dim_ticket copies each ticket's priority and its sla_hours onto the ticket row. Moving sla_hours out into dim_priority, with dim_ticket keeping only the priority as a key into it, is the snowflaked form. Folding sla_hours back into dim_ticket is the star form.9

This is week 3's normalisation applied to the dimensions only. The fact table is never split: it stays one table at its grain, and only the tables around it branch out.

On sight, a snowflake shows itself as a dimension holding a foreign key to another dimension. Its queries reach the fact through a chain of joins, such as dim_priority to dim_ticket to the fact.

One question, two shapes

The second business question asks for events per priority, with each priority's SLA hours. The star form needs one join:

-- Events per priority, star form.
SELECT
  t.priority,
  t.sla_hours,
  COUNT(*) AS events
FROM desk_dw.fact_ticket_events AS f
JOIN desk_dw.dim_ticket AS t ON t.ticket_key = f.ticket_key
GROUP BY t.priority, t.sla_hours
ORDER BY t.sla_hours;
+----------+-----------+--------+
| priority | sla_hours | events |
+----------+-----------+--------+
| high     |         4 |      4 |
| normal   |        24 |      6 |
| low      |        72 |      1 |
+----------+-----------+--------+

The snowflake form reaches the same columns through a second join, from the ticket to its priority:

-- Events per priority, snowflake form.
SELECT
  p.priority,
  p.sla_hours,
  COUNT(*) AS events
FROM desk_dw.fact_ticket_events AS f
JOIN desk_dw.dim_ticket AS t ON t.ticket_key = f.ticket_key
JOIN desk_dw.dim_priority AS p ON p.priority = t.priority
GROUP BY p.priority, p.sla_hours
ORDER BY p.sla_hours;
+----------+-----------+--------+
| priority | sla_hours | events |
+----------+-----------+--------+
| high     |         4 |      4 |
| normal   |        24 |      6 |
| low      |        72 |      1 |
+----------+-----------+--------+

Both return the same rows. The snowflake version stores each SLA number once, in the three rows of dim_priority, and pays with one more join in every query that needs it.

When snowflaking pays

Snowflaking stores less repeated text but adds joins. BigQuery performs best on denormalised data, because joining large tables on every query is resource intensive.15 A snowflaked dimension can still be worth it in three cases:4

  • the dimension is very large, and storage matters more than query speed;
  • another fact table sits at a higher grain, such as a product subcategory, and needs a dimension at that level;
  • history is tracked at the higher level, such as a priority whose SLA hours change over time.

For the desk, with three priorities and six tickets, the star form wins. The repeated SLA hours cost almost nothing, and every priority question saves a join.

Nested and repeated fields

BigQuery has a third way, and its documentation calls it the native one: nested and repeated fields.14 A ticket row can hold its events in a repeated field, an array of records inside the row, so related rows stay together without a join on every query.15

DesignShapeGood fit
Stara fact plus flat, denormalised dimensionsmost reporting; the default for a warehouse
Snowflakedimensions split into linked lookup tablesvery large dimensions, facts at a higher grain, history kept at a higher level
Nested and repeatedchild rows stored inside the parent rowBigQuery data always read together, such as a ticket and its events

The desk keeps a flat star because its questions cut events by several dimensions at once, and flat tables keep each cut a plain join.

Takeaways
  • A snowflake normalises the dimensions into lookup tables, and the fact stays whole.
  • Snowflaking saves repeated text and costs a join in every query that needs the detail.
  • BigQuery favours denormalised data and offers nested, repeated fields as its native option.
Say it in an interview

A snowflake schema is a star whose dimensions are normalised further. The ticket dimension points to a separate priority table instead of carrying the priority's details itself, so it stores less repetition, but every query that needs the detail pays an extra join.

I'd use a star by default, especially in BigQuery, which performs best on denormalised data. I'd snowflake a dimension when it's huge and storage matters, when another fact sits at that higher level, or when the higher level keeps its own history. In BigQuery I'd also consider nested, repeated fields for child rows that are always read with their parent.

Physical model

The physical model in BigQuery: partitions, clusters and the cache

The physical model decides what a query has to read, and in BigQuery what a query reads is what it costs. Three features of the desk's fact table settle that.

Partitioning and pruning

A partitioned table is divided into segments. BigQuery offers three partitioning strategies:16

  • a time-unit column: a DATE, DATETIME or TIMESTAMP column of the table;
  • ingestion time: the moment each row was loaded;
  • integer range: a whole-number column cut into ranges, such as customer ids in blocks of a thousand.

A query that filters on the partition column prunes partitions. It skips the segments the filter rules out, so it scans and bills fewer bytes and runs faster.17 The desk's fact is partitioned by event_date, one partition per day, because most questions ask about a range of days.

A CREATE TABLE with PARTITION BY and CLUSTER BY before its AS SELECT creates a partitioned and clustered table from a query.18 The fact statement from the star section gains two lines, PARTITION BY event_date and CLUSTER BY ticket_key, just before AS. Everything else stays exactly as it was:

-- One row per ticket event, partitioned by day and clustered by ticket.
CREATE OR REPLACE TABLE desk_dw.fact_ticket_events
PARTITION BY event_date
CLUSTER BY ticket_key
AS
SELECT
  e.event_id,
  t.ticket_id AS ticket_key,
  c.customer_key,
  COALESCE(t.agent_id, 0) AS agent_key,
  CAST(FORMAT_DATE('%Y%m%d', DATE(e.created_at)) AS INT64) AS date_key,
  DATE(e.created_at) AS event_date,
  e.kind,
  DATETIME_DIFF(e.created_at, t.opened_at, HOUR) AS hours_since_open,
  1 AS event_count
FROM desk_raw.ticket_events AS e
JOIN desk_raw.tickets AS t ON t.ticket_id = e.ticket_id
JOIN desk_dw.dim_customer AS c ON c.customer_id = t.customer_id
WHERE e.kind IN ('open', 'assigned', 'closed')
  AND e.created_at >= t.opened_at
QUALIFY ROW_NUMBER() OVER (PARTITION BY e.ticket_id, e.kind, e.created_at ORDER BY e.event_id) = 1;

Run again, the statement rebuilds the table with the same 11 rows, now in three daily partitions: one event on 2026-10-17, six on 2026-10-18 and four on 2026-10-19.

Clustering

Clustering sorts a table's storage by up to four columns, and a filter on those columns reduces the bytes scanned. The gain grows with the size of the table.19 The desk clusters its fact by ticket_key, so the events of one ticket sit together inside each daily partition. A question about one ticket then reads only the blocks that hold it.

The two work together. The partition filter removes whole days, then the cluster order narrows the read inside the days that remain. On 11 rows neither makes a measurable difference, so the desk's example cannot show the gain. It appears when the same fact holds years of events.

The query cache and the dry run

Two tools show what a query costs. A dry run reports the bytes a query would process, without running it:20

bq query --dry_run --use_legacy_sql=false 'SELECT kind, COUNT(*) AS events FROM desk_dw.fact_ticket_events GROUP BY kind'

The command prints a byte count and runs nothing. On a fact with months of data, the same dry run with a filter on event_date counts only the partitions the filter keeps.

Query results are cached for about 24 hours per user and project. A rerun of the same query text over unchanged tables reads the cached result and bills no bytes.21 The cache is skipped when the query calls a non-deterministic function such as CURRENT_TIMESTAMP, or when a table it reads has changed.21 A fast, free rerun therefore shows only that the cache answered. The dry run is the reliable measure of cost.

The sandbox's 60-day partition expiration

The BigQuery sandbox applies a 60-day default expiration to tables and partitions, and allows no DML.6 A partition of fact_ticket_events is aged by its event_date, so a partition more than 60 days old is deleted, and a table partitioned by an old date comes out empty.

The desk's events date from mid-October 2026, so its partitions last until mid-December 2026. A project whose data dates from 2019 would load a partitioned fact and find nothing in it. That project partitions by load date instead, or leaves a small fact unpartitioned, and says why in its README.

Design best practices on one page

Warehouse design advice falls into three groups. On the data-quality side, a load should test integrity between related tables and use special member rows instead of null keys.4

Takeaways
  • Partitions by a date column, ingestion time or integer range let a matching filter prune them.
  • Clustering sorts storage by up to four columns, so filters on them scan fewer bytes.
  • A cached rerun bills nothing; a dry run reports the bytes before anything runs.
  • The sandbox expires partitions older than 60 days, so old dates load empty.
Say it in an interview

BigQuery can partition a table by a date or timestamp column, by ingestion time, or by an integer range. When a query filters on the partition column, BigQuery skips the partitions the filter rules out, so it scans and bills fewer bytes and runs faster. A filter on any other column still reads every partition.

On a fact table I'd partition by the event date and cluster by the column people look up most, like the ticket key. I check the cost with a dry run first. Identical reruns over unchanged tables come from the cache for about a day and bill nothing.

Slowly changing dimensions

Slowly changing dimensions: types 0 to 6 and how to choose

Dimensions change too, only slowly. Dana Whitfield, customer 1, pays 49.00 a month through October, and on 2026-11-05 she moves to the 199.00 plan.

What should last month's report say?

A slowly changing dimension manages values that change slowly and unpredictably, such as a customer's email or plan.9 The question it raises is what happens to the old value. Suppose a report sums October's ticket events by the customer's monthly fee:

  • if the dimension overwrites Dana's fee, her October events report under 199.00, a plan she did not have yet;
  • if the dimension keeps both versions, her October events report under 49.00 and November's under 199.00.

Neither answer is wrong in general. The first suits "what are our customers worth today", and the second suits "what did October look like". The rule chosen for each attribute is its SCD type.

Types 0 to 6

Each type is a different rule for the old value:48

TypeOn a changeWhat it keeps
0nothing happens; the value is fixedthe original only
1the value is overwrittenthe current value only
2the old row is closed and a new row addedevery version, with dates
3the old value moves to a previous-value columnthe current value and one before it
4changing attributes live in a separate mini-dimension or history tablethe main row plus a separate history
5a hybrid that combines simpler typeswhat the combined types keep
6a hybrid of types 1, 2 and 3what types 1, 2 and 3 keep, together

Type 3 keeps only limited history and is rarely used, and types 5 and 6 are harder to maintain.48

Choosing a type

Choose per attribute, from two questions: how does this data change, and what must reports show? Use type 1 where no history matters, and type 2 only where a report must show the value in force when the event happened.4 On the desk:

  • dim_date is type 0, because a date's attributes never change;8
  • dim_ticket is type 1, because its status is current state and the history already sits in the fact;
  • dim_customer is type 2, because revenue questions need the fee a customer paid at the time.

An attribute that changes often belongs in the fact table, not in a type 2 dimension, or every change would add a dimension row.4 Type 2 costs more rows and a date-range join, while type 1 is simple but files every past event under the new value.4

Effective dates and a current flag

Three columns make type 2 history queryable:

  • effective_from holds the first day the version is valid;
  • effective_to holds the first day it no longer is, so the range excludes that day;
  • is_current is true for the version in force.

A type 2 change sets the old row's end date and current flag to false, then adds a new current row whose start date is that end date.4 After Dana's change her rows read:

SELECT
  customer_key,
  effective_from,
  effective_to,
  is_current
FROM desk_dw.dim_customer
WHERE customer_id = 1
ORDER BY customer_key;
+--------------+----------------+--------------+------------+
| customer_key | effective_from | effective_to | is_current |
+--------------+----------------+--------------+------------+
|            1 | 2026-10-01     | 2026-11-05   | false      |
|            5 | 2026-11-05     | 9999-12-31   | true       |
+--------------+----------------+--------------+------------+

The far-future date 9999-12-31 is the open end of the version still in force. Facts join to a type 2 dimension with a time-based lookup on the event's date.9 Inside the fact statement, the customer join line stays and gains two conditions below it: AND DATE(e.created_at) >= c.effective_from and AND DATE(e.created_at) < c.effective_to.

Each event now matches exactly one of Dana's versions. Without the two date conditions, each of her four October events would match both rows and be counted twice. The end date is exclusive: with <=, an event on 2026-11-05 would match both versions. Once the fact is rebuilt, a query counts which version her events carry:

-- Dana's events by the version of her customer row they joined.
SELECT
  c.customer_key,
  COUNT(*) AS events
FROM desk_dw.fact_ticket_events AS f
JOIN desk_dw.dim_customer AS c ON c.customer_key = f.customer_key
WHERE c.customer_id = 1
GROUP BY c.customer_key;

It returns one row, customer key 1 with 4 events. All four of Dana's events fall in October, before her 199.00 version starts, so key 5 has none yet.

Takeaways
  • A slowly changing dimension needs a rule for what happens to an attribute's old value.
  • Types 0 to 3 fix, overwrite, version or keep one previous value; 4 to 6 add history and hybrids.
  • Choose per attribute, from how it changes and what reports must show.
  • Type 2 rows carry effective dates and a current flag, and facts join on the event date.
Say it in an interview

A slowly changing dimension is one whose attributes change now and then, like a customer's plan. Type 0 never changes, type 1 overwrites, type 2 adds a new dated row per version, and type 3 keeps one previous value in an extra column. Type 4 moves the changing attributes to a history table, and 5 and 6 are hybrids, with 6 combining 1, 2 and 3.

I choose per attribute. If reports must show the value as it was when the event happened, like a customer's fee, it's type 2 with effective dates. If only the current value matters, it's type 1. Anything that changes constantly goes in the fact table instead.

SCD type 2

SCD type 2 in Python, tested

The type 2 rule is easiest to trust in a plain Python function. A function that takes the current rows, the source rows and a date, and returns the new rows, touches no database, so a test can check it in milliseconds.

A function from old rows to new rows

Five things in it are new to the course: three pieces of syntax and two built-in functions:

  • [dict(row) for row in dimension] is a list comprehension, which builds a new list holding a copy of each row;
  • the braces after current = form a dict comprehension with an if, mapping each customer id to its current row;
  • the parentheses inside max(...) and all(...) hold generator expressions, which hand over one value at a time;
  • default=0 makes max return 0 when it is handed no values, so an empty dimension starts its keys at 1;
  • all(...) returns True only when every value it is handed is true, here every tracked column matching.
from datetime import date

TRACKED = ("name", "email", "country", "monthly_fee")
OPEN_END = date(9999, 12, 31)


def apply_scd2(dimension, source, as_of):
    """Return the customer dimension after applying the source rows as an SCD type 2."""
    rows = [dict(row) for row in dimension]
    current = {row["customer_id"]: row for row in rows if row["is_current"]}
    next_key = max((row["customer_key"] for row in rows), default=0) + 1
    for src in source:
        old = current.get(src["customer_id"])
        if old is not None and all(old[col] == src[col] for col in TRACKED):
            continue
        if old is not None:
            old["effective_to"] = as_of
            old["is_current"] = False
        rows.append({
            "customer_key": next_key,
            "customer_id": src["customer_id"],
            "name": src["name"],
            "email": src["email"],
            "country": src["country"],
            "monthly_fee": src["monthly_fee"],
            "effective_from": as_of,
            "effective_to": OPEN_END,
            "is_current": True,
        })
        next_key += 1
    return rows

Saved as transform.py, the module prints nothing. A customer whose tracked values all match the current row is skipped. A changed customer has the current row closed, and a changed or new customer gets a new current row with the next surrogate key. as_of is always passed in, so the same call gives the same rows on any day.

The comparisons are safe for two reasons. A date compares with < and >=, which is how an effective-date range picks a version.22 The fee is a Decimal, which compares exactly where a float may not.23

from datetime import date
from decimal import Decimal

from transform import OPEN_END, apply_scd2

dana = {"customer_key": 1, "customer_id": 1, "name": "Dana Whitfield",
        "email": "dana@example.com", "country": "CA", "monthly_fee": Decimal("49.00"),
        "effective_from": date(2026, 10, 1), "effective_to": OPEN_END, "is_current": True}
source = [{"customer_id": 1, "name": "Dana Whitfield", "email": "dana@example.com",
           "country": "CA", "monthly_fee": Decimal("199.00")}]
for row in apply_scd2([dana], source, date(2026, 11, 5)):
    print(row["customer_key"], row["monthly_fee"], row["effective_from"],
          row["effective_to"], row["is_current"])
1 49.00 2026-10-01 2026-11-05 False
2 199.00 2026-11-05 9999-12-31 True

Testing it with pytest

The tests build their rows inline in a fixture, so they need no MySQL, no BigQuery and no environment variable. Each test gets a fresh copy of the fixture's rows.

"""Tests for the SCD type 2 transform."""
from datetime import date
from decimal import Decimal

import pytest

from transform import OPEN_END, apply_scd2

AS_OF = date(2026, 11, 5)


@pytest.fixture
def dimension():
    """One current row for Dana at 49.00."""
    return [{"customer_key": 1, "customer_id": 1, "name": "Dana Whitfield",
             "email": "dana@example.com", "country": "CA", "monthly_fee": Decimal("49.00"),
             "effective_from": date(2026, 10, 1), "effective_to": OPEN_END, "is_current": True}]


def source_row(fee):
    """Dana as the source system holds her, at the given fee."""
    return {"customer_id": 1, "name": "Dana Whitfield", "email": "dana@example.com",
            "country": "CA", "monthly_fee": Decimal(fee)}


def test_unchanged_customer_changes_nothing(dimension):
    """Equal tracked values leave the dimension as it was."""
    assert apply_scd2(dimension, [source_row("49.00")], AS_OF) == dimension


def test_changed_customer_closes_old_row_and_adds_new(dimension):
    """A new fee closes the current row and appends a current one."""
    old, new = apply_scd2(dimension, [source_row("199.00")], AS_OF)
    assert (old["effective_to"], old["is_current"]) == (AS_OF, False)
    assert (new["customer_key"], new["monthly_fee"], new["is_current"]) == (2, Decimal("199.00"), True)


def test_input_rows_are_not_changed(dimension):
    """The function copies its input instead of editing it."""
    apply_scd2(dimension, [source_row("199.00")], AS_OF)
    assert dimension[0]["is_current"] is True

Loading the result without DML

The sandbox allows no DML, so no UPDATE can close Dana's old row in place.6 A type 2 change becomes a whole-table load instead: read the dimension, apply the function, and replace the table with WRITE_TRUNCATE.6

The client finds its credentials through Application Default Credentials, written once by gcloud auth application-default login, so no key file sits in the repository.24 query(sql).result() waits for the job and returns its rows.25 Passing the table's own schema to the load keeps BigQuery from guessing the column types.25

import os
from datetime import date
from decimal import Decimal

from google.cloud import bigquery

from transform import apply_scd2

bq = bigquery.Client(project=os.environ["DESK_GCP_PROJECT"])
table = "desk_dw.dim_customer"
dimension = [dict(row) for row in bq.query(f"SELECT * FROM {table}").result()]
source = [{"customer_id": 1, "name": "Dana Whitfield", "email": "dana@example.com",
           "country": "CA", "monthly_fee": Decimal("199.00")}]
rows = apply_scd2(dimension, source, date(2026, 11, 5))
payload = [
    {key: str(value) if isinstance(value, (date, Decimal)) else value for key, value in row.items()}
    for row in rows
]
config = bigquery.LoadJobConfig(schema=bq.get_table(table).schema,
                                write_disposition="WRITE_TRUNCATE")
job = bq.load_table_from_json(payload, table, job_config=config)
job.result()
print(job.output_rows)

It prints 5: the four customers' rows, with Dana's closed, plus her new current row under key 5. Only Dana is in source, and apply_scd2 leaves every customer it is not given exactly as it was. The payload step writes dates and Decimals as text, because a load from JSON takes plain values.

Inside the payload step, isinstance(value, (date, Decimal)) asks whether a value is a date or a Decimal. The conditional expression x if c else y gives x when c is true and y otherwise, so those values become str(value) and every other value passes through unchanged.

Keeping the history on a rerun

Once the dimension keeps history, its SQL statement must stop rebuilding it. CREATE OR REPLACE on every run would wipe Dana's closed row, so the customer statement becomes CREATE TABLE IF NOT EXISTS:

-- Customers, kept as an SCD type 2 after the first build.
CREATE TABLE IF NOT EXISTS desk_dw.dim_customer AS
SELECT
  ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_key,
  customer_id,
  name,
  email,
  country,
  monthly_fee,
  DATE '2026-10-01' AS effective_from,
  DATE '9999-12-31' AS effective_to,
  TRUE AS is_current
FROM desk_raw.customers;

A first run builds four current rows, with keys 1 to 4 from ROW_NUMBER().12 Once the table exists, the statement does nothing.18 In someone else's code, type 2 looks like this: a function taking current rows, source rows and an as-of date, and 9999-12-31 as the open end.

Takeaways
  • Type 2 fits a pure function: current rows, source rows and a date in, new rows out.
  • Its tests build rows inline and need no database.
  • Without DML, the new dimension replaces the old in one load that uses the table's schema.
  • A history-keeping dimension is created only when missing, never replaced.
Say it in an interview

I write type 2 as a pure function. It takes the current dimension rows, the source rows and an as-of date, and returns the new rows: each changed customer's current row is closed on the as-of date, and a new current row gets the next surrogate key. Because it never touches a database, I can test it with pytest on a few inline rows.

Then I load the result. A BigQuery sandbox has no UPDATE, so I replace the whole table with WRITE_TRUNCATE and pass the table's own schema so nothing is autodetected.

Check yourself

Answer each question out loud before you open it. Each one matches a section above.

What is a data model, and how does "events per agent, per month" turn into tables?

A data model is the blueprint of what data an organisation keeps, how the pieces relate and how they are stored and queried. The thing counted, events, becomes a fact table at one row per event. Each "per" names a dimension: an agent dimension, and a date dimension with a month attribute.

Which of the three model levels does a business stakeholder sign off, and which one is rewritten when the desk moves from MySQL to BigQuery?

The conceptual model, with its entities and rules, is the one stakeholders agree on. A change of engine rewrites the physical model, for example DECIMAL(8,2) becoming NUMERIC. The logical model, with its attributes, keys and grain, survives the move.

What are facts, dimensions and measures, and why is the grain stated before any column?

A fact table records events at one grain and holds keys plus numeric measures, such as event_count. Dimension tables hold the descriptive attributes that queries filter and group by. Stating the grain first keeps every measure at one level; a ticket-level number copied onto event rows is summed twice.

How does dimensional modeling differ from the entity-relationship model behind the desk's MySQL tables?

The ER model is normalised so each fact is stored once and writes stay consistent. A dimensional model accepts repeated descriptive data so analytic questions need only one join per dimension. The application keeps the first and reporting reads the second.

Design a star schema for an online shop's orders: grain, fact, dimensions and measures.

Grain: one row per order line. The fact fact_order_lines holds keys to product, customer and date dimensions, with quantity and amount as additive measures. The date dimension can be shared with any other fact table as a conformed dimension.

When is a snowflake's extra join worth paying, and which design would you start with in BigQuery?

When a dimension is very large and storage matters more than speed, when another fact sits at the higher level, or when the higher level keeps its own history. Otherwise start with a star, because BigQuery performs best on denormalised data, and consider nested, repeated fields for rows always read with their parent.

The fact is partitioned by event_date. A query filters only on kind, and its second run is free. Is it cheap?

No. A filter on a column other than the partition column prunes nothing, so every partition is read. The free second run came from the cache, which serves identical queries over unchanged tables for about 24 hours; a dry run shows the real byte count.

Dana moves from the 49.00 plan to the 199.00 plan. Which SCD type suits dim_customer, and what would types 1 and 3 keep instead?

Type 2, because revenue reports must show the fee in force when each event happened: her old row is closed on the change date and a new current row is added. Type 1 would overwrite 49.00 and file October under 199.00. Type 3 would keep 49.00 in a previous-value column and lose anything older.

Why does the customer dimension's SQL say CREATE TABLE IF NOT EXISTS, and why is the date join < effective_to, not <=?

CREATE OR REPLACE would rebuild the table from staging on every run and wipe the closed versions. The end date is exclusive, so an event on the change day matches only the new version; with <= it would match both and count twice.
