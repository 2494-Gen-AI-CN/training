Big data

Big data and the five V's

Monday's page set up the cloud vocabulary: a region, a managed service and the Google Cloud services a data team reaches for. This page asks when data needs those services at all. The running example stays the ticket desk from week 3, seven MySQL tables that hold six tickets.

What makes data big

Google Cloud describes big data by three properties: volume, velocity and variety.1 Volume is the amount of data. Velocity is the speed at which it arrives and has to be processed. Variety is the mix of formats and sources it comes in.1

Two more V's are commonly added to make five.1 Veracity is how far the data can be trusted: whether it holds duplicates, gaps or values that cannot be true. Value is what the data is worth to the business that pays to collect and keep it.

None of the five is a size threshold. Each one is measured against what a team's storage and processing can handle, so the V's describe pressures on a system rather than a size.1

The five V's measured on the desk

The desk's six tickets were opened over three days in October, and a query in the MySQL client counts them per day. DATE() keeps only the date part of a DATETIME value.2

SELECT DATE(opened_at) AS day, COUNT(*) AS opened
FROM tickets
GROUP BY day
ORDER BY day;
+------------+--------+
| day        | opened |
+------------+--------+
| 2026-10-17 |      1 |
| 2026-10-18 |      3 |
| 2026-10-19 |      2 |
+------------+--------+

Two tickets a day is nothing for one machine. The next snippet sets the desk beside an invented SaaS company with ten thousand customers. It assumes each customer opens two tickets a month, each ticket writes three events, and each customer's twenty users click about five hundred times a day in the product.

SECONDS_PER_DAY = 24 * 60 * 60


def profile(name, events_per_day):
    per_second = events_per_day / SECONDS_PER_DAY
    print(name, events_per_day, "a day,", round(per_second, 4), "a second")

The SaaS company's ticket events still arrive only about once a minute. The volume and velocity pressure comes from the click log: a hundred million rows a day, more than a thousand a second.

How each V shapes a warehouse design

A data warehouse is a database built for analysis rather than for running an application, and it is Wednesday's subject. The five V's are the pressures its design answers, one design choice each.

  • Volume pushes toward storage that scales out by adding machines and costs little per byte.3 BigQuery stores table data by column, so a query reads only the columns it names.4 Large tables are also split by date, so a question about last week reads last week.
  • Velocity pushes toward a streaming path beside the nightly batch one. Dataflow, for example, runs pipelines in both modes.5
  • Variety pushes toward file formats that carry or tolerate different shapes, and BigQuery loads several of them.6
  • Veracity pushes toward cleansing before analysis,1 with a landing copy of the raw data kept so a bad clean can be run again.
  • Value comes first: a stated business question decides which data is worth collecting and paying for.1

What counts as big for one team

Interviewers often follow the five V's with "so how big is big?". A useful answer is that data becomes big for a team when one machine running an ordinary database stops coping. The disk fills, the nightly report runs past morning, or a new source will not fit the existing tables.

More machines make a slow query fast, so volume and velocity give way to money. Veracity does not: a duplicated row stays wrong on a thousand machines, and only cleansing rules and a data owner fix it.

Takeaways
  • The five V's are volume, velocity, variety, veracity and value.
  • The V's are pressures measured against what a team's systems can handle, not a size.
  • Each V pushes one design choice, from scale-out storage to a stated business question.
  • Veracity is the V that extra hardware cannot fix.
Say it in an interview

Big data is usually described by five V's: volume, velocity, variety, veracity and value. I treat them as pressures on a system rather than a size.

In a warehouse, volume pushes me toward columnar storage that scales out and is split by date, velocity toward a streaming path beside the batch load, variety toward formats that tolerate different shapes, veracity toward cleansing with the raw copy kept, and value means I start from the business question.

If the source moves from a nightly file to events every second, I'd add a streaming path, because the batch answer would always be a day old.

Components

The components of a big data system

The V's say why a system is under pressure. The components say what the system is made of. Google Cloud's architecture guide describes a data platform as a lifecycle of stages: ingest, store, process and analyse, then explore and visualise, with a Google Cloud service named for each.7 Courses and interviewers usually split that into five components.

Five stages from a ticket form to a chart

Picture the desk at the SaaS company's scale and follow its data from the ticket form to a manager's chart. Each component has one job.

  1. Ingestion gets data in from where it is produced. When a customer submits the form or an agent closes a ticket, that event has to leave the application and enter the data system.
  2. Storage keeps the data, raw and cheaply, so it can be read again later. Every ticket and event the desk ever produced sits here.
  3. Processing turns raw data into usable data. It removes duplicates, fixes types, joins tickets to customers and reshapes rows for the questions people ask.
  4. Analysis asks those questions, usually in SQL: how many high-priority tickets broke their SLA last month?
  5. Visualisation turns the answers into charts and dashboards, such as tickets opened per hour, which a manager reads without writing a query.

Ingestion takes two shapes. A batch arrives as files, for example a nightly export of the day's tickets. Events arrive one at a time as messages. The snippet below builds one ticket event as a message would carry it.

import json

event = {"ticket_id": 4, "kind": "assigned", "note": "was open, agent 1"}
message = json.dumps(event)
print(message)
{"ticket_id": 4, "kind": "assigned", "note": "was open, agent 1"}

json.dumps, from week 2, turns the dict into one line of text. That line is what the application would send each time an agent assigns a ticket, and whatever receives it turns it back into a dict with json.loads.

A Google Cloud service at each stage

Each component maps to a managed service on Google Cloud.7 The services below are the ones its architecture guide and product pages describe for these jobs.

ComponentGoogle Cloud serviceWhat it does there
IngestionPub/Suba publisher sends each message to a topic and subscribers receive it8
StorageCloud Storageholds objects, which are files, in buckets; the usual landing place for raw files9
ProcessingDataflowruns Apache Beam pipelines over batch or streaming data5

VisualisationLooker Studioreads BigQuery tables to draw charts and dashboards10

On sight, this is the architecture diagram in almost every data team's wiki: boxes labelled Pub/Sub, Cloud Storage, Dataflow, BigQuery and a dashboard tool, with arrows running left to right. Read it as the five components in order, and ask what each arrow carries: a message, a file, a table or a chart.

The trade-off is that each stage has its own service. A team can choose the best tool per stage, but it also owns the work of connecting them: permissions, formats and failure handling at every arrow.7 A single database that does everything is simpler and runs out of room sooner.

Swapping a file drop for a message queue changes the rhythm of everything downstream. With files, processing wakes up when a file lands, handles all of it and stops. With a queue, processing has to be running whenever a message might arrive and handles one event at a time. The next step names those two rhythms batch and streaming.

Who runs the stages: orchestration

Interviewers who hear the five components often ask who starts each one. Something has to start the nightly export, run processing once the file lands and refresh the dashboard after that, in that order, and retry when a stage fails. That job is orchestration.

The simplest orchestrator is a scheduled script that runs the stages one after another. Larger teams use a dedicated scheduler that knows which stage depends on which. Either way, name it when you draw the pipeline.

Takeaways
  • The five components are ingestion, storage, processing, analysis and visualisation.
  • On Google Cloud they map to Pub/Sub, Cloud Storage, Dataflow, BigQuery and Looker Studio.
  • Separate services give choice per stage and add the work of connecting them.
  • Orchestration starts each stage in order and on schedule.
Say it in an interview

A big data system has five components. Ingestion brings data in, as files or as a stream of messages. Storage keeps it raw and cheap. Processing cleans, joins and reshapes it. Analysis asks questions of it, usually in SQL. Visualisation turns the answers into dashboards people read.

On Google Cloud I'd draw that as Pub/Sub for events, Cloud Storage for raw files, Dataflow for processing, BigQuery for analysis and Looker Studio for the charts, with something like a scheduler starting each stage.

Architecture

Batch and streaming paths, and why they are distributed

The components can be wired together in two rhythms. A typical big data architecture runs both from the same source, side by side, and spreads the heavy stages across many machines. This step takes the desk's ticket_events table as the source.

The batch path

Batch processing handles a bounded set of data, collected over a period.11 Bounded means the input has an end: yesterday's events, last month's tickets. A batch job processes that input and then ends.11

On the desk, the batch path is a nightly extract. At two in the morning a job reads the day's rows from ticket_events, writes them to files, loads the files and computes the reports. The function below does the processing part on four events, which stand in for a night's worth.

events = [
    {"ticket_id": 1, "kind": "open"},
    {"ticket_id": 1, "kind": "closed"},
    {"ticket_id": 4, "kind": "open"},
    {"ticket_id": 4, "kind": "assigned"},
]


def batch_count(rows):
    counts = {}
    for row in rows:
        counts[row["kind"]] = counts.get(row["kind"], 0) + 1
    return counts


print("batch:", batch_count(events))
batch: {'open': 2, 'closed': 1, 'assigned': 1}

The function sees the whole list, returns one answer and is done. Nobody sees a count until the run finishes, and an event that arrives at 2:01 waits for the next night.

The streaming path

Stream processing handles an unbounded sequence of events as they arrive.11 Unbounded means there is no last event, so a streaming job keeps running.11 On the desk, each new event would be published to a Pub/Sub topic the moment the trigger writes it, and a streaming job would update the counts one event at a time.

running = {}
for event in events:
    running[event["kind"]] = running.get(event["kind"], 0) + 1
    print("stream:", running)
stream: {'open': 1}
stream: {'open': 1, 'closed': 1}
stream: {'open': 2, 'closed': 1}
stream: {'open': 2, 'closed': 1, 'assigned': 1}

Run after the batch snippet, the loop prints an answer after every event. A real streaming job never reaches the end of its list, because the list keeps growing.

Streaming gives fresh results at a higher cost and with more to get right. Events can arrive out of order, arrive late, or arrive twice when a sender retries. Batch is simpler and cheaper, and its answer is stale until the next run.11 On an architecture diagram the two paths show up as parallel arrows from one source:

  • batch: nightly extract, then files, then a batch job, then tables;
  • streaming: each event, then a topic, then a streaming job, then the same tables.

Why one machine stops being enough

When one database server is too small, the first idea is a bigger server. Scaling up like that hits a hardware ceiling: there is a largest machine you can buy. Scaling out adds ordinary machines to a cluster instead, the model HDFS, Hadoop's distributed file system, is built for.12

A distributed system splits two things across its machines.

  • Storage: the data is cut into blocks, and each block is copied to several machines, so a failed machine loses no data.12
  • Processing: a job is split into pieces of work that many workers run at once.5

The snippet deals the desk's six tickets to three workers by the remainder of the ticket id, the way a cluster deals work out by a key.

workers = {0: [], 1: [], 2: []}
for ticket_id in range(1, 7):
    workers[ticket_id % 3].append(ticket_id)
print(workers)

counts = []
for tickets in workers.values():
    counts.append(len(tickets))
print(counts, sum(counts))
{0: [3, 6], 1: [1, 4], 2: [2, 5]}
[2, 2, 2] 6

Each worker counts its own share, and adding the shares gives the same six a single machine would count. With three workers each handles a third of the rows, and a fourth worker can be added when the data grows.

Latency versus throughput

A common question is which of two numbers a design optimises. Latency is the time from an event to an answer that includes it. Throughput is how much data the system gets through per hour. A nightly batch has high throughput and high latency: it moves a whole day's rows at once, and the answer is up to a day old.

Batch is good enough whenever yesterday's answer serves the question, such as a monthly SLA report or a weekly count of tickets per agent. Streaming earns its cost when the answer must be fresh, such as an alert when a high-priority ticket has waited an hour with no agent.

Takeaways
  • A batch job reads a bounded input and ends; a streaming job reads an unbounded input and keeps running.
  • Streaming is fresher and costlier, with late, out-of-order and duplicate events to handle.
  • Distributed systems scale out by splitting data into copied blocks and work into parallel pieces.
  • A nightly batch optimises throughput; a streaming path optimises latency.
Say it in an interview

A typical architecture has two paths from the same sources. The batch path collects a bounded set, like a nightly extract, processes it and ends.

The streaming path publishes each event to a topic as it happens and a job that never stops processes it. Both land in the same analytical tables.

It's distributed because one machine has a ceiling. Scaling out splits the data into replicated blocks across machines, so losing one loses nothing, and splits the processing into pieces that many workers run in parallel.

Benefits

What big data is worth to an organisation

Everything so far costs money, so the next question is what an organisation gets back. Google Cloud groups the benefits of big data into three kinds: better decisions, new products and services, and more efficient operations.1 An interview answer needs one concrete example of each, and the desk supplies all three.

Better decisions

Better decisions come from analysing patterns across more records than a person could read.1 A desk manager decides how many agents to schedule for each hour of the day. Without data that is a guess; with a year of tickets it is a count. HOUR() returns the hour part of a time value.2

SELECT HOUR(opened_at) AS hour, COUNT(*) AS opened
FROM tickets
GROUP BY hour
ORDER BY hour;
+------+--------+
| hour | opened |
+------+--------+
|    8 |      2 |
|   12 |      3 |
|   18 |      1 |
+------+--------+

Six tickets prove nothing, but the shape of the answer carries over. Run over a year of the SaaS company's tickets, the same query says that noon needs more agents than six in the evening, and the schedule follows the numbers.

New products and services

New products and services can be built from data an organisation already collects about its customers.1 The desk already records when every ticket opened and closed, and its priority. From those rows it can offer customers a self-service status page: your ticket is assigned, and tickets of this priority usually close within a day.

Nothing new was collected to build that page: the product is the existing records, summarised and shown to the people they describe.

Operational efficiency

Operational efficiency comes from finding delays and waste in a process through the process's own records.1 Every desk ticket can carry tags such as billing or ui. If the events show that billing tickets wait hours in a shared queue before someone who understands invoices picks them up, routing by tag sends them straight to the billing agents.

A project pitch usually sets this out in three columns, and when you see "Today", "With data" and "Expected change" side by side, someone is arguing for a data project's benefit.

BenefitTodayWith dataExpected change
Better decisionthe same number of agents every houragents scheduled by tickets opened per hourshorter waits at the busy hours
New productcustomers email to ask about their ticketa self-service status pagefewer "any update?" emails

Return on investment

A benefit only counts against what it costs. BigQuery bills the bytes stored and the bytes each query scans, so data nobody ever analyses still costs storage every month.13 The next step covers the challenges that add to that cost.

To show a manager the value of a project, measure before and after. For the staffing change, record the average wait before a ticket's first assignment, hour by hour, for a month. Change the schedule, measure the next month the same way, and compare the two, since without the first month's numbers the benefit cannot be checked.

Takeaways
  • The three benefits are better decisions, new products and services, and operational efficiency.
  • Each benefit needs one concrete example, such as staffing by hour, a status page or routing by tag.
  • A benefit counts only against its cost, and stored data is billed even when nobody reads it.
  • Measuring a baseline before the change is what proves the benefit afterwards.
Say it in an interview

I'd name three benefits. Better decisions: a support desk counts tickets opened per hour and staffs to match instead of guessing.

New products: the same records power a self-service status page that tells customers how long tickets like theirs take. Operational efficiency: the event history shows billing tickets waiting in a shared queue, so we route them by tag.

To prove it, I'd measure the wait before the change and again after, because the benefit has to beat the storage and query costs.

Data quality and integration of sources

Real systems produce duplicates, misspellings and impossible dates.1 A retry writes the same event twice, a status arrives as closd, or a ticket is assigned an hour before it was opened. A report built on those rows is wrong without any error message, so data quality is checked, not assumed.

Integration is harder, because sources disagree on keys, types and time zones.1 Suppose the SaaS company's sales system also tracks support tickets. It calls ticket 4 TCK-0004, a string, and records times four hours ahead of the desk.

desk = {"ticket_id": 4, "opened_hour": 8}
crm = {"ref": "TCK-0004", "opened_hour": 12}

print(desk["ticket_id"] == crm["ref"])

crm_id = int(crm["ref"][4:])
crm_hour = crm["opened_hour"] - 4
print(desk["ticket_id"] == crm_id, desk["opened_hour"] == crm_hour)
False
True True

Compared as they arrive, the two records do not match at all. Only after slicing off the prefix, converting to an integer and shifting the hour do they turn out to be one ticket. Every new source brings its own version of this, and someone has to write the rule down.

Storage and processing cost

Cloud storage looks cheap per byte, but it is billed every month, and BigQuery also bills the bytes each query scans.13 Keeping everything "in case" raises the storage bill and the privacy exposure together.13 A query that reads every column of a large table every hour costs far more than one that reads the two columns it needs.

Privacy and governance

An email address is personal data, and privacy law applies to it. In Canada, PIPEDA sets rules for collecting, using and keeping personal information.14 The desk's customers.email column is personal data, and so is agents.email.

Location is part of privacy too. A BigQuery dataset's location decides where its data is stored, and it is fixed when the dataset is created.15 A company that promised to keep Canadian customers' data in Canada has to pick that location before the first table exists.

Governance is the idea interviewers pair with privacy: who owns each dataset, who may see it and who must delete it, written down. You spot its absence on sight: a column named email or phone with no note about who may read it or how long it is kept.

Skills

The last challenge is people. Running the pipeline from the earlier steps takes skills a small team may not have:

  • distributed processing;
  • streaming;
  • SQL over very large tables;
  • cost control;
  • privacy rules.

A desk team fluent in MySQL and Python still has to learn the new services, and hiring data engineers costs money and time.

Takeaways
  • The five challenges are quality, integration, cost, privacy and governance, and skills.
  • Integration is hard because sources disagree on keys, types and time zones.
  • Storage and scanned bytes are both billed, so keeping everything costs money and privacy.
  • Customer emails are personal data, and a dataset's location is fixed at creation.
Say it in an interview

The usual five are data quality, integration, cost, privacy and governance, and skills. Quality means duplicates and impossible dates. Integration means two systems that name the same ticket differently and record time in different zones.

Cost means paying for storage and for every byte a query scans.

On a support desk the customers' email column is personal data, so in Canada PIPEDA applies: we decide who can see it, where it's stored and when it's deleted. And the team needs people who can run all of this.

Lifecycle

The data lifecycle: one ticket from form to deletion

The components describe the machinery. The data lifecycle describes the life of the data itself, from the moment it exists to the moment it is gone. Sources count the stages differently: Google's architecture guide uses four (ingest, store, process and analyse, explore and visualise), and this course uses eight.7 The eight add the stages that matter for privacy and cost: sharing, archival and deletion.

Eight stages in order

Data is generated by applications, devices and people, and then collected into storage.7 From there it moves through the remaining six stages in order.

  1. Generation: an event happens and produces data, such as a customer submitting a form.
  2. Collection: the data is captured and brought into a system, the ingestion component's job.
  3. Storage: the data is kept. A relational database stores collected records as rows in tables.2
  4. Processing: the data is cleaned, joined and reshaped for the questions people ask.
  5. Analysis: queries and reports turn the processed data into answers.
  6. Sharing: the answers, or the data, go to people and systems outside the team that produced them.
  7. Archival: data that is rarely read moves somewhere cheaper but is still kept. Cold data can move to cheaper storage classes.16
  8. Deletion: the data is destroyed once nobody may or should keep it.

A common slip in interviews is listing the stages out of order or dropping sharing and archival. Deletion always comes last, and it follows a retention period rather than happening the moment data stops being useful.

Following ticket 1 through the stages

The clearest way to learn the stages is to follow one record through all eight. Here is ticket 1 as the desk stores it today.

SELECT ticket_id, title, status, opened_at, closed_at

Retention policy: when archival becomes deletion

A retention policy is a rule stating how long data is kept. It decides when archival turns into deletion. Data is archived rather than deleted at once because someone may still need it: a customer disputes an old ticket, or an auditor asks for last year's response times. Archival keeps it at a lower price until that need has passed.

Suppose the desk's policy archives a ticket 90 days after it closes and deletes it two years after it closes. The snippet adds each period to ticket 1's closing time.

from datetime import datetime, timedelta

closed_at = datetime(2026, 10, 18, 11, 0)
archive_after = timedelta(days=90)
delete_after = timedelta(days=730)

print("closed  ", closed_at)
print("archive ", closed_at + archive_after)
print("delete  ", closed_at + delete_after)
closed   2026-10-18 11:00:00
archive  2027-01-16 11:00:00
delete   2028-10-17 11:00:00

The policy turns into dates a machine can act on, which is how deletion is triggered in practice. Cloud Storage can delete objects automatically through bucket lifecycle rules,17 and a BigQuery table can carry an expiration time after which it is removed.18 When you see a table expiration setting, or a bucket rule that deletes objects after a number of days, you are looking at a retention policy written as configuration.

Takeaways
  • The eight stages are generation, collection, storage, processing, analysis, sharing, archival and deletion.
  • Different sources count different stages; Google's guide uses four.
  • Archival keeps rarely read data at a lower price until the retention period ends.
  • A retention policy becomes dates, and expiration settings or lifecycle rules act on them.
Say it in an interview

I'd list eight stages: generation, collection, storage, processing, analysis, sharing, archival and deletion.

For a support ticket that's the form, the insert, the database row, the nightly extract and cleaning, the SLA report, the report going to a manager, the row moving to cheap storage after a few months, and deletion when the retention period ends.

We archive instead of deleting straight away because disputes and audits still need old records. Deletion is triggered by the retention policy, usually as an expiration or lifecycle rule.

Types of data

Structured, semi-structured and unstructured data

Variety, the third V, is easier to discuss with three labels for how much shape data carries. The desk holds all three kinds once its attachments and emails are counted, and each kind is stored and queried in its own way.

TypeDesk exampleUsually stored inQueried by
Structuredthe seven MySQL tablesa relational database tableSQL over named columns
Semi-structuredweek 2's tickets.json, events with notes as JSONfiles, or JSON columns in a tablereading keys, with a plan for missing ones
Unstructureda screenshot attached to a ticket, the body of a customer's emailobject storage such as Cloud Storageextracting structure or metadata first

Structured data

Structured data fits a fixed schema of rows and columns, the shape of a SQL table.1 Every row of tickets has the same eight columns, each with a declared type, and the database rejects a row that does not fit. That is why SQL can query it directly: the column names and types are known before anyone asks.2

Semi-structured data

Semi-structured data carries its own structure through keys or tags, as JSON and XML do.1 Each JSON object names its fields, but nothing forces two objects to name the same ones. JSON looks tidy, which tempts people to call it structured; it is semi-structured because each object may carry different keys.

import json

text = '[{"id": 4, "tags": ["billing", "ui"], "note": null}, {"id": 5, "note": "rows missing"}]'
tickets = json.loads(text)

for ticket in tickets:
    print(ticket["id"], ticket.get("tags", []), ticket["note"])
4 ['billing', 'ui'] None
5 [] rows missing

Ticket 5 has no tags key at all. Reading it with ticket["tags"] would stop with a KeyError, so the loop uses get with an empty list as the default. Two objects side by side, one with a key and one without, are how you recognise semi-structured data on sight.

Semi-structured data is flexible to write, because a sender can add a field without asking anyone, but it is costly to query reliably, because fields may be missing or change type from one record to the next.19

Unstructured data

Unstructured data has no predefined model: images, free text, audio.1 A screenshot of the frozen checkout button has pixels, not columns. Images and email bodies are stored as objects, such as files in a Cloud Storage bucket.9

To query unstructured data, structure or metadata is extracted from it first.1 The screenshot's file name, size and ticket id go into a table row that points at the object, and the email's sender and date are pulled out of its header. So the answer to "where would a screenshot attached to a ticket be stored?" is in object storage, with a structured row describing it.

Nested and repeated fields

The first question once JSON meets a table is what happens to a list inside one object, such as ticket 4's two tags. One answer is to flatten it into extra rows, one per tag, the way the desk's ticket_tags table does.

for ticket in tickets:
    for tag in ticket.get("tags", []):
        print("row:", ticket["id"], tag)
row: 4 billing
row: 4 ui

The other answer is to keep the list inside the row. BigQuery can load and query JSON with nested and repeated fields, so semi-structured data can be queried without flattening first.19 A nested object loads as a RECORD column and a list as a REPEATED column.19 Flattening suits a relational database; nesting keeps one row per ticket.

Takeaways
  • Structured data has a fixed schema of rows and columns and is queried with SQL.
  • JSON and XML are semi-structured: each record names its own fields, and some may be missing.
  • Unstructured data such as screenshots is stored as objects and queried through extracted metadata.
  • A list inside a JSON object is either flattened into rows or kept as a repeated column.
Say it in an interview

Structured data has a fixed schema, like a SQL table, and I query it with SQL. Semi-structured data, like JSON or XML, carries its own keys, so records can differ; I store it as files or JSON columns and query it knowing fields may be missing.

Unstructured data, like screenshots or email bodies, has no model; it goes in object storage and I query metadata extracted from it.

JSON isn't structured, even when it looks tidy, because nothing stops the next object having different keys.

File formats

File formats compared and chosen

A file's format decides its size, whether types survive and how fast it reads. BigQuery loads CSV, JSON lines, Avro, Parquet and ORC, and the format chosen changes how the table's schema is obtained.6 XML is the sixth format interviewers name.

Text formats: CSV, JSON, JSON lines and XML

CSV is a plain-text row format with no embedded types, so a loader has to detect or be told each column's type.20 Here are the six tickets, four columns of each:

ticket_id,title,priority,status
1,Login page returns 500,high,closed
2,Invoice PDF is blank,normal,closed
3,Typo on pricing page,normal,closed
4,Checkout button frozen,high,assigned
5,Export is missing rows,normal,assigned
6,Add dark mode,low,open

The header names the columns once, and nothing says ticket_id is a number. A title containing a comma would need quoting. CSV is readable, opens in any spreadsheet and is large for what it holds.20

JSON lines, also called newline-delimited JSON, holds one complete JSON object per line, so a file can be split and read a line at a time.19 Its objects may hold nested fields.19

{"ticket_id": 1, "title": "Login page returns 500", "priority": "high", "status": "closed"}
{"ticket_id": 2, "title": "Invoice PDF is blank", "priority": "normal", "status": "closed"}
{"ticket_id": 3, "title": "Typo on pricing page", "priority": "normal", "status": "closed"}
{"ticket_id": 4, "title": "Checkout button frozen", "priority": "high", "status": "assigned"}
{"ticket_id": 5, "title": "Export is missing rows", "priority": "normal", "status": "assigned"}
{"ticket_id": 6, "title": "Add dark mode", "priority": "low", "status": "open"}

Plain JSON wraps all six objects in one array, so a reader must take in the whole document first. Both repeat every key in every record.

XML is semi-structured like JSON, and names every field with an opening and a closing tag.1 Two tickets show its shape:

<tickets>
  <ticket>
    <ticket_id>1</ticket_id>
    <title>Login page returns 500</title>
    <priority>high</priority>
    <status>closed</status>
  </ticket>
  <ticket>
    <ticket_id>2</ticket_id>
    <title>Invoice PDF is blank</title>
    <priority>normal</priority>
    <status>closed</status>
  </ticket>
</tickets>

Every field name appears twice per record, so XML is the most verbose of the four, and its tags carry no types. The snippet below measures what repeated keys cost.

import json

tickets = [
    {"ticket_id": 1, "title": "Login page returns 500", "priority": "high", "status": "closed"},

JSON takes more than twice the characters of CSV for the same data. At six rows that is nothing; at a hundred million rows a day it is the storage bill.

Columnar and binary formats: Parquet, ORC and Avro

All four text formats store rows. A columnar format stores each column's values together, as the snippet shows.

by_row = [
    {"ticket_id": 1, "priority": "high", "status": "closed"},
    {"ticket_id": 2, "priority": "normal", "status": "closed"},
    {"ticket_id": 3, "priority": "normal", "status": "closed"},
    {"ticket_id": 4, "priority": "high", "status": "assigned"},
    {"ticket_id": 5, "priority": "normal", "status": "assigned"},
    {"ticket_id": 6, "priority": "low", "status": "open"},
]

by_column = {"ticket_id": [], "priority": [], "status": []}
for row in by_row:
    for name in by_column:
        by_column[name].append(row[name])

print(by_column["priority"])
print(by_column["priority"].count("high"))
['high', 'normal', 'normal', 'high', 'normal', 'low']
2

Counting high-priority tickets now reads one list and never touches the statuses. A column also holds values of one type that often repeat, which compresses well.

  • Parquet is a columnar format with per-column compression and an embedded schema, suited to analytical reads.21
  • ORC is a columnar format with built-in indexes and compression, from the Hadoop ecosystem.22
  • Avro is row-based, and its schema, written in JSON, travels in the file header. It supports schema evolution, so a field can be added without breaking older files.23

Columnar files read fast for a few columns, but they are slower to write and awkward to append to one row at a time, and row formats suit streaming writes.21 So Avro is favoured for streams and Parquet for analysts' tables. Parquet files can also be split into pieces that many workers read at once, and they compress with a choice of compression method (a codec), which is another reason analytics prefers them to plain text.

Choosing a format for a workload

A choice starts from the workload. Four common ones:

  • A nightly extract of the desk's small tables: CSV for flat tables, JSON lines for events whose notes contain commas, with the types given to the loader.
  • A large nightly extract for analysts who read a few columns at a time: Parquet, because it is columnar, typed and compressed per column.
  • A stream of events whose fields change over time: Avro, which writes a row at a time and lets its schema evolve.
  • A list a manager will open in a spreadsheet: CSV.
Takeaways
  • CSV, JSON, JSON lines and XML are text row formats; only JSON lines reads a line at a time.
  • Parquet and ORC are columnar and compressed; Avro is row-based with its schema in the header.
  • Columnar files read a few columns fast but are slow to append to row by row.
  • Choose by workload: analytics points to Parquet, streams to Avro, simple exchange to CSV.
Say it in an interview

CSV, JSON and XML are text row formats. CSV has no types, JSON and XML repeat field names, and JSON lines can be read a line at a time.

Parquet is columnar, typed and compressed per column; ORC is columnar with built-in indexes and compression and, like Parquet, carries its typed schema in the file. Both suit analytics. Avro is row-based with its schema in the file header and supports schema evolution, which suits streams.

For a nightly analytical extract I'd pick Parquet. Columnar hurts when you append one row at a time or look up single rows, so for a stream I'd pick Avro.

Check yourself

Check yourself

Answer each question out loud, as you would in an interview, before you open it.

Is the six-ticket desk big data? Which V's would rise first if it served a SaaS company with ten thousand customers?

No. The V's are pressures measured against what a team's systems can handle, and one MySQL server copes easily with the desk. At the SaaS company, velocity and variety rise first: a click log arriving a thousand times a second, and emails, chats and screenshots beside the tables.

Name the five components of a big data system, the job of each, and a Google Cloud service for each.

Ingestion brings data in (Pub/Sub for events), storage keeps it raw (Cloud Storage), processing cleans and reshapes it (Dataflow), analysis queries it in SQL (BigQuery), and visualisation draws the answers (Looker Studio). Something like a scheduler starts each stage in order.

What separates a batch path from a streaming path, and why are big data systems distributed?

A batch job reads a bounded input, such as last night's events, and ends; a streaming job reads an unbounded input as each event arrives and keeps running, fresher but costlier. Systems are distributed because one machine has a ceiling: scaling out splits data into replicated blocks and work into pieces that many workers run at once.

Give one example of each benefit of big data for a support desk.

Better decisions: staffing agents by the hour tickets are opened. A new product: a self-service status page built from open and close times. Operational efficiency: routing tickets by tag once the events show billing tickets waiting in a shared queue.

List the five challenges of big data. Which desk column is personal data, and what follows?

Data quality, integration of sources, storage and processing cost, privacy and governance, and skills. The email column of customers (and of agents) is personal data, so privacy law such as PIPEDA applies: decide who may see it, where it is stored and when it is deleted.

List the eight lifecycle stages in order. Why is a closed ticket archived rather than deleted at once?

Generation, collection, storage, processing, analysis, sharing, archival, deletion. Archival keeps rarely read data at a lower price because disputes and audits may still need it; deletion follows when the retention period ends.

Is JSON structured data? Where would a screenshot attached to a ticket be stored, and how would you query it?

JSON is semi-structured: each object names its own keys, and the next object may have different ones. The screenshot is unstructured, so it goes in object storage such as a Cloud Storage bucket, and you query a table row of metadata (file name, ticket id) that points at it.

Which file format would you choose for a large nightly analytical extract, and when does columnar hurt?

Parquet: columnar, typed and compressed per column, so analysts read only the columns they need. Columnar hurts when you append one row at a time or write a stream, where a row format such as Avro, with its schema in the header, fits better.
