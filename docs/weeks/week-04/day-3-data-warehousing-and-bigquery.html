Warehousing

What a data warehouse is, and OLTP against OLAP

The ticket desk's MySQL database is good at the job it was built for: opening, assigning and closing tickets one at a time. This step explains why teams copy that data somewhere else before they analyse it.

Why not report straight from production

A data warehouse is a store of historical data built for analysis. It is fed from the operational systems a business runs on, and it integrates data from several of them into one consistent model.1 A company with a ticket desk, a billing system and a sales system has three databases with three ideas of what a "customer" is. The warehouse is where they agree.

The other reason is load. Analytical queries run against the transactional database compete with the writes it exists to serve.2 A report that scans every ticket from the last quarter holds resources that an agent closing a ticket needs at the same moment. Copying the data to a second system lets each one do one job well.

Textbooks describe a warehouse with four words, and interviewers like to hear them:

  • subject-oriented: organised around business subjects such as tickets and customers, not around one application's screens
  • integrated: one consistent model built from several sources
  • time-variant: every row belongs to a point in time, so you can ask how things looked last month
  • non-volatile: data is mostly appended, not updated in place, so history is kept1

The limit is freshness. A warehouse holds a copy that is only as current as its last load, so it is the wrong place to ask "what is ticket 4's status right now".1 You recognise the pattern in a codebase as a nightly job that copies tables into a separate database, with a dashboard that reads the copy and never production. That dashboard, and the business intelligence reports beside it, are the consumers a warehouse exists to serve.

OLTP and OLAP compared

OLTP stands for online transaction processing and OLAP for online analytical processing. OLTP systems run many short read and write transactions on current data. OLAP systems run fewer, larger, read-mostly queries that scan and aggregate history.2 The desk's two kinds of question show the difference.

-- OLTP: one ticket, found by its key
SELECT status
FROM tickets
WHERE ticket_id = 4;
+----------+
| status   |
+----------+
| assigned |
+----------+
-- OLAP: every ticket, grouped and counted
SELECT priority, COUNT(*) AS tickets
FROM tickets
GROUP BY priority
ORDER BY priority;
+----------+---------+
| priority | tickets |
+----------+---------+
| high     |       2 |
| low      |       1 |
| normal   |       3 |
+----------+---------+

Both run on the desk's six tickets in an instant. The first stays fast with a million tickets, because the primary key leads straight to one row. The second has to read every row it groups, so its cost grows with the history. That is the OLAP shape: GROUP BY priority over a quarter of rows, where OLTP is WHERE ticket_id = 4.

AspectOLTP (the desk's MySQL)OLAP (a warehouse such as BigQuery)
Workloadmany small reads and writesfew large reads, loads in batches
Query shapeone row by its keyscans and aggregates many rows
Schemanormalised, each fact stored oncedenormalised for fewer joins
Usersmany concurrent application usersanalysts and BI tools
Freshnesscurrent to the last commithistorical, as of the last load

The rows follow the AWS comparison of OLTP and OLAP.3 BigQuery is an OLAP system and is not built for high-rate single-row updates.2 One system cannot be tuned for both workloads at once, which is why teams copy data into a second store.2

Row storage and column storage

The follow-up question is usually about storage. A row store such as MySQL keeps each row's columns together on disk, which suits fetching or changing one whole record. A column store keeps each column's values together, which suits scanning a few columns across millions of rows. BigQuery stores table data in a columnar format called Capacitor, so a query reads only the columns it names.4 The grouping query above would read the priority column and nothing else.

Takeaways
  • A warehouse is an integrated, historical copy of operational data, built for analysis.
  • OLTP serves many small current transactions; OLAP serves few large scans of history.
  • A warehouse is only as fresh as its last load.
  • Column stores read only the columns a query names.
Say it in an interview

OLTP is the transactional side: lots of small reads and writes on current data, a normalised schema, and many application users at once, like a ticket desk updating one ticket. OLAP is the analytical side: fewer, bigger queries that scan and aggregate history for analysts and dashboards, usually on a denormalised schema.

I wouldn't report straight from production because those big scans compete with the writes the application needs. A warehouse integrates the sources into one model and keeps history, and the trade-off is that it's only as fresh as its last load.

Architecture

Warehouse architecture, data lakes, the ODS and data marts

This step draws the warehouse pipeline left to right, then places a lake, an ODS and marts beside it.

The layers from source to consumer

The typical flow has six parts.1

  1. Sources: the operational databases and files, such as the desk's MySQL tables.
  2. Extract: a job that reads each source and writes what it read somewhere the warehouse can reach.
  3. Staging: the extracts held as they arrived, before cleansing and conforming.
  4. The warehouse: cleansed, integrated, modelled tables that keep history.
  5. Data marts: subject-focused slices of the warehouse for one team.
  6. Consumers: BI dashboards, reports and machine-learning jobs.

Across every layer, metadata in a data catalogue records what each table means. Staging keeps the raw extract apart from the modelled tables. If a cleansing rule turns out to be wrong, the staged rows are still there to rebuild from, and nobody has to extract from production again.1

Each added layer adds latency and something to maintain. Small teams therefore collapse staging, warehouse and marts into separate datasets inside one system.1 In BigQuery the dataset is the unit that groups and secures tables,5 so you will often see one project holding datasets named raw, staging, dw and mart_support. The desk follows that pattern with two datasets: desk_raw for the staged extracts and desk_dw for the modelled warehouse.

Data warehouse against data lake

A data lake keeps raw data in its original format and applies a schema only when the data is read. A warehouse applies a schema when the data is loaded.6

AspectData lakeData warehouse
What it holdsstructured, semi-structured and unstructured filesstructured, modelled tables
Schemaapplied on readapplied on write
Strengthcheap, flexible, keeps everythingreliable, fast to query, consistent
Cost of the strengthwithout governance it becomes unusableneeds modelling before the load

The table's rows come from Google's comparison of the two.6 A lake that nobody catalogues or cleans is called a data swamp. You recognise a lake as a storage bucket full of CSV, JSON and Parquet files with no table definitions, and a warehouse as typed tables you query by name.

The desk's raw staging dataset plays a small lake's role beside the modelled warehouse dataset.5 A lakehouse, a name worth knowing, adds warehouse features on top of lake storage.

Operational data store

An operational data store, or ODS, sits between the operational sources and the warehouse. It gives a near-real-time view of current operations for day-to-day reporting, and it can feed the warehouse.7 It is often fed by replicating each change from the source.

The difference from a warehouse is history. An ODS holds current operational data, while a warehouse or mart holds historical data for analysis.7 So the ODS can answer "which high-priority tickets are open across all our products right now" without touching production, and it cannot answer "how has time to close changed since last year".

Data marts: dependent, independent and hybrid

A data mart is a subject-focused subset of data for one business unit, narrower than the enterprise-wide warehouse.7 The desk's support managers might get a mart_support dataset holding only tickets, agents and response times.

  • A dependent mart is filled from a subset of the central warehouse, and fails if the warehouse fails.
  • An independent mart reads its own sources with no warehouse behind it.
  • A hybrid mart reads from both.7

Dependent marts keep numbers consistent, because every team's "average hours to close" comes from the same warehouse table, but they wait on the warehouse. Independent marts are quick to set up and harder to manage, and they drift into separate definitions of the same metric.7 Choose dependent when a warehouse exists and consistency matters, and independent when one team needs answers before any warehouse is built.

A mart is also an access-control tool. A BigQuery dataset can be shared read-only, so one team sees only its mart.8

Takeaways
  • Data flows from sources through extract and staging into the warehouse, then marts, then consumers.
  • A lake applies its schema on read; a warehouse applies it on write.
  • An ODS is fresh and shallow; a warehouse is historical and staler.
  • Dependent marts read the warehouse; independent marts read their own sources.
Say it in an interview

A lake stores raw files in any format and applies a schema when someone reads them, so it's cheap and flexible but turns into a swamp without governance. A warehouse stores modelled, typed tables and applies the schema on load, so it's reliable and fast to query but needs the modelling first.

The layers go sources, extract, staging, warehouse, marts, consumers. Staging holds the extract as it arrived, a job cleanses it into the warehouse, and marts give one team its slice. An ODS sits beside that as a near-real-time integrated copy for day-to-day reports, without the history.

A data mart is a subject-focused subset for one team. A dependent mart is built from the warehouse, so its numbers match everyone else's; an independent mart reads sources directly, which is quick to set up but drifts into its own definitions. I'd pick dependent when a warehouse exists and consistency matters, and independent when one team needs answers before there is a warehouse.

Scalability, cost and maintenance

Cloud data warehouses scale storage and compute on demand, bill by use, and are maintained by the provider. On-premises warehouses need hardware bought up front, sized for peak load and maintained by the owner.1

ConcernOn-premisesCloud
Scalabilityfixed capacity; growing means buying more machineselastic; capacity grows and shrinks with demand
Costcapital cost up front, paid whether or not it is usedpay-per-use; a careless query costs money
Maintenanceyour team patches, backs up and upgradesthe vendor patches, backs up and upgrades
Other concernsdata never leaves your buildingegress charges and lock-in to one vendor

The comparison follows Google's warehouse overview.1 Neither side wins outright. A company with steady load, its own data centre and strict rules about where data lives can reasonably stay on-premises. A team that wants to start this week with no hardware chooses the cloud.

Managed, self-hosted and serverless

Underneath the vendor names sits one decision: who patches, scales and backs up the system. Self-hosted means your team does. Managed means the vendor does it while you still choose a size, such as a number of nodes in a cluster.

Serverless goes one step further. BigQuery has no cluster to size, provision or patch,2 so the first thing you do with it is create a dataset, not a machine. The trade-off of serverless is control: you cannot tune the hardware, and the bill follows what your queries read.

Takeaways
  • Teradata, Oracle and SQL Server are on-premises names; BigQuery, Snowflake, Redshift and Synapse are cloud ones.
  • On-premises means capital cost, fixed capacity and your own maintenance.
  • Cloud means pay-per-use, elastic capacity, vendor maintenance, and egress and lock-in concerns.
  • Serverless means no cluster to size or patch at all.
Say it in an interview

Cloud warehouses like BigQuery, Snowflake and Redshift scale on demand, bill by use and are maintained by the provider. On-premises ones like Teradata or SQL Server need hardware bought up front for peak load, and my own team patches and backs them up. The cloud's catches are egress costs and lock-in; on-premises keeps the data in the building.

Serverless, for BigQuery, means there's no cluster at all. I create datasets and run queries, and I'm billed for what the queries read and what I store.

Data quality

Data quality problems and cleansing

If the same event is counted twice, every report built on it is wrong, so the pipeline checks rows before they reach the modelled tables.

The common problems

Data quality problems fall into a handful of kinds, and each has a standard fix.15

ProblemExample on the deskCleansing step
Missing valuesa customer row with no countryfill with a stated default, or reject the row
Duplicatesthe same assigned event recorded twicededuplicate on a business key
Invalid valuesan event whose kind is closdvalidate against the allowed values
Inconsistent formatsdates written two different waysstandardise to one format
Inconsistent timestampsan event dated before its ticket openedcheck the order against the parent row

Cleansing happens after the extract and before the load into the modelled layer.1 Staging keeps the rows as they arrived, and the cleansing step decides what goes on into the warehouse. A business key is the set of columns that identify one real-world thing. For a ticket event it is the ticket, the kind and the time, not the auto-increment event_id, which differs between two copies of the same event.

Profiling before deciding

Before writing any rule, look at the data. Profiling means counting nulls, distinct values and ranges per column. A one-line profile of the desk's event kinds, run against MySQL, already shows a problem:

SELECT kind, COUNT(*) AS events
FROM ticket_events
GROUP BY kind
ORDER BY kind;
+----------+--------+
| kind     | events |
+----------+--------+
| assigned |      4 |
| closd    |      1 |
| closed   |      3 |
| open     |      6 |
+----------+--------+

The desk's history has 14 events, and the trigger from week 3 only ever writes open, assigned or closed. A fourth spelling is a typo that arrived from somewhere other than the trigger.

Finding bad rows with queries

Each problem has a finding query. These list the bad rows and change nothing; removing or rejecting them is a separate, later step.

-- invalid values: a kind outside the allowed list
SELECT event_id, ticket_id, kind
FROM ticket_events
WHERE kind NOT IN ('open', 'assigned', 'closed');
+----------+-----------+-------+
| event_id | ticket_id | kind  |
+----------+-----------+-------+
|        8 |         2 | closd |
+----------+-----------+-------+
-- duplicates: the same business key more than once
SELECT ticket_id, kind, created_at, COUNT(*) AS copies
FROM ticket_events
GROUP BY ticket_id, kind, created_at
HAVING COUNT(*) > 1;
+-----------+----------+---------------------+--------+
| ticket_id | kind     | created_at          | copies |
+-----------+----------+---------------------+--------+
|         4 | assigned | 2026-10-19 09:00:00 |      2 |
+-----------+----------+---------------------+--------+
-- inconsistent timestamps: an event before its ticket opened
SELECT e.event_id, e.ticket_id, e.created_at, t.opened_at
FROM ticket_events AS e
JOIN tickets AS t ON t.ticket_id = e.ticket_id
WHERE e.created_at < t.opened_at;
+----------+-----------+---------------------+---------------------+
| event_id | ticket_id | created_at          | opened_at           |
+----------+-----------+---------------------+---------------------+
|       13 |         6 | 2026-10-19 11:00:00 | 2026-10-19 12:00:00 |
+----------+-----------+---------------------+---------------------+

Each of the three queries finds one bad row. The duplicate query reports the key and a count rather than which copy is extra; step 7 shows a window function that names the extra copy by its event_id.

Who decides what a valid row is

Engineers write the rules, but the business owns them. Whether an event an hour before its ticket opened is a clock problem or a real data error is a question for the people who run the desk. Teams write the agreed rules down so a reviewer can check the code against them.

Cleansing silently can hide a bug in the source, and dropping rows without a record loses evidence.15 A good pipeline keeps the rejected rows with a reason, so the count of bad rows becomes a number someone watches.

Takeaways
  • The common problems are missing values, duplicates, invalid values and inconsistent formats or timestamps.
  • Cleansing runs after the extract and before the load into the modelled layer.
  • Profile the columns first, then write finding queries against agreed rules.
  • Keep rejected rows with a reason instead of dropping them silently.
Say it in an interview

The usual data quality problems are missing values, duplicates, invalid values and inconsistent formats. The fixes are to fill or reject the nulls, deduplicate on a business key, validate against the allowed values, and standardise the formats. I'd also check timestamps against their parent rows, like an event before its ticket opened.

Cleansing happens after the extract, between staging and the warehouse, so the raw rows are still there if a rule is wrong. The business decides what a valid row is, and I'd keep rejected rows with a reason rather than drop them silently.

Extract

Extracting a transactional database into files

The first move of any warehouse pipeline is reading the source. The desk thread does it in Python: read each MySQL table and write it to a file that BigQuery can load.

Why the extract lands as files

An extract could write straight into the warehouse, and many tools do. Writing files first has three advantages for a team learning the pattern:

  • The extract and the load are separate steps, so a failed load does not mean reading production again.
  • The files are something you can open and read, which makes the first debugging session short.
  • The extract needs no cloud credentials at all; only the load does.

The extract also changes nothing. The desk's three bad events from step 4 go out exactly as MySQL holds them, because staging is meant to hold rows as they arrived.1 A full extract reads every row each time. Friday's page covers reading only what changed since the last run.

Order matters when tables refer to each other. Extracting parents before children (priorities, customers and agents before tickets, tickets before events) means a reader of the files never meets a ticket whose customer has not been written yet. The extract folder holds real customer data, so it goes in .gitignore and never reaches a public repository.

CSV for flat rows, JSON lines for text

BigQuery's CSV loader can skip a header row with --skip_leading_rows, and its --source_format flag names either CSV or NEWLINE_DELIMITED_JSON.16 Newline-delimited JSON, often called JSON lines, is one complete JSON object per line. The desk uses CSV for the four flat tables and JSON lines for the events, whose notes such as was open, agent none contain commas.

This example builds two rows by hand, shaped like what the MySQL connector returns, and writes them the way the extract does. It uses the csv module's DictWriter for the table rows and week 2's json.dumps for the event. The sys module's sys.stdout is the screen, so DictWriter writes there instead of to a file and you can see every character.

import csv
import json
import sys
from datetime import datetime

rows = [
    {"ticket_id": 1, "priority": "high", "opened_at": datetime(2026, 10, 18, 8, 0),
     "closed_at": datetime(2026, 10, 18, 11, 0)},
    {"ticket_id": 4, "priority": "high", "opened_at": datetime(2026, 10, 19, 8, 0),
     "closed_at": None},
]
writer = csv.DictWriter(sys.stdout, fieldnames=list(rows[0]))
writer.writeheader()
writer.writerows(rows)
event = {"event_id": 8, "ticket_id": 2, "kind": "closd", "note": "was open, agent none",
         "created_at": datetime(2026, 10, 18, 18, 0)}
print(json.dumps(event, default=str))
ticket_id,priority,opened_at,closed_at
1,high,2026-10-18 08:00:00,2026-10-18 11:00:00
4,high,2026-10-19 08:00:00,
{"event_id": 8, "ticket_id": 2, "kind": "closd", "note": "was open, agent none", "created_at": "2026-10-18 18:00:00"}

Read the output for the conventions the load will rely on. The header row carries the MySQL column names. The missing closed_at of the open ticket is an empty field. Dates come out as YYYY-MM-DD HH:MM:SS, which is how a DATETIME column reads them. In the JSON line, default=str turns the datetime into the same text, since JSON has no date type, and the commas in the note need no quoting.

A real extract writes the same lines to one file per table instead of to the screen. A money column such as a customer's monthly fee should come out as 49.00, with both decimal places, so nothing is rounded on the way.

What the loader will make of the files

A file carries text, not types. When BigQuery loads a file with autodetect, it guesses each column's type from a sample of the file and can guess wrongly; a custom schema fixes the types.17 So the extract keeps one consistent format per type, and step 6 loads every staging table with a schema written out by hand.

You recognise an extract in someone else's repository as a script with a list of table names, a loop that reads each one, and an exports/ or landing/ folder that is ignored by Git.

Takeaways
  • Writing the extract to files keeps extracting and loading as separate, rerunnable steps.
  • The extract copies rows as they are; bad rows go to staging untouched.
  • CSV suits flat tables; JSON lines suits text full of commas.
  • One consistent format per type helps the loader, but only a schema fixes the types.
Say it in an interview

The extract reads each source table and lands it somewhere the warehouse can load from, usually files or a staging area. I keep it dumb on purpose: it copies rows as they are, parents before children, and leaves cleansing to a later step, so the raw data is always there to rebuild from.

For formats I'd use CSV with a header for flat tables and newline-delimited JSON when a column holds free text with commas. Either way I load with an explicit schema instead of trusting type detection.

BigQuery

BigQuery: architecture, datasets, tables and loads

How BigQuery runs a query

BigQuery separates storage from compute. Each scales on its own, with no cluster to size.2 Tables sit in the columnar Capacitor format.4 When a query arrives, the Dremel engine splits it into a tree of stages and schedules them over slots, reading only the columns it needs.18

A slot is BigQuery's unit of computational capacity for running a query.18

On-demand pricing bills by bytes processed, and a dry run reports those bytes without running the query.19 The console shows the same estimate beside the Run button as "This query will process X MB". Because storage is columnar, SELECT * over a wide table costs more than naming two columns.19

Each learner works in a free sandbox project. It needs no billing account and gives 10 GB of storage and 1 TB of query processing a month, with a 60-day default table expiration.20 It does not support DML (INSERT, UPDATE, DELETE), streaming inserts or the Data Transfer Service,20 so tables are written by loads and DDL only.

Creating datasets

A dataset is the top-level container that groups tables and views inside a project. It carries a location and a default table expiration.5 A table's full name is project.dataset.table, so the desk's staged tickets live at desk-<id>.desk_raw.tickets.

bq mk --dataset --location=northamerica-northeast2 --default_table_expiration=2592000 desk_raw
bq show desk_raw

The first command prints a one-line confirmation, and the second shows the dataset's location and default expiration. bq mk --dataset creates the dataset, and --default_table_expiration is given in seconds.21 2592000 seconds is 30 days, and it applies to tables created later.22 A table that sets its own expiration overrides the dataset default.22

northamerica-northeast2 is the Toronto region.23 A dataset's location is fixed at creation, and a query can only join tables whose datasets share a location.23 So name the location once and use it for every dataset. The console's Create dataset dialog asks for the same ID, location and expiration.

Create and use tables

GoogleSQL types map closely onto the MySQL types of week 3.24 In GoogleSQL, INTEGER is an alias of INT64, and the schema file below uses it.24

The file prints nothing; bq load reads it as its last argument. A file reaches a table in one of three ways:16

  • The console's upload form, for a one-off file you are exploring.
  • bq load on the command line, for a step you script and keep in Git.
  • A load job submitted from code, for a pipeline that loads on every run.
bq load --replace --source_format=NEWLINE_DELIMITED_JSON desk_raw.ticket_events ticket_events.jsonl ticket_events.json
bq load --replace --source_format=CSV --skip_leading_rows=1 desk_raw.customers customers.csv customer_id:INTEGER,name:STRING,email:STRING,country:STRING,monthly_fee:NUMERIC
bq show --schema desk_raw.customers

Each load reports a finished job, and the last line prints the schema as one JSON list in which monthly_fee is NUMERIC. --replace overwrites the table, and a schema is given inline or as a file.16 Uploaded with Auto detect instead, the same CSV can arrive with monthly_fee as FLOAT; only a schema fixes that.17

Changing a schema and an expiration

Adding a column and relaxing a column's mode are allowed. Most other type changes need a copy of the table, or ALTER COLUMN ... SET DATA TYPE for a permitted widening.25 A table's expiration is changed with ALTER TABLE ... SET OPTIONS.26 These run in the console's query editor on a scratch table:

CREATE TABLE desk_raw.scratch_notes (note_id INT64, score INT64);
ALTER TABLE desk_raw.scratch_notes ADD COLUMN body STRING;
ALTER TABLE desk_raw.scratch_notes ALTER COLUMN score SET DATA TYPE NUMERIC;
ALTER TABLE desk_raw.scratch_notes SET OPTIONS (expiration_timestamp = TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 1 DAY));
DROP TABLE desk_raw.scratch_notes;

Each statement reports what it changed and touches no rows. TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 1 DAY) means "this time tomorrow". The change from INT64 to NUMERIC is one of the permitted widenings.25

Sharing with IAM, and the console beside bq

Access is granted with IAM roles such as BigQuery Data Viewer, Data Editor and Data Owner, on a dataset or on a single table.8 In the console, a dataset's Share menu leads to Manage permissions and Add principal. A Data Viewer grant then prints as a READER entry with userByEmail in the access list of bq show --format=prettyjson.821

Takeaways
  • Storage and compute scale separately; a query runs as stages over slots.
  • On-demand queries bill by bytes read, so name columns instead of selecting everything.
  • A dataset's location is permanent, and its default expiration is given in seconds.
  • Load with a custom schema; autodetect can guess a money column as FLOAT.
Say it in an interview

BigQuery separates storage from compute. Data sits in a columnar format, and when I run a query the engine breaks it into stages and spreads them over slots, which are units of compute. On demand I'm billed for the bytes the query reads, so selecting only the columns I need is the main cost control.

A dataset groups tables in a project and sets the location and a default table expiration. The location can't change and joins only work within one location, so I pick it once. On the command line it's bq mk with the location and the expiration in seconds.

I can load through the console upload, bq load, or a load job from code. I pass a custom schema, inline or as a JSON file, because autodetect can get types wrong. Schemas can gain columns or widen a type with ALTER TABLE. I create a table by loading it with a schema or with CREATE TABLE and its column list, and I grant BigQuery Data Viewer on a dataset or on a single table when someone needs only one.

GoogleSQL

BigQuery queries and advanced queries

Once the staging tables are loaded, the desk's data answers SQL in BigQuery. Most of what week 3 taught carries over, and a few additions make analytical questions shorter.

A first GoogleSQL query

GoogleSQL is BigQuery's default standard dialect, and the older legacy SQL is avoided.27 A table is named with its dataset, and the rest reads like MySQL.

-- tickets per status
SELECT
  status,
  COUNT(*) AS tickets
FROM desk_raw.tickets
GROUP BY status
ORDER BY status;

It returns three rows: assigned 2, closed 3 and open 1. In the console you paste it into the query editor and press Run. On the command line the same file runs like this:

bq query --use_legacy_sql=false < per_status.sql

It prints the same three rows. --use_legacy_sql=false selects GoogleSQL, and < feeds the file to the command the way week 3 fed SQL files to MySQL.

A few differences from MySQL catch people. DATETIME is a date and time with no time zone, while TIMESTAMP is an exact moment, and table names are case-sensitive.27 LIMIT does not reduce the bytes a query reads or bills, so it is no way to make a big scan cheap.19 Repeating an identical query can be answered from cached results instead of a new scan.19

Results do not have to stay on screen. The console can save them to a BigQuery table, a CSV or JSON file, or a Google Sheet.28

Window functions and QUALIFY

A window function computes a value for each row from a group of related rows, and keeps every row. GROUP BY collapses each group to one row; a window does not. The window is described by OVER (PARTITION BY ... ORDER BY ...): PARTITION BY says which rows form a group, and ORDER BY says their order inside it.

ROW_NUMBER() numbers the rows within each group, and QUALIFY filters on a window function's result without a subquery.27 Together they name the extra copy that step 4's GROUP BY could only count:

-- the second and later copies of an event
SELECT
  event_id,
  ticket_id,
  kind,
  ROW_NUMBER() OVER (PARTITION BY ticket_id, kind, created_at ORDER BY event_id) AS copy
FROM desk_raw.ticket_events
QUALIFY copy > 1;

One row comes back: event 12, ticket 4, assigned, copy 2. Event 11 is copy 1 of the same business key and stays out of the result.

LAG(x) OVER (PARTITION BY k ORDER BY t) reads the previous row's value in each group,29 and DATETIME_DIFF(a, b, HOUR) returns the number of whole hour part boundaries crossed between two DATETIMEs.30 Together they measure the gap between one event and the one before it on the same ticket:

-- hours since the previous event on ticket 4
SELECT
  event_id,
  kind,
  DATETIME_DIFF(created_at, LAG(created_at) OVER (PARTITION BY ticket_id ORDER BY event_id), HOUR) AS hours_since_previous
FROM desk_raw.ticket_events
WHERE ticket_id = 4
ORDER BY event_id;

Three rows: event 10 (open) with NULL, because the first event has no previous one; event 11 (assigned) with 1; and event 12, the duplicate, with 0.

Named subqueries with WITH, and recursion

A non-recursive WITH names a subquery for the rest of the statement, often called a CTE (common table expression). WITH RECURSIVE needs an anchor term, UNION ALL and a recursive term, and repeats until no rows are added.27 This one counts from 1 to 8 and keeps the numbers that are not ticket ids:

-- ticket ids from 1 to 8 with no ticket
WITH RECURSIVE numbers AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 AS n
  FROM numbers
  WHERE n < 8
)
SELECT n
FROM numbers
LEFT JOIN desk_raw.tickets AS t
  ON t.ticket_id = numbers.n
WHERE t.ticket_id IS NULL
ORDER BY n;

Two rows: 7 and 8, since the desk holds tickets 1 to 6. The anchor starts at 1, and the recursive term adds one row per pass until n reaches 8. Recursion in BigQuery has an iteration limit and is rarely the right tool for large hierarchies.27 Its everyday uses are filling gaps in a series and walking a small tree such as a reporting line.

Takeaways
  • GoogleSQL is the dialect to use; run it in the console or with bq query and the legacy flag off.
  • LIMIT does not reduce the bytes a query bills.
  • A window function keeps every row; QUALIFY filters on its result.
  • WITH names a subquery; WITH RECURSIVE repeats until no rows are added.
Say it in an interview

A basic BigQuery query is standard SQL against dataset-qualified tables, like counting tickets per status from desk_raw.tickets. I run it in the console or with bq query with legacy SQL turned off, and I watch the bytes estimate, since LIMIT doesn't make a scan cheaper.

A window function computes something per row over a group without collapsing the rows, which is the difference from GROUP BY. To find duplicates I number rows with ROW_NUMBER partitioned by the business key and keep anything above one with QUALIFY. A recursive CTE has an anchor, a UNION ALL and a recursive part, and I use it for things like generating a series to fill gaps.

Denormalization

Denormalisation and nested fields

Week 3 split the desk into seven tables so that each fact is stored once. Analytical stores often undo some of that on purpose, and this step explains why.

Why analytical stores denormalise

Normalisation suits OLTP because each fact is stored once, so an update touches one place.3 Changing a customer's email is one UPDATE on one row, and every ticket sees the new value through its foreign key.

Denormalisation deliberately stores copies of values, or nests related rows together, so that analytical queries need fewer joins. It trades storage and update cost for fewer joins and faster scans.31 A query that reads one wide table avoids the join.

ConcernNormalised (OLTP)Denormalised (OLAP)
Storageeach value oncevalues copied onto many rows
Query speedjoins on every reportfewer joins, faster scans
Update costone row changesevery copy must change

The update cost matters less in a warehouse than in OLTP, because warehouse data is mostly appended and reloaded in batches rather than edited row by row.

You recognise denormalisation as one wide board query or table joining ticket, customer and agent into a single row, so the customer's name repeats on every one of their tickets. A materialised view, a stored and refreshed query result, is another way to pay storage for read speed.

STRUCT and ARRAY columns

BigQuery encourages denormalised tables with nested and repeated columns, because they avoid joins at scale.31 A STRUCT groups named fields inside one column, such as an address with a street and a city. An ARRAY repeats a value. Together they model one-to-many without a join.31

ARRAY_AGG(STRUCT(...) ORDER BY ...) builds such a column from ordinary rows: for each group it collects one STRUCT per row into an ARRAY. This board puts each ticket's whole history inside the ticket's row:

-- board, denormalised: one row per ticket, its history nested
SELECT
  t.ticket_id,
  t.title,
  t.status,
  ARRAY_AGG(STRUCT(e.kind, e.created_at) ORDER BY e.event_id) AS history
FROM desk_raw.tickets AS t
JOIN desk_raw.ticket_events AS e
  ON e.ticket_id = t.ticket_id
GROUP BY t.ticket_id, t.title, t.status
ORDER BY t.ticket_id;

Six rows come back, one per ticket. Ticket 4's history holds three entries in event order: open, assigned and assigned again. Ticket 2's holds open, closed and the misspelt closd. The bad rows from step 4 are still there, because nothing has removed them yet.

The console shows each ticket as one row with its history entries stacked inside it. A plain join would have returned 14 rows with the title repeated on each. The nested version keeps one row per ticket and still carries every event.

The staged tables are still a copy of MySQL's shape, and Thursday's page designs a model built for analysis on top of them.

Takeaways
  • Normalisation stores each fact once, so an update touches one place.
  • Denormalisation copies or nests values to avoid joins, paying in storage and update cost.
  • A STRUCT groups named fields; an ARRAY repeats a value.
  • ARRAY_AGG of a STRUCT nests a one-to-many relation inside one row.
Say it in an interview

Denormalisation means storing copies of values, or nesting related rows, so analytical queries need fewer joins. Transactional databases normalise because each fact lives in one place and an update is cheap. Warehouses denormalise because they're read far more than they're updated, so they trade extra storage and a costlier update for faster scans.

In BigQuery the usual tool is nested and repeated fields: a STRUCT groups named fields in one column, and an ARRAY holds many values, so one row can carry a ticket and its whole history without a join.

Check yourself

Check yourself

Ten retrieval questions, at least one per section. Answer each out loud before you open it.

The desk's MySQL answers "what is ticket 4's status" and a dashboard answers "tickets closed per priority last quarter". Which is OLTP and which is OLAP, and why keep them in separate systems?

The status lookup is OLTP: one row by its key, current data, many application users. The dashboard is OLAP: a scan and aggregate over history for analysts. One system cannot be tuned for both, and big analytical scans on production compete with the writes the application needs, so the history is copied into a warehouse.

What is the difference between schema-on-read and schema-on-write, and which belongs to a lake?

A lake stores raw files in their original format and applies a schema when someone reads them (schema-on-read). A warehouse checks and types data against a fixed schema when it is loaded (schema-on-write). A lake is cheap and flexible but turns into a swamp without governance; a warehouse is reliable but needs modelling first.

Name the layers of a warehouse architecture in order, and say where an ODS and a data mart sit.

Sources, extract, staging, the warehouse, data marts, consumers. An ODS sits between the sources and the warehouse as a near-real-time integrated copy for day-to-day reports, with little history. A mart sits after the warehouse when it is dependent, or reads sources directly when it is independent.

Compare a cloud warehouse with an on-premises one on scalability, cost and maintenance.

Cloud scales storage and compute on demand, bills by use and is maintained by the vendor, with egress and lock-in as the concerns. On-premises needs hardware bought up front and sized for peak load, has fixed capacity, and the owner patches and backs it up.

The desk's events hold a closd kind, two identical assigned rows and an event an hour before its ticket opened. Name each problem and its cleansing step.

An invalid value, fixed by validating against the allowed kinds; a duplicate, fixed by deduplicating on the business key (ticket, kind, time); an inconsistent timestamp, fixed by checking the event against the ticket's opened_at. Cleansing runs after the extract and before the warehouse, and rejected rows should keep a reason.

Why does the desk extract its events as newline-delimited JSON instead of CSV, and why does the extract not drop the bad rows?

The event notes contain commas, which JSON lines never has to quote. The extract copies rows as they are so staging holds exactly what the source held; cleansing is a later, separate step that can be rerun from staging.

A CSV of customers uploaded with Auto detect shows monthly_fee as FLOAT. What are the three ways to load it, and how do you get NUMERIC?

The console's upload form, bq load, or a load job submitted from code (the other two create one). Load it again with a custom schema, inline as monthly_fee:NUMERIC or in a JSON schema file, with --replace to overwrite the table and --skip_leading_rows=1 for the header.

How do you add a column to a BigQuery table, change a column's type, and make a table expire tomorrow?

ALTER TABLE ... ADD COLUMN adds a column. ALTER COLUMN ... SET DATA TYPE works for a permitted widening such as INT64 to NUMERIC; other changes need a copy of the table. ALTER TABLE ... SET OPTIONS (expiration_timestamp = TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 1 DAY)) sets the expiration.

How do you create a dataset in Toronto with a 30-day default expiration from the command line, share another dataset read-only, and confirm the share with bq?

bq mk --dataset --location=northamerica-northeast2 --default_table_expiration=2592000 desk_raw, since the expiration is in seconds. The share is made in the console (Share, Manage permissions, Add principal, BigQuery Data Viewer). bq show --format=prettyjson on the dataset then lists a READER entry with the person's userByEmail.

How does a window function differ from GROUP BY, and why is denormalising worth its cost in a warehouse?

GROUP BY collapses each group to one row; a window function computes a value per row over its group and keeps every row, and QUALIFY filters on it. Denormalising copies or nests values to avoid joins, paying in storage and update cost, which suits a warehouse that is read far more than it is updated.
