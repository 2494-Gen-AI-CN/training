Four routes with no upload

A notebook that loads its data from code runs anywhere: on a fresh runtime, on a reviewer's laptop, a month from now. A file uploaded by hand into Colab disappears when the runtime resets, and nobody else can rerun the notebook without it. Four routes need no upload:

RouteThe callWhat comes back
Keras built-intf.keras.datasets.<name>.load_data()numpy arrays, already split into training and test1314
scikit-learn loaderfetch_<name>(...), such as fetch_california_housingthe data and its labels, cached after the first download15
TensorFlow Datasetstfds.load(name, split=..., as_supervised=True)a named dataset from a large catalogue16
A public CSVpd.read_csv(url)a pandas DataFrame, the table type18

The first route is the one the setup cell below uses: load_data() downloads the data once, keeps a cached copy, and returns two pairs of arrays.13 Each example in this step loads a dataset the week's notebooks have used already, so the cells show how each route works and are not suggestions for your project's data.

Setup: the digits and the split

Every example on this page runs in one fresh Colab notebook, cell after cell, starting with the cell below. It imports the libraries, sets the seeds (step 3 explains those lines) and loads MNIST, the handwritten digits, by the Keras built-in route.

Run in Colab

import numpy as np
import pandas as pd
import tensorflow as tf

RANDOM_STATE = 42
np.random.seed(RANDOM_STATE)
tf.keras.utils.set_random_seed(RANDOM_STATE)

(x_train, y_train), (x_test, y_test) = tf.keras.datasets.mnist.load_data()
x_train = x_train.reshape(-1, 784).astype("float32") / 255.0
x_test = x_test.reshape(-1, 784).astype("float32") / 255.0
x_tr, y_tr = x_train[:54000], y_train[:54000]
x_val, y_val = x_train[54000:], y_train[54000:]
print(x_tr.shape, x_val.shape)
(54000, 784) (6000, 784)

The cell prepares MNIST exactly as Monday's page did: each image flattened to 784 pixel values between 0 and 1. The output reads as 54,000 training rows and 6,000 validation rows, each 784 numbers wide. x_test and y_test stay untouched until step 4.

Looking at the data before modelling

In your notebook, right after the loading cell and before any model, write down:

  • the size: how many rows, and how many columns or pixels per row
  • the columns and their types, or for images the classes
  • the blanks in each column
  • how many examples each class has
  • a few rows or images, looked at with your own eyes

A model learns only what is in the data, and one accuracy number hides most of what can go wrong: blank cells, a column read as the wrong type, one class far rarer than the others. A few lines of pandas find these before any model is built, and a reader of the notebook meets the data before the model.

A table: size, columns, blanks, classes

For a table, pandas gives each item in one line: df.shape, df.dtypes, df.isna().sum(), df.head() and value_counts() on the label column.20 Here they run on the penguins table from step 1.

Run in Colab

print(penguins.isna().sum())

The first list prints one line per column with its type, as dtypes reports it.20 A text column such as species shows as object, and a measurement as a decimal type such as float64. Text columns need encoding before a network can read them.

The second list counts the blanks per column: the four measurement columns have 2 each and sex has 11. Those blanks need a fill learned from the training rows, as Wednesday's penguins build did, and step 4 explains why the order matters.

Run in Colab

print(penguins["species"].value_counts())
penguins.head()

The first output lists each species with its number of rows: 152 Adelie, 124 Gentoo and 68 Chinstrap, so the rarest class has under half the rows of the largest. If one class is much rarer than the others, plain accuracy can mislead. A model that never once predicts the rare class can still be right on every row of the common ones, so its accuracy looks high.

Monday's page put a number on it: on MNIST, where about one image in eleven is a 5, a model that always answers "not 5" scores about 91% accuracy and finds none of the 5s, a recall of 0.

Below the counts, head() draws the first five rows as a table, where a blank shows as NaN, pandas' mark for a missing value.

Seeds and Runtime > Run all on a fresh runtime

In your notebook, set the seeds in the top cell, and check the whole notebook with Runtime > Run all on a fresh runtime. Both make it reproducible: it gives the same results when someone else runs it from the top. Loading the data from code, step 1, was the first habit, and these are the other two.

Seeds at the top

Training is full of random choices:

  • the starting weights
  • the order fit shuffles the rows into
  • the rows a split puts aside

A random seed is a starting number that makes those choices repeat on a rerun. tf.keras.utils.set_random_seed(n) sets the Python, NumPy and TensorFlow seeds in one call.21 This cell shows the effect on numpy's random numbers.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
print(np.random.rand(3).round(3))
tf.keras.utils.set_random_seed(RANDOM_STATE)
print(np.random.rand(3).round(3))
[0.375 0.951 0.732]
[0.375 0.951 0.732]

It prints two lines of three numbers each, and the two lines are the same. np.random.rand(3) draws three random numbers between 0 and 1, and round(3) keeps three decimals. Because the seed is set again before the second draw, the second line repeats the first exactly. Without that second seed line, the second draw would give three new numbers. The same thing happens to a network's starting weights, which is why fit gives the same curves on a rerun.

You recognise the pattern at the top of most model notebooks: a constant such as RANDOM_STATE = 42, then np.random.seed(RANDOM_STATE) and tf.keras.utils.set_random_seed(RANDOM_STATE). Every later call that takes a seed gets the same constant, as in train_test_split(..., random_state=RANDOM_STATE).

Seeds have a limit. They make a rerun on the same runtime repeat, and on a CPU that is the aim. Different hardware, other library versions or a GPU may still change the numbers.21 Colab's preinstalled versions also change over time,19 so record the ones your run used.

Run in Colab

print(tf.__version__, np.__version__, pd.__version__)

It prints three version numbers: TensorFlow, numpy and pandas. Copy them into your README, so a reader knows what your numbers were measured on.

The real check: a fresh runtime

A notebook can work in your session and fail for everyone else. A fresh runtime catches three causes:

  • cells that were run out of order
  • a variable left over from a cell you deleted
  • a file you uploaded once that is still sitting in the session

None of that shows until someone starts from nothing. The check takes three moves:

  1. Start a fresh runtime, one with none of your session's variables or files.
  2. Runtime > Run all, which runs every cell from the top, in order.
  3. Read down the outputs: every cell finished without an error, and the numbers match the ones in your markdown and your results table.

On a fresh runtime the only state is what the cells create, top to bottom, so a pass means anyone can reproduce your notebook. Run the check at the end of each working session, not only before the hand-in. It also catches a Colab trap: files a cell writes, such as a saved .keras model, vanish when the runtime resets, so the cell that writes a file must come before the cell that reads it.

Takeaways
  • set_random_seed sets the Python, NumPy and TensorFlow seeds in one call.
  • Seeds make reruns repeat on the same runtime; other hardware or versions may still differ.
  • Start a fresh runtime, then Run all, and check every output before trusting a notebook.
Say it in an interview

The data loads from code, so there's no file to upload. The top cell sets one seed constant for Python, NumPy and TensorFlow, and every split or shuffle uses it. And before I trust the notebook I start a fresh runtime and run all the cells from the top, so nothing depends on leftovers from my session. Seeds give me the same numbers on the same runtime, but a different machine or library version can still move them, so I record the versions too.

Part A · Project

The test set used once, and a results table kept as you go

In your notebook, split off the test set first and run the test cell once, at the end. Between the two, keep a results table of every model on validation data. The final number of a model project should say how the model will do on data it has never met, and the test set can measure that only if nothing about it shaped the model.

Split first, test last

The rule is short: the test set is held out at the start and used once, at the end, and every choice before then is made on the validation data. It fixes the order of the notebook:

  1. Split off the test set first, right after loading and looking at the data.
  2. Split the remaining rows into training and validation rows.
  3. Fit every fill for blanks, every encoder and every scaler on the training rows only, then apply them to the other two parts.22
  4. Choose the layers, the epochs and every change by the validation numbers.
  5. Run the test cell once, on the model you keep.

Item 3 is where the test set most often leaks. A scaler fitted on all the rows has learned the test rows' averages, so the test rows helped shape the model, and the final number looks better than the model deserves. Fitting it on the training rows keeps the test rows unseen.

For a table with uneven classes, pass stratify=y to train_test_split, which keeps the class proportions the same in each part.22 Without it, a plain random split can leave the rarest class with only a handful of rows in the test set, or none, and the test number then says little about that class. In code you recognise the habit as train_test_split(X, y, test_size=0.2, stratify=y, random_state=RANDOM_STATE).

MNIST arrives with its test set already split off, and the setup cell took the last 6,000 training rows as validation. On this page x_test appears in one cell only, the last one in this step.

A results table

A results table is a short table kept as you go, with one row per trained model and its validation numbers. It puts every before-and-after on record, including the changes that did not help, so "what I tried" in a README is honest.

The next two cells train two versions of the digit network, so the table has rows to hold. One is the plain network. The other adds one BatchNormalization layer after the hidden layer, which rescales the hidden layer's outputs with each batch's own mean and spread while training.9 Everything else is the same.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
plain_model = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.Dense(10, activation="softmax"),
])
plain_model.compile(optimizer="adam", loss="sparse_categorical_crossentropy", metrics=["accuracy"])
plain_model.fit(x_tr, y_tr, epochs=5, batch_size=128, validation_data=(x_val, y_val), verbose=2)

The cell prints the training and validation loss and accuracy as each of the five epochs ends, one line per epoch because of verbose=2. In one run the fifth line ended near val_loss 0.090 and val_accuracy 0.973. The seed line restarts the random numbers, as step 3 showed, so both runs start from the same seed.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
bn_model = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.BatchNormalization(),
    tf.keras.layers.Dense(10, activation="softmax"),
])
bn_model.compile(optimizer="adam", loss="sparse_categorical_crossentropy", metrics=["accuracy"])
bn_model.fit(x_tr, y_tr, epochs=5, batch_size=128, validation_data=(x_val, y_val), verbose=2)

The second run reports its five epochs the same way; in the same run it ended near val_loss 0.083 and val_accuracy 0.973. The cell below starts the results table with both runs.

Run in Colab

results = []
for name, model in [("plain", plain_model), ("batchnorm", bn_model)]:
    val_loss, val_accuracy = model.evaluate(x_val, y_val, verbose=0)
    results.append({"model": name, "val_loss": val_loss, "val_accuracy": val_accuracy})
pd.DataFrame(results).round(4)

evaluate returns the loss and then each metric named in compile, here accuracy, so the two names before the = receive them in that order.3 Each append adds one dictionary, one row. The last line draws a two-row table with the columns model, val_loss and val_accuracy, rounded to four decimals.

In one run the table read about 0.090 for plain and about 0.088 for batchnorm, with a validation accuracy near 0.973 for both. Under the table, write one plain sentence: did batch normalization lower the validation loss or not.

Run in Colab

if results[0]["val_loss"] <= results[1]["val_loss"]:
    kept, kept_name = plain_model, "plain"
else:
    kept, kept_name = bn_model, "batchnorm"
print("kept:", kept_name)

It prints kept: and the name of the run with the lower validation loss, batchnorm in the run above. The choice is made here, in one line of logic, before the test set is touched.

The test cell

Run in Colab

test_loss, test_accuracy = kept.evaluate(x_test, y_test, verbose=0)
print(f"test accuracy of {kept_name}: {test_accuracy:.4f}")

It prints one line, the kept model's accuracy on the 10,000 test images, to four decimals: about 0.970 in the run above. That is the number a README reports as the final result, beside the validation numbers in the results table.

Run this cell once. If you run it, dislike the number, change the model and run it again, the test set has started choosing the model, and its number has become a validation number in disguise. A later idea goes into the results table on validation data, and the README reports the first test number.

Takeaways
  • Split the test set off first; fit every fill, encoder and scaler on the training rows only.
  • stratify=y keeps the class proportions the same in every part of the split.
  • Keep a results table with one row per model and its validation numbers.
  • Choose the kept model on validation data, then run the test cell once.
Say it in an interview

The test set is my estimate of how the model does on data it has never seen, so nothing about it may shape the model. I split it off first, fit scalers and fills on the training rows only, make every choice on the validation set, and run the test once on the model I keep. If I tuned against the test set, its number would just be another validation number and would flatter the model.

Part B · Training (optional)

What fit does on every batch

Part B starts here. Project 1 does not need it, so read it any time, for example once your own model trains. Use it when you want to know what fit is doing while its progress bar fills, or before you read someone else's training code. Its cells need only the setup cell of step 1.

One batch: forward pass, loss, gradients, update

Under its progress bar, fit loops over epochs, and inside each epoch it loops over batches.1 A batch is the small group of rows the model sees before its weights change once, 128 rows here. An epoch is one pass over all the training rows. On every batch the same four things happen, in this order:2

  1. The batch goes through the layers and comes out as predictions, ten probabilities per row. This is the forward pass.
  2. The predictions are compared with the true labels, which gives the loss: one number, large when the model is wrong.
  3. For every trainable weight, TensorFlow works out the gradient, the slope of the loss for that weight.
  4. The optimizer moves every weight a small step in the direction that lowers the loss.

Monday's gradient descent did the last two lines by hand for one weight, finding each slope by nudging the weight a hair each way. The 784-128-10 network has 101,770 weights, so fit asks TensorFlow for all the slopes at once. The cell below trains that network for two epochs with fit, as fit_model, after resetting the seeds so earlier cells cannot change Part B's numbers. Step 7 writes the same loop by hand and compares the two.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
fit_model = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.Dense(10, activation="softmax"),
])
fit_model.compile(optimizer="adam", loss="sparse_categorical_crossentropy", metrics=["accuracy"])
history = fit_model.fit(x_tr, y_tr, epochs=2, batch_size=128, validation_data=(x_val, y_val))

Keras prints one progress bar per epoch, ending at 422/422, followed by loss, accuracy, val_loss and val_accuracy. The 422 is the number of batches: 54,000 rows divided by 128 is 421.875, and the leftover rows make one last, shorter batch. The first two numbers are measured on the training rows and the last two on the validation rows.

On a healthy run both losses are lower after epoch 2 than after epoch 1. In one run of this cell, val_loss fell from about 0.17 to about 0.13, and val_accuracy ended near 0.97.

Batches, epochs and the knobs of fit

The weights change once per batch, many times per epoch. Two epochs of 422 batches make 844 updates. Each update looks at only 128 rows, so it is cheap and a little rough, and hundreds of small corrections per epoch move the weights much further than a single correction per pass would.

The arguments you pass to fit are its knobs. This page sets them and leaves them alone, because tuning is Friday's subject.32

KnobWhat it setsOn this page
epochshow many passes over the training rows2 here, 5 in steps 4 and 8
batch_sizehow many rows go into each update128
validation_datarows scored after every epoch and never trained on(x_val, y_val)
callbacksobjects fit calls during training, such as a loggerTensorBoard's, in step 8
shufflereorders the training rows every epoch; on by defaultleft on
verbosehow much fit prints while it runs2 in steps 4 and 8: one line per epoch

You recognise these knobs in anyone's code by where they sit: inside the fit(...) call, after the training arrays. The model's layers and the compile line decide what is trained, and the knobs decide how long and in what pieces.

Takeaways
  • On every batch, fit runs a forward pass, computes the loss, gets the gradients and updates the weights.
  • Weights change once per batch: 422 batches of 128 rows make one epoch.
  • The knobs of fit are its arguments: epochs, batch size, validation data, callbacks, shuffle and verbose.
Say it in an interview

Inside fit there are two loops: epochs, and inside each epoch the batches. For every batch it runs the forward pass to get predictions, computes the loss against the labels, gets the gradient of the loss for every trainable weight, and has the optimizer take one small step with those gradients. So the weights change once per batch, many times per epoch.

The knobs I set on fit are the number of epochs, the batch size, the validation data, any callbacks such as TensorBoard's logger, and whether to shuffle, which is on by default.

Part B · Training (optional)

The same loop written by hand with tf.GradientTape

Step 6 listed the four things fit does on every batch; this step writes them as Python on the same 784-128-10 network.

The tape

A hand-written loop needs the gradients that fit gets behind the scenes. tf.GradientTape is TensorFlow's tool for them. It records the operations run inside its with block, and afterwards tape.gradient(loss, variables) returns the slope of the loss for each variable.4

TensorFlow can work out how the loss depends on a weight only if it saw every step from that weight to the loss. If the loss is computed outside the block, the tape never saw it, and tape.gradient returns None instead of slopes.4

The loop, batch by batch

The first cell makes three objects: a fresh, uncompiled copy of the network, the loss and the optimizer.

Run in Colab

loop_model = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.Dense(10, activation="softmax"),
])
loss_fn = tf.keras.losses.SparseCategoricalCrossentropy()
optimizer = tf.keras.optimizers.Adam(learning_rate=0.001)

The cell prints nothing. SparseCategoricalCrossentropy is the loss that the string "sparse_categorical_crossentropy" names in compile: it takes labels as the integers 0 to 9 and the ten probabilities from the softmax layer.5 compile chose Adam by name; a hand loop makes the optimizer object itself, here with a learning rate of 0.001.6

Run in Colab

for epoch in range(2):
    batch_losses = []
    for start in range(0, len(x_tr), 128):
        xb = x_tr[start:start + 128]
        yb = y_tr[start:start + 128]
        with tf.GradientTape() as tape:
            preds = loop_model(xb, training=True)
            loss = loss_fn(yb, preds)
        grads = tape.gradient(loss, loop_model.trainable_variables)
        optimizer.apply_gradients(zip(grads, loop_model.trainable_variables))
        batch_losses.append(float(loss))
    print(f"epoch {epoch + 1}: mean loss {np.mean(batch_losses):.4f}")

The cell prints two lines, epoch 1 and epoch 2, each with the mean of that epoch's batch losses. The second should be lower than the first, because the weights improved over the 422 updates of epoch 1; in one run they read about 0.39 and about 0.19. The lines that do the work:

  • range(0, len(x_tr), 128) gives the first row of each batch: 0, 128, 256 and so on.8
  • x_tr[start:start + 128] slices out the next 128 rows of images, and the same slice of y_tr gives their labels.
  • Inside the tape, loop_model(xb, training=True) is the forward pass and loss_fn(yb, preds) is the loss.
  • tape.gradient returns one gradient per trainable variable, and apply_gradients uses them for one update.7 A model's trainable variables are its weights and biases, the numbers training changes.

zip pairs each gradient with its variable, and float(loss) turns the batch's loss into a plain number so the list can be averaged. The training=True flag tells each layer it is training. It changes the output only for layers such as Dropout and BatchNormalization; this network has neither, so here it is a habit.9

One corner of the slicing:

Run in Colab

starts = list(range(0, len(x_tr), 128))
print(len(starts), starts[-1], len(x_tr) - starts[-1])
422 53888 112

There are 422 batches, the same count fit printed. The last one starts at row 53,888 and holds only 112 rows, because 54,000 is not a multiple of 128. A numpy slice past the end simply stops at the end, so the loop needs no special code for it.

Comparing the hand loop with fit

Run in Colab

loop_model.compile(loss=loss_fn, metrics=["accuracy"])
print("hand loop:", loop_model.evaluate(x_val, y_val, verbose=0))
print("fit:      ", fit_model.evaluate(x_val, y_val, verbose=0))

A hand loop can train a model that was never compiled; compile is needed only for evaluate and fit, so the first line exists purely so evaluate can run.3 Each printed line is a pair, validation loss then validation accuracy, on the same 6,000 rows.

Expect the two pairs to differ a little. In one run the hand loop scored a validation accuracy of about 0.964 and fit about 0.966, with validation losses near 0.13 for both. fit shuffles the rows every epoch while the loop takes them in order.1 Compare these validation numbers, not the printed epoch losses: fit shows a running average over the epoch, and the loop prints whatever its author chose to average.3

When a team writes its own loop

fit with callbacks is the default. Teams write the loop themselves in a few situations:1

  • a custom loss or a custom update rule, such as clipping the gradients before they are applied
  • several models trained against each other, as in a GAN, where one network makes images and a second judges them
  • research code that tries a new way of training

The price of that control is that the loop above lacks four things fit gives for free, each of them code you would add:1

  • shuffling the rows each epoch
  • a validation score after each epoch
  • metrics such as accuracy
  • callbacks

You recognise a hand loop in a repository by three lines together: a with tf.GradientTape() as tape: block, a call to tape.gradient and a call to apply_gradients.

Takeaways
  • tf.GradientTape records the forward pass so tape.gradient can return a slope for each weight.
  • The loss must be computed inside the tape's block, or the gradients come back as None.
  • Compare the hand loop with fit on validation numbers; fit shuffles each epoch, so they differ slightly.
Say it in an interview

GradientTape records the operations TensorFlow runs inside its with block. After the forward pass and the loss, I ask the tape for the gradient of the loss with respect to the model's trainable variables, and I get one gradient per variable. Then the optimizer's apply_gradients takes one step. The loss has to be computed inside the block, or the tape has nothing to differentiate and returns None.

I'd use fit by default, and write the loop myself for a custom loss or update rule, a GAN where two models train against each other, or research code, knowing I then own shuffling, metrics and validation.

  • On the epoch_loss chart, the two validation lines. The run that ends with the lower validation loss did better on the measure every before-and-after this week uses.
  • Each run's gap between its training and validation lines, the same reading as one run's two curves on one chart, now done across two runs.
  • The Histograms tab, which shows how each layer's weights spread and shift epoch by epoch, written because of histogram_freq=1.

Two mistakes leave the dashboard wrong. An empty TensorBoard usually means --logdir points at the wrong path, or the fit never ran with the callback.11 Rerunning a fit into the same folder adds a second run's events on top of the first, so one line turns into a tangle; the fix is a new folder name for each run.11 The logs folder also disappears when the Colab runtime resets.

Takeaways
  • TFLearn is unmaintained; its tensorboard settings became the Keras TensorBoard callback.
  • The callback writes a run's numbers to log_dir; histogram_freq=1 adds weight histograms.
  • One folder per run under one parent lets the Scalars tab overlay the runs.
  • An empty dashboard usually means a wrong logdir; a reused folder merges two runs.
Say it in an interview

TensorBoard is a dashboard for training runs. Its files come from the Keras TensorBoard callback, which I pass to fit with a log directory, and it writes the loss and metrics every epoch. TFLearn was a high-level library on top of TensorFlow. Its last release was in 2020 and it doesn't import on current TensorFlow, so where an old tutorial sets tensorboard_verbose on its model, today I'd use Keras and the TensorBoard callback.

Check yourself

Answer each question out loud first, the way you would in an interview, then open it to compare.

Name four ways to load a dataset into Colab with no upload.

A Keras built-in with load_data(), a scikit-learn fetch_ loader, tfds.load from TensorFlow Datasets, and pd.read_csv on the URL of a public CSV.

How do you show a notebook is reproducible, and what can seeds not promise?

Load the data from code, set one seed constant at the top with tf.keras.utils.set_random_seed, then start a fresh runtime, Run all, and check every output. Seeds make reruns on the same runtime repeat, but other hardware, library versions or a GPU can still change the numbers.

Why is a scaler fitted on the training rows only, and why does the test cell run only once?

A scaler fitted on every row has learned the test rows' averages, so the test rows leak into the model. Running the test cell, changing the model and running it again lets the test set choose the model; its number then says no more than a validation number.

What does a .keras file hold, and how do you check that a saved model loads back correctly?

The architecture, the weights, the compile settings and the optimizer's state, in one zip file. Load it with tf.keras.models.load_model and compare its predictions with the original model's on the same rows using np.allclose.

What happens on every batch inside fit, and how many weight updates do two epochs on 54,000 rows at a batch size of 128 make?

A forward pass gives predictions, the loss compares them with the labels, the gradients give the slope of the loss for every weight, and the optimizer takes one step. One epoch is 422 batches, the last one short, so two epochs make 844 updates.

A hand-written loop computes the loss on the line after the with tf.GradientTape() as tape: block ends. What goes wrong?

The tape records only what runs inside its block, so it never saw the loss being computed. tape.gradient returns None, and apply_gradients then fails or changes nothing. Move the loss line inside the block.

Your hand loop and fit trained the same network for two epochs, and their validation accuracies differ slightly. Is that a bug?

No. fit shuffles the rows every epoch while the loop takes them in order. Compare validation numbers and expect a small difference; the printed epoch losses are averaged differently, so they are compared loosely at best.

When would a team write its own training loop, and what does it give up?

For a custom loss or update rule, for models trained against each other such as a GAN, or for research code. It gives up what fit does for free: shuffling, metrics, validation after each epoch and callbacks all become code the team writes.

TensorBoard shows an empty page, and on another day one tangled line where you expected two runs. What happened each time?

An empty page usually means --logdir points at the wrong folder or the fit never ran with the callback. The tangle means two runs were written into the same folder; give each run its own folder under one parent and point TensorBoard at the parent.

An old tutorial builds its model with tflearn.DNN(net, tensorboard_verbose=3, tensorboard_dir="logs"). What do you use instead?

TFLearn is unmaintained since 2020 and does not import on current TensorFlow. Build the network in Keras and pass tf.keras.callbacks.TensorBoard(log_dir=...) to fit through callbacks.
