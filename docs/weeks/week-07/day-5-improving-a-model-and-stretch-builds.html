A fresh notebook for this page

Every example is a cell for Google Colab. Make a new notebook (File, then New notebook) and run the cells in the order they appear. Each one needs only the cells above it, so if the runtime resets, running from the top brings everything back. The runtime is the machine Colab lends you; a CPU one is enough for every cell here.

The setup cell imports the libraries, fixes the random seeds and defines two drawing helpers. tf.keras.utils.set_random_seed sets the Python, NumPy and TensorFlow seeds in one call,1 as Thursday's page shows with a rerun.

Run in Colab

import numpy as np
import pandas as pd
import matplotlib.pyplot as plt
import tensorflow as tf

RANDOM_STATE = 42
np.random.seed(RANDOM_STATE)
tf.keras.utils.set_random_seed(RANDOM_STATE)

def plot_history(history, metric="loss", title=""):
    """Draw the training and validation curves of one metric on one chart."""
    plt.plot(history.history[metric], label="training")
    plt.plot(history.history["val_" + metric], label="validation")
    plt.xlabel("epoch")
    plt.ylabel(metric)
    plt.title(title)
    plt.legend()
    plt.show()

def show_image_grid(images, titles, columns=5):
    """Draw 28 by 28 images in rows of `columns`, each under its title."""
    rows = int(np.ceil(len(images) / columns))
    plt.figure(figsize=(2.2 * columns, 2.4 * rows))
    for i, (image, title) in enumerate(zip(images, titles)):
        plt.subplot(rows, columns, i + 1)
        plt.imshow(np.reshape(image, (28, 28)), cmap="gray")
        plt.title(title, fontsize=9)
        plt.axis("off")
    plt.show()

print("Setup complete")
Setup complete

plot_history draws one metric's training curve and validation curve on one chart, and show_image_grid turns each row of 784 pixels back into a 28 by 28 picture with a title over it. The next cell loads the MNIST handwritten digits and splits them the same way as every other page this week.

Run in Colab

(x_train, y_train), (x_test, y_test) = tf.keras.datasets.mnist.load_data()

x_test = x_test.reshape(-1, 784).astype("float32") / 255.0
x_tr, y_tr = x_train[:54000], y_train[:54000]
x_val, y_val = x_train[54000:], y_train[54000:]
print(x_tr.shape, x_val.shape)
(54000, 784) (6000, 784)

That is 54,000 training rows and 6,000 validation rows, each a digit flattened to 784 pixel values between 0 and 1. Validation data is the set of rows held back from fitting and used to compare models. The 10,000 test digits in x_test wait untouched until step 4. A first run also prints a download line.

Two curves: too little fit or too much

fit returns a History object. Its history dictionary holds the training loss and the validation loss for every epoch, plus each metric with a val_ twin.2 Those lists are the two curves, and their shape tells you which family of changes to try.

What the curves doNameWhat it means
Training loss still falling, validation loss risingOverfittingThe model is learning the training rows themselves, quirks included, and doing worse on rows it has not seen
Both losses high and flatUnderfittingThe model is too small or trained too briefly to learn the pattern at all
Both falling and close togetherA good fit so farThe curves give no sign; the wrong examples decide the next change

The first two rows are the TensorFlow tutorial's definitions.3 Monday's page showed the first row on this network. The cell below fits the week's 784-128-10 digit network for 20 epochs, twice the usual 10, so the overfitting has time to show.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
base_20 = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.Dense(10, activation="softmax"),
])
base_20.compile(optimizer="adam", loss="sparse_categorical_crossentropy", metrics=["accuracy"])
base_history = base_20.fit(x_tr, y_tr, epochs=20, batch_size=128,
                           validation_data=(x_val, y_val), verbose=0)
plot_history(base_history, title="base_20: 784-128-10, 20 epochs")
print("lowest validation loss at epoch", int(np.argmin(base_history.history["val_loss"])) + 1)

verbose=0 switches off the per-epoch log, so the chart is the output. The training curve falls for all 20 epochs. The validation curve falls for about ten, flattens, then turns up. Every epoch after its lowest point fits the training digits better and the validation digits worse, which is overfitting.

The printed line finds that lowest point. np.argmin gives the position of the smallest value in the list, counting from 0, so + 1 turns it into an epoch number counting from 1. One run of these cells printed epoch 12. There the validation loss was about 0.082, and by epoch 20 it had climbed back to about 0.096. Colab's library versions differ a little from that run's, so expect an epoch near 12.

The fit should finish well inside three minutes on a CPU runtime. If it does not, pass x_tr[:20000] and y_tr[:20000] instead, and do the same in step 4 so the two fits stay comparable.

The wrong examples speak about the data

The curves say whether the model fits too little or too much. The digits it gets wrong show what the curves cannot: whether the trouble sits in the data, the labels or the preprocessing.3 Look at them before choosing a change.

Run in Colab

val_pred = base_20.predict(x_val, verbose=0).argmax(axis=1)
wrong = np.where(val_pred != y_val)[0]
print(len(wrong), "of", len(y_val), "validation digits are wrong")
show_image_grid(x_val[wrong[:10]], [f"true {y_val[i]}, predicted {val_pred[i]}" for i in wrong[:10]])

predict gives ten probabilities per digit, and argmax(axis=1) picks the position of the largest one in each row, which is the predicted digit. np.where(...)[0] returns the row numbers where prediction and label disagree. The print counts them out of 6,000, about 120 in one run, so about 2% of the validation digits. The grid draws the first ten with their true and predicted labels.

Read the grid for what the mistakes share, and ask whether that trait sits in the data, the labels or the preprocessing. The answer steers the lever you pick in step 2.

Takeaways
  • Read both curves and the wrong examples before choosing what to change.
  • Training loss falling while validation loss rises is overfitting.
  • Both losses high and flat is underfitting.
  • The wrong examples point at the data, the labels or the preprocessing.
Say it in an interview

First I wouldn't change anything. I'd plot training and validation loss on one chart. With a 99 against 90 gap I'd expect training loss still falling while validation loss turns up: overfitting.

Then I'd look at the validation examples it gets wrong, because they tell me whether the problem is the model or the data. Only then would I pick one change, such as dropout, and measure it.

Part A · Levers

The levers: what each is for and the sign that says to pull it

Use this when step 1's curves and wrong examples have told you what kind of problem you have, and you need the one change to try.

A lever is one setting you change to try to improve a model. Look a lever up in the table; the subsections give the reasons.

LeverWhat it is forThe sign to try itWhat to watch

Capacity: hidden units, layers and a second architecture

Capacity is how much a network can learn, set mostly by its number of layers and units. Too little underfits and too much overfits, so more units cure one sign and worsen the other.4

Monday's page pulled this lever once, adding Dense(64) after the first hidden layer. A second architecture is the bigger version of the same lever:4 Wednesday's CNN is built for images where the Dense network is not.

Dropout, early stopping and batch normalization

Dropout and early stopping are the levers for a growing gap between training and validation loss.5 Dropout, from Wednesday's CNN build, switches off a random share of its inputs while training. The new detail here is the scaling: the inputs it keeps are multiplied by 1 / (1 - rate).6

When any unit may vanish on the next batch, the network cannot rest its answers on a few units that memorised the training rows. The cell runs a Dropout(0.2) layer on a row of 100 ones, once as fit would and once as predict would.

Run in Colab

drop = tf.keras.layers.Dropout(0.2)
ones = np.ones((1, 100), dtype="float32")
print(np.unique(drop(ones, training=True).numpy()))
print(np.unique(drop(ones, training=False).numpy()))
[0.   1.25]
[1.]

np.unique lists the distinct values in the output. With training=True each value is either switched off to 0 or scaled to 1.25, which is 1 / (1 - 0.2). Scaling the survivors keeps the layer's total about the same on average, so nothing downstream has to adjust. With training=False the ones pass through unchanged, which is how predict and evaluate run the layer.6

Early stopping lets the validation loss choose the epoch count,5 so base_20 would have stopped a few epochs after its turn. In someone else's code it is one argument to fit: callbacks=[tf.keras.callbacks.EarlyStopping(monitor="val_loss", patience=3, restore_best_weights=True)]. It stops training once the validation loss has not improved for patience epochs in a row, and restore_best_weights=True puts back the weights from the best epoch.5 Wednesday's page passes it to the CNN's fit.

Batch normalization is the lever to try when training is slow or unsteady in a deeper stack.7 Wednesday's page explains the layer and measures it against the plain digit network like any other change.

The learning rate, the preprocessing and the threshold

The learning rate sets how far each weight moves on every update. Adam's default is 0.001, and a different rate goes in compile as optimizer=tf.keras.optimizers.Adam(learning_rate=...).8 Too small a rate makes the loss crawl over many epochs; too large makes it bounce or grow.9

The preprocessing is the lever when the wrong examples share a trait of the input rather than of the model. Whatever you change there is still learned from the training rows only, as in Wednesday's penguins build.

The decision threshold applies to a yes-or-no model. A sigmoid output is a probability, and Keras's precision and recall metrics turn it into a yes at 0.5 unless told otherwise. Moving the cut trades precision against recall,10 and week 8 tunes it properly. The digit network has no threshold to move, because it picks the largest of ten probabilities.

Takeaways
  • Each lever has a job and a sign in the curves or the wrong examples.
  • More units or layers help underfitting and make overfitting worse.

Say it in an interview

I pick the lever from the curves. Both losses high and flat is underfitting, so I add capacity: more units or another layer. Training loss falling while validation loss rises is overfitting, so I try dropout or early stopping. If the loss bounces, I check the learning rate.

Dropout switches off a random share of a layer's outputs on every training step and scales up the rest, so the network can't rely on a few units. It's only active during training; at prediction time every unit is used.

Part A · Method

One change at a time: measured on the same validation data

Use this when you have picked a lever from step 2 and are about to train the changed model.

A change is worth keeping only when you can show that it moved the number and that nothing else did. Three habits make that possible:

  • each run changes one lever against the model before it
  • every run starts from the same seeds and is scored on the same validation rows
  • a results table keeps every run, the ones that did worse included

Fixed seeds make a rerun repeat

Change a wider layer and dropout together, and a better number cannot say which one helped, or whether one helped while the other hurt. So each run changes exactly one thing.

The seed matters as much, and Thursday's page explains tf.keras.utils.set_random_seed.1 The new point here is where the call goes: just before building each model being compared. The cell checks this.

Run in Colab

def new_digit_model():
    return tf.keras.Sequential([
        tf.keras.Input(shape=(784,)),
        tf.keras.layers.Dense(128, activation="relu"),
        tf.keras.layers.Dense(10, activation="softmax"),
    ])

tf.keras.utils.set_random_seed(RANDOM_STATE)
first = new_digit_model()
tf.keras.utils.set_random_seed(RANDOM_STATE)
second = new_digit_model()
third = new_digit_model()
print(np.allclose(first.get_weights()[0], second.get_weights()[0]))
print(np.allclose(first.get_weights()[0], third.get_weights()[0]))
True
False

get_weights()[0] is the first layer's 784 by 128 table of starting weights. first and second were each built right after the same seed call, so they start identical and the first line prints True. third had no fresh seed call and drew new random numbers, so the second line prints False. That is why every fit cell on this page opens with tf.keras.utils.set_random_seed(RANDOM_STATE).

A results table kept as you go

A comparison counts only when both models are scored on the same 6,000 validation digits. The cell scores base_20, so it needs step 1's cells run first. Thursday's page builds this table and reads what evaluate returns;2 here it gets its first row.

Run in Colab

results = []
val_loss, val_accuracy = base_20.evaluate(x_val, y_val, verbose=0)
results.append({"model": "base 20 epochs", "val_loss": val_loss, "val_accuracy": val_accuracy})
pd.DataFrame(results).round(4)

Colab draws the cell's last line as a one-row table with the columns model, val_loss and val_accuracy, rounded to four places, one row per dictionary in the list.11

One run gave a validation loss of about 0.096 and an accuracy of about 0.979. That accuracy means about 5,880 of the 6,000 digits right and about 120 wrong, which matches the count step 1 printed for the same model. In your own project, use the metric your project is judged by in place of accuracy, with the same val_ prefix.

When a change did not help, and the test set

Some changes will not help, and their rows stay in the table. A gain of 0.1 point on 6,000 validation rows may be noise: with the seeds fixed a rerun repeats the number, but a different seed can flip a small gap.3 Here 0.1 point of accuracy is 6 digits out of 6,000. Report a gap that small plainly as "did not help".

The test set stays out of every one of these choices and is scored once, on the kept model, at the end, for the reason Thursday's page gives.12

An honest results table has these marks:

  • every model you trained has a row, including those that did worse
  • every row was scored on the same validation data
  • one plain sentence under the table says whether the change helped
  • the test number appears once, for the kept model only
Takeaways
  • Change one lever per run, so a moved number has one cause.
  • Set the seed before building each model so a rerun repeats its number.
  • Score every model on the same validation rows and keep every row.
  • Score the test set once, on the kept model, at the end.
Say it in an interview

One change at a time, because if I widen a layer and add dropout together and the score moves, I can't say which one did it. I fix the seeds so a rerun repeats, and I score every model on the same validation set, one row each in a results table.

I use the test set once, on the model I keep. Checking it after every change and picking the best means I've tuned on it. When a change didn't help, I say so and keep the row; a tenth of a point may be noise.

Part A · Worked example

Worked example: one improvement on the digit network

Use this when you want to see the whole loop once, from a sign in the curves to a test number, before running it on your own project.

This step builds on the cells of steps 1 and 3, so run those first: step 1 fitted base_20 and its curves showed overfitting, and step 3 put it in the results table. Validation loss rising while training loss falls points at dropout or early stopping. This step pulls the dropout lever.

The change: Dropout(0.2) after the hidden layer

The one change is a Dropout(0.2) layer between the hidden layer and the output layer.6 Everything else matches base_20:

  • the seed, set just before the model is built
  • the 20 epochs
  • the batch size of 128
  • the 6,000 validation rows

Dropout has no weights of its own, so both models have 784 × 128 + 128 + 128 × 10 + 10 = 101,770 numbers to learn.

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
dropout_20 = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(128, activation="relu"),
    tf.keras.layers.Dropout(0.2),
    tf.keras.layers.Dense(10, activation="softmax"),
])
dropout_20.compile(optimizer="adam", loss="sparse_categorical_crossentropy", metrics=["accuracy"])
dropout_history = dropout_20.fit(x_tr, y_tr, epochs=20, batch_size=128,
                                 validation_data=(x_val, y_val), verbose=0)
plot_history(dropout_history, title="dropout_20: Dropout(0.2) after the hidden layer")
print(dropout_20.count_params(), base_20.count_params())

The last line prints 101770 101770, the count worked out above. Put the chart beside step 1's and look at the gap between the curves. The training loss is computed with a fifth of the hidden units switched off, so it sits higher than before; the validation loss is scored with all of them. In one run the validation curve kept falling until about epoch 16 and then stayed near 0.065, where base_20's turned up after epoch 12.

The kept model is the row with the better validation number, chosen before the test set is touched. The next cell picks it by validation loss, the number the curves were read on, and then scores the test set once.

Run in Colab

table = pd.DataFrame(results)
kept_name = table.loc[table["val_loss"].idxmin(), "model"]

The print shows the kept model's name and its test accuracy, the number a write-up reports as the estimate for new digits. One run kept dropout 0.2 and printed a test accuracy of about 0.980, a little under its validation figure. This is the one cell where x_test appears, and its number goes back into no choice.

Part B · Stretch build 1

Part B, build 1: a denoising autoencoder

This stretch build helps a project that uses an autoencoder or works with digit images, and it assumes Tuesday's autoencoder plus the setup and MNIST cells from step 1. Part B is optional, and this build stands alone: nothing else from Part A is needed.

Part B has no build for a project that predicts a number. The "Variant: predicting a number" step of Wednesday's page covers it, and that page's "Open the notebook in Colab" link opens the notebook, whose section 7 builds it.

Same model, a different pair of arrays

An autoencoder is trained to rebuild its own input. The image goes in, passes through a narrow middle layer called the bottleneck, and the output is scored against the same image. Tuesday's autoencoder flagged unusual digits by how badly it rebuilt them.

A denoising autoencoder is trained with a corrupted input and the clean input as the target: fit(x_noisy, x_clean).16 To rebuild a clean digit from a speckled one, the 32 numbers in the bottleneck have to hold the strokes and leave out the specks. That is why the target must be the clean image.

The model is Tuesday's shape, unchanged: 784 inputs, 32 ReLU units, 784 sigmoid outputs. The sigmoid gives pixel values between 0 and 1, which matches the clean target.4 Only what fit is given changes.

Noise drawn once and clipped to 0 to 1

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
x_tr_noisy = np.clip(x_tr + 0.3 * np.random.normal(size=x_tr.shape), 0.0, 1.0).astype("float32")
x_val_noisy = np.clip(x_val + 0.3 * np.random.normal(size=x_val.shape), 0.0, 1.0).astype("float32")
print(x_tr_noisy.shape, x_tr_noisy.min(), x_tr_noisy.max())
(54000, 784) 0.0 1.0

np.random.normal(size=x_tr.shape) draws one random number per pixel from a bell curve centred on 0, and multiplying by 0.3 keeps most of them within 0.6 of zero. Added to the pixels, they speckle every image. np.clip(x, 0.0, 1.0) keeps the noisy pixels in the 0 to 1 range that the sigmoid output layer can reproduce.17 The print confirms it: the smallest value is 0.0 and the largest 1.0. .astype("float32") returns the 64-bit random sums to the 32-bit floats the network reads.

The noise is drawn once, before fit, for both splits, and the seed call on the cell's first line makes it the same whether or not Part A was run. The validation pair is (x_val_noisy, x_val), so every epoch is scored on the same noisy rows.2 Fresh noise on every call would make the validation loss wobble for reasons unrelated to the model.

The noise level 0.3 is itself a choice. Too little and the model learns to copy its input; too much and the digit cannot be recovered at all.16

Noisy, rebuilt and clean in one grid

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
denoiser = tf.keras.Sequential([
    tf.keras.Input(shape=(784,)),
    tf.keras.layers.Dense(32, activation="relu"),
    tf.keras.layers.Dense(784, activation="sigmoid"),
])
denoiser.compile(optimizer="adam", loss="mse")
denoise_history = denoiser.fit(x_tr_noisy, x_tr, epochs=10, batch_size=256,
                               validation_data=(x_val_noisy, x_val), verbose=0)
plot_history(denoise_history, title="denoiser: noisy in, clean out")

The chart shows the mean squared error between the rebuilt and the clean digits, falling on both curves. In one run the validation MSE went from about 0.050 after the first epoch to about 0.016 after the tenth. That number alone does not prove the specks are gone, so the next cell draws the evidence.16

Run in Colab

rebuilt = denoiser.predict(x_val_noisy[:5], verbose=0)

show_image_grid(images, titles)

np.concatenate stacks the three groups of five into one array of 15 images, which the helper draws as three rows: the noisy inputs on top, the model's rebuilds in the middle and the clean originals below. Expect rebuilds that are clean but blurry. The loss is MSE, and a soft grey edge costs less than a sharp edge in the wrong place.16

The three mistakes that break this build:

  • fit(x_noisy, x_noisy), which teaches the model to rebuild the specks too
  • no clip, which leaves pixels outside the range the sigmoid can produce
  • fresh validation noise on every call, which makes the validation loss wobble
Takeaways
  • A denoising autoencoder takes a noisy input and is scored against the clean image.
  • The shape stays 784-32-784; only the arrays given to fit change.
  • Noise is drawn once and clipped to 0 to 1 before fit.
  • The noisy, rebuilt and clean grid is the evidence, more than the MSE.
Say it in an interview

An autoencoder is trained to rebuild its own input through a small bottleneck, so it has to learn a compact version of the data. A denoising one gets a noisy copy as the input and the clean original as the target, so it learns to keep the structure and drop the noise.

I clip the noisy image to zero to one because the sigmoid output can only produce values in that range, like the clean target. And I show noisy, rebuilt and clean images side by side, because the loss alone doesn't prove the noise is gone.

Part B, build 2: text with TextVectorization and Embedding

This stretch build helps a project that classifies text, and it assumes Tuesday's TF-IDF text build plus the setup cell from step 1. It stands alone: it needs nothing else from Part A or from build 1.

Tuesday's text build scored each forum post with TF-IDF and fed the scores to a Dense network. This build swaps that front end for two Keras layers and compares the two models on the same posts. The TF-IDF baseline, rebuilt

The baseline is rebuilt here so both models share one split. fetch_20newsgroups downloads the posts on its first call, and remove=("headers", "footers", "quotes") strips the sender's details so the model reads the post itself.18

TfidfVectorizer(max_features=5000) keeps the 5,000 most frequent words of the training posts and gives each post one score per word, so every row is 5,000 wide.19 It is fitted on the training posts only, and .toarray().astype("float32") turns its output into the dense table of 32-bit floats the network reads. results = [] starts a fresh table for this comparison. TF-IDF ignores word order: "the bike hit the car" and "the car hit the bike" get the same scores.

TextVectorization: from a post to word ids

TextVectorization(max_tokens=10000, output_sequence_length=200) maps raw strings to integer word ids, padding or cutting each post to 200 of them. adapt learns the vocabulary, and it is called on the training posts only.20 An id is a word's position in that vocabulary.

Run in Colab

vectorize = tf.keras.layers.TextVectorization(max_tokens=10000, output_sequence_length=200)
vectorize.adapt(np.array(texts_tr))
ids_tr = vectorize(np.array(texts_tr))
ids_val = vectorize(np.array(texts_val))
print(vectorize.get_vocabulary()[:2], ids_tr.shape[1], ids_val.shape[1])
['', '[UNK]'] 200 200

adapt takes a numpy array of strings, so the posts are converted once with np.array.20 The first two vocabulary entries are reserved. Id 0 is padding, the empty string that fills a short post up to 200. Id 1 is [UNK], the out-of-vocabulary token every unknown word becomes. max_tokens counts both, so at most 9,998 real words get their own id.20

Both splits come out 200 wide. Leave output_sequence_length unset and each split is as wide as its own longest post, so the two would not match each other or the model's input. Adapting on the validation posts as well would leak their words into the vocabulary. The layer can also sit inside the model so a saved model reads raw text, as the TensorFlow text tutorial does in its export step.21

An Embedding layer and average pooling

Embedding(input_dim, output_dim) is a trainable lookup table from an integer id to a list of output_dim numbers, and input_dim must be at least the vocabulary size.22 Embedding(10000, 16) gives each of the 10,000 ids a row of 16 numbers. They start random and fit learns them like any other weight, so a post of 200 ids becomes 200 rows of 16.

GlobalAveragePooling1D averages those rows over the post, so a post of any length becomes one list of 16 numbers for the Dense layer.23 Averaging loses the order, so this model ignores word order just as TF-IDF does.19

Run in Colab

tf.keras.utils.set_random_seed(RANDOM_STATE)
embed_model = tf.keras.Sequential([
    tf.keras.Input(shape=(200,)),
    tf.keras.layers.Embedding(10000, 16),
    tf.keras.layers.GlobalAveragePooling1D(),
    tf.keras.layers.Dense(1, activation="sigmoid"),
])
embed_model.compile(optimizer="adam", loss="binary_crossentropy", metrics=["accuracy"])
print(embed_model.count_params(), text_model.count_params())
160017 160065

The embedding table holds 10,000 × 16 = 160,000 trainable numbers,22 and the output layer adds 16 weights and a bias. The TF-IDF model's first layer has 5,000 × 32 + 32 = 160,032, and its output layer 33 more. The two models are nearly the same size. The difference is that TF-IDF scores come from a fixed formula, while the embedding table is learned from 953 posts.

Takeaways
  • TextVectorization turns each post into 200 word ids, adapted on training posts only.
  • Embedding gives each id a learned row of 16 numbers; pooling averages them.
  • Both the TF-IDF model and the embedding model ignore word order.
  • On about a thousand posts the embedding model often only matches TF-IDF.
Say it in an interview

TextVectorization turns raw text into a fixed-length list of integer word ids, using a vocabulary it learns with adapt. I adapt it on the training text only, otherwise validation words leak into the vocabulary.

An Embedding layer takes those ids and gives back a learned vector for each one, which I average into one before the output layer. On a small dataset I'd expect TF-IDF to match or beat it, because the embedding learns its whole table from scratch.

Ten questions, at least one per step. Answer each out loud before you open it.

Training loss is still falling at epoch 20, but validation loss bottomed at epoch 4 and has risen since. What is this, and what do you look at before changing anything?

Overfitting: the model keeps fitting the training rows while getting worse on rows it has not seen. Before choosing a lever, look at the validation examples it gets wrong, because they show whether the trouble is the model or the data, labels or preprocessing.

What can the wrong examples tell you that the two curves cannot?

The curves only say whether the model fits too little or too much. The wrong examples show what the mistakes share, and whether the trouble sits in the data, the labels or the preprocessing.

Which levers fit underfitting, and which fit overfitting?

For underfitting, both curves high and flat, add capacity: more hidden units or layers, or a second architecture such as a CNN for images. For overfitting, a growing gap between the curves, try dropout or early stopping.

What does Dropout(0.2) do during fit, and during predict?

During fit it sets a random 20% of its inputs to 0 on each step and scales the rest by 1.25, which is 1 / (1 - 0.2). During predict and evaluate it does nothing, and every unit is used.

Your change gains 0.1 point of validation accuracy on 6,000 rows. Why do you call that "did not help", and why must only one thing have changed?

0.1 point is 6 digits, and a different seed can flip a gap that small, so it may be noise. If two things changed at once, even a real gain could not be traced to either of them.

Why is the test set scored only once, on the kept model?

Scoring it after each change and keeping the best turns it into a second validation set used for choosing. Its number then stops being an honest estimate of how the model does on new data.

An old TFLearn tutorial has tflearn.dropout(net, 0.8). What is the Keras line?

tf.keras.layers.Dropout(0.2). TFLearn's number is the share kept and Keras's is the share dropped, so copying 0.8 would switch off 80% of the units.

The loss is nan from the first epoch; elsewhere fit says target and output "must have the same rank". What do you check first in each?

For nan, blanks in the inputs: count them with np.isnan and fill them from the training rows before scaling. For the rank error, the labels against the loss: integer labels need sparse_categorical_crossentropy; two classes need one sigmoid unit.

What goes into fit for a denoising autoencoder, and why are the noisy pixels clipped?

The noisy images as the input and the clean images as the target, as in fit(x_tr_noisy, x_tr). The clip keeps every pixel between 0 and 1, the range the sigmoid output can produce and the clean target lives in.

What do TextVectorization and Embedding(10000, 16) each output, and when would TF-IDF beat them?

TextVectorization outputs a fixed-length list of integer word ids, here 200 per post, with 0 for padding and 1 for unknown words. The Embedding layer outputs a learned row of 16 numbers per id, 160,000 numbers in all. On a small set, about a thousand posts, the embedding learns its table from scratch and often only matches TF-IDF.
