Testing with pytest & NumPy: proving the desk's rules and measuring its hours

Week 2 · Day 3 Wed Oct 21, 2026 Python advanced ~39 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-15 · python 3.15 · pytest 9.1.1 · numpy 2.5.4

This page assumes Tuesday's JSON-backed ticket desk: the rules in desk.py, a storage.py that saves and loads tickets as JSON, and errors raised as ValueError. It teaches automated testing from the ground up (why teams test, what a unit test is, and pytest with its fixtures, temporary folders and parametrised cases), then NumPy arrays set against the lists of week 1, and the first part of interview practice. Each section shows a runnable example with its output, names the trade-off and ends with the words to say when an interviewer asks. Afterwards you can sketch the test pyramid, read a pytest failure, say what @ above a def does, and explain why assert arr == [3.0, 30.0] raises an error instead of failing.

Testing

Why teams test, and what kinds of test there are

So far the desk has been checked by running it and reading the output. This step says why teams stop there.

What an automated test buys a team

An automated test is a small program that runs part of your code with known inputs and compares the result with what you expected. Checking by eye works once: run python ticket_desk.py, read the lines, decide they look right. It stops working when the code has a dozen rules and four people are changing them, because nobody re-reads every line of output after every edit. A test suite re-checks every rule in a second or two and names the one that broke.

Python ships a testing framework in its standard library, unittest, so any Python install can run unit tests with no extra package.1 Its documentation names four building blocks that every framework has in some form: a test fixture (the set-up and clean-up a test needs), a test case (one individual check), a test suite (a collection of test cases) and a test runner (the program that executes the tests and reports the outcome).1

import unittest

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}


class SlaTest(unittest.TestCase):
    def test_high_is_four_hours(self):
        self.assertEqual(SLA_HOURS["high"], 4)


if __name__ == "__main__":
    unittest.main()

Saved as test_sla_unittest.py and run with python test_sla_unittest.py, this prints a single dot, then Ran 1 test in 0.000s, then OK. A class that inherits from unittest.TestCase, with methods named test_... calling self.assertEqual, is how you recognise unittest code in someone else's repository. pytest, the runner the rest of this page uses, runs TestCase tests like this one unchanged, so a team can switch runners without rewriting its suite.2 Once pytest is installed (the pytest section below covers it), python -m pytest test_sla_unittest.py reports 1 passed for the same file.

Unit, integration and end-to-end tests

Tests are sorted by how much of the system they exercise. A unit test checks one small piece, usually one function or one method, on its own: does a high-priority ticket fall due four hours after it opened? An integration test checks that several pieces work together: does a desk saved to a JSON file come back with the same tickets when it is loaded? An end-to-end test drives the whole program the way a user would and checks what it printed and wrote to disk.

A unit test runs in milliseconds and, when it fails, names one function. An end-to-end test proves the parts really fit together, but it is slow, needs more set-up, and its failure only tells you that something somewhere is wrong.

The test pyramid

The usual whiteboard picture is the test pyramid: many small, fast unit tests at the base, fewer integration tests in the middle, and a few slow end-to-end tests at the top. Martin Fowler's short article is the usual reading on it.3 The shape comes down to cost. If most of the checking happens at the top, every run is slow and every failure needs detective work, so people run the suite less often and bugs live longer. The opposite mistake costs something too: a suite of only unit tests can pass while two pieces that each work correctly disagree about the format of the file between them.

You can tell that a project tests by its layout. pytest documents two layouts: test files in a separate tests/ folder outside the application code, or test modules placed beside the code they test.4 The ticket desk uses the second, with test_desk.py next to desk.py.

Green before merge, and what coverage does not prove

"Green before merge" is the team rule that the whole suite passes before a branch is merged into main. A reviewer reads the diff for design and clarity; the test run is the check a reviewer cannot do by eye, that the change did not break a rule three files away. A red run on a pull request holds the merge until someone fixes the code or, when the rule really did change, the test.

Teams also measure coverage. A coverage tool reports which lines of the code ran while the tests ran, and which did not.5 Its limit is worth saying in an interview: a line that ran was executed, and nothing says an assert checked its result. A test that calls a function and asserts nothing raises the coverage figure without proving anything, so a high figure tells you where the tests have been and says nothing about whether the behaviour is right.5

Say it in an interview

Teams write automated tests so that every rule gets re-checked in seconds after every change, which nobody reading output by hand can keep up with. And when something breaks, the failing test names the rule, so the fix starts in the right place.

A unit test checks one function on its own, an integration test checks a few pieces together, like saving to a file and loading it back, and an end-to-end test drives the whole program like a user. You want lots of fast unit tests and a few slow end-to-end ones; flip that and the suite is slow and every failure takes detective work.

Testing

Unit testing: one rule, one test

The unit is the smallest piece worth testing on its own. In the ticket desk that means one rule: a deadline, a redaction, the list of overdue tickets.

What a unit test checks

The unittest documentation defines a test case as a check for a specific response to a particular set of inputs,1 and that is the shape of a good unit test: one rule, one situation, one expected answer. A good unit test runs quickly because it touches no network and no shared files, gives the same answer on every run, and when it fails you know which rule broke without opening its code.

The name does a lot of that last job. pytest's short summary of failures names each failing test as file::function,6 so a name such as test_unknown_priority_raises reads as a bug report on its own, while test_1 tells the next person nothing. Long, plain test names are normal; nobody calls a test function from anywhere else, so the name only has to be read, never typed.

Arrange, act, assert

Most unit tests have three parts in order. Arrange builds the inputs, act calls the one thing under test, and assert checks the result. A test is an ordinary function, so you can write one and call it yourself before any test runner is involved:

from datetime import datetime, timedelta

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}


def deadline(opened_at, priority):
    if priority not in SLA_HOURS:
        raise ValueError(f"unknown priority: {priority!r}")
    return opened_at + timedelta(hours=SLA_HOURS[priority])


def test_high_deadline_is_four_hours():
    opened = datetime(2026, 10, 19, 8, 30)
    due = deadline(opened, "high")
    assert due == datetime(2026, 10, 19, 12, 30)


test_high_deadline_is_four_hours()
print("passed")

Saved as check_rules.py and run with python check_rules.py, this prints passed. The three lines of the test are the three parts: build an opening time, call deadline, assert the answer. Had the deadline been wrong, the assert line would have stopped the script with an AssertionError and the print would never have run. The last two lines are there only so the file runs by itself; a test runner calls test functions for you. In pytest a plain assert is all a test needs, because pytest rewrites the assertion so that a failure shows the values on both sides.7

The three-part shape is how you recognise a unit test in someone else's code: a def test_overdue_skips_closed_tickets(): line, a few set-up lines, one call, one assert. A test with five calls and assertions scattered between them is usually several tests sharing one name, and its first failure hides whatever the later lines would have told you.

Testing the path that must fail

A rule that rejects bad input needs a test as much as a rule that accepts good input. The desk's Ticket raises ValueError for a priority outside SLA_HOURS, and so does the deadline function above. Testing that error path is part of unit testing: pytest.raises turns "this input must fail" into an assertion that itself fails when no exception is raised.7

def test_unknown_priority_raises():
    with pytest.raises(ValueError, match="urgent"):
        deadline(datetime(2026, 10, 19, 8, 30), "urgent")

The with block runs the call. The test passes only when the block raises that exception type and the message matches the regular expression given as match, which pytest checks with re.search.7 Delete the raise line from deadline and the lookup SLA_HOURS["urgent"] still fails, with a KeyError, so the test goes red because the type is wrong. Leave out match and any ValueError raised anywhere inside the block would count as a pass.

Test isolation: no shared files, no real clock

The interviewer's next question is often how a unit test avoids depending on the real disk or the current time. Two things make a result change between runs when nothing in the code changed: a file that other tests also write to, and the clock. The desk handles the clock with a fixed NOW in desk.py; overdue() uses it as its default "now", so a ticket opened two days before NOW is overdue on every run, whatever today's date is.

For files, pytest provides tmp_path, a built-in fixture that gives each test function its own unique temporary directory.8 The cost is that such a test never touches the real tickets.json: it proves that saving and loading work on a file, and something else still has to confirm the program uses the right file. Shared data in memory gets the same treatment. A fixture in the default function scope is created again for each test that asks for it and torn down at the end of that test, so one test cannot leave changes behind for the next.9 The fixtures section shows both in code.

Say it in an interview

A good unit test checks one rule in one situation, runs fast, gives the same answer every time, and has a name that says what broke. I write it as arrange, act, assert: build the inputs, call the one function, then check the result with an assert.

To test a function that reads a file without touching the real disk, I give the test its own temporary folder, which pytest's tmp_path fixture does, write the file I need there and point the function at it. For time, I pass in a fixed "now" so the answer doesn't depend on today's date.

Testing

pytest: finding, running and reading tests

Installing pytest and pinning it

pytest is a third-party package, installed with pip into the project's virtual environment from Monday and pinned in requirements.txt beside pylint. A requirements file lists pinned packages such as pytest==9.1.1, and pip install -r requirements.txt installs everything in it, which is how a fresh clone rebuilds the same environment.10 pytest --version prints the installed version and is the first check after an install.11

python -m pip install pytest==9.1.1
python -m pip install -r requirements.txt
pytest --version

Between the first and second commands, requirements.txt gains the line pytest==9.1.1 under pylint==4.0.0. The second command then reports both pins as already satisfied, and the last prints pytest 9.1.1. Pinning is a trade-off: everyone on the team gets the same behaviour, and someone has to raise the version on purpose when an upgrade is wanted. The usual first stumble is typing pytest in a terminal where .venv is not active, so the shell says it cannot find the command. python -m pytest runs pytest with the same Python that python -m pip install used, which makes it the safe form when in doubt.

How pytest finds tests

pytest discovers test files named test_*.py or *_test.py and, inside them, functions whose names start with test.4 Run with no arguments, it collects those files from the current folder and every folder below it, and prints a . for each test that passes and an F for each that fails.11 Nothing is registered by hand; the names are the registration. So the classic silent mistake is a name: a file called desk_tests.py or a function called check_redact is skipped, and pytest reports that no tests ran. Run it from inside ticket-desk/, too, because started from a folder above, it also collects any other test files it finds further down.

Move deadline and SLA_HOURS from check_rules.py into rules.py and put the tests in test_rules.py beside it:

from datetime import datetime

import pytest

from rules import deadline


def test_high_deadline_is_four_hours():
    opened = datetime(2026, 10, 19, 8, 30)
    due = deadline(opened, "high")
    assert due == datetime(2026, 10, 19, 12, 30)


def test_unknown_priority_raises():
    with pytest.raises(ValueError, match="urgent"):
        deadline(datetime(2026, 10, 19, 8, 30), "urgent")

pytest in that folder prints a header, then collected 2 items, then test_rules.py .. with one dot per passing test, and ends with 2 passed and the time taken.

Reading a failure

Change "high": 4 to "high": 8 in rules.py and run pytest again. The progress line now reads test_rules.py F. and the report underneath includes these lines:

>       assert due == datetime(2026, 10, 19, 12, 30)
E       assert datetime.datetime(2026, 10, 19, 16, 30) == datetime.datetime(2026, 10, 19, 12, 30)

test_rules.py:11: AssertionError
=========================== short test summary info ===========================
FAILED test_rules.py::test_high_deadline_is_four_hours - assert datetime.date...
========================= 1 failed, 1 passed in 0.05s =========================

Read it from the > marker down. A failure report shows the failing line, the values compared and the difference between them:7 the code produced 16:30 and the test expected 12:30. The summary names the test as file::function.6 From those lines alone you know which rule broke and by how much. The deadline is four hours late, so the high SLA must be 8 where it should be 4. Restore the value and the run is green again. Breaking a rule on purpose like this is worth doing once for every new test, because a test that has never failed may not be checking anything.

Choosing which tests run

pytest -v raises the verbosity so that each test is printed on its own line with its result.6 pytest -k followed by an expression selects the tests whose names match it.12

pytest -v
pytest -k unknown

The first prints test_rules.py::test_high_deadline_is_four_hours PASSED and the same line for the second test. The second runs only test_unknown_priority_raises and ends with 1 passed, 1 deselected. Good names help here too: in a suite with test_redact_hides_email and test_ticket_refs_reads_numbers, one word from a name narrows the run to one rule while you work on it.

unittest or pytest

Asked why teams choose pytest, the usual answer has two parts. Tests are plain functions with a plain assert, and the failure report still shows the values on both sides.7 And set-up is shared through fixtures that a test requests by naming them, which the next step covers.9 pytest also runs existing unittest.TestCase suites, so adopting it does not mean rewriting.2 What unittest has in its favour is that it needs no install at all,1 which matters for a small script on a machine you do not control.

Say it in an interview

pytest collects files named test-something dot py, or something-underscore-test, and runs every function in them whose name starts with test. There's no registration step, the naming convention is the registration, so a misnamed file just silently doesn't run.

Teams usually pick pytest over unittest because tests are plain functions with a plain assert, and the failure report still shows both values. Shared set-up goes into fixtures, and pytest runs old unittest suites as they are, so switching is cheap.

Testing

Fixtures, temporary folders and parametrised tests

Three pytest features remove most of the repetition from a test file, and two of them start with a line that begins with @. That line comes first.

What @ above a def does

A decorator is a function applied with @ syntax to the function defined on the next line: @name above def f is shorthand for f = name(f).13 The def runs as usual, then Python hands the new function to name and stores whatever comes back under f. pytest uses exactly this to register a fixture or to mark a test.13

registry = []


def register(func):
    registry.append(func.__name__)
    return func


@register
def sample_tickets():
    return ["Login page returns 500"]


print(registry)
print(sample_tickets())

Run as a script, this prints ['sample_tickets'] and then ['Login page returns 500']. Defining the function was enough to put its name in registry, because @register ran register(sample_tickets) at that moment. register returned the function unchanged, so calling it afterwards still works. @pytest.fixture and @pytest.mark.parametrize(...) do the same kind of bookkeeping: they note the function down so pytest can use it later. In other people's code you spot a decorator by the @ at the start of a line directly above a def, sometimes stacked two or three deep.

Fixtures: set-up a test asks for by name

A fixture is a function marked with @pytest.fixture; a test receives its return value by naming the fixture as a parameter.9 Without one, every test that needs the same four-ticket desk repeats a dozen set-up lines. With one, the lines live in a single place and pytest calls the fixture for each test that asks for it, building it fresh for every test in the default function scope.9 A test can request several fixtures at once, such as the built-in tmp_path together with a project fixture, and fixtures can request other fixtures.9

The ticket desk's fixture is sample_desk: a Desk of four tickets, with a high ticket closed after 3 hours, a normal ticket closed after 30 hours, one assigned and one still open. Every later test of the desk's numbers starts from it. The usual slip is calling a fixture like a function, writing sample_desk() inside a test, which pytest rejects with an error saying the fixture was called directly. Name it as a parameter and let pytest do the calling.

tmp_path: a folder of your own for each test

tmp_path is a built-in fixture that gives each test function its own unique temporary directory as a pathlib.Path.8 The test below asks for it and for a small project fixture, writes a JSON file into the folder, reads it back and checks nothing was lost. The second test is the subject of the next section.

import json

import pytest

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}


@pytest.fixture
def records():
    return [{"id": 1, "priority": "high"}, {"id": 2, "priority": "low"}]


def test_round_trip(tmp_path, records):
    path = tmp_path / "tickets.json"
    path.write_text(json.dumps(records), encoding="utf-8")
    assert json.loads(path.read_text(encoding="utf-8")) == records


@pytest.mark.parametrize("priority, hours", [("high", 4), ("normal", 24), ("low", 72)])
def test_sla_hours(priority, hours):
    assert SLA_HOURS[priority] == hours

Saved as test_store.py, pytest -v prints four lines: test_store.py::test_round_trip PASSED, then test_sla_hours[high-4], test_sla_hours[normal-24] and test_sla_hours[low-72], each PASSED, and ends with 4 passed. Because the folder is new for each test, a file one test writes cannot collide with the real tickets.json or with another test's file. Testing a missing file is easy: name a path inside tmp_path and never write it. The desk's own storage tests do exactly that, and also write the broken text [{ into a file there to check that loading it raises ValueError.

One test, several inputs

@pytest.mark.parametrize runs one test function once per argument set, and each case is reported separately under its own ID.14 The first argument names the parameters in one string, "priority, hours"; the second is a list of tuples, one per case; and the test function takes the same names as its parameters. It is the second decorator on the page and reads the same way: the line above the def hands test_sla_hours to pytest, which this time runs it three times.

Packing cases into one definition is shorter, and it would hide which case failed if the report did not say. pytest builds an ID from each parameter set, such as test_sla_hours[high-4], and reports every case separately.14 If the low limit were wrong, the summary would name test_sla_hours[low-72] while the other two still passed. You recognise parametrisation by the list of tuples above a test and by square-bracket IDs in a verbose run.

Say it in an interview

A fixture is a function marked with pytest dot fixture that builds test data. A test gets it by naming it as a parameter, and pytest builds a fresh one for each test, so tests can't leak changes into each other. It beats copying set-up into every test because the set-up lives in one place.

To run one test against several inputs I use pytest dot mark dot parametrize with a list of input and expected-value pairs. pytest runs the function once per pair and reports each under its own ID, so I can still see exactly which case failed.

NumPy

NumPy arrays against Python lists

The page now leaves testing for NumPy, a library for working with numbers in bulk. It is taught against the lists of week 1, because the quickest way to see what an array is, is to do the same thing to a list and to an array and compare the results.

Installing NumPy and importing it

NumPy is a third-party library whose main object is the array, a container of values that all share one type and that supports arithmetic on every element at once. It installs and pins the same way pytest does: python -m pip install numpy==2.5.4, then the line numpy==2.5.4 added to requirements.txt so that a fresh clone gets it too. The import is always written the same way. import numpy as np is the convention the NumPy documentation uses throughout,15 so np.array, np.median and np.float64 in any codebase all mean NumPy, and a file that starts with that import is a file that works on arrays.

A list and an array side by side

Type these into the Python REPL one line at a time. The first three use a plain list of resolution hours; the rest build an array from the same list.

hours = [3.0, 30.0, 6.5]
hours * 2
hours + 1
import numpy as np
arr = np.array(hours)
arr * 2
arr + 1

hours * 2 shows [3.0, 30.0, 6.5, 3.0, 30.0, 6.5], because on a list * 2 repeats the sequence. hours + 1 raises TypeError: can only concatenate list (not "int") to list, because + on a list only joins another sequence.16 The array does arithmetic instead: arr * 2 shows array([ 6., 60., 13.]) and arr + 1 shows array([ 4. , 31. , 7.5]), because arithmetic between an array and a single number is applied to every element.15

That is vectorisation: one expression over the whole array, with no loop written by you. Doubling every hour in a list takes a for loop that builds a new list, and the same five characters, * 2, does something else. Moving between the two catches people out: code that was written for a list and is handed an array (or the other way round) often runs without an error and gives a different answer, so when a number looks wrong, the first question is which of the two you are holding.

dtype and shape

arr.dtype
arr.shape
arr.mean()

Continuing the same session, these show dtype('float64'), (3,) and np.float64(13.166666666666666). Every array has a dtype, the type of every element, and a shape tuple, such as (3,) for three elements in one dimension.17 Built from three floats, the array is float64 with shape (3,).18 A list has neither attribute; len(hours) is the closest it gets. mean() is a method of the array, and its result prints as np.float64(...), a NumPy number, which the next step comes back to. Arrays with rows and columns, reshaping and random numbers wait for week 6; this page stays in one dimension.

One type per array: the trade-off

An array holds one dtype, so np.array picks a type that can represent every value it is given: integers mixed with floats become floats, and anything mixed with a string becomes a string.18

np.array([3, 30, 6.5]).dtype
np.array([3, "30"]).dtype
counts = np.array([1, 2, 3])
counts[0] = 2.7
counts

The first line shows dtype('float64') and the second a string dtype. The last still shows an integer array: counts was created with integers, the array keeps its dtype, and so the 2.7 is converted to that type on the way in. That is the answer to the interview question about putting a float into an integer array. The fixed type is what makes whole-array arithmetic fast, and it takes away the list's freedom to mix types.18 In practice that means checking the dtype of any array you did not build yourself before trusting arithmetic on it; one stray string in the input turns the whole array into strings.

Say it in an interview

A NumPy array holds values of one fixed type, so arithmetic runs over the whole array in one expression instead of a Python loop. That fixed type is what makes it fast, and the price is that it can't mix types the way a list can.

On a list, times two repeats the list and plus one is a TypeError. On an array, times two doubles every element and plus one adds one to each. dtype is the element type and shape is the length in each dimension. If I put 2.7 into an integer array, the array keeps its dtype and the value is converted to that type.

NumPy

Vectorised comparisons, and testing arrays

Comparing arrays element by element

The desk needs two numbers for each closed ticket: how long it took, and how long it was allowed. The time taken comes from subtracting opened_at from closed_at, which gives a timedelta, then dividing total_seconds() by 3600. total_seconds() returns the whole duration as a float, unlike .seconds, which is only the seconds component,19 so a 30-hour ticket comes out as 30.0 hours instead of the 6 hours left over after a whole day. In a fresh REPL, with the two closed tickets of the desk's test data:

import numpy as np
hours = np.array([3.0, 30.0])
limits = np.array([4, 24])
late = hours > limits
late
hours[late]
late.sum()

late shows array([False, True]). Comparing two arrays of the same shape with > is an element-by-element operation, a ufunc in NumPy's terms, and it returns a boolean array.20 The first ticket took 3 hours against a 4-hour limit, the second 30 against 24. One comparison replaces a loop with an if inside it. The desk's stats.py defines a breach exactly this way: breached(desk) returns resolution_hours(desk) > sla_limits(desk), two arrays built by one loop each over the closed tickets and compared in a single line.

Boolean masks: filtering and counting without a loop

Indexing an array with a boolean array of the same shape keeps the elements where the boolean is True,21 so hours[late] shows array([30.]), the hours of the late tickets only, and hours[hours > 24] filters by a threshold with no loop. An array like late is called a mask. Summing a boolean array counts its True values, because booleans behave as the integers 0 and 1 in arithmetic,2223 so late.sum() shows np.int64(1): one breach. Filtering with a mask and counting with .sum() is the standard answer to "how do you filter an array without a loop?"

The limit is alignment. Element-wise work assumes position 0 in hours and position 0 in limits describe the same ticket. In stats.py both arrays come from the same loop over the same closed tickets, in the same order, which is what keeps them in step. Build them from two differently filtered lists and the comparison still runs, pairing one ticket's hours with another's limit.

Summary numbers and NumPy scalars

arr.mean() and arr.max() are array methods; np.median(arr) is a module-level function with no method form,24 so hours.median() fails with an AttributeError. What all three return is a NumPy scalar. hours.mean() returns an np.float64, and NumPy 2 prints such a scalar as np.float64(16.5) inside a dict or a list,25 so a summary built straight from these values prints as {'mean_hours': np.float64(16.5), 'breached': np.int64(1)}. There is a second reason to convert. An np.float64 inherits from Python's float, but NumPy's integer scalars do not inherit from int,26 so json.dumps accepts the mean and rejects the count with "Object of type int64 is not JSON serializable".27

summary = {
    "mean_hours": float(hours.mean()),
    "median_hours": float(np.median(hours)),
    "max_hours": float(hours.max()),
    "breached": int(late.sum()),
}
summary

Typed into the same session, this shows {'mean_hours': 16.5, 'median_hours': 16.5, 'max_hours': 30.0, 'breached': 1}, plain Python numbers that print cleanly and go into a JSON file without complaint. The desk's summary() is built the same way.

Testing an array with pytest

The first test most people write for an array is assert resolution_hours(sample_desk) == [3.0, 30.0], and it stops with an error instead of a red assertion: ValueError: The truth value of an array with more than one element is ambiguous. The == is element-wise too, so it produces array([ True, True]), and assert then needs one True or False from that; calling bool() on an array of more than one element raises ValueError because its truth value is ambiguous.17 These three tests ask the real questions instead:

def test_hours_array_is_float(sample_desk):
    hours = resolution_hours(sample_desk)
    assert hours.dtype == np.float64
    assert hours.shape == (2,)


def test_breach_mask(sample_desk):
    assert np.array_equal(breached(sample_desk), [False, True])


def test_summary_mean(sample_desk):
    assert summary(sample_desk)["mean_hours"] == pytest.approx(16.5)

The first checks type and size, the two properties from the previous step. numpy.array_equal returns a single True only when both arrays have the same shape and the same elements,28 so the second test gets one answer for the whole mask. The third compares a float within a tolerance: pytest.approx uses a relative tolerance of 1e-6 and an absolute tolerance of 1e-12 by default, so 0.1 + 0.2 == pytest.approx(0.3) passes.29 The sample desk's mean of 16.5 happens to be exact, so approx there is a habit; with real data it is what keeps the test from failing on the last digit. With the sample_desk fixture from the fixtures section, all three pass and the desk's suite reaches fourteen tests.

Say it in an interview

To filter an array without a loop I build a boolean mask with a comparison, like hours greater than 24, and index the array with it, so only the elements where the mask is True come back. Summing the mask counts the Trues, which is how I'd count tickets over their limit.

You can't just assert that an array equals a list, because equals compares element by element and assert can't turn several booleans into one answer. I check dtype and shape directly, use np.array_equal for whole arrays, and pytest.approx for floats.

Interview mindset

Interview mindset, part 1: reasoning aloud and checking your answer

Interview practice starts on a testing day because "how would you check that it works?" closes most junior coding questions, and answering it well uses the same skill as choosing unit tests. Part 2, with mock interview questions, comes in week 3.

How a junior technical interview runs

When you work through a small problem, the interviewer weighs how you reason aloud, whether you ask clarifying questions and whether you check your own answer, as much as the final code. A correct answer reached in silence tells them less than a nearly correct one whose reasoning they could follow, because the job they are hiring for is mostly working with other people on code that nobody fully understands yet.

You can recognise a strong candidate from the outside. They restate the problem, name an example input and its output, state a plan in a sentence or two, write the simple solution first, then check one normal case, an empty input and a boundary value. None of those moves needs a clever idea, so they can all be practised.

Thinking aloud on a small problem

Take "given a list of resolution hours, return the longest". Restate it: "So I get a list of floats and return the largest?" Agree an example: [3.0, 30.0, 6.5] gives 30.0. Give the plan: "Python's max does this; I'll use it, then check the edge cases." Thinking aloud costs time on a timed problem, so keep the plan to a sentence or two before you write code. Then ask the question that matters here: what should an empty list return?

def longest(hours):
    return max(hours, default=0.0)


print(longest([3.0, 30.0, 6.5]))
print(longest([]))

Run as a script, this prints 30.0 and then 0.0. max() raises ValueError on an empty iterable unless a default= value is given,30 so without it the second call stops with ValueError: max() iterable argument is empty. Whether 0.0, None or an error is right for an empty list is a decision for whoever owns the code, which is why you ask instead of guessing. Saying what you do not know works the same way. "I'm not sure whether median is an array method in NumPy; I'd check the docs, and for now I'll write np.median" is a good answer, because it shows where the gap is and how you would close it.

Checking your own answer

Check one normal case, an empty input and a boundary value. For a breach rule the boundary is a ticket that took exactly its limit: is a high ticket closed after exactly 4.0 hours a breach? With > it is not, and you say that you chose it on purpose. Those three checks are the unit tests you would write, and naming them before you are asked is what interviewers mean by thinking about edge cases.

Two limits are worth knowing when you check by hand. Comparing floats with == is fragile, because 0.1 + 0.2 == 0.3 is False in binary floating point;31 0.1 + 0.2 is 0.30000000000000004. When you check a computed mean, say what tolerance counts as equal, the way pytest.approx does with its defaults, which can be set explicitly with rel= and abs=.29 And assert belongs in tests. Python emits no code for assert statements when it runs with optimisation (python -O),32 so a function that must reject bad input raises an exception instead, the way the desk's Ticket raises ValueError for an unknown priority.

Say it in an interview

I'd start by restating the problem and agreeing one example input and output, then say my plan in a sentence and write the simplest version first. If I don't know something, I say so, say how I'd find out, and carry on with a stated assumption.

To check it works, I'd try a normal case, an empty input and a boundary value, the same cases I'd turn into unit tests. If the answer's a float I compare with a tolerance, because 0.1 plus 0.2 isn't exactly 0.3 in binary.

Check yourself

Check yourself

Ten retrieval questions, at least one for each section. Answer each out loud before you open it.

What separates a unit test, an integration test and an end-to-end test, and why does a healthy suite have the most unit tests?

A unit test checks one function on its own, an integration test checks several pieces together (the desk and its JSON file), and an end-to-end test drives the whole program as a user would. Unit tests are fast and point at one function when they fail, so most of the checking happens there; a suite weighted towards end-to-end tests is slow and every failure needs detective work.

A pull request shows 100% coverage. What does that prove, and what does it not?

It proves every line ran during the tests. It does not prove any assert checked what those lines produced, so the behaviour can still be wrong.

Name the three parts of test_high_deadline_is_four_hours, and say what match="urgent" adds to pytest.raises(ValueError, ...).

Arrange builds the opening time, act calls deadline, assert compares the result with 12:30. match makes the test pass only when the error message also matches, checked with re.search, so an unrelated ValueError inside the block does not count.

pytest says no tests ran, although you wrote three. Give two likely causes.

The file name does not match test_*.py or *_test.py, or the functions do not start with test. Running from the wrong folder, or in a terminal where .venv is not active, are the other usual suspects.

What does @pytest.fixture above def sample_desk(): do, and how does a test get the desk?

@name above a def is shorthand for f = name(f), so pytest receives the function and registers it as a fixture. A test names sample_desk as a parameter and pytest calls the fixture for it, fresh for every test; calling sample_desk() directly is an error.

Why does a parametrised test not hide which case failed?

pytest builds an ID from each parameter set, such as test_sla_hours[low-72], and reports every case separately, so the failing pair is named in the summary.

With hours = [3.0, 30.0, 6.5] and arr = np.array(hours), what do hours * 2, hours + 1 and arr * 2 give, and what are arr.dtype and arr.shape?

The list repeats to six elements, hours + 1 raises TypeError, and arr * 2 doubles every element. The dtype is float64 and the shape is (3,).

How do you count the tickets that breached their SLA without a loop, and why does the summary wrap the count in int(...)?

Compare the hours array with the limits array to get a boolean mask, then call .sum() on it, because True counts as 1. The result is an np.int64, which prints as np.int64(1) and which json.dumps rejects, so int(...) turns it into a plain Python integer.

Why does assert resolution_hours(desk) == [3.0, 30.0] raise a ValueError, and what do you write instead?

== on an array is element-wise, so it gives an array of booleans, and assert cannot get one truth value from an array of more than one element. Check dtype and shape directly, compare whole arrays with np.array_equal, and compare floats with pytest.approx.

In an interview you have written a function that returns the longest resolution time. Which three inputs do you check aloud, and what do you say about comparing floats?

A normal list, an empty list (where max() raises ValueError unless you give default=) and a boundary value. Floats are compared with a tolerance, because 0.1 + 0.2 == 0.3 is False in binary floating point.
