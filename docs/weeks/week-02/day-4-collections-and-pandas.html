Collections & pandas: counting, naming and tabulating the tickets

Week 2 · Day 4 Thu Oct 22, 2026 Python advanced ~36 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-15 · python 3.15 · pandas 3.0.6

This page assumes Wednesday's pytest tests and NumPy arrays, and Tuesday's tickets.json, the file in which the desk saves its tickets as a list of JSON objects. The first four sections cover the standard library's collections module: Counter for counting, namedtuple for read-only rows with field names, OrderedDict for a queue whose order you can change, and defaultdict, deque and ChainMap for grouping, two-ended queues and layered lookups. The last two sections cover pandas as a library of its own: a DataFrame loaded from a JSON file, then computed columns, missing values, counting and grouping. Afterwards you can explain when each container fits, say how a DataFrame differs from a list of dicts, and talk through groupby and NaN in an interview.

Collections

Counter: counting without the bookkeeping

The first question anyone asks of a ticket desk is how many tickets sit in each status. Python's standard library answers it with Counter, one of several container types in the collections module. This step starts with the loop that Counter replaces, because interviewers ask about both and because the loop explains what Counter is doing for you.

Counting by hand with a dict

A dict maps keys to values, so a count per status is a dict from each status to a number. The manual pattern walks the list, looks up the current count with get, which returns a default you supply when the key is missing, and stores that count plus one.2

statuses = ["closed", "assigned", "closed", "open", "closed", "assigned"]
counts = {}
for s in statuses:
    counts[s] = counts.get(s, 0) + 1
print(counts)
print(counts["escalated"])

Saved as a script and run, the first print shows {'closed': 3, 'assigned': 2, 'open': 1}, with the keys in the order they were first inserted.2 The second line stops the program with KeyError: 'escalated', because indexing a plain dict with a key it does not hold raises that error.2

The loop works, and it still turns up in older code and in code written by people who learned to count this way in another language. Its weakness is repetition. Every counting loop restates the same three ideas (start at zero, add one, guard the missing key), and the guard is the part that gets forgotten when someone writes counts[s] += 1 on a key that is not there yet.

Counter, a dict that counts

collections.Counter is a dict subclass for counting hashable objects. Elements are stored as the keys and their counts as the values.1 Passing an iterable, such as a list, to the constructor counts its elements, so the whole loop above becomes one call.1 A subclass is a class built on top of another, keeping everything the parent can do and adding to it, so anything you can do with a dict you can do with a Counter.

from collections import Counter

statuses = ["closed", "assigned", "closed", "open", "closed", "assigned"]
counts = Counter(statuses)
print(counts)
print(counts["escalated"])
print("escalated" in counts)
print(counts == {"closed": 3, "assigned": 2, "open": 1})

This prints four lines: Counter({'closed': 3, 'assigned': 2, 'open': 1}), then 0, then False, then True. Reading a missing key returns 0 instead of raising KeyError, and the read does not insert the key, which is why the membership test straight afterwards is still False.1 Because a Counter is a dict, comparing it with a plain dict compares the counts, and dict(counts) turns it back into an ordinary dict when other code expects one.1

That equality is what makes a Counter pleasant to test. An assertion such as assert status_counts(desk) == {"closed": 2, "assigned": 1, "open": 1} reads like the sentence it checks, and when it fails pytest prints both sides so you can see which status is off. In the ticket-desk code a new reports module gains exactly this kind of function: it loops over the desk, collects each ticket's status into a list and hands the list to Counter.

most_common, update and the arithmetic

Three methods carry most of the everyday use.

  • most_common(n) returns the n most common elements as (element, count) pairs, highest count first.1
  • update adds the counts from an iterable to the ones the Counter holds, where dict.update would replace each value.1
  • And elements() expands the counts back into repeated items.1
from collections import Counter

counts = Counter(["closed", "assigned", "closed", "open", "closed", "assigned"])
print(counts.most_common(1))
counts.update(["open", "open"])
print(counts["open"])

plain = {"open": 1}
plain.update({"open": 2})
print(plain["open"])

print(sorted(Counter(["b", "a", "a"]).elements()))

The output is [('closed', 3)], then 3, then 2, then ['a', 'a', 'b']. The Counter added two to the one open ticket it had; the plain dict threw its 1 away and kept the 2. Mixing those two meanings up is the most common Counter bug, and nothing fails when it happens; the numbers are just wrong.

A Counter has two limits. It accepts only hashable elements, so you cannot count a list of lists directly (step 4 explains what hashable means). And its + and - operators drop zero and negative counts from the result, so subtracting one day's closures from another day's totals quietly loses any status that falls to zero.1 When a zero needs to show in a report, read it with counts["status"] rather than expecting the key to be there.

You recognise a Counter in someone else's code by two shapes. One is Counter(item.status for item in items); the parentheses hold a generator expression, which works like a list comprehension without building the list and hands the statuses over one at a time. The other is counts.most_common(3) feeding a "top three" line in a report or a log message.

Takeaways
  • Counter is a dict subclass that counts hashable elements.
  • Reading a missing key neither raises an error nor inserts the key.
  • On a Counter, update adds to the counts; on a dict it replaces them.
Say it in an interview

Counter is a dict subclass from the collections module that counts hashable things. I pass it a list and it gives me each element with how many times it appears, so it replaces the loop where I'd call get with a default of zero and add one. most_common gives me the top few as pairs, highest first.

A Counter returns zero for a key it doesn't have instead of raising KeyError, and reading the key doesn't add it. The other difference from a dict is update: on a Counter it adds to the counts, on a dict it replaces the values.

Collections

namedtuple: rows whose fields have names

A report usually wants a flat, read-only record per ticket: its id, priority, status and how many hours it took to close. The desk's Ticket class carries far more than that, including methods, and a report has no business changing a ticket. A named tuple is the standard library's answer to "a small record whose fields have names and never change".

Why a plain tuple is not enough

A tuple is an ordered, fixed-length sequence written with parentheses, such as (4, "normal", "assigned", None). You read it by position, so row[2] is the status. That is fine inside three lines of code and a trap everywhere else. A reader has to remember that position 2 is the status, and if someone later inserts a field at the front, every row[2] in the codebase silently reads the wrong thing.

A tuple does have a property worth keeping, though. Its unpacking assigns each position to a name in one line, and that is the adjacent idea interviewers often connect to named tuples.

row = (4, "normal", "assigned", None)
ticket_id, priority, status, hours = row
print(status)
print(row[2] == status)

This prints assigned and then True. The number of names on the left must match the length of the tuple, or the line fails. A named tuple keeps both readings, by position and by unpacking, and adds a third: by name.

Defining and reading a named tuple

namedtuple(typename, field_names) returns a new tuple subclass whose fields can be reached by name as well as by index.1 The field names can be passed as a list of strings or as a single string separated by spaces or commas.1 The result is a class, so by convention it is assigned to a name in CapWords, the same spelling used for any other class.

from collections import namedtuple

TicketRow = namedtuple("TicketRow", ["ticket_id", "priority", "status", "hours"])
row = TicketRow(4, "normal", "assigned", None)
print(row)
print(row.status, row[1], len(row))
print(row._asdict())
print(TicketRow._fields)

The four lines of output are TicketRow(ticket_id=4, priority='normal', status='assigned', hours=None), then assigned normal 4, then {'ticket_id': 4, 'priority': 'normal', 'status': 'assigned', 'hours': None}, then ('ticket_id', 'priority', 'status', 'hours'). The printed form names every field, which makes log lines and pytest failure messages readable.

Because a named tuple is still a tuple, row[1] and len(row) work exactly as they would on the plain version.1 _asdict() returns the fields as a dict, and _fields lists the field names as a tuple of strings.1 The leading _ on these method names is there so they cannot collide with a field you name yourself; here it does not mean "private".

The ticket-desk code builds one TicketRow per ticket, with hours left as None while a ticket is still open, so a report can read row.status without touching the live Ticket objects.

Immutable rows and _replace

Named tuple instances are immutable: assigning to a field raises AttributeError. To "change" a field you call _replace with the new values as keyword arguments, and it returns a new instance with those fields swapped while the original stays as it was.1

from collections import namedtuple

TicketRow = namedtuple("TicketRow", ["ticket_id", "priority", "status", "hours"])
row = TicketRow(4, "normal", "assigned", None)
try:
    row.status = "closed"
except AttributeError:
    print("rows are read-only")
closed = row._replace(status="closed", hours=22.5)
print(closed.status, closed.hours)
print(row.status)

The output is rows are read-only, then closed 22.5, then assigned. The original row is unchanged, so a function that receives a row cannot change it behind the caller's back, and two parts of the program can share it safely.

Named tuple, dict, class or typing.NamedTuple

Instances of a named tuple have no per-instance dictionary, so each one takes the same memory as a plain tuple.1 A dict holding the same four values is mutable and bigger, and its keys are strings, so a typo like row["staus"] is only caught when that line runs.

A class is the right shape when the record has behaviour, such as the desk's Ticket with its deadline() method, or when its fields must change over time. A named tuple sits between them: a fixed set of named fields, no behaviour to speak of, and no changes after creation.

You will also meet the class-syntax version, typing.NamedTuple, which builds the same kind of type and adds a type annotation (a hint written after a colon saying what kind of value a field holds) to each field.3

from typing import NamedTuple

class TicketRow(NamedTuple):
    ticket_id: int
    priority: str
    status: str
    hours: float | None

print(TicketRow(6, "low", "open", None).priority)

This prints low. Newer codebases tend to prefer this spelling because editors and type checkers can read the annotations, while Point = namedtuple("Point", ["x", "y"]) followed by p.x is the older shape you will spot in existing code.

Takeaways
  • A named tuple is a tuple whose fields can also be read by name.
  • Changing a field means building a new row, not assigning to it.
  • Use a class when the record needs behaviour or changing fields.
Say it in an interview

A namedtuple is a tuple whose positions also have names. I'd use one over a plain tuple when the record has more than two or three fields, because row.status says what it is and row[2] doesn't. It's still a real tuple, so indexing and unpacking work, and it uses the same memory as a plain tuple.

It's immutable, so assigning to a field raises AttributeError. To change one, I call its replace method with the new value, which gives me a new row and leaves the old one alone. If the record needs methods or changing state, I'd write a class instead.

Collections

OrderedDict: when the order is part of the data

A support team works its queue in an order: the ticket whose deadline comes soonest goes first, and an escalated ticket jumps to the front. The order is part of the data, and the code has to be able to change it. That is the job OrderedDict still does well, even though plain dicts now keep their order too.

Plain dicts keep insertion order

OrderedDict is a dict subclass that remembers the order in which its keys were inserted.1 When it was added to the standard library that was a genuine difference, because plain dicts made no promise about order. Since Python 3.7, insertion order for plain dicts is a language guarantee: iterating a dict gives the keys in the order they were first added.2

So the old reason for OrderedDict is gone, and the first interview question about it is usually a version of "why does it still exist?"

The answer is that OrderedDict still differs in two ways: it has methods for reordering, and its equality checks care about order.1 If your code only needs to remember the order things arrived in, a plain dict is the better choice. Reach for OrderedDict when the code moves items to one end or takes them off the front, or when two mappings in a different order must count as different.

Building the order with sorted and key=

An ordered queue has to be built in the right order to start with, and the usual tool is sorted. sorted(iterable, key=...) returns a new list and leaves the input alone, and the key function is called once per element to produce the value that is compared.4 A lambda is a function written as a single expression with no name, which suits a key that is only used once.

from collections import OrderedDict

deadlines = {5: "2026-10-19 15:30", 4: "2026-10-17 15:00", 6: "2026-10-18 10:00"}
queue = OrderedDict()
for tid in sorted(deadlines, key=lambda t: deadlines[t]):
    queue[tid] = deadlines[tid]
print(list(queue))

This prints [4, 6, 5]: ticket 4's deadline is the earliest, so it went in first. Looping over a dict gives its keys, so sorted receives the ticket ids, and the lambda turns each id into its deadline for the comparison. The deadline strings are written year first, so their text order is their time order. In the ticket-desk code the key calls each live ticket's own deadline() method, and the queue holds the tickets that are still open or assigned, keyed by id.

move_to_end and popitem

OrderedDict adds move_to_end(key, last=True) and popitem(last=True), which reorder or remove at either end.1 With last=False, move_to_end moves a key to the front, and popitem removes and returns the first-inserted pair, which gives queue behaviour: first in, first out.1

from collections import OrderedDict

queue = OrderedDict()
queue[4] = "Invoice PDF is blank"
queue[6] = "Typo on the pricing page"
queue[5] = "Checkout fails on mobile"

queue.move_to_end(5, last=False)
print(list(queue))
print(queue.popitem(last=False))
print(list(queue))
queue.move_to_end(4)
print(list(queue))

The output is [5, 4, 6] after the escalation, then (5, 'Checkout fails on mobile') as the next ticket is taken off the front, then [4, 6], and finally [6, 4] because the default last=True sends ticket 4 to the back. A plain dict has no move_to_end, so you would have to rebuild the whole dict to escalate one ticket.

You will spot the same two calls in caching code. A least-recently-used (LRU) cache keeps a fixed number of recent results: each time an entry is read it is moved to the end with move_to_end, and when the cache is full the stalest entry comes off the front with popitem(last=False). When you see those calls side by side, the code is keeping something in "most recent last" order.

Equality and the cost of the extra features

Comparing two OrderedDict objects checks the order of their keys as well as the contents. Comparing an OrderedDict with a plain dict ignores order, the same way two plain dicts do.1

from collections import OrderedDict

a = OrderedDict([(4, "high"), (6, "low")])
b = OrderedDict([(6, "low"), (4, "high")])
print(a == b)
print(dict(a) == dict(b))
print(a == dict(b))

The three lines print False, True and True. That makes OrderedDict useful in a test that has to prove the order of a queue as well as its contents: an assertion against another OrderedDict fails if two tickets swap places.

The cost of the reordering methods is memory, since an OrderedDict uses more of it than a plain dict holding the same items.1 For a queue of a few hundred tickets that does not matter; for millions of small mappings it does, and it is one more reason the plain dict is the default.

Takeaways
  • Plain dicts keep insertion order, so OrderedDict is for reordering.
  • Moving a key to an end or popping from the front is what it adds.
  • Its equality checks key order, and it uses more memory.
Say it in an interview

Plain dicts have kept insertion order since Python 3.7, so I don't need OrderedDict just to remember order. It still earns its place when I need to reorder: move_to_end sends a key to either end, and popitem with last equals False takes the oldest entry off the front, which is how you'd build a simple queue or an LRU cache.

Equality is the other difference. Two OrderedDicts are only equal if their keys are in the same order, while comparing with a plain dict ignores order. It also uses more memory, so plain dict stays the default.

Collections

The rest of the collections module

Counter, namedtuple and OrderedDict are the three names most people learn first, and the module holds several more. Three of them come up often enough in real code and in interviews to learn properly: defaultdict, deque and ChainMap. Underneath all of the dict-based ones sits one rule about keys, which is worth understanding once.

defaultdict: a starting value on first use

Grouping is the other half of counting. Instead of "how many tickets does each agent hold?" the question is "which tickets does each agent hold?", and the answer is a dict from agent to a list of ticket ids. With a plain dict you have to create the empty list the first time you meet each agent.

assignments = [("Priya", 4), ("Marcus", 5), ("Priya", 7)]
groups = {}
for agent, tid in assignments:
    if agent not in groups:
        groups[agent] = []
    groups[agent].append(tid)
print(groups)

This prints {'Priya': [4, 7], 'Marcus': [5]}. A defaultdict removes the if: defaultdict(list) calls the factory you gave it, here list, to create a value the first time a missing key is used.1 That removes the need for the if key not in d check before appending.1

from collections import defaultdict

assignments = [("Priya", 4), ("Marcus", 5), ("Priya", 7)]
groups = defaultdict(list)
for agent, tid in assignments:
    groups[agent].append(tid)
print(dict(groups))
print(groups["Lee"])
print(len(groups))

The output is {'Priya': [4, 7], 'Marcus': [5]}, then [], then 3. That last number is the trap. A defaultdict inserts the key on every lookup of a missing key, including a lookup that was only meant to read, so asking about Lee added Lee.1

If you only want to check, use "Lee" in groups or groups.get("Lee"), which never call the factory. Compare that with Counter, whose missing-key read returns 0 and leaves the dict alone. In the ticket-desk code, a by_agent function builds exactly this kind of defaultdict(list) of ticket ids per assignee. You recognise the pattern on sight as groups = defaultdict(list) followed by groups[key].append(x) inside a loop.

Why keys must be hashable

A dict finds a key quickly by first turning it into a hash, an integer computed from the key's value, and using that number to jump to the right place instead of searching every entry. That only works if the value, and so the hash, can never change while the key sits in the dict. So dict keys must be hashable.2

Numbers, strings and tuples of them are hashable; lists and dicts can change after they are created, so they are not, and using one as a key fails with a TypeError. The same rule explains why a Counter accepts only hashable elements:1 each element becomes a key. To count pairs such as (agent, priority), put each pair in a tuple rather than a list.

deque: a queue with two fast ends

A list is fast to add to or remove from at its right end and slow at its left end. A deque (short for double-ended queue) gives O(1) appends and pops at both ends, where a list is O(n) at the left end.1 O(1) means the cost stays the same however long the sequence is, and O(n) means it grows in step with the length, because every remaining item of a list shifts one place when the first is removed.

A deque created with maxlen=n discards from the opposite end once it is full.1

from collections import deque

recent = deque(maxlen=3)
for tid in [1, 2, 3, 4]:
    recent.append(tid)
print(recent)
recent.appendleft(9)
print(recent)
print(recent.popleft())

This prints deque([2, 3, 4], maxlen=3), because ticket 1 fell off the left when ticket 4 arrived; then deque([9, 2, 3], maxlen=3), because adding on the left pushed 4 off the right; then 9. A "last N events" buffer like this is the most common place you will see one. Whenever code calls pop(0) on a long list in a loop, a deque with popleft() is the usual fix a reviewer suggests.

ChainMap, and finding the rest with dir

ChainMap groups several mappings into one view that is searched in order. Lookups try each mapping in turn, and writes always go to the first one.1 That fits layered settings: a team's overrides in front of the company defaults.

from collections import ChainMap

defaults = {"sla_hours": 24, "notify": "email"}
team = {"sla_hours": 8}
settings = ChainMap(team, defaults)
print(settings["sla_hours"], settings["notify"])
settings["notify"] = "chat"
print(team)
print(defaults)

The first line prints 8 email: the team value wins, and the missing notify falls through to the defaults. After the write, team is {'sla_hours': 8, 'notify': 'chat'} and defaults is unchanged.

To see everything a module offers, dir(module) lists the names it defines.5 In the REPL, import collections followed by dir(collections) shows:

  • ChainMap
  • Counter
  • OrderedDict
  • defaultdict
  • deque
  • and namedtuple among a longer list.
Takeaways
  • A defaultdict creates a starting value the first time a missing key is used.
  • Dict keys must be hashable, so lists and dicts cannot be keys.
  • A deque is fast at both ends; a ChainMap searches layered mappings in order.
Say it in an interview

I reach for defaultdict when I'm grouping, like a list of ticket ids per agent: I write groups of key dot append and never check whether the key exists. The catch is that even reading a missing key creates it, so to check membership I use in or get.

A list is slow to pop from the front because everything shifts along, so for a queue I use a deque, which is constant time at both ends. ChainMap is for layered lookups, like user settings in front of defaults: reads search each mapping in order and writes go to the first.

pandas

pandas: a DataFrame from a JSON file

The collections module works on Python objects one at a time: a loop builds a list of statuses, a Counter counts them, a namedtuple names the fields of each row. pandas is a separate library built for the moment your data is a table and you want to ask questions of whole columns at once. The desk saves its tickets to tickets.json as a list of JSON objects, one per ticket, and that file is already a table.

Installing and pinning pandas

pandas is not part of the standard library. It installs from PyPI with python -m pip install pandas, and by convention it is imported as import pandas as pd, so every example you read online writes pd. in front of its functions.6 A team pins the exact version in requirements.txt, with a line such as pandas==3.0.6, so that python -m pip install -r requirements.txt rebuilds the same environment on a fresh clone.78

python -m pip install pandas==3.0.6
python -m pip install -r requirements.txt
python -c "import pandas as pd; print(pd.__version__)"

Run inside the project's activated virtual environment, the first command installs that exact release, the second confirms every pinned line is satisfied, and the third prints 3.0.6. Pinning matters more for pandas than for a small tool, because a new major version can change what a function returns, and a teammate who installs a newer one gets different output from the same code without knowing why.

What a DataFrame is

A DataFrame is a two-dimensional, size-mutable, labelled table whose columns can hold different types.9 Two-dimensional means rows and columns. Labelled means each column has a name and each row has an index label, which is 0, 1, 2 and so on unless you choose otherwise. Size-mutable means you can add columns and rows after it is built. Each column is a Series, a labelled sequence of values of one type, and selecting one column with df["col"] gives you that Series.

The question interviewers ask here is how a DataFrame differs from a list of dicts. A list of dicts is organised by row: to get every status you loop over the rows and pull one key from each. A DataFrame is organised by column, with each column stored together and holding one type, so df["status"] is every status at once and an operation like a comparison applies to the whole column in one expression.

The columns also play the part that namedtuple fields played. list(df.columns) for the desk's table lists ticket_id, priority and status just as TicketRow._fields does, alongside the extra keys the JSON file carries.

read_json and datetime columns

pd.read_json(path) reads a JSON file into a DataFrame, and a JSON list of objects becomes one row per object, with the object keys as the columns.10 JSON itself has no date type, so dates travel through the file as text. pd.to_datetime converts such values to datetime64, the pandas date-and-time type that supports arithmetic.11 Four attributes describe a frame at a glance: df.head() shows the first rows, df.shape gives (rows, columns), df.dtypes gives each column's type, and df.columns holds the labels.9

import json
import pandas as pd

tickets = [
    {"ticket_id": 1, "priority": "high", "status": "closed",
     "opened_at": "2026-10-19T08:30:00", "closed_at": "2026-10-19T10:00:00"},
    {"ticket_id": 2, "priority": "normal", "status": "closed",
     "opened_at": "2026-10-16T09:15:00", "closed_at": "2026-10-18T16:00:00"},
    {"ticket_id": 6, "priority": "low", "status": "open",
     "opened_at": "2026-10-15T10:00:00", "closed_at": None},
]
with open("mini.json", "w") as f:
    json.dump(tickets, f)

df = pd.read_json("mini.json")
df["opened_at"] = pd.to_datetime(df["opened_at"])
df["closed_at"] = pd.to_datetime(df["closed_at"])
print(df.shape)
print(df)

The first line printed is (3, 5): three tickets, five keys. Then comes the table, with the index 0 to 2 down the left, one column per key, and the open ticket's closed_at shown as NaT, "not a time", because its JSON value was null. df.dtypes would report int64 for ticket_id and a datetime64 type for both date columns.

The ticket-desk code wraps these lines in a load_frame(path) function, so every report starts from the same typed table. Converting explicitly, rather than trusting whatever the reader guessed, means the function's result does not depend on how the dates happen to be spelled in the file.

Selecting columns and rows

Square brackets select. df["col"] returns a Series, while df[["a", "b"]], with a list inside the brackets, returns a DataFrame of those columns.12 Putting a boolean Series inside the brackets, as in df[df["priority"] == "high"], selects the rows where it is True, and df.loc[row, col] selects by label.12

print(df[["ticket_id", "status"]])
print(df[df["priority"] == "high"]["ticket_id"].tolist())
print(df[(df["priority"] == "normal") & (df["status"] == "closed")]["ticket_id"].tolist())
print(df.loc[2, "status"])

Added to the end of the script above, these print a two-column table of ids and statuses, then [1], then [2], then open. The comparison df["priority"] == "high" does not give a single True or False; it gives a Series of them, one per row, and the outer brackets keep the rows marked True. Two pitfalls live here.

  • df["status"] and df[["status"]] look almost the same and return different things, a Series and a one-column DataFrame.
  • And combining two conditions needs & with each condition in parentheses; Python's and cannot combine two whole columns.12
Takeaways
  • A DataFrame is organised by column; a list of dicts is organised by row.
  • pandas reads a JSON list of objects as one row per object.
  • Square brackets select columns, and a boolean Series selects rows.
Say it in an interview

A DataFrame is pandas' table: labelled rows and columns, where each column is a Series of one type. A list of dicts is organised by row, so I'd loop to get every status. A DataFrame is organised by column, so df of status gives me the whole column and I can compare or count it in one expression.

To select rows by a condition I put a boolean Series in the brackets, like df where priority equals high. For two conditions I use the ampersand with each one in parentheses, not the word and.

pandas

pandas: computed columns, missing values and groups

Loading a table is the easy half. Teams install a large library for the second half: deriving new columns, counting and grouping in one line each, and having missing values handled by rule instead of by an if in every loop. This step continues with the three-ticket df from step 5.

A computed column

Subtracting one datetime column from another gives a column of timedeltas, durations, and .dt.total_seconds() converts each one to a float number of seconds.11 The .dt part is an accessor: it reaches the date-and-time methods of the values inside a Series. Dividing by 3600 turns seconds into hours, and assigning to a new column name adds the column.

df["hours"] = (df["closed_at"] - df["opened_at"]).dt.total_seconds() / 3600
print(df[["ticket_id", "hours"]])
print(df["hours"].mean())

The table shows 1.50 for ticket 1, 54.75 for ticket 2 and NaN for ticket 6, and the mean prints 28.125, the average of the first two. There is no loop. The subtraction, the conversion and the division each run over the whole column, the same idea as the NumPy arrays of resolution hours, and the one expression replaces the per-ticket if t.closed_at is not None check that the rows function needed to leave hours as None.

NaN: the missing number

Ticket 6 is still open, so it has no closing time and no duration. In a numeric column pandas stores a missing value as NaN, "not a number", and mean() skips NaN by default.13 That is why the mean above is 28.125 and not something dragged towards zero or turned into an error. A column that holds NaN is a float column, which is why hours prints with decimals even for whole numbers.13

NaN has one behaviour that catches everyone once: NaN == NaN is False, so you cannot find missing values with ==.13 Use df["hours"].isna(), which returns a boolean Series you can filter with, and df[df["hours"].isna()] gives the open tickets.13

The follow-up interview question is usually "what do you do with missing values?", and the answer is "it depends what the gap means". Here a missing duration means "not closed yet", so skipping it in an average is right, while filling it with 0 would claim the ticket closed instantly.

value_counts where Counter was

Series.value_counts() returns the count of each distinct value, sorted by count from highest to lowest.14 Over the same column it yields the same numbers a Counter would, returned as a Series instead of a dict.14

from collections import Counter

table = df["status"].value_counts()
print(table)
print(table.to_dict() == dict(Counter(df["status"])))

The first print shows a small two-column listing headed status, with closed 2 and open 1, and a footer line Name: count, dtype: int64. The second prints True: the pandas counts and the Counter agree. The ticket-desk code turns this comparison into a test. It saves a known desk to a temporary JSON file, loads it into a frame, and asserts that the frame's status counts equal the Counter from the collections step, so if either function drifts the test goes red.

groupby: split, apply, combine

df.groupby(col)[other].mean() splits the rows into groups by the values in one column, applies an aggregation to another column within each group, and combines the results into one Series.15 Like mean() on a single column, the grouped mean() skips NaN by default.15

print(df.groupby("priority")["hours"].mean())

This prints one line per priority: high 1.50, low NaN and normal 54.75.15 The low group holds only the open ticket, so it has nothing to average and its result is NaN.

value_counts is the counting special case of the same idea: group by the column's values, count each group, sort by the count. In the ticket desk, defaultdict(list) did the split by hand; here the split, the aggregation and the combine are one chained expression. You recognise the pattern in analysis code as df.groupby("priority")["hours"].mean() or the same shape with sum or count.

Sorting, and when pandas is too much

df.sort_values("col", ascending=False) returns a new sorted frame and leaves the original unchanged.16 So df.sort_values("hours", ascending=False)["ticket_id"].tolist() gives [2, 1, 6], while df["ticket_id"].tolist() afterwards is still [1, 2, 6]. Forgetting to assign the result is the usual slip, because nothing fails; the frame simply stays in its old order.

The limit is size, in both directions. A DataFrame lives in memory, so a dataset larger than the machine's RAM needs a different approach, and pandas is a large dependency to install.17

For a handful of records, a Counter or a list of named tuples is lighter, starts faster and needs nothing from PyPI.17 The ticket desk uses both on purpose: the collections functions for the desk's own rules, the DataFrame for reports over the saved file, which Friday's page turns into a chart.

Takeaways
  • Column arithmetic runs over a whole column with no loop.
  • NaN marks a missing number; mean skips it and isna finds it.
  • value_counts and groupby replace hand-written counting and grouping.
Say it in an interview

groupby splits the rows by a key column, applies an aggregation like mean to each group, and combines the results into one Series, so average hours per priority is one line. value_counts is the counting version of the same thing: it groups by each value, counts, and sorts highest first.

A missing number in pandas is NaN, and mean skips it by default. NaN isn't equal to itself, so I find missing values with isna, and I decide what to do with them based on what the gap means rather than filling with zero.

Check yourself

Eight retrieval questions, at least one per section. Answer each out loud before you open it.

A Counter holds closed and open. What does counts["escalated"] return, and is "escalated" in the Counter afterwards?

It returns 0, where a plain dict would raise KeyError. Reading a missing key does not insert it, so "escalated" in counts is still False.

What is the difference between update on a Counter and update on a dict?

On a Counter, update adds the new counts to the ones it holds. On a plain dict it replaces each value, so the old number is lost.

Why use a namedtuple instead of a plain tuple, and how do you "change" a field?

Fields read by name, such as row.status, say what they are and survive a reordering, while row[2] depends on remembering positions. Fields cannot be reassigned, so row._replace(status="closed") returns a new row and leaves the original alone.

Plain dicts keep insertion order. Name two things OrderedDict still does that a plain dict does not.

It can reorder: move_to_end(key, last=False) moves a key to the front and popitem(last=False) removes the oldest entry. And its equality is order-sensitive when compared with another OrderedDict.

You check if groups["Lee"]: on a defaultdict(list). What side effect did that have, and what should you write instead?

The read created the key "Lee" with an empty list, so the dict grew. Use "Lee" in groups or groups.get("Lee"), which never call the factory.

Why is a deque a better queue than a list, and why can a list not be a dict key?

A deque appends and pops in constant time at both ends, while removing from the front of a list shifts every remaining item. A list can change after it is created, so it is not hashable, and dict keys must be hashable.

What is the difference between df["status"] and df[["status"]], and how do you select rows that are high priority and still open?

The first returns a Series, the second a one-column DataFrame. Rows matching two conditions need & with each condition in parentheses: df[(df["priority"] == "high") & (df["status"] == "open")].

An open ticket has NaN in the hours column. What does groupby("priority")["hours"].mean() do with it, and how do you find the open tickets?

The mean skips NaN by default, so the open ticket does not drag its group's average down; a group with only open tickets gets NaN as its result. Because NaN == NaN is false, find them with df[df["hours"].isna()].
