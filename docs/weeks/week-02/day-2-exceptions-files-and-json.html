Exceptions, files & JSON: code that fails clearly and remembers its data

Week 2 · Day 2 Tue Oct 20, 2026 Python advanced ~38 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-15 · python 3.15

This page assumes the ticket desk as the first day of week 2 left it: a desk module holding Ticket and Desk, imported by a script whose main() sets up logging. It teaches how Python reports errors and how to read a traceback, how to raise exceptions and handle them with try, except, else and finally, how to read, write, create and delete text files, and how to save objects as JSON and load them back. Afterwards you can explain what KeyError, ValueError and TypeError each mean, say what finally guarantees and why a bare except is a code smell, choose between the "w", "a" and "x" modes, and describe how a date survives a JSON round trip.

Errors

Errors and how to read a traceback

Every program meets bad input, missing files and plain typing mistakes. Python reports each of them in the same format, and reading that report quickly is the first skill this page builds, because every later section produces one on purpose.

What an exception is

An exception is an object Python creates when a line cannot do what it was asked to do, such as looking up a dictionary key that is not there. Python abandons that line and looks for code that has said it handles that kind of exception. If it finds none, the program stops and Python prints a traceback, the report of where things went wrong.

A raised exception that nothing handles ends the program with a non-zero exit status.1 The exit status is the number a program hands back to whatever started it, and a non-zero status marks the run as failed.

The word "error" is used loosely. Strictly, Python separates syntax errors, found while the file is being read, from exceptions, raised while the code runs.1 Most of this page is about the second kind, because those are the ones a program can respond to.

Reading a traceback from the bottom up

A traceback lists the chain of calls that led to the failure with the most recent call last, so the line you read first is the final one: it holds the exception's type and its message.1 Each pair of lines above it names a file, a line number and the function that was running, and shows the source line.

You read upward until you reach a line in a file you wrote, which is usually where the bad value came from. python -c runs the quoted text as a one-line program, which makes it handy for trying a single expression against the desk module the ticket-desk code was split into:

python -c "from desk import SLA_HOURS; SLA_HOURS['urgent']"

The output is a five-line traceback:

Traceback (most recent call last):
  File "<string>", line 1, in <module>
    from desk import SLA_HOURS; SLA_HOURS['urgent']
                                ~~~~~~~~~^^^^^^^^^^
KeyError: 'urgent'

The last line says KeyError: 'urgent'. SLA_HOURS maps the priorities high, normal and low to hours, and urgent is not one of its keys. File "<string>" appears because the code came from -c; in a real script that line names the file and the function, as in File "desk.py", line 12, in <module>, and the row of ~ and ^ marks the part of the line that failed. In a bug report or a chat message, that last line is the first thing a teammate asks you to paste.

KeyError, ValueError and TypeError

Three built-in exceptions turn up most often, and each has a precise meaning.

  • A KeyError is raised when a mapping (a dictionary) is asked for a key it does not hold.2
  • A ValueError is raised when an argument has the right type but an unacceptable value; int("TD-7") is the classic case, because int() accepts a string and this string does not spell a number.2
  • A TypeError is raised when an operation is applied to the wrong type altogether, as in len(5): a whole number has no length.2
python -c "int('TD-7')"
python -c "len(5)"

The first command ends with ValueError: invalid literal for int() with base 10: 'TD-7' and the second with TypeError: object of type 'int' has no len(). Telling the three apart is a quick diagnosis. A KeyError points at the data, a missing entry. A ValueError points at the content of a value. A TypeError usually means the code passed the wrong kind of thing, such as a number where a list was expected.

SyntaxError: the error found before anything runs

Python reads and parses the whole file before it runs any of it, and a SyntaxError is raised during that reading, so not a single line has run when you see it.1 Leave the colon off a function definition and the report shows the file, the line and a caret under the spot where the parser gave up:1

  File "ticket_desk.py", line 8
    def main()
              ^
SyntaxError: expected ':'

There is no list of calls above it, because no call was running. For the same reason, a try statement in the same file cannot catch the error: it is found before the program starts, so that statement never begins to run.1 The only fix is to correct the source.

The exception hierarchy

Exception types are classes arranged in a family tree. BaseException sits at the top, and Exception under it is the parent of nearly every error a program should handle. KeyboardInterrupt, raised when you press Ctrl+C, and SystemExit sit beside Exception rather than under it.2

OSError groups failures reported by the operating system, and FileNotFoundError and FileExistsError are both its subclasses.2 The tree decides what a handler matches: a handler written for a parent type also catches every child, which is why the next step insists on naming the narrowest type you can deal with.

Takeaways
  • An exception is an object Python creates when a line cannot do its job; unhandled, it stops the program.
  • Read a traceback from the last line upward to the first line in your own code.
  • A KeyError is a missing key, a ValueError a bad value, and a TypeError the wrong type.
  • A SyntaxError is found before anything runs, so a try statement cannot catch it.
Say it in an interview

I read a traceback from the bottom. The last line gives me the exception type and the message, and the lines above are the calls that led there, most recent last, so I walk up until I reach a line in my own code.

A KeyError means a dictionary lookup used a key that isn't there. A ValueError means the type was right but the value wasn't usable, like turning the text TD-7 into an integer. A TypeError means the operation doesn't work on that type at all, like asking a number for its length.

A SyntaxError is found while Python parses the file, before any line runs, so a try in that same file never even starts. Exceptions raised while the program runs are the ones try can catch.

Exception handling

Raising and handling exceptions with try and except

Exception handling has two halves. Code that finds a problem raises an exception, and code that can do something about the problem catches it. They are often in different files, written by different people.

Raising an exception yourself

The raise statement takes an exception instance, stops the current function at once and unwinds through the callers until it reaches the nearest handler for that type.3 Here is the ticket-desk rule that a priority must be one of the known ones, cut down so it runs on its own:

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}


class Ticket:
    """One support ticket."""
    def __init__(self, ticket_id, title, priority):
        if priority not in SLA_HOURS:
            raise ValueError(f"unknown priority: {priority!r}")
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority


Ticket(7, "Refund charged twice", "urgent")

Run as a file, this ends with a traceback whose last line is ValueError: unknown priority: 'urgent', quotes included, which shows exactly what value arrived. The three assignments below the check never run. ValueError is the right type to raise because the argument is a string, as it should be, and only its value is wrong.2

Validating at the boundary

Putting the check at the very top of __init__ is a design decision with a name: validate at the boundary. If the constructor refuses bad input, no invalid Ticket ever exists, so no other method has to wonder whether self.priority is usable.

The pattern is an if guard followed by raise ValueError(...) as the first lines of a constructor or a public function. Raise when your code is handed something it cannot work with and the caller is better placed to decide what happens next. Code that silently "fixes" bad input, say by quietly treating urgent as high, hides the mistake from the person who made it.

try and except

A try statement runs its body. If the body raises an exception that matches an except clause, that clause runs; the first matching clause wins and the rest are skipped.1 except ValueError as err binds the exception object to the name err, and only inside that clause.4 One clause can name a tuple, except (KeyError, ValueError):, to catch either type.1 A handler often logs the problem and carries on, and Logger.error records an ERROR-level message without stopping the program.5

import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
log = logging.getLogger(__name__)


def parse_id(text):
    try:
        number = int(text)
    except ValueError as err:
        log.error("rejected id: %s", err)
        return None
    else:
        log.info("accepted id %s", number)
        return number
    finally:
        log.info("parse done")


print(parse_id("7"))
print(parse_id("TD-7"))

The first call logs INFO __main__: accepted id 7, then INFO __main__: parse done, then prints 7. The second logs ERROR __main__: rejected id: invalid literal for int() with base 10: 'TD-7', then parse done, then prints None. The second call returns None and the script carries on to its next line.

else and finally

The else clause runs only when the try body raised nothing, and the finally clause runs on every path, whether or not an exception occurred and even if a handler itself raises.1 In the example, parse done is logged before each return completes.

That guarantee is what finally is for: closing, releasing or logging "done" whatever happened. else answers a subtler need. Keep only the risky line inside try and put the follow-up work in else, so a ValueError raised by the follow-up code is never mistaken for the one you meant to handle.

The ticket desk uses the same four-part shape around adding a ticket: a rejected ticket is logged as an error, an accepted one as information, and "intake done" is logged either way.

Catch narrow: the bare except problem

A bare except: with no type catches everything, including KeyboardInterrupt and SystemExit, so Ctrl+C stops working inside it; name the type you expect.1 except Exception is narrower, because those two sit outside Exception in the hierarchy,2 but it still catches errors from bugs in the code along with the one you meant. A handler that is too wide hides real bugs, so catch the narrowest type the code can actually recover from.1

Takeaways
  • Raise when your code is handed something it cannot use and the caller can decide what happens next.
  • The first matching except clause runs, and finally runs on every path.
  • A bare except hides real bugs, so catch the narrowest type the code can recover from.
Say it in an interview

I raise an exception when my code is handed something it can't work with and the caller is better placed to decide what to do. A constructor is the usual place: if the priority isn't one we know, I raise a ValueError before the object exists, so no invalid ticket is ever created.

The try body runs first. If it raises, the first matching except clause runs; if it doesn't, else runs. finally runs last on every path, even when a handler raises again, so that's where cleanup goes.

A bare except catches everything, including Ctrl+C and SystemExit, so it hides real bugs. I name the narrowest exception I can actually recover from, and I log it rather than pass.

Files

Opening and reading files

A program that forgets everything when it stops is not much use. Files are the simplest way to keep data between runs, and the ticket-desk code gains a storage module whose first job is reading a text file.

open(), file objects and the with statement

open() returns a file object, and in text mode that object converts the bytes on disk into Python strings using an encoding.6 A file you open has to be closed again, and the reliable way to do that is a with statement: the file is closed when the block ends, even if an exception is raised inside it.7

An object that sets something up on entry to a with block and cleans it up on exit is called a context manager, and an open file is the one you will meet most.

def read_lines(path):
    """Return the lines of a text file without their line endings."""
    with open(path, encoding="utf-8") as f:
        return f.read().splitlines()


print(read_lines("requirements.txt"))
print(read_lines("missing.txt"))

With a requirements.txt holding the single line pylint==4.0.0, the first call prints ['pylint==4.0.0']. The second ends the program with a traceback whose last line is FileNotFoundError: [Errno 2] No such file or directory: 'missing.txt'. FileNotFoundError is a subclass of OSError,2 and it is the error the JSON storage later on this page handles on purpose. The return sits inside the with block, and the file is still closed on the way out.

Text mode and the encoding argument

The default mode is "r", read text, so open(path) with no mode reads text.6 Adding b to the mode, as in "rb", opens the file in binary mode, which returns raw bytes with no decoding; images and other non-text files are read that way.6

Text mode needs an encoding to turn bytes into characters, and when you leave the encoding argument out, Python uses a default that depends on the platform.6 Reviewers look for this: without encoding="utf-8", the same code can read the same file differently on a Windows laptop and on a Linux server, and a title such as "Zoë can't log in" comes back garbled on one of them.

You will see with open(path, encoding="utf-8") as f: in nearly every codebase that handles text files.

Reading the whole file, or one line at a time

f.read() returns the whole content as one string, and f.readline() returns the next single line.7 str.splitlines() then splits text at line boundaries and drops the line endings, unlike readlines(), which keeps them.8 It also gives no empty last item when the text ends with a newline,8 which is where it differs from splitting on "\n":

text = "high\nnormal\n"
print(text.split("\n"))
print(text.splitlines())

The first line prints ['high', 'normal', ''], with a stray empty string at the end, and the second prints ['high', 'normal']. Text files written by programs nearly always end in a newline, so splitlines() is the one to reach for, and return f.read().splitlines() is a line you will recognise in other people's code.

The limit of read() is memory: it loads the entire file at once, which is fine for a small file and wrong for one of several gigabytes.7 Looping over the file object itself yields one line at a time, each still ending in its newline, so memory use stays flat however long the file is:7

with open("requirements.txt", encoding="utf-8") as f:
    for line in f:
        print(line, end="")

This prints pylint==4.0.0 once. The end="" stops print adding a second newline after the one the line already carries.7

Relative paths and the working directory

A path such as "requirements.txt" is relative, and a relative path is resolved against the current working directory,6 the folder your terminal was in when you started Python, which is not necessarily the folder that holds the script. Start the ticket desk from its parent folder and the same open("requirements.txt") looks in the parent, then reports FileNotFoundError for a file you can see in your editor. When that happens, check where the terminal is before you check the code.

Takeaways
  • A with block closes the file when the block ends, even if an exception is raised inside it.
  • Name the encoding, because the default depends on the platform.
  • read() loads the whole file at once; looping over the file object reads one line at a time.
  • A relative path is resolved against the working directory, not the script's folder.
Say it in an interview

I open files in a with block because it closes the file when the block ends, even if an exception is raised inside it. Without it, an error between opening and closing leaves the file open.

Text mode decodes the bytes into strings using an encoding, and binary mode hands me the raw bytes. I always pass encoding utf-8, because the default depends on the operating system, so the same file could read differently on a teammate's machine or on the server.

read gives me the whole file as one string, which is fine for small files. For a very large one I loop over the file object, which reads one line at a time and keeps memory flat.

Files

Writing, appending and creating files

Writing uses the same open() and the same with block as reading. What changes is the mode string, and choosing the wrong one is the most common way to lose data in a file.

Three modes for writing: w, a and x

  • Mode "w" creates the file if it is absent and empties it if it is present.
  • Mode "a" also creates a missing file, but writes at the end of an existing one.
  • Mode "x" creates the file and raises FileExistsError if it already exists.6

The detail that catches people out is when "w" empties the file: at the moment it is opened, before a single character is written.6 Open a file with "w" intending to add to it, and the old content is already gone.

The ticket desk writes its board as a plain text file, one tab-separated line per ticket, and then appends a closing line. Cut down to run on its own:

def export_board(rows, path):
    """Write one tab-separated line per row, replacing the file."""
    with open(path, "w", encoding="utf-8") as f:
        for row in rows:
            f.write("\t".join(row) + "\n")


def append_line(path, text):
    """Add one line to the end of a file."""
    with open(path, "a", encoding="utf-8") as f:
        f.write(text + "\n")


rows = [["1", "Login page returns 500", "high", "closed"],
        ["6", "Typo on the pricing page", "low", "open"]]
export_board(rows, "board.txt")
append_line("board.txt", "end of shift")
with open("board.txt", encoding="utf-8") as f:
    print(f.read().splitlines())

It prints ['1\tLogin page returns 500\thigh\tclosed', '6\tTypo on the pricing page\tlow\topen', 'end of shift'], where each \t is a real tab in the file. Run it a second time and the output is identical, three lines and no more, because "w" wiped the board before rewriting it and the append then added one line to a fresh file. "\t".join(row) builds one line from a list of strings, and every item must be a string, which is why the desk's version wraps the ticket number in str().9 An append looks like with open(path, "a", encoding="utf-8") as f: followed by f.write(text + "\n").

Mode "x" is the guard for the opposite risk, overwriting a file someone wanted to keep:

with open("shift-notes.txt", "x", encoding="utf-8") as f:
    f.write("first shift\n")

The first run creates shift-notes.txt. The second ends with FileExistsError: [Errno 17] File exists: 'shift-notes.txt', another member of the OSError family,2 and the file keeps its content. Use "x" when creating the file must never destroy an existing one, and "w" when replacing it is the whole point, as with a board that is regenerated on every run.

write() adds exactly what you give it

f.write() writes exactly the string it is given and returns the number of characters written.7 It adds no newline, unlike print, so forgetting the + "\n" runs every line into the next one.

with open("note.txt", "w", encoding="utf-8") as f:
    print(f.write("end of shift"))
    print(f.write("\n"))

This prints 12 and then 1: twelve characters for the text and one for the newline. The return value is rarely used in scripts, but in the interactive prompt it is echoed after every write, which puzzles people the first time.

Buffering, and why the file has to close

Writes are buffered. Text passed to write() can wait in memory and reach the disk in larger pieces, instead of going to the disk on every call.6 The cost is that a file written without with or f.close() might not be completely written to disk, even when the program exits normally.7 Closing the file pushes out whatever is still buffered, and that is the second reason, after error safety, that file code lives inside a with block.

Takeaways
  • Mode w empties the file when it is opened, a adds to the end, and x refuses to overwrite.
  • The write method adds no newline and returns the number of characters written.
  • Writes are buffered, so closing the file pushes the rest out to disk.
Say it in an interview

"w" creates the file or empties it the moment it's opened, "a" creates it or adds to the end, and "x" creates it but fails with FileExistsError if it's already there. So I use "a" for logs, "w" for a file I regenerate every time, and "x" when I must never overwrite anything.

write doesn't add a newline. It writes exactly the string I give it and returns how many characters it wrote, so I add the newline myself, and I write inside a with block so the buffer is flushed when the file closes.

Files

Deleting files safely

Deleting a file is one call. Doing it safely is mostly about what happens when the file is not there, and that brings exceptions back into the picture.

Path.unlink() and os.remove()

The pathlib module wraps a filesystem path in a Path object with methods such as unlink.10 Path.unlink() deletes a file or a symbolic link (a small file that points at another path), and raises FileNotFoundError if there is nothing to delete.10 The ticket desk's version turns that error into a yes-or-no answer:

from pathlib import Path


def delete_file(path):
    """Delete a file and say whether there was one to delete."""
    try:
        Path(path).unlink()
    except FileNotFoundError:
        return False
    else:
        return True


with open("board.txt", "w", encoding="utf-8") as f:
    f.write("end of shift\n")
print(delete_file("board.txt"), delete_file("board.txt"))

This prints True False. The first call deletes the file the with block just created; the second finds nothing, catches the FileNotFoundError and reports it as False instead of crashing. The try, except FileNotFoundError: return False shape is what a safe delete looks like in someone else's code.

There are two variations you will meet. Path(path).unlink(missing_ok=True) ignores a missing file in one line,10 which suits a cleanup step that does not care, at the price of never knowing whether anything was deleted.

Older code uses os.remove(path), which does the same job on a plain string path.11 Both have the same limit: unlink removes only files and links, and a directory needs Path.rmdir() instead,10 while os.remove() raises FileNotFoundError for a missing path and IsADirectoryError when the path is a directory.11 Code that deletes is worth a second look in review, because a wrong path deletes the wrong thing and there is no undo.

Look before you leap, or ask forgiveness

The alternative is to check first:

from pathlib import Path

path = "board.txt"
if Path(path).exists():
    Path(path).unlink()

The script prints nothing. It deletes board.txt only if the file exists at the moment it is checked.

This style is called LBYL, look before you leap. It reads well and it has a gap. Between the check and the delete, another program, a second copy of your script or a cleanup job can remove the file, and then unlink() raises FileNotFoundError anyway, the very error the check was meant to prevent. The check makes the failure rarer without making it impossible, and a rare failure is harder to reproduce than a frequent one.

The other style is EAFP, easier to ask forgiveness than permission: try the operation and handle the failure, which is what delete_file does. Python code leans towards EAFP because the operation itself is the only reliable test of whether it can succeed, and the try statement makes the failure path explicit.

LBYL still has its place where the check is cheap and nothing else can change the answer in between, such as testing whether a dictionary holds a key before reading it. Files live on a disk other processes share, so for files EAFP is the safer habit.

Takeaways
  • Unlink deletes a file and raises FileNotFoundError when there is nothing to delete.
  • Checking first, called LBYL, leaves a gap in which another program can remove the file.
  • Trying the operation and handling the failure, called EAFP, is the safer habit for files.
Say it in an interview

I delete a file with Path.unlink from pathlib, or os.remove on a plain string path. If the file doesn't exist both raise FileNotFoundError, so I catch it, or pass missing_ok when I genuinely don't care. A directory needs rmdir instead.

I'd rather try the delete and handle FileNotFoundError than check first. Another process can remove the file between my check and my delete, so the check doesn't make the delete safe. That's EAFP, the usual Python style.

JSON

JSON: saving structured data and reading it back

A tab-separated board is fine for a person to read, but turning it back into tickets would mean splitting strings and guessing types. JSON stores the structure along with the values, which is why the ticket desk saves its tickets as tickets.json.

What JSON is and how Python values map to it

JSON is a text format for structured data: objects in braces with string keys, arrays in square brackets, strings, numbers, true, false and null. Python's json module converts in both directions: a dict becomes an object, a list an array, None becomes null and True becomes true.12 The mapping is not symmetric, and tuples come back as lists:12

import json

record = {"ticket_id": 4, "assignee": None, "tags": ("billing", "pdf"), "urgent": False}
text = json.dumps(record)
print(text)
print(json.loads(text))

The first print shows the JSON text, {"ticket_id": 4, "assignee": null, "tags": ["billing", "pdf"], "urgent": false}, with null, false and square brackets. The second shows the Python dict rebuilt from it, {'ticket_id': 4, 'assignee': None, 'tags': ['billing', 'pdf'], 'urgent': False}, where tags is now a list.

dump and dumps, load and loads

json.dump(obj, f) writes JSON to a file object and json.dumps(obj) returns it as a string; json.load(f) and json.loads(text) are the same pair for reading.12 The trailing s stands for string, and mixing the two up is one of the most common slips with this module. indent=2 pretty-prints the output, one value per line, which makes a committed JSON file readable when a reviewer looks at a diff.12

import json

records = [{"ticket_id": 6, "title": "Typo on the pricing page", "closed_at": None}]
with open("tickets.json", "w", encoding="utf-8") as f:
    json.dump(records, f, indent=2)
with open("tickets.json", encoding="utf-8") as f:
    print(json.load(f) == records)

This prints True, and tickets.json now holds the list spread over several lines:

[
  {
    "ticket_id": 6,
    "title": "Typo on the pricing page",
    "closed_at": null
  }
]

In other people's code you will recognise this as json.dump(records, f, indent=2) inside a with open(path, "w", encoding="utf-8") block, and the file by a line such as "closed_at": null.

Dates travel as ISO 8601 text

JSON has no date type, and json.dumps raises TypeError for any object it has no JSON type for, a datetime included.12 Passing {"opened_at": datetime(2026, 10, 19, 8, 30)} to it fails with TypeError: Object of type datetime is not JSON serializable. The fix is to store the date as ISO 8601 text, the international format that reads like 2026-10-19T08:30:00. isoformat() produces that text and datetime.fromisoformat() reads it back:13

from datetime import datetime

opened = datetime(2026, 10, 19, 8, 30)
text = opened.isoformat()
print(text)
print(datetime.fromisoformat(text) == opened)

The output is 2026-10-19T08:30:00, then True. ISO text has a second advantage: written year first, it sorts into date order as plain text. The ticket desk wraps this in two small functions.

  • to_record turns a Ticket into a dict of plain values whose keys are exactly its attribute names:
    • ticket_id
    • title
    • priority
    • status
    • assignee
    • opened_at and closed_at
    With each date as ISO text and closed_at left as None while the ticket is open.
  • from_record does the reverse, building a Ticket and restoring its dates with fromisoformat.

Saving the desk becomes a loop of to_record calls followed by one json.dump.

Round trips: how a storage layer is checked

Converting an object in memory into text or bytes that can be stored or sent is called serialization, and rebuilding it is deserialization. The property that matters is the round trip: save, then load, and you must get back something equal to what you saved.

The == records line above is that check in its smallest form. It is also where the limits show. A tuple saved and loaded comes back as a list, and a date comes back as a string unless your loading code converts it, so a round trip is only exact when you design the record format for it.12

That is why the desk converts tickets to records of plain values and ISO dates before saving: every field then survives the trip. Turning such round trips into automated tests is the next day's topic.

Takeaways
  • JSON stores structure along with values, but tuples come back as lists and dates need converting.
  • The functions with an s work on strings; the ones without it work on file objects.
  • Store dates as ISO text so a saved and loaded record comes back equal.
Say it in an interview

dump writes JSON to an open file object and dumps returns it as a string; load and loads are the same pair for reading. The s stands for string.

JSON only has objects, arrays, strings, numbers, true, false and null. A datetime or a custom object makes dumps raise a TypeError, so I convert to a dict of plain values first, and I remember that tuples come back as lists.

JSON has no date type, so I store dates as ISO 8601 text with isoformat, and when I load I call datetime.fromisoformat to get a real datetime back. Then save followed by load gives me an equal object, which is the round trip I test.

JSON

When the JSON file is missing or corrupt

Loading is where files and exceptions meet. The file may not exist yet, or someone may have edited it by hand and broken it, and the two cases need different handling.

Here is the ticket desk's loader. It is an excerpt of the storage module and does not run on its own: the module above it imports json and defines log, the module's logger, and it brings in Desk and from_record, the pieces described in the previous step.

def load_desk(path):
    """Read a JSON file into a new desk, or return an empty desk if there is none."""
    try:
        with open(path, encoding="utf-8") as f:
            records = json.load(f)
    except FileNotFoundError:
        return Desk()
    except json.JSONDecodeError as err:
        log.error("cannot read %s: %s", path, err)
        raise ValueError(f"{path} is not valid JSON") from err
    desk = Desk()
    for record in records:
        desk.add(from_record(record))
    return desk

The run further down this step shows what it prints on a corrupt file.

A missing file is a normal first run

The first time the program runs there is no tickets.json, and open() raises FileNotFoundError.2 That is an expected situation, so the loader handles it by returning an empty Desk. The calling code checks for an empty desk, seeds the six sample tickets, and saves at the end of the run; on the second run the file exists, the six tickets are loaded and nothing is seeded again.

Only the risky part, opening and parsing, sits inside try, and the loop that rebuilds tickets runs after it, so an error in from_record is never mistaken for a file problem.

A corrupt file raises JSONDecodeError

Delete the final ] from tickets.json by hand and json.load raises json.JSONDecodeError, a subclass of ValueError that carries the message and the line and column where parsing failed.12 Without the second except clause, the traceback runs through several frames inside Python's own json package and ends with json.decoder.JSONDecodeError: Expecting ',' delimiter: line 56 column 1 (char 1279).

Read bottom-up as usual: the last line says the parser expected a comma on line 56, one line past the last }, which is where it noticed the list had not been closed. Walking up, the lowest frame in a file you wrote is the json.load(f) line in load_desk.

Because JSONDecodeError is a ValueError, the hierarchy from the first step applies. The first matching except clause wins,1 so a clause for plain ValueError placed above it would catch the decode error first.

Raising a clearer error with from

The second clause logs the problem and raises a new exception. raise ... from err records err as the direct cause of the new exception, stored in its __cause__ attribute, and the traceback prints both, joined by the line "The above exception was the direct cause of the following exception".3

Without from, an exception raised inside an except clause is still chained, implicitly. The handled exception lands in the new one's __context__ attribute and the traceback joins them with "During handling of the above exception, another exception occurred", which reads like a second bug in the handler. from sets __cause__ and states the link was intended.3

Shortened, a run on the damaged file prints:

ERROR storage: cannot read tickets.json: Expecting ',' delimiter: line 56 column 1 (char 1279)
Traceback (most recent call last):
  ...
json.decoder.JSONDecodeError: Expecting ',' delimiter: line 56 column 1 (char 1279)

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
ValueError: tickets.json is not valid JSON

The person running the program gets a last line that names the file they need to fix, and whoever debugs it still sees the exact line and column above. Catching JSONDecodeError and quietly returning an empty desk would be worse than crashing here: the calling code would see an empty desk, seed it and save, overwriting the damaged file, the only copy someone could have repaired by hand.

Every save rewrites the whole file

The save side has its own limit. Saving opens the file with "w", which empties it the moment it is opened, so every save rewrites the whole file.6 For a desk of a few hundred tickets that is quick and simple. It also means a program killed halfway through a save leaves a partial file, which the next load reports as exactly the JSONDecodeError above.

A single JSON file suits one program and modest data. Two programs saving at once can overwrite or corrupt each other's work, which is the reason databases exist; week 3 introduces one.

Takeaways
  • A missing file on the first run is expected, so the loader returns an empty desk.
  • A corrupt file raises JSONDecodeError, which the loader logs and raises again as a ValueError naming the file.
  • Returning an empty desk for a corrupt file would let the next save overwrite the only copy.
Say it in an interview

A missing file on the first run is normal, so I catch FileNotFoundError and start with an empty collection. A corrupt file isn't normal: I catch JSONDecodeError, log it, and raise a ValueError that names the file, using raise from.

raise from stores the original exception as the new one's cause, in dunder cause, and the traceback says "the above exception was the direct cause". Without from, the link goes in dunder context and reads "during handling of the above exception", which looks like an accident.

I don't swallow a decode error by returning empty data, because the next save would overwrite the broken file, and that file was the only thing anyone could have repaired.

Check yourself

Check yourself

Nine retrieval questions, at least one per section. Answer each out loud before you open it.

A traceback ends with KeyError: 'urgent'. What does that mean, and where do you look next?

A dictionary was asked for the key 'urgent' and does not hold it. Walk up the traceback from that last line to the lowest frame in a file you wrote, which is where the lookup was made.

What separates a ValueError from a TypeError? Give an example of each.

A ValueError means the type was right but the value was unusable, as in int("TD-7"). A TypeError means the operation does not apply to that type at all, as in len(5).

Why can a try statement not catch a missing colon in the same file?

A missing colon is a SyntaxError, raised while Python parses the file before any line runs. The try statement itself never starts, so it has nothing to catch with.

In a try with except, else and finally, which clauses run when the body raises a caught ValueError, and which when it raises nothing?

With the caught error, the matching except runs and then finally. With no error, else runs and then finally. finally runs on every path.

Why does a reviewer reject except: pass?

A bare except catches everything, including KeyboardInterrupt and SystemExit, so Ctrl+C stops working and real bugs vanish without a trace. Name the narrowest type the code can recover from and log it.

Why pass encoding="utf-8" to open(), and why open files in a with block?

Without it, text mode uses a platform-dependent default, so the same file can read differently on two machines. The with block closes the file when it ends, even after an exception, which also flushes any buffered writes.

A logging function opens its file with "w" and the file only ever holds one line. What is wrong, and what do "a" and "x" do instead?

"w" empties the file the moment it is opened, so each call wipes the last line. "a" writes at the end of the file, and "x" creates a new file and raises FileExistsError if one is already there.

Why does delete_file call unlink() inside try instead of checking that the file exists first?

The file can disappear between the check and the delete, so the check does not make the delete safe. Trying the operation and catching FileNotFoundError (EAFP) handles every case, and here it turns a missing file into False.

json.dumps fails on a ticket's opened_at. Why, and how does the desk store dates instead? And what should loading do with a missing file and with a corrupt one?

JSON has no date type, so dumps raises TypeError for a datetime; the desk stores isoformat() text and rebuilds it with datetime.fromisoformat(). A missing file returns an empty desk, while a corrupt one is logged and re-raised as a ValueError chained to the JSONDecodeError with from err.
