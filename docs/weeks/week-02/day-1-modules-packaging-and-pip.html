Modules, packaging & pip: from one script to a small codebase

Week 2 · Day 1 Mon Oct 19, 2026 Python advanced ~36 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-15 · python 3.15 · pip 26 · pylint 4.0.0

This page assumes the functions and classes from the end of week 1, plus the branch, merge and push commands from week 1's Git day. It explains the import statement and then the tools that turn the single-file ticket desk into a small codebase: the math module, logging, regular expressions, pip with a virtual environment, the pylint linter, and finally a module of your own with a __name__ guard. Afterwards you can say what an import binds, why log.info prints nothing by default, why patterns are raw strings, why a project pins its packages, how to read a pylint message, and what the guard protects.

Standard library

The import statement and the math module

A module is a file of Python code that another file loads by name. Python ships with a large set of them, the standard library, and week 1 used one with the datetime line at the top of the ticket desk and gave import a sentence. This step explains the import statement properly, using the math module as the example, because every later step on this page starts with an import.

What an import binds

import math does two things. It loads the module, and it binds the module object to the name math in the file that ran the statement, so you reach what is inside with a dot, as in math.ceil.1 from math import ceil loads the same module but binds only the name ceil; the name math stays undefined in your file.1 import math as m changes nothing about loading. It only binds the module under a shorter name.1

A module is loaded once per interpreter and cached in sys.modules, so a second import of the same module, under any spelling, reuses the object that is already there.1

import math
import math as m
from math import ceil

print(math.ceil(2.1), m.floor(2.7), ceil(2.1))
print(m is math)

The first print shows 3 2 3. The second shows True, because m and math are two names for one module object, which is what "loaded once" means in practice. The ticket desk's first lines use both forms: import math sits beside from datetime import datetime, timedelta, which binds two names from the datetime module so the code can write datetime(2026, 10, 19, 14, 0) with no prefix.

Which form to use is mostly a readability choice. math.ceil(x) tells the reader where ceil came from at every call, and from ... import saves typing for a name used often. One form is off the table on most teams: from math import * pulls every public name into your file, and PEP 8, the style guide most Python teams follow, discourages wildcard imports because they hide where a name came from.2

Rounding up with ceil, down with floor

math.ceil(x) returns the smallest integer greater than or equal to x, and math.floor(x) returns the largest integer less than or equal to x.3 Both return an int, so the result can be used as a count straight away.3 That is what a ticket desk needs to report whole days open: a ticket opened 71 hours ago is part of the way through its third day, and a support team counts that as three.

import math

hours_open = 71
print(hours_open / 24)
print(math.ceil(hours_open / 24), math.floor(hours_open / 24))
print(math.sqrt(16), math.pi)

The first print shows 2.9583333333333335 and the second 3 2. The third shows 4.0 3.141592653589793: math.sqrt returns a float even for a perfect square, and math.pi is written with no parentheses because it is a constant, not a function.3 The module works only on real numbers, so math.sqrt(-1) raises ValueError instead of returning an answer, and the complex-number versions of these functions live in a separate module, cmath.3

In other people's code you will meet math.ceil(hours / 24) wherever a duration turns into a count of days or pages, and import math as m followed by m.floor(x) in code written by people who like short names.

Comparing floats with isclose

In Python 0.1 + 0.2 == 0.3 is False, while math.isclose(0.1 + 0.2, 0.3) is True.3 The sum is stored as a binary fraction that sits a tiny distance from 0.3, so an exact comparison fails. isclose compares with a relative tolerance of 1e-09 by default, so the two values may differ by about one part in a billion of their size.3 It takes two keyword arguments, rel_tol and abs_tol, and the second one matters when one side is zero, because a tolerance relative to zero is zero.3

import math

print(0.1 + 0.2 == 0.3, math.isclose(0.1 + 0.2, 0.3))
print(math.isclose(1e-12, 0), math.isclose(1e-12, 0, abs_tol=1e-9))

Both lines print False True. Compare computed floats with isclose, and give it an abs_tol whenever zero is one of the values.

round, and why round(2.5) is 2

The built-in round behaves differently from ceil and floor. It rounds a value that sits exactly halfway between two integers to the even one, a rule called banker's rounding, so round(2.5) is 2. Here are all three side by side:

xmath.floor(x)math.ceil(x)round(x)
2.5232
-2.5-3-2-2

floor always moves toward minus infinity, so -2.5 floors to -3, which surprises anyone who expects it to drop the fraction.3 Ties to even avoid always rounding halves up.

Takeaways
  • An import binds a name; the module itself loads once and is cached.
  • Compare computed floats with isclose, and give it abs_tol when zero is involved.
  • floor, ceil and round treat halves and negatives differently.
Say it in an interview

import math binds the module itself to the name math, so I write math.ceil at each call and the reader sees where it came from. from math import ceil binds only ceil. Either way the module is loaded once and cached, so importing it again costs nothing.

0.1 plus 0.2 is stored as a binary fraction a hair away from 0.3, so double-equals says False. I compare floats with math.isclose, which uses a relative tolerance, and I pass abs_tol when one side is zero.

floor goes down toward minus infinity and ceil goes up. round goes to the nearest integer with ties to even, so 2.5 rounds to 2 and minus 2.5 rounds to minus 2.

Standard library

Logging: a record of what the program did

A program that runs for more than a few seconds needs a record of what it did: which ticket was added, who it was assigned to, which one broke its deadline. The logging module is the standard library's answer, and teams use it where a beginner would scatter print calls.

Why a logger instead of print

print writes every line, every time, to the same place as the program's real output. A log message carries more. It has a level that says how serious it is, a logger name that says which part of the code sent it, and a destination chosen once for the whole program. You get a logger with logging.getLogger(__name__), which returns a logger named after the current module.4

__name__ is a variable Python sets in every file; when the file is run directly it holds "__main__", a detail first met on week 1's data-types day that step 6 comes back to. The five standard levels, in rising order, are

  • DEBUG (10),
  • INFO (20),
  • WARNING (30),
  • ERROR (40)
  • and CRITICAL (50).4

There is a second practical difference. The default handler writes log output to stderr, the error stream, while print writes to stdout.5 A terminal shows both streams mixed together, but they are separate, so the desk's board can go one way and its log another.

Levels and the default threshold

Every logger checks a message's level against a threshold, and records below the threshold are dropped.5 With no configuration at all, the effective threshold is WARNING, so log.info(...) prints nothing until something like logging.basicConfig(level=logging.INFO) runs.5 log.error and log.critical record at 40 and 50, above WARNING, so they show under the default threshold too.4

import logging

log = logging.getLogger(__name__)
log.info("before basicConfig")
logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
log.info("added %s", "#1 Login page returns 500")
log.debug("hidden at INFO")
log.warning("%s is past its SLA", "#4 Invoice PDF is blank")
print("overdue: 1")

Saved as levels.py and run, this prints three lines: INFO __main__: added #1 Login page returns 500, then WARNING __main__: #4 Invoice PDF is blank is past its SLA, then overdue: 1. The first INFO call printed nothing because the threshold was still WARNING, and the debug line is below INFO. Change the level to logging.DEBUG and the debug line appears too.5 The two streams are easy to see from Git Bash, where 2>/dev/null after a command throws stderr away:

python levels.py
python levels.py 2>/dev/null

The second run prints only overdue: 1, because both log lines went to stderr.

Format strings and lazy arguments

The format argument of basicConfig is built from LogRecord attributes such as

  • %(levelname)s,
  • %(name)s,
  • %(message)s and
  • %(asctime)s.4

Adding %(asctime)s puts a timestamp on every line, which production logs want and which makes example output change on every run, so the desk leaves it out.4

The message is written as log.info("added %s", ticket), with the value passed as a separate argument. The logging module fills in the %s only when a handler actually emits the record. An f-string inside the call is built every time the line runs, even when the level filters the message out.5 For one message the cost is tiny; for a debug line inside a loop over thousands of tickets it is wasted work on every pass.

You recognise logging in a codebase by log = logging.getLogger(__name__) near the top of a module and calls such as log.warning("%s is past its SLA", t) in the body.

Handlers, formatters and who calls basicConfig

A handler decides the destination, and a formatter decides how each line looks. basicConfig is shorthand for attaching one StreamHandler, with a formatter built from your format string, to the root logger. A named logger such as the desk's has no handler of its own; its records propagate up to the root, and the root's one handler prints them.5 Logger names are dotted and form a hierarchy, so a logger named desk.sub is a child of desk and inherits its level.4

basicConfig is a one-shot convenience. It does nothing if the root logger already has handlers, unless you pass force=True, so it belongs once, at the program's entry point.4 Code meant to be imported by other code never calls it; only the application that runs does.5

That rule also explains a common surprise. Calling the module-level logging.warning("too early") before basicConfig configures the root logger on the spot, so the later basicConfig is silently ignored and its INFO level and format never apply. Calling log.info on a named logger configures nothing, so it does not cause this.

Takeaways
  • Each log message has a level, a logger name and one chosen destination.
  • The default threshold is WARNING, so info and debug are dropped.
  • Only the application's entry point calls basicConfig, once.
Say it in an interview

I use logging instead of print because each message gets a level, a logger name and a destination I set once. I can turn debug output on without editing code, and the log goes to stderr, so it stays out of the program's real output.

The levels are DEBUG, INFO, WARNING, ERROR and CRITICAL. With no configuration the threshold is WARNING, so info and debug messages are dropped until the entry point calls basicConfig with a lower level.

getLogger with dunder name gives each module its own logger named after the module, so every line says where it came from, and the names form a hierarchy I can tune one branch at a time.

Standard library

Regular expressions with the re module

Customers write free text. A note that says "Same problem as TD-2 and TD-5, reply to dana@example.com" holds two ticket references a program should link and an email address it should hide before the note is shared. A regular expression is a small pattern language for finding or replacing text that follows a shape, and Python's re module runs them.

Reading a pattern

A handful of symbols cover most real patterns.

  • \b is a word boundary,
  • \d a digit,
  • \w a word character (a letter, a digit or an underscore),
  • + means one or more of what comes before it,
  • * zero or more, and
  • parentheses make a capturing group that remembers the text inside them.6

Inside square brackets most symbols lose their special meaning, so [\w.+-]+ matches one or more letters, digits, underscores, dots, plus signs and hyphens.6 A backslash in front of a special symbol makes it literal, so \. outside brackets matches a real dot.6

Read the desk's two patterns left to right with that list. \bTD-(\d+)\b is a word boundary, the letters TD-, a group of one or more digits, and another boundary, so TD-12 matches while XTD-9 and TD-3a do not.

[\w.+-]+@[\w-]+\.[\w.]+ is a run of name characters, an @, a domain word, a literal dot, and the rest of the domain. That email pattern only approximates the real address grammar, so it suits redacting likely addresses and would be the wrong tool for proving an address can receive mail.

Compile once, then finditer, findall and sub

re.compile(pattern) returns a pattern object you can reuse with finditer, search, match and sub.7 finditer yields one match object at a time as it scans, while findall returns a list of strings, or of tuples when the pattern has several groups.7 On a match object, match.group(1) returns the text the first group captured as a str, or None when that group took no part in the match; in TD-(\d+) the group always takes part, so the result is always a string ready for int().7

import re

TICKET_REF = re.compile(r"\bTD-(\d+)\b")
EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")
note = "Same problem as TD-2 and TD-5, reply to dana@example.com"

refs = []
for match in TICKET_REF.finditer(note):
    refs.append(int(match.group(1)))
print(refs)
print(TICKET_REF.findall(note))
print(EMAIL.sub("[email]", note))
print(note)

The four prints show [2, 5], then ['2', '5'], then Same problem as TD-2 and TD-5, reply to [email], then the note unchanged. findall gives the group's text as strings, which is why the loop converts each one itself. sub returns a new string; strings cannot be changed in place, so the original note is untouched.7

The module-level functions such as re.search(pattern, text) compile and cache patterns internally, so compiling first is rarely about speed. A named, compiled pattern at the top of a module documents what the pattern is for and keeps it in one place.7 That is the shape you will recognise in real code: TICKET_REF = re.compile(r"...") among the module's constants, and calls like EMAIL.sub("[email]", text) further down.

match against search, and raw strings

Two mistakes catch nearly everyone once. The first is re.match, which only tries at the start of the string, while re.search scans the whole string.7 The second is the missing r. A raw string literal such as r"\bTD-" keeps every backslash as typed, while in a normal string "\b" is a single backspace character.7

import re

note = "Same problem as TD-2 and TD-5, reply to dana@example.com"
print(re.match("TD-", note))
print(re.search("TD-", note))
print(len("\b"), len(r"\b"))
print(re.search("\bTD-2", note))
print(re.search(r"\bTD-2", note))

The prints show None, then <re.Match object; span=(16, 19), match='TD-'>, then 1 2, then None, then a match for 'TD-2'. Without the r the pattern looks for a backspace character the note does not contain, and nothing warns you; it silently matches nothing. The habit is to write every pattern as a raw string, even one with no backslash yet.

Greedy and lazy quantifiers

Once + and * are on the table, the next question is how much they take. . matches any character, and .* is greedy: it matches as much as it can and gives characters back only if the rest of the pattern needs them. Adding a question mark, .*?, makes it lazy, so it matches as little as it can.6

import re

html = "<b>urgent</b> and <i>today</i>"
print(re.search(r"<.*>", html).group())
print(re.search(r"<.*?>", html).group())

The greedy pattern prints the whole string, from the first < to the last >; the lazy one prints only <b>. A regular expression is the wrong tool when you are looking for a fixed piece of text. "TD-2" in note or note.replace("Same", "Similar") is simpler to read and faster when no pattern is needed.6

Takeaways
  • Compile a named pattern once, then use finditer, findall or sub on it.
  • match tries only the start of the string; search scans all of it.
  • Write every pattern as a raw string.
Say it in an interview

re.match only tries at the start of the string, re.search scans the whole string for the first match, and findall returns every match as a list of strings. When I need positions or groups one at a time I use finditer.

I write patterns as raw strings so the backslashes reach the regex engine as typed. In a normal string, backslash b becomes a backspace character and the pattern silently matches nothing.

Backslash d matches one digit and plus means one or more, so backslash d plus is a whole number. Parentheses make a group, and match dot group one gives me just the captured text.

Tooling

pip, virtual environments and requirements.txt

Everything so far came with Python. pylint, the linter in the next step, does not: it is a third-party package that has to be installed, and installing packages well is mostly a question of where they land. A shell is the text window you type commands into; the commands below are written for Git Bash, the shell this course uses on Windows.

A virtual environment per project

python -m venv .venv creates an isolated environment in a folder named .venv, with its own site-packages folder where installed packages live. Once the environment is activated, pip installs into that folder and nowhere else.8 The activation scripts live in .venv/Scripts/ on Windows and in .venv/bin/ on macOS and Linux.8

On Windows the py launcher picks an interpreter version, as in py -3.15.9 This course builds the desk's environment on 3.14 because the research for this page found no pylint release that declares 3.15; the desk code runs the same on both.

python --version
py -3.14 -m venv .venv
source .venv/Scripts/activate
python -m pip --version

The first line prints the shell's default Python. The next two create and activate the environment, and from then on the prompt starts with (.venv). The last line prints pip's version, the word from, a path that runs through .venv\Lib\site-packages\pip, and (python 3.14): that path is the proof of which Python this pip installs into. On macOS the second and third lines are python3.14 -m venv .venv and source .venv/bin/activate.

Since Python 3.13, venv also writes a .gitignore inside the new folder whose only rule is *, so Git skips the environment even before the project ignores it.8 The reason for one environment per project is that two projects often need different versions of the same package, and a single shared install can hold only one.

Installing with python -m pip

pip is the tool that downloads packages and installs them into the active environment. Running it as python -m pip guarantees it is the pip that belongs to the same interpreter as python; a bare pip command is whichever pip the shell finds first, which may belong to a different Python.11 pip --version shows which Python the pip belongs to, and pip list shows the installed packages with their versions.12

python -m pip install pylint==4.0.0
python -m pip list

The install prints a Collecting line for pylint and one for each package it depends on, then Successfully installed followed by every name and version. Installing a package also installs its dependencies, so pip list then shows a table with more rows than you asked for: pip itself, pylint and the packages pylint needs.12

The failure to expect is a shell where the environment is not active. Nothing stops pip install running there; the package lands in whatever Python that shell points at, and the next pylint in the project's environment is reported as not found.8 The prompt tells you which case you are in: no (.venv) at the front means activate first.

Pinning versions in requirements.txt

pip install name==X.Y.Z pins an exact version. A requirements.txt file lists such pins one per line, and pip install -r requirements.txt installs that same set on another machine.13 The environment itself is disposable. Anyone can rebuild it from the requirements file, so it is never committed.8 The desk's requirements.txt holds one line, pylint==4.0.0, and its .gitignore holds .venv/ and __pycache__/. A teammate who clones the repository rebuilds the environment with three commands:

py -3.14 -m venv .venv
source .venv/Scripts/activate
python -m pip install -r requirements.txt

The trade-off of pinning is that every machine gets the same version, including the same bugs. A security fix in a newer release reaches the project only when someone edits the pin, tests, and commits the change. The other common slip is order: if git add . runs before .gitignore exists, the whole .venv/ folder is staged. Write the ignore file first, and add files by name, as in git add .gitignore requirements.txt ticket_desk.py.

You recognise this setup on sight in any Python repository:

  • a requirements.txt of name==version lines,
  • .venv/ in the .gitignore,
  • a README that says python -m pip install -r requirements.txt, and
  • a terminal prompt that begins with (.venv).

PyPI, where packages come from

By default pip downloads from PyPI, the Python Package Index, the public online index of Python packages.11 The name after pip install is a project on PyPI, and the version in a pin is one of that project's releases.13 That is why a pin such as pylint==4.0.0 asks every machine for the same release of the same project.

Takeaways
  • Each project gets its own virtual environment, which is never committed.
  • Run pip as python -m pip so it matches the interpreter.
  • A requirements file pins exact versions so every machine installs the same set.
Say it in an interview

pip installs Python packages, by default from PyPI, into whichever environment is active. I run it as python dash m pip so I know it belongs to the interpreter I think it does.

I create a virtual environment per project so each project gets its own packages and versions without clashing with another project or the system Python. The venv is disposable, so it goes in the gitignore and is rebuilt from the requirements file.

requirements.txt pins exact versions so every machine and the CI server install the same set. The cost is that upgrades, security fixes included, only arrive when someone bumps the pin on purpose.

Tooling

pylint: reading a linter's report

A linter is a tool that reads source code without running it and reports style problems and likely mistakes. pylint is the linter installed in the previous step, and its report is a review your code can get before a teammate ever sees it.

What a linter checks

pylint prints each finding on one line in the shape file:line:column: ID: text (symbol), then a score out of 10.10

The first letter of the ID says what kind of finding it is: C for convention, R for refactor, W for warning, E for error and F for fatal.10

On new code the first messages are nearly always the missing-docstring family: missing-module-docstring (C0114), missing-class-docstring (C0115) and missing-function-docstring (C0116).14 A docstring is a string literal written as the first statement of a module, class or function, and PEP 257 sets the conventions those checks point at.15 pylint's naming checks enforce PEP 8's names, snake_case for functions and CapWords for classes.2

import math

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}


class Ticket:
    def __init__(self, ticket_id, priority):
        self.ticket_id = ticket_id
        self.priority = priority

    def days_open(self, hours):
        return math.ceil(hours / 24)


def sla_for(priority):
    return SLA_HOURS[priority]

Saved as sla.py inside the activated environment, pylint sla.py prints this report:

************* Module sla
sla.py:1:0: C0114: Missing module docstring (missing-module-docstring)
sla.py:6:0: C0115: Missing class docstring (missing-class-docstring)
sla.py:11:4: C0116: Missing function or method docstring (missing-function-docstring)
sla.py:6:0: R0903: Too few public methods (1/2) (too-few-public-methods)
sla.py:15:0: C0116: Missing function or method docstring (missing-function-docstring)

-----------------------------------
Your code has been rated at 5.00/10

Read it one line at a time. sla.py:6:0 is line 6, column 0, the class line. Four findings are conventions about docstrings, and one is a refactor hint saying the class has fewer public methods than pylint expects. A related tool you will hear named alongside linters is a formatter, which rewrites the layout of your code; a linter only reports, and changes nothing.

Fixing, re-running and the score

Add a one-line docstring as the first line of the module, the class and each function, for example """Return whole days open, rounded up.""" under def days_open, and run pylint sla.py again. The report shrinks to the single R0903 line and the score line reads Your code has been rated at 9.00/10 (previous run: 5.00/10, +4.00). The score line also prints the previous run's score and the change, so you can see what the fixes were worth.

pylint also exits with a non-zero status whenever it reports messages.10 That status is how CI uses it. CI, continuous integration, is a server that runs checks on every push, and a non-zero exit fails the check, so a branch with lint findings is flagged before anyone reviews it.

The ticket desk's own first report, excerpted below, names ten missing docstrings, two warnings about variables inside a method sharing a name with variables at the file's top level, and one naming message. The last three go away once the script's code moves into a function in step 6.

Silencing one message

Sometimes the code is right and the message is not useful. A class with one method is a reasonable shape for a small record, so the R0903 hint above can be switched off for that class alone with a comment on its line:

class Ticket:  # pylint: disable=too-few-public-methods
    """One support ticket."""

With that comment the run reports nothing and rates the file at 10.00/10. Silencing is acceptable when you have read the message, the code is deliberate, and the comment names the message by its symbol so a reviewer can see what was switched off. A # pylint: disable=... comment in someone else's code is your cue to ask why.

The score is a heuristic. Chasing 10/10 pushes people to add noise, docstrings that repeat the function name or disable comments nobody justified, and no score proves the code does the right thing.10 pylint checks style and likely mistakes without running anything, while a test runs the code and checks its behaviour; testing is Wednesday's subject. You recognise a pylint report on sight by lines such as ticket_desk.py:12:0: C0115: Missing class docstring (missing-class-docstring).

Takeaways
  • A linter reads code without running it and reports style problems and likely mistakes.
  • Each message ID starts with a letter naming its kind.
  • The score is a heuristic, and a test is what checks behaviour.
Say it in an interview

A linter reads code without running it and reports style problems and likely bugs. pylint checks naming, docstrings, names that hide other names, and design hints, and gives each message an ID whose first letter says whether it's a convention, refactor, warning, error or fatal.

pylint can't tell me the code is correct, because it never runs it. A test runs the code and checks the result. I want both: the linter in CI catches style and obvious mistakes, the tests catch wrong behaviour.

I silence a single message with a pylint disable comment on that line, naming the message, and only after I have read it and decided the code is deliberate. Disabling things just to raise the score is noise.

Code organisation

Writing your own module

After the regex step the ticket desk is one file of about 95 lines: the model, the rules, the patterns and a script that builds six sample tickets and prints a board. This step splits it in two. desk.py holds the code other files can reuse, and ticket_desk.py holds the script that uses it.

A file is a module

Any .py file can be imported by its file name without the .py. Importing a module runs its top-level statements once. A def statement at the top level only defines the function, and a class statement defines the class and its methods; the body of a function or method runs later, when something calls it.16

While a file is being imported, its __name__ is the module's name; when the same file is run as a script, __name__ is "__main__".17 A small module shows all of this:

"""SLA rules for the ticket desk."""
import math

SLA_HOURS = {"high": 4, "normal": 24, "low": 72}
print("loading", __name__)


def days_open(hours):
    """Return the whole days a ticket has been open, rounded up."""
    return math.ceil(hours / 24)


if __name__ == "__main__":
    print(days_open(71))

Save that as sla.py, and save a second file, board.py, in the same folder:

"""Print one line of the board."""
from sla import SLA_HOURS, days_open

print("normal SLA:", SLA_HOURS["normal"], "hours")
print("days open:", days_open(71))

Then run these from that folder. python -c runs the quoted text as a tiny program.

python sla.py
python board.py
python -c "import sla; import sla; print(sla.__name__, sla.days_open(25))"
ls __pycache__

python sla.py prints loading __main__ and 3. python board.py prints loading sla, normal SLA: 24 hours and days open: 3; the guarded line in sla.py did not run, because the file was imported.

The third command prints loading sla only once despite two imports, because the module is cached after the first, then sla 2.1

The last command lists a file such as sla.cpython-314.pyc (the number is the Python version that ran it). Python caches the compiled bytecode of imported modules in __pycache__/, and that folder belongs in .gitignore.16 Bytecode is the lower-level form Python turns your source into before running it, so the next import can skip that step.16

The __name__ guard and main()

The test if __name__ == "__main__": keeps importing free of side effects: the code under it runs when the file is the script and is skipped when another file imports it.17

Teams go one step further and move the script's lines into a function named main(), with the guard calling it. The script's variables then belong to main(), so they cannot clash with names elsewhere in the file, and the module can be imported by another script, or later by a test, without printing a thing.

The desk ends up with exactly that layout.

Where Python looks, and names that collide

An import looks in the running script's own directory first, then in the rest of sys.path, a list of folders Python searches.16 That order means a file of your own named re.py or logging.py shadows the standard library module of the same name. import re next to it loads your file, and the first re.compile fails with an AttributeError. Name your modules after what they hold, such as desk.py, never after a library.

The second collision is between a module and a variable. import desk followed by desk = Desk() rebinds the name desk from the module to the new instance, and the reference to the module is lost.1 The next desk.Ticket(...) raises AttributeError. Inside a function it fails even earlier, because assigning to a name anywhere in a function makes that name local for the whole function.18

ticket_desk.py sidesteps both problems by importing names with from desk import, so its local desk variable never meets a module called desk.

Modules, packages and circular imports

A module is one file. A package is a folder of modules imported with dotted names, such as helpdesk.storage.16 The classic failure once code is spread across files is the circular import, where a.py imports b and b.py imports a.

Splitting too early has a cost as well: small code is scattered across files that nothing else imports. A module earns its own file by being imported by more than one caller or by having one clear job, and desk.py qualifies on the second count.16

Takeaways
  • Importing a module runs its top-level statements once.
  • The name guard keeps importing free of side effects.
  • Your own file names must not shadow library modules or variables.
Say it in an interview

A module is a single Python file I import by name. A package is a folder of modules that I import with dotted names.

Every file has a dunder name. It's dunder main when I run the file directly and the module's name when it's imported, so the if dunder name equals dunder main guard runs the script part only when the file is the program. I put that code in a main function and call it from the guard.

Importing a module runs its top-level code once, so anything at the top level, a print or a basicConfig call, happens on import. Function and method bodies only run when called, which is why the script part goes into main and under the guard.

Check yourself

Check yourself

Eight retrieval questions, at least one per section. Answer each out loud before you open it.

What is the difference between import math and from math import ceil, and what happens on a second import of the same module?

import math binds the module object to the name math, so calls read math.ceil. from math import ceil binds only ceil. A second import of either kind reuses the module already cached in sys.modules.

What do math.floor, math.ceil and round give for 2.5 and for -2.5?

For 2.5: 2, 3 and 2. For -2.5: -3, -2 and -2. floor goes toward minus infinity, ceil toward plus infinity, and round sends exact halves to the even integer.

A module calls log.info("added %s", ticket) and nothing appears. Why, and where does the fix belong?

With no configuration the threshold is WARNING, so INFO records are dropped. Call logging.basicConfig(level=logging.INFO) once, at the program's entry point, never inside code that other code imports.

Why does a reviewer ask you to write log.debug("checking %s", t) instead of an f-string?

With %s and a separate argument, the message is only formatted if a handler emits the record. An f-string is built every time the line runs, even when DEBUG is filtered out.

re.match("TD-", note) returns None although the note contains TD-2. Why, and what else silently matches nothing?

re.match only tries at the start of the string; re.search scans the whole string. A pattern such as "\bTD-" written without the r prefix also matches nothing, because "\b" becomes a backspace character.

Why run python -m pip rather than pip, and what goes in requirements.txt and .gitignore?

python -m pip is guaranteed to be the pip of the interpreter python runs, which inside an active venv is the venv's own. requirements.txt holds pinned lines such as pylint==4.0.0; .gitignore holds .venv/ and __pycache__/, because the venv is rebuilt from the pins.

pylint prints sla.py:6:0: C0115: Missing class docstring (missing-class-docstring). Read it aloud, and say what pylint can never tell you.

File sla.py, line 6, column 0, a convention message (C) with ID C0115 and symbol missing-class-docstring. pylint never runs the code, so it cannot tell you the code behaves correctly; that is a test's job.

What does if __name__ == "__main__": do, and what goes wrong after import desk then desk = Desk()?

The guard runs its block only when the file is run directly, so importing the module has no side effects. The assignment rebinds desk from the module to the instance, so a later desk.Ticket raises AttributeError, or UnboundLocalError inside a function.
