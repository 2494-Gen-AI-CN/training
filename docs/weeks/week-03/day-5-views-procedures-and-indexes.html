Trigger

Triggers: SQL that runs when a row changes

So far every change to the desk came from a statement someone sent. A trigger lets the database add a step of its own.

What a trigger is and what it automates

A trigger is a named object stored with one table. The server runs it automatically when an INSERT, UPDATE or DELETE happens on that table, either BEFORE or AFTER the row changes.1 Each trigger is bound to exactly one table, one event and one timing, and FOR EACH ROW means its body runs once for every row the statement touches.1

The MySQL manual's examples cover three common jobs for a trigger:2

  • writing an audit or history row each time a record changes;
  • keeping a derived value in step with the rows it comes from;
  • checking a rule and refusing a bad row before it is written.

The desk wants the first job. Its ticket_events table has existed since Wednesday and stayed empty, because nothing wrote to it on its own. A trigger on tickets can write one event whenever a ticket's status or agent changes, whichever program made the change.

Writing one: DELIMITER, BEGIN and END

A trigger with several statements wraps its body in BEGIN ... END, and each statement inside ends with a semicolon. The mysql client normally sends a statement to the server as soon as it reads a semicolon. DELIMITER // changes that end marker for a moment, so the whole CREATE travels as one statement and stops at END //.3

DELIMITER //
CREATE TRIGGER tickets_status_change
AFTER UPDATE ON tickets
FOR EACH ROW
BEGIN
  IF OLD.status <> NEW.status OR NOT (OLD.agent_id <=> NEW.agent_id) THEN
    INSERT INTO ticket_events (ticket_id, kind, note)
    VALUES (NEW.ticket_id, NEW.status, CONCAT('was ', OLD.status, ', agent ', COALESCE(NEW.agent_id, 'none')));
  END IF;
END //
DELIMITER ;

The client answers Query OK, 0 rows affected and the trigger waits for its first UPDATE. Without the two DELIMITER lines, the first semicolon inside the body ends the statement early and the client reports a syntax error. The last line sets the marker back to the semicolon.

UPDATE tickets SET status = 'closed', closed_at = '2026-10-19 14:00:00' WHERE ticket_id = 5;
SELECT event_id, ticket_id, kind, note FROM ticket_events;
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

+----------+-----------+--------+-----------------------+
| event_id | ticket_id | kind   | note                  |
+----------+-----------+--------+-----------------------+
|        1 |         5 | closed | was assigned, agent 2 |
+----------+-----------+--------+-----------------------+
1 row in set

Nobody typed an INSERT into ticket_events. The UPDATE moved ticket 5 from assigned to closed, so the trigger wrote the row itself, taking the old status and the current agent from the two versions of the row.

OLD, NEW and the NULL-safe comparison

Inside a row trigger, OLD.col is a column's value before the change and NEW.col is its value after. An INSERT has no OLD row and a DELETE has no NEW row, so each name exists only where it makes sense.2

The test on agent_id needs care, because that column is NULL on four of the six tickets. A plain <> yields NULL when either side is NULL, and IF treats NULL as false, so a ticket's first agent would never count as a change. The NULL-safe equals <=> always answers 1 or 0, and NOT (OLD.agent_id <=> NEW.agent_id) is the NULL-safe way to detect a change.4

SELECT NULL = NULL, NULL <=> NULL, NULL <> 1, NOT (NULL <=> 1);
+-------------+---------------+-----------+------------------+
| NULL = NULL | NULL <=> NULL | NULL <> 1 | NOT (NULL <=> 1) |
+-------------+---------------+-----------+------------------+
|        NULL |             1 |      NULL |                1 |
+-------------+---------------+-----------+------------------+
1 row in set

BEFORE or AFTER

The timing decides what a trigger may do with the row.1

TimingCan it change the incoming row?Typical job
BEFOREYes, with SET NEW.col = ..., because the row is not written yettidy a value, or check a rule and refuse the row
AFTERNo, the row is already writtenwrite an audit or history row about the final row

A BEFORE trigger that tidies titles shows the difference. This one is an illustration, and the desk does not keep it.2

DELIMITER //
CREATE TRIGGER tickets_tidy_title
BEFORE INSERT ON tickets
FOR EACH ROW
BEGIN
  SET NEW.title = TRIM(NEW.title);
END //
DELIMITER ;
INSERT INTO tickets (ticket_id, title, priority, customer_id, opened_at)
VALUES (7, '   Reset link expired  ', 'normal', 4, '2026-10-19 13:00:00');
SELECT ticket_id, CONCAT('[', title, ']') AS title, status FROM tickets WHERE ticket_id = 7;
Query OK, 0 rows affected

Query OK, 1 row affected

+-----------+----------------------+--------+
| ticket_id | title                | status |
+-----------+----------------------+--------+
|         7 | [Reset link expired] | open   |
+-----------+----------------------+--------+
1 row in set

The spaces never reach the table, because the trigger rewrote NEW.title before the row was stored. An AFTER trigger could not do that, which is why audit rows, which describe what was written, go in an AFTER trigger.

The cost of logic nobody sees

A trigger runs on every matching change, out of sight of the code that made it. A developer reading the Python that closes a ticket sees one UPDATE and nothing about a history row, so a surprise in ticket_events sends them searching. Each trigger also adds work to every write on its table.1

Two facts limit the surprise. A trigger fires inside the transaction of the statement that caused it, so a ROLLBACK undoes the trigger's writes along with the change.2 And MySQL fires triggers only for changes made by SQL statements, so a row removed by an ON DELETE CASCADE foreign key fires no DELETE trigger.1

SHOW TRIGGERS lists a database's triggers and DROP TRIGGER removes one by name.5 In someone else's schema a trigger shows as CREATE TRIGGER, a timing, an event, ON a table and FOR EACH ROW.

Takeaways
  • A trigger runs by itself on one table's insert, update or delete, before or after the change.
  • OLD is the row before, NEW the row after, and the NULL-safe equals compares nullable columns.
  • BEFORE can rewrite the incoming row; AFTER suits audit and history rows.
  • A rollback undoes a trigger's writes together with the statement that fired it.
Say it in an interview

A trigger is SQL the database runs by itself when a row in one table is inserted, updated or deleted. I'd use one for something that has to happen whatever program makes the change, like writing an audit row every time a ticket's status changes. Inside it, OLD is the row before the change and NEW is the row after.

The catch is visibility. The application shows an UPDATE and nothing else, so whoever debugs the history table has to know the trigger exists. I keep triggers short, give them names that say what they do, and keep them in the same SQL files as the schema.

Views

Views: a saved query with a name

Thursday's board query joins four tables and runs to nine lines. A view gives that query a name, so the desk, a report and a teammate all read the same board without retyping it. The examples from here on start from a rebuild of the desk's database, so ticket 5 is assigned again, ticket 7 is gone and neither trigger above exists.

A stored SELECT, read like a table

A view is a stored SELECT with a name. It holds no rows of its own: each time something reads it, the server runs its query against the tables underneath.6 In a FROM clause a view is used exactly like a table.6

CREATE VIEW open_board AS
SELECT t.ticket_id, CONCAT('TD-', t.ticket_id) AS ref, t.title, t.priority, t.status,
       c.name AS customer, a.name AS agent,
       DATE_ADD(t.opened_at, INTERVAL p.sla_hours HOUR) AS deadline
FROM tickets AS t
JOIN customers AS c ON c.customer_id = t.customer_id
JOIN priorities AS p ON p.priority = t.priority
LEFT JOIN agents AS a ON a.agent_id = t.agent_id
WHERE t.status <> 'closed'
ORDER BY t.ticket_id;
SELECT * FROM open_board;
Query OK, 0 rows affected

+-----------+------+------------------------+----------+----------+------------+-------+---------------------+
| ticket_id | ref  | title                  | priority | status   | customer   | agent | deadline            |
+-----------+------+------------------------+----------+----------+------------+-------+---------------------+
|         4 | TD-4 | Checkout button frozen | high     | assigned | Mei Chen   | Priya | 2026-10-19 12:00:00 |
|         5 | TD-5 | Export is missing rows | normal   | assigned | Ravi Patel | Marco | 2026-10-19 12:00:00 |
|         6 | TD-6 | Add dark mode          | low      | open     | Mei Chen   | NULL  | 2026-10-22 12:00:00 |
+-----------+------+------------------------+----------+----------+------------+-------+---------------------+
3 rows in set

The body is Thursday's board query with one line added, the WHERE that drops closed tickets. The view's columns take their names from the SELECT's names and aliases, which is why the query says AS ref, AS customer and AS agent.6 Callers depend on those names, so the aliases are part of the view's contract.

A view also re-runs its query on every read. It saves typing and keeps one definition of the board; it saves no computation, and reading the view a thousand times runs the four-table join a thousand times.6

Reading a view from Python

Python reads a view with an ordinary SELECT through cursor.execute. A cursor made with conn.cursor(dictionary=True) returns each row as a dict keyed by the view's column names, so the code says row["ref"] instead of remembering a position.7

from db import connect

conn = connect()
cursor = conn.cursor(dictionary=True)
cursor.execute("SELECT * FROM open_board")
rows = cursor.fetchall()
cursor.close()
conn.commit()
for row in rows:
    print(row["ref"], row["customer"], row["agent"], row["deadline"])
conn.close()
TD-4 Mei Chen Priya 2026-10-19 12:00:00
TD-5 Ravi Patel Marco 2026-10-19 12:00:00
TD-6 Mei Chen None 2026-10-22 12:00:00

The missing agent arrives as Python's None, and the deadline as a datetime that prints in the same format the client shows. The conn.commit() after the read ends its transaction, as every desk function has done since Wednesday. Nothing in the Python names a join: if the board's definition changes, the view changes and this code does not.

Updating through a view

Some views accept INSERT, UPDATE and DELETE and pass them to the table underneath. A view that uses aggregates, GROUP BY, DISTINCT or UNION is not updatable, because one of its rows does not map back to one row of a table; a plain view over one table generally is.8

a list of agent ids and namesone table, plain columnsgenerally yes

CREATE VIEW agent_load AS
SELECT a.name AS agent, COUNT(t.ticket_id) AS open_tickets
FROM agents AS a
LEFT JOIN tickets AS t ON t.agent_id = a.agent_id AND t.status <> 'closed'

ORDER BY a.agent_id;

Sam's zero is a count, and no row of any table holds it, so there is nothing for the UPDATE to change. When a view is no longer wanted, DROP VIEW agent_load; removes the definition and no data.9

Views as a security boundary

Teams also create views to control what an account can see. A view can expose chosen columns and chosen rows, and a GRANT can name a single view, so an account may read the view while holding no privilege on the tables beneath it.10 A reporting login could read open_board and never see a customer's email or monthly fee.

In someone else's schema a view reads as CREATE VIEW, a name, AS and a SELECT. Everywhere else it looks like a table, so the name is often the only clue. The desk's names help here: tables are plural nouns such as tickets, while each view is named for the report it gives, such as open_board.

Takeaways
  • A view is a named SELECT that holds no rows and runs its query on every read.
  • Aliases in the SELECT become the view's column names, which callers read by name.
  • A view with an aggregate, GROUP BY, DISTINCT or UNION cannot be updated through.
  • A grant on a view alone shows an account chosen columns and rows.
Say it in an interview

A view is a saved SELECT with a name. I create it with CREATE VIEW, the name, AS and the query, say an open board that joins tickets, customers, priorities and agents, and then I read it with SELECT star FROM the view as if it were a table. From Python it's an ordinary SELECT.

It doesn't store any data. The query runs every time it's read, so a view keeps one definition of the board in one place but saves no work. A view with GROUP BY or an aggregate can't be updated through, and I can grant an account a single view to hide the columns it shouldn't see.

What is a stored procedure

Stored procedures: a unit of work kept in the database

A view names a read. A stored procedure names a piece of work: one or more statements kept in the database and run on demand.

Defining and calling a procedure

CREATE PROCEDURE defines routine code with a list of parameters, and CALL runs it.11 A procedure may change rows, return result sets to the client or set OUT parameters.12 Its body sits between BEGIN and END, so it needs the same DELIMITER lines as a trigger. The examples below run in order, starting from a rebuild with tickets_status_change created again, so ticket_events starts empty.

DELIMITER //
CREATE PROCEDURE close_ticket(IN p_ticket_id INT, IN p_closed_at DATETIME)
BEGIN
  UPDATE tickets
  SET status = 'closed', closed_at = p_closed_at
  WHERE ticket_id = p_ticket_id;
END //
DELIMITER ;
CALL close_ticket(4, '2026-10-19 15:00:00');
SELECT event_id, ticket_id, kind, note FROM ticket_events;
Query OK, 0 rows affected

Query OK, 1 row affected

+----------+-----------+--------+-----------------------+
| event_id | ticket_id | kind   | note                  |
+----------+-----------+--------+-----------------------+
|        1 |         4 | closed | was assigned, agent 1 |
+----------+-----------+--------+-----------------------+
1 row in set

The p_ prefix keeps parameters apart from columns, so closed_at = p_closed_at plainly sets the column from the parameter. The event row came from the trigger, because the procedure's UPDATE changed a status like any other statement.

A procedure can also hand rows back. A SELECT in the body sends its result to whoever called:

DELIMITER //
CREATE PROCEDURE tickets_for_customer(IN p_email VARCHAR(255))
BEGIN
  SELECT t.ticket_id, t.title, t.status
  FROM tickets AS t
  JOIN customers AS c ON c.customer_id = t.customer_id
  WHERE c.email = p_email
  ORDER BY t.ticket_id;
END //
DELIMITER ;
CALL tickets_for_customer('dana@example.com');

The caller passes a variable, @n, for the procedure to fill, then reads it: 2, because ticket 4 is now closed and only tickets 5 and 6 are still open. Inside BEGIN and END a procedure can also DECLARE local variables and branch or loop with IF and WHILE, so a body can hold real logic.13

A trigger that calls a procedure

A trigger body may CALL a procedure, so logic shared by several triggers or callers is written once.2 The desk moves its history INSERT into a small procedure, log_event, and the trigger's INSERT becomes a CALL. In the routines file the procedure comes first, because the trigger names it. The old trigger goes first with DROP TRIGGER, so the new one can take its name.5

DROP TRIGGER tickets_status_change;
DELIMITER //
CREATE PROCEDURE log_event(IN p_ticket_id INT, IN p_kind VARCHAR(20), IN p_note VARCHAR(255))
BEGIN
  INSERT INTO ticket_events (ticket_id, kind, note)
  VALUES (p_ticket_id, p_kind, p_note);
END //
CREATE TRIGGER tickets_status_change
AFTER UPDATE ON tickets
FOR EACH ROW
BEGIN
  IF OLD.status <> NEW.status OR NOT (OLD.agent_id <=> NEW.agent_id) THEN
    CALL log_event(NEW.ticket_id, NEW.status, CONCAT('was ', OLD.status, ', agent ', COALESCE(NEW.agent_id, 'none')));
  END IF;
END //
DELIMITER ;
UPDATE tickets SET agent_id = 3 WHERE ticket_id = 6;
SELECT event_id, ticket_id, kind, note FROM ticket_events WHERE ticket_id = 6;
Query OK, 0 rows affected

Query OK, 0 rows affected

Query OK, 0 rows affected

Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

+----------+-----------+------+-------------------+
| event_id | ticket_id | kind | note              |
+----------+-----------+------+-------------------+
|        2 |         6 | open | was open, agent 3 |
+----------+-----------+------+-------------------+

Ticket 6 kept its status and gained its first agent, and the NULL-safe test caught the change. The event is number 2 because ticket 4's closure already wrote number 1. One restriction shapes which procedures a trigger may call: a procedure that returns a result set to the client cannot be called from a trigger.14 log_event only inserts, so it qualifies, and tickets_for_customer never would.

Calling a procedure from Python

Connector/Python's cursor.callproc(name, args) calls a stored procedure, with the arguments as a tuple in the order the procedure declares them.7

from db import connect

conn = connect()
cursor = conn.cursor()
cursor.callproc("close_ticket", (5, "2026-10-19 16:00:00"))
conn.commit()
cursor.execute("SELECT kind, note FROM ticket_events WHERE ticket_id = %s", (5,))
print(cursor.fetchall())
conn.commit()
cursor.close()
conn.close()
[('closed', 'was assigned, agent 2')]

The Python sent one CALL; the database ran the UPDATE, the trigger and the INSERT behind it. The desk calls procedures that return no rows this way, and runs a result-set procedure such as tickets_for_customer at the mysql> prompt.

EXECUTE, definer rights and the trade-off

GRANT EXECUTE on a database lets an account CALL its procedures and use its functions.10 The desk's own account gets it with one statement:

GRANT EXECUTE ON ticket_desk.* TO 'desk_app'@'%';

The server answers Query OK, 0 rows affected, and from then on desk_app may CALL every procedure and use every function in ticket_desk.

A routine runs with the privileges of its DEFINER by default (SQL SECURITY DEFINER), so an account holding only EXECUTE can still change the tables the routine touches; with SQL SECURITY INVOKER the caller would need those privileges itself.11 To see what that buys, take an illustration account named report_app, which the desk does not have, holding only SELECT and EXECUTE on ticket_desk. It tries both ways:

UPDATE tickets SET status = 'closed' WHERE ticket_id = 6;
CALL close_ticket(6, '2026-10-19 17:00:00');
SELECT ticket_id, status, closed_at FROM tickets WHERE ticket_id = 6;
ERROR 1142 (42000): UPDATE command denied to user 'report_app'@'localhost' for table 'tickets'

Query OK, 1 row affected

+-----------+--------+---------------------+
| ticket_id | status | closed_at           |
+-----------+--------+---------------------+
|         6 | closed | 2026-10-19 17:00:00 |
+-----------+--------+---------------------+
1 row in set

The account may close a ticket only the way the procedure closes it, which is the security case for procedures. They also save round trips: one CALL replaces several statements sent from the application. The cost is that logic in procedures lives apart from the application code, so it is versioned separately and is harder to test and review.15 You recognise one in a schema file by CREATE PROCEDURE with IN parameters between DELIMITER lines, and in code by CALL or callproc.

Takeaways
  • A stored procedure is named SQL kept in the database and run with CALL.
  • IN parameters carry values in; OUT parameters hand values back through a variable.
  • A trigger can CALL a procedure, as long as that procedure returns no result set.
  • With definer rights, a grant of EXECUTE can replace direct table privileges.
Say it in an interview

A stored procedure is a named block of SQL kept in the database. I create it with CREATE PROCEDURE, give it parameters such as an IN ticket id, write the body between BEGIN and END after changing the client's delimiter, and run it with CALL and the arguments. From Python I call it with callproc.

A trigger can call one too. On a ticket desk, the AFTER UPDATE trigger on tickets calls a log_event procedure, so the history insert is written once and every status change goes through it. And since a procedure runs with its definer's rights by default, an app can be granted EXECUTE instead of UPDATE on the table.

What is a user defined function

User-defined functions: one value, used inside a query

A procedure is run on its own. A function is the other kind of stored routine, the kind a query can use in the middle of a SELECT. The examples below start from a fresh rebuild of the desk's database, so tickets 4, 5 and 6 have no closing time again.

Creating and calling a function

A user-defined function, which MySQL calls a stored function, returns one value and is used inside an expression such as a SELECT list or a WHERE.11 It has only IN parameters, and its body must RETURN exactly one value of the type named after RETURNS.11

CREATE FUNCTION hours_open(p_opened DATETIME, p_closed DATETIME)
RETURNS DECIMAL(8,2)
DETERMINISTIC
RETURN ROUND(TIMESTAMPDIFF(MINUTE, p_opened, p_closed) / 60, 2);
SELECT ticket_id, hours_open(opened_at, closed_at) AS hours FROM tickets;
Query OK, 0 rows affected

+-----------+-------+
| ticket_id | hours |
+-----------+-------+
|         1 |  3.00 |
|         2 | 30.00 |
|         3 | 10.00 |
|         4 |  NULL |
|         5 |  NULL |
|         6 |  NULL |
+-----------+-------+
6 rows in set

The body is a single RETURN statement, so there is no BEGIN and END and no DELIMITER change; the semicolon ends the whole CREATE.3 The three unclosed tickets show NULL because TIMESTAMPDIFF returns NULL when either time is NULL, and these tickets have no closed_at.16

Why the function says DETERMINISTIC

With binary logging on, creating a function that is not declared DETERMINISTIC, NO SQL or READS SQL DATA fails with error 1418.17 The desk's server has binary logging on, so the same function without the word is refused:

CREATE FUNCTION hours_open(p_opened DATETIME, p_closed DATETIME)
RETURNS DECIMAL(8,2)
RETURN ROUND(TIMESTAMPDIFF(MINUTE, p_opened, p_closed) / 60, 2);
ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)

DETERMINISTIC promises that the same inputs always give the same output. A body that reads NOW() is strictly not deterministic, because the answer changes with the clock, so hours_open takes both times as parameters and leaves the caller to supply the time.11

Function or procedure

The two routines share CREATE syntax and differ in almost everything else.11

FunctionProcedure
Gives backexactly one value, with RETURNresult sets, OUT parameters, or nothing
Usedinside an expression, in SELECT or WHEREon its own, with CALL
ParametersIN onlyIN, OUT and INOUT

A function also cannot run COMMIT or ROLLBACK or return a result set.14 As a rule, when the answer is a value you want in a column or a condition, write a function, and when the job is a change or a list of rows, write a procedure.

Built-in functions, and the cost per row

Thursday's built-in functions, such as CONCAT, ROUND and DATE_ADD, are the model a UDF extends: a name, parentheses, arguments and one value back. hours_open is itself built from two built-ins, TIMESTAMPDIFF and ROUND, and once created it is called exactly like them.

A function called in a WHERE or a SELECT runs once for every row the query reads, which is slow on a big table.11

SELECT ticket_id, title FROM tickets WHERE hours_open(opened_at, closed_at) > 20;
+-----------+----------------------+
| ticket_id | title                |
+-----------+----------------------+
|         2 | Invoice PDF is blank |
+-----------+----------------------+
1 row in set

To answer, the server called hours_open six times, once per ticket. A function wrapped around a column also hides that column from an index, which the next step shows in a query plan. You recognise a UDF in a schema by CREATE FUNCTION, RETURNS and a type, and in a query by a name that is not MySQL's own.

Takeaways
  • A user-defined function takes IN parameters and returns exactly one value of a declared type.
  • It is used inside a query, wherever a built-in function could go.
  • With binary logging on, a function must declare DETERMINISTIC or MySQL refuses it.
  • A function in a WHERE runs once per row the query reads.
Say it in an interview

A user-defined function is a routine in the database that takes inputs and returns one value, so I can use it in a query the way I'd use a built-in. I create it with CREATE FUNCTION, the parameters, RETURNS and a type, DETERMINISTIC, and a RETURN expression, like an hours-open function over two datetimes, and then I call it in a SELECT on the opened and closed columns.

DETERMINISTIC says the same inputs always give the same output, and with binary logging on MySQL refuses a function without it, error 1418. Against a procedure: a function returns exactly one value and lives inside an expression, while a procedure runs on its own with CALL and can return rows or OUT values.

Indexes

Indexes: finding rows without reading them all

Every query on this page has read all six tickets to find the few it wanted. On six rows nobody notices; on six million, an agent waiting for the board does.

What an index is

An index is a separate sorted structure on one or more columns that lets the server find matching rows without reading the whole table. In InnoDB that structure is a B-tree.18 A B-tree is a sorted tree the server walks from the top to the right entry in a few steps, much as you find a word in a printed dictionary without reading every page.

A secondary index in InnoDB, meaning any index other than the primary key, is a B-tree whose entries point to the primary key.19 A lookup on a status index finds the ids of the open tickets, then fetches those rows by id. Some indexes exist before anyone asks: InnoDB indexes the primary key automatically, and a foreign-key column gets an index if none exists.20

SHOW INDEX FROM tickets;

The result is fifteen columns wide; the two that matter here are Key_name and Column_name.21 It lists four indexes: PRIMARY on ticket_id, and one each named priority, customer_id and agent_id for the three foreign keys, every one with Index_type BTREE. Nothing indexes status yet, and DROP INDEX with a name and ON tickets removes one later.

Reading EXPLAIN before and after

EXPLAIN shows the plan for a statement. In MySQL 9.7 the default output format is a tree, and its lines name a table scan or an index lookup.22

1 row in set

Each arrow is one operation, and the more indented line runs first. Before the index, Table scan on tickets means every row is read and a Filter then keeps the matches. After it, Index lookup on tickets using idx_tickets_status means the server went straight to the open entries in the index.23

The cost and rows figures are the optimizer's estimates, and the times the client prints are no guide on six rows. On a table this small the optimizer may even choose a scan for some queries, so judge an index by reading the plan, not by timing a tiny table.23

What an index costs

Every index speeds some reads and slows every change.24

  • Disk space: the index is a second sorted copy of its columns, kept beside the table.
  • Slower writes: each INSERT, UPDATE and DELETE must update every index on the table as well as the row.
  • Little gain on a column with few distinct values: a three-value status can still match a large share of the table.

The last point means idx_tickets_status earns its place only while open tickets are a small part of a large history of closed ones.24 An index also helps only a query that compares the indexed column itself:

Composite indexes and the leftmost prefix

An index can cover several columns, such as an index on (customer_id, status). Its entries are sorted by the first column, then by the second within each value of the first, so the server can use it only for a leftmost prefix of its columns.18

WHERE clauseUses an index on (customer_id, status)?
customer_id = 3 AND status = 'open'yes, both columns
customer_id = 3yes, the leftmost column
status = 'open'no, status alone is not a leftmost prefix

Column order is therefore a design choice: the column most queries filter on goes first. In someone else's schema you recognise an index by CREATE INDEX, a name that often starts idx_, and ON a table with its columns in parentheses; in a plan, by using and that name.

Takeaways
  • An index is a sorted B-tree beside the table that finds rows without a full scan.
  • EXPLAIN shows a table scan before the index and an index lookup after it.
  • Each index costs disk space and extra work on every write.
  • A composite index serves only queries that filter on its leftmost columns.
Say it in an interview

An index is a separate sorted structure on one or more columns, a B-tree in InnoDB, so the database can find matching rows without reading the whole table. The benefit is fast lookups for queries that filter on those columns. The cost is disk space and extra work on every insert, update and delete, because the index has to stay sorted.

To check a query uses one, I run EXPLAIN. A table scan means every row is read; an index lookup that names the index means it's used. If it isn't, I check whether the column is wrapped in a function, and for a composite index, whether the query filters on its leftmost column.

Choosing the tool

Friday's five objects answer different questions, and the interview question "when do you pick which?" comes up often.

One trade-off runs through the first three rows. Every automatic mechanism moves behaviour out of the application, which trades visibility for consistency: the rule holds for every writer, and fewer people see it.15

Rules that hold for every writer

Some of the week's guarantees live in the database or the connector, whichever program does the work:

  • Foreign keys and CHECK constraints enforce rules inside the database, regardless of which program writes.25
  • ACID transactions, meaning atomicity, consistency, isolation and durability, are how InnoDB keeps multi-statement changes safe.26
  • Placeholders, %s with a tuple, keep values out of the SQL text and prevent injection.7
from db import connect

conn = connect()
cursor = conn.cursor()
cursor.execute("SELECT title FROM tickets WHERE ticket_id = %s", (4,))
print(cursor.fetchone())
cursor.close()
conn.commit()
conn.close()
('Checkout button frozen',)

The 4 travels to the server apart from the statement, so a value holding a quote or a semicolon can never become part of the SQL. An f-string that pasted the value into the text would allow exactly that.

Rebuild, then test

The desk's sql/ folder holds the structure, the rows, the account, the reports and the routines, each in its own file. The database can be rebuilt from these files alone, run in order.

cat sql/schema.sql sql/seed.sql sql/routines.sql | docker exec -i desk-mysql mysql -uroot -pdesk
mysql: [Warning] Using a password on the command line interface can be insecure.

The warning is the only output. The schema file drops and recreates the database, the seed fills parents before children, and the routines file adds the trigger, procedures, views, function and index, so every run starts from the same six tickets.

The tests rely on that. Their database fixture skips when the password variable is missing and rolls back whatever the test changed:

@pytest.fixture
def conn():
    """Yield a database connection and roll back what the test changed."""
    if "DESK_DB_PASSWORD" not in os.environ:
        pytest.skip("no database")
    connection = connect()
    yield connection
    connection.rollback()
    connection.close()

Calling pytest.skip inside a fixture skips every test that uses it, which keeps the suite green on a laptop where the database cannot be reached.27 The lines after yield run when the test finishes, the yield-then-clean-up shape pytest documents for fixtures.28

Takeaways
  • Triggers, views, procedures, functions and indexes each answer a different design question.
  • Keys, constraints and transactions hold for every program that writes to the database.
  • Placeholders keep values out of the SQL text, which prevents injection.
  • A database rebuilt from files in order gives every run and every test the same rows.

Check yourself

Check yourself

Answer each question out loud, as you would to an interviewer, before you open it.

A ticket gets its first agent and keeps the status open. Why would a trigger testing OLD.agent_id <> NEW.agent_id miss the change, and what catches it?

The old agent is NULL, and NULL <> 3 yields NULL, which IF treats as false. The NULL-safe equals always answers 1 or 0, so NOT (OLD.agent_id <=> NEW.agent_id) reports the change.

Which trigger timing would you use to trim a title before it is stored, and which to write an audit row? Why?

BEFORE for the trim, because only a BEFORE trigger can change the incoming row with SET NEW.title. AFTER for the audit row, because it describes the row that was actually written.

Does a view store the rows of its query? What follows when a page reads it a thousand times?

No. A view is a named SELECT that holds no rows and runs its query on every read, so a thousand reads run the join a thousand times. It saves typing and keeps one definition, not computation.

Why does UPDATE agent_load SET open_tickets = 0 fail with ERROR 1288?

agent_load uses COUNT and GROUP BY, so each of its rows is a summary that maps back to no single table row. A view with an aggregate, GROUP BY, DISTINCT or UNION is not updatable.

How do you create and call a stored procedure that closes a ticket, and how does Python call it?

Change the client's delimiter, then write CREATE PROCEDURE close_ticket(IN p_ticket_id INT, IN p_closed_at DATETIME) with the UPDATE between BEGIN and END //, and set the delimiter back. Run it with CALL close_ticket(4, '2026-10-19 15:00:00');. From Python, cursor.callproc("close_ticket", (ticket_id, at)) followed by a commit.

The desk's trigger calls log_event. Could it call tickets_for_customer instead? Why?

No. tickets_for_customer ends with a SELECT that returns a result set to the client, and a procedure that returns a result set cannot be called from a trigger. log_event only inserts a row, so it can.

How do you create a function that returns how many hours a ticket was open, and why must it say DETERMINISTIC?

CREATE FUNCTION hours_open(p_opened DATETIME, p_closed DATETIME) RETURNS DECIMAL(8,2) DETERMINISTIC followed by a RETURN of the rounded TIMESTAMPDIFF, then use it in a SELECT. With binary logging on, MySQL refuses a function that declares none of DETERMINISTIC, NO SQL or READS SQL DATA, error 1418. The body takes both times as parameters, so the promise is true.

An index on status exists, yet EXPLAIN for WHERE UPPER(status) = 'OPEN' shows a table scan. Why, and what does every index cost?

The index is sorted by status, not by UPPER(status), so the server must compute the function for every row. Every index also costs disk space and extra work on each INSERT, UPDATE and DELETE.

A table has an index on (customer_id, status). Which can use it: a filter on customer_id alone, or one on status alone?

Only the filter on customer_id, because the server uses a composite index for a leftmost prefix of its columns. A filter on status alone skips the first column, so it needs an index of its own.

A teammate asks whether "hours open" belongs in a view, a procedure or a function. What do you answer?

A function, because it is one computed value used inside a query, per ticket. A view suits a shared read such as the board, and a procedure suits a unit of work such as closing a ticket.
