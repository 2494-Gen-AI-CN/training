Keys, constraints & normalization: a schema that refuses bad rows

Week 3 · Day 3 Wed Oct 28, 2026 SQL with MySQL ~40 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-23 · python 3.15 · mysql 9.7 · mysql-connector-python 26.7.0 · pytest 9.1.1 Exit criteria

This page assumes Tuesday's ticket desk in MySQL: tables with columns and types only, rows loaded by INSERT, and the duplicate ticket 1 that a table with no key let in. It teaches the keys that identify rows and link tables, normalization from a flat sheet to third normal form, the constraints that make the server refuse bad rows, cascades and a rebuild script, and INSERT, UPDATE and DELETE from Python. Afterwards you can explain a primary, foreign, composite, unique and alternate key, walk a table from 0NF to 3NF with a reason per step, and name every constraint an interviewer lists.

Keys

Primary, candidate and composite keys

Tuesday's tickets table had columns and types and nothing else, and a table declared with no primary key and no unique key accepts two identical rows.1 That is how a second ticket 1 got in. A key is the rule that stops it.

What a primary key guarantees

A primary key is the column, or set of columns, whose value picks out exactly one row. MySQL holds two promises for it: the value is unique across the table, and it is never NULL, because a primary key column is implicitly NOT NULL.1 A table has at most one primary key.1

Everything that refers to a row depends on those two promises. A foreign key in another table, the WHERE of an UPDATE and a Python object rebuilt from the row all assume the id they hold means one row and only one.

The examples on this page run in order in a scratch database called keys_lab, so the desk's own database stays as its rebuild leaves it. Open the client in the container and type:

CREATE DATABASE keys_lab;
USE keys_lab;
CREATE TABLE tickets (
    ticket_id INT PRIMARY KEY,
    title VARCHAR(200)
);

The client answers Query OK, 1 row affected, then Database changed, then Query OK, 0 rows affected. Now try the duplicate that Tuesday's table let in, and a row with no id at all:

INSERT INTO tickets (ticket_id, title) VALUES (1, 'Login page returns 500');
INSERT INTO tickets (ticket_id, title) VALUES (1, 'Login page returns 500');
INSERT INTO tickets (ticket_id, title) VALUES (NULL, 'Invoice PDF is blank');
Query OK, 1 row affected
ERROR 1062 (23000): Duplicate entry '1' for key 'tickets.PRIMARY'
ERROR 1048 (23000): Column 'ticket_id' cannot be null

Error 1062 is the duplicate-key refusal, and it is what now turns away the second ticket 1.2 Error 1048 is the NOT NULL that came with the key.2 You recognise a primary key on sight as ticket_id INT PRIMARY KEY on the column's line, or as a PRIMARY KEY (ticket_id) line at the end of a CREATE TABLE. In DESCRIBE output its column shows PRI under Key.

Candidate keys: the columns that could be primary

Before you choose a primary key, list the candidates. A candidate key is a minimal set of columns whose value is unique and present in every row the table could ever hold, not only the rows it holds today. Each candidate has to pass three tests:

  • Unique: no two real rows could ever share the value. Two customers can share a name, so name fails.
  • Never null: every row has a value. A phone number that some customers never give fails.
  • Minimal: no column can be removed from the set and still leave it unique. The pair (customer_id, email) is unique, but customer_id alone already is, so the pair is not a candidate.

On the desk's customers table, customer_id and email each pick out exactly one customer, so both are candidate keys.1 One is chosen as primary, and every candidate left over becomes an alternate key, which the step after next covers.

The choice has a cost later on. A natural primary key that can change, such as an email, forces every foreign key that references it to change too.3 So the desk keys customers on a short integer that never changes and keeps the email beside it.

Composite keys

Some rows are identified by a combination. A composite primary key lists several columns in one PRIMARY KEY clause, and the combination must be unique, not each column on its own.1 The table that links tickets to tags is the standard case:

CREATE TABLE ticket_tags (
    ticket_id INT,
    tag_id INT,
    PRIMARY KEY (ticket_id, tag_id)
);
INSERT INTO ticket_tags (ticket_id, tag_id) VALUES (4, 2), (4, 3), (6, 3);
INSERT INTO ticket_tags (ticket_id, tag_id) VALUES (4, 2);
DESCRIBE ticket_tags;
Query OK, 0 rows affected
Query OK, 3 rows affected
Records: 3  Duplicates: 0  Warnings: 0
ERROR 1062 (23000): Duplicate entry '4-2' for key 'ticket_tags.PRIMARY'
+-----------+------+------+-----+---------+-------+
| Field     | Type | Null | Key | Default | Extra |
+-----------+------+------+-----+---------+-------+
| ticket_id | int  | NO   | PRI | NULL    |       |
| tag_id    | int  | NO   | PRI | NULL    |       |
+-----------+------+------+-----+---------+-------+
2 rows in set

Ticket 4 appears twice and tag 3 appears twice, yet only the repeated pair (4, 2) is refused.1 Both columns show NO under Null, because every column of a composite primary key is NOT NULL.1

A common question is why the table does not get its own link_id column instead. A lone generated id is unique on every row, so the same ticket and tag could be linked twice under two different ids; the composite key makes the duplicate link impossible.1 The limit is width. A foreign key must name the same columns as the key it references, so any table that points at a ticket_tags row would need both columns.3

Takeaways
  • A primary key is unique and never NULL, and a table has at most one.
  • A candidate key is a minimal unique, never-null column set; one becomes primary.
  • A composite key makes the combination unique, so each column may repeat on its own.
Say it in an interview

A primary key is the column or columns that identify exactly one row. The database guarantees it's unique and never null, and a table gets one of them. Without it, a table will accept two identical rows, and nothing that refers to the row can tell them apart.

To find candidate keys I ask which columns are unique for every row the table could ever hold, never null, and minimal. On a customers table both the id and the email qualify. I'd make the integer id primary because it never changes, and keep the email as an alternate key.

A composite key is a primary key over two or more columns, where only the combination has to be unique. I use one on a link table, like ticket id and tag id, so the same link can't be stored twice.

Keys

Foreign keys and referential integrity

A primary key names a row inside its own table. A database needs one table to be able to name a row in another, and the server to refuse a name that points at nothing.

A foreign key points at a parent row

A foreign key is a column in one table, the child, whose values must match a key in another table, the parent. InnoDB enforces foreign keys, and the referenced columns must be the parent's primary key or a unique key, with a compatible type in the child.3 InnoDB is MySQL's default storage engine, so a plain CREATE TABLE gets that enforcement.4

In the scratch database, give tickets a customer. DROP TABLE removes a table with its rows, as on Tuesday, so the table can be created again with the new column:

CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100)
);
DROP TABLE tickets;
CREATE TABLE tickets (
    ticket_id INT PRIMARY KEY,
    title VARCHAR(200),
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
);

Each of the three statements prints Query OK, 0 rows affected. The last line of the CREATE TABLE is the shape to recognise in any schema: FOREIGN KEY (child_column) REFERENCES parent (parent_column). The parent's key is named in brackets after the parent table.

A foreign key column may hold NULL unless it is also declared NOT NULL, and NULL means the row has no parent.3 On the desk that is how a ticket with no agent is stored: agent_id is NULL until someone picks the ticket up.

Referential integrity and the orphan row

Referential integrity is the guarantee that every foreign key value matches an existing parent row or is NULL. The failure it prevents is the orphan row, a child whose parent does not exist. An orphan ticket would name customer 99, and a report that looked up customer 99 would find no one to bill.

INSERT INTO customers (customer_id, name) VALUES (1, 'Dana Whitfield'), (2, 'Ravi Patel');
INSERT INTO tickets (ticket_id, title, customer_id) VALUES (1, 'Login page returns 500', 1);
INSERT INTO tickets (ticket_id, title, customer_id) VALUES (2, 'Ghost ticket', 99);
INSERT INTO tickets (ticket_id, title, customer_id) VALUES (3, 'Question by phone', NULL);
DELETE FROM customers WHERE customer_id = 1;
Query OK, 2 rows affected
Records: 2  Duplicates: 0  Warnings: 0
Query OK, 1 row affected
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`keys_lab`.`tickets`, CONSTRAINT `tickets_ibfk_1` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`customer_id`))
Query OK, 1 row affected
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`keys_lab`.`tickets`, CONSTRAINT `tickets_ibfk_1` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`customer_id`))

The integrity rule works from both sides. A child insert with an unknown parent id fails with 1452.3 Deleting a parent that a child still references fails with 1451, so Dana cannot vanish from under her ticket. From Python, mysql-connector-python raises both as mysql.connector.IntegrityError.5 The NULL customer on ticket 3 passes, because NULL claims no parent.

What happens on a parent delete is a choice written on the foreign key. Five referential actions exist:3

ActionWhen the parent row is deleted
RESTRICTThe delete is refused while children exist (1451).
NO ACTIONAlso refused; RESTRICT or NO ACTION is what you get when no action is written.
CASCADEThe child rows are deleted with the parent.
SET NULLThe child rows stay and their foreign key becomes NULL.
SET DEFAULTRejected by InnoDB.

RESTRICT protects data but forces the caller to delete the children first. CASCADE is convenient but can delete far more than intended.3 The CASCADE step later on this page puts both on the desk's tables.

Parents first, and what the check costs

Order matters twice. The parent table must exist before a child table that references it is created, and parent rows must be inserted before the child rows that name them.3 There is no agents table in the scratch database yet, so this fails:

CREATE TABLE agent_notes (
    note_id INT PRIMARY KEY,
    agent_id INT,
    FOREIGN KEY (agent_id) REFERENCES agents (agent_id)
);
ERROR 1824 (HY000): Failed to open the referenced table 'agents'

That is why a schema file creates its lookup and parent tables at the top. The check also has a price: a foreign key adds a lookup on every write to the child and on every delete or key change in the parent, which costs time on heavy writes.3 The price buys a database where no ticket can name a customer who does not exist.

Takeaways
  • A foreign key's values must match the parent's primary or unique key, or be NULL.
  • Referential integrity refuses orphans: 1452 on a bad child, 1451 on a referenced parent.
  • Create and fill parent tables before the child tables that point at them.
Say it in an interview

A foreign key is a column in a child table that has to match the primary key, or a unique key, of a row in a parent table. On a ticket desk, tickets carry a customer id that must exist in customers. It can be null if I allow that, which means the row has no parent, like a ticket nobody has picked up.

Referential integrity means every foreign key points at a row that really exists. The database enforces it both ways: it refuses a child row with an unknown parent, and it refuses to delete a parent that still has children, unless the key says to cascade or set null.

Keys

Unique keys and alternate keys

A primary key is one unique column set per table. Most tables have other columns that must not repeat either, and UNIQUE is how you say so.

UNIQUE and what it still allows

A UNIQUE constraint refuses a duplicate value, but for every engine it permits several NULLs in a column that can hold NULL.1 A table can have many UNIQUE keys and only one primary key.1 Add agents to the scratch database, with an email that may be missing:

CREATE TABLE agents (
    agent_id INT PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(255) UNIQUE
);
INSERT INTO agents (agent_id, name, email) VALUES (1, 'Priya', 'priya@desk.example');
INSERT INTO agents (agent_id, name, email) VALUES (2, 'Marco', 'priya@desk.example');
INSERT INTO agents (agent_id, name, email) VALUES (3, 'Sam', NULL), (4, 'Lee', NULL);
SELECT agent_id, name, email FROM agents;
Query OK, 0 rows affected
Query OK, 1 row affected
ERROR 1062 (23000): Duplicate entry 'priya@desk.example' for key 'agents.email'
Query OK, 2 rows affected
Records: 2  Duplicates: 0  Warnings: 0
+----------+-------+--------------------+
| agent_id | name  | email              |
+----------+-------+--------------------+
|        1 | Priya | priya@desk.example |
|        3 | Sam   | NULL               |
|        4 | Lee   | NULL               |
+----------+-------+--------------------+
3 rows in set

The duplicate email raises 1062, the same error a repeated primary key raises.2 The unique key takes its column's name, so the message says agents.email. Sam and Lee both got in with no email, which is the limit: on its own, UNIQUE does not promise that every row has a value. Pair it with NOT NULL when the column must identify a row.1

The two kinds of key differ in a handful of ways:

PRIMARY KEYUNIQUE
How many per tableAt most oneAs many as you need
NULL allowedNeverYes, several, unless the column is NOT NULL
Duplicate error1062 for key PRIMARY1062 for the key's name
A foreign key may reference itYesYes

The last row comes from the foreign key rule: the referenced columns must be the parent's primary key or a unique key.3 You recognise a unique key on sight as email VARCHAR(255) NOT NULL UNIQUE on the column's line, or as a named line such as UNIQUE KEY uq_email (email) in the table's definition.

Alternate keys, natural keys and surrogate keys

Every candidate key that was not chosen as primary is an alternate key, sometimes called a secondary key, and in MySQL it is declared UNIQUE NOT NULL.1 On the desk's customers, customer_id is primary and email is the alternate key.1

Two terms name the options. A natural key is a value with meaning outside the database, such as an email. A surrogate key is a meaningless generated id, such as customer_id. A surrogate id keeps foreign keys short and stable when the natural key changes.3

Suppose the desk had made email the primary key of customers. Every ticket would then carry the customer's email as its foreign key. When Dana changes her address, every one of her tickets would have to change too, or the key would need ON UPDATE CASCADE to carry the change down.3 With an integer primary key, her email changes in one row and no ticket notices.

A natural key still makes sense when the value truly never changes and is short. The desk's priorities lookup table is keyed on the word itself ('high', 'normal', 'low'), because a ticket that stores 'high' reads clearly and the words are fixed. In someone else's schema, the pattern to look for is an integer primary key with an email ... NOT NULL UNIQUE line right below it.

Takeaways
  • UNIQUE refuses duplicates but allows several NULLs unless the column is also NOT NULL.
  • An alternate key is a candidate key not chosen as primary, declared UNIQUE NOT NULL.
  • A surrogate primary key keeps foreign keys short and stable when a natural value changes.
Say it in an interview

A table has one primary key but can have many unique keys. Both refuse duplicates, but a primary key is never null, while a unique column can hold several nulls unless I also make it not null. That's why an email that must identify a customer is declared not null unique.

An alternate key is a candidate key I didn't pick as the primary key. For customers I'd make a generated integer the primary key and keep the email as the alternate key, because emails change and I don't want every ticket's foreign key changing with them.

Design

Normalization from 0NF to 3NF, and multiplicity

Keys say how rows are identified. Normalization decides which tables should exist in the first place, by asking of every column which key it is a fact about.

The flat sheet: unnormalized form

Teams often start with one sheet, one row per ticket:

ticketcustomeremailagentprioritysla_hourstags
1Dana Whitfielddana@example.comhigh4login
3Dana Whitfielddana@example.comnormal24
4Mei Chenmei@example.comPriyahigh4billing, ui
6Mei Chenmei@example.comlow72ui

This is unnormalized form, or 0NF. It reads easily and breaks in three ways, called anomalies:

  • Update anomaly: Dana's email sits on two rows, and changing one leaves the sheet disagreeing with itself.
  • Insert anomaly: a new customer with no ticket yet has no row to live on.
  • Delete anomaly: deleting Mei's last ticket would erase the only record that Mei exists.

No constraint can make the email on Dana's first row agree with the email on her second, so a fact repeated across rows can drift out of agreement; storing it once in a customers row prevents that.1

First normal form: one value per cell

A table is in first normal form (1NF) when every column holds one value and there are no repeating groups. The tags cell breaks it: 'billing, ui' is two values. The fix makes the list into rows, one row per ticket and tag, so ticket 4 now appears twice, once with billing and once with ui.

A foreign key compares a column's whole value with a parent key, so a comma list can never reference a tags table, while one tag per row can.3 The 1NF result gives tags a table of their own, keyed by tag_id.

Second normal form: facts about the whole key

After 1NF, the row for a ticket and a tag is identified by the pair, a composite key of ticket and tag. Second normal form (2NF) requires a 1NF table whose non-key columns depend on the whole key, not part of it.

The customer, agent and priority depend on the ticket alone, half of the key, so they move to a tickets table keyed on ticket_id. A tag's name depends on the tag alone, so it stays in tags, and ticket_tags keeps only the pair.

Third normal form: facts about nothing but the key

Third normal form (3NF) requires a 2NF table in which no non-key column depends on another non-key column. tickets still breaks it twice. sla_hours depends on the priority, since every high ticket has 4. The customer's name and email depend on the customer. Each moves to its own table, and tickets keeps only the key that points there:

  • priorities (priority, sla_hours), referenced by tickets.priority
  • customers (customer_id, name, email), referenced by tickets.customer_id
  • agents (agent_id, name), referenced by tickets.agent_id

The lookup table also guards its values. A foreign key refuses a value its parent does not hold (1452), so an unknown priority such as 'urgent' can no longer be stored.3 In the scratch database the new tables look like this; a line starting with -- is a comment:

-- 3NF: sla_hours depends on the priority, not the ticket
CREATE TABLE priorities (
    priority VARCHAR(10) PRIMARY KEY,
    sla_hours INT
);
-- 1NF: one tag per row, not a comma list
CREATE TABLE tags (
    tag_id INT PRIMARY KEY,
    name VARCHAR(30) UNIQUE
);
DROP TABLE ticket_tags;
-- 2NF: each row depends on the whole (ticket_id, tag_id) key
CREATE TABLE ticket_tags (
    ticket_id INT,
    tag_id INT,
    PRIMARY KEY (ticket_id, tag_id),
    CONSTRAINT fk_ticket_tags_ticket
        FOREIGN KEY (ticket_id) REFERENCES tickets (ticket_id),
    CONSTRAINT fk_ticket_tags_tag
        FOREIGN KEY (tag_id) REFERENCES tags (tag_id)
);
INSERT INTO tags (tag_id, name) VALUES (1, 'login'), (2, 'billing');
INSERT INTO ticket_tags (ticket_id, tag_id) VALUES (1, 1), (1, 2);

Each statement prints Query OK; the two INSERTs each report 2 rows affected. The CONSTRAINT names are explained in the next step.

Multiplicity and bridge tables

Multiplicity, or cardinality, says how many rows sit on each side of a relationship. Monday's ERD drew it as the crow's-foot ends of each line.

MultiplicityDesk exampleHow the tables express it
One-to-manyA customer files many ticketsA foreign key on the many side, tickets.customer_id
Many-to-manyA ticket has many tags; a tag labels many ticketsA bridge table whose composite primary key is its two foreign keys, ticket_tags
One-to-oneA customer and a single billing profileA foreign key that is also UNIQUE, so each parent has at most one child

A foreign key column holds one parent value per row, so it can express one-to-many directly but many-to-many only through a third table.3 Declaring the foreign key column UNIQUE allows each parent at most one child.1

What normalization buys and what it costs

Normalizing stores each fact once in a parent table that children reference by key, which removes the update, insert and delete anomalies.3 Dana now has her own row, so deleting her last ticket no longer erases her.

The cost is more tables, and a join to read one record back whole, which Thursday teaches. Teams sometimes denormalize on purpose, repeating data to save reads after measuring a slow query, usually in reporting tables. To design a schema for any flat data set, take it through the three forms, then give every table a primary key and every pointer a foreign key.

Takeaways
  • 1NF: one value per cell, so a comma list becomes one row per item.
  • 2NF: no column depends on only part of a composite key.
  • 3NF: no non-key column depends on another non-key column.
  • Many-to-many needs a bridge table keyed on its two foreign keys.
Say it in an interview

For first normal form, the comma list of tags becomes one row per ticket and tag. For second, the ticket's details depend only on the ticket, half of that key, so they move to a tickets table. For third, the SLA hours depend on the priority and the email on the customer, so each gets its own table.

One-to-many puts a foreign key on the many side, like a customer id on each ticket. Many-to-many needs a bridge table holding both foreign keys as its composite primary key. One-to-one is a foreign key that's also unique.

Normalizing removes update, insert and delete anomalies because each fact lives in one row. The cost is more tables and more joins to read a record back.

Constraints

Consistency through constraints

Consistency: rules the database holds for every writer

A database is consistent when every row obeys the rules that say what valid data is. Declared constraints are the schema's statement of those rules.6 The server refuses a statement that violates one, and InnoDB rolls back that statement, so no half-applied write is left.6

Strict SQL mode backs this up. With STRICT_TRANS_TABLES on, which is the default, an invalid or missing value is an error instead of a silent adjustment.7

A rule in the database holds for every client, while a rule kept only in application code can be bypassed by another writer, such as a script or a teammate at the prompt.6 Each constraint costs a check per write, but the rule lives in one place.6 In other people's code, the sign that this was missed is Python validation repeating a rule the schema could hold with NOT NULL or CHECK.

Constraints on a column, on a table, and by name

MySQL gives a table these constraints:

  • NOT NULL: the column must have a value
  • UNIQUE: no two rows share the value
  • PRIMARY KEY: unique and not null, one per table
  • FOREIGN KEY: the value must exist in the parent
  • CHECK: a condition every row must meet
  • DEFAULT: the value used when an INSERT leaves the column out

A column constraint sits on one column's line and applies to that column; a table constraint is its own line and can span several columns, as a composite key does.1 Any of them can be named with CONSTRAINT name, and ALTER TABLE adds or drops one later.8 A name makes the error message readable and the constraint easy to remove.

NOT NULL and DEFAULT

NOT NULL refuses NULL, and in strict mode an INSERT that omits a NOT NULL column with no default fails.9 DEFAULT supplies the value only when the INSERT omits the column or writes the keyword DEFAULT as its value.9 Together they require a value and name the one the server fills in. Add a status to the scratch tickets, then test it:

ALTER TABLE tickets
    ADD COLUMN status VARCHAR(10) NOT NULL DEFAULT 'open'
    CONSTRAINT chk_tickets_status CHECK (status IN ('open', 'assigned', 'closed'));
INSERT INTO tickets (ticket_id, title, customer_id) VALUES (4, 'Checkout button frozen', 2);
SELECT ticket_id, status FROM tickets;
UPDATE tickets SET status = 'done' WHERE ticket_id = 4;
INSERT INTO tickets (ticket_id, title, customer_id, status) VALUES (5, 'Export is missing rows', 2, NULL);
Query OK, 2 rows affected
Records: 2  Duplicates: 0  Warnings: 0
Query OK, 1 row affected
+-----------+--------+
| ticket_id | status |
+-----------+--------+
|         1 | open   |
|         3 | open   |
|         4 | open   |
+-----------+--------+
3 rows in set
ERROR 3819 (HY000): Check constraint 'chk_tickets_status' is violated.
ERROR 1048 (23000): Column 'status' cannot be null

The two existing rows took the default when the column arrived, and ticket 4 got it by leaving the column out. An explicit NULL is an error, not the default.9 The limit of a default is that it hides an omitted value instead of flagging it, so choose defaults that are truly sensible.9 On the desk, country CHAR(2) NOT NULL DEFAULT 'CA' is one.

CHECK

A CHECK is a condition every row must meet. MySQL enforces CHECK constraints since 8.0.16, so on 9.7, and a violating INSERT or UPDATE fails with error 3819.10 In the condition above, IN is true when the value equals one of the listed values; Thursday covers it with the other operators. From Python, the connector raises a CHECK failure as DatabaseError, not IntegrityError.11

Two limits matter. A CHECK that evaluates to NULL passes, so pair it with NOT NULL.10 And a CHECK cannot use subqueries or read other tables, so a list that grows belongs in a lookup table with a foreign key.10 That is why the desk keeps priorities as rows, where adding one is an INSERT, and keeps a CHECK list for its three fixed statuses.

You will meet CHECKs such as CHECK (monthly_fee >= 0) and CHECK (closed_at IS NULL OR closed_at >= opened_at). Read >= as "at least", IS NULL as "has no value" and OR as "either side is enough".

AUTO_INCREMENT and BIGINT ids

AUTO_INCREMENT makes the server generate the next integer for a key column, normally the primary key, when the INSERT omits it or passes NULL.12 An event log gains a row for every change to a ticket, so its id is a BIGINT:

CREATE TABLE ticket_events (
    event_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    ticket_id INT NOT NULL,
    kind VARCHAR(20) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_ticket_events_ticket
        FOREIGN KEY (ticket_id) REFERENCES tickets (ticket_id)
        ON DELETE CASCADE
);
INSERT INTO ticket_events (ticket_id, kind) VALUES (1, 'opened');
START TRANSACTION;
INSERT INTO ticket_events (ticket_id, kind) VALUES (4, 'opened');
ROLLBACK;
INSERT INTO ticket_events (ticket_id, kind) VALUES (4, 'opened');
SELECT event_id, ticket_id, kind FROM ticket_events;
Query OK, 0 rows affected
Query OK, 1 row affected
Query OK, 0 rows affected
Query OK, 1 row affected
Query OK, 0 rows affected
Query OK, 1 row affected
+----------+-----------+--------+
| event_id | ticket_id | kind   |
+----------+-----------+--------+
|        1 |         1 | opened |
|        3 |         4 | opened |
+----------+-----------+--------+
2 rows in set

Id 2 is missing. InnoDB hands out an auto-increment value before the row is checked, and a failed or rolled-back insert discards it, so ids have gaps.13 A gap is normal; code should never assume ids are consecutive. CURRENT_TIMESTAMP is a function the server runs for each new row, and a DATETIME column may take it as its default.14 The CASCADE line is the next step's subject.

BIGINT holds up to 9223372036854775807 signed, against 2147483647 for INT.15 An INT id overflows at its limit, and BIGINT delays that for log-like tables. You recognise the pattern as event_id BIGINT AUTO_INCREMENT PRIMARY KEY.

Takeaways
  • Constraints in the schema hold for every writer; the server refuses a violating statement.
  • NOT NULL requires a value; DEFAULT fills one in only when the column is left out.
  • CHECK fails with 3819, passes on NULL, and cannot read other tables.
  • AUTO_INCREMENT ids can have gaps; BIGINT suits fast-growing tables.
Say it in an interview

The constraints are not null, unique, primary key, foreign key, check and default, plus auto increment for generated ids.

Not null forces a value, unique stops duplicates, the primary key identifies the row, a foreign key must match a parent, a check is a condition every row has to meet, and default fills in a value when the insert leaves the column out.

I put rules in the schema because they hold for every client that writes to the database, including scripts and other services. For a status column I'd write not null, default open, and a check that the value is one of open, assigned or closed.

Constraints

CASCADE, and the CREATE, DROP, TRUNCATE rebuild

ON DELETE CASCADE and ON DELETE SET NULL

ON DELETE CASCADE on a foreign key deletes the child rows when their parent row is deleted.3 Without an ON DELETE action the parent delete is refused with 1451.3 In the scratch database, ticket_events cascades and ticket_tags does not yet, so deleting ticket 1 fails until the bridge's key is replaced by name:

DELETE FROM tickets WHERE ticket_id = 1;
ALTER TABLE ticket_tags DROP FOREIGN KEY fk_ticket_tags_ticket;
ALTER TABLE ticket_tags
    ADD CONSTRAINT fk_ticket_tags_ticket
    FOREIGN KEY (ticket_id) REFERENCES tickets (ticket_id)
    ON DELETE CASCADE;
DELETE FROM tickets WHERE ticket_id = 1;
SELECT ticket_id, tag_id FROM ticket_tags;
SELECT event_id, ticket_id, kind FROM ticket_events;
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`keys_lab`.`ticket_tags`, CONSTRAINT `fk_ticket_tags_ticket` FOREIGN KEY (`ticket_id`) REFERENCES `tickets` (`ticket_id`))

Deleting the ticket removed its two tag links and its event as well, because both keys now cascade.3 Look at the count, though: the client reported 1 row affected. A cascade can delete a whole tree of child rows in one statement while reporting only the parent.3 Cascades run inside the same statement and roll back with it.3

CASCADE suits rows that mean nothing without their parent, such as a ticket's tags and history. It is dangerous on a key like tickets.customer_id, where one careless DELETE of a customer would erase every ticket they ever filed. The desk leaves that key on the default, which refuses.

ON DELETE SET NULL keeps the child and clears its foreign key. The desk uses it for tickets.agent_id, so an agent who leaves turns their tickets back into unassigned ones instead of deleting them.3 Its relative, ON UPDATE CASCADE, carries a changed parent key down to the children.3 You recognise all of these on the foreign key's own line, after REFERENCES.

DROP, DELETE and TRUNCATE

Tuesday compared the three ways to remove data. Foreign keys and AUTO_INCREMENT add two more columns to that comparison:

StatementRemovesWHEREId counterUndo with ROLLBACK
DROP TABLEThe structure and every rowNoGone with the tableNo
DELETEMatching rows, one by oneYesKept where it wasYes
TRUNCATE TABLEEvery row, keeping the tableNoReset to the startNo

DROP TABLE removes structure and rows.16 DELETE without WHERE removes every row but keeps the structure and the AUTO_INCREMENT counter.17 TRUNCATE TABLE empties a table, resets its counter and causes an implicit commit, and it is refused on a table that another table's foreign key references.18 An implicit commit ends the current transaction, which is why a TRUNCATE cannot be rolled back.

TRUNCATE TABLE tags;
TRUNCATE TABLE ticket_events;

Query OK, 1 row affected

| event_id | ticket_id | kind     |
+----------+-----------+----------+
|        1 |         4 | assigned |
+----------+-----------+----------+
1 row in set

The bridge points at tags, so it cannot be truncated, even with no links left. Nothing references ticket_events, so it empties, and the next event starts again at 1. TRUNCATE is fast, but it takes no WHERE and cannot be undone.18

A rebuild script you can run twice

A schema file that can run twice gives the same database every time. Its first line is DROP DATABASE IF EXISTS, which removes a database and all its tables without an error when it is missing.19 The scratch database has done its job, so drop it twice:

DROP DATABASE IF EXISTS keys_lab;
DROP DATABASE IF EXISTS keys_lab;
Query OK, 7 rows affected
Query OK, 0 rows affected, 1 warning

The first run reports the seven tables it removed. The second finds nothing and warns instead of failing. Monday's file used CREATE TABLE IF NOT EXISTS, which skips creation when the table exists and so hides a stale structure; a rebuild drops instead.1 After the DROP and a CREATE DATABASE, the desk's file creates each parent before any table that points at it, and its seed file inserts in the same order:

  1. priorities, customers and agents, which reference nothing
  2. tickets, which references all three
  3. tags, which references nothing but must exist before the bridge
  4. ticket_tags and ticket_events, which reference tickets

The desk runs the schema file and the seed file as one stream into the client in the container. Run from the folder that holds both files:

cat schema.sql seed.sql | docker exec -i desk-mysql mysql -uroot -pdesk
mysql: [Warning] Using a password on the command line interface can be insecure.

cat prints the files one after the other, and the pipe | feeds that text into the client. The warning is the only output, because every statement succeeded.

Takeaways
  • CASCADE deletes children with the parent; SET NULL keeps them and clears the key.
  • TRUNCATE resets the id counter, commits at once and is refused on a referenced table.
  • A rebuild starts with DROP DATABASE IF EXISTS and creates parents before children.
Say it in an interview

On delete cascade means deleting a parent row also deletes its child rows, in the same statement. I'd use it for rows that mean nothing alone, like a ticket's tags or history. I wouldn't use it from customers to tickets, because one delete could wipe a customer's whole history, and the client only reports the parent row.

Drop removes the table itself. Delete removes rows, takes a where clause and can be rolled back. Truncate empties the table fast and resets the id counter, but it commits immediately and it's refused on a table a foreign key points to.

INSERT, UPDATE and DELETE from Python

The desk's Python code read and wrote tickets.json in week 2. From here it talks to MySQL through a driver, and the same three DML statements from Tuesday do the writing.

Connecting with mysql-connector-python

mysql-connector-python is MySQL's own driver for Python.20 Version 26.7.0 ships as a pure-Python wheel that installs on Python 3.15 with python -m pip install mysql-connector-python==26.7.0.20 Its connect() function takes the server's host and port, the user, the password and the database as keyword arguments.20

To try this step, set the password variable in Git Bash, start python in the desk's folder with its virtual environment active, and type the blocks one after another. The REPL reports an error and carries on. At the REPL, an empty line ends an indented block, so keep the empty lines the blocks show.

The password comes from an environment variable, set in Git Bash with export DESK_DB_PASSWORD=deskapp, so it never sits in a committed file. If the variable is missing, os.environ[...] raises KeyError. Each row arrives as a tuple, as the output shows.

The connector runs with autocommit off, so nothing a connection writes is saved until conn.commit().21 That is Tuesday's COMMIT, called from Python, and it ends the transaction.22 The desk ends every function that touches the database with one, even a read.

INSERT with placeholders

Values never go into the SQL text. The statement carries a %s placeholder for each value, whatever its type, and the values travel as a tuple that the driver escapes.22 A title with an apostrophe shows why, in the same session:

from datetime import datetime


def insert_ticket(conn, ticket_id, title, priority, customer_id, opened_at):
    """Insert one ticket and commit it."""
    cursor = conn.cursor()
    cursor.execute(
        """INSERT INTO tickets (ticket_id, title, priority, customer_id, opened_at)
        VALUES (%s, %s, %s, %s, %s)""",
        (ticket_id, title, priority, customer_id, opened_at),
    )
    conn.commit()
    cursor.close()


title = "Can't reset password"
insert_ticket(conn, 7, title, "high", 1, datetime(2026, 10, 19, 13, 0))
cursor.execute(f"UPDATE tickets SET title = '{title}' WHERE ticket_id = 6")

The insert prints nothing and commits ticket 7, with status filled in as 'open' by its DEFAULT. The f-string line fails, and its traceback ends:

mysql.connector.errors.ProgrammingError: 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 't reset password' WHERE ticket_id = 6' at line 1

The apostrophe in "Can't" closed the string early. A user who types a title on purpose can close it and add SQL of their own, which is SQL injection. With placeholders the title is only ever data. In code review, any f-string or + inside execute() is what to flag.

Two more habits come from the INSERT reference. Name the columns, because an INSERT without a column list breaks when the table gains a column. And one INSERT with several VALUES tuples inserts many rows in one statement.23 When the server generates the id instead, cursor.lastrowid returns the id the last INSERT generated.24

UPDATE and DELETE, and the rows they touch

UPDATE assigns several columns in one SET, separated by commas.25 It reports changed rows, so setting a value to what it already is reports 0.25 After a DELETE, cursor.rowcount counts the rows removed.26

closed = datetime(2026, 10, 19, 15, 0)
for attempt in range(2):
    cursor.execute(
        """UPDATE tickets
        SET status = 'closed', closed_at = %s
        WHERE ticket_id = %s""",
        (closed, 7),
    )
    print(cursor.rowcount)

cursor.execute("DELETE FROM tickets WHERE ticket_id = %s", (7,))
print(cursor.rowcount)
conn.commit()
1
0
1

The first UPDATE closed ticket 7, the second changed nothing, and the DELETE removed one row. Code that checks rowcount to learn whether a ticket exists has to remember the 0 from an unchanged row. An UPDATE or DELETE without WHERE touches every row, so a safe habit is to run the WHERE as a SELECT first.25

Many teams avoid DELETE for records they may need later and use a soft delete instead: a status or flag column marks the row as removed, and the history stays.17

A DELETE of a parent row is refused with 1451 or cascades, according to the foreign key's action.3 An UPDATE that breaks a CHECK or a foreign key fails and changes nothing.10 The constraint errors reach Python as exceptions:

try:
    insert_ticket(conn, 8, "Ghost ticket", "low", 99, datetime(2026, 10, 19, 13, 0))
except mysql.connector.IntegrityError as err:
    print(err.errno, err.msg)

try:
    cursor.execute("UPDATE tickets SET status = %s WHERE ticket_id = %s", ("done", 4))
except mysql.connector.DatabaseError as err:
    print(type(err).__name__, err.errno, err.msg)

conn.close()
1452 Cannot add or update a child row: a foreign key constraint fails (`ticket_desk`.`tickets`, CONSTRAINT `tickets_ibfk_2` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`customer_id`))
DatabaseError 3819 Check constraint 'tickets_chk_1' is violated.

The unknown customer 99 is a foreign-key error, raised as IntegrityError.5 The CHECK failure is a DatabaseError, so a handler that catches only IntegrityError misses it.11 Production code catches mysql.connector.Error, and a test names the exact class it expects.

Takeaways
  • With autocommit off, a write is saved only when the connection commits.
  • Pass values as placeholders with a tuple, never inside an f-string.
  • rowcount counts changed rows, so an UPDATE to the same value reports 0.
Say it in an interview

I write the statement with a placeholder for each value and pass the values as a tuple, so the driver escapes them. Building the SQL with an f-string lets a value change the statement itself, which is SQL injection, and even an apostrophe in a title breaks it.

To close one ticket I'd run an UPDATE that sets the status and closed time with a WHERE on the ticket id. Without the WHERE it would change every row, so I check the WHERE with a SELECT first. Then I commit, because the connector doesn't save anything until I do.

Check yourself

Check yourself

Ten retrieval questions covering every step. Answer each out loud before you open it.

What two things does a primary key guarantee, and how did a second ticket 1 get into Tuesday's table?

Every value is unique and none is NULL, and a table has one primary key. Tuesday's table had no primary key and no unique key, so the server had no rule against two identical rows.

A customers table has customer_id, email, name and phone. Which are candidate keys, which becomes primary, and what is the other called?

customer_id and email are each unique and always present; name can repeat and phone can be missing. Make the integer id primary because it never changes; the email becomes the alternate key, declared UNIQUE NOT NULL.

Errors 1452 and 1451 are both foreign-key refusals. Which side of the relationship causes each?

1452 comes from the child: an insert or update names a parent id that does not exist. 1451 comes from the parent: a delete or key change would leave children pointing at nothing. Together they are referential integrity.

Can a UNIQUE email column hold two NULLs, and what makes every row carry an email?

Yes; UNIQUE allows several NULLs in a column that can hold NULL. Adding NOT NULL makes the value required, which is how an alternate key is declared.

A flat sheet has one row per ticket with the customer's name and email, the priority, its SLA hours and a comma list of tags. Take it to 3NF, then make it a schema.

1NF: the tag list becomes one row per ticket and tag. 2NF: the ticket's details depend only on the ticket, so they move to tickets, and the bridge keeps only (ticket, tag). 3NF: SLA hours depend on the priority and the name and email on the customer, so each moves to its own table. Then give every table a primary key and every pointer a foreign key.

How do you store a many-to-many relationship between tickets and tags?

With a bridge table, ticket_tags, holding a foreign key to each side. Its composite primary key over the two columns stops the same link being stored twice.

Name the constraints you can declare on a table. Which one fills in a value, and which one refuses a value outside a list?

NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK and DEFAULT, with AUTO_INCREMENT for generated ids. DEFAULT fills in a value when the INSERT leaves the column out; a CHECK such as status IN ('open', 'assigned', 'closed') refuses anything else with error 3819.

An events table shows ids 1 and 3 but no 2. Is something wrong?

No. InnoDB hands out an auto-increment value before the row is checked, so a failed or rolled-back insert leaves a gap. Code should never assume ids are consecutive.

What does ON DELETE CASCADE do on ticket_tags, and why is it a bad idea on tickets.customer_id?

Deleting a ticket also deletes its tag links in the same statement. On the customer key, one DELETE would erase every ticket that customer filed, while the client reports only one row affected.

Why does the desk pass values as %s placeholders, and what does rowcount report for an UPDATE that sets a value it already has?

Placeholders send the values as data the driver escapes, so a value can never change the statement, which stops SQL injection. rowcount counts changed rows, so that UPDATE reports 0.
