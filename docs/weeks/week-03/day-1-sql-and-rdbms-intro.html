SQL & RDBMS introduction: from a JSON file to tables in MySQL

Week 3 · Day 1 Mon Oct 26, 2026 SQL with MySQL ~42 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-23 · python 3.15 · mysql 9.7 Exit criteria

This page assumes week 2's ticket desk, whose six tickets live in tickets.json, and a laptop that passed last Friday's Docker check. It runs MySQL 9.7 in a Docker container, then explains why records like the desk's belong in a relational database, what SQL is, and what a schema, a table and a data type are. It ends by modelling tickets, customers and agents as an ERD and writing that model as three CREATE TABLE statements. Afterwards you can explain an image, a container and a volume, argue for the relational model, choose between CHAR, VARCHAR, INT and DECIMAL, and read an ERD's crow's feet aloud.

MySQL

MySQL in a Docker container

Before any SQL, the database has to run somewhere. This step installs nothing on the laptop itself: the server runs inside a Docker container, and so does the program you type into.

MySQL: a database server

A database server is a program that keeps running, holds data on disk and answers requests from other programs. MySQL is a relational database management system, or RDBMS, and its default storage engine is InnoDB.1 The storage engine is the part that writes rows to disk and reads them back. A program that wants the data never opens those files. It connects to the server and sends statements, and the server can serve many such connections at once.2

This week's server is MySQL 9.7, the long-term-support line, pulled as the image tag mysql:9.7. A tag like that names a release line, and the patch release inside it can change between two pulls.3 That is why these notes write 9.7 and never a full patch number: two laptops that pulled a week apart may print different last digits, and both are right.

Images and containers

Docker separates two things that are easy to blur. An image is the read-only package of files and settings a program needs. A container is an isolated process started from an image, with its own filesystem, that runs until it stops.4 One image can start many containers, the way one installer can set up the same program on many machines.

docker images
docker pull mysql:9.7
docker images

The first listing shows hello-world, left behind by the Docker check, among any other images on the laptop. docker pull downloads the MySQL image without starting anything, and the second listing shows mysql with the tag 9.7 beside it.

The docker run line, flag by flag

One command creates and starts the desk's database server. It is long, and the table below takes it flag by flag.

docker run --name desk-mysql -e MYSQL_ROOT_PASSWORD=desk -p 3306:3306 -v desk-data:/var/lib/mysql -d mysql:9.7

It prints one long container id and hands the prompt straight back, because the container runs in the background.5

Two words in the table need a line first. A port is a numbered door on a machine: a server program listens at one number, and a client connects to that number to reach it. An environment variable is a named setting that a program can read when it starts.

FlagIn this lineWhat it does
--namedesk-mysqlGives the container a name, so later commands can say desk-mysql instead of the id.
-eMYSQL_ROOT_PASSWORD=deskSets an environment variable, a named setting the program reads at start; the image reads this one on first start to set the root password, and refuses to start without it.3

The line runs once per laptop. Run it a second time and Docker refuses, because the name desk-mysql is taken. The fix is docker start desk-mysql. Deleting the container and its volume to clear the error throws away the data you meant to keep. In Git Bash on Windows, the shell can rewrite /var/lib/mysql into a Windows path; putting MSYS_NO_PATHCONV=1 in front of the line stops that.

Volumes: where the data outlives the container

A container's own files sit in a writable layer that is deleted with the container. A database that kept its tables there would lose them the day someone removed and recreated the container. A Docker volume is storage that Docker manages outside any one container, so data written to it outlives the container.6 Mounting desk-data at /var/lib/mysql puts every MySQL file in the volume.

docker volume ls
DRIVER    VOLUME NAME
local     desk-data

On a laptop with other volumes the list is longer, and desk-data is one line of it. docker ps shows the running container, and its ports column reads laptop port 3306 mapped to container port 3306. docker stop desk-mysql halts the container and keeps it and its volumes, and docker start desk-mysql brings the same container back.7

Client and server: the client inside the container

The server is one program and the client is another. The server listens on port 3306, and the mysql command-line client connects to it, sends what you type and prints the answers. Because they talk over a port, the client could run on the laptop or inside the container. The MySQL image ships the client, and the official Docker instructions connect from inside the container.8 docker exec runs a command inside a running container, and -it gives it an interactive terminal.9

docker exec -it desk-mysql mysql -uroot -p

The client prints Enter password:. A bare -p with no value asks for the password, so it never appears in the command or the shell history.10 You type desk, nothing echoes, and the mysql> prompt appears. If Git Bash answers "the input device is not a TTY", put winpty in front of the same line.

SELECT VERSION();
+-----------+
| VERSION() |
+-----------+
| 9.7.x     |
+-----------+
1 row in set

VERSION() returns the server's version string, and the x stands for whatever patch the tag held when you pulled.11 A name followed by parentheses that hands back one value is a function; Thursday covers SQL's functions. Typing exit leaves the client.

Takeaways
  • An image is a read-only package; a container is a running process started from it.
  • The named volume keeps the database files when the container is removed.
  • The client and the server are separate programs that talk over port 3306.
Say it in an interview

MySQL is a relational database server: a program that keeps running, stores tables on disk through its storage engine, InnoDB, and answers SQL from any client that connects to it, many at the same time.

An image is the read-only package, and a container is a running process started from it. A container's own files go when the container is removed, so I mount a named volume at MySQL's data folder and the tables survive.

Introduction to RDBMS

Why a relational database

Week 2's desk keeps its six tickets in tickets.json. That works for one person on one laptop. This step gives the reasons a team moves records like these into a relational database.

What a JSON file cannot do for the desk

Here is one of the six records as the file stores it.

{
  "ticket_id": 4,
  "title": "Checkout button frozen",
  "priority": "high",
  "status": "assigned",
  "assignee": "Priya",
  "opened_at": "2026-10-19T08:00:00",
  "closed_at": null
}

To change this ticket's status, the desk loads all six records, changes one field and writes all six back. The whole file is the smallest unit of change, which has these costs.

  • Every save rewrites every record, even when one field changed.
  • The file holds no rules: a status of "closd" or a priority of 7 saves as happily as a correct value.
  • When two programs save at nearly the same moment, the later write replaces the earlier one and a change is lost.
  • Every question, such as "which open tickets are high priority?", means loading everything and writing a loop.

Tables, rows and relations

A relational database stores data as tables of rows and columns, and rows in different tables are related by matching column values.2 Drawn as a table, the desk's six tickets are six rows, and each JSON key becomes a column.

ticket_idtitleprioritystatusassigneeopened_at
1Login page returns 500highclosed2026-10-18 08:00
2Invoice PDF is blanknormalclosed2026-10-17 12:00
3Typo on pricing pagenormalclosed2026-10-18 18:00
4Checkout button frozenhighassignedPriya2026-10-19 08:00
5Export is missing rowsnormalassignedMarco2026-10-18 12:00
6Add dark modelowopen2026-10-19 12:00

Every row has the same columns, in the same order, and an empty cell is a missing value. The closed_at column is left off here to fit the page. The relation part comes next: the name in the assignee column is a fact about an agent, and it belongs in a table of its own.

One fact in one place

Suppose the desk also stored each agent's email inside every ticket the agent holds. When Priya's address changes, every copy has to be found and edited, and one missed copy leaves two answers to "what is Priya's email?". A relational design keeps that fact in one row of an agents table. Each ticket carries only a number, such as agent_id 1, and the agents row with the same number holds the name and the email.2

Changing the address is then one change to one row, and every ticket sees it at once because none of them holds a copy. Wednesday's page gives this idea its formal name, normalisation, and works through its rules.

Rules the database enforces, and many writers at once

A table declares a type for each column, and the server checks it. In strict SQL mode, which is on by default, MySQL refuses a value that does not fit a column's type instead of storing a changed one.12 The rule lives in the database, so a script, a web app and a teammate's report all meet the same check. Keys and constraints, which Wednesday adds, are further rules of the same kind.

The MySQL server handles many client connections at once, so several programs can read and write the same data through it.2 A change to one ticket is a statement about one row, so two programs changing two different tickets do not overwrite each other's work. Thursday's page covers how the server keeps two changes to the same row apart. And there is a query language: SQL says which rows are wanted, and the server works out how to find them.2

When a file or a document store fits better

These reasons have a limit. A relational table needs its columns declared before any row goes in, so changing the shape of the data is a deliberate change to the table, not a free edit.13 A settings file, a small tool one person runs, or records whose fields differ from one record to the next can stay in a file. They also suit a document store, a database that keeps each record as a JSON-like document.

On sight, file storage looks like code that loads a whole list, changes one item and dumps the whole list back. Database storage looks like code that sends one statement naming one row.

Takeaways
  • A JSON file is rewritten whole on every save and enforces no rules.
  • A relational database keeps each fact in one row and relates rows by matching values.
  • The server checks types and serves many writers; the price is a schema declared up front.
Say it in an interview

I'd use a relational database when the data has structure and more than one writer. Each fact is stored once, in one row, and other rows point at it by a value, so an update happens in one place and nothing drifts out of sync.

The database enforces rules itself. Every column has a type the server checks, and later keys and constraints, so every program that writes meets the same rules. It serves many connections at once, and I get SQL to ask questions instead of loading a whole file and looping over it.

The trade-off is the schema. I declare the shape up front, so changing it is a deliberate step. For a settings file or records whose fields vary a lot, a plain file or a document store can be the better fit.

What is SQL

What SQL is

Everything said to MySQL from here on is SQL, typed at the client's prompt or saved in a file. This step covers what kind of language it is and how the client reads it.

Structured Query Language

SQL stands for Structured Query Language.2 It is the standard language for describing the data in a relational database, changing it and asking questions of it. One language covers all three jobs: creating a table, putting rows in it and reading rows out are all SQL statements. Tuesday's page sorts the statements into families by job.

Is SQL a programming language? It is a language with one job, talking to a database. A Python program has variables, loops and functions that run step by step. Most SQL you write is a single statement, sent to the server, that comes back with a result or a message. Teams use both side by side, and from Wednesday the desk's Python code sends SQL to the server.

Declarative: say what, not how

SQL is declarative: a query says which rows are wanted, and the server chooses how to find them.2 Week 2's desk answered "which tickets are open?" with a loop that walked the list, tested each ticket and collected the matches. That is procedural code, where you spell out every step. In SQL the same question is one sentence that names the table, the columns and the condition, and the loop is the server's business.

The gain is that the server can pick a faster route as the table grows, without the query changing. The limit is that you see less of what happens, so a slow query needs the server's own tools to explain it; Friday's page shows one.

Statements at the mysql> prompt

At the mysql> prompt you type a statement and end it with a semicolon. Two first statements need no tables at all.

SELECT 1 + 1;
SHOW DATABASES;
+-------+
| 1 + 1 |
+-------+
|     2 |
+-------+
1 row in set

+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
4 rows in set

The client draws every result as a boxed table, even a single number. The four databases are the server's own system databases. A statement runs when it ends with a semicolon. Without one, the client changes its prompt to -> and waits for more lines.14

SELECT VERSION()
;

After the first line the prompt reads ->, which looks as if the client has hung. The lone semicolon on the second line ends the statement, and the version table prints. Because a statement can run over many lines, a long one is written with one clause or one column per line.

SQL keywords are not case sensitive, while whether table names are depends on the operating system the server runs on.15 A line that starts with two dashes and a space is a comment.16 Teams fix a house style so that every file reads the same, and this week's style is:

  • keywords in capitals, such as SELECT and CREATE TABLE
  • table and column names in lower snake case, with plural table names such as tickets
  • every statement ending with a semicolon
  • text values in single quotes
  • comment lines starting with -- and a space

SQL and MySQL: a standard and its dialects

SQL is a standard, and MySQL is one server that speaks it. MySQL follows the SQL standard, adds its own extensions and differs from it in places.17 PostgreSQL and SQL Server do the same with their own extensions, so each server speaks a dialect. Saying "I know SQL" is a claim about the language; "I know MySQL" is a claim about one product.

The trade-off is portability. Plain statements such as CREATE TABLE with common types move between servers with little change. Statements built on one server's extensions need rewriting on another, so code that must run on two servers sticks to the shared core. You recognise SQL on sight by capitalised keywords and a semicolon at the end, as in SELECT VERSION(); typed at the prompt.

Takeaways
  • SQL is Structured Query Language, the standard language of relational databases.
  • A declarative query names the rows wanted; the server decides how to find them.
  • A statement runs at its semicolon; without one the prompt waits at the arrow.
  • MySQL is one server with its own dialect of the SQL standard.
Say it in an interview

SQL stands for Structured Query Language. It's the standard language for defining, changing and querying the data in a relational database, and it's declarative: I say which rows I want and the server decides how to get them, where in Python I'd write the loop myself.

SQL is the language standard, and MySQL is one database server that implements it with its own extensions, like PostgreSQL or SQL Server do, so a query can need small changes when it moves between them.

Schema · Table structure

Schemas and table structure

A database needs a shape before it holds anything. This step names the parts of that shape and shows how to read it back from the server.

A schema is the shape, not the data

A database schema is the structure of the data: which tables exist, which columns each one has, the type of each column, and how the tables relate. The data is the rows that fill that structure. A blank form and a stack of filled-in copies is a fair picture: the schema is the form, and every copy is a row.

Describing a schema means naming those three layers in order. For the desk it reads:

  • customers, with the fields customer_id, name, email, country and monthly_fee
  • agents, with agent_id, name and email
  • tickets, with the week-2 record keys and agent_id in place of the assignee's name
  • two relationships: a ticket's customer_id matches one customer, and its agent_id matches one agent

The schema changes rarely and on purpose, while the rows change all day.

In MySQL a schema is a database

In MySQL, CREATE SCHEMA is a synonym for CREATE DATABASE, so a schema and a database are the same thing.18 Creating one needs the CREATE privilege, which the root account has.18 USE then makes it the default database for the statements that follow in the session.19

CREATE DATABASE ticket_desk;
USE ticket_desk;
SHOW TABLES;
Query OK, 1 row affected

Database changed
Empty set

The database exists and holds no tables yet. SHOW DATABASES now lists ticket_desk beside the system databases such as mysql and information_schema.20 The second of those, information_schema, is a read-only set of views that describes the server's own databases, tables and columns.21 Tools and tests read it to check what a schema really contains.

Some other servers treat a schema as a namespace inside a database. Because MySQL treats the two words as one, an interview answer should name the product before it defines the word.18

Rows, columns and fields

A table is a grid. Each column is a named attribute with one data type, such as title holding text. Each row is one record, such as ticket 4. A field is one cell: the value of one column in one row. The words overlap in practice, and MySQL's own listing of a table's columns heads them Field.

A column has exactly one type so that every value in it is the same kind of thing. The server can then check new values, compare them and sort them without guessing. An empty cell holds NULL, meaning "no value". A column declared with only a type accepts NULL.22 Wednesday's page adds the rules that forbid it.

Every column exists in every row, even when the cell is empty. A table with dozens of columns that are mostly NULL wastes space and usually means several kinds of thing were squeezed into one table.13

Say it in an interview

A schema is the structure of the data: the tables, the fields in each with their types, and how the tables relate. In a help desk, tickets, customers and agents are tables, and each ticket carries a customer id and an agent id that match rows in the other two.

In MySQL a schema and a database are the same thing; CREATE SCHEMA is a synonym. Some other servers treat a schema as a namespace inside a database, so I'd say which product I mean.

SQL data types

SQL data types

Every column gets exactly one data type. The type decides:

  • which values fit in the column
  • how much space each value takes
  • how values compare and sort

MySQL sorts its types into families.26

  • numeric: the integer, fixed-point, floating-point and bit-value types
  • string: types including CHAR, VARCHAR, TEXT and BLOB

Five types cover the whole desk.

ColumnTypeWhy this type
ticket_id, customer_id, agent_idINTwhole numbers that name one row
title, name, emailVARCHAR(n)text whose length varies
priority, statusVARCHAR(10)short words such as high or assigned
countryCHAR(2)always two letters, such as CA
monthly_feeDECIMAL(8,2)money, which must be exact to the cent
opened_at, closed_atDATETIMEa date and a time, with no time zone

Integers: INT and BIGINT

INT is a 4-byte integer. Signed, it runs from -2147483648 to 2147483647. BIGINT takes 8 bytes and holds far larger numbers.27 An id column of INT therefore runs out a little past two billion rows. That is plenty for customers and tickets, but a log that records every event on every ticket could pass it one day.

The trade-off is space against headroom: BIGINT doubles the storage of every value.27 Choose it for a table that may grow past two billion rows, and INT elsewhere. Wednesday's event history is the desk's first BIGINT column.

MySQL has no separate true-or-false column type. It accepts BOOL and BOOLEAN as synonyms for TINYINT(1), a small integer column, where 0 is read as false and 1 as true.28 A column shown as tinyint(1) in someone else's table is usually a flag.

DECIMAL for money, FLOAT approximate

DECIMAL(M,D) stores exact fixed-point values. FLOAT and DOUBLE store approximate ones.29 An approximate type keeps a binary fraction close to the number you gave it, so a price can come back a hair off. Summed over thousands of rows, those hairs turn into a total that does not match the invoice. An exact type stores 49.00 as 49.00, which is why money goes in DECIMAL.

In DECIMAL(8,2), the 8 is the total number of digits and the 2 is how many of them follow the decimal point, so the largest value is 999999.99.29 The limit is that you pick the size up front. A value that does not fit is refused under strict mode, so a column sized for monthly fees cannot later hold a yearly contract worth millions.12

CHAR and VARCHAR

CHAR(n) is fixed length: a stored value is padded with spaces to n characters, and the trailing spaces are removed when it is read back. VARCHAR(n) stores only the characters given, plus a short length prefix.30 Use CHAR when every value has the same length, such as a two-letter country code. Use VARCHAR for names, titles and emails, whose length varies.

The n counts characters, not bytes. Under the utf8mb4 character set one character can take up to four bytes.30 That set is MySQL's default, so a VARCHAR column stores accented letters and emoji with no extra settings.31 VARCHAR(100) means one hundred characters, so "Chloé" counts as five.

Two slips are common. One is making every text column VARCHAR(255), which hides what the data really is. The other is reaching for CHAR because a value is short, when its length still varies.

On sight, a good column list reads like the data it holds, as in the desk's customers table:

DESCRIBE customers;
+-------------+--------------+------+-----+---------+-------+
| Field       | Type         | Null | Key | Default | Extra |
+-------------+--------------+------+-----+---------+-------+
| customer_id | int          | YES  |     | NULL    |       |
| name        | varchar(100) | YES  |     | NULL    |       |
| email       | varchar(255) | YES  |     | NULL    |       |
| country     | char(2)      | YES  |     | NULL    |       |

+-------------+--------------+------+-----+---------+-------+

The server writes type names in lower case, whatever case the table was created with.

DATETIME and TIMESTAMP

DATETIME holds a date and a time from 1000-01-01 00:00:00 to 9999-12-31 23:59:59 and has no time zone attached. TIMESTAMP is stored as UTC, converted on the way in and out, and limited to 1970-01-01 through 2038-01-19.32 The interviewer's follow-up is usually "which would you use?", and the answer depends on what the times mean.

The desk's times in week 2's JSON carry no zone, such as 2026-10-18T08:00:00. DATETIME stores them exactly as written and hands them back unchanged. A TIMESTAMP column would shift them by the session's time zone, and it stops in 2038.32

Takeaways
  • INT holds about two billion; BIGINT goes further at twice the bytes.
  • DECIMAL is exact, so money goes in DECIMAL and never in FLOAT.
  • CHAR is fixed length; VARCHAR stores what it is given; both count characters.
  • DATETIME keeps the time as written; TIMESTAMP converts through UTC and ends in 2038.
Say it in an interview

I use CHAR when every value is the same length, like a two-letter country code, and VARCHAR when the length varies, like a name or an email. VARCHAR stores only what's there plus a small length prefix, and the number in brackets counts characters, not bytes.

Money goes in DECIMAL because it's exact. FLOAT is approximate, so cents drift when you add up a lot of rows. DECIMAL eight comma two holds up to 999,999.99.

INT is four bytes and tops out just over two billion. If a table could pass that, like an event log, I'd use BIGINT, which is eight bytes per value.

Data modeling and ERD

Data modelling and reading an ERD

The tables do not come first. A team first models the data on paper or a whiteboard, as an entity relationship diagram, or ERD, and only then writes the statements that create the tables.

From a description to entities, attributes and relationships

Data modelling starts from a plain description of the business. The desk's reads: "Customers file tickets. Each ticket has a title, a priority and a status, and records when it was opened and closed. Agents work the tickets, and a ticket is worked by at most one agent. The desk keeps each customer's name, email, country and monthly fee, and each agent's name and email."

  1. Pick out the nouns that the business keeps records about: customers, tickets and agents. Each becomes an entity.
  2. For each entity, list the facts that describe it. These are its attributes, such as a ticket's title and status.
  3. Give each entity one attribute that picks out exactly one instance, such as ticket_id.
  4. Read the verbs between entities ("files", "works") as relationships, and ask how many sit on each side.
  5. Translate: an entity becomes a table, an attribute becomes a column, and each instance becomes a row.33

Words that describe a value, such as "high" or "closed", are values of an attribute and not entities. Asking "would the business keep a list of these?" sorts most nouns quickly.

Reading the boxes

Each box in an ERD is one entity. The box lists the entity's attributes, and the one that picks out a single instance is marked: customer_id on customers, agent_id on agents, ticket_id on tickets.33 Here the marked attribute carries a #. Drawn in text, the desk's model looks like this:

+---------------+                  +---------------+
| customers     |                  | agents        |
+---------------+                  +---------------+
| # customer_id |                  | # agent_id    |
|   name        |                  |   name        |
|   email       |                  |   email       |
|   country     |                  +---------------+
|   monthly_fee |                          |
+---------------+                         -+-
        |                                  |
       -+-                                 |
        |                                 /|\
       /|\                                 |
+--------------------------------------------------+
| tickets                                          |
+--------------------------------------------------+
| # ticket_id                                      |
|   title, priority, status                        |
|   customer_id, agent_id, opened_at, closed_at    |
+--------------------------------------------------+

Three boxes and two lines. The short crossing bar sits at the customers and agents ends, and the three-pronged fork sits at the tickets end of both lines. The tickets box also carries customer_id and agent_id, and those shared attributes are what the lines are drawn through.33

Reading the lines: one-to-many and the crow's foot

One customer to many tickets is a one-to-many relationship. It is drawn with a single bar at the customer end and a crow's foot, the three-pronged fork, at the ticket end.33 Read the line twice, once from each box. From customers: one customer files many tickets. From tickets: each ticket belongs to one customer. The fork always sits on the "many" side.

The agents line reads the same way: one agent works many tickets, and a ticket names one agent through its single agent_id column. A ticket that nobody has picked up yet leaves that column empty, which is why the description says "at most one". Wednesday's page covers the other shapes a line can take and how each is built.

Reading the line backwards is the classic slip. Before trusting an ERD, say both sentences aloud and check each against the description.

What an ERD leaves out

An ERD records structure and relationships. It does not record the rules the database will enforce or the queries it will have to answer, so a model is checked against both before the tables are built.33 The desk's diagram does not say that a status must be one of three words, or that the busiest question is "which tickets are open?". Those come from the description and from the people who will use the data.

Tools draw ERDs as well as whiteboards do. MySQL Workbench, MySQL's own desktop design tool, draws an EER diagram (an enhanced ERD, its name for the same boxes and lines), generates the CREATE TABLE script from it, and can reverse-engineer a diagram from an existing database.34 On sight, an ERD in a design document is a set of named boxes listing columns, such as a tickets box with ticket_id, title and customer_id, joined by lines that end in bars and forks.

Takeaways
  • Entities become tables, attributes become columns, and instances become rows.
  • Each box marks the attribute that picks out one instance.
  • The crow's foot marks the many end of a one-to-many line.
  • An ERD shows structure, not the rules or the queries.
Say it in an interview

An ERD is an entity relationship diagram. Each box is an entity with its attributes listed and its identifying attribute marked, and each line is a relationship. The end with the crow's foot is the many side, so a bar at customers and a fork at tickets means one customer has many tickets.

To model a description, I pick out the nouns the business keeps records about as entities, list the facts about each as attributes, give each an identifying attribute, and read the verbs between them as relationships. Then each entity becomes a table and each attribute a column.

Defining schema

Defining the schema with CREATE TABLE

The ERD names the tables and columns, and the type table gives each column a type. This step writes both down as SQL, in a file the team keeps in Git, and runs it.

The shape of a CREATE TABLE

A CREATE TABLE statement names the table, then lists column definitions inside parentheses, separated by commas, and ends with a semicolon. Each column definition is a name followed by a data type.13 The desk's whole schema fits in one short file, schema.sql, written one column per line:

CREATE DATABASE IF NOT EXISTS ticket_desk;
USE ticket_desk;

CREATE TABLE IF NOT EXISTS customers (
    customer_id INT,
    name VARCHAR(100),
    email VARCHAR(255),
    country CHAR(2),
    monthly_fee DECIMAL(8,2)
);

CREATE TABLE IF NOT EXISTS agents (
    agent_id INT,
    name VARCHAR(50),
    email VARCHAR(255)
);

CREATE TABLE IF NOT EXISTS tickets (
    ticket_id INT,
    title VARCHAR(200),
    priority VARCHAR(10),
    status VARCHAR(10),
    customer_id INT,
    agent_id INT,
    opened_at DATETIME,
    closed_at DATETIME
);

Saving the file runs nothing; it prints output only when the client reads it, below. Every column traces back to a box in the ERD. The tickets table holds week 2's record keys, with agent_id in place of the assignee's name and a new customer_id. There are no keys and no rules yet, only names and types; Wednesday's page adds the rest.

Two slips break a statement like this. Column definitions are separated by commas, so a comma after the last column is a syntax error.13 A table named after a reserved word such as order or group must be quoted with backticks every time it is used, which is why schema names avoid those words.35

A schema file you can run again

Typing CREATE TABLE at the prompt works once and leaves no record. A .sql file is the source of the structure: it lives in Git beside the code, a teammate reads it in a review, and any laptop can rebuild the tables from it. The mysql client reads statements from standard input, the stream a program reads typed input from, so a shell redirect can feed it a file in place of the keyboard.10 From the folder that holds sql/schema.sql:

docker exec -i desk-mysql mysql -uroot -pdesk < sql/schema.sql
mysql: [Warning] Using a password on the command line interface can be insecure.

The < sends the file's contents into the command, and the line uses -i alone in place of -it.9

With no prompt to answer, the password rides in the same argument as -p. That works, and the client warns because a password on the command line is visible to other users of the machine.36 The warning is the only line printed, which means every statement in the file succeeded.

Run the same line a second time and it prints the same single warning. IF NOT EXISTS turns "this table already exists" from an error into a warning, so a file can be rerun from the top.13 Without it, the second run would stop at the first CREATE with an error.

When IF NOT EXISTS hides a mistake

The same clause has a cost. IF NOT EXISTS skips a CREATE TABLE whenever a table of that name exists, even when its columns differ from the file.13 Suppose you widen title to VARCHAR(300) in the file and rerun it. The run is quiet, and DESCRIBE tickets still shows varchar(200), because the old table was never touched.

The file and the database now disagree, and nothing said so. Wednesday's version of the file avoids the trap by dropping the whole database and creating it again from the top on every run.

Checking what you built

A file that ran without errors may still not hold what you meant, so read the result back. At the mysql> prompt, after USE ticket_desk;:

SHOW TABLES;
+-----------------------+
| Tables_in_ticket_desk |
+-----------------------+
| agents                |
| customers             |
| tickets               |
+-----------------------+
3 rows in set
DESCRIBE tickets;
+-------------+--------------+------+-----+---------+-------+
| Field       | Type         | Null | Key | Default | Extra |

| ticket_id   | int          | YES  |     | NULL    |       |
| title       | varchar(200) | YES  |     | NULL    |       |

Eight columns, the types from the file, and an empty Key column, since nothing is a key yet. The tables hold no rows; Tuesday's page puts the six tickets in. SHOW CREATE TABLE tickets prints the full statement the server would use to rebuild the table.25 Automated checks, such as tests, read the same facts from information_schema.21

Takeaways
  • CREATE TABLE lists comma-separated column names and types in parentheses, ending with a semicolon.
  • A schema file in Git is the source of the structure, run through a shell redirect.
  • IF NOT EXISTS makes a rerun safe but never changes a table that already exists.
  • SHOW TABLES and DESCRIBE confirm what the server really built.
Say it in an interview

For a table with an id, a short name, an amount of money and a created time, I'd write CREATE TABLE with four columns: the id as INT, the name as VARCHAR of a sensible length, the amount as DECIMAL with two decimal places, and the time as DATETIME, one column per line, ending with a semicolon.

IF NOT EXISTS lets me rerun the schema file without an error, but it skips a table that already exists even if I've changed its columns in the file. So after any run I check the result with SHOW TABLES and DESCRIBE.

Check yourself

Eight retrieval questions, at least one per section. Answer each out loud before you open it.

What is the difference between a Docker image and a container, and why do the desk's tables survive when the container is removed and created again?

An image is the read-only package of files and settings, such as mysql:9.7; a container is an isolated process started from it. The container's own files go with it, but the -v desk-data:/var/lib/mysql flag puts MySQL's data folder in a named volume, which Docker keeps outside any one container.

The docker run line fails the second time with a name conflict. What happened, and what should you run instead?

The container desk-mysql already exists, so the name is taken. Run docker start desk-mysql to bring the same container back; deleting the container and its volume to clear the error would throw away the data.

Give three reasons to keep the desk's tickets in a relational database instead of a JSON file, and one case where a file is fine.

Each fact lives in one row and other rows point at it, so an update happens in one place. The server checks every value against its column's type and serves many connections at once, and SQL answers questions without loading everything into a loop. A settings file or a small one-person tool, whose shape changes freely, can stay a file.

You type SELECT VERSION() at the mysql> prompt and press Enter. The prompt turns into -> and nothing prints. What is going on?

The statement has no semicolon, so the client is waiting for the rest of it. Type ; and press Enter, and the version table prints.

What is a database schema, and how does the word's meaning in MySQL differ from servers that use it as a namespace?

A schema is the structure of the data: the tables, the typed fields in each and the relationships between them; the rows are the data. In MySQL a schema is a database and CREATE SCHEMA is a synonym for CREATE DATABASE, while some other servers treat a schema as a namespace inside a database.

Pick a type for each: a product code that is always eight characters, a price, a product description, and the id of an event log that could pass two billion rows.

CHAR(8) for the fixed-length code, DECIMAL with two decimal places for the price because it is exact, VARCHAR(n) for the description whose length varies, and BIGINT for the log id because INT stops at 2,147,483,647.

An ERD shows a line with a single bar at customers and a crow's foot at tickets. Read it in both directions, and say how many agents one desk ticket can have.

One customer has many tickets, and each ticket belongs to one customer, because the fork marks the many side. A desk ticket names at most one agent, since it has a single agent_id column, while one agent can work many tickets.

You changed title to VARCHAR(300) in schema.sql and reran it with no error, but DESCRIBE tickets still shows varchar(200). Why?

CREATE TABLE IF NOT EXISTS skips a table whose name already exists, even when its columns differ from the file, so the old table was never touched. Reading the result back with DESCRIBE after every run is what catches it.
