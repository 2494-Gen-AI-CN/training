This page assumes Wednesday's constrained schema with its seeded rows, and the desk's Python code reading MySQL through mysql-connector-python. Clauses

Clauses: filtering, sorting and grouping rows

Every query on this page runs against the desk's seeded tables as Wednesday left them: six tickets, four customers, four agents and three priorities. Each result shown is what the mysql client prints for those rows, with the timing line left off.

The clauses of a SELECT, written and evaluated

A SELECT statement is made of clauses, each a keyword followed by its part of the question. You write them in one fixed order: SELECT, FROM, JOIN, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT.1 The server does not evaluate them in that order. It logically starts with FROM and WHERE and reaches SELECT near the end.1 The table lists the clauses in the order the server works through them.

ClauseWhat it does to the rows
FROM and JOINname the tables the rows come from
WHEREkeeps the rows that pass a condition
GROUP BYputs rows with equal values into one group
HAVINGkeeps the groups that pass a condition
SELECTpicks and computes the output columns
ORDER BYsorts the result
LIMITkeeps only the first rows of the sorted result

The gap between writing order and evaluation order explains two rules that trip people up. An aggregate such as COUNT(*) cannot appear in WHERE, and a column alias made in SELECT cannot be used in WHERE, because WHERE runs before either exists.2

WHERE with comparison and logical operators

WHERE keeps the rows for which its condition is true and drops the rest. Equality is = and inequality is <>. The ordering operators are <, <=, > and >=.3 AND joins two conditions that must both hold, and OR joins two of which either may hold.

SELECT ticket_id, title, status
FROM tickets
WHERE priority = 'high' AND status <> 'closed';
+-----------+------------------------+----------+
| ticket_id | title                  | status   |
+-----------+------------------------+----------+
|         4 | Checkout button frozen | assigned |
+-----------+------------------------+----------+

Two tickets are high priority, and ticket 1 is closed, so only ticket 4 survives both tests. String values sit in single quotes. When a condition mixes AND with OR, add parentheses so the reader does not have to remember which one binds first.

Sets, ranges, patterns and NULL

Four more operators cover the questions plain comparison cannot ask neatly.

  • IN (...) matches any value in a list, such as status IN ('open', 'assigned').3
  • BETWEEN a AND b matches a range and includes both of its end values.3
  • LIKE matches a pattern, where % stands for any run of characters and _ for exactly one.4
  • IS NULL and IS NOT NULL test for a missing value.5
SELECT ticket_id, opened_at
FROM tickets
WHERE opened_at BETWEEN '2026-10-18 00:00:00' AND '2026-10-18 23:59:59';
+-----------+---------------------+
| ticket_id | opened_at           |
+-----------+---------------------+
|         1 | 2026-10-18 08:00:00 |
|         3 | 2026-10-18 18:00:00 |
|         5 | 2026-10-18 12:00:00 |
+-----------+---------------------+

Because BETWEEN includes its ends, the upper bound is the last second of the day; ending it at midnight of the 19th would also catch a ticket opened exactly then. Missing values need their own test, and the wrong one fails without an error.

SELECT ticket_id FROM tickets WHERE agent_id = NULL;
SELECT ticket_id FROM tickets WHERE agent_id IS NULL;
Empty set
+-----------+
| ticket_id |
+-----------+
|         1 |
|         2 |
|         3 |
|         6 |
+-----------+

The first query raises no error and returns nothing, because col = NULL is never true, not even on a row whose agent is missing.5 In code review, = NULL in a WHERE clause is a bug on sight.

ORDER BY and LIMIT

ORDER BY sorts the result by one or more columns, and DESC after a column reverses it. LIMIT keeps the first rows of what is left, so the two together answer "the three newest tickets".

SELECT ticket_id, title, opened_at
FROM tickets
ORDER BY opened_at DESC
LIMIT 3;
+-----------+------------------------+---------------------+
| ticket_id | title                  | opened_at           |
+-----------+------------------------+---------------------+
|         6 | Add dark mode          | 2026-10-19 12:00:00 |
|         4 | Checkout button frozen | 2026-10-19 08:00:00 |
|         3 | Typo on pricing page   | 2026-10-18 18:00:00 |
+-----------+------------------------+---------------------+

LIMIT without ORDER BY returns an unspecified set of rows,1 so a query that happens to return the right three today can return different ones after the table changes. Treat a bare LIMIT in someone else's code as a question to ask.

GROUP BY and HAVING

GROUP BY puts the rows with equal values in the listed columns into one group, and the query returns one row per group.6 HAVING then filters those groups. WHERE filters rows before grouping and HAVING filters groups after aggregation, so COUNT(*) is legal in HAVING and illegal in WHERE.1

SELECT status, COUNT(*) AS tickets
FROM tickets
GROUP BY status
HAVING COUNT(*) > 1
ORDER BY status;
+----------+---------+
| status   | tickets |
+----------+---------+
| assigned |       2 |
| closed   |       3 |
+----------+---------+

The one open ticket forms a group of one, and HAVING drops it. Moving the condition into WHERE fails before any row is read.

SELECT status, COUNT(*) AS tickets
FROM tickets
WHERE COUNT(*) > 1
GROUP BY status;
ERROR 1111 (HY000): Invalid use of group function

One more rule comes with grouping. Under the default ONLY_FULL_GROUP_BY SQL mode, a selected column that is neither grouped nor aggregated is rejected with an error.6 Adding title to the SELECT list above is rejected, because a group of three closed tickets has three titles and the server will not pick one for you.

Takeaways
  • Clauses are written SELECT first, but the server evaluates FROM and WHERE first.
  • Test missing values with IS NULL, because a comparison with NULL is never true.
  • WHERE filters rows before grouping; HAVING filters groups after the aggregates are computed.
Say it in an interview

I filter rows with WHERE, using comparison operators such as equals, not-equals and greater-than, and I combine conditions with AND and OR. For a list, a range, a pattern or a missing value I reach for IN, BETWEEN, LIKE and IS NULL, and I never write equals NULL, because it is never true.

WHERE filters individual rows before grouping, and HAVING filters groups after the aggregates are computed, so a condition on a count or a sum goes in HAVING. GROUP BY returns one row per distinct value, and every column I select has to be grouped or aggregated, or MySQL rejects the query.

Functions

Scalar functions, aggregate functions and aliases

Scalar functions: one value per row

A scalar function takes values from one row and returns one value for that row. Most fall into string, date and numeric families, plus a few that deal with NULL. These are the ones a ticket desk uses most.

FunctionFamilyWhat it returns for one row
CONCAT(a, b, ...)stringits arguments joined into one string7
UPPER(s)stringthe string in capitals7
DATE_ADD(d, INTERVAL n unit)datethe date moved on by the interval8
NOW()datethe current date and time8
ROUND(x, d)numericthe number rounded, one row at a time9
COALESCE(a, b, ...)NULL handlingthe first argument that is not NULL3
 
SELECT CONCAT('TD-', ticket_id) AS ref,
       UPPER(priority) AS level,
       DATE_ADD(opened_at, INTERVAL 4 HOUR) AS four_hours_later,
       COALESCE(agent_id, 0) AS agent
FROM tickets
WHERE ticket_id <= 3;
+------+--------+---------------------+-------+
| ref  | level  | four_hours_later    | agent |
+------+--------+---------------------+-------+
| TD-1 | HIGH   | 2026-10-18 12:00:00 |     0 |
| TD-2 | NORMAL | 2026-10-17 16:00:00 |     0 |
| TD-3 | NORMAL | 2026-10-18 22:00:00 |     0 |
+------+--------+---------------------+-------+

Three rows went in and three came out, which is how you recognise scalar functions on sight. Because each one needs only the row in front of it, a scalar function also works in WHERE and ORDER BY.

Two details are easy to miss. CONCAT('TD-', ticket_id) turned a number into a string without being asked, and that implicit conversion means sorting by ref sorts text, so TD-10 would come before TD-2. And CONCAT returns NULL if any argument is NULL,7 so one missing value blanks the whole result.

SELECT CONCAT('closed ', closed_at) AS label
FROM tickets
WHERE ticket_id IN (1, 6);
+----------------------------+
| label                      |
+----------------------------+
| closed 2026-10-18 11:00:00 |
| NULL                       |
+----------------------------+

Ticket 6 is still open, so its closed_at is NULL and the label vanishes. Wrapping the column as COALESCE(closed_at, 'not yet') supplies a fallback.3

Aggregate functions: one value per group

An aggregate function collapses many rows into one value per group, or one value for the whole table when there is no GROUP BY.10 The five you meet everywhere are COUNT, SUM, AVG, MIN and MAX, and they differ in how they treat NULL and an empty input.

COUNT(*)rows10counted0
COUNT(col)non-NULL values10skipped0
COUNT(DISTINCT col)unique non-NULL values10skipped0
SUM / AVGtotal / mean10ignoredNULL

SELECT COUNT(*) AS tickets,
       COUNT(agent_id) AS assigned,
       COUNT(DISTINCT customer_id) AS customers,
       MIN(opened_at) AS first_opened,
       MAX(opened_at) AS last_opened
FROM tickets;
+---------+----------+-----------+---------------------+---------------------+
| tickets | assigned | customers | first_opened        | last_opened         |
+---------+----------+-----------+---------------------+---------------------+
|       6 |        2 |         3 | 2026-10-17 12:00:00 | 2026-10-19 12:00:00 |
+---------+----------+-----------+---------------------+---------------------+

Six rows became one: six tickets, two with an agent, and three distinct customers among them.

SELECT COUNT(*) AS customers, SUM(monthly_fee) AS revenue
FROM customers
WHERE country = 'FR';
+-----------+---------+
| customers | revenue |
+-----------+---------+
|         0 |    NULL |
+-----------+---------+

No customer is in France, and the revenue is NULL rather than 0. Code that adds that value to something else should wrap it in COALESCE. Mixing an aggregate with a plain column and no GROUP BY, as in SELECT COUNT(*), title FROM tickets, is an error under ONLY_FULL_GROUP_BY.6

Column and table aliases

A column alias is AS name after an expression. It becomes the column name of the result, so it is the header in client output and the key a program reads.1 A table alias such as tickets AS t gives a table a short name for one statement, and once a table is aliased, its columns are written with the alias.1 The word AS is optional for both, but writing it makes the intent clear.1

SELECT CONCAT('TD-', ticket_id) AS ref
FROM tickets
WHERE ref = 'TD-4';
ERROR 1054 (42S22): Unknown column 'ref' in 'where clause'

The alias does not exist yet when WHERE runs. The same alias works in ORDER BY, GROUP BY and HAVING, which run after SELECT has named it.2 An alias with a space in it needs backticks or quotes,11 so snake_case names such as open_tickets avoid the problem. A SQL alias lasts for one statement and has nothing to do with how Python names objects.

Window functions: aggregates that keep every row

GROUP BY collapses each group to one row. A window function computes over a set of related rows and still returns every row, and MySQL supports them from 8.0 with an OVER (...) clause.12 Inside OVER, PARTITION BY says which rows belong together and ORDER BY sets their order.

SELECT ticket_id, customer_id, opened_at,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY opened_at) AS nth
FROM tickets
ORDER BY customer_id, nth;
+-----------+-------------+---------------------+-----+
| ticket_id | customer_id | opened_at           | nth |
+-----------+-------------+---------------------+-----+
|         1 |           1 | 2026-10-18 08:00:00 |   1 |
|         3 |           1 | 2026-10-18 18:00:00 |   2 |
|         2 |           2 | 2026-10-17 12:00:00 |   1 |
|         5 |           2 | 2026-10-18 12:00:00 |   2 |
|         4 |           3 | 2026-10-19 08:00:00 |   1 |
|         6 |           3 | 2026-10-19 12:00:00 |   2 |
+-----------+-------------+---------------------+-----+

All six tickets are still there, each numbered within its customer. A GROUP BY on customer_id would have returned three rows and no ticket ids. Window functions are the usual next question after GROUP BY in an interview, and an OVER clause is how you spot one.

Takeaways
  • A scalar function returns one value per row; an aggregate returns one value per group.
  • COUNT(*) counts rows, COUNT(column) skips NULLs, and the other aggregates ignore NULL too.
  • A column alias names a result column and works after SELECT, never in WHERE.
  • A window function computes over related rows without collapsing them.
Say it in an interview

A scalar function returns one value for each row, like CONCAT, UPPER or DATE_ADD, so it can go in SELECT, WHERE or ORDER BY. An aggregate function such as COUNT, SUM, AVG, MIN or MAX collapses a set of rows into one value per group, so it goes in SELECT or HAVING and never in WHERE.

COUNT star counts rows and COUNT of a column skips NULLs. I give computed columns an alias with AS so the result has a readable name, and I alias tables so a join stays short and unambiguous.

Subqueries

Subqueries and common table expressions

What a subquery is

A subquery is a SELECT written inside another statement, in parentheses, whose result the outer statement uses. It comes in three shapes, named by where it sits and what it returns.13

  • A scalar subquery returns one value, so it can stand where a single value would.
  • A subquery after IN or EXISTS in WHERE supplies a list of values or a yes-or-no test.
  • A subquery in FROM is a derived table, a temporary result the outer query reads like a table.
SELECT ticket_id, title
FROM tickets
WHERE customer_id = (SELECT customer_id FROM customers WHERE email = 'dana@example.com');
+-----------+------------------------+
| ticket_id | title                  |
+-----------+------------------------+
|         1 | Login page returns 500 |
|         3 | Typo on pricing page   |
+-----------+------------------------+

The inner query finds Dana's id, 1, from her email, and the outer query uses it as if you had typed it. The email is UNIQUE, so the inner query can never return two rows. A scalar subquery that does return more than one row raises ERROR 1242.14

SELECT ticket_id, title
FROM tickets
WHERE customer_id = (SELECT customer_id FROM customers WHERE country = 'CA');
ERROR 1242 (21000): Subquery returns more than 1 row

Two customers are in Canada, and = cannot compare against two values. When the inner query can return several rows, the operator should be IN.

IN, NOT IN and EXISTS

IN with a subquery tests membership in whatever list the subquery returns. NOT IN asks the opposite, which finds the customers who have never opened a ticket.

SELECT name
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM tickets);
+-------------+
| name        |
+-------------+
| Omar Haddad |
+-------------+

The same pattern on agents goes wrong. Sam and Lee hold no tickets, yet asking for agents whose id is not in the tickets' agent_id column returns nothing. NOT IN returns no rows when the subquery's list contains a NULL,15 and four tickets have a NULL agent.

SELECT name
FROM agents
WHERE agent_id NOT IN (SELECT agent_id FROM tickets);
Empty set

NOT EXISTS does not have that problem.15 It asks, for each agent, whether any ticket row matches, and its subquery is correlated: it refers to a column of the outer query, so it is logically re-evaluated for every outer row.16

SELECT a.name
FROM agents AS a
WHERE NOT EXISTS (SELECT 1 FROM tickets AS t WHERE t.agent_id = a.agent_id);
+------+
| name |
+------+
| Sam  |
| Lee  |
+------+

You recognise a correlated subquery by an inner WHERE that names the outer alias, here a.agent_id. The SELECT 1 is a convention: EXISTS only cares whether a row comes back, so what it selects does not matter.

Derived tables and WITH

A subquery in FROM is a derived table, and it must have an alias.17 Leave the alias off and MySQL refuses the query. Derived tables let you aggregate an aggregate, such as the average number of tickets per customer.

SELECT AVG(per_customer.tickets) AS average_tickets
FROM (SELECT customer_id, COUNT(*) AS tickets FROM tickets GROUP BY customer_id) AS per_customer;
+-----------------+
| average_tickets |
+-----------------+
|          2.0000 |
+-----------------+

Nesting gets hard to read after one level. A WITH clause defines a common table expression, a named subquery written at the top, and MySQL supports it from 8.0.18 The main query then reads from the name as if it were a table.

WITH open_work AS (
  SELECT customer_id, COUNT(*) AS open_tickets
  FROM tickets
  WHERE status <> 'closed'
  GROUP BY customer_id
)
SELECT name
FROM customers
WHERE customer_id IN (SELECT customer_id FROM open_work WHERE open_tickets > 1);
+----------+
| name     |
+----------+
| Mei Chen |
+----------+

Mei has tickets 4 and 6 still open, the only customer with more than one. The query reads top to bottom: first the open work per customer, then who has more than one. A query that opens with WITH is a CTE on sight.

Subquery or join?

Many subqueries can be rewritten as the joins of the next two sections, and the choice is mostly about what the result needs.

  • Use a subquery when you need a value or a membership test from another table but none of its columns in the output, as in "tickets of the customer with this email".
  • Use a join when the output needs columns from both tables, as in "each ticket with its customer's name".
  • For "rows with no match", NOT EXISTS and the LEFT JOIN anti-join of the outer-joins section are equivalent; NOT IN is safe only when the inner column can never be NULL.
Takeaways
  • A subquery is a SELECT inside another statement: a value, a list or a derived table.
  • NOT IN returns nothing when the list holds a NULL; NOT EXISTS does not.
  • A WITH clause names a subquery so the main query reads top to bottom.
Say it in an interview

A subquery is a SELECT inside another statement. It can return a single value to compare against, a list for IN, a test for EXISTS, or a whole derived table in FROM. A correlated subquery refers to the outer row, so logically it runs once per outer row.

I use a subquery when I only need a value or a membership test from another table, and a join when the result needs columns from both. When a query has several steps I write them as WITH clauses, because named steps read top to bottom, and I prefer NOT EXISTS to NOT IN when the inner column can be NULL.

Joins

Joins: cross, equi, theta and inner

What a join is

Wednesday's schema stores each fact once. A ticket holds a customer_id, not the customer's name, so a question such as "which customer raised each ticket" needs two tables at once. A join combines a row of one table with a row of another wherever a condition pairs them, and the result has the columns of both.

The condition goes in ON, and it usually follows a foreign key back to the primary key it references. USING (customer_id) is shorthand when both tables share the column name.19 Several joins chain one after another in FROM, each with its own ON.19 In someone else's code a join looks like FROM tickets AS t JOIN customers AS c ON c.customer_id = t.customer_id.

Cross join and the Cartesian product

The simplest join has no condition. CROSS JOIN pairs every row of one table with every row of the other, which set theory calls the Cartesian product.19 Four agents and three priorities give twelve pairs, an on-call rota that lists every agent against every priority.

SELECT a.name AS agent, p.priority
FROM agents AS a
CROSS JOIN priorities AS p
WHERE a.agent_id <= 2
ORDER BY a.agent_id, p.sla_hours;
+-------+----------+
| agent | priority |
+-------+----------+
| Priya | high     |
| Priya | normal   |
| Priya | low      |
| Marco | high     |
| Marco | normal   |
| Marco | low      |
+-------+----------+

The WHERE keeps two agents so the output stays short; without it the rota has all twelve rows. A comma between tables, as in the older FROM agents, priorities, is also a cross join, with lower precedence than the JOIN keywords.19

The cost is that output grows multiplicatively, so a cross join of two large tables is a performance hazard.19 It also explains the most common join bug. In MySQL, JOIN, INNER JOIN and CROSS JOIN are syntactic equivalents, and an inner join with no match condition behaves as a cross join.19 FROM tickets AS t JOIN customers AS c with the ON forgotten returns 24 rows, six tickets times four customers, and every ticket appears to belong to everyone.

Equi and theta joins

An equi join's condition uses only =; a theta join uses any comparison operator.19 The ON clause may hold any condition that is valid in a WHERE clause.19 Joining each ticket to its priority is an equi join, and a scalar function on the joined row turns the SLA into a deadline.

SELECT t.ticket_id, t.priority, p.sla_hours,
       DATE_ADD(t.opened_at, INTERVAL p.sla_hours HOUR) AS deadline
FROM tickets AS t
JOIN priorities AS p ON p.priority = t.priority
ORDER BY t.ticket_id;
+-----------+----------+-----------+---------------------+
| ticket_id | priority | sla_hours | deadline            |
+-----------+----------+-----------+---------------------+
|         1 | high     |         4 | 2026-10-18 12:00:00 |
|         2 | normal   |        24 | 2026-10-18 12:00:00 |
|         3 | normal   |        24 | 2026-10-19 18:00:00 |
|         4 | high     |         4 | 2026-10-19 12:00:00 |
|         5 | normal   |        24 | 2026-10-19 12:00:00 |
|         6 | low      |        72 | 2026-10-22 12:00:00 |
+-----------+----------+-----------+---------------------+

Adding a comparison to the ON makes it a theta join. This one keeps only the tickets closed after their deadline, the breached ones.

SELECT t.ticket_id, t.title, t.closed_at
FROM tickets AS t
JOIN priorities AS p ON p.priority = t.priority
  AND t.closed_at > DATE_ADD(t.opened_at, INTERVAL p.sla_hours HOUR);
+-----------+----------------------+---------------------+
| ticket_id | title                | closed_at           |
+-----------+----------------------+---------------------+
|         2 | Invoice PDF is blank | 2026-10-18 18:00:00 |
+-----------+----------------------+---------------------+

Ticket 2 had 24 hours and took 30. The open tickets have a NULL closed_at, so the comparison is never true for them. A join on comparison alone is slower: with no equality condition, the hash join has nothing to build its lookup on, so every pair of rows is compared and the condition is applied as a filter.20

A self-join joins a table to itself, and it needs two aliases so each copy has a name. Pairing each ticket with a later ticket from the same customer combines an equality with a >.

SELECT a.ticket_id AS earlier, b.ticket_id AS later
FROM tickets AS a
JOIN tickets AS b ON b.customer_id = a.customer_id AND b.opened_at > a.opened_at
ORDER BY a.ticket_id;
+---------+-------+
| earlier | later |
+---------+-------+
|       1 |     3 |
|       2 |     5 |
|       4 |     6 |
+---------+-------+

NATURAL JOIN is a different thing from an equi join. It matches on every column the two tables share by name, so it silently changes if someone adds a same-named column, and an explicit ON is safer.19

Inner join

INNER JOIN returns only the rows where the ON condition is true, and the word INNER is optional.19 For an inner join, a condition placed in ON or in WHERE gives the same result.19 Joining three tables and filtering the joined rows looks like this.

SELECT CONCAT('TD-', t.ticket_id) AS ref, t.title, c.name AS customer, p.sla_hours
FROM tickets AS t
INNER JOIN customers AS c ON c.customer_id = t.customer_id
INNER JOIN priorities AS p ON p.priority = t.priority
WHERE t.status <> 'closed'
ORDER BY t.ticket_id;
+------+------------------------+------------+-----------+
| ref  | title                  | customer   | sla_hours |
+------+------------------------+------------+-----------+
| TD-4 | Checkout button frozen | Mei Chen   |         4 |
| TD-5 | Export is missing rows | Ravi Patel |        24 |
| TD-6 | Add dark mode          | Mei Chen   |        72 |
+------+------------------------+------------+-----------+

Every ticket has a customer and a priority, so nothing went missing here. The limit is that an inner join silently drops unmatched rows, so a report can under-count.19 Inner-joining these tickets to agents would keep only tickets 4 and 5, because the rest have no agent. Table order does not change an inner join's rows.19

Both tables here have a customer_id. Selecting it without a prefix gives ERROR 1052, "Column 'customer_id' in field list is ambiguous",19 which is why joined queries prefix every column with its table alias.

Takeaways
  • A join pairs rows of two tables wherever its ON condition holds, usually along a foreign key.
  • A cross join returns every combination; a forgotten ON does the same by accident.
  • An equi join compares with equals only; a theta join uses any comparison.
  • An inner join keeps only matched rows, so unmatched rows drop out without warning.
Say it in an interview

A join combines rows from two tables into one result row wherever a condition pairs them, usually a foreign key matching the primary key it points to. Relational schemas store each fact once, so a ticket holds a customer id and a join brings the customer's name back.

An inner join returns only the pairs where the condition is true, so rows with no match disappear. An equi join's condition uses only equals, a theta join's uses any comparison, and a cross join has no condition and returns every combination of rows.

Outer joins

Left, right and full outer joins, and UNION

Left and right joins

An inner join drops what does not match. An outer join keeps it. LEFT JOIN keeps every row of the left table and fills the right table's columns with NULL when nothing matches, and RIGHT JOIN is the mirror image.19 LEFT JOIN is shorthand for LEFT OUTER JOIN; the word OUTER is optional.19

SELECT a.name AS agent, t.ticket_id
FROM agents AS a
LEFT JOIN tickets AS t ON t.agent_id = a.agent_id
ORDER BY a.agent_id;
+-------+-----------+
| agent | ticket_id |
+-------+-----------+
| Priya |         4 |
| Marco |         5 |
| Sam   |      NULL |
| Lee   |      NULL |
+-------+-----------+

All four agents appear, and Sam and Lee carry NULL where a ticket would be. Writing the same join as FROM agents AS a RIGHT JOIN tickets AS t keeps every ticket instead: six rows, with a NULL agent on tickets 1, 2, 3 and 6. At the parser stage MySQL rewrites a RIGHT JOIN as the equivalent LEFT JOIN with the tables swapped,21 so most teams write only LEFT JOIN and put the table they must keep first.

Those NULLs reach a program too. The connector converts each returned value to a Python object,22 and a database driver hands SQL NULL to Python as None,23 so an unassigned ticket read through a LEFT JOIN on agents arrives with None as its agent's name. That is how the desk's Python code reads agent names once its two-query lookup becomes one join.

Finding the rows with no match

A LEFT JOIN followed by WHERE right_table.key IS NULL keeps only the left rows that found no partner. This anti-join pattern is the join form of NOT EXISTS.

SELECT c.name
FROM customers AS c
LEFT JOIN tickets AS t ON t.customer_id = c.customer_id
WHERE t.ticket_id IS NULL;
+-------------+
| name        |
+-------------+
| Omar Haddad |
+-------------+

A WHERE condition on the right table's columns also removes the NULL rows and turns the LEFT JOIN back into an inner join, so that condition belongs in ON.21

SELECT a.name AS agent, COUNT(t.ticket_id) AS open_tickets
FROM agents AS a
LEFT JOIN tickets AS t ON t.agent_id = a.agent_id AND t.status <> 'closed'
GROUP BY a.agent_id, a.name
ORDER BY a.agent_id;
+-------+--------------+
| agent | open_tickets |
+-------+--------------+
| Priya |            1 |
| Marco |            1 |
| Sam   |            0 |
| Lee   |            0 |
+-------+--------------+

This is an agent-load report. COUNT(t.ticket_id) skips the NULL on Sam's and Lee's rows and gives 0, where COUNT(*) would have counted their one unmatched row and said 1.

Full outer join through UNION

A full outer join keeps the unmatched rows of both sides. MySQL has no FULL OUTER JOIN keyword, and refuses a query that uses one. The standard emulation is a LEFT JOIN combined by UNION with a RIGHT JOIN.24

SELECT a.name AS agent, t.ticket_id
FROM agents AS a
LEFT JOIN tickets AS t ON t.agent_id = a.agent_id
UNION
SELECT a.name AS agent, t.ticket_id
FROM agents AS a
RIGHT JOIN tickets AS t ON t.agent_id = a.agent_id
ORDER BY ticket_id, agent;
+-------+-----------+
| agent | ticket_id |
+-------+-----------+
| Lee   |      NULL |

Transactions

Transactions and the ACID properties

What a transaction is

A transaction groups statements so that all of them take effect or none do.26 Tuesday met START TRANSACTION, COMMIT and ROLLBACK as the TCL statements. This section covers why they exist.

Assigning a ticket is two writes. The ticket's agent_id and status change, and a row in ticket_events records the assignment. If the update succeeds and the insert fails, the desk shows an assignment with no history, and nobody can say when it happened or who did it. Inside one transaction, the two writes succeed together or are undone together.

START TRANSACTION;
UPDATE tickets
SET agent_id = 3, status = 'assigned'
WHERE ticket_id = 6;
INSERT INTO ticket_events (ticket_id, kind, note)
VALUES (6, 'assigned', 'agent 3');
ROLLBACK;
SELECT t.ticket_id, t.status, t.agent_id,
       (SELECT COUNT(*) FROM ticket_events) AS events
FROM tickets AS t
WHERE t.ticket_id = 6;

The client answers each statement before the SELECT with a Query OK line. The SELECT then shows that both writes were undone:

+-----------+--------+----------+--------+
| ticket_id | status | agent_id | events |
+-----------+--------+----------+--------+
|         6 | open   |     NULL |      0 |
+-----------+--------+----------+--------+

With COMMIT in place of ROLLBACK, the same SELECT shows assigned, agent 3 and one event. Use a transaction whenever one business action needs more than one write, or reads a value and then writes based on it. Application code calls this pattern a unit of work: one action, one transaction.

Three more facts apply.

  • Only transactional engines such as InnoDB roll back; MyISAM does not.26
  • A transaction left open when the connection closes is rolled back, so a dropped connection loses the uncommitted work.27
  • Long transactions hold locks and snapshots, so keep them short.28

The four ACID properties

InnoDB, the storage engine behind the desk's tables, supports transactions with the ACID properties: atomicity, consistency, isolation and durability.29 Each one is a separate promise, and interviewers ask for all four.

PropertyWhat it guaranteesIn the ticket assignment
Atomicityall the statements commit, or none do29the update and the event row land together or not at all
Consistencya committed transaction leaves the data satisfying the schema's constraints29an event can never point at a ticket that does not exist
Isolationconcurrent transactions do not see each other's half-finished work, to a degree set by the isolation level29another agent's screen never shows the update without its event
Durabilitya committed change survives a crash, through the redo log and doublewrite buffer29the assignment is still there after the server restarts

Consistency is the property the constraints serve: Wednesday's keys and CHECKs define what "valid" means, and a statement that would break one is refused before it can be committed. Durability is the one the redo log serves.

Durability has a price. It costs a disk flush per commit, and the setting innodb_flush_log_at_trx_commit can relax it at the risk of losing the most recent commits.30 Some distributed data stores relax these guarantees on purpose, a style called BASE, and accept that their copies of the data agree only eventually.

Transaction properties: autocommit, implicit commits and the undo log

A few properties decide where a transaction starts and ends, and they explain most unexpected behavior.

  • Autocommit is on by default in the mysql client, so each statement is its own transaction until START TRANSACTION begins a multi-statement one.27
  • START TRANSACTION turns autocommit off until the next COMMIT or ROLLBACK.26
  • Connector/Python leaves autocommit off by default, so a write from Python needs conn.commit().31
  • InnoDB keeps the old version of each row a transaction changes in the undo log, so a rollback can restore it and other transactions can still read it.32

DDL statements such as CREATE TABLE and DROP TABLE cause an implicit commit and cannot be rolled back.33 Mixing DDL into a transaction therefore breaks its atomicity, as this run on the throwaway scratch_notes table shows.

START TRANSACTION;
INSERT INTO ticket_events (ticket_id, kind, note) VALUES (5, 'note', 'kept?');
CREATE TABLE scratch_notes (note_id INT PRIMARY KEY);
ROLLBACK;
SELECT ticket_id, note FROM ticket_events;

The ROLLBACK reports success, yet the event row survives:

+-----------+-------+
| ticket_id | note  |
+-----------+-------+
|         5 | kept? |
+-----------+-------+

The CREATE TABLE committed the INSERT before it ran, so the ROLLBACK had nothing left to undo. Drop scratch_notes and rebuild afterwards. In a script, SET autocommit = 0; near the top, or conn.autocommit = False in Python, is how you recognise code that manages its own transactions. Savepoints from Tuesday add partial rollback inside one transaction.

Takeaways
  • A transaction makes several statements take effect together or not at all.
  • ACID means atomicity, consistency, isolation and durability, each a separate promise.
  • The client autocommits each statement; Connector/Python does not, so writes need a commit.
  • DDL commits implicitly, so it cannot be rolled back.
Say it in an interview

A transaction is a group of statements the database treats as one unit: either all of them take effect or none do. I use one whenever a single business action needs more than one write, like assigning a ticket, which updates the ticket and inserts an event row. If either fails, both roll back.

Atomicity means all or nothing. Consistency means a committed transaction leaves the data satisfying the schema's constraints. Isolation means concurrent transactions don't see each other's half-finished work, to a degree the isolation level sets. Durability means a commit survives a crash, which InnoDB gets from its redo log.

Commit, rollback and isolation levels

COMMIT and ROLLBACK from Python

In Connector/Python the transaction statements are methods on the connection. start_transaction() begins a transaction, accepts an isolation_level argument, and raises ProgrammingError when a transaction is already in progress.34 commit() makes the work permanent,31 and on an error you call conn.rollback() before the exception leaves the function.35 The desk's assignment, written that way:

import logging

import mysql.connector

log = logging.getLogger(__name__)


def assign_ticket(conn, ticket_id, agent_id):
    """Give a ticket to an agent in one transaction, rolling back on any error."""
    cursor = conn.cursor()
    try:
        conn.start_transaction()
        cursor.execute(
            """UPDATE tickets
            SET agent_id = %s, status = 'assigned'
            WHERE ticket_id = %s AND status <> 'closed'""",
            (agent_id, ticket_id),
        )
        if cursor.rowcount == 0:
            raise ValueError(f"ticket {ticket_id} was not assigned")
        cursor.execute(
            """INSERT INTO ticket_events (ticket_id, kind, note)
            VALUES (%s, 'assigned', %s)""",
            (ticket_id, f"agent {agent_id}"),
        )
        event_id = cursor.lastrowid
        conn.commit()
    except (mysql.connector.Error, ValueError):
        conn.rollback()
        log.error("assignment of ticket %s rolled back", ticket_id)
        raise
    finally:
        cursor.close()
    return event_id

Defining the function prints nothing. The shape to recognise in anyone's code is try, the writes, commit(), then except with rollback() and raise. Calling it with the desk's connect() helper from Wednesday shows both paths.

The four isolation levels

Isolation decides what one transaction can see of another's work. InnoDB's default level is REPEATABLE READ, and the other three are READ UNCOMMITTED, READ COMMITTED and SERIALIZABLE.36

LevelWhat a plain read seesAnomaly it allows
READ UNCOMMITTEDother transactions' changes before they commit36dirty reads
READ COMMITTEDcommitted data only, but each read can see a newer commit36non-repeatable reads
REPEATABLE READ (default)the snapshot taken at its first read, so repeated reads agree37neither of those two
SERIALIZABLEthe same, but plain reads take shared locks when autocommit is off36none of those two; reads take shared locks, so other transactions block more

A dirty read is reading a change that another transaction may still undo. A non-repeatable read is reading the same row twice in one transaction and getting two answers. SET TRANSACTION ISOLATION LEVEL changes the level for the next transaction or for the session.38 The trade-off runs one way: stricter isolation reduces anomalies but increases blocking and deadlocks.36

Locks, deadlocks and retries

InnoDB implements the levels with row locks and consistent-read snapshots, so long transactions hold locks and snapshots longer.3628 Two transactions that each hold a lock the other is waiting for form a deadlock. Deadlocks are the cost of locking, they grow with stricter isolation,36 and the usual fix is to retry the transaction that failed.

Takeaways
  • In Python, commit at the end of the writes and roll back in the except block.
  • A read with autocommit off opens a transaction, so commit before starting another.
  • MySQL's default, REPEATABLE READ, reads from a snapshot taken at the first read.
  • Stricter isolation means fewer anomalies, more blocking and more deadlocks.
Say it in an interview

COMMIT makes every change in the current transaction permanent and visible to others, and ROLLBACK undoes all of them. In Python I start the transaction, run the writes and commit at the end; in the except block I roll back and re-raise, so a failure halfway never leaves half a change behind.

There are four isolation levels. READ UNCOMMITTED allows dirty reads, READ COMMITTED sees only committed data but a repeated read can change, REPEATABLE READ, MySQL's default, reads from a snapshot so repeated reads agree, and SERIALIZABLE also locks what it reads. Stricter levels mean fewer anomalies but more waiting.

CRUD: four letters, four statements

CRUD stands for create, read, update and delete. It is an industry name, not a MySQL keyword, and its four letters map to INSERT, SELECT, UPDATE and DELETE, the four statements the manual lists under Data Manipulation Statements.39 Job descriptions say "CRUD app" to mean an application whose main work is those four operations on its tables.

The two letters that change existing rows carry the classic accident. An UPDATE or DELETE without a WHERE clause touches every row of the table,40 so a reviewer reads the WHERE of every UPDATE and DELETE first.

Placeholders, rowcount and the dictionary cursor

cursor.execute(sql, params) sends the values separately from the SQL text.41 Each %s in the SQL is filled from the tuple, and the value is never pasted into the statement. An f-string does paste it, so a title containing a quote would end the string early and the rest of the title would run as SQL. That is SQL injection, and placeholders are the fix. AUTO_INCREMENT as MySQL's sequence

A sequence is a generator of increasing ids. PostgreSQL and Oracle have sequence objects, while MySQL has no CREATE SEQUENCE and uses an AUTO_INCREMENT column instead. A table has at most one, and it must be a key, typically the primary key.44 You recognise it by ticket_id INT AUTO_INCREMENT PRIMARY KEY in a schema and new_id = cursor.lastrowid in the code.

LAST_INSERT_ID() returns the first AUTO_INCREMENT value generated by the current connection's most recent INSERT, and another client's insert does not change it.45 cursor.lastrowid exposes that value in Connector/Python.46 Because it is per connection, two programs inserting at once each get their own id back.

The example below starts from a fresh rebuild, because the round trip above already moved the counter past 7: cat sql/schema.sql sql/seed.sql | docker exec -i desk-mysql mysql -uroot -pdesk.

A rolled-back INSERT still consumes its AUTO_INCREMENT value, so gaps are normal and ids are not a row count.47 Wednesday's refused foreign-key insert burned an id the same way.   • Pass values as placeholders with a tuple, never inside an f-string.

Ten retrieval questions, at least one per section. Answer each out loud before you open it.

A report should list only the statuses that more than one ticket holds. Why does WHERE COUNT(*) > 1 fail, and what replaces it?

WHERE filters single rows before any grouping, so no count exists yet and MySQL raises ERROR 1111. Group with GROUP BY status and filter the groups with HAVING COUNT(*) > 1.

Why does WHERE agent_id = NULL return no rows even though four tickets have no agent?

A comparison with NULL is never true, so no row passes. Missing values are tested with IS NULL or IS NOT NULL.

What is the difference between a scalar and an aggregate function? Give one example of each from the desk.

A scalar function returns one value per row, such as CONCAT('TD-', ticket_id) turning each ticket into a reference. An aggregate collapses many rows into one value per group, such as COUNT(*) per status.

On the seeded desk, COUNT(*) over the tickets gives 6 and COUNT(agent_id) gives 2. Why do they differ, and what does SUM return over zero rows?

COUNT(column) skips rows where that column is NULL, and four tickets have no agent. Over zero rows COUNT returns 0, while SUM, AVG, MIN and MAX return NULL.

A query for agents without tickets uses NOT IN (SELECT agent_id FROM tickets) and returns nothing. What went wrong, and what is the safe version?

The subquery's list contains NULLs from unassigned tickets, and NOT IN returns no rows when its list holds a NULL. Use a correlated NOT EXISTS, or a LEFT JOIN with WHERE t.ticket_id IS NULL.

A join of tickets to customers returns 24 rows instead of 6. What happened?

The ON condition is missing, so the join behaved as a cross join and paired each of the six tickets with all four customers. Add ON c.customer_id = t.customer_id, an equi join along the foreign key.

What is the difference between an inner join and a left join, and how do you write a full outer join in MySQL?

An inner join keeps only matched pairs; a left join keeps every row of the left table and fills the right side with NULL when nothing matches. MySQL has no FULL OUTER JOIN, so you combine a LEFT JOIN and a RIGHT JOIN with UNION.

Assigning a ticket updates the ticket and inserts an event row. Why must both run in one transaction, and which ACID property is that?

If the update succeeded and the insert failed, the desk would show an assignment with no history. Atomicity makes both statements commit together or neither, and a ROLLBACK on any error undoes the half that ran.

Under REPEATABLE READ, connection B reads a title, connection A changes it and commits, and B reads again without committing. Which title does B see, and what changes under READ COMMITTED?

B still sees the old title, because REPEATABLE READ reads from the snapshot taken at its first read. Under READ COMMITTED each read can see the newest commit, so B would see the new title.

A rolled-back INSERT took id 7 and the next INSERT got 8. Is something broken, and how should code learn a new row's id?

Nothing is broken: a rolled-back INSERT still consumes its AUTO_INCREMENT value, so gaps are normal. Read the id from cursor.lastrowid, which is per connection, rather than predicting it.
