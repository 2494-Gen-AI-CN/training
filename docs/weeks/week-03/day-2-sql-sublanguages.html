SQL sublanguages: the five kinds of statement that run the desk's tables

Week 3 · Day 2 Tue Oct 27, 2026 SQL with MySQL ~37 min · reference notes @150 wpm · diagram · check Sources checked 2026-10-23 · python 3.15 · mysql 9.7 Exit criteria

This page assumes Monday's ticket_desk database in the MySQL container, with its three empty tables for customers, agents and tickets. It teaches SQL's five sublanguages on those tables: DDL to shape a table, DML to fill and change its rows, DQL to read them, DCL to decide what an account may do, and TCL to group changes so they can be undone. An overview sorts every statement by what it acts on, and the last step turns the day into interview answers. Afterwards you can write CREATE, ALTER, TRUNCATE, DROP, INSERT, UPDATE and DELETE, explain DROP against DELETE against TRUNCATE, and say what ROLLBACK can and cannot undo.

DDL

DDL: statements that shape tables

Monday's page ended with three empty tables in the ticket_desk database: customers, agents and tickets. SQL statements fall into five groups that courses and interviewers call sublanguages, and this page takes them one at a time. The first group is the one that built those tables.

What DDL covers

DDL stands for Data Definition Language. Its statements define or change structure: a database, a table, the columns of a table and their data types. MySQL's manual files CREATE TABLE, ALTER TABLE, DROP TABLE and TRUNCATE TABLE together under Data Definition Statements.1 Each of the four does one job:

  • CREATE makes a new table, or a new database.
  • ALTER changes the columns of a table that already exists.
  • TRUNCATE empties a table and keeps the table.
  • DROP removes the table itself, rows and all.

In someone else's repository, DDL usually lives in a schema file full of CREATE TABLE statements, or in small change files whose lines start with ALTER TABLE. Either way it describes the shape of the data, and it says nothing about any particular customer or ticket.

CREATE TABLE

CREATE TABLE names a table and lists its columns, each with a data type.2 Adding IF NOT EXISTS makes the statement skip without an error when the table is already there, which is what lets a schema file run a second time safely.2 A scratch table is the right place to practise DDL, because no other table and no program depends on it.

USE ticket_desk;
CREATE TABLE scratch_notes (
  note_id INT,
  body VARCHAR(50)
);
Database changed
Query OK, 0 rows affected

"0 rows affected" is the normal answer to DDL. The statement made structure and touched no rows, so there was nothing to count.

TRUNCATE TABLE and DROP TABLE

TRUNCATE TABLE empties a table by dropping it and creating it again, so the table survives with no rows.4 It also resets an AUTO_INCREMENT counter to its start value.4 AUTO_INCREMENT is a column option, taught on Wednesday, that has the server number new rows by itself. Below, an INSERT (the next step's subject) gives TRUNCATE two rows to remove, and SELECT * reads every row back.

INSERT INTO scratch_notes VALUES (1, 'call back'), (2, 'refund sent');
TRUNCATE TABLE scratch_notes;
SELECT * FROM scratch_notes;
Query OK, 2 rows affected

"Empty set" shows the table still exists with nothing in it. TRUNCATE reports 0 rows affected even though two rows went, because it rebuilt the table instead of removing rows one at a time. The second DROP fails because the table is gone. DROP TABLE IF EXISTS suppresses that error for a missing table and records a note instead,5 which is why clean-up scripts are written with it.

DDL against DML, and why DDL cannot be undone

DDL acts on structure. DML, the next step, acts on the rows inside that structure. The split decides what can be undone. In MySQL most DDL statements cause an implicit commit: the server saves its work the moment the statement runs, so a ROLLBACK afterwards undoes nothing.6

So DROP TABLE cannot be rolled back.5 TRUNCATE is DDL as well, so it cannot be rolled back either.4 Step 5 shows what ROLLBACK does undo. On sight, ALTER TABLE scratch_notes ADD COLUMN author VARCHAR(50); and DROP TABLE scratch_notes; are both DDL: each names a table and changes what the table is.

Takeaways
  • CREATE, ALTER, TRUNCATE and DROP change structure, never individual rows.
  • ALTER TABLE adds, drops, modifies and renames columns on an existing table.
  • TRUNCATE empties a table and keeps it; DROP removes the table and its data.
  • DDL commits implicitly in MySQL, so ROLLBACK cannot undo it.
Say it in an interview

DDL is data definition language, the statements that shape the database: CREATE, ALTER, DROP and TRUNCATE. To practise I'd create a scratch table with CREATE TABLE and two typed columns, empty it with TRUNCATE TABLE, which keeps the table, and then remove it with DROP TABLE, which takes the definition and the data with it.

To change a table after it exists I use ALTER TABLE. ADD COLUMN puts a new column at the end, MODIFY changes a column's data type, and RENAME COLUMN or CHANGE renames one.

On a table that already has data I check the values before narrowing a type, because that can fail or cut them off. A DROP TABLE can't be rolled back in MySQL because DDL commits implicitly. The drop is saved the moment it runs.

DML

DML: adding, changing and removing rows

DML stands for Data Manipulation Language, the group that works on rows. INSERT adds rows, UPDATE changes them and DELETE removes them. The desk's three tables are still empty, so the first job is to fill them with the customers, agents and tickets the week-2 JSON file held.

INSERT with a column list

INSERT ... VALUES adds one or more rows to a table.7 A multi-row INSERT uses one VALUES list with each row written as a tuple in parentheses and the tuples separated by commas.7 The column list after the table name says which column each value goes to.

INSERT INTO agents (agent_id, name, email)
VALUES (1, 'Priya', 'priya@desk.example'),
       (2, 'Marco', 'marco@desk.example'),
       (3, 'Sam', 'sam@desk.example'),
       (4, 'Lee', 'lee@desk.example');
Query OK, 4 rows affected
Records: 4  Duplicates: 0  Warnings: 0

Strings go in single quotes. Every id is written out, because Monday's tables do not number new rows by themselves. The tickets follow the same shape, with NULL (no quotes) for a value that is not there: four of the six tickets have no agent yet.

INSERT INTO tickets (ticket_id, title, priority, status, customer_id, agent_id, opened_at, closed_at)
VALUES (1, 'Login page returns 500', 'high', 'closed', 1, NULL, '2026-10-18 08:00:00', '2026-10-18 11:00:00'),
       (2, 'Invoice PDF is blank', 'normal', 'closed', 2, NULL, '2026-10-17 12:00:00', '2026-10-18 18:00:00'),
       (3, 'Typo on pricing page', 'normal', 'closed', 1, NULL, '2026-10-18 18:00:00', '2026-10-19 04:00:00'),
       (4, 'Checkout button frozen', 'high', 'assigned', 3, 1, '2026-10-19 08:00:00', NULL),
       (5, 'Export is missing rows', 'normal', 'assigned', 2, 2, '2026-10-18 12:00:00', NULL),
       (6, 'Add dark mode', 'low', 'open', 3, NULL, '2026-10-19 12:00:00', NULL);
Query OK, 6 rows affected
Records: 6  Duplicates: 0  Warnings: 0

The scratch INSERT in step 1 left the column list out. That works only while the values line up with the table's columns in order. An INSERT with an explicit column list is safer than one that relies on column order, and it survives a column added later.7 A seed file that loads a table from scratch is a list of INSERTs like these two.

UPDATE and the WHERE that picks rows

UPDATE changes values in rows that already exist. SET names a column and its new value, and WHERE picks the rows. Here WHERE compares one column with =, which is all this page needs; Thursday teaches the other operators. An UPDATE with no WHERE clause changes every row in the table.8

UPDATE tickets
SET title = 'Add a dark mode'
WHERE ticket_id = 6;
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

UPDATE reports two numbers, the rows its WHERE matched and the rows it really changed. Run the same statement a second time and it matches one row but changes none, because the title already holds that value:8

Query OK, 0 rows affected
Rows matched: 1  Changed: 0  Warnings: 0

DELETE

DELETE removes rows and keeps the table. With WHERE it removes a chosen subset of rows; without WHERE it removes every row.9 Nothing in Monday's tables stops two rows from sharing an id yet, so a second ticket 1 loads without complaint. The SELECT with a column list, step 3's subject, shows both.

INSERT INTO tickets (ticket_id, title, priority, status, customer_id, agent_id, opened_at, closed_at)
VALUES (1, 'Login page returns 500', 'high', 'open', 1, NULL, '2026-10-20 09:00:00', NULL);
SELECT ticket_id, title, status FROM tickets WHERE ticket_id = 1;
Query OK, 1 row affected

+-----------+------------------------+--------+
| ticket_id | title                  | status |
+-----------+------------------------+--------+
|         1 | Login page returns 500 | closed |
|         1 | Login page returns 500 | open   |
+-----------+------------------------+--------+
2 rows in set

Two rows now answer to ticket 1, and any UPDATE or DELETE by that id hits both. That is the problem Wednesday's primary key solves. Until then, a second condition joined with AND tells the rows apart, since a row matches only when both conditions are true.

DELETE FROM tickets WHERE ticket_id = 1 AND status = 'open';
Query OK, 1 row affected

Rows affected: the client's receipt

Every INSERT, UPDATE and DELETE ends with a Query OK line that counts rows. Reading that count is the first check that a write touched the rows it was meant to:

  • INSERT counts the rows added, and a multi-row INSERT adds a Records line.
  • UPDATE counts the rows changed and adds Rows matched and Changed.
  • DELETE counts the rows removed, so 0 means the WHERE matched nothing.
DELETE FROM tickets WHERE ticket_id = 99;

This prints Query OK, 0 rows affected. "Query OK" means the statement was valid, which is not the same as doing what you wanted: no ticket 99 exists, so nothing went. The opposite alarm is a count far larger than expected. UPDATE tickets SET status = 'closed'; with its WHERE forgotten reports Rows matched: 6, every ticket on the desk.8

DROP against DELETE against TRUNCATE

All three statements remove something, and interviewers ask for the difference often. The table below puts them side by side.549

StatementSublanguageRemovesWHERE allowedRolls backAUTO_INCREMENT
DROP TABLEDDLthe table, its rows and its indexesnonogone with the table
TRUNCATE TABLEDDLevery row; the table staysnonoreset to its start value
DELETEDMLthe rows WHERE picks, or every rowyesyes, with InnoDBleft where it was

TRUNCATE takes no WHERE clause,4 and DELETE leaves the AUTO_INCREMENT counter where it was.9 The trade-off is speed against undo. DELETE removes rows one at a time, so it is slower than TRUNCATE on a large table, which is why TRUNCATE exists for emptying one.4 TRUNCATE pays for that speed with the undo: of the three, only DELETE can be rolled back.4

Takeaways
  • An INSERT with a column list survives columns added later.
  • UPDATE and DELETE without WHERE touch every row in the table.
  • The rows-affected count is the first check that a write hit the right rows.
  • Of DROP, TRUNCATE and DELETE, only DELETE can be rolled back.
Say it in an interview

For two rows I write INSERT INTO the table with the column list in parentheses, then VALUES with two row tuples. Spelling out the columns means it still works if someone adds a column later.

To retitle ticket 6 it's UPDATE tickets SET title to the new value WHERE ticket_id is 6, and DELETE FROM tickets WHERE ticket_id is the id removes one. Leave the WHERE off and they hit every row.

DROP removes the table itself, structure and data. TRUNCATE empties the table but keeps it, and resets the auto-increment counter. DELETE removes the rows a WHERE picks, or all of them, and keeps the counter. DROP and TRUNCATE are DDL and commit implicitly, so DELETE is the only one of the three I can roll back.

DQL

DQL: reading rows with SELECT

DQL stands for Data Query Language, and it holds one statement: SELECT, which reads rows and changes nothing. MySQL's manual files SELECT among its Data Manipulation Statements. The course splits it out as DQL because it reads and never writes.10 So when an interviewer asks whether SELECT is DML or DQL, both labels are in use.

SELECT and its column list

A SELECT names its columns in a comma-separated list after the keyword, and FROM names the table. The result shows the columns in the order the list gives them.11 A * in place of the list means every column, in the table's own order.

SELECT * FROM customers;

The footer counts the rows returned, and the client right-aligns numbers and left-aligns text. Ticket 6 shows the title the UPDATE in step 2 gave it. A SELECT without FROM can evaluate an expression on its own:11 SELECT VERSION(); returns one row holding the server's version, 9.7 followed by a patch number that moves with the image tag.

Reading one row by its id

WHERE works in a SELECT the way it works in UPDATE and DELETE: only rows whose condition is true come back. An id compared with = picks one ticket, and any other column can be compared the same way.

SELECT title FROM tickets WHERE ticket_id = 2;
SELECT ticket_id, title FROM tickets WHERE status = 'open';

Those two lines are the shape to recognise on sight: a column list, FROM one table, and a WHERE on one column. Sorting, the other comparison operators and grouping rows are Thursday's clauses. For now a habit is worth more: before an UPDATE or DELETE, run a SELECT with the same WHERE and look at what it returns.

Why application code avoids SELECT *

SELECT * is fine at the prompt, where a person reads the result. In application code it causes trouble, because it returns every column the table has today. A later ALTER TABLE changes what the caller receives.11 Code that reads the third value of each row gets a different column after someone adds one in the middle.

Naming the columns turns the query into a contract: the code asks for these columns in this order and gets exactly that, whatever else is added. It also documents what the code depends on, which helps the next person who wants to change the table.

Column aliases with AS

A column alias with AS renames a result column and does not change the table.11 It is the first way a query shapes its own output for the reader. The table keeps its column names; only the heading of the result changes.

SELECT ticket_id AS id, title AS summary FROM tickets WHERE agent_id = 1;
+------+------------------------+
| id   | summary                |
+------+------------------------+
|    4 | Checkout button frozen |
+------+------------------------+
1 row in set

Priya, agent 1, holds ticket 4. An alias earns its keep when the result column is computed instead of stored: SELECT name, monthly_fee * 12 AS yearly_fee FROM customers WHERE country = 'CA'; returns Dana Whitfield with 588.00 and Ravi Patel with 2388.00 under a heading that says what the number means.

Takeaways
  • SELECT reads rows and never changes them, which is why it gets its own label.
  • A column list picks the columns and sets their order in the result.
  • SELECT * in application code changes shape when the table does.
  • AS renames a result column without touching the table.
Say it in an interview

SELECT is the read statement. MySQL's manual files it with DML, but it's often taught as DQL, data query language, because it only reads. To pick columns I list them after SELECT, and to read one ticket I add WHERE ticket_id equals its id.

I avoid SELECT star in application code because it returns whatever columns the table has today. If someone adds a column with ALTER TABLE, the code gets a different result, so naming the columns keeps the query's shape stable.

DCL

DCL: who may run what

DCL stands for Data Control Language: GRANT and REVOKE, the statements that give an account permissions or take them away. Every statement so far ran as root, the account that may do anything to any database. A person setting up a schema needs that power. A program that only reads and writes tickets does not, so it gets an account of its own.

An account is a user and a host

A MySQL account is the pair user@host, and two accounts with the same user name and different hosts are two distinct accounts.12 The host part is part of the identity, and 'desk_app'@'%' matches a connection from any host, because % stands for any host.13 The desk's account uses it because the program that will log in with it runs outside the container.

Statements that name an account must name the same user and host pair. GRANT, REVOKE and SHOW GRANTS that leave the host off, or name a different one, talk about a different account.12

CREATE USER and GRANT

CREATE USER ... IDENTIFIED BY makes the account and sets its password. Since MySQL 8, GRANT no longer creates accounts, so the two statements come as a pair.13 GRANT gives privileges at a level, and ON ticket_desk.* covers every table of one database.14

CREATE USER 'desk_app'@'%' IDENTIFIED BY 'deskapp';
GRANT SELECT, INSERT, UPDATE, DELETE ON ticket_desk.* TO 'desk_app'@'%';
Query OK, 0 rows affected

Query OK, 0 rows affected

Privileges can be granted at the global, database, table, column and routine levels.14 The ON clause is where the level shows; the routine level belongs to Friday's stored procedures.

A common slip is ON ticket_desk without the .*. Written that way the grant does not match the desk's tables, so the account gets no privileges on them.

Privileges are checked when each statement runs, so the refused one fails with ERROR 1142 before it touches the table.14 The message says "command denied to user" and names the statement and the table.16 It also names the host the connection came from, here localhost, since this client runs inside the container, and '%' matches that host because % stands for any host.13

A DELETE as desk_app now fails with the same ERROR 1142, and the GRANT line run again restores it. One limit to know: a grant on ticket_desk.* survives DROP DATABASE and the re-creation of the tables.14 That is handy for a database rebuilt from files, and it also means a grant nobody remembers keeps working until someone revokes it.

Least privilege

Least privilege means giving an account only the permissions its job needs, so a mistake or a leaked password does less damage. The desk's program reads and writes tickets. It never needs to drop a table, so its account cannot, and a bug or a copied password cannot either. Root stays with the person who runs the schema file.

In someone else's project, least privilege shows up as a short GRANT naming only the statements the app uses, such as GRANT SELECT, INSERT, UPDATE, DELETE ON ticket_desk.* TO 'desk_app'@'%';. A program configured to log in as root is the line a reviewer flags.

Takeaways
  • A MySQL account is a user and a host, and every statement names the same pair.
  • CREATE USER makes the account; GRANT gives it privileges at a level such as one database.
  • SHOW GRANTS lists what an account holds, and REVOKE takes a privilege back.
  • An app account gets only the statements it needs, so it cannot drop tables.
Say it in an interview

GRANT gives an account permission to run certain statements on certain objects, for example SELECT, INSERT, UPDATE and DELETE on every table of one database. REVOKE takes a privilege back, and SHOW GRANTS FOR the account lists what it holds. If the account runs something it wasn't granted, MySQL refuses it with a command-denied error.

I'd give an application its own account instead of root because of least privilege. The app only reads and writes rows, so if its password leaks or the code has a bug, nobody can drop a table through it. The name desk_app at percent means the user desk_app connecting from any host.

TCL

TCL: changes that land or vanish together

TCL stands for Transaction Control Language: START TRANSACTION, COMMIT, ROLLBACK and SAVEPOINT. A transaction groups statements so that they apply together or vanish together.18 To commit is to make a change permanent. This step covers the statements at the prompt; the guarantees a transaction makes, and how two connections see each other's work, are Thursday's subject.

Autocommit: every statement saves itself

MySQL's autocommit setting defaults to 1, which means on. Each statement outside START TRANSACTION commits itself the moment it finishes.18 The @@ prefix reads one of the server's settings:

SELECT @@autocommit;
+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+
1 row in set

Autocommit is why every INSERT, UPDATE and DELETE on this page has been permanent so far. It is also the pitfall: a DELETE you did not wrap in a transaction is already saved by the time you notice the missing WHERE, and a ROLLBACK typed afterwards has nothing to undo.

START TRANSACTION, ROLLBACK and COMMIT

START TRANSACTION turns autocommit off until the next COMMIT or ROLLBACK.18 COMMIT saves everything since START TRANSACTION, and ROLLBACK throws it away. A ROLLBACK after a DELETE restores the deleted rows, and a SELECT shows them again.18 To see that safely, make the worst mistake on this page on purpose, inside a transaction:

START TRANSACTION;
DELETE FROM tickets;
SELECT * FROM tickets;
ROLLBACK;
SELECT ticket_id, title FROM tickets;
Query OK, 0 rows affected

Query OK, 6 rows affected

Empty set

+-----------+------------------------+
|         1 | Login page returns 500 |
|         2 | Invoice PDF is blank   |
|         3 | Typo on pricing page   |
|         4 | Checkout button frozen |
|         5 | Export is missing rows |
|         6 | Add a dark mode        |
+-----------+------------------------+
6 rows in set

The DELETE emptied the table for this connection, and ROLLBACK put all six tickets back. Only tables stored by InnoDB take part in a transaction. InnoDB is MySQL's default storage engine, the part of the server that keeps a table's rows, and it is the one that supports transactions.19 Monday's tables named no engine, so they are InnoDB.

Closing the client in the middle of a transaction rolls the transaction back.18 A window closed too early never leaves work half saved, but nothing is saved until COMMIT runs.

SAVEPOINT

SAVEPOINT names a point inside a transaction, and ROLLBACK TO SAVEPOINT undoes only the work done after it.20 The transaction stays open, and the work before the savepoint stays intact.20

START TRANSACTION;
UPDATE tickets SET priority = 'normal' WHERE ticket_id = 6;
SAVEPOINT before_title;
UPDATE tickets SET title = 'Dark mode' WHERE ticket_id = 6;
ROLLBACK TO SAVEPOINT before_title;
COMMIT;
SELECT ticket_id, title, priority FROM tickets WHERE ticket_id = 6;

The priority change came before the savepoint, so it survived and was committed. The title change came after it and was undone. A savepoint is useful in a long run of changes where one late step may need redoing without throwing away the rest.

What a ROLLBACK cannot undo

Statements that cause an implicit commit include most DDL (CREATE, ALTER, DROP, TRUNCATE) and account statements such as CREATE USER and GRANT.6 A DDL or account statement inside a transaction therefore commits it, and a ROLLBACK after it restores nothing.6

START TRANSACTION;
DELETE FROM agents WHERE agent_id = 4;
CREATE TABLE scratch_notes (note_id INT);
ROLLBACK;
SELECT agent_id, name FROM agents;
Query OK, 0 rows affected

Query OK, 1 row affected

+----------+-------+
| agent_id | name  |
+----------+-------+
|        1 | Priya |
|        2 | Marco |
|        3 | Sam   |
+----------+-------+
3 rows in set

Lee is gone. The CREATE TABLE committed the DELETE before it ran, so the ROLLBACK found nothing to undo. Running Lee's INSERT again and dropping the scratch table puts the desk back. ROLLBACK cannot undo:

  • a statement that ran while autocommit was on;
  • anything before the last COMMIT;
  • DDL such as DROP TABLE, TRUNCATE TABLE or ALTER TABLE;
  • account statements such as CREATE USER and GRANT.
Takeaways
  • Autocommit is on by default, so a statement outside a transaction is saved at once.
  • START TRANSACTION holds changes until COMMIT saves them or ROLLBACK discards them.
  • ROLLBACK TO SAVEPOINT undoes only the work after the savepoint.
  • DDL and account statements commit implicitly, so ROLLBACK cannot undo them.
Say it in an interview

COMMIT makes the changes of the current transaction permanent, and ROLLBACK throws them away. MySQL runs with autocommit on, so a statement outside START TRANSACTION commits itself straight away. That's why a DELETE without a WHERE is permanent unless I opened a transaction first.

A savepoint marks a point inside a transaction, and ROLLBACK TO that savepoint undoes only what came after it while the transaction stays open. I can't roll back a DROP TABLE, though, because DDL commits implicitly, even inside a transaction.

Overview

The five sublanguages side by side

Every statement on this page belongs to one of five groups. Interviewers ask for the groups by name, and then ask where a particular statement sits or which ones ROLLBACK can undo. Both answers come from one habit: look at what the statement acts on.

To place a statement you have not seen before, ask these questions in order:

  1. Does it change what a table is, its columns or its existence? DDL.
  2. Does it add, change or remove rows? DML.
  3. Does it only read rows? DQL.
  4. Does it change who may run what? DCL.
  5. Does it start, end or mark a transaction? TCL.

A typical exam question lists CREATE, GRANT, SELECT, INSERT and COMMIT and asks for the group of each. The answers in that order are DDL, DCL, DQL, DML and TCL.

Which statements ROLLBACK can undo

The same table answers the undo question. ROLLBACK discards the uncommitted work of the current transaction,18 and only InnoDB tables take part in one.19 DDL and account statements commit implicitly, so they are never uncommitted work.6 Group by group:

  • DML inside an open transaction is undone by ROLLBACK.
  • DQL changed nothing, so there is nothing to undo.
  • DDL and DCL commit implicitly, and they commit the DML that came before them too.
  • TCL statements are the controls themselves.

So the short answer is "uncommitted INSERT, UPDATE and DELETE". The longer answer adds the catch: a CREATE, DROP, TRUNCATE or GRANT in the middle of a transaction ends it, and the work before it can no longer be rolled back.

A teaching convention, and how the manual files statements

The five-way grouping is a teaching convention. The MySQL manual files its statements by function instead of by DDL and DML labels.23 This page's statements sit in four of its chapters:1102221

Takeaways
  • DDL shapes structure, DML changes rows, DQL reads, DCL sets permissions, TCL controls transactions.
  • ROLLBACK undoes uncommitted DML; DDL and DCL commit implicitly.
  • The five labels are a teaching convention; the MySQL manual files statements by function.
Say it in an interview

SQL is usually split into five sublanguages. DDL defines structure with CREATE, ALTER, DROP and TRUNCATE. DML changes rows with INSERT, UPDATE and DELETE. DQL is SELECT, which only reads. DCL is GRANT and REVOKE for permissions, and TCL is START TRANSACTION, COMMIT, ROLLBACK and SAVEPOINT.

ROLLBACK can only undo DML that hasn't been committed yet, so inserts, updates and deletes inside an open transaction. DDL and account statements like GRANT commit implicitly, so they can't be rolled back, and a SELECT changed nothing, so there's nothing to undo.

Interview prep

Getting ready for your interview, part 2

This second round of interview preparation turns the SQL so far into spoken answers. Three questions come up again and again at junior level: the difference between DROP, DELETE and TRUNCATE, what a GRANT does, and what ROLLBACK undoes. Each has a short answer that scores well and a common answer that loses marks.

The shape of a spoken answer

Spoken answers are scored on structure as much as on content. An interviewer listening to a ramble cannot tell which part was the answer. One shape works for almost any "what is" or "what's the difference" question:

  1. a one-sentence definition of the thing;
  2. one example statement, said in words;
  3. one limit: when it does not apply, or what it costs.

Applied to TRUNCATE it sounds like this: "TRUNCATE empties a table and keeps its structure. TRUNCATE TABLE scratch_notes removes every row. It's DDL, so it commits implicitly and can't be rolled back." That takes about fifteen seconds. The likely follow-up is why anyone would use it over DELETE, and the answer is speed on a large table.4

Practise aloud with a partner. One person answers, the other scores the three parts against this page, and then you swap. Saying an answer under a little pressure is a different skill from reading it silently.

DROP, DELETE and TRUNCATE, answered aloud

The answer that loses marks is "TRUNCATE is just a fast DELETE". It misses three things:

  • TRUNCATE is DDL.4
  • It resets AUTO_INCREMENT.4
  • It cannot be rolled back.4

A strong answer says what each statement removes. DROP removes structure and data, DELETE removes rows with a WHERE, and TRUNCATE removes all rows and keeps the structure.5

Re-create the scratch table from step 1 with its two notes, then run the three statements in order. Their receipts show the difference:

Expect two follow-ups. Which one can you roll back? Only DELETE, inside a transaction. Which is faster on a big table? TRUNCATE.

Pitfalls an interviewer listens for

Each of these slips shows up in interviews, and naming one before the interviewer does is a good sign:

  • running UPDATE or DELETE without WHERE and trusting ROLLBACK when autocommit already saved it;
  • expecting ROLLBACK to undo a DROP TABLE, ALTER TABLE or GRANT;
  • naming an account without its host part, or granting on ticket_desk instead of ticket_desk.*;
  • forgetting the semicolon, so the client shows its -> continuation prompt and waits;
  • writing a string in double quotes or leaving a closing quote off;
  • trusting SELECT * in application code until an ALTER TABLE changes the columns.
Takeaways
  • A spoken answer has three parts: a definition, one example statement and one limit.
  • TRUNCATE is DDL, resets AUTO_INCREMENT and cannot be rolled back.
  • GRANT needs an account from CREATE USER; ROLLBACK cannot undo DDL or GRANT.
Say it in an interview

DROP removes the whole table, definition and data. TRUNCATE removes every row but keeps the table and resets the auto-increment counter, and it takes no WHERE. DELETE removes the rows a WHERE picks, or all of them. DROP and TRUNCATE are DDL and commit implicitly, so DELETE inside a transaction is the only one I can roll back.

GRANT gives an existing account privileges on a database, a table or columns, for example read and write on every desk table but nothing that changes structure. ROLLBACK undoes the uncommitted changes of my current transaction. It can't undo a DROP, an ALTER or a GRANT, because those commit implicitly.

Check yourself

Answer each question out loud, as you would in an interview, before you open it. If an answer will not come, reread the step it belongs to.

Write the statements that create a scratch table, empty it and remove it.

CREATE TABLE scratch_notes (note_id INT, body VARCHAR(50)); creates it. TRUNCATE TABLE scratch_notes; empties it and keeps the table, and DROP TABLE scratch_notes; removes the definition and the data. All three are DDL.

How do you add a column to an existing table, and how do you change a column's data type?

ALTER TABLE with ADD COLUMN, as in ALTER TABLE scratch_notes ADD COLUMN author VARCHAR(50);, which puts the column at the end unless FIRST or AFTER says otherwise. ALTER TABLE with MODIFY, as in ALTER TABLE scratch_notes MODIFY body VARCHAR(500);, changes the type and keeps the name. Check the existing values before narrowing a type, because that can fail or cut data.

Write an UPDATE that retitles ticket 6 and a DELETE that removes ticket 3. What happens if you leave the WHERE off?

UPDATE tickets SET title = 'Add a dark mode' WHERE ticket_id = 6; and DELETE FROM tickets WHERE ticket_id = 3;. Without WHERE the UPDATE changes every row and the DELETE removes every row, and with autocommit on both are saved at once.

Explain DROP against DELETE against TRUNCATE, and say which of the three can be rolled back.

DROP removes the table itself, its definition and its data. TRUNCATE removes every row, keeps the table, takes no WHERE and resets AUTO_INCREMENT. DELETE removes the rows a WHERE picks, or all of them, and keeps the counter. DROP and TRUNCATE are DDL and commit implicitly, so only DELETE can be rolled back.

Is SELECT DML or DQL, and why avoid SELECT * in application code?

MySQL's manual files SELECT with the data manipulation statements; the course calls it DQL because it only reads. SELECT * returns whatever columns the table has today, so an ALTER TABLE changes what the code receives. Naming the columns keeps the result's shape fixed.

What does 'desk_app'@'%' mean, and why does the desk's program not log in as root?

It is the account with user desk_app connecting from any host; the host is part of the account's identity. The program gets SELECT, INSERT, UPDATE and DELETE on ticket_desk.* and nothing else, which is least privilege. A bug or a leaked password then cannot drop a table, and a DROP from that account fails with ERROR 1142.

You typed DELETE FROM tickets; and forgot the WHERE. When can ROLLBACK save you?

Only if you typed START TRANSACTION first. Then ROLLBACK restores every row. Without it, autocommit saved the DELETE the moment it ran, and ROLLBACK has nothing to undo.

Name the five sublanguages with one statement each, and say which ones ROLLBACK can undo.

DDL (CREATE), DML (INSERT), DQL (SELECT), DCL (GRANT) and TCL (COMMIT). ROLLBACK undoes uncommitted DML inside a transaction. DDL and account statements such as GRANT commit implicitly, and SELECT changes nothing.
