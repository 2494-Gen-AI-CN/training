Index management

Index management: finding near vectors without reading every row

Tuesday's page stored the help-centre articles and searched them. This step asks what makes that search fast; the next one covers how Pinecone manages the structure that does it.

Exact search: one comparison per stored vector

The simplest search compares the query with every stored vector and keeps the closest. That is exact search, also called flat search. It always finds the true nearest vectors, and its cost grows in proportion to the number of rows.1 The block below times it on random vectors of the size the week's model produces, 384 numbers each.

Run in Colab

import time
import numpy as np

rng = np.random.default_rng(42)
for n in [10_000, 100_000, 400_000]:
    vectors = rng.standard_normal((n, 384), dtype=np.float32)
    vectors /= np.linalg.norm(vectors, axis=1, keepdims=True)
    query = vectors[0]
    start = time.perf_counter()
    scores = vectors @ query
    top10 = np.argsort(-scores)[:10]
    seconds = time.perf_counter() - start
    print(f"{n:>7} rows  {vectors.nbytes / 1e6:4.0f} MB  {seconds:.4f} s  best={top10[0]}")

It prints one line per size. The memory column is plain arithmetic: 384 numbers of 4 bytes make 1,536 bytes a row, so the three sizes hold about 15 MB, 154 MB and 614 MB.2 The seconds depend on the machine, but each tenfold jump in rows makes roughly ten times the work, because every row is multiplied once. best=0 says the query's own row came first, as it must.

standard_normal with dtype=np.float32 draws 4-byte numbers directly, half the memory of the 8-byte default.2 The division by np.linalg.norm scales every row to length 1: axis=1 measures along each row, and keepdims=True keeps the lengths as a column so each row is divided by its own length. vectors @ query multiplies every row by the query at once, and np.argsort(-scores) lists row positions from the highest score down.

A vector index exists to avoid that full pass. It is a structure built beside the vectors so that a query reaches its near neighbours after visiting only a small share of them.

HNSW: a layered graph walked from the top

HNSW, short for Hierarchical Navigable Small World, is the index Chroma builds for each collection.3 It is a stack of graphs. Each vector is a point linked to a few of its near neighbours; the bottom layer holds every vector, and each layer above holds a smaller random subset with longer links.1 A search walks it like this:4

  1. Enter at the top layer, where the links are longest.
  2. Move to whichever linked neighbour is closest to the query, and repeat until no neighbour is closer.
  3. Drop to the same point one layer down and walk again.
  4. Stop on the bottom layer and return the closest points met.

The search cost grows about logarithmically with the number of vectors.1 As a worked number, log₂ of 1,000 is about 10 and log₂ of 1,000,000 about 20, so a thousand times more vectors roughly doubles the walk instead of multiplying it by a thousand.

The walk is greedy, and that is why the index is approximate. It can stop at a point whose neighbours are all farther from the query, while a closer vector sits in another part of the graph.4 Two settings tune the trade: more links per point (called M) and a longer candidate list during search (efSearch) raise recall and slow the search, and memory is set almost entirely by M.4

Recall measures the price of approximation: the share of the exact top 10 that the index returns. The block stores 2,000 random unit vectors, asks 20 queries, and checks each answer against numpy's exact ranking.

Run in Colab

data = rng.standard_normal((2_000, 384), dtype=np.float32)
data /= np.linalg.norm(data, axis=1, keepdims=True)
random_2k.add(ids=[str(i) for i in range(2_000)], embeddings=data)

queries = rng.standard_normal((20, 384), dtype=np.float32)
queries /= np.linalg.norm(queries, axis=1, keepdims=True)
found = random_2k.query(query_embeddings=queries, n_results=10, include=[])

hits = 0
for q, got in zip(queries, found["ids"]):
    exact = {str(i) for i in np.argsort(-(data @ q))[:10]}
    hits += len(exact & set(got))
print("recall:", hits / 200)

There are 20 × 10 = 200 true neighbours, so 184 found prints 0.92. Runs of this check on the pinned Chroma printed between about 0.90 and 0.96. The share moves a little because the graph is built slightly differently each time, and the index misses up to about one true neighbour in ten here.

include=[] asks for no documents, metadata or distances; the ids always come back, and they are all the check needs.22 exact & set(got) is the set of ids both lists share. A team runs this check on its own vectors and raises ef_search until recall is high enough.

Takeaways
  • Exact search compares the query with every vector, so its time grows with the rows.
  • HNSW walks a layered graph from the top: fast, and it can miss a true neighbour.
  • Space and graph size are fixed at creation; ef_search can be raised later to buy recall.
Say it in an interview

A vector index lets a search find the closest vectors without comparing the query with every stored one. Exact search costs time in proportion to the rows, so at millions of vectors it gets slow. HNSW links each vector to a few neighbours in layers, and a query walks from the top layer down, so the cost grows roughly logarithmically.

It's approximate because the greedy walk can stop at a local minimum and miss a true neighbour. I'd measure recall against an exact search on our own data and raise ef_search until it's high enough, accepting a slower query.

Index management in Pinecone

Index management in Pinecone: lifecycle, performance and backups

Chroma builds its index inside each collection. Pinecone makes the index itself the named thing a team creates, inspects, protects, tunes and backs up.

An index's lifecycle in Pinecone

In Pinecone the index is the thing you create and manage by name. The block installs the pinned client, reads the PINECONE_API_KEY Colab secret that Tuesday's page set up, and walks the lifecycle: create, describe, list, protect, and a delete that is refused.

The first line shows 384, cosine, the status and disabled. The status reads IndexStatus(ready=True, state='Ready') once the index takes requests. The second line lists the project's index names, including any made for something else.

Then comes "refused:" and the error text, [403 FORBIDDEN] Deletion protection is enabled for this index. Disable deletion protection before retrying.6 The pinned client raises it as a ForbiddenError.35 403 is the HTTP status a server sends when it understands a request and refuses it.

  • dimension and metric should match the embedding model: 384 and cosine for the week's model.7
  • describe_index returns the dimension, the metric, the host the data calls go to, the status and the deletion protection setting. These are the Python SDK's fields in the pinned client. On API version 2026-07 the raw REST response groups them into deployment, read_capacity and schema instead, while the SDKs still return the top-level fields as well.6
  • The free Starter plan supports only AWS us-east-1, which is why the spec names that region.8
  • configure_index changes deletion protection, tags, replicas, pod type and read capacity; it has no field for the metric or the dimension.9

The same lifecycle can be run by hand in the Pinecone console at app.pinecone.io. An index can be deleted there, and its backups are listed under the Backups tab or the Indexes tab.6

Pinecone's current docs call this kind of index, built from a dimension and a metric, a legacy vector index, and point new projects to a Documents API.7 The two styles do not mix on one index, so check that an example you copy uses the calls on this page.

The usual path is to start serverless, which is what the free plan gives, and to move an index with a steady, heavy read load to dedicated read nodes, accepting the one-namespace limit.

Backups, Pinecone collections and rollback

A backup is a static copy of a serverless index that cannot be queried and costs only storage. Restoring one creates a new serverless index in the same project and cloud.13 Backups can run on a daily, weekly or monthly schedule with a retention policy, which deletes old backups; scheduling needs API version 2026-04 or later, which the pinned client does not send. A backup holds only vectors that were in the index at least 15 minutes before it ran.13

A Pinecone collection, unrelated to a Chroma collection, is the older read-only snapshot of a pod-based index. Existing ones can still be listed, described and deleted, but a new one has no pod index to copy, and on API 2026-07 an index built from one is rejected with a 400.12 A backup plan built on collections now uses backups instead. Neither can be tried on a learner's account: backups are not offered on the Starter plan.1314

A backup and rollback plan has three parts:

  1. Scheduled backups with a retention policy cover disaster recovery: a restore makes a new index.13
  2. Each new version of the data goes into a new namespace while a namespace alias, a stable name for a namespace, still serves the old one; once the load checks out, the alias is repointed in one atomic step. Atomic means all at once, so no query sees a half-done change.15
  3. Rolling back is repointing the alias to the old namespace, kept until the new one has proved itself.

Creating aliases needs API version 2026-07, while reading through one works on any version.8 This page pins the pinecone 9.1.0 client on purpose, so the calls stay the same all week. That client sends API version 2025-10, so it can read through an alias but cannot create one, and the plan here is described, not run.16 The newest client, 10.3.0 (2026-11-03), sends 2026-07 and is not used.34

Takeaways
  • A Pinecone index is created, described, protected and deleted by name.
  • Deletion protection refuses every delete until it is switched off.
  • Serverless reads share capacity; dedicated read nodes give one index its own hardware.
  • Backups restore into a new index; an alias swap between namespaces gives rollback.
Say it in an interview

With the Pinecone SDK I check has_index, create the index with the model's dimension and metric and a serverless spec, then read describe_index for the host and status. I switch deletion protection on with configure_index for anything that matters, so a stray delete gets a 403.

For a Pinecone deployment I'd start serverless, and move a heavy read workload to dedicated read nodes. For backups I'd schedule them with a retention policy, load each new data version into a new namespace behind an alias, and roll back by pointing the alias at the old namespace.

Deleting a collection is destructive and cannot be undone.19 That is why the risky calls ran on a scratch copy. Names have rules too:19

  • 3 to 512 characters
  • starts and ends with a lowercase letter or digit
  • dots, dashes and underscores allowed in between
  • no two dots in a row
  • not shaped like an IP address

kb_scratch_old passes; KB fails, being under 3 characters. The pinned 1.5.9 also accepts upper-case letters, although the docs ask for lowercase, so lowercase names are the safe habit.

In other people's code, get_or_create_collection near the top of a script is the common way to open a collection that may or may not exist yet. Because it ignores new settings for a collection that exists, changing the space in that line later changes nothing.

One model and one size per collection

Every vector in a collection must have the same length. The block tries to add a vector of 768 numbers, the size a larger model might produce, to the 384-number collection.

Run in Colab

The first line names the problem in full: the collection was built for 384 numbers per vector, and the add sent 768. An embedding whose length differs from the collection's raises an exception.20 The second line shows that nothing was stored: the count is still 8.

Equal length is not enough. Two models of the same size place texts in different spaces, so their numbers cannot be compared, and a search across them returns noise.20 A model change therefore means a new collection, filled again from the source texts.

A collection can also carry an embedding function, the model Chroma would run on a text sent without a vector. This week passes embedding_function=None everywhere and sends every vector itself, so the only model in play is embed.

Takeaways
  • Create raises on an existing name; get-or-create returns the existing collection unchanged.
  • Count, peek, list, rename and delete are one call each, and delete cannot be undone.
  • A collection holds vectors of one length from one model; a new model needs a new collection.
Say it in an interview

In Chroma I create a collection with create_collection, which raises if the name exists, or get_or_create_collection, which returns the existing one and ignores the other arguments. I check it with count and peek, list them with list_collections, rename with modify, and remove one with delete_collection, which can't be undone.

Two embedding models can't share a collection. Different lengths are refused outright, and even at the same length the two models' numbers mean different things, so similarity across them is meaningless. A new model means a new collection, re-embedded from the source text.

Upsert

Upsert: insert what is new, replace what exists

Help-centre articles change: a policy is rewritten, a new article appears. A load of fresh data usually mixes both kinds of record, and upsert is the write built for that mix. Its name joins "update" and "insert".

Add, update and upsert in Chroma

The block defines a batch of two articles. kb-019 already exists and gets a new text with a 60-day window; kb-031 is new. The same batch is sent first with add, then with upsert.

Stable ids and loads you can run twice

Upsert decides between insert and replace by the id alone, so the id must name the same article on every load. The block makes the common mistake: it numbers the batch's rows and uses the row numbers as ids.

Run in Colab

The count jumps from 9 to 11, because row-0 and row-1 are ids the collection has never seen. The query shows the damage: the returns article comes back twice, once as kb-019 and once as row-0, and the copy fills one of the three places. found["ids"][0] is the first query's list, because query groups its results per query.22 delete removes records by id, permanently, which puts the count back to 9.23

The fix is to take the id from the source record, a["id"], never from a position in a list. A load built that way is idempotent: running it twice leaves the same records as running it once. With stable ids and upsert, a failed load can run again.

Upsert in Pinecone

Pinecone has no separate add: every write of a record is an upsert. A new id is inserted, and an existing id has its entire record overwritten.24 The block writes the eight articles to kb-wednesday, then the update batch, and fetches the changed article.

Run in Colab

def wait_for_count(index, expected, namespace=None):
    """Poll the index stats every 2 seconds, for up to 60 seconds, until they show `expected` vectors."""
    for _ in range(30):
        stats = index.describe_index_stats()
        if namespace is None:
            count = stats.total_vector_count
        else:
            ns = stats.namespaces.get(namespace)
            count = ns.vector_count if ns else 0
        if count == expected:
            break
        time.sleep(2)
    print(namespace or "all", count)

def to_records(articles, vectors):
    return [{"id": a["id"], "values": v.tolist(), "metadata": {**meta(a), "text": a["text"]}}
            for a, v in zip(articles, vectors)]

index = pc.Index("kb-wednesday")
index.upsert(vectors=to_records(KB_SAMPLE, sample_vectors))
wait_for_count(index, 8)
index.upsert(vectors=to_records(SAMPLE_UPDATES, update_vectors))
wait_for_count(index, 9)
print(index.fetch(ids=["kb-019"]).vectors["kb-019"].metadata["text"][:45])

It should print all 8, then all 9, then the 60-day text. to_records builds Pinecone's record shape: an id, the vector as values, and the metadata. v.tolist() turns a numpy row into a plain Python list, and {**meta(a), "text": ...} copies the four fields and adds the text, so the fetched record can show which version is stored.

fetch returns vectors, a map from each id to its stored record, which is where the new text is read.25 wait_for_count is the week's helper: it reads describe_index_stats() until the count arrives, so the next line never runs against a count that has not caught up.

The overwrite has a cost. An upsert that sends only new metadata replaces the whole record, so a change to one field belongs in update, which changes part of a record.24 A single upsert request should hold up to 1,000 records within 2 MB, so a large load is sent in batches.24

In other people's code, col.upsert(ids=..., embeddings=...) or index.upsert(vectors=[{"id": ..., "values": ..., "metadata": ...}]) marks a load meant to be rerun.

Takeaways
  • Upsert inserts a new id and replaces an existing one; Chroma's add silently skips existing ids.
  • Ids come from the source record, so a load can run twice without duplicates.
  • Pinecone writes only by upsert, and an upsert overwrites the whole record.
Say it in an interview

Upsert inserts a record when its id is new and replaces it when the id exists, so one call handles a batch that mixes new and changed records. In Chroma, add ignores an existing id without an error, which silently loses the change; in Pinecone every write is an upsert and overwrites the whole record.

The id has to come from the source data, like the article's own id. If I used row numbers, the next load would write the same articles under new ids and every search would return duplicates. Stable ids plus upsert make the load safe to rerun.

Partitioning vectors

Partitioning vectors: collections and namespaces

Partitioning splits the stored vectors into separate parts so that a query searches one part and never sees the others. Chroma partitions with collections, and Pinecone with namespaces inside one index.

A collection per partition in Chroma

The block first builds SAMPLE_ALL, the eight articles with the update batch applied by id, nine in all. It then stores the web articles and the mobile articles in two collections and asks both the same question.

Namespaces in Pinecone

A namespace is a named partition inside a Pinecone index. Every upsert, query and other read or write targets exactly one namespace, and a namespace is created automatically by the first upsert into it.26 The records written in the upsert step went to the default namespace, since no name was given, which the stats list as "__default__".27 The block writes the same nine articles again, split by product into web and mobile, and queries one.

Run in Colab

for product in ["web", "mobile"]:
    rows = [i for i, a in enumerate(SAMPLE_ALL) if a["product"] == product]
    index.upsert(vectors=to_records([SAMPLE_ALL[i] for i in rows], sample_all_vectors[rows]),
                 namespace=product)
wait_for_count(index, 5, namespace="web")
wait_for_count(index, 4, namespace="mobile")

question = embed(["the app keeps closing by itself"])[0].tolist()
found = index.query(vector=question, top_k=2, namespace="web", include_metadata=True)
for match in found.matches:
    print(match.id, round(match.score, 2), match.metadata["title"])

It should print web 5 and mobile 4, then kb-008 and kb-024, the same two articles kb_web returned, because the vectors are the same. Pinecone's cosine score is a similarity, 1 minus Chroma's cosine distance, and higher is closer. So the two scores should come out near 1 − 0.73 = 0.27 and 1 − 0.80 = 0.20. Each match carries an id, a score and the metadata.25 A namespace= argument on index.upsert or index.query is the sign of a partitioned index.

The other namespace calls a team uses:

  • describe_index_stats() lists every namespace with its vector_count.25
  • index.list_namespaces() and describe_namespace list and describe them, and the name "__default__" targets the default namespace.27
  • index.delete_namespace(namespace="mobile") deletes every record in that namespace, permanently.27
  • query_namespaces(...) searches several namespaces and merges the results.25

When to partition: multitenancy

Multitenancy means one index serving many customers, called tenants, and it is the main reason namespaces exist. Pinecone's guide gives each tenant its own namespace, which brings three properties:28

  • Isolation: a query in one tenant's namespace cannot return another tenant's records.
  • Even load: a search's cost follows the size of its namespace, so a large tenant does not slow a small one.
  • Easy removal: offboarding a tenant is deleting its namespace, which the guide calls "lightweight and almost instant".

The other common reasons to partition are data that must never mix, such as two languages, and vectors from different models. In Chroma different models go in different collections. A Pinecone index has one dimension, so a model of another size needs its own index.7

Partitions have costs too. A question that spans partitions needs one query per partition, or query_namespaces, and an index on dedicated read nodes supports only one namespace.10 Namespaces per serverless index run from 100 on Starter to 1,000,000 on Enterprise.2814

Takeaways
  • A partition is a part of the data a query searches alone; other parts are invisible to it.
  • Chroma partitions with collections, Pinecone with namespaces inside one index.
  • One namespace per tenant isolates customers and makes deleting one customer a single call.
Say it in an interview

A Pinecone namespace is a named partition inside an index. Every upsert and query targets one namespace, so records in other namespaces are never seen. In a multi-tenant app I'd give each customer a namespace: their data is isolated, a big customer doesn't slow the others, and offboarding is deleting that namespace.

With the SDK I'd create the index with has_index and create_index, upsert each customer's records with namespace set to their name, and query with the same namespace argument. describe_index_stats shows the vector count per namespace, which is how I'd check the writes landed.

Metadata partitioning

Vector partitioning using metadata: filters

A metadata filter is a condition on the fields stored beside each vector, such as category or year. It limits which records a similarity search may return, so it carves a part out of one collection at query time instead of storing the parts apart.

A where filter

Chroma's query and get both take a where argument.22 The block asks one question of kb_articles twice, without a filter and with one.

Run in Colab

question = embed(["how do I get my money back"])

Both narrow a search, and they suit different needs. In Pinecone, a filter narrows the candidates while the search still scans the whole namespace, so a filter-based tenant scheme reads every tenant's data.28

Distance metrics

Distance metrics: cosine, dot product and Euclidean

A distance metric is the rule that turns two vectors into one number saying how close they are. Every collection and index on this page was created with one, and this step compares the three common ones.

Three measures worked by hand

Tuesday's page worked the dot product (50) and the cosine (1.0) of a = [3, 4] and b = [6, 8]. The third measure, Euclidean distance, is the straight-line gap: √((3 − 6)² + (4 − 8)²) = √25 = 5.0.

Run in Colab

a, b, c = np.array([3, 4]), np.array([6, 8]), np.array([4, 3])

def cosine(u, v):
    return np.dot(u, v) / (np.linalg.norm(u) * np.linalg.norm(v))

for name, u, v in [("a,b", a, b), ("a,c", a, c), ("b,c", b, c)]:
    print(name, round(cosine(u, v), 2), np.dot(u, v), round(np.linalg.norm(u - v), 2))
a,b 1.0 50 5.0
a,c 0.96 24 1.41
b,c 0.96 48 5.39

Each line shows a pair, its cosine (the same cosine as Tuesday's page), its dot product and its distance. The measures disagree.3 Cosine and dot product call a, b the closest pair, and Euclidean calls a, c closest. The reason is length. b points the way a does, so the cosine is 1.0, but it is twice as long, so its tip sits 5 away. Cosine looks only at direction; the dot product and the distance also feel length.

Make b ten times longer, b = [30, 40], and the gap grows. Cosine for a, b stays 1.0 while the distance grows to 45.0 and the dot product to 250.3 Euclidean distance fits vectors whose length carries meaning, such as counts or measurements.32

Vectors of length 1

The disagreement disappears when every vector has length 1, a unit vector. The block divides a, b and c by their lengths and measures again, printing the squared distance this time.

Run in Colab

ua, ub, uc = (x / np.linalg.norm(x) for x in (a, b, c))
for name, u, v in [("a,b", ua, ub), ("a,c", ua, uc), ("b,c", ub, uc)]:
    print(name, round(cosine(u, v), 2), round(np.dot(u, v), 2), round(np.sum((u - v) ** 2), 2))
a,b 1.0 1.0 0.0
a,c 0.96 0.96 0.08
b,c 0.96 0.96 0.08

For unit vectors the dot product equals the cosine, and the squared Euclidean distance is 2 − 2 × cosine. Check one line by hand: 2 − 2 × 0.96 = 0.08.3 Since the distance is a fixed function of the cosine, the closest pair by one measure is the closest by all three. a and b now coincide, so they are 0 apart.

This is the case this week uses. embed passes normalize_embeddings=True, so every stored vector has length 1, and the three metrics put the articles in the same order.3

Choosing a metric

Use the metric the embedding model was trained with. all-MiniLM-L6-v2 was trained on the cosine similarity of sentence pairs, so cosine is its metric.1732 Cosine on raw vectors and dot product on normalised vectors are the same calculation, so a dot-product index also suits it when the vectors have length 1.32

The model card is where to look for a new model. Pinecone's index guide says the dimension and metric should match the model's.7 Most text models name cosine; Euclidean belongs to vectors that encode counts or measurements.

The metric is named once, at creation: configuration={"hnsw": {"space": "ip"}} in Chroma, and metric="euclidean" in create_index.

Takeaways
  • Cosine looks at direction only; dot product and Euclidean distance also feel length.
  • For unit vectors all three give the same order, since squared distance is 2 − 2 × cosine.
  • Chroma reports distances, lower closer; Pinecone's cosine score is a similarity, higher closer.
  • The metric is fixed at creation, and it should be the one the model was trained with.
Say it in an interview

Cosine similarity compares direction only, the dot product multiplies matching numbers and adds them, and Euclidean distance is the straight-line gap. They disagree when lengths differ: [3, 4] and [6, 8] have cosine 1 but sit 5 apart.

For vectors of length 1 they agree on the order, because squared distance is 2 minus 2 times the cosine. I pick the metric the model card names, cosine for most text models, and set it when I create the index, since neither Chroma nor Pinecone lets me change it later.

Check yourself

Check yourself

Nine questions, at least one per section. Answer each out loud before you open it.

What is a vector index for, and why is an HNSW index approximate?

Without an index a search compares the query with every stored vector, so its time grows in proportion to the rows. HNSW links each vector to a few near neighbours in layers and walks from the top layer down, so the cost grows about logarithmically. The walk is greedy and can stop at a local minimum, which is why it sometimes misses a true neighbour.

An HNSW collection returns 182 of the exact top 10 over 20 queries. What is its recall, and what would you change to raise it?

20 queries × 10 = 200 true neighbours, so recall is 182 / 200 = 0.91. Raise ef_search with modify(configuration={"hnsw": {"ef_search": 200}}), which buys recall with slower queries; space, ef_construction and max_neighbors cannot change after creation.

Walk through a Pinecone index's lifecycle with the SDK. What happens if someone deletes it while deletion protection is on?

Check has_index, then create_index with the model's dimension and metric and a serverless spec; read describe_index for the dimension, metric, host, status and protection, and list_indexes for the names. With protection switched on by configure_index, delete_index fails with 403 FORBIDDEN until protection is disabled again. The console at app.pinecone.io can do the same by hand, deleting an index included.

How would you make a Pinecone deployment faster, and how would you back it up and roll it back?

Serverless reads share capacity up to 2,000 read units per second per index and namespace; dedicated read nodes give one index its own read hardware, with one namespace only. For backups, schedule them with a retention policy and restore into a new index; for rollback, load each data version into a new namespace behind an alias and repoint the alias to the old one. Backups are not on the free Starter plan, and new pod-based collections cannot be created.

What is the difference between create_collection and get_or_create_collection, and what happens when you add a 768-number vector to a 384-number collection?

create_collection raises if the name exists; get_or_create_collection returns the existing collection and ignores the other arguments. The 768-number add raises an error naming both sizes, and the count does not change; even two models of the same size cannot share a collection, because their numbers mean different things.

A nightly job writes the help-centre articles to Chroma with add, using each article's row number as its id. What goes wrong, and what is the fix?

add ignores ids that already exist, so changed texts are silently kept old. Row-number ids name a different article as soon as the list changes, so the same article gets written under a new id and searches return duplicates. Use the article's own id and upsert, which makes the job safe to run twice.

How would you keep two customers' data apart in one Pinecone index, and remove a customer who leaves?

Give each customer a namespace: every upsert and query names it, so one customer's query never reads the other's records, and a large customer does not slow a small one. Removing a customer is delete_namespace, which deletes that namespace's records permanently.

Write a Chroma filter for mobile articles updated in 2025 or later. Why might a query with it and n_results=3 return one result?

{"$and": [{"product": "mobile"}, {"updated": {"$gte": 2025}}]}, with the year stored as an integer because the comparison operators take numbers only. If only one record passes the filter, only one comes back, with no error or warning.

Why do cosine, dot product and Euclidean distance rank the week's vectors in the same order, and when would they disagree?

embed normalises every vector to length 1, and for unit vectors the dot product equals the cosine and squared distance is 2 − 2 × cosine. They disagree when lengths differ: [3, 4] and [6, 8] have cosine 1.0 but are 5 apart, so Euclidean prefers [4, 3]. Pick the metric the model was trained with, at creation.
