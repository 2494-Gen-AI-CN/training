Feature engineering & model evaluation: better columns, the right metric and an honest score

Last week's builds filled blanks, one-hot encoded and scaled a table, and read a confusion matrix with precision, recall and F1; this page assumes those steps and goes deeper on one table of 1,000 loan applicants. It builds and judges features, encodes categories inside one Pipeline, handles blanks and outliers, and ranks features. It then picks a metric and a threshold from what each mistake costs, and regularises models with L1 and L2, checked by cross-validation. Afterwards you can say why a column is left out, which encoding fits a column, what threshold the costs imply and how far one validation score can be trusted.

Feature engineering

Feature engineering: new columns from old, and columns you may not use

Last week's penguin build filled blanks, one-hot encoded and scaled in a single pass. This page goes over those steps more slowly, on one table of loan applicants, and asks of every change whether it helped.

The credit table, the columns left out and the split

The table is credit-g, the Statlog German credit data: 1,000 loan applicants, 20 attributes, no missing values, each classed as a good or a bad credit risk.1 OpenML, a public library of datasets, serves it, and fetch_openml downloads it. The function wants an exact version, because active versions of one name may differ, and as_frame=True returns one pandas DataFrame.2

Run in Colab

import numpy as np
import pandas as pd
from sklearn.datasets import fetch_openml
from sklearn.model_selection import train_test_split

RANDOM_STATE = 42
credit = fetch_openml("credit-g", version=1, as_frame=True).frame
print(credit.shape, credit.isna().sum().sum())
print(credit["class"].value_counts().to_dict())

credit = credit.drop(columns=["personal_status", "foreign_worker", "age"])
X = credit.drop(columns="class")
y = (credit["class"] == "bad").astype(int)
X_trval, X_test, y_trval, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=RANDOM_STATE)
X_tr, X_val, y_tr, y_val = train_test_split(
    X_trval, y_trval, test_size=0.25, stratify=y_trval, random_state=RANDOM_STATE)
print(len(X_tr), len(X_val), len(X_test), y_val.sum())
(1000, 21) 0
{'good': 700, 'bad': 300}
600 200 200 60

The output shows 1,000 rows, 0 blank cells and 700 good against 300 bad. y is 1 for an applicant who defaults, so "bad" is the positive class: every precision, recall and F1 on this page is about the defaulters.

The test set takes 20%, and a quarter of the rest becomes validation, leaving 600 rows to train on. stratify keeps the 30% share of defaulters in every part, so the 200 validation rows hold 60. X_trval holds the 800 training and validation rows for step 8's cross-validation.

Three columns were dropped before the split. personal_status mixes sex and marital status, and foreign_worker records national origin.1 The Canadian Human Rights Act lists national or ethnic origin, age, sex and marital status among its prohibited grounds of discrimination, and it covers services customarily available to the public.3

In the United States, Regulation B under the Equal Credit Opportunity Act counts national origin, sex, marital status and age as a prohibited basis.4 It allows age only in a statistically sound scoring system that gives an elderly applicant no negative value, so using age needs legal review.5

These columns go even if they would raise the score. A model that learns from a protected column decides on that ground, and so does a feature built from one or from a close stand-in, so they are ruled out before any score is read.

New features from old: a monthly payment and duration bands

Feature engineering is building new input columns from the ones you have, and keeping each one only if it helps on validation rows. Two candidates come straight from the loan's terms:

  • monthly_payment, the amount divided by the number of months, a ratio no single column holds;
  • duration_band, the loan's length cut into four ranges: up to 12 months, 13 to 24, 25 to 36, and over 36.

Why add a ratio when the model already has both columns? A linear model such as logistic regression only adds up its inputs, each multiplied by a weight, so it cannot divide one column by another.6 A ratio that matters has to be handed over as its own column.

Run in Colab

def add_features(df):
    """Add two columns built from each row's own values."""
    return df.assign(
        monthly_payment=df["credit_amount"] / df["duration"],
        duration_band=pd.cut(df["duration"], bins=[0, 12, 24, 36, np.inf],
                             labels=["<=12", "13-24", "25-36", ">36"]))

X_tr, X_val, X_test, X_trval = (add_features(d) for d in (X_tr, X_val, X_test, X_trval))
print(X_tr[["credit_amount", "duration", "monthly_payment", "duration_band"]].head(3).round(1))
print(X_tr["duration_band"].value_counts(sort=False).to_dict())
     credit_amount  duration  monthly_payment duration_band

The first row borrowed 4,811 over 30 months, so it pays about 160.4 a month and lands in the 25 to 36 band. The numbers on the left are the rows' positions in the original table. assign returns a new DataFrame with the extra columns.

pd.cut makes right-closed bins by default, (0, 12], (12, 24] and so on, so a 12-month loan lands in the first band. A value outside every bin becomes NA, so the last edge is np.inf, infinity.7 The four counts add up to the 600 training rows.

add_features reads only each row's own values, so running it on every part of the split leaks nothing. A step that learns from many rows, such as a median or a fence, is fitted on X_tr alone.8

Judging a feature, and a feature from the future

A new feature is a change like any other: fit with it and without it, and compare on the validation rows. Step 4 does that for monthly_payment, which scores a small negative importance there, about −0.01 of F1.9

The next question is whether the feature exists when the decision is made. A column filled in after the loan was granted, such as a later missed payment, would score very well and be useless: it carries the answer. That is leakage from the future.

In someone else's code, feature engineering is a line such as X["monthly_payment"] = X["credit_amount"] / X["duration"], or a pd.cut. Row-wise lines are safe; question a mean or a count taken over the whole table before the split.

Takeaways
  • Columns for sex, marital status, national origin and age are left out before any score is read.
  • A ratio such as monthly payment adds something a linear model cannot build from the two columns.
  • Keep a new feature only if it helps on validation rows and exists at decision time.
Say it in an interview

Feature engineering is building new inputs from the columns you have. On a loan table I'd add the monthly payment, amount over duration, because a linear model only adds up weighted columns and can't divide one by another. I'd compare the model with and without it on the validation rows and keep it only if it helped.

Some columns stay out even if they raise the score. Sex, marital status, national origin and age are protected grounds for a lender, so I drop them, and anything standing in for them, before I look at any number.

Encoding

Encoding categorical data: one-hot, ordinal and frequency

A model reads numbers, so a category column such as purpose has to become numbers first. The right encoding depends on what the values mean and how many there are:

EncodingEach value becomesFits when
one-hotits own 0-or-1 columna handful of values with no order
ordinalone integer, 0, 1, 2 and so on, in a chosen orderthe values have a real order
frequencyits share of the training rowsmany values, where one-hot would be too wide

Ordered categories need their order written out

employment records how long the applicant has held their present job: unemployed, under a year, 1 to 4 years, 4 to 7, or 7 or more.1 Those values have a real order, so one integer column can carry them. The catch is that the table stores its categories in alphabetical order.

Run in Colab

from sklearn.preprocessing import OrdinalEncoder

print(list(X_tr["employment"].cat.categories))
ORDERED = {"employment": ["unemployed", "<1", "1<=X<4", "4<=X<7", ">=7"]}
encoder = OrdinalEncoder(categories=[ORDERED["employment"]]).fit(X_tr[["employment"]])
print(encoder.transform(pd.DataFrame({"employment": ["unemployed", "1<=X<4", ">=7"]})).ravel())
['1<=X<4', '4<=X<7', '<1', '>=7', 'unemployed']
[0. 2. 4.]

The first line is the stored order: "unemployed" comes last, so an encoder that trusted it would rank having no job above seven years in one. OrdinalEncoder with its default categories="auto" takes the order from the data, so the real order is passed in as a list of lists, one inner list per column.10 The second line confirms it: unemployed is 0, 1 to 4 years is 2, and 7 or more is 4.

Integer codes are read by a model as ordered, which is often not what you want for a column without an order.11 checking_status looks ordered (under 0, 0 to 200, 200 or more) until its fourth value, "no checking account", which is not a balance at all.1 No single order fits, so it stays one-hot, and savings_status with "no known savings" has the same shape.

When one-hot is the wrong choice

One-hot works for purpose, which has 10 values. Picture a column with hundreds, such as a city or a product code. One-hot gives it hundreds of columns that are almost all zeros, which inflates the feature space,11 and production will keep sending values the training rows never held. OneHotEncoder has a middle path: min_frequency and max_categories group rare values into one "infrequent" column.12

Frequency encoding replaces each value with its share of the training rows, which is one column however many values there are. credit-g has no column with hundreds of values, so purpose stands in for one here.

Run in Colab

shares = X_tr["purpose"].value_counts(normalize=True)
print(len(shares), shares[["new car", "retraining"]].round(3).to_dict())
X_val_purpose = X_val["purpose"].map(shares).astype(float)
unseen = pd.Series(["new car", "drone"]).map(shares).astype(float).fillna(0.0)

The first line prints 10 purposes and two shares: value_counts(normalize=True) gives shares instead of counts, so new car is about 0.27 of the training applicants and retraining about 0.007.11 map(shares) swaps each validation value for its share. "Drone" is not in the table, so map gives a blank, filled here with 0.

Two more encodings come up in interviews:

  • Target encoding replaces each value with the average label of its rows. It suits many-valued columns, but it puts the label into the feature, so TargetEncoder (scikit-learn 1.3 and later) cross-fits inside fit_transform to keep the target from leaking.13
  • Learned embeddings let a network learn a short list of numbers for each value. Tomorrow's page starts on vectors like these.

One Pipeline for every step

ColumnTransformer sends each list of columns to its own transformer and joins the outputs side by side. Columns in no list are dropped by default, remainder="drop".14 Pipeline chains that preparation and a final model into one object, so they are fitted, used and cross-validated together.15

Run in Colab

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import f1_score

ONE_HOT = ["purpose", "checking_status", "savings_status", "credit_history", "housing",
           "other_parties", "property_magnitude", "other_payment_plans", "job", "own_telephone"]
NUMERIC = ["duration", "credit_amount", "installment_commitment", "residence_since",
           "existing_credits", "num_dependents", "monthly_payment"]

def make_pipe(numeric=NUMERIC, one_hot=ONE_HOT, num_step=None, model=None):
    """Prepare the columns and fit a model, as one object."""
    prep = ColumnTransformer([
        ("num", num_step or StandardScaler(), numeric),
        ("ord", OrdinalEncoder(categories=[ORDERED["employment"]]), ["employment"]),
        ("oh", OneHotEncoder(handle_unknown="ignore", sparse_output=False), one_hot)])
    return Pipeline([("prep", prep), ("model", model or LogisticRegression(max_iter=5000))])

pipe = make_pipe().fit(X_tr, y_tr)
prep = pipe.named_steps["prep"]
print(prep.transform(X_val).shape, prep.get_feature_names_out()[[0, 7, 8]])
pred = pipe.predict(X_val)
print(f"validation F1 for 'bad' {f1_score(y_val, pred):.3f}")
(200, 51) ['num__duration' 'ord__employment' 'oh__purpose_business']
validation F1 for 'bad' 0.425

The 51 columns are 7 scaled numbers, 1 ordinal column and 43 one-hot columns. duration_band is in no list, so it was dropped; adding it to ONE_HOT would add 4 columns. Each name carries its transformer's prefix, which is how you read the encoded width back.14 num_step or StandardScaler() means "the step passed in, or a scaler if none was".

Two arguments on the one-hot step matter. handle_unknown="ignore" encodes a category the training rows never held as all zeros instead of raising an error. sparse_output=False returns an ordinary array, because the default is a sparse matrix that stores only the non-zero cells.12 The F1 of 0.425 is the baseline every later change is compared against.

What does the Pipeline prevent? fit on X_tr learns every mean, scale and category list from those 600 rows only, and cross_val_score refits the whole pipeline inside each fold, so no held-out row ever shapes the preparation.8

Takeaways
  • One-hot suits a few unordered values; ordinal suits a real order, written out by hand.
  • Many values make one-hot too wide; frequency or target encoding keeps one column.
  • A Pipeline learns every preparation step from the training rows only, also inside each fold.
Say it in an interview

I one-hot encode a category with a few unordered values, and use ordinal encoding when the values have a real order, which I write out myself because the data may store them alphabetically. One-hot is wrong when a column has hundreds of values: you get hundreds of mostly empty columns and constant unseen values, so I'd use frequency or target encoding instead.

I put the encoders, the scaler and the model in one scikit-learn Pipeline. Fitting it on the training rows means nothing is learned from validation or test data, and cross-validation refits the whole thing per fold, so it prevents leakage.

Missing values & outliers

Handling missing values and outliers

Blanks and extreme values call for choices, measured like a new feature. credit-g has no blanks,1 so this step adds some to a copy on purpose.

Blanks: fill, flag or drop

There are three ways to deal with a blank:

  • Drop the row. It is simple, but it throws away the rest of that row, data you may still need.16
  • Fill it, which is called imputation. SimpleImputer fills with the mean, the median (numbers only), the most frequent value or a constant, learned in fit from the training rows.17
  • Fill it and flag it. add_indicator=True adds a 0-or-1 column saying which cells were blank, so the model can use the fact that a value was missing.16

Run in Colab

from sklearn.impute import SimpleImputer

toy = pd.DataFrame({"credit_amount": [1000.0, np.nan, 3000.0, 5000.0]})
print(SimpleImputer(strategy="median").fit_transform(toy).astype(int).tolist())
print(SimpleImputer(strategy="median", add_indicator=True).fit_transform(toy).astype(int).tolist())
[[1000], [3000], [3000], [5000]]
[[1000, 0], [3000, 1], [3000, 0], [5000, 0]]

The median of the three known amounts, 1,000, 3,000 and 5,000, is 3,000, and it fills the blank in the second row. The second imputer adds a column whose 1 marks that row as filled. An indicator column appears only for a column that had blanks at fit time,17 so the training rows must contain them.

A blank that means something

Blanks that fall at random carry no information. Blanks that fall mostly on one kind of row do, which is called missing not at random. The code below blanks credit_amount in two copies: one at random, one mostly for defaulters. It leaves out monthly_payment, which still holds the real amount.

Run in Colab

def blank_amounts(df, labels, mostly_defaulters, seed):
    """Copy df with some credit_amount cells blanked."""
    rng = np.random.default_rng(seed)
    labels = labels.to_numpy()
    share = np.where(labels == 1, 0.5, 0.05) if mostly_defaulters else np.full(len(df), 0.2)
    out = df.copy()
    out.loc[rng.random(len(out)) < share, "credit_amount"] = np.nan
    return out

for mostly in (False, True):
    tr, val = blank_amounts(X_tr, y_tr, mostly, 1), blank_amounts(X_val, y_val, mostly, 2)
    row = []
    for flag in (False, True):
        fill = Pipeline([("fill", SimpleImputer(strategy="median", add_indicator=flag)),
                         ("scale", StandardScaler())])
        p = make_pipe(numeric=NUMERIC[:-1], num_step=fill).fit(tr, y_tr)
        row.append(f1_score(y_val, p.predict(val)))
    print(f"mostly defaulters {mostly}: median F1 {row[0]:.2f}, median + indicator F1 {row[1]:.2f}")

The share line gives each row its chance of a blank: 20% for everyone in the random copy, or 50% for a defaulter and 5% for anyone else. The loop prints one line per copy, the validation F1 of the median fill and of the fill plus indicator.

The indicator wins only on the second copy. A random blank says nothing about the applicant, so the extra column adds nothing. When blanks cluster on defaulters, the indicator column itself predicts default, and the model uses it.16

Finding outliers with the 1.5 IQR rule

An outlier is a value far from most of a column's values. The interquartile range, IQR, is the width of the middle half: the third quartile Q3 minus the first, Q1. Q1 is the value a quarter of the way up the sorted column and Q3 the value three quarters of the way up, which is what quantile([0.25, 0.75]) below computes.

A point below Q1 − 1.5 IQR or above Q3 + 1.5 IQR, the inner fences, is a mild outlier; beyond 3 IQR it is an extreme one.18

Run in Colab

q1, q3 = X_tr["credit_amount"].quantile([0.25, 0.75])
lower, upper = q1 - 1.5 * (q3 - q1), q3 + 1.5 * (q3 - q1)
print(f"Q1 {q1:.0f}, Q3 {q3:.0f}, fences {lower:.0f} and {upper:.0f}")
print((X_tr["credit_amount"] > upper).sum(), (X_tr["credit_amount"] < lower).sum())
Q1 1345, Q3 4042, fences -2701 and 8088
41 0

The IQR is 4,042 − 1,345 = 2,697, and 1.5 times that is about 4,046, so the upper fence is about 8,088. 41 of the 600 training loans sit above it and none below, since no amount is negative. Then ask of each flagged value: is it an error, or a real big loan? An impossible value is an error to fix; a large possible one is data.

Keep, clip or log

ChoiceWhat it doesIn a pipeline
keepleaves the value; a scaler that ignores extremes keeps it from setting the scaleRobustScaler()19
clipcaps every value at the fence.clip(upper=upper) before the fit
logpulls a long right tail in while keeping the order of valuesFunctionTransformer(np.log1p)20

RobustScaler subtracts the median and divides by the IQR, because outliers pull the mean and the variance a plain scaler uses.19 A log is monotonic: a larger amount always gives a larger log, so the rank of the values is kept.21 Skew measures how lopsided a column is: 0 is symmetric, and a positive number means a long right tail. credit_amount has a skew of about 1.95 on the full table, the tail a log pulls in.21

Run in Colab

from sklearn.preprocessing import FunctionTransformer

log_amount = Pipeline([
    ("log", ColumnTransformer([("amount", FunctionTransformer(np.log1p), ["credit_amount"])],
                              remainder="passthrough")),
    ("scale", StandardScaler())])
clip = lambda df: df.assign(credit_amount=df["credit_amount"].clip(upper=upper))
runs = {"keep": (make_pipe(), X_tr, X_val),
        "clip": (make_pipe(), clip(X_tr), clip(X_val)),
        "log": (make_pipe(num_step=log_amount), X_tr, X_val)}
for name, (p, tr, val) in runs.items():
    print(f"{name}: validation F1 {f1_score(y_val, p.fit(tr, y_tr).predict(val)):.3f}")

Each choice is its own pipeline scored on the same validation rows, so the three printed lines compare directly. The clip uses the fence from X_tr on both sets. np.log1p is the log of 1 plus the value, and the inner ColumnTransformer logs only credit_amount.

The choice matters for linear models and networks, whose weighted sums feel a value's size. A decision tree splits one column at a threshold, and a log keeps the rank, so the tree's possible splits stay the same.22 IsolationForest goes further and flags whole unusual rows.23

Takeaways
  • Fill blanks with a median learned from the training rows; dropping rows loses data.
  • An indicator column helps when the blanks themselves carry information.
  • The 1.5 IQR fences flag outliers; then decide whether each is an error or real.
  • Clipping or a log matters for linear models and networks, hardly for trees.
Say it in an interview

For missing numbers I usually fill with the median learned from the training rows, because it isn't pulled by extremes. If the blanks might mean something, say they fall mostly on customers who default, I also add an indicator column and check on validation data whether it helps. Dropping rows is the last resort, since it throws data away.

For outliers I flag values beyond 1.5 interquartile ranges and ask whether each is an error or a real value. Real ones I keep, then clip, log or scale by the median and IQR for a linear model, and compare each on validation rows.

Feature selection

Feature selection techniques

Feature selection keeps the columns that help and drops the rest, then measures whether dropping helped.

Why fewer features

  • Noise: a column with no signal gives the model something to fit by chance.
  • Cost: every column has to be collected, checked and kept up to date in production.
  • Explanation: a model on ten columns is easier to explain to the people it decides about.
  • Columns a lender may not use: personal_status, foreign_worker and age were dropped in step 1 and are never offered to a ranking.34

Selection learns from data, so it follows the split-first rule. scikit-learn's guide shows the cost of breaking it: selecting features on all the rows before splitting made pure noise score about 0.76, where 0.5 was expected.8 There are three families of method:

FamilyHow it ranksExample
filtereach column against the target, with no modelmutual information
model-basedhow much a fitted model's score depends on each columnpermutation importance
built into trainingthe penalty sets some weights to exactly zeroL1 regularisation, step 8

A filter: mutual information

Mutual information measures how much knowing a column tells you about the target. mutual_info_classif returns one non-negative score per column, zero only when the column and the target are independent. The estimate has some randomness in it, which random_state fixes.24

Run in Colab

from sklearn.feature_selection import mutual_info_classif

mi = mutual_info_classif(prep.transform(X_tr), y_tr, random_state=RANDOM_STATE)
ranking = pd.Series(mi, index=prep.get_feature_names_out()).sort_values(ascending=False)
print(ranking.index[:6].tolist())
['oh__checking_status_<0', 'oh__checking_status_no checking', 'oh__credit_history_critical/other existing credit', 'oh__housing_own', 'num__credit_amount', 'num__duration']

The filter scores the 51 encoded training columns one at a time.24 Two checking_status values, under 0 and no checking account, say the most on their own, followed by a critical credit history and owning a home, then the amount and the duration. The scores are rough: with its default discrete_features="auto" the function treats a dense array as continuous, though the one-hot columns are really 0 or 1.24

A model-based ranking: permutation importance

Permutation importance shuffles one column, which breaks its link to the target, and records how much the score drops. Computed on held-out rows, it shows which columns the model needs on data it has not seen.9 On the training rows, a column the model had memorised would look important too. A fitted pipeline takes the raw columns, so the ranking is per original column, and n_repeats sets how many shuffles are averaged.25

Run in Colab

from sklearn.inspection import permutation_importance

imp = permutation_importance(pipe, X_val, y_val, scoring="f1", n_repeats=10, random_state=RANDOM_STATE)
by_column = pd.Series(imp.importances_mean, index=X_val.columns).sort_values(ascending=False)
print(by_column.index[:5].tolist())
print(by_column[by_column < 0].index.tolist())
['savings_status', 'duration', 'property_magnitude', 'employment', 'checking_status']
['monthly_payment', 'other_payment_plans', 'existing_credits']

The first line lists the five columns whose shuffle costs the most validation F1. The second lists those with a negative importance: the score went up when the column was scrambled, so what the model learned from it does not hold on new rows.25 monthly_payment is one of those, at about −0.01 F1. Two correlated columns, such as the amount and the payment, share their importance and can both look weak.9

Does dropping help?

Run in Colab

top10 = [c for c in by_column.index if c != "duration_band"][:10]
fewer = make_pipe(numeric=[c for c in NUMERIC if c in top10],
                  one_hot=[c for c in ONE_HOT if c in top10]).fit(X_tr, y_tr)
no_payment = make_pipe(numeric=NUMERIC[:-1]).fit(X_tr, y_tr)
for name, p in [("all columns", pipe), ("top 10", fewer), ("no monthly_payment", no_payment)]:
    print(f"{name}: validation F1 {f1_score(y_val, p.predict(X_val)):.3f}")

The loop prints one validation F1 per pipeline, all on the same 200 rows. The top-10 line is flattered, because the ranking that chose those ten came from these same rows. Removing monthly_payment does not lower the score, so the feature from step 1 did not earn its place.

Takeaways
  • A filter such as mutual information ranks each column against the target, with no model.
  • Permutation importance on validation rows ranks columns by what the fitted model needs.
  • Removing columns is a change like any other: measure it on validation rows.
Say it in an interview

A filter method scores each column against the target without a model, for example mutual information. A model-based method asks the fitted model, for example permutation importance: shuffle one column on validation rows and see how much the score drops. L1 regularisation is a third way, because it sets weights to zero.

To know whether removing features helped, I refit without them and compare on the same validation rows, or better with cross-validation. I compute permutation importance on validation rows, because on training rows a column the model memorised looks important.

Choosing a metric

Model evaluation: choosing a metric with the people who own the decision

Before any model is tuned, someone has to say what a good model is, and the data scientist does not make that choice alone.

Accuracy on a 70/30 table

Accuracy is the share of answers that are right. On a table that is 70% good applicants, a model that answers "good" every time scores 70% without reading a single column.

Run in Colab

from sklearn.metrics import accuracy_score, recall_score, balanced_accuracy_score

always_good = np.zeros(len(y_val), dtype=int)
for name, guess in [("always good", always_good), ("pipeline", pred)]:
    print(f"{name}: accuracy {accuracy_score(y_val, guess):.2f}, recall {recall_score(y_val, guess):.2f}, "
          f"balanced accuracy {balanced_accuracy_score(y_val, guess):.2f}")
always good: accuracy 0.70, recall 0.00, balanced accuracy 0.50
pipeline: accuracy 0.68, recall 0.40, balanced accuracy 0.60

always_good is 200 zeros, "good" for everyone. It beats the pipeline on accuracy, 0.70 against 0.68, while catching none of the 60 defaulters; the pipeline's recall of 0.40 means it catches 24 of them.

Balanced accuracy averages the recall of each class, so "always good" scores (1.0 + 0.0) / 2 = 0.50. A classifier that only looks good because the classes are unbalanced drops to 1 / number of classes, here 0.5.26 The pipeline's 0.60 is above that, but only a little.

Who owns the decision, and which mistake costs more

A classifier makes two kinds of mistake, and they rarely cost the same. Which one is worse is a business or a medical question, so it is answered by the people who own the decision: the lender's credit team, the clinic, the product owner. Your job is to ask, then turn the answer into a metric.

  • Loan approval: credit-g's own costs say approving a defaulter is five times worse than refusing a good applicant.1
  • Tumour screening: a missed cancer costs far more than an extra follow-up test, so the threshold is lowered to favour recall.27

A binary classifier's predict turns a probability into a yes at 0.5, which scikit-learn's guide calls "most certainly not ideal for most use cases".27 The cut-off belongs to the cost of each mistake, and step 7 sets it.

The cost matrix

An interviewer who hears "approving a defaulter is worse" asks how much worse. A cost matrix answers with numbers: one cost for each pairing of true answer and predicted answer. credit-g ships with one:1

True classPredicted good (approve)Predicted bad (refuse)
good01, a good applicant refused
bad5, a defaulter approved0

The total cost of a model is 5 times the defaulters it approved plus 1 times the good applicants it refused. "Always good" approves all 60 defaulters on the validation rows, so it costs 5 × 60 = 300. scikit-learn's own cost-sensitive example uses this dataset with these costs and "bad" as the positive class.28 In code, a matrix such as [[0, -1], [-5, 0]] next to a confusion_matrix call is this idea written as gains.

Takeaways
  • On a 70/30 table, "always good" scores 70% accuracy and catches no defaulter.
  • The people who own the decision say which mistake costs more.
  • A cost matrix turns that answer into numbers: here 5 for a defaulter approved, 1 for a good refusal.
Say it in an interview

I start by asking the people who own the decision what each kind of mistake costs. For a lender, approving someone who defaults costs much more than refusing a good customer, so I'd report recall on the defaulters and the total cost, not accuracy.

A model with 70% accuracy can be worthless: if 70% of applicants are good, answering "good" every time gets that score and catches nobody. That's why I check recall or balanced accuracy, and why the threshold should come from the costs instead of the default 0.5.

Precision, recall, F1

Accuracy, precision, recall and F1 for the defaulters

Week 7 defined precision, recall and F1 for one digit against the rest. This step reads them for the defaulters in a full report, then looks at the two averages the report adds underneath.

The report prints precision, recall, F1 and support for each class, then accuracy and two averages.29 target_names labels class 0 "good" and class 1 "bad". Support is the number of true rows in each class: 140 good and 60 bad. Read the "bad" row, since the defaulters are what the lender cares about:

  • F1 0.42: one number that is high only when both are.

Macro and weighted averages

The two average rows combine the per-class scores in different ways. The macro average is the plain mean of the classes. The weighted average weights each class by its support.29

Run in Colab

per_class = f1_score(y_val, pred, average=None)
print(per_class.round(3))
print(round(f1_score(y_val, pred, average="macro"), 3), round(f1_score(y_val, pred, average="weighted"), 3))
[0.774 0.425]
0.599 0.669

average=None returns one F1 per class, good first. The macro F1 is (0.774 + 0.425) / 2, about 0.60. The weighted F1 is (140 × 0.774 + 60 × 0.425) / 200, about 0.67, pulled up by the larger good class.

Macro averaging treats every class as equally important, so it over-emphasizes the typically low score of an infrequent class.26 Weighted averaging can hide that score: reading 0.67 as "the defaulter F1" is a common mistake when the defaulter F1 is 0.42. Macro F1 is the mean of the per-class F1s, not an F1 worked out from mean precision and mean recall.26 There is no micro row, because for a single-label problem with every class included micro averaging equals accuracy.29

Why F1 is a harmonic mean

F1 is the harmonic mean of precision and recall, which works out to 2 tp / (2 tp + fp + fn), where tp, fp and fn count true positives, false positives and false negatives.26 For the defaulters that is 48 / (48 + 29 + 36) = 48 / 113, about 0.42.

A harmonic mean is pulled towards the smaller of its two numbers. Take precision 1.0 and recall 0.1: the plain average is 0.55, but F1 is 2 × 1.0 × 0.1 / 1.1, about 0.18, close to the weak recall.

One edge case comes up in interviews. A model that never predicts "bad" has no predicted positives, so its precision is 0 / 0, undefined. classification_report then reports 0 and prints a warning, which is its default zero_division="warn".29 Step 8's most heavily penalised model is one of these.

Takeaways
  • Read the defaulter row: precision 0.45, recall 0.40, F1 0.42 at threshold 0.5.
  • Macro is the plain mean over classes; weighted weights each class by its support.
  • The weighted 0.67 can hide the defaulters' 0.42.
  • F1 is a harmonic mean, so a low precision or recall pulls it down.
Say it in an interview

The macro average is the plain mean of the per-class scores, so every class counts the same and a rare class with a low score drags it down. The weighted average weights each class by how many true rows it has, so a big class can hide a small one. On the credit data the defaulters' F1 is 0.42, macro is 0.60 and weighted is 0.67.

F1 is the harmonic mean of precision and recall, so it's only high when both are high. When the positive class is the defaulter, I report precision, recall and F1 for that class, not the weighted average.

Confusion matrix

Reading a confusion matrix as costs, and choosing the threshold

Week 7 read a confusion matrix for which digits were confused. Here it is read as money, which sets the threshold.

Each cell has a price

In confusion_matrix the rows are the true labels and the columns the predicted ones, and for two classes .ravel() flattens it into tn, fp, fn, tp.30 With "bad" as 1, a false negative is a defaulter approved and a false positive a good applicant refused.

The decision threshold

predict_proba(X_val)[:, 1] gives each applicant's probability of default, and (proba >= t).astype(int) turns it into a decision at threshold t. Which t? Refusing an applicant whose chance of default is p costs (1 − p) × 1 on average, and approving costs p × 5. Refuse when p × 5 is larger, which is when p is above 1 / (1 + 5), about 0.17.

That is Elkan's rule: with no cost for a correct answer, predict the positive class when its probability is at least the false-positive cost divided by the sum of the two costs.31 Check it at p = 0.2: approving costs 0.2 × 5 = 1.0 and refusing 0.8 × 1 = 0.8, so refuse. At a cost of 10 instead of 5, the rule falls to 1 / 11, about 0.09.

Run in Colab

def best_cost_threshold(y_true, proba):
    """Return the (threshold, cost) pair with the lowest total cost."""
    costs = []
    for t in np.arange(0.05, 0.96, 0.05):
        tn, fp, fn, tp = confusion_matrix(y_true, (proba >= t).astype(int)).ravel()
        costs.append((round(float(t), 2), int(5 * fn + 1 * fp)))
    return min(costs, key=lambda pair: pair[1])

proba = pipe.predict_proba(X_val)[:, 1]
for t in (0.10, 0.15, 0.20, 0.50):
    tn, fp, fn, tp = confusion_matrix(y_val, (proba >= t).astype(int)).ravel()
    print(f"threshold {t:.2f}: defaulters approved {fn}, good refused {fp}, cost {5 * fn + fp}")
print(best_cost_threshold(y_val, proba))

Lowering the threshold refuses more people: at 0.10 only 2 defaulters slip through, at the price of 88 good applicants refused. The cost falls from 209 to 98. min(..., key=...) picks the pair with the lowest cost, its second item. The grid steps by 0.05, so it holds no 0.17; its neighbours are 0.15 and 0.20, and the lowest-cost point reads as near the rule.31 The rule also assumes the probabilities are calibrated, meaning that 0.2 really is a 20% chance.28

A threshold belongs to one model

Tune the threshold on validation rows and never on the rows the model was trained on.27 Two warnings follow from the output above:

  • 200 rows give a noisy answer: 98 at 0.10 and 99 at 0.15 are almost equal, so the bottom of the curve is flat.
  • A threshold tuned for one model is wrong for another, so a new model gets its own sweep on its own validation probabilities.27

scikit-learn also offers TunedThresholdClassifierCV and FixedThresholdClassifier for this job;27 the loop above keeps the arithmetic in view.

ROC, AUC and precision-recall curves

One confusion matrix describes one threshold. An ROC curve describes all of them: it plots the true positive rate (recall) against the false positive rate as the threshold moves, and RocCurveDisplay.from_predictions draws it.32 The false positive rate is the share of good applicants wrongly refused, fp / (fp + tn): 29 / 140, about 0.21, at 0.5.

The area under it, AUC, needs no threshold: it measures how well the model ranks defaulters above good applicants, and a random ranking scores 0.5.33

An AUC of about 0.72 is well above 0.5 and far from 1.0, and its rescaled form, the Gini coefficient 2 × AUC − 1, is about 0.44.33 roc_auc_score takes the probabilities, predict_proba(X)[:, 1], not the 0-or-1 predictions.

precision_recall_curve returns the precision and recall at every threshold. The two arrays are one longer than the thresholds and end at precision 1 and recall 0, which the second line shows.34 Drawn against each other, they tell you more than ROC when positives are few, because precision counts the false alarms directly.

Takeaways
  • Multiply each cell by its cost: 36 approved defaulters at 5 dominate the 209.
  • The cost rule puts the threshold near 1 / (1 + 5), about 0.17, not 0.5.
  • Tune the threshold on validation rows, again for every model you keep.
  • AUC measures ranking over all thresholds; 0.5 is random.
Say it in an interview

I read the confusion matrix as money. On the credit data a defaulter approved costs 5 and a good customer refused costs 1, so 36 approved defaulters and 29 refusals cost 209. With those costs you should refuse once the chance of default passes one in six, so the threshold belongs near 0.17, not 0.5.

I sweep the threshold on validation rows for the model I'm keeping and pick the lowest cost. The ROC curve and its AUC tell me how well the model ranks cases across every threshold, which one confusion matrix can't.

Overfitting

Avoiding overfitting: regularisation and cross-validation

Week 7 fought overfitting with dropout and early stopping. Regularisation is a third way: a penalty on large weights is added to the training loss, so the model stays simpler. Cross-validation then replaces one validation number with several.

L2 in scikit-learn: a smaller C is a stronger penalty

LogisticRegression uses an L2 penalty by default, and C, default 1.0, is the inverse of its strength: smaller values specify stronger regularisation.35 L2 shrinks every coefficient towards zero, which is week 6's ridge.6

Run in Colab

for C in [0.001, 0.01, 0.1, 1, 10, 100]:
    m = make_pipe(model=LogisticRegression(C=C, max_iter=5000)).fit(X_tr, y_tr)
    print(f"C={C}: training F1 {f1_score(y_tr, m.predict(X_tr)):.3f}, "
          f"validation F1 {f1_score(y_val, m.predict(X_val)):.3f}")
C=0.001: training F1 0.000, validation F1 0.000
C=0.01: training F1 0.224, validation F1 0.061
C=0.1: training F1 0.579, validation F1 0.408

At C=0.001 the penalty squeezes the weights so hard that the model never predicts a defaulter, and F1 is 0: underfitting. scikit-learn can warn there, because precision with no predicted defaulter is undefined. From C=1 up, training F1 sits near 0.62 and validation near 0.43. That gap of about 0.2 is the overfitting, and on 600 rows a weaker penalty does not close it.

L1 sets weights to exactly zero

L1 adds a cost proportional to the absolute size of each weight and pushes many of them to exactly zero; L2 adds a cost proportional to the squared weights and shrinks them without zeroing them.36 L1 is week 6's lasso, which prefers fewer non-zero coefficients and can be used for feature selection.6 The default lbfgs solver (a solver is the algorithm that searches for the weights) supports only L2 or none, so L1 needs liblinear or saga.35

Run in Colab

l1 = make_pipe(model=LogisticRegression(penalty="l1", solver="liblinear", C=0.1)).fit(X_tr, y_tr)
l2 = make_pipe(model=LogisticRegression(C=0.1, max_iter=5000)).fit(X_tr, y_tr)
for name, m in [("L1", l1), ("L2", l2)]:
    w = m.named_steps["model"].coef_.ravel()
    print(f"{name}: {(w == 0).sum()} of {w.size} weights are zero, "
          f"validation F1 {f1_score(y_val, m.predict(X_val)):.2f}")
L1: 39 of 51 weights are zero, validation F1 0.28
L2: 0 of 51 weights are zero, validation F1 0.41

coef_ holds the model's 51 weights, one per encoded column. At the same C, L1 keeps 12 columns and drops the rest, selection done by the penalty, while L2 keeps all 51. Here L1 went too far and F1 fell to 0.28, so a larger C is the next thing to try. From scikit-learn 1.8, penalty is deprecated in favour of l1_ratio, with l1_ratio=1 for L1, so newer code looks different.37

L2 in a Keras layer

In Keras the penalty goes on each layer. tf.keras.regularizers.l2(0.01) adds 0.01 times the sum of the squared weights to the loss, and it is passed to a layer as kernel_regularizer.38 A Dense layer's kernel is its weight matrix.

Run in Colab

import tensorflow as tf

X_tr_enc, X_val_enc = prep.transform(X_tr), prep.transform(X_val)

def make_credit_net(l2=None):
    """One hidden layer of 32 ReLU units and a sigmoid output, optionally L2-penalised."""
    reg = tf.keras.regularizers.l2(l2) if l2 else None
    net = tf.keras.Sequential([
        tf.keras.Input(shape=(X_tr_enc.shape[1],)),
        tf.keras.layers.Dense(32, activation="relu", kernel_regularizer=reg),
        tf.keras.layers.Dense(1, activation="sigmoid", kernel_regularizer=reg)])
    net.compile(optimizer="adam", loss="binary_crossentropy")
    return net

tf.keras.utils.set_random_seed(RANDOM_STATE)
credit_net, credit_net_l2 = make_credit_net(), make_credit_net(l2=0.01)
for net in (credit_net, credit_net_l2):
    net.fit(X_tr_enc, y_tr, epochs=100, batch_size=32, validation_data=(X_val_enc, y_val), verbose=0)
print(credit_net.count_params(), credit_net_l2.count_params())

Both networks read the 51 encoded columns and hold 51 × 32 + 32 + 32 + 1 = 1,697 weights: the penalty adds no weight, only a term in the loss. Keras adds that term to the loss it reports, so credit_net_l2's loss curve sits higher by construction.36 Compare the two on validation F1, recall and cost, because their loss curves are not on the same footing.

Stratified k-fold cross-validation

k-fold cross-validation splits the rows into k folds, trains on k − 1 of them and scores the one left out, k times. cross_val_score returns one score per fold, and the guide reports their mean and standard deviation.39 StratifiedKFold keeps each class's share in every fold, and its random_state has effect only with shuffle=True.40

Run in Colab

from sklearn.model_selection import StratifiedKFold, cross_val_score

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)
scores = cross_val_score(make_pipe(), X_trval, y_trval, cv=cv, scoring="f1")
print(scores.round(2))
print(f"mean {scores.mean():.2f}, standard deviation {scores.std():.2f}")
[0.56 0.62 0.47 0.3  0.57]
mean 0.50, standard deviation 0.11

Each fold holds 160 of the 800 rows, 48 of them defaulters. The same pipeline scores from 0.30 to 0.62 depending on which rows are held out, so the single validation F1 of 0.425 was one draw. Report the mean and the spread: about 0.50, give or take 0.11. With 10 folds the mean is about 0.49 and the folds range from 0.24 to 0.65, because smaller folds give noisier scores.

Choosing C inside the folds

GridSearchCV(pipe, {"model__C": [...]}, scoring="f1", cv=cv) tries each C with cross-validation. model__C means the C of the step named model. It refits the best setting on all the rows it was given and reports best_params_ and best_score_.41 That score is optimistic, because the folds were used to choose. The kept pipeline, with a threshold tuned on its own validation probabilities, then meets the test set once.

Takeaways
  • In scikit-learn a smaller C is a stronger penalty; too strong predicts no defaulter at all.
  • L1 zeroes weights and so selects features; L2 shrinks them all.
  • Compare a Keras L2 network on validation metrics, since its loss includes the penalty.
  • Stratified k-fold gives a mean and a spread instead of one number.
Say it in an interview

Regularisation adds a penalty on the weights to the loss. L2 penalises squared weights and shrinks them all; L1 penalises absolute weights and sets many to exactly zero, so it also selects features. In scikit-learn I set C on LogisticRegression, where smaller means stronger, and L1 needs the liblinear or saga solver. In Keras I pass an L2 regulariser as the kernel regulariser of each Dense layer.

Stratified k-fold splits the training data into k folds that each keep the class balance, trains k times with a different fold held out, and gives k scores. I report the mean and the spread, because on small data one split can be lucky or unlucky.

Check yourself

Check yourself

Ten questions, at least one per step. Answer each out loud before you open it.

A colleague adds age back to the credit model because it raises validation F1 by 0.02. What do you say?

Age is a protected ground under the Canadian Human Rights Act, and Regulation B allows it only in a narrow use that needs legal review. A better score does not make a column allowed: protected columns and their stand-ins are ruled out before any score is read.

Why add a monthly payment column when the model already has the amount and the duration, and how do you know whether it helped?

Logistic regression only adds up weighted columns, so it cannot divide the amount by the duration itself. Fit with and without the column and compare on the validation rows; here removing it left F1 at 0.425, so it did not earn its place.

A column has 800 distinct values, such as a product code. Why is one-hot the wrong choice, and what would you use instead?

One-hot would add 800 mostly-zero columns and keep meeting codes the training rows never held. Frequency encoding gives one column of each value's share of the training rows, and target encoding gives one column of the average label, cross-fitted so the label does not leak.

Blanks in a column fall mostly on applicants who later default. Median fill, or median fill plus an indicator, and why?

Median fill plus an indicator. The fact that the value is missing carries information, and the indicator column lets the model use it; on the copy blanked mostly for defaulters, the indicator raised validation F1. With random blanks the indicator adds nothing.

The training amounts have Q1 = 1,345 and Q3 = 4,042. Where is the upper 1.5 IQR fence, and what do you do with a loan above it?

The IQR is 2,697, so the fence is 4,042 + 1.5 × 2,697, about 8,088. Ask first whether it is an error or a real big loan; a real one is kept, then clipped, logged or scaled with RobustScaler, each choice compared on validation rows.

Name a filter method and a model-based method for ranking features. Why is permutation importance computed on validation rows?

Mutual information is a filter: it scores each column against the target with no model. Permutation importance is model-based: shuffle one column and measure how much the fitted model's score drops. On training rows a column the model memorised would look important, so validation rows show what it needs on new data.

How can a model with 70% accuracy be worthless on credit-g?

70% of the applicants are good, so answering "good" every time scores 0.70 and catches no defaulter: recall 0, balanced accuracy 0.5, cost 300.

A report shows defaulter F1 0.42, macro F1 0.60 and weighted F1 0.67. Which do you report for the defaulters, and why do the averages differ?

The defaulter row, 0.42. Macro is the plain mean of the good and bad F1s, and weighted weights them by support, 140 against 60, so the large good class pulls it up and hides the defaulters' lower score.

A defaulter approved costs 5 and a good applicant refused costs 1. Where should the threshold be, and on which rows do you choose it?

Near 1 / (1 + 5), about 0.17: refuse once the chance of default passes one in six. Sweep it on the validation rows for the model you keep, never on the training rows; here the lowest cost was 98 at 0.10, against 209 at the default 0.5.

Does a larger C mean more or less regularisation, and what do you report from five fold scores of 0.56, 0.62, 0.47, 0.30 and 0.57?

Less: C is the inverse of the penalty's strength, so a smaller C is stronger. From the folds you report the mean and the spread, about 0.50 give or take 0.11, because one split of 800 rows can be lucky or unlucky.
