Review

The week's vector-database ideas on one page

Tuesday to Thursday built one idea three ways: texts turned into vectors, stored, then searched by meaning. This step puts those ideas side by side in the order an interviewer tends to ask about them. Each subsection names the day that taught it, so you can open that page for the full version.

What a vector database adds over a table you scan

Tuesday's page first stored each article's vector in a SQLite table and searched by reading every row, comparing the query's vector with each one. That is fine for thirty articles. It slows as the table grows, because every query has to touch every row. A vector database keeps each vector with its id and metadata and answers "which stored vectors are closest to this one?" in one call, with calls beside it to add, change, filter and delete records.

The week used two of them, and they differ mostly in where they run:

ChromaPinecone
Where it runsInside your Python process; PersistentClient saves to a local folder and loads it on start1A managed service on AWS, GCP and Azure, with writes and reads on separate paths that scale apart2
Records live inA collectionAn index, split into namespaces
A query reportsA distance: lower is closerA score: higher is closer
Needs a keyNoYes, read from Colab Secrets

In this week's notebooks neither database embeds anything: they store and compare the vectors you hand them. Pinecone's guide states the rule that follows. You embed each document before you upsert it and each query before you search, with the same model, and the index's dimension and metric match that model.3 The week's model, all-MiniLM-L6-v2, turns a text into 384 numbers and cuts any input longer than 256 word pieces, the chunks of words it reads.4

The same-model rule matters because its failure is quiet. A different model that also gives 384 numbers puts the query in a different space from the stored vectors. The call succeeds, results come back, and the nearest neighbours are near only by accident. A model with a different count fails loudly: on Wednesday, a 768-number vector sent to a 384-dimension collection was refused with an error.

add, update and upsert

Chroma's add needs a unique string id per record and documents, embeddings or both. Adding a record whose id already exists is ignored without an error.5 update on a missing id logs an error and skips that item, and upsert creates the ids that are missing and updates the ones that exist.6 The cell below uses vectors of two numbers so you can check every result by hand.

Run in Colab

%pip install -q chromadb==1.5.9
import chromadb

client = chromadb.Client()
# start from an empty collection, so the cell reruns
try:
    client.delete_collection("review")
except Exception:
    pass
col = client.create_collection(
    "review",
    embedding_function=None,
    configuration={"hnsw": {"space": "cosine"}},
)
col.add(ids=["a"], embeddings=[[1.0, 0.0]], documents=["first text"])
col.add(ids=["a"], embeddings=[[0.0, 1.0]], documents=["second text"])
print(col.count(), col.get(ids=["a"])["documents"])

col.upsert(ids=["a"], embeddings=[[0.0, 1.0]], documents=["second text"])
print(col.count(), col.get(ids=["a"])["documents"])
1 ['first text']
1 ['second text']

chromadb.Client() is the in-memory client, for experiments where nothing has to persist.1 The try block removes a review collection if one is already there, so the cell can run twice. embedding_function=None switches off Chroma's own embedding, which would otherwise embed any document sent without a vector.5 The configuration line picks the cosine space; the default is l2, and the space cannot be changed after the collection is created.7

The first line of output is the trap. The second add was skipped, the count stayed at 1 and the record still holds "first text", with nothing on screen to say so. The upsert replaced it. In Pinecone an upsert with an existing id overwrites the entire record, and one request carries up to 1,000 records and 2 MB.8

Distance against score

The interviewer's next question is usually "so is a bigger number better?" It depends on which database printed it. Run this in the next cell, after the one above:

col.upsert(ids=["b"], embeddings=[[0.6, 0.8]], documents=["third text"])
res = col.query(query_embeddings=[[1.0, 0.0]], n_results=2)
print(res["ids"][0], [round(d, 2) for d in res["distances"][0]])
['b', 'a'] [0.4, 1.0]

Chroma returns one list of results per query vector, so [0] picks the results for our single query. Work it by hand. Both vectors have length 1, so their cosine similarity is the dot product: 1 × 0.6 + 0 × 0.8 = 0.6. Chroma's cosine distance is 1 minus the similarity, so "b" sits at 0.4.7 Record "a" now points straight up, at right angles to the query: similarity 0, distance 1.

Pinecone reports the similarity itself. Cosine similarity runs from -1 to 1, where 1 means the two vectors point the same way, so the same two records would score 0.6 and 0.9 Down a Chroma results table the distance column rises; down a Pinecone table the score column falls. The rule of thumb for choosing a metric is the one the embedding model was trained with.9

Chroma takes a list of query vectors and a where filter; Pinecone takes one vector as a plain list, a namespace and a filter whose comparisons are spelled with operators such as $eq.

Namespace or metadata filter

Pinecone splits an index's records into namespaces, which are created automatically during upsert, and a query scans only its own namespace. Metadata is a flat JSON object of fields you filter on at query time, up to 40 KB per record, with no null values.3 Both give a way to keep one customer's articles apart from another's. A tenant is one customer whose data must stay apart from the others. Pinecone's guidance compares the two:

One namespace per tenantOne namespace, a metadata filter
IsolationPhysical: each tenant's records sit apartNone: every record shares the namespace
Query costScans only that tenant's recordsScans the whole namespace, so it costs more and takes longer
Search across tenantsNo: every operation targets one namespaceYes

Pinecone recommends one namespace per tenant and keeps the filter for cases where isolation is not strict or a search must cross tenants.10 Wednesday's web and mobile namespaces are the first shape, and {"product": {"$eq": "web"}} is the second. Pinecone does not allow a bare comparison operator at the top level of a filter.11 Chroma's where uses the same style of operators, such as $eq and $in.12

Takeaways
  • The same model embeds every stored text and every query, at the index's dimension.
  • Chroma's add skips an existing id without an error; upsert replaces it.
  • Chroma reports a distance, lower is closer; Pinecone reports a score, higher is closer.
  • A namespace isolates a tenant and scans less; a filter can cross tenants but scans everything.
Say it in an interview

A SQL table can hold vectors, but searching it means comparing the query with every row, so it slows as the data grows. A vector database stores each vector with its id and metadata and answers "what is closest to this?" in one call. I embed the documents and the queries with the same model, or the results are close only by accident.

In Chroma, add ignores an id that already exists without any error, so a correction silently never lands. Upsert creates the missing ids and replaces the existing ones, and in Pinecone an upsert overwrites the whole record.

For one index holding every customer's articles I'd give each customer a namespace. A query then reads only that customer's records and they're physically apart. A metadata filter only makes sense when isolation isn't strict or I need to search across customers, and it scans the whole namespace.

Presenting

Presenting a model to a mixed audience: the problem and the finding first

A model is finished when someone who did not build it can decide what to do with it. The rest of this page covers what to show, what to say about the numbers and what you will be asked.

Who is listening to a model talk

Week 5's showcase page set out the audience rule from Google's technical writing course: define the audience by role first, then by how close it is to the knowledge.13 A model talk stretches that distance further than a data talk. An engineer in the call knows what a validation set is, while a manager may never have seen what a model's output looks like.

The same course warns that an expert's understanding of a topic ruins their explanations to newcomers, and that the wider the audience, the more you must explain.13 After a week inside a notebook, words such as recall, epoch and threshold feel ordinary. To most listeners they are noise until you say what each one means for the decision. A mixed audience usually holds three kinds of listener:

  • a manager, who wants to know what the model is for and whether to trust it
  • an engineer, who wants to know how it was evaluated and whether it reruns
  • someone who knows the problem, such as a credit officer, who wants to know which mistakes it makes and how often

A slide flow that follows the listener

A first deck tends to follow the order of the notebook: data, cleaning, features, model, metrics. That is the order you built it in. The listener wants the order they would use it in, which starts with the problem and the answer. A flow that works for most model talks:

  1. The problem and who has it, in one line.
  2. The finding, as a sentence with one number in it.
  3. The data, and the baseline the model is compared against.
  4. The model, and the one choice that mattered most.
  5. The result, said in plain words, with the baseline beside it.
  6. What it gets wrong, from looking at the wrong predictions.
  7. The improvement you tried, and what it did to the number.
  8. The limits, and what would come next.

The method sits in the middle, short. The engineer will ask about it, and step 4 covers what they ask.

The finding as the title, one number per slide

The UK Government Analysis Function's chart guidance says a chart's title should communicate its headline message. Its test for a chart: if you cannot tell its message over the phone in a few sentences, rethink it.14 Penn State's assertion-evidence approach does the same for whole slides, building each one on a short sentence message rather than a topic phrase, backed by visual evidence rather than a bulleted list.15

Topic titleFinding title (illustrative)
ResultsThe model finds about 7 in 10 of the applicants who later default
Confusion matrixMost of its mistakes are good applicants flagged, not defaulters missed
Model comparisonThe larger network did no better than logistic regression

Each finding title carries one number or one direction, so a listener who reads only the titles still gets the argument. A results slide holds one number, said in words: "0.70 recall" becomes "finds 7 in 10 defaulters". Show a five-column table of metrics and the listener has to pick which number matters. Most will pick accuracy, because it is the one they recognise, and step 3 shows why that is often the wrong one.

Say what the model cannot do

Plain words cost precision. "Finds 7 in 10 defaulters" hides the good applicants wrongly flagged on the way. So the slide gives one number in plain words, and the notebook keeps the full table for the engineer's question. Overstating is the bigger risk. The Analysis Function's guidance says being upfront about limitations protects the integrity of the findings, while overstated certainty risks inappropriate decisions.16

The same guidance asks the analyst to explain how each limitation feeds through into the decisions users take.16 A limitation with its consequence attached reads like this: "It learned from 600 past applicants in one table and has not been checked on new ones, so it should advise a credit officer rather than decide alone." A listener can act on that sentence, where "The data has some limitations" gives them nothing.

Takeaways
  • Order the deck the way the listener uses it: problem and finding first, method short.
  • Title each slide with its finding, and give a results slide one number in plain words.
  • State each limitation with what it means for the decision to use the model.
Say it in an interview

For a manager I'd start with the problem and the answer, and keep the method short. Something like: the model flags applicants likely to default, and it finds about seven in ten of them, where the simplest rule finds none.

Then one limitation with its consequence, that it should support a credit officer rather than replace one, and I'd keep the full metrics table in the notebook for whoever asks.

Presenting

Metrics, curves and a confusion matrix for people who do not train models

Every listener asks some version of "how good is it?" A metric answers that only once you say what it counts. Monday's page computes the metrics on the credit table; this step is about saying them to someone who has never computed one.

The confusion matrix in two sentences

A confusion matrix sorts every prediction into four boxes: true positives, false positives, false negatives and true negatives.17 "Positive" means the class the model looks for, here an applicant who defaults, which is a quirk of the vocabulary: a positive is bad news. For a listener, give each box a plain name:

BoxPlain nameIn the credit example
True positiveCaughtDefaulted, and the model flagged them
False negativeMissedDefaulted, and the model let them through
False positiveFalse alarmRepaid, but the model flagged them
True negativeCorrectly clearedRepaid, and the model let them through

The cell below builds 200 illustrative predictions from counts, not from any notebook, and prints the matrix and three metrics. scikit-learn is preinstalled on Colab.

Run in Colab

import numpy as np
from sklearn.metrics import accuracy_score, confusion_matrix, precision_score, recall_score

# illustrative: 60 applicants defaulted (1), 140 repaid (0)
y_true = np.array([1] * 60 + [0] * 140)
y_pred = np.array([1] * 42 + [0] * 18 + [1] * 25 + [0] * 115)

print(confusion_matrix(y_true, y_pred, labels=[1, 0]))
print("recall   ", round(recall_score(y_true, y_pred), 2))
print("precision", round(precision_score(y_true, y_pred), 2))
print("accuracy ", round(accuracy_score(y_true, y_pred), 3))
[[ 42  18]
 [ 25 115]]
recall    0.7
precision 0.63
accuracy  0.785

labels=[1, 0] puts the defaulters first, so the top row is the 60 who defaulted (42 caught, 18 missed) and the bottom row is the 140 who repaid (25 flagged, 115 cleared). Recall is 42 / 60 = 0.70, the share of defaulters caught. Precision is 42 / (42 + 25) = 0.63, the share of flags that were right. Accuracy is (42 + 115) / 200 = 0.785.

Said to a manager, the whole matrix is two sentences. Of the 60 applicants who defaulted, the model caught 42 and missed 18. Of the 140 who repaid, it wrongly flagged 25 and cleared the rest.

Which number leads

Accuracy is the share of all predictions that were right. On a rare positive class, a model that always predicts negative can score 99% and still be useless.18 The same happens here on a smaller scale. A rule that approves everyone is right about all 140 who repaid, so it scores 140 / 200 = 0.70 and catches no defaulter at all. Against that, 0.785 sounds like a small gain, while recall went from 0 to 0.70.

Which metric leads depends on which mistake costs more. Recall matters most when a missed positive is the costly mistake, precision when a positive prediction has to be reliable.18 If a missed defaulter costs the lender more than a refused good applicant, recall leads the slide. If every flag triggered an expensive manual review, precision would.

The two move against each other through the threshold, the probability above which the model says "flag". Raising it generally lowers false positives and raises false negatives.17 For a listener: a stricter model flags fewer people, so it raises fewer false alarms and misses more defaulters.

Two curves on one chart

A network's training history is two curves: the loss on the examples it learns from, and the loss on the validation examples it never trains on. Week 7's plot_history(history, metric="loss") draws both on one chart. TensorFlow's overfitting tutorial reads them the same way you will be asked to: a lower validation loss means a better model.19

While both curves fall, the model is learning patterns that carry over to new applicants. When the validation curve turns up while the training curve keeps falling, the model has started to fit details of its own training rows that do not carry over, which is overfitting.19

For a listener, one sentence carries it: "after about epoch 20 it stopped getting better on applicants it had not seen, so I kept the earlier weights" (illustrative). Both curves belong on one chart because the gap between them is the evidence.

Takeaways
  • Name the four boxes caught, missed, false alarm and correctly cleared.
  • Accuracy flatters a model when one class is common; name the baseline beside it.
  • Recall leads when a miss costs more, precision when a false alarm does.
  • A validation curve rising while training keeps falling is overfitting.
Say it in an interview

A confusion matrix counts four kinds of outcome. In two sentences: of the 60 applicants who defaulted, the model caught 42 and missed 18; of the 140 who repaid, it wrongly flagged 25 and cleared the rest.

I wouldn't lead with accuracy on that data, because approving everyone already scores 70 percent and catches nobody. A missed defaulter is the costly mistake, so I lead with recall and give precision beside it, and I say that moving the threshold trades one against the other.

Presenting

What a reviewer asks about a model, and why

Four questions come up in almost every review of a model. Each one has a reason, and once you know the reason you know what a good answer has to contain. They map onto the parts of a model card, a short report on a model. It says how the model performs under varied conditions, including across relevant groups, the context it is meant for and how it was evaluated, so it is not used where it is poorly suited.20

QuestionWhy a reviewer asks itModel card part (closest)
What is the baseline?A score means nothing until it is compared with something simpler—
How was the test set kept apart?A test set that influenced the model gives a score that is too goodEvaluation procedure
What does it get wrong?An average hides which cases, and which people, pay for the mistakesPerformance under varied conditions
Would you ship it?It checks that you know what the model is for and where it stopsIntended use

What is the baseline?

scikit-learn's DummyClassifier makes predictions that ignore the input features and serves as a simple baseline to compare other classifiers against. With strategy="most_frequent" it always predicts the most common class.21 The cell loads Monday's credit table and splits it the week's way: 200 rows for test, then 200 of the remaining 800 for validation.

Run in Colab

from sklearn.datasets import fetch_openml
from sklearn.dummy import DummyClassifier
from sklearn.metrics import accuracy_score, recall_score
from sklearn.model_selection import train_test_split

RANDOM_STATE = 42
credit = fetch_openml("credit-g", version=1, as_frame=True).frame
y = (credit["class"] == "bad").astype(int)
X = credit.drop(columns=["class"])
X_trval, X_test, y_trval, y_test = train_test_split(X, y, test_size=0.2, stratify=y, random_state=RANDOM_STATE)
X_tr, X_val, y_tr, y_val = train_test_split(X_trval, y_trval, test_size=0.25, stratify=y_trval, random_state=RANDOM_STATE)

baseline = DummyClassifier(strategy="most_frequent").fit(X_tr, y_tr)
val_pred = baseline.predict(X_val)
print("val accuracy", round(accuracy_score(y_val, val_pred), 3))
print("val recall  ", round(recall_score(y_val, val_pred), 3))
val accuracy 0.7
val recall   0.0

y is 1 for an applicant who defaulted, so the most common class is 0 and the baseline approves everyone. It is fitted on X_tr and scored on X_val, never on the test rows. Its 0.7 accuracy is the 140 good applicants among the 200 validation rows, and its recall of 0.0 means it catches no defaulter. Any model you present has to clear both numbers, and a slide that shows 0.75 accuracy without this row invites the question.

TensorFlow's overfitting tutorial works the same way. It starts with a simple model of densely-connected layers as a baseline, then builds larger models and compares each one against it.19

How was the test set kept apart?

This question is about data leakage: using information that would not be available at prediction time, which gives over-optimistic scores. scikit-learn's guidance is blunt: test data should never be used to make choices about the model, you never call fit on it, and you split before any preprocessing.22 A good answer names the split, says where choices were made and says how often the test set was scored:

  • the split came first, before any scaling or encoding
  • every choice, from features to threshold, was made on the validation rows
  • the test set was scored once, at the end, by the model already chosen

Step 5 shows how to check your own notebook for each of these.

What does it get wrong, and would you ship it?

Error analysis means looking at the examples a model gets wrong and asking what they have in common. A reviewer asks for it because an average can hide a pattern. Eighteen missed defaulters is one number; eighteen missed defaulters who all asked for short, small loans is a finding about where the model fails (illustrative). The model card's call for performance across relevant groups asks the same of people.20

"Would you ship it?" checks whether you know the model's intended use and its limits. "Yes, it's 78 percent accurate" fails that check. A good answer says what the model is fit for now and what it would need before real customers: a check on new applicants, its performance across groups of applicants, and a person who reviews the flags.

The improvement that did not help

Many attempts to improve a model make it no better, and some make it worse. The common slip is leaving that out or spinning it. Report it as a row in the results table with one sentence on why. Owning a limitation protects the integrity of the rest of the findings.16

Model (illustrative)Validation recallValidation F1
Baseline, most frequent class0.000.00
Logistic regression0.700.62
Network with L2 regularisation0.660.60

The sentence for that last row: "The network with L2 reached 0.66 recall against 0.70 for logistic regression, so I kept logistic regression; the network's curves showed little overfitting for a penalty to fix."

Takeaways
  • A most-frequent baseline sets the floor every presented score must clear.
  • The test set answer names the split, where choices were made, and one final score.
  • An improvement that did not help goes in the table with one sentence on why.
Say it in an interview

The first thing I'd ask about any model is the baseline. A dummy model that always predicts the commonest class scored 70 percent accuracy on my validation rows and caught no defaulters, so a 75 percent model is barely better unless its recall says otherwise.

Yes, the failed improvement stays in the deck. I show it as a row next to the model I kept, say its recall came out a little lower, and give the reason I think it didn't help. It tells the reviewer the other numbers weren't picked to look good.

Project review

Project review: checking your own notebook before you present

Before anyone else reads your notebook, read it the way a reviewer will. Five checks catch most of what goes wrong between the last edit and the presentation:

  • Runtime, then Run all, on a fresh runtime, finishes without an edit
  • the test set is used once
  • the training and validation curves share one chart
  • the results table holds the improvement attempt as its own row
  • every number on a slide is printed by a cell

Run all on a fresh runtime

Colab deletes a virtual machine that has been idle for a while, and every machine has a maximum lifetime, in general at most 12 hours. Colab does not publish the exact limits, so a notebook has to carry the cells that reinstall its libraries and reload its data.23

A runtime you have used all day hides missing cells: a name you defined in a cell you later deleted still lives in memory, and the notebook works for you and fails for everyone else.

The test is a fresh runtime (Runtime, then Disconnect and delete runtime), then Runtime, then Run all, with no edits on the way. You can spot a notebook that was never rerun this way by its execution counts. Cells numbered [7], [3], [12] down the page were run out of order.

A rerun should also land on the same numbers. tf.keras.utils.set_random_seed sets the Python, NumPy and TensorFlow seeds in one call and can make almost any Keras program fully deterministic, with limits around some GPU operations.24

Run in Colab

import numpy as np
import tensorflow as tf

tf.keras.utils.set_random_seed(42)
print(np.random.rand(3).round(4))
tf.keras.utils.set_random_seed(42)
print(np.random.rand(3).round(4))
[0.3745 0.9507 0.732 ]
[0.3745 0.9507 0.732 ]

Each line draws three random numbers between 0 and 1. Because the seed is set again before the second draw, both lines match. That is why the seed call belongs at the top of the notebook: every shuffle, split and weight that follows starts from the same place on every Run all.

The test set used once

Two patterns give leakage away on sight. One is model.evaluate(X_test, y_test) appearing in several cells, each after a change. The other is a preprocessing step fitted before the split:

In the first version the scaler has seen the test rows before the model is scored on them, which breaks the rule to split before any preprocessing.22 In the second, the test rows are split off first, a second split carves the validation rows out of the rest (the same names as step 4's baseline cell), and every step of the pipeline learns from X_tr alone.

Cross-validation does not remove the need for a test set. scikit-learn says a test set should still be held out for final evaluation, and tuning settings until the test score is best lets knowledge of the test set leak into the model.25 Validation data has a quieter limit. Google's course says validation and test sets wear out with repeated use: each decision taken on the same rows tunes the model to them, leaving less confidence about new data.26

That explains a common surprise. Suppose validation recall was 0.70 and test recall is 0.65 (illustrative). Twenty choices made on the validation rows made 0.70 a little optimistic. The test score is the one to trust, so you report it, and you do not go back and tune until the test number rises.

Every number on a slide found in a cell

A slide number typed from an earlier run, rounded differently, or changed by a rerun without seeds, is the number a reviewer will ask about. Copy every number on a slide from the output of the final Run all, at the same rounding the cell prints. If a slide says "about 7 in 10", some cell prints 0.70. Keep both curves on one chart, since the reviewer reads overfitting from the gap between them.

Takeaways
  • Run all on a fresh runtime proves the notebook rebuilds its own state.
  • One seed call at the top makes a rerun land on the presented numbers.
  • Split first, fit on training rows, score the test set once.
  • Every slide number comes from a cell of the final run.
Say it in an interview

Before I share a notebook I delete the runtime, start a fresh one and run all with no edits. Colab throws runtimes away, so the notebook has to install and load everything itself, and the seed call at the top means the numbers come out the same as on my slides.

I split off the test set before any preprocessing, made every choice on the validation rows and scored the test set once at the end.

If the test score comes in a few points lower, that's the honest number. My validation score was a bit optimistic from all the choices I made on it, and I don't go back and tune on the test set.

Interview

Telling the project in an interview: situation, task, action, result

The showcase and the interview tell the same story to different listeners. "Tell me about a machine learning project you built" is a behavioural question, and week 5's showcase page introduced the shape that answers it. This step fits that shape to a model.

STAR with the time where it belongs

STAR splits an answer into Situation, Task, Action and Result. The University of Washington's career centre puts about 20% of the time on the situation, 10% on the task, 60% on the action and 10% on the result. The action is the steps you personally took, which it calls the most important part, and the result carries numbers where possible.27 For a two-minute answer that is 24 seconds, 12, 72 and 12.

PartShareFor a model project (illustrative)
SituationAbout 20%A table of past loan applicants, and a lender who wanted to know which new ones would default
TaskAbout 10%Build and evaluate a classifier on my own, then present it in under seven minutes
ActionAbout 60%Split first, set a baseline, chose recall because a missed defaulter costs more, tuned the threshold on validation, tried L2 and measured it
ResultAbout 10%Test recall of 0.65 against 0 for the baseline, and what it would need before real use

The common slip is a long situation and a short action: three minutes on the dataset and one sentence on the model. The action is where the interviewer learns how you think, so it gets the time. Each action names a choice and the reason for it.

"I", a number, and the follow-up

MIT's career office suggests preparing three to five stories as bullet notes, using "I" statements to show ownership, and not memorising scripts, which are hard to adapt and can sound unnatural.28 A project built alone makes "I" easy. The trap is the tutorial voice, "we then fit the model", which hides what you decided.

Amazon calls STAR the cornerstone of its interviews and asks for precise metrics and data that quantify your impact: "Don't just list what you did, but demonstrate the impact of your actions."29 For a model, the impact is a number against the baseline. "I trained a logistic regression" is an activity. "It caught 65% of defaulters on the test set, where approving everyone catches none" is a result.

The first answer is rarely the last. Google's structured-interviewing guide says interviewers plan follow-ups to draw out a high level of detail, and score every answer on a shared rubric of outstanding, solid, borderline and poor.30 Your story has to survive a second and a third question, so prepare the reason behind each action. The follow-ups a model story draws:

  • Walk me through one choice you made, and why.
  • Why that metric, and why that threshold?
  • What did the model get wrong?
  • What would you need before it was used on real customers?

The same guide separates behavioural questions, which ask about something you did, from hypothetical ones, which pose a job-related situation.30 The last follow-up above is hypothetical. The model card questions in step 4 answer it: checked on new applicants, measured across groups, and a person reviewing the flags.

Takeaways
  • STAR gives the action about 60% of the answer; the result ends on a number.
  • Say "I" for what you decided, and give each action its reason.
  • Prepare from bullet notes, and expect a second and third question.
Say it in an interview

I built a classifier that flags loan applicants likely to default. I split off a test set first, set a baseline that approves everyone, tuned on validation data and kept logistic regression. On the test set it caught about two thirds of defaulters, where the baseline caught none.

One choice was the metric. I led with recall rather than accuracy, because approving everyone already scores 70 percent accuracy, and a missed defaulter costs the lender more than a refused good applicant. Then I tuned the threshold on the validation rows, never on the test set.

The Project 1 showcase: what a strong 5 to 7 minutes holds

Each presentation is solo and runs 5 to 7 minutes with its question included; the table below spends a 6-minute slot.

The slot, minute by minute

Ten slides in six minutes leaves well under a minute a slide, and the question still has to fit. So the flow from step 2 stays, while the time goes to the results, the errors and the improvement. One way to spend a 6-minute slot:

TimeWhat it holds
0:00 to 0:30The problem, and the finding in one sentence
0:30 to 1:15The data and the baseline
1:15 to 2:00The model, and the one choice that mattered
2:00 to 3:30The result in plain words, the confusion matrix in two sentences, what it gets wrong
3:30 to 4:15The improvement attempt and its row in the table
4:15 to 4:45The limits, and what would come next
4:45 to 6:00One question

The usual way to lose the slot is to read ten slides aloud and reach the last one at seven minutes, with no time for the question. Rehearse twice against a clock, to the slot you were given, from bullet notes rather than a script. A memorised script cannot bend to the question asked.28

Sharing one screen on a call

Speaker notes are private notes attached to each slide, which you see and the audience does not. Google Slides shows them in presenter view, and pressing s during a presentation opens it. One limit matters on a call: you cannot use presenter view and full screen at the same time with one monitor.31 On a single laptop screen you choose between seeing your notes and filling the shared screen with the slide.

Decide which before your slot, and keep the bullet notes somewhere that is not the shared screen, such as paper beside the keyboard. Open the notebook in a second tab with its outputs showing, so a question about a number takes you straight to the cell that printed it. Sharing your screen once before you present catches the wrong window being shared.

One question, answered in two sentences

The Scrum Guide describes the Sprint Review, where a team shows its work to stakeholders, as a working session that the team should avoid limiting to a presentation.32 A showcase works the same way: the question is part of the review, and how you handle it counts as much as the slides. Answer in two sentences, the answer first, then the evidence or the limitation:

  • "Why not accuracy?" Approving everyone already scores 0.70 accuracy and catches no defaulter. Recall shows the model finds about two thirds of them, and the full table is in the notebook.
  • "Would you use it tomorrow?" Not on its own. It has only been scored on a held-out part of one historical table, so I would check it on new applicants and keep a person reviewing its flags.

If you do not know, say so in the first sentence and say how you would find out in the second.

Your repository is the part of the showcase that stays. A project folder a stranger can use opens with a README that states the problem, links the dataset, says how to run the notebook and shows the results table. Anyone who reads it after the call can check every number you said.

Takeaways
  • Spend the slot on results, errors and the improvement, and leave time for the question.
  • On one monitor, presenter view and full screen cannot run together.
  • Answer a question in two sentences: the answer, then the evidence or the limit.
Say it in an interview

Before real customers I'd want three things. I'd score it on applicants who came after the training data, check how it performs across different groups of applicants, and keep a person reviewing the flags at first. Until then it's a well-evaluated prototype rather than something I'd ship.

Weekly feedback form

Check yourself

Check yourself

Ten questions over the week and the showcase, at least one per section. Answer each out loud before you open it.

What does a vector database add over storing vectors in a SQL table and reading every row?

A table scan compares the query with every stored vector, so each search slows as the rows grow. A vector database keeps each vector with its id and metadata and answers "which stored vectors are closest to this one?" in one call, with calls to add, change, filter and delete records beside it.

What makes a slide title a finding title, and how many numbers does a results slide carry?

A finding title is a sentence that states the slide's message, with one number or one direction in it, so a listener who reads only the titles still gets the argument. A results slide carries one number, said in plain words, such as "finds about 7 in 10 defaulters".

You call Chroma's add with an id that is already stored. What happens, and what should you have called?

Chroma ignores the record without raising an error, so the stored version stays. upsert creates ids that are missing and updates those that exist; in Pinecone an upsert overwrites the whole record.

Chroma shows 0.4 for a result and Pinecone shows 0.6 for the same pair of vectors. Which is closer, and why do the numbers differ?

They describe the same closeness. Pinecone reports cosine similarity, where higher is closer, and Chroma reports cosine distance, 1 minus the similarity, where lower is closer: 1 − 0.6 = 0.4.

One Pinecone index holds every customer's articles. Namespaces or a metadata filter?

A namespace per customer: records are physically apart and a query scans only that customer's records. A filter suits cases where isolation is not strict or one search must cross customers, and it scans the whole namespace, which costs more and takes longer.

Explain a confusion matrix to a manager in two sentences, using 60 defaulters (42 caught) and 140 good applicants (25 flagged).

Of the 60 applicants who defaulted, the model caught 42 and missed 18. Of the 140 who repaid, it wrongly flagged 25 and cleared the other 115.

Why does a reviewer ask for the baseline, and what does a most-frequent baseline score on 140 good and 60 bad applicants?

A score means nothing until it is compared with something simpler. Always predicting "good" scores 140 / 200 = 0.70 accuracy and 0 recall, so a model at 0.75 accuracy is barely better unless its recall says otherwise.

Your test score is five points below your validation score. What does it tell you, and what do you not do next?

Many choices made on the validation rows wore them out, so the validation score was optimistic; the test score is the honest one and is the one you report. You do not tune until the test score rises, because that leaks the test set into the model.

In a two-minute STAR answer about your project, how long is the action, and what does the result end on?

About 60%, so roughly 72 seconds, naming the choices you made and why, in "I" statements. The result ends on a number from the notebook against the baseline, with the limit that matters.

You have one laptop screen and are sharing slides on a call. What can't you do, and how do you answer the one question?

Presenter view and full screen cannot run together on one monitor, so keep your bullet notes off the shared screen, for example on paper. Answer the question in two sentences: the answer first, then the evidence or the limit.
