Semantic search

Semantic search: matching meaning instead of words

A search box has two broad ways to decide which stored texts answer a query. Keyword search, also called lexical search, ranks texts by the words they share with the query. Semantic search ranks them by how close their meaning is, which it measures by comparing embeddings: lists of numbers a model computes for each text. A keyword engine can only find documents that match on words. Semantic search tries to match what the query means.1

Keywords against meaning

The example uses eight short invented sentences and one query, "my car will not start when it is freezing". Only one sentence is about that problem, and it shares no content word with the query. The first block also installs the two database clients Colab lacks, at the week's pinned versions, and defines encoder and embed, which every later example reuses. Run the page's cells in order in one Colab notebook.

On Colab, red ERROR: pip's dependency resolver text naming google-adk and tweepy is harmless: the installs still work. So is a warning about unauthenticated requests to the HF Hub.

Run in Colab

%pip install -q chromadb==1.5.9
%pip install -q pinecone==9.1.0
import numpy as np
from sentence_transformers import SentenceTransformer
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

encoder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

def embed(texts):
    return encoder.encode(texts, normalize_embeddings=True).astype("float32")

SENTENCES = [
    "The engine struggles to turn over on cold mornings.",
    "My phone battery dies before lunch.",
    "The dentist said I need a filling.",
    "Rocket launches are delayed when the wind is too strong.",
    "This recipe needs two cups of flour.",
    "When it is sunny, the park fills with families.",
    "I will not pay that parking ticket.",
    "The printer shows error code E-104 after every page.",
]
query = "my car will not start when it is freezing"

tfidf = TfidfVectorizer()
keyword_scores = cosine_similarity(tfidf.fit_transform(SENTENCES), tfidf.transform([query]))[:, 0]
meaning_scores = embed(SENTENCES) @ embed([query])[0]

print("keyword:", SENTENCES[keyword_scores.argmax()])
print("meaning:", SENTENCES[meaning_scores.argmax()])
print("engine sentence, keyword score:", round(float(keyword_scores[0]), 2))
keyword: When it is sunny, the park fills with families.
meaning: The engine struggles to turn over on cold mornings.
engine sentence, keyword score: 0.0

The keyword side is week 6's TF-IDF. fit_transform learns a vocabulary from the eight sentences and weights each word, and transform scores the query with that same vocabulary, so a query word the sentences never used counts for nothing.2 "Car", "start" and "freezing" appear in no sentence. What is left is "when it is" and "will not", so the sunny-park sentence wins at about 0.37 and the parking-ticket sentence comes second at about 0.35. The engine sentence scores exactly 0.

The meaning side turns every sentence and the query into 384 numbers with the MiniLM model and multiplies them with @, the dot product from Tuesday's page. Because embed scales every vector to length 1, that sum is the cosine similarity, where 1 means the same direction and 0 means unrelated.1

The engine sentence comes first at about 0.36, well ahead of the next at about 0.22. The model was trained on sentence pairs that mean the same thing, so "freezing" and "cold mornings", or "car will not start" and "engine struggles to turn over", land close.3

A score of 0.36 looks low, and it is not a percentage. What matters is the order and the gap: 0.36 against 0.22 is a clear first place. A short query against longer passages is what the Sentence Transformers docs call asymmetric search.1

Where keywords win

Meaning is a weakness when the query is an exact string. Lexical search suits specific terms like product codes, error strings and names, and semantic search suits an answer phrased in different words.4 Part numbers show it best. Three sentences say "Replacement filter part 7731-B fits the 2019 model.", the same with 7713-B and 2021, and with 1377-B and 2017, beside "Filters should be changed every six months." The query is just "7731-B".

Run in Colab

PARTS = [
    "Replacement filter part 7731-B fits the 2019 model.",
    "Replacement filter part 7713-B fits the 2021 model.",
    "Replacement filter part 1377-B fits the 2017 model.",
    "Filters should be changed every six months.",
]
tfidf_parts = TfidfVectorizer()
keyword = cosine_similarity(tfidf_parts.fit_transform(PARTS), tfidf_parts.transform(["7731-B"]))[:, 0]
meaning = embed(PARTS) @ embed(["7731-B"])[0]
print("keyword:", PARTS[keyword.argmax()])
print("meaning:", PARTS[meaning.argmax()])
keyword: Replacement filter part 7731-B fits the 2019 model.
meaning: Replacement filter part 7713-B fits the 2021 model.

TF-IDF scores only the exact part, at about 0.47, and gives every other sentence 0. MiniLM ranks the wrong part 7713-B first at about 0.23, just above the right one at about 0.21: to the model, two codes made of the same digits look nearly the same. One lone error code in a set is a weaker test, because with nothing similar around it the model finds it too.

Teams that need both run hybrid search: it combines two or more retrieval signals, a lexical one and a dense one, because each method misses what the others catch.4 In code, keyword search looks like TfidfVectorizer, or BM25 (another word-scoring formula, used by full-text search engines), followed by cosine_similarity; semantic search looks like encoder.encode(...) followed by a dot product or a vector database query.

The pipeline from raw posts to a search

A real search runs over a dataset, and several steps come before the first query works. The rest of this page follows them in order on 1,000 real forum posts:

  1. Load the posts and look at them.
  2. Prepare: choose the topics and how many posts to keep.
  3. Clean: fix whitespace, drop empty, short and duplicate posts, cut long ones.
  4. Tag entities: find the organisations, people and places each post names.
  5. Build metadata: the fields a search filters on and shows.
  6. Embed in batches: one vector per post.
  7. Build records, check them, and upsert them in batches.
  8. Query: a search function with filters, and a check that it is any good.

Retrieval for an LLM's answer reuses exactly this pipeline, and week 9 adds the model on top.

Takeaways
  • Keyword search ranks texts by shared words; semantic search ranks them by embedding closeness.
  • Semantic search finds paraphrases with no shared word; keyword search wins on exact codes and names.
  • Hybrid search merges both rankings so each catches what the other misses.
  • Before any search: load, prepare, clean, tag, build metadata, embed, check, upsert.
Say it in an interview

Keyword search matches the words in the query, so a TF-IDF search for "my car won't start when it's freezing" misses a sentence about an engine on cold mornings, because they share no content word. Semantic search embeds both with a model trained on paraphrases and compares the vectors, so it finds that sentence first.

Keywords still win on exact strings like part numbers, error codes and rare names, where a model sees 7731-B and 7713-B as nearly the same. When a product needs both, I'd run hybrid search and merge the two rankings.

Embedding models

Vector embedding models: what turns a text into 384 numbers

Tuesday's and Wednesday's pages used embed as a black box that turns a text into 384 numbers. This step opens it. An embedding model is the part of a vector database setup that produces every vector: the database stores and compares vectors, and the model decides what they mean.

What the model learned

The model is all-MiniLM-L6-v2, a sentence transformer: a model that turns a whole sentence or short passage into one fixed-length vector. It was trained by contrastive learning on over 1 billion sentence pairs: given one sentence, pick its true partner out of a random set. Texts that mean the same therefore end up with vectors that point the same way.3

Nobody told it that "freezing" relates to "cold". It learned that from pairs where those words played the same part.

Size, length limit and length-1 vectors

Three properties of a model set three choices in the database that stores its vectors. The example reads them from the loaded encoder.

Run in Colab

print(encoder.get_embedding_dimension(), encoder.max_seq_length)
v = embed(["The engine struggles to turn over on cold mornings."])
print(v.shape, v.dtype, round(float(np.linalg.norm(v[0])), 3))
384 256
(1, 384) float32 1.0
  • Output size: get_embedding_dimension() returns 384, so a Pinecone index for this model needs dimension=384.5 On Colab's sentence-transformers the old name get_sentence_embedding_dimension() still works but prints a FutureWarning saying it was renamed.6
  • Length limit: max_seq_length is 256 word pieces, the sub-word units the model reads. Longer inputs are truncated, with no error.5
  • How to compare: normalize_embeddings=True scales each vector to length 1, which the np.linalg.norm value of 1.0 confirms. A dot product of two length-1 vectors is their cosine similarity, so the database's metric is cosine.1

The shape (1, 384) is one row per input text and one column per number. encode always returns that two-dimensional shape for a list of texts, and its default is normalize_embeddings=False, which is why embed passes True.5 float32 means each number takes 4 bytes.

Two models compared

A bigger model is the obvious alternative. all-mpnet-base-v2 maps text to 768 numbers and reads up to 384 word pieces.7 The Sentence Transformers docs say it provides the best quality of their general models, while MiniLM is 5 times faster and still offers good quality.8

The storage row is plain arithmetic: 384 numbers × 4 bytes = 1,536 bytes, times a million is about 1.5 GB, before the index adds its own overhead. The timings come from one Colab CPU run, where mpnet was about six times slower; both models put the engine sentence first for the cold-morning query. For this data the bigger model doubles the storage and costs far more time without changing the top answer.

Choosing a model, and keeping it

A team weighs four things:

  • Quality on tasks like yours: the Sentence Transformers docs point to the MTEB leaderboard, which scores embedding models on retrieval, clustering, classification, reranking and similarity tasks.8910
  • Size: the index dimension and the bytes per vector.
  • Speed: the timing row of the table above.
  • The languages the model covers.

The model card on Hugging Face states the output size, the length limit and the training data. Hosted embedding services are the other route: an API computes the vectors and no model runs on your machine.

Whatever model you choose, the query vector must come from the same model used at upsert.11 A model with a different output size fails loudly, but a different model with the same size returns confident nonsense with no error, because its 384 numbers mean something else. Moving to a better model therefore means re-embedding every stored text.

Chroma can also run the model for you, through SentenceTransformerEmbeddingFunction from chromadb.utils.embedding_functions. It takes model_name (default "all-MiniLM-L6-v2"), device and normalize_embeddings (default False).12 Chroma's own default embedding function is the same MiniLM model.13 This page keeps embedding_function=None as Tuesday did and passes vectors from embed, so Chroma and Pinecone hold identical vectors.

Takeaways
  • An embedding model produces every vector; the database only stores and compares them.
  • Output size sets the index dimension, the length limit sets what is read, normalising sets cosine.
  • A bigger model costs storage and time; 768 numbers take twice the bytes of 384.
  • The same model must embed at upsert and at query time.
Say it in an interview

An embedding model turns text into a fixed-length vector, trained so texts that mean the same land close together. In a vector database it's the piece that gives the vectors their meaning: I embed every document at upsert and the query at search time, and the database finds the nearest vectors.

I check three things on the model card: the output size, which becomes the index dimension, the length limit, and the metric.

If we switch to a better model next month, every stored text has to be re-embedded. A query from the new model compared with vectors from the old one gives confident wrong answers.

Data preparation

Data preparation: loading and sampling real forum posts

Tuesday and Wednesday stored 36 help-centre articles written by hand, each one tidy. Real text is not. The rest of this page uses the 20 Newsgroups dataset: posts from 20 online discussion groups, 18,846 posts in all, which scikit-learn downloads with one function.14 Data preparation is the part before any cleaning: getting the texts into a table and deciding which of them to use.

Loading the posts

Four groups are enough to see whether a search separates topics: space, medicine, cars and computer graphics.

Run in Colab

import pandas as pd
from sklearn.datasets import fetch_20newsgroups

RANDOM_STATE = 42
TOPICS = ["sci.space", "sci.med", "rec.autos", "comp.graphics"]
raw = fetch_20newsgroups(subset="train", categories=TOPICS,
                         remove=("headers", "footers", "quotes"), random_state=RANDOM_STATE)
posts = pd.DataFrame({
    "post_id": range(len(raw.data)),
    "topic": [raw.target_names[i] for i in raw.target],
    "text": raw.data,
})
print(raw.target_names)
print(len(posts))
for topic, n in posts["topic"].value_counts().sort_index().items():
    print(topic, n)
['comp.graphics', 'rec.autos', 'sci.med', 'sci.space']
2365
comp.graphics 584
rec.autos 594
sci.med 594
sci.space 593

The arguments that matter:

  • subset="train" takes the training part of the set, which is also the default.14
  • categories keeps only the four groups, which gives 2,365 posts.
  • remove strips each post's headers, its footer (the signature block) and the lines quoted from earlier posts, so the text is what the writer added.14
  • random_state fixes the shuffle, which is on by default, so the posts come back in the same order on every run.14

The function returns a bunch, an object whose fields data, target, target_names and filenames are read with a dot.14 target holds a number per post, and target_names came back sorted alphabetically, not in the order of TOPICS. That is why the code looks each name up with raw.target_names[i] instead of assuming that 0 means "sci.space".

The topics are nearly equal in size, so none will crowd the others out of the results. Before writing any cleaning code, print two posts whole and read them: runs of blank lines, posts left almost empty by remove, and signatures the filter missed are what the next step fixes.

Choosing what to keep

The first choice, made before any vector exists, is a stable id for each document. post_id is the row's position at load, which is unique and stays the same on every run because the shuffle is fixed. A stable id matters later: writing the same id twice overwrites a record, while a new random id each run would pile up duplicates.

The second is the sample size: 250 posts per topic after cleaning, 1,000 in all. Tagging entities and embedding are the slow steps, and 1,000 posts keep every step fast enough to rerun from the top while you change it. The trade-off is that a sample may miss rare cases the full set holds, so a team runs the whole set only once the pipeline is right.

The label topic comes for free with the data. It becomes the first filter field in the metadata and the answer key when the search is checked at the end of the page.

Takeaways
  • Load the texts into a table with an id, a label and the text, then read some whole.
  • Topic names come from target_names by number, which is sorted alphabetically.
  • A stable id makes rewriting a record an overwrite instead of a duplicate.
  • Start with a sample so the slow steps can be rerun quickly.
Say it in an interview

Before building anything on a text dataset I load it into a table, count the rows per label and read a few documents whole, because that tells me what the cleaning has to fix. I give each document a stable id so a rerun overwrites records instead of duplicating them.

I start with a sample, here 1,000 of 18,846 posts, because entity tagging and embedding are slow and I want to rerun the whole pipeline in minutes while I get it right. Then I scale up.

Preprocessing

Data preprocessing: cleaning, dropping and cutting text

Preprocessing turns raw text into text worth embedding. A vector is only as good as the text behind it: an empty post still gets 384 numbers, and a search will happily return it.

Cleaning text

Forum posts carry line breaks, tabs and runs of spaces from the way they were typed. clean_text collapses every run of whitespace into one space and trims both ends.

Run in Colab

import re

def clean_text(s):
    return re.sub(r"\s+", " ", s).strip()

posts["text"] = posts["text"].map(clean_text)
print(f"empty {(posts['text'] == '').sum()}, under 100 characters {(posts['text'].str.len() < 100).sum()}")
empty 77, under 100 characters 220

re.sub replaces every match of a pattern, and \s+ means "one or more whitespace characters", so a blank line, a tab and three spaces all become one space. .strip() removes the whitespace left at the start and end. .map(clean_text) runs the function on every post in the column.

The printout reads: 77 of the 2,365 posts are now empty and 220 are under 100 characters, the 77 included. They were not empty to begin with. remove= stripped their quotes and signature, and some posts were nothing else. That filter is a guess, too: only the header filter follows an exact standard, and the docs warn that the others are not always correct.14 Signatures and e-mail addresses survive in some posts, and the NER helper step meets one.

Dropping short and duplicate posts

A post under 100 characters ("Thanks!", "Me too") says too little to be worth returning, and an exact duplicate would take two of the five result slots with the same text.

posts = posts[posts["text"].str.len() >= 100]

posts["text"].str.len() >= 100 gives True or False per row, and indexing the table with it keeps the True rows. drop_duplicates(subset="text") keeps the first of any rows whose text is identical. The worked number: 2,365 minus 220 short posts is 2,145, minus 3 duplicates is 2,142. Every topic keeps more than 500 posts, so 250 per topic fits.

Length: what the model actually reads

The last preparation step keeps 250 posts per topic and cuts every text to at most 1,000 characters.

Run in Colab

def cut(text, limit=1000):
    if len(text) <= limit:
        return text
    return text[:limit].rsplit(" ", 1)[0]

posts = posts.groupby("topic").head(250).reset_index(drop=True)
posts["text"] = posts["text"].map(cut)
print(len(posts), posts["text"].str.len().max() <= 1000)
1000 True

groupby("topic").head(250) keeps the first 250 rows of each topic, 1,000 in all. cut takes the first 1,000 characters, then rsplit(" ", 1)[0] splits once at the last space and keeps the left part, so no word is cut in half. Of the kept posts, 227 were longer than 1,000 characters, and the longest ran to 55,808.

The cut exists because of the model. MiniLM reads at most 256 word pieces and drops the rest with no error.35 A 55,808-character post would be embedded from its opening lines only. After the cut, the median post is about 129 word pieces, but 63 of the 1,000 still exceed 256, so the model trims those further. The 1,000 characters bound what is stored; they do not promise the model reads it all.

Nothing warns you: calling the tokenizer directly on a long post prints a message such as "Token indices sequence length is longer than the specified maximum sequence length for this model (393 > 256)", but encode itself truncates without a word.5 Splitting a long document into several chunks, each embedded on its own, is the usual fix, and week 9 teaches it.

Takeaways
  • Collapse whitespace first, then judge posts by their cleaned length.
  • Drop very short posts and exact duplicates before anything is embedded.
  • Header, footer and quote removal is a heuristic and leaves some signatures behind.
  • The model silently reads only the first 256 word pieces, so decide what it sees.
Say it in an interview

I normalise whitespace, then drop posts that are empty or under about 100 characters and exact duplicates, because an empty post still gets a vector and a duplicate wastes result slots. On the forum data that took 2,365 posts down to 2,142.

For a 55,000-character post the model reads only the first 256 word pieces and drops the rest silently, so I cut the text myself at a word boundary and know exactly what was embedded. For long documents the real fix is splitting into chunks.

NER

Named entity recognition: finding the names in a text

A user searching the forum may want "posts that mention NASA", which is a filter, not a similarity. To filter on it, every post needs a field listing the organisations it names. Named entity recognition, or NER, is a model that finds the names of real-world things in text and labels each one with its kind.

What NER finds

spaCy is a Python library for processing text, and en_core_web_sm is its small English pipeline, 12 MB, trained on a corpus called OntoNotes 5.15 Loading it gives a function, by convention named nlp, that turns a string into a Doc: the text split into words, with what each component found attached.

Run in Colab

import spacy

nlp = spacy.load("en_core_web_sm")
doc = nlp("NASA said Sally Ride trained in Houston before the shuttle flew from Florida.")
for ent in doc.ents:
    print(ent.text, ent.label_, spacy.explain(ent.label_))
NASA ORG Companies, agencies, institutions, etc.
Sally Ride PERSON People, including fictional
Houston GPE Countries, cities, states
Florida GPE Countries, cities, states

A named entity is a real-world object that is assigned a name, and doc.ents holds every one the model found as a span of the text. label_ is its kind as a short code, and spacy.explain turns the code into a description.16 Its NER component has 18 entity labels; the four this page keeps are:

  • ORG: companies, agencies, institutions.
  • PERSON: people, including fictional ones.
  • GPE: countries, cities and states.
  • LOC: other locations; with GPE it fills the page's places field.15

"Sally Ride" came back as one entity of two words, because NER finds spans, not single words. You recognise NER in code by spacy.load(...) followed by a loop over doc.ents that reads ent.text and ent.label_.

Where NER goes wrong on forum text

The model is statistical and strongly depends on the examples it was trained on.16 Even on test text like its training data, its published precision and recall are both about 84 in 100, so roughly one entity in six is missed or mislabelled.15 Forum posts are further from that data. On forum-style text it made mistakes such as:

  • "Ford Taurus", a car model, tagged ORG.
  • "BP" (blood pressure) and "MSG" tagged ORG.
  • An e-mail address from a signature, geb@cadre.dsl.pitt.edu, tagged ORG.

Run in Colab

doc = nlp("My Honda Civic broke down in Ottawa, so I called Bob at CAA.")
for ent in doc.ents:
    print(ent.text, ent.label_)
Honda ORG
Civic PRODUCT
Ottawa GPE

"Honda Civic" was split into a company and a product, and the person and the club were not found at all. None of this raises an error, and the output looks confident. Entity metadata therefore needs a look before it becomes a filter, and the next step shows the cost of skipping that look.

Takeaways
  • NER finds named spans in text and labels each one, such as ORG, PERSON or GPE.
  • doc.ents holds the spans; label_ is the kind; spacy.explain describes the label.
  • The model reflects its training text, so forum posts get wrong and missing labels.
Say it in an interview

Named entity recognition finds the names of real things in text, organisations, people and places, and labels each one. In spaCy I run en_core_web_sm on a text and read doc.ents. For a search index those entities become metadata, so a user can filter to posts that mention NASA.

I wouldn't trust it blindly. It's a statistical model trained on news-like text, so on forum posts it tags e-mail addresses and abbreviations as organisations and misses names. I'd look at the most common entities before using them as a filter.

NER helper

An NER helper function over many texts

Calling nlp once per post works for two sentences. For 1,000 posts a team wraps NER in one helper that takes a list of texts and returns one small dict per text, ready for the metadata step.

One fixed shape per text

Run in Colab

KEEP = {"ORG": "orgs", "PERSON": "people", "GPE": "places", "LOC": "places"}

def extract_entities(texts, batch_size=50):
    """One dict of orgs, people and places per text, deduplicated, at most 10 each."""
    results = []
    for doc in nlp.pipe(texts, batch_size=batch_size):
        found = {"orgs": [], "people": [], "places": []}
        for ent in doc.ents:
            key = KEEP.get(ent.label_)
            if key and ent.text not in found[key] and len(found[key]) < 10:
                found[key].append(ent.text)
        results.append(found)
    return results

for ents in extract_entities([
    "NASA said Sally Ride trained in Houston before the shuttle flew from Florida.",
    "My Honda Civic broke down in Ottawa, so I called Bob at CAA.",
]):
    print(ents)
{'orgs': ['NASA'], 'people': ['Sally Ride'], 'places': ['Houston', 'Florida']}
{'orgs': ['Honda'], 'people': [], 'places': ['Ottawa']}

The line doing the work is nlp.pipe(texts, batch_size=batch_size). It processes the texts as a stream in batches, which is usually more efficient than one call per text; batch_size is the number of texts it buffers at a time.1718 It yields one Doc per text in the order of the original texts, so result number 7 belongs to post number 7.18

KEEP maps each label worth keeping to a field, and any other label (Civic's PRODUCT) gets None from .get and is skipped. Three rules hold the shape fixed:

  • Every dict has all three keys, even when a list is empty, as in the second line's 'people': []. The next step can then read the same keys for every post.
  • A name is added once, in the order first seen, so a post that says "NASA" twelve times lists it once.
  • Each list stops at 10, so one long post cannot carry a huge field.

Run in Colab

A faster pipeline

Going deeper. NER needs only some of the pipeline's components, and the rest can be skipped. Passing disable=["parser", "lemmatizer"] to nlp.pipe skips the sentence parser and the word-root finder; a disabled component stays loaded but does not run, while an excluded one is never loaded.17

On our Colab run this cut the 1,000 posts from about 9.9 s to about 6.9 s, and 995 of them kept exactly the same organisations, so compare the output before switching. n_process spreads the work over several processes, but its start-up cost is high.17

Takeaways
  • nlp.pipe streams texts in batches and returns Docs in input order.
  • The helper returns the same three keys for every text, empty lists included.
  • Deduplicate and cap each list so one post cannot flood a field.
  • Read the most common entities per topic before using them as filters.
Say it in an interview

For a thousand texts I'd use spaCy's nlp.pipe with a batch size, which streams the texts through the model in batches and gives the docs back in the same order. I'd switch off components NER doesn't need, like the parser and lemmatizer, which cut about a third of the time.

The helper always returns the same keys, orgs, people and places, deduplicated and capped at ten, so the metadata step never has to guess.

Metadata

Metadata processing: what you filter on and what you show

Metadata is the small dict stored beside each vector. The help-centre articles of Tuesday and Wednesday carried category and product; this step designs the dict for the forum posts and shapes it so both databases accept it.

What goes in metadata

Every field earns its place in one of two ways:

  • Fields you filter on: topic, and the entity lists orgs, people and places, so a query can ask for space posts that mention NASA.
  • Fields you show: preview, the first 300 characters, and chars, the length, so a result can be displayed without a second lookup.

Everything else stays out. The full text, for example, lives with the originals and is found by id. Both databases cap a record: Pinecone allows at most 40 KB of metadata per record.1920 On the 1,000 posts the largest dict is about 870 bytes as JSON and the median about 388, far inside that.

Values a database refuses

Types are the other limit, and the two databases draw it in different places:

DatabaseAcceptsRefuses
Chromastrings, integers, floats, booleans, and a list of one of these, all the same type21None, an empty list, a list mixing types
Pineconestrings, numbers, booleans, and a list of strings19null

One shape, two filter spellings

The same dict goes to both databases. What differs is how a query asks "does this post's orgs list hold NASA?":

DatabaseFilterBehaviour
Chroma{"orgs": {"$contains": "NASA"}}$contains checks whether a metadata list includes a value22
Pinecone{"orgs": {"$in": ["NASA"]}}A filter on a list matches when any value in it satisfies the filter23

The operators do not carry over. In Chroma, $in against a list field matched nothing and raised no error. In Pinecone, a bare {"orgs": "NASA"} also works, but an array as a bare filter value is an HTTP 400 error, the server refusing a badly formed request.23 A post with no orgs key simply does not match an orgs filter.

In someone else's code, this design shows up as a metadata dict with a list field, such as {"topic": "sci.space", "orgs": ["NASA", "JPL"], "preview": ...}, queried with where={"orgs": {"$contains": "NASA"}} in Chroma or filter={"orgs": {"$in": ["NASA"]}} in Pinecone.

Takeaways
  • Metadata holds the fields you filter on and the fields you show, nothing more.
  • Chroma refuses empty and mixed lists; a None is refused, or dropped silently by upsert.
  • Leave out a key whose list is empty instead of writing an empty value.
  • Chroma filters a list with $contains, Pinecone with $in or a bare value.

I split metadata into fields I filter on, like topic and a list of organisations from NER, and fields I show, like a 300-character preview. The full text stays with the originals. Both databases cap metadata per record, Pinecone at 40 KB, so I keep it small.

Batches

Vector embedding in batches

With clean text and metadata ready, each post needs its vector. A batch is a group of texts the model processes in one pass; embedding in batches means feeding the posts through in groups of a fixed size.

Why batches

Three reasons, and they grow with the data:

  • Memory: the model works on one batch at a time, so its working memory stays the same however many texts there are; only the finished vectors grow, 1,536 bytes each.
  • Progress: a long run shows how far it has got.
  • Failure: if something breaks, one batch is lost, not the whole run.

Run in Colab

EMBED_BATCH = 64
texts = posts["text"].tolist()
start = time.time()
vectors = encoder.encode(texts, batch_size=EMBED_BATCH, normalize_embeddings=True,
                         show_progress_bar=True).astype("float32")
print(vectors.shape, vectors.dtype, f"{time.time() - start:.0f} s")

A progress bar counts the 16 batches (1,000 divided by 64, rounded up), then the line prints (1000, 384) float32 and the seconds taken. encode returns one row per input text and one column per number, and batch_size sets how many texts go through the model at once; its default is 32.5 show_progress_bar defaults to showing a bar only when logging is set to a detailed level, which is why the call passes True.5 Every row has length 1, ready for cosine.

Our Colab run took about 72 s at batch size 64. On a laptop, 8 against 64 hardly moved the time (about 33 s against 30 to 37 s over three runs); Colab did not time 8. batch_size can change speed and memory, and the vectors stay the same (next subsection).

The result is one sentence-level embedding per post, handed to the database as numbers. Chroma's bridge, SentenceTransformerEmbeddingFunction, would compute them inside the client instead.12

The same loop by hand

encode hides the loop. Writing it out shows what batching is: slices of 64 texts, each embedded, then stacked into one array.

Run in Colab

by_hand = np.vstack([embed(texts[i:i + EMBED_BATCH]) for i in range(0, len(texts), EMBED_BATCH)])
print(by_hand.shape, np.allclose(by_hand, vectors), np.allclose(by_hand, vectors, atol=1e-5))
(1000, 384) False True

range(0, len(texts), EMBED_BATCH) gives 0, 64, 128 and so on, and texts[i:i + 64] is the slice starting there; the last slice holds only the 40 posts left. np.vstack stacks the 16 small arrays into one of 1,000 rows. np.allclose asks whether two arrays are equal within a tolerance.

The answer is False at the default tolerance and True with atol=1e-5, that is, every number agrees to within 0.00001. The tiny difference comes from inside encode: it sorts the texts by length before cutting them into batches and pads each batch to its longest text, so the two runs group the posts differently.6 Search results are unaffected; only the last decimal places differ.

In someone else's code, batching shows up as encode(texts, batch_size=...), or as a loop over range(0, len(texts), N) whose slices are embedded and then joined with np.vstack.

Takeaways
  • Batches bound memory, show progress and limit what a failure loses.
  • encode returns a 1,000 by 384 float32 array for 1,000 texts.
  • Batch size changes speed and memory, not the meaning of the vectors.
  • Different batching gives differences only in the last decimal places.
Say it in an interview

I'd call the sentence-transformers model's encode with a batch size, say 64, normalised embeddings and a progress bar. Batches keep the model's working memory flat, show progress, and if something fails I lose one batch, not the run.

Batch size changes speed and memory, not the vectors. Two batching schemes can differ in the fifth decimal place, because encode sorts texts by length and pads each batch, so I compare them with a tolerance.

Upsert and query

Preparing for upsert and querying: from records to ranked results

Each post now has an id, a vector and a metadata dict. This step joins them into records, writes them in batches and searches them, in Chroma and then in Pinecone.

Records, and checks before writing

Run in Colab

UPSERT_BATCH = 100
records = [{"id": f"post-{row['post_id']}", "values": vec.tolist(), "metadata": meta}
           for row, vec, meta in zip(posts.to_dict("records"), vectors, metas)]

def check_records(records, dim=384):
    """Stop before writing if ids repeat, a vector has the wrong size or a value is None."""
    ids = [r["id"] for r in records]
    assert len(ids) == len(set(ids)), "duplicate ids"
    for r in records:
        assert len(r["values"]) == dim, f"{r['id']} has {len(r['values'])} numbers"
        assert None not in r["metadata"].values(), f"{r['id']} has a None"
    print(f"{len(records)} records OK")

check_records(records)
1000 records OK

A record is the dict Pinecone's client takes: id, values and metadata.24 vec.tolist() turns a numpy row into a plain list of numbers, because the pinned client cannot turn a numpy array into JSON and raises a TypeError ("Type is not JSON serializable") before any request is sent.25 assert stops the program with the message when its condition is false. Each check catches a mistake that would otherwise reach the database:

  • A repeated id would make one post overwrite another.
  • A vector of the wrong size means a different model, or a broken row.
  • A None would be refused by Pinecone halfway through the write, and dropped without a word by Chroma's upsert.

In an application the vector database is one tool among several. The originals stay in files or a SQL table keyed by the same id. The store holds the id, the vector and the metadata needed to filter and show. A search returns ids that lead back to the original, so the id joins the store to the source.

A search function with filters

Run in Colab

def chroma_hits(result):
    """A Chroma query result as a table: id, distance, topic, orgs, preview."""
    return pd.DataFrame([{"id": i, "distance": round(d, 3), "topic": m["topic"],
                          "orgs": m.get("orgs", []), "preview": m["preview"][:60]}
                         for i, d, m in zip(result["ids"][0], result["distances"][0], result["metadatas"][0])])

def search(query, top_k=5, topic=None, org=None):
    filters = ([{"topic": topic}] if topic else []) + ([{"orgs": {"$contains": org}}] if org else [])
    where = {"$and": filters} if len(filters) == 2 else (filters[0] if filters else None)
    result = posts_col.query(query_embeddings=embed([query]), n_results=top_k,
                             where=where, include=["distances", "metadatas"])
    return chroma_hits(result)

Check yourself

Nine questions, at least one per step. Answer each out loud before you open it.

Why does a TF-IDF search for "my car will not start when it is freezing" score the engine sentence 0, while MiniLM ranks it first?

TF-IDF scores only words the query shares with a text, and the engine sentence shares none. MiniLM was trained on sentence pairs that mean the same, so "freezing" and "cold mornings" land close, and the sentence comes first at about 0.36 against 0.22.

When does keyword search find the better result, and what does hybrid search add?

On exact strings such as part numbers, error codes and rare names: MiniLM ranked part 7713-B above the 7731-B that was asked for. Hybrid search runs both kinds and merges the rankings, so exact matches and paraphrases are both found.

You build a Pinecone index for all-mpnet-base-v2. What dimension does it need, and what goes wrong if queries are embedded with MiniLM?

768. MiniLM gives 384 numbers, so the query fails loudly on the size. A different model with the same size would fail silently instead, returning confident nonsense, which is why one model serves both upsert and query.

Why does the code look up each topic with raw.target_names[i] instead of using the order of TOPICS?

target_names comes back sorted alphabetically, so 0 means comp.graphics, not sci.space. Reading the name by number keeps every label right whatever order TOPICS was written in.

A post is 5,000 characters long. What does MiniLM embed of it, and what does the pipeline do about it?

Only the first 256 word pieces; the rest is dropped without an error. The pipeline cuts every post to 1,000 characters at a word boundary so it knows what was stored, and even then 63 of 1,000 posts are trimmed further. Splitting into chunks is the fuller fix.

What does NER find, and what is one mistake it makes on forum posts?

It finds named spans such as organisations, people and places and labels each one, for example NASA as ORG and Houston as GPE. On forum text it tagged an e-mail address from a signature as ORG, 27 times in the medical posts.

Why does make_metadata leave out a key whose list is empty?

Chroma refuses an empty list with a ValueError. A None is refused by Pinecone and by Chroma's add, and Chroma's upsert drops it silently. With 359 of 1,000 posts naming no organisation, writing "orgs": [] would fail the Chroma upsert; a missing key simply does not match an orgs filter.

Why embed 1,000 posts in batches, and does changing the batch size from 64 to 8 change the vectors?

Batches bound memory, show progress and limit a failure to one batch. Batch size changes speed and memory only; the vectors agree to within 0.00001, because encode sorts texts by length and pads each batch.

For one post, Chroma reports a distance of 0.36 and Pinecone, holding the same vector, a score. What score, and which list end is the best match in each?

About 0.64, since score = 1 − distance for cosine. Chroma's best match has the lowest distance and Pinecone's the highest score.
