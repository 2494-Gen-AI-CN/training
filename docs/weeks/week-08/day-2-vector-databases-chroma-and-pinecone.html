This page assumes Monday's numeric features and week 3's SQL. It turns whole texts into vectors of 384 numbers, compares them with cosine similarity, stores them in SQLite to show why a table stops scaling, and then uses two vector databases: Chroma inside a notebook and Pinecone in the cloud. Vectors

Vectors: a list of numbers that places a thing

A vector database stores vectors and finds the ones nearest to a question. Before the database comes the vector itself: what it is, and how two of them are compared.

A vector places a thing

A vector is an ordered list of numbers. Two numbers place a point on a flat page and three place it in a room. A list of 384 numbers places it in a space nobody can draw, but the arithmetic is the same at any length.

An embedding is a vector that represents a piece of data, such as a word, a film or a whole paragraph. The numbers are chosen so that things that are alike sit close together, which means the distance between two embeddings can be read as how alike the two things are. Google's machine-learning course shows this by placing foods as points such as (0.5, 0.3).1

Turning data into such numbers is called vectorising it, and it is what makes text or images readable by a program that only does arithmetic.

The smallest example is hand-made. Four films are scored from 0 to 10 on two invented features, action and romance, so each film becomes a vector of two numbers.

Run in Colab

import numpy as np

films = {
    "Star Run":     np.array([9, 1]),   # [action, romance]
    "Moon Base":    np.array([8, 2]),
    "Love Letters": np.array([1, 9]),
    "Paris Days":   np.array([2, 8]),
}
for name, v in films.items():
    print(f"{name:13} {v}")
Star Run      [9 1]
Moon Base     [8 2]
Love Letters  [1 9]
Paris Days    [2 8]

np.array makes a NumPy array, a list of numbers that supports arithmetic on the whole list at once. The dictionary maps each film's name to its vector, and {name:13} pads the name to 13 characters so the vectors line up. Drawn as points, the two action films sit together near the action axis and the two romance films near the other.

A hand-made vector carries only what its features say: these two numbers know nothing about a film's length or language. A learned embedding has hundreds of numbers, and none of them has a name, so a single number cannot be read alone; only the position as a whole means something.1

Cosine similarity, worked by hand

Cosine similarity measures how closely two vectors point the same way, ignoring how long they are. It is the dot product of the two vectors divided by the product of their lengths.2

  • The dot product multiplies the numbers in matching positions and adds the results.
  • A vector's length, or norm, is the square root of the sum of its squared numbers.
  • The result runs from -1 (opposite directions) through 0 (nothing in common) to 1 (the same direction).

Work two pairs by hand. For [3, 4] and [6, 8] the dot product is 3 × 6 + 4 × 8 = 50, and the lengths are 5 and 10, so the similarity is 50 / 50 = 1.0. The second vector is the first one doubled: longer, same direction, so it scores a perfect 1. For [3, 4] and [4, -3] the dot product is 12 - 12 = 0, so the similarity is 0.0. Those two point at right angles.

Run in Colab

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(cosine(np.array([3, 4]), np.array([6, 8])), cosine(np.array([3, 4]), np.array([4, -3])))
print(round(cosine(films["Star Run"], films["Moon Base"]), 2),
      round(cosine(films["Star Run"], films["Love Letters"]), 2))
1.0 0.0
0.99 0.22

The function is the formula line for line: np.dot is the dot product and np.linalg.norm is the length. NumPy agrees with the hand calculation, 1.0 and 0.0. Star Run and Moon Base score 0.99, nearly the same direction, while Star Run and Love Letters score only 0.22.

When every vector has length 1, the bottom of the fraction is 1 × 1, so the dot product alone is the cosine similarity. That is why the embedding code on the next step scales every vector to length 1 first.3 Week 6's k-means measured a different thing, the straight-line (Euclidean) distance between two points; Wednesday's page compares the two measures.

You recognise cosine similarity in someone else's code by np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)), or by a bare @ or np.dot between vectors that were normalised to length 1.

Takeaways
  • A vector is a list of numbers that places a thing as a point.
  • An embedding places alike things close together, so closeness reads as similarity.
  • Cosine similarity runs from -1 to 1 and ignores a vector's length.
  • For vectors of length 1, the dot product is the cosine similarity.
Say it in an interview

A vector embedding is a list of numbers that represents a piece of data, like a sentence or an image, as a point in space. The model that makes it places similar things close together, so a program can compare meaning with plain arithmetic. That's what makes text machine-readable for search.

To compare two embeddings I usually use cosine similarity: the dot product divided by the product of their lengths. It goes from -1 to 1, where 1 means the same direction, and it ignores length, so a vector and its double score exactly 1.

Similarity search

Vector similarity search: text in, nearest texts out

Vector similarity search finds the stored vectors closest to a query's vector and returns them in order, nearest first. It has two halves: turn every text into a vector with one model, then compare the query's vector with the stored ones.

A model turns text into 384 numbers

The model on this page is all-MiniLM-L6-v2 from the sentence-transformers library, which Colab ships. It maps a sentence or a short paragraph to a vector of 384 numbers and is built for search and for grouping similar texts.4 Input longer than 256 word pieces (the fragments of words the model reads) is cut off. Thursday's page opens the model up; here it is a black box, text in and 384 numbers out.

Run in Colab

from sentence_transformers import SentenceTransformer

encoder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

def embed(texts):
    return encoder.encode(texts, normalize_embeddings=True).astype("float32")

v = embed(["hello"])
print(v.shape)
print(np.round(v[0, :5], 3))
print(round(float(np.linalg.norm(v[0])), 3))
(1, 384)
[-0.063  0.055  0.052  0.086 -0.083]
1.0

The first run downloads the model's files from Hugging Face, a public site that hosts models. The work is done by encode, which returns one row per text, so one text gives the shape (1, 384). With normalize_embeddings=True every row is scaled to length 1, which the last line confirms, so a dot product of two rows is their cosine similarity.3 astype("float32") stores each number in 4 bytes, which matters when the vectors go into a file.

Search by comparing with every row

The data is a list of invented help-centre articles, one dictionary per article with six keys:

  • id and title;
  • text, one or two sentences: the part that is embedded;
  • category: account, billing, shipping or technical;
  • product: web or mobile;
  • updated: the year the article last changed.

The full set has 30 articles; this page keeps ten of them so every example fits on screen.

Run in Colab

kb_vectors = embed([a["text"] for a in KB])
query = "I can't get into my account"
query_vector = embed([query])[0]
scores = kb_vectors @ query_vector
print(kb_vectors.shape, query_vector.shape)
for i in np.argsort(-scores)[:3]:
    print(KB[i]["id"], f"{scores[i]:.2f}", KB[i]["title"])
(10, 384) (384,)
kb-001 0.46 Resetting a forgotten password
kb-004 0.33 Deleting your account
kb-005 0.32 Signing out on every device

embed([query])[0] embeds a list of one text and takes its only row, a vector of shape (384,). @ is matrix multiplication: each of the ten article rows is dotted with the query, giving ten scores. np.argsort returns positions from the smallest value to the largest, so negating the scores puts the largest first, and [:3] keeps three.5 Colab's NumPy has no descending= option yet, which is why the minus sign is there.

The top article is the password reset, and the query shares no word with its title or text. The model placed both texts near each other because they are about the same problem. Embedding the query and the stored texts into one space and returning the closest is exactly how the library describes this kind of search.6 Other queries from the full set of 30 behave the same way:

  • "my parcel never showed up" finds kb-015, "Tracking an order that has not arrived" (about 0.56).
  • "the app keeps closing by itself" finds kb-022, "Fixing crashes on phones" (about 0.50).
  • "how do I stop paying every month" finds kb-008, "Ending a plan" (about 0.55).

The query must go through the same embed as the articles. A vector only has a meaning next to vectors from the same model.

Reading the scores

The scores for related short texts sat between about 0.3 and 0.65, nowhere near 1.0. So the useful reading is the order and the gap: kb-001 at about 0.46 stands well clear of the next article at about 0.33.4 A fixed rule such as "only trust scores above 0.8" would throw away every good match here.

Similarity search also has no threshold built in. It returns the top results even when none of them is relevant, so a question about cooking still gets three help-centre articles back, and only the scores show it.7

The top k results are called the k nearest neighbours: the stored vectors with the highest similarity to the query. This page finds them by comparing with every row. A vector database answers the same question with an index, explained further down this page.

You recognise this search in code by query_vector = embed([query])[0], then scores = kb_vectors @ query_vector and np.argsort(-scores)[:3].

Takeaways
  • A model turns each text into 384 numbers of length 1.
  • Search embeds the query with the same model and compares it with every stored vector.
  • The nearest article can share no word with the query.
  • Read the order and the gap between scores; there is no built-in cut-off.
Say it in an interview

To vectorise text, I run every document through an embedding model, which gives each one a fixed-length vector, 384 numbers for MiniLM, normalised to length 1. At search time I embed the query with the same model, compare it with every stored vector by cosine similarity, and return the top few.

Vector similarity search means finding the stored vectors nearest to the query's vector and returning them nearest first. It finds matches that share no words with the query, but it always returns something, so I look at the scores and the gap, not just the top hit.

SQLite

Storing and retrieving vectors in SQLite

Before reaching for a vector database, try an ordinary one. SQLite is a whole database in one file with no separate server, and Python ships the sqlite3 module to use it, so week 3's SQL now runs from Python.8

A table with a vector column

A relational table has no vector type, but it can hold raw bytes. SQLite's BLOB column type stores bytes, which arrive in Python as a bytes value.8 A NumPy array's tobytes() copies its raw bytes, so each vector fits in one column.9

Run in Colab

import sqlite3

con = sqlite3.connect("kb.db")
con.execute("DROP TABLE IF EXISTS articles")
con.execute("""CREATE TABLE articles (id TEXT PRIMARY KEY, title TEXT, text TEXT,
               category TEXT, product TEXT, updated INTEGER, vector BLOB)""")
rows = [(a["id"], a["title"], a["text"], a["category"], a["product"], a["updated"], v.tobytes())
        for a, v in zip(KB, kb_vectors)]
con.executemany("INSERT INTO articles VALUES (?, ?, ?, ?, ?, ?, ?)", rows)
con.commit()
print(con.execute("SELECT COUNT(*) FROM articles").fetchone())
(10,)

connect opens the file kb.db, creating it if needed, and the DROP TABLE IF EXISTS line lets the cell run twice. zip pairs each article with its vector row. executemany runs the one INSERT once per row, and commit() saves the transaction the insert opened; without it the rows are lost when the connection closes.8 The count comes back as a one-item tuple, (10,).

Each ? is a placeholder. The values travel separately from the SQL text, so a value can never change the statement. Pasting values into the string with an f-string invites SQL injection, where a crafted value rewrites the query.8

Reading vectors back, and narrowing with WHERE

Reading a vector back is the reverse: np.frombuffer turns the bytes into an array. Its dtype defaults to float64, eight bytes per number, while the vectors were written as float32, four bytes per number.10

Run in Colab

blob = query_vector.tobytes()
print(len(blob), np.frombuffer(blob).shape, np.frombuffer(blob, dtype=np.float32).shape)
1536 (192,) (384,)

384 numbers × 4 bytes = 1,536 bytes. Read with the default type, those bytes become 192 meaningless numbers and no error is raised. With dtype=np.float32 the original 384 come back.

Run in Colab

ids, vectors = [], []
for id_, blob in con.execute("SELECT id, vector FROM articles"):
    ids.append(id_)
    vectors.append(np.frombuffer(blob, dtype=np.float32))
stored = np.vstack(vectors)
scores = stored @ query_vector
best = int(np.argmax(scores))
print(stored.shape, ids[best], round(float(scores[best]), 2))

print(con.execute("SELECT id, title FROM articles WHERE category = 'billing'").fetchall())
(10, 384) kb-001 0.46
[('kb-008', 'Ending a plan'), ('kb-009', 'Two entries for one purchase')]

The loop reads every row, np.vstack stacks the vectors into one 10-by-384 array, and np.argmax gives the position of the highest score. The answer matches the search on the previous step: kb-001 at 0.46. The last line uses a WHERE clause to narrow the rows to the two billing articles before any comparison. A vector database's metadata filter does the same job at scale; Wednesday's page adds its operators.

What happens at 50,000 rows

SQLite has no index for vectors. Every search reads every row and compares it in Python, so the time grows in step with the number of rows. This is called a brute-force search: exact, and slower with every row added.11

Run in Colab

import time

rng = np.random.default_rng(42)
big = rng.normal(size=(50_000, 384)).astype("float32")
big /= np.linalg.norm(big, axis=1, keepdims=True)    # every row to length 1
con.execute("DROP TABLE IF EXISTS scale_test")
con.execute("CREATE TABLE scale_test (id INTEGER PRIMARY KEY, vector BLOB)")
con.executemany("INSERT INTO scale_test VALUES (?, ?)", ((i, v.tobytes()) for i, v in enumerate(big)))
con.commit()

start = time.perf_counter()
best_score = max(float(np.frombuffer(blob, dtype=np.float32) @ query_vector)
                 for (blob,) in con.execute("SELECT vector FROM scale_test"))
print(f"{time.perf_counter() - start:.1f} s to read and compare 50,000 rows")
con.execute("DROP TABLE scale_test")
con.commit()
con.execute("VACUUM")                                # give the disk space back

np.random.default_rng(42) makes a random-number generator with a fixed seed, so every run draws the same numbers. normal(size=(50_000, 384)) draws a 50,000-by-384 array of random values; the underscore in 50_000 only separates the digits. axis=1 takes one length per row, and keepdims=True keeps the lengths as a 50,000-by-1 column, so each row is divided by its own length.

time.perf_counter() reads a clock, so the difference between two readings is the elapsed seconds. The timed part reads each blob, scores it and keeps the maximum. Each row comes back as a one-item tuple, so (blob,) unpacks the single column.

Our Colab run searched 50,000 rows in about 0.36 seconds. On a laptop, 50,000 rows took about 0.35 seconds and 100,000 about 0.66, so doubling the rows roughly doubles the time.11 Times vary by machine. The table makes the file about 103 MB, so the last lines drop it. A dropped table's space stays inside the file until VACUUM rebuilds it and gives the space back to the disk.

A fraction of a second is acceptable until every search pays it on millions of rows. Avoiding that full comparison is why vector databases exist.

You recognise vectors in a relational table by a vector BLOB column, a tobytes() in the insert, and np.frombuffer(blob, dtype=np.float32) on the way out.

Takeaways
  • A vector fits in a BLOB column as its raw bytes.
  • Read it back with dtype float32, or you get 192 wrong numbers.
  • Placeholders keep values apart from the SQL text.
  • Without a vector index, search time grows with every row.
Say it in an interview

I'd store each vector as bytes in a BLOB column next to its other fields, using tobytes on the way in and frombuffer with the right dtype on the way out. Inserts use placeholders, so values never become part of the SQL text and can't inject anything.

The catch is search. The table has no vector index, so every query reads every row and compares in Python. Double the rows and you roughly double the time, which is why at scale I'd move the vectors into a vector database.

Vector databases

Vector databases: what they add and where they are used

A vector database indexes and stores vector embeddings for fast retrieval and similarity search. A traditional database looks for rows whose values exactly match the query; a vector database applies a similarity measure to find the vectors most like the query's.11

What a vector database adds

Each addition answers something the SQLite table lacked.11

  • An approximate nearest-neighbour index finds vectors close to the query without comparing it with every stored vector. The best-known kind is HNSW, a graph that links nearby vectors, and it is the one Chroma builds.12
  • Metadata, such as an article's category, is stored with each vector and can filter a search.
  • Client libraries handle connecting, writing and querying, so no SQL or byte conversion is written by hand.

The index works like the SQL indexes from week 3. A B-tree index finds rows with an exact value without reading the whole table. An HNSW graph, the kind of index Chroma builds, finds vectors near a query vector without visiting every row, so both avoid the full scan.

"Approximate" is the trade: the index can miss a few of the true nearest neighbours, so it gives up a little recall (the share of true neighbours found) for a large gain in speed. Teams accept that because a near-perfect answer fast beats a perfect one after reading millions of rows. An HNSW index must also sit in memory to be queried or updated, so a single machine's RAM caps how large one Chroma collection can grow.12

Vector database use cases

Pinecone describes its own database as powering retrieval for applications "including search, recommendations, and long-term memory".18 The same pattern fits any app that finds "things like this one". For each, ask what the vectors are made from and what the metadata holds.

Week 7's recommender filled the blanks of a ratings table. A similarity recommender works differently: it finds items whose vectors sit near the ones a user already liked. A duplicate ticket is a new ticket whose vector sits very close to an open one.

Takeaways
  • A vector database adds an approximate nearest-neighbour index, metadata filters and client libraries.
  • Approximate indexes trade a little recall for a lot of speed.
  • Search, recommendations, duplicates and retrieval for language models all find near vectors.
  • Similarity says alike, so metadata filters handle dates, product and permissions.
Say it in an interview

A vector database stores embeddings with their metadata and finds the ones nearest to a query vector. A normal database matches exact values; a vector database ranks by similarity. It uses an approximate nearest-neighbour index such as HNSW, so it doesn't compare the query with every stored vector.

I wouldn't keep vectors in a plain SQL table at scale, because every search would read every row. The index gives up a little recall for a lot of speed, and the metadata lets me filter by things similarity can't judge, like dates or permissions.

Chroma setup

Chroma DB setup: install, clients and where the data lives

Chroma is the vector database that fits inside a notebook. It runs in the same Python process as your code, needs no account, and keeps its data in a folder, so it suits learning, prototypes and small apps. When several programs need the same data, the same Chroma runs as a server instead.

Installing Chroma in a notebook

Colab does not ship Chroma, so the notebook installs it with one pinned line. %pip is a notebook command that runs pip, Python's package installer, for the notebook's own Python. -q keeps the output short, and ==1.5.9 pins the version, so the calls on this page keep working when a newer release comes out.21

Run in Colab

%pip install -q chromadb==1.5.9
import chromadb
print(chromadb.__version__)
1.5.9

The install pulls in about fifteen packages Colab lacks. Checked against Colab's own package list, it adds new packages, upgrades three of Colab's own, and needed no runtime restart.22 Red ERROR: pip's dependency resolver text naming google-adk and tweepy, and an HF Hub warning about unauthenticated requests, are both harmless.

Clients: in memory or on disk

A client is the object your code talks to. Chroma's constructor decides where the data lives.23

ClientWhere the data livesAfter a restart
EphemeralClient()in memorygone
PersistentClient(path=...)a folder on diskstill there
HttpClient(host, port)a Chroma serverkept by the server

Run in Colab

import shutil

chromadb.api.client.SharedSystemClient.clear_system_cache()
shutil.rmtree("chroma_kb", ignore_errors=True)   # start from an empty store, so the notebook reruns from the top
scratch = chromadb.EphemeralClient()
client = chromadb.PersistentClient(path="chroma_kb")
print(client.heartbeat())

heartbeat() prints a 19-digit integer such as 1795553514122653035: the server's clock in nanoseconds. Its job is to prove the client is alive.23 PersistentClient stores its files in chroma_kb and loads them again when a new client opens that path.24 On Colab that folder survives a session restart but not a brand-new runtime.

The first two lines make the cell safe to run twice. shutil.rmtree deletes the folder. Chroma also caches one system per path for the life of the process, so without clear_system_cache() a second run reuses the stale one and fails with "Collection [kb_articles] already exists".25

Chroma's own store is SQLite again. Inside chroma_kb sits a chroma.sqlite3 file holding the documents and metadata, plus one folder per collection for its HNSW index.12 Its tables include collections and embeddings, but the layout may change between releases, so code never reads it directly.26

Chroma as a server: Docker, the cloud and HttpClient

An embedded client belongs to one program. To share one store between several programs, Chroma runs as a server: chroma run --path /db_path serves it on your own machine at port 8000 (a numbered door on the machine that a program listens on).27 Docker is a tool that runs a program packaged with everything it needs, called a container, and Chroma publishes one.

In a terminal on a machine with Docker (not Colab)

docker run -v ./chroma-data:/data -p 8000:8000 chromadb/chroma

-v ./chroma-data:/data maps a folder on the host into the container, so the data outlives the container. -p 8000:8000 opens port 8000 to the outside.28

A Python program that connects to it

client = chromadb.HttpClient(host="localhost", port=8000)

Only the constructor changes; every collection call stays the same. On a cloud machine, host is that machine's address.2728 You recognise the three set-ups by their constructors: PersistentClient(path=...) for a local folder, HttpClient(host=..., port=8000) for a server.

Takeaways
  • Chroma installs with one pinned pip line and runs inside the notebook.
  • EphemeralClient keeps data in memory; PersistentClient keeps it in a folder.
  • Chroma keeps documents and metadata in SQLite and each collection's index beside it.
  • As a server, in Docker or the cloud, programs connect with HttpClient.
Say it in an interview

Vector databases are the retrieval layer of an ML app: they hold the embeddings and find the nearest ones fast. Chroma is the lightweight end. I install it with pip and it runs inside my Python process, which is ideal for prototypes and small apps.

For storage I pick the client. EphemeralClient is in memory and gone on restart, which is fine for tests. PersistentClient writes to a folder, so the data survives. When several services need the same data, I run Chroma as a server, for example in Docker with a volume, and connect with HttpClient and the host and port.

Chroma

A local vector database with Chroma

A Chroma collection is a named set of records, roughly what a table is in SQL. Each record has an id, a document (the text), an embedding and metadata.

A collection with no embedding function

Chroma can embed text for you. A collection created without an embedding_function gets Chroma's default one, which runs its own copy of all-MiniLM-L6-v2 locally and downloads the model files on first use.29 Passing embedding_function=None switches that off, so the collection holds exactly the vectors embed made, and nothing is embedded behind your back.

The distance measure is set when the collection is created. The default is squared L2, a straight-line distance; configuration={"hnsw": {"space": "cosine"}} picks cosine.2

The four lists line up by position: the first id goes with the first document, vector and metadata. Three rules to watch for:

  • Allowed metadata values: a string, an integer, a float, a boolean, or a non-empty list of one of those.30
  • add with an id that already exists is ignored, with no error, and the old record stays.
  • A vector of the wrong length raises InvalidArgumentError: Collection expecting embedding with dimension of 384, got 10.

Because a skipped add is silent, count() is the check after every write.30

Query: the nearest neighbours and their distances

Run in Colab

import pandas as pd

def chroma_hits(result):
    """A Chroma query result as a table: id, distance, then the display fields."""
    rows = []
    for id_, dist, meta in zip(result["ids"][0], result["distances"][0], result["metadatas"][0]):
        rows.append({"id": id_, "distance": round(dist, 2), "title": meta["title"],
                     "category": meta["category"], "product": meta["product"]})
    return pd.DataFrame(rows)

result = collection.query(query_embeddings=[query_vector], n_results=3)

Pinecone overview

Pinecone: a managed vector database

Pinecone is a managed vector database: the index lives on Pinecone's servers, and your code reaches it over the internet with an API key. Its core features are the ones a vector database adds, an approximate nearest-neighbour index, metadata beside every vector and client libraries, run as a service with no server for your team to manage.11

Projects, indexes and records

Pinecone nests its objects four levels deep.33

  • An organization is your account, which owns projects.
  • A project holds indexes and the API keys that reach them.
  • An index holds the vectors, all of one length, compared with one metric.
  • A namespace splits an index into parts; Wednesday's page uses them.

Each record has an id, its values (the vector) and optional metadata that a query can filter on.20 It is a Chroma record without the separate document field.

A serverless index keeps its data in object storage, a cheap cloud file store, and runs writes and reads on separate paths. Reads also check an in-memory table of recent writes, so new data is searchable right after it is written. The cost is a "cold" read: a namespace nobody has queried lately is fetched from object storage on its first query, which is slower.33

In a retrieval workflow for a language model, Pinecone is the store the application searches for passages to hand the model; week 9 wires that up.19

The free Starter plan

Every example on this page runs on the free Starter plan. Its limits, as Pinecone's pricing page listed them when fetched on 2026-11-24, which the documentation's object limits repeat:3435

Units are how Pinecone counts work. A query costs 1 read unit per GB of namespace, with a minimum of 0.25. An upsert, update or delete costs 1 write unit per KB, with a minimum of 5 per request.37

Worked through for all 30 articles: each record is about 1.5 KB (384 numbers × 4 bytes, plus metadata), so one upsert costs about 50 write units, and ten queries about 2.5 read units. Both sit far inside the monthly allowance.

  • Pinecone is a managed vector database reached over the internet with a key.
  • An organization holds projects, projects hold indexes, indexes hold records.

Say it in an interview

Pinecone is a managed vector database. I create an index with a dimension and a metric, upsert records of id, vector and metadata, and query for the nearest ones. Over a traditional database it gives me similarity ranking, metadata filtering and scaling without running servers. In a RAG app it's the store I retrieve passages from before calling the language model.

Pod-based indexes are fixed hardware billed per minute whether used or not, and can be tuned for latency. Serverless scales itself and bills by reads, writes and storage, which is usually cheaper unless the load stays above roughly one query per second.

Pinecone setup

Pinecone setup: keys, permissions and an index

Setting up Pinecone takes an API key from the console, a safe place to keep it and the Python client. Then one call creates an index.

API keys and their permissions

An API key is a secret string that proves to Pinecone which project a request belongs to. You create one in the Pinecone console:41

  1. Open your project, then API keys, then "+ API key".
  2. Name the key, choose its permissions and press Create key.
  3. Copy the key at once: it is shown only this once and cannot be viewed again.

A key belongs to one project, and deleting it immediately disables every application that uses it. On a paid plan a key carries a role.4142

RoleWhat it may do
ProjectEditorread and write all resources and data
ProjectViewerread only
ControlPlaneEditor / Viewerindexes, backups and collections
DataPlaneEditor / Viewerrecords and namespaces

Least privilege means giving each program only what it needs: a read-only search service gets DataPlaneViewer. Starter keys can only have the All permission, so a free key can also create and delete indexes, and needs guarding.41

If a key leaks, delete it in the console straight away; applications using it get a 401 error (the server's "not authorised" answer) within seconds. Then create a new key and store it where the old one was. A planned rotation runs the other way round: create the replacement, switch to it, then delete the old key.43

CRUD

CRUD with vector data in Pinecone

CRUD is short for create, read, update and delete, the four basic operations on stored records. Pinecone's index object has a method for each, and every one takes keyword arguments only: a positional index.query(v, 3) raises a TypeError.49

Create: upsert the records

Run in Colab

import time

def wait_for_count(index, expected, namespace=None):
    """Poll the index stats every 2 seconds, for up to 60 seconds, until it holds `expected` vectors."""
    for _ in range(30):
        stats = index.describe_index_stats()
        if namespace is None:
            count = stats.total_vector_count
        else:
            ns = stats.namespaces.get(namespace)
            count = ns.vector_count if ns else 0
        if count == expected:
            break
        time.sleep(2)
    print(f"{count} vectors in the index")

records = [{"id": a["id"], "values": v.tolist(),
            "metadata": {"title": a["title"], "category": a["category"],
                         "product": a["product"], "updated": a["updated"]}}
           for a, v in zip(KB, kb_vectors)]
index.upsert(vectors=records)
wait_for_count(index, 10)
10 vectors in the index

Pinecone has no separate add: new records are written with upsert, and Wednesday's page shows what it does beyond adding. Each record is a dictionary of id, values and metadata. .tolist() matters: this client never converts NumPy, so an array in values raises TypeError: Type is not JSON serializable: numpy.float32.45 The metadata comes from the KB dictionaries, plain Python numbers, for the same reason.

Pinecone is eventually consistent: a count or a read can lag a write by a few seconds. Reading the stats straight after the upsert can show 0, which is why the helper polls instead of sleeping for a guessed time.50 On a test run the count was already complete straight away, but nothing guarantees that.

With namespace=None the helper reads the whole index's total_vector_count; given a namespace's name it reads that namespace's vector_count, which Wednesday's page uses. Records written without a namespace go to the default one, which the stats list under the key __default__.

Check yourself

Check yourself

Nine questions, one per section, asked the way an interviewer would. Answer each out loud before you open it.

What is a vector embedding, and what is the cosine similarity of [3, 4] and [6, 8]?

An embedding is a list of numbers that represents a piece of data as a point, placed so that alike things sit close together. The cosine similarity is 50 / (5 × 10) = 1.0: the second vector is the first one doubled, and cosine ignores length.

Walk through turning a text into a vector and searching with it.

Embed every stored text with one model, here 384 numbers of length 1 each. Embed the query with the same model, score it against every stored vector with a dot product, which equals the cosine similarity for unit vectors, and return the top few, nearest first.

How would you store a vector in SQLite, and why does search there slow down as the table grows?

As bytes in a BLOB column, written with tobytes() and read back with np.frombuffer(blob, dtype=np.float32), with ? placeholders in the insert. SQLite has no vector index, so every search reads and compares every row, and doubling the rows roughly doubles the time.

What is a vector database, and what does "approximate" in approximate nearest neighbour cost you?

A database that stores embeddings with metadata and finds those most similar to a query vector, using an index such as HNSW instead of a full scan. The index can miss a few true nearest neighbours, a little recall given up for a lot of speed.

When would you use EphemeralClient, PersistentClient and HttpClient in Chroma?

EphemeralClient for throwaway tests, since its data is gone on restart. PersistentClient when one program keeps its data in a folder. HttpClient when several programs share one Chroma server, for example one run in Docker.

A Chroma query returns a distance of 0.54 for the top article. Is that good, and what happens if you update a text without its embedding?

It is a cosine distance, 1 minus the similarity, so lower is closer and 0.54 means a similarity of about 0.46. On a collection with embedding_function=None the update raises a ValueError asking for an embedding function; on one with the default function, Chroma quietly embeds the text with its own model.

Compare pod-based and serverless Pinecone indexes for cost, latency and scale.

Pods are legacy hardware you choose, billed per minute whether used or not and scaled by hand, with types tuned for latency or throughput. Serverless scales itself and bills use, which is cheaper in most cases but dearer above about one query per second sustained; a cold namespace's first query is slower.

A teammate pushed a notebook with a Pinecone key in a cell to a public repository. What do you do, in order?

Delete the key in the Pinecone console at once, which cuts off every application using it within seconds. Create a new key, store it in Colab Secrets or an environment variable, and change the notebook to read it with userdata.get.

Why can describe_index_stats() show 0 right after an upsert, and what does Chroma's add do with an id that already exists?

Pinecone is eventually consistent, so counts lag a write by a few seconds; poll instead of writing again. Chroma's add skips an id that already exists without an error, and the old record stays.
